## 구현계획

### 배경

`@simplysm/angular`의 signal 기반 반응형 패턴과 Angular 내부 API 의존에서 발견된 3개의 Medium severity 이슈를 수정한다.

1. `setupRevealOnShow`의 effect가 어떤 signal도 추적하지 않아 `type` input 변경에 반응하지 않음 (LOGIC-034)
2. `injectParent`가 Angular 내부 `_lView[8]` 슬롯을 무검증 접근하여 버전 업그레이드 시 취약 (DESIGN-001)
3. `SdSheetConfigModal`의 `input.required()`가 Provider의 `setInput` 타이밍에 의존 (DESIGN-003)

### 목표

- `setupRevealOnShow`의 effect가 `type` signal 변경에 반응하도록 수정
- `injectParent`에 `lView[8]` 반환값의 컴포넌트 여부 검증 추가
- `SdModalProvider.showAsync`가 `input.required()` 모달을 에러 없이 여는 것을 테스트로 검증

### 비목표

- `enabled` signal을 tracked으로 변경 (D1에 의해 의도적 제외)
- `injectParent`의 Angular 내부 API 의존 자체를 제거 (대안 없음)
- `SdSheetConfigModal`을 optional input으로 변경 (D3에 의해 제외)

### 설계

#### setupRevealOnShow — computed를 통한 선택적 추적

`optFn()`이 type과 enabled 두 signal을 동시에 읽으므로, `computed`를 사용하여 type만 선택적으로 추적한다. `computed()`는 값이 실제로 변경될 때만 의존자에 통지하므로, enabled가 변경되어도 type이 같으면 effect가 재실행되지 않는다.

```typescript
const resolvedType = computed(() => optFn?.().type ?? "t2b");

effect((onCleanup) => {
  const el = elRef.nativeElement;
  const type = resolvedType();  // type 변경 시에만 effect 재실행
  // ... IntersectionObserver 설정
  // enabled는 observer 콜백 내에서 untracked로 읽기 유지
});
```

#### injectParent — 컴포넌트 인스턴스 검증

`lView[8]`이 컴포넌트가 아닌 객체(embedded view context 등)일 수 있으므로, 반환 전에 검증한다. Angular 컴포넌트는 class instance이므로 `constructor`가 `Object`가 아니다.

```typescript
const comp = lView[8];
if (comp == null || typeof comp !== "object" || comp.constructor === Object) {
  // embedded view context 등 — 건너뜀
  currentInjector = currentInjector.get(Injector, ...);
  continue;
}
```

#### SdSheetConfigModal — 타이밍 검증 테스트

기존 `SdModalTestBasic`이 이미 `input.required<string>()`을 사용하므로, 이를 활용하여 `showAsync` 호출 시 에러 없이 렌더링됨을 검증한다.

### 대안 검토

| 접근 방식 | 선택 여부 | 이유 |
|-----------|-----------|------|
| optFn의 untracked 제거 (둘 다 tracked) | 미채택 | enabled 변경 시 effect 재실행 → 이미 표시된 요소가 다시 숨겨지는 시각적 결함 |
| setupRevealOnShow API를 Signal 직접 수용으로 변경 | 미채택 | 소비자 API 변경이 필요하여 영향 범위 과대 |
| injectParent의 _lView 의존 자체 제거 | 미채택 | Angular가 공식 API로 부모 컴포넌트 접근을 제공하지 않음 |
| SdSheetConfigModal을 optional input으로 변경 | 미채택 | 모든 로직에 null 가드 필요, 복잡도 증가 (D3) |

#### Slice 1: setupRevealOnShow type signal 추적

- **구현 내용:** `setupRevealOnShow`에 `computed`를 도입하여 `type` signal 변경 시 effect가 재실행되도록 수정. `enabled`는 untracked 유지.
- **호출 그래프:**
  ```mermaid
  flowchart TD
    SDE[SdShowEffectDirective.constructor] --> SRO[setupRevealOnShow]
    SRO --> COMP["computed(() => optFn?.().type)"]
    SRO --> EFF[effect]
    EFF -->|reads| COMP
    EFF --> IO[new IntersectionObserver]
    IO -.->|intersect event| CB[observer callback]
    CB -->|untracked| OPT["optFn?.().enabled"]
  ```
- **Scenarios:**
  - Scenario: sdShowEffectType이 변경되면 transform 방향이 갱신된다
  - Scenario: sdShowEffectType이 변경되지 않으면 effect는 재실행되지 않는다
  - Scenario: 뷰포트 진입 시 enabled가 true이면 애니메이션 트랜지션이 적용된다
  - Scenario: 뷰포트 진입 시 enabled가 false이면 트랜지션 없이 스타일이 초기화된다

#### Slice 2: injectParent 컴포넌트 검증

- **구현 내용:** `lView[8]`에서 가져온 값이 컴포넌트 인스턴스(class instance)인지 검증하는 가드 추가. plain object, null, primitive는 건너뛰고 상위 인젝터 탐색 계속.
- **의존:** 없음
- **호출 그래프:**
  ```mermaid
  flowchart TD
    IP[injectParent] --> LOOP["while (currentInjector)"]
    LOOP --> LV["lView = injector._lView"]
    LV --> GUARD{"comp != null && typeof comp === 'object' && comp.constructor !== Object?"}
    GUARD -->|Yes| TC{type != null?}
    TC -->|Yes| INST{"comp instanceof type?"}
    INST -->|Yes| RET[return comp]
    INST -->|No| NEXT[next injector]
    TC -->|No| RET
    GUARD -->|No| NEXT
    NEXT --> LOOP
  ```
- **Scenarios:**
  - Scenario: type 인수 제공 시 매칭되는 부모를 반환한다
  - Scenario: type 인수 없이 호출 시 lView[8]이 유효한 컴포넌트가 아니면 건너뛴다
  - Scenario: Angular 버전 업그레이드로 CONTEXT 슬롯이 변경되면 에러 대신 안전 처리

#### Slice 3: Modal required input 타이밍 테스트
