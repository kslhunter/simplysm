## 구현계획

### 배경

`SdSharedDataProvider`는 서버-클라이언트 간 공유 데이터의 로드/동기화를 담당하는 추상 클래스다. `_loadAndListen`(초기 로드)은 에러 처리가 되어 있으나, `_onEvent`(이벤트 콜백)에는 catch가 누락되어 있다. 또한 부분 업데이트 시 key 타입 비교와 동시 로드 방지 로직이 부재하다.

### 목표

- `_onEvent`에서 getter 실패 시 unhandled promise rejection 방지
- 부분 업데이트 시 string/number key 혼재에도 정확한 매칭
- 동시 로드 요청 방지 및 완료 후 자동 재로드

### 비목표

- `_loadAndListen`의 기존 에러 처리 변경 (이미 정상 동작)
- `emitAsync`의 동작 변경
- 새로운 public API 추가

### 설계

#### _onEvent 에러 처리 (LOGIC-003)

기존 `try { ... } finally { ... }`에 `catch` 블록을 추가하여 `_loadAndListen`과 동일한 패턴으로 에러를 `_errorHandler.handleError()`로 라우팅한다.

#### key 타입 정규화 (LOGIC-012)

`_onEvent`의 부분 업데이트 경로에서 `changeKeys`와 `item.__valueKey`를 `String()` 변환 후 비교한다.

#### concurrent load 방지 (LOGIC-013)

`ISharedDataEntry`에 `isLoading` 플래그를 추가한다. `getHandle()`에서 `isLoading`이 true이면 `_loadAndListen`을 호출하지 않는다. `_loadAndListen`의 `.finally()` 블록에서 `needsReload`를 재확인하여 true이면 자동 재로드한다.

### 대안 검토

| 접근 방식 | 선택 여부 | 이유 |
|-----------|-----------|------|
| _onEvent 호출부(listener callback)에서 try-catch | 미채택 | _onEvent 자체에 catch 추가가 _loadAndListen과 패턴 일관성 유지 |
| key 비교 시 Number() 변환 | 미채택 | NaN 위험 (빈 문자열 등). String()이 안전 |
| concurrent load 시 AbortController로 이전 요청 취소 | 미채택 | getter()가 AbortSignal을 지원하지 않음. isLoading flag가 단순하고 충분 |

### Vertical Slices

- [x] Slice 1: _onEvent 에러 처리 + key 타입 정규화
- [x] Slice 2: concurrent load 방지

#### Slice 1: _onEvent 에러 처리 + key 타입 정규화

- **구현 내용:** `_onEvent` 메서드에 catch 블록 추가, 부분 업데이트의 key 비교를 String 변환으로 변경
- **호출 그래프:**
  ```mermaid
  flowchart TD
    LC[_loadAndListen] -.->|이벤트: SdSharedDataChangeEvent| OE[_onEvent]
    OE --> G[entry.info.getter]
    OE --> EH[_errorHandler.handleError]
  ```
- **Scenarios:**
  - Scenario: 이벤트 콜백에서 getter가 reject되면 에러 핸들러가 호출된다
  - Scenario: 이벤트 콜백에서 getter가 성공하면 기존 동작을 유지한다
  - Scenario: 서버 key가 string이고 클라이언트 key가 number일 때 매칭 성공
  - Scenario: 서버 key가 number이고 클라이언트 key가 string일 때 매칭 성공
  - Scenario: 동일 타입 key일 때 기존과 동일하게 매칭 성공

#### Slice 2: concurrent load 방지

- **구현 내용:** `ISharedDataEntry`에 `isLoading` 플래그 추가, `getHandle()`에서 isLoading 체크, `_loadAndListen()`에서 isLoading 관리 및 완료 후 needsReload 재확인
- **의존:** Slice 1 (Slice 1이 _onEvent의 catch를 추가해야 _loadAndListen의 finally 수정과 충돌하지 않음)
- **호출 그래프:**
  ```mermaid
  flowchart TD
    R[register] -->|needsReload=true| E[entry]
    GH[getHandle] -->|needsReload && !isLoading| LL[_loadAndListen]
    LL -->|isLoading=true| E
    LL -->|.finally| CHECK{needsReload?}
    CHECK -->|Yes| LL
    CHECK -->|No| DONE[isLoading=false]
  ```
- **Scenarios:**
  - Scenario: _loadAndListen 진행 중 getHandle 재호출 시 중복 로드가 발생하지 않는다
  - Scenario: _loadAndListen 완료 후 needsReload가 true이면 자동 재로드한다
