## 구현계획

### 배경

`esbuild-angular-compiler-plugin.ts`(Feature 1.1)는 `transformStylesheet` 콜백 옵션 slot을 제공하지만, SCSS 의존성의 `FileReferenceTracker` 등록과 SCSS 에러 수집 브릿징이 없다. `createClientTransformStylesheet`(`client-transform-stylesheet.ts`)는 이미 SCSS 컴파일, PostCSS 적용, 파일 캐시, 의존성 추적(`scssDependencies` Map), 에러 수집(`scssErrors` Array)을 완비하고 있다. Plugin과 이 인프라 사이의 브릿징만 추가하면 된다. [근거: `esbuild-angular-compiler-plugin.ts:32-37`, `client-transform-stylesheet.ts:57-59`]

### 목표

- `stylesheetDependencies` Map을 통해 SCSS 의존성을 `FileReferenceTracker`에 전달하여 증분 빌드 정확성 확보 [근거: Rule "stylesheetDependencies를 FileReferenceTracker에 등록"]
- `stylesheetErrors` Array를 통해 SCSS 에러를 esbuild 빌드 결과에 포함 [근거: Rule "stylesheetErrors를 esbuild PartialMessage로 변환"]
- 빌드 시작 시 에러 상태 리셋으로 stale 에러 방지 [근거: Rule "onStart 시작 시 stylesheetErrors를 리셋"]

### 비목표

- `createClientTransformStylesheet` 수정 (이미 완성) [근거: wbs 경계 — 기존 인프라 활용]
- `outputFiles/metafile` 생성 (sd-cli는 인라인 스타일 방식) [근거: D3]
- `esbuild-client-config.ts` 통합 (Feature 3.1) [근거: wbs 경계]
- `esbuild-scss-plugin.ts` 수정 (side-effect import용 별도 유지) [근거: wbs 경계]
- `FileReferenceTracker` 수정 (Feature 1.1에서 완성) [근거: D4]

### 대안 검토

1. **Plugin 내부에서 `createClientTransformStylesheet` 생성 vs 외부 주입**
   - 내부 생성: Plugin이 SCSS loadPaths, postcssPlugins 등의 설정을 받아야 함 → SCSS 인프라에 결합
   - 외부 주입: Plugin은 `transformStylesheet` 콜백만 받고, 의존성/에러는 공유 참조로 전달 → 느슨한 결합
   - **선택: 외부 주입** — Plugin의 단일 책임(AOT 컴파일 + esbuild 통합) 유지

2. **콜백 시그니처 변경 (의존성 반환 포함) vs 별도 Map 옵션**
   - 시그니처 변경: `transformStylesheet` → `{ content, dependencies }` 반환 → AngularCompiler 수정 필요
   - 별도 Map 옵션: 기존 시그니처 유지, `scssDependencies` Map 공유 → 변경 최소화
   - **선택: 별도 Map 옵션** — 기존 API 무변경, `createClientTransformStylesheet`와 직접 호환
