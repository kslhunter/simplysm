### 설계 결정

| # | 결정사항 | 선택 | 근거 |
|---|---------|------|------|
| D1 | 병렬화 전략 | `Promise.all`로 `changeInfos` 루프 병렬 | 배치 1회는 수백 건 이하로 제한적. p-limit 도입은 오버엔지니어링 |
| D2 | 동일 source의 multi-target 복사 | 내부 `sourceEntries` 루프는 순차 유지 | 한 `changedPath`의 복수 entry는 각기 다른 `actualTargetPath`이므로 충돌 없으나 I/O 안정성·단순성 우선 |
| D3 | `hasActualCopy` 집계 | 각 경로 처리 return flag → `some`으로 병합 | 공유 변수 race 방지 + 가독성 |
| D4 | 빈 `allWatchPaths` 로그 레벨 | `warn` | `entries.length > 0`이면 감시가 시작되지 않은 **비정상** 상황 |
| D5 | `readdir` 지연 방식 | `loadFilesField` 먼저 await → null이면 early return → 이후 `readdir` | 병렬 유지 + 조건부 skip은 복잡. 순차 분기가 단순 |
| D6 | `pathx.posix` 중복 제거 | `const key = entry.resolvedSourcePath` | `resolvedSourcePath`는 이미 `pathx.posixResolve` 결과로 POSIX(resolve-ts:185) |
| D7 | consola 경고 검증 | `vi.spyOn(consola, "withTag").mockReturnValue(mockLogger)` | 코드베이스 기존 관행 (check.spec.ts 등 다수) |
| D8 | `readdir` 호출 여부 검증 | `vi.spyOn(fs.promises, "readdir")` | 표준 Vitest 패턴, 테스트 자체는 readdir 미사용이므로 call count 검증 가능 |
| D9 | dispose 검증 방법 | `dispose()` 호출 → writeFile → 1.5초 대기 → `callCount === 0` | spec.ts 기존 패턴("files에 없는 파일" 테스트) 재활용 |

## 구현계획

### 배경

Feature 1.1에서 단일 `FsWatcher` + longest-prefix 매칭 구조로 리팩토링하였다. 최종 심층 리뷰(review.md)에서 Medium 1건(테스트 커버리지 부족) + Low 4건(성능·설계·일관성)이 도출되었다. 사용자 선택(B안)에 따라 5건 전부를 해소한다.

### 목표

- 명세 Gherkin의 6개 Scenario를 회귀 테스트로 고정 [근거: Rule "한 source…", "동일 source…", "files 필드…", "모든 변경이…", "소스 파일이…", "dispose 이후"]
- onChange 콜백의 내부 직렬화를 경로 단위 병렬로 전환하여 런타임 복사 지연 최소화 [근거: Rule "onChange 콜백은…"]
- `entries.length > 0`이지만 감시가 시작되지 않는 비정상 상황을 warn으로 가시화 [근거: Rule "모든 source가…"]
- `loadFilesField` null 시 `readdir` I/O 제거 [근거: Rule "loadFilesField…"]
- `pathx.posix` 중복 호출 제거 [근거: Rule "sourceMap 키는…"]

#### 1. PERF-001 onChange 병렬화 (`replace-deps.ts:269-315`)

**변경 전:**

```ts
watcher.onChange({ delay: 300 }, async (changeInfos) => {
  let hasActualCopy = false;
  for (const { path: changedPath } of changeInfos) {   // 순차
    const src = findSource(changedPath);
    if (src == null) continue;
    const sourceEntries = sourceMap.get(src)!;
    for (const e of sourceEntries) {                    // 순차 유지
      // ... access/stat/copy ...
      // hasActualCopy = true (부분 할당)
    }
  }
  if (hasActualCopy) options?.onChanged?.();
});
```

**변경 후:**

```ts
watcher.onChange({ delay: 300 }, async (changeInfos) => {
  const flags = await Promise.all(
    changeInfos.map(async ({ path: changedPath }) => {
      const src = findSource(changedPath);
      if (src == null) return false;
      const sourceEntries = sourceMap.get(src)!;
      let localActualCopy = false;
      for (const e of sourceEntries) {                   // 순차 유지 [D2]
        // ... access/stat/copy ...
        // localActualCopy = true (로컬)
      }
      return localActualCopy;
    }),
  );
  if (flags.some((f) => f)) options?.onChanged?.();      // [D3]
});
```

### 대안 검토

- **A. 병렬화에 `p-limit` 사용**: 동시 I/O 제한을 걸면 안전하나, 배치 1회의 변경 수가 수백 건 이하이므로 오버엔지니어링. 기각.
- **B. sourceEntries 루프도 병렬화**: 동일 changedPath의 여러 target을 병렬로 복사. 이득은 미미하고 destination 중복 시 race 리스크 발생 가능(현재 설계상 destination이 겹치진 않지만 안전 마진). 기각 [D2].
- **C. 빈 감시 대상 시 error 로그**: 비정상이지만 치명적이지 않으므로 warn이 적절. error는 과도. 기각.
- **D. readdir을 Promise.all 유지 + files null 시 결과 폐기**: 현재 방식. I/O 낭비. 기각.
- **E. 테스트를 별도 .acc.spec.ts로 분리**: 기존 파일이 acc 변형 없이 단일 spec.ts 구조이므로 일관성 유지를 위해 단일 파일 유지. 채택.
