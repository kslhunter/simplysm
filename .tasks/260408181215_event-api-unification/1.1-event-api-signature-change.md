```gherkin
Feature: 1.1 이벤트 API 시그니처 변경

  Background:
    Given service-* 패키지의 이벤트 시스템이 존재한다
    And 서비스 API는 getService<T>(name: string) 패턴을 사용한다

  Rule: 이벤트 API 시그니처는 서비스 API와 동일한 패턴을 따른다
    # 근거: 사용자 요청 "완전히 동일한 방식으로 통일"

    Scenario: 클라이언트에서 이벤트 리스너 등록
      Given 서버에 이벤트가 defineEvent<TInfo, TData>("EventName")으로 정의되어 있다
      And 클라이언트에서 import type으로 이벤트 타입을 가져온다
      When client.addListener<EventDef>("EventName", info, cb)을 호출한다
      Then info 파라미터는 EventDef["$info"] 타입으로 추론된다
      And cb의 data 파라미터는 EventDef["$data"] 타입으로 추론된다
      And 서버에 evt:add 메시지가 전송된다

    Scenario: 클라이언트에서 이벤트 발행
      Given 이벤트 리스너가 등록되어 있다
      When client.emitEvent<EventDef>("EventName", selector, data)를 호출한다
      Then selector의 item 파라미터는 EventDef["$info"] 타입으로 추론된다
      And data는 EventDef["$data"] 타입으로 추론된다

    Scenario: 서버에서 이벤트 발행
      When server.emitEvent<EventDef>("EventName", selector, data)를 호출한다
      Then 매칭되는 클라이언트에 evt:on 메시지가 전송된다

  Rule: 기존 값 기반 API(eventDef 인자)는 제거한다
    # 근거: "통일" 의도

    Scenario: 기존 eventDef 값 전달 시 컴파일 에러
      When addListener(eventDefValue, info, cb)를 호출한다
      Then TypeScript 컴파일 에러가 발생한다

  Rule: removeListener는 변경하지 않는다
    # 근거: 이미 key(string) 기반

    Scenario: 리스너 제거는 기존과 동일
      Given 리스너가 등록되어 key가 반환되었다
      When client.removeListener(key)를 호출한다
      Then 정상적으로 리스너가 제거된다
```

## 구현계획

### 배경

현재 이벤트 API는 `ServiceEventDef` 런타임 값을 첫 번째 인자로 받는다. 이로 인해 서버 패키지에서 `import type`으로만 이벤트를 공유할 수 없어, 서비스 호출과 이벤트 구독/발행의 패턴이 불일치한다. [근거: 사용자 요청]

### 목표

- 이벤트 API 시그니처를 `eventName: string` + 제네릭 `TEventDef`로 변경하여 서비스 API 패턴과 통일 [근거: Rule "이벤트 API 시그니처는 서비스 API와 동일한 패턴"]
- 소비앱에서 서버 이벤트를 `import type`으로 공유 가능하게 함

### 비목표

- 프로토콜 메시지 변경 [근거: wbs 경계 — 와이어 프로토콜은 이미 문자열 기반]
- `defineEvent()` 함수 변경 [근거: wbs 경계]

### 설계

**시그니처 변경 패턴 (Before → After):**

```typescript
// Before
addListener<TInfo, TData>(
  eventDef: ServiceEventDef<TInfo, TData>,
  info: TInfo,
  cb: (data: TData) => PromiseLike<void>,
): Promise<string>;

emit<TInfo, TData>(
  eventDef: ServiceEventDef<TInfo, TData>,
  infoSelector: (item: TInfo) => boolean,
  data: TData,
): Promise<void>;

// After
addListener<TEventDef extends ServiceEventDef>(
  eventName: string,
  info: TEventDef["$info"],
  cb: (data: TEventDef["$data"]) => PromiseLike<void>,
): Promise<string>;

emit<TEventDef extends ServiceEventDef>(
  eventName: string,
  infoSelector: (item: TEventDef["$info"]) => boolean,
  data: TEventDef["$data"],
): Promise<void>;
```

동일 패턴을 `ServiceClient`, `WebSocketHandler`, `ServiceServer`에도 적용.

**소비자 변경 패턴:**

```typescript
// Before
await client.addListener(SdSharedDataChangeEvent, { name, filter }, cb);
await client.emitEvent(SdSharedDataChangeEvent, selector, data);

// After
await client.addListener<typeof SdSharedDataChangeEvent>("SdSharedDataChange", { name, filter }, cb);
await client.emitEvent<typeof SdSharedDataChangeEvent>("SdSharedDataChange", selector, data);
```

### 대안 검토

| 대안 | 선택 여부 | 이유 |
|------|----------|------|
| 오버로드로 신/구 API 공존 | 기각 | "통일" 목표에 반하고 API 복잡도 증가 |
| 유틸리티 타입 `EventInfo<T>`, `EventData<T>` 추가 | 기각 | `ServiceEventDef["$info"]`/`["$data"]` 인덱스 접근으로 충분 |
