# Feature 1.1 sd-cli debug 로그 보강

## 참조 자료

### 대상 범위

sd-cli 패키지(`packages/sd-cli/src/`)의 workers, utils, engines, orchestrators 전체.

### 현황

- 기존 debug 로그: 일부 함수에만 시작/종료 존재
- 양호: `tsc-build.ts`, `engines/index.ts`
- 심각한 누락: `package-utils.ts`(10개 중 9개 함수), `ngtsc-build-core.ts`(9개 중 7개), `angular-compiler.ts`, 엔진 서브클래스(`TscEngine`, `NgtscEngine`, `ServerEsbuildEngine`)
- 공통 누락 패턴: lint 블록, FsWatcher 시작, onChange 핸들러 내부

### 로그 패턴 (기존 코드 기준)

- `logger.debug()` 사용
- 한국어 메시지: "빌드 시작", "빌드 완료" 등
- 패키지명 prefix: `[${info.name}]` 또는 `[${pkgName}]`

### 설계 결정

| # | 결정사항 | 선택 | 근거 |
|---|---------|------|------|
| D1 | 순수 유틸 함수(1~3줄 변환) 포함 여부 | 제외 | 로그 노이즈 방지, 핵심 흐름 파악에 집중 |
| D2 | for 루프 내 개별 항목 로그 여부 | 루프 전체만 (총 N건/완료) | 로그 폭주 방지, 항목 수 파악으로 충분 |

    Scenario: 순수 유틸 함수는 로그 대상에서 제외

      When debug 로그 추가 대상을 판단한다
      Then 해당 함수는 로그 대상에서 제외한다

  Rule: 주요 로직 블록에 시작/종료 debug 로그를 추가한다

    Scenario: lint 실행 블록에 로그 추가
      Given 워커 함수 내에 lint 실행 블록이 있다
      When debug 로그를 추가한다
      Then lint 시작 debug 로그를 출력한다
      And lint 완료 debug 로그를 출력한다

    Scenario: esbuild 빌드/리빌드 블록에 로그 추가
      Given esbuild.rebuild() 또는 esbuild.build() 호출이 있다
      When debug 로그를 추가한다
      Then esbuild 시작 debug 로그를 출력한다
      And esbuild 완료 debug 로그를 출력한다

    Scenario: FsWatcher 생성에 로그 추가
      Given FsWatcher를 생성하는 블록이 있다
      When debug 로그를 추가한다
      Then FsWatcher 시작 debug 로그를 출력한다

    Scenario: AngularCompiler 초기화에 로그 추가
      Given AngularCompiler를 초기화하는 블록이 있다
      When debug 로그를 추가한다
      Then 초기화 시작 debug 로그를 출력한다
      And 초기화 완료 debug 로그를 출력한다

      Given scss 파일 컴파일이나 dependency 처리 등 복수 항목을 순회하는 for 루프가 있다

      Then 루프 시작 시 총 항목 수를 포함한 로그를 출력한다
      And 루프 종료 시 완료 로그를 출력한다
      But 개별 항목에는 로그를 추가하지 않는다

  Rule: 기존 로그 패턴과 일관성을 유지한다

    Scenario: 한국어 메시지 패턴을 따른다
      Given 기존 debug 로그가 "빌드 시작", "빌드 완료" 등 한국어 메시지를 사용한다
      When 새 debug 로그를 추가한다
      Then 동일한 한국어 메시지 패턴을 따른다

    Scenario: 패키지명 prefix 패턴을 따른다
      Given 기존 로그가 "[패키지명]" prefix를 사용한다
      When 새 debug 로그를 추가한다
      Then 해당 파일의 기존 prefix 패턴을 동일하게 사용한다

    Scenario: logger.debug() 호출을 사용한다
      Given 기존 코드가 logger.debug()를 사용한다
      When 새 debug 로그를 추가한다
      Then 동일한 logger.debug() 호출을 사용한다

## 구현계획

### 배경

sd-cli의 `--debug` 모드에서 빌드/watch 흐름을 추적하기 위한 debug 로그가 일부 함수에만 존재한다. 모든 파일에 `consola.withTag()`로 logger가 이미 준비되어 있으므로, `logger.debug()` 호출만 추가하면 된다.

### 목표

- sd-cli의 모든 의미 있는 함수와 로직 블록에 시작/종료 debug 로그를 추가하여, `--debug` 실행 시 전체 흐름을 추적할 수 있게 한다

### 비목표

- performance.now() 기반 소요 시간 측정 (불필요)
- 순수 유틸 함수(1~3줄 변환)에 로그 추가 (D1)
- for 루프 개별 항목 로그 (D2)
- 기존 info/warn/error 레벨 로그 변경

### 설계

#### logger 접근 방식 (파일별)

| 파일 유형 | logger 변수 | 비고 |
|-----------|------------|------|
| workers/*.ts | `logger` (모듈 레벨) | `consola.withTag("sd:cli:*:worker")` |
| utils/*.ts | `logger` (모듈 레벨) | `consola.withTag("sd:cli:*")` |
| engines/BaseEngine.ts | `logger` (모듈 레벨) | `consola.withTag("sd:cli:engine")` |
| engines/ViteEngine.ts | `logger` (모듈 레벨) | `consola.withTag("sd:cli:engine:vite")` |
| engines/{Tsc,Ngtsc,ServerEsbuild}Engine.ts | 없음 → BaseEngine의 `logger` 사용 불가 | `consola.withTag()` 새로 추가 |
| orchestrators/*.ts | `this._logger` (인스턴스) | `consola.withTag("sd:cli:*")` |
| utils/rebuild-manager.ts | `this._logger` (인스턴스) | 생성자에서 주입 |
| utils/worker-events.ts | `workerEventsLogger` (모듈 레벨) | `consola.withTag("sd:cli:worker-events")` |

#### 엔진 서브클래스 logger 추가

TscEngine, NgtscEngine, ServerEsbuildEngine에는 logger가 없다. 각 파일에 `consola.withTag("sd:cli:engine:tsc")` 등을 추가한다.

#### 로그 메시지 규칙

- 시작: `logger.debug("X 시작")` 또는 `logger.debug("[패키지명] X 시작")`
- 종료: `logger.debug("X 완료")` 또는 `logger.debug("[패키지명] X 완료")`
- 루프: `logger.debug("X 처리 중 (N개)")` → `logger.debug("X 처리 완료")`
- 기존 패턴이 있는 파일에서는 해당 파일의 prefix 패턴을 따른다

#### 제외 대상 함수 (D1: 순수 유틸)

- `hasTemplateExtension()`, `createEnvBanner()`, `formatScssError()`, `buildScssLoadPaths()`
- `getTypesFromPackageJson()`, `toTypecheckEnvs()`, `getCompilerOptionsForEnv()`
- `isPortAvailable()`, `findAvailablePort()`

### 대안 검토

| 접근 방식 | 선택 여부 | 이유 |
|-----------|-----------|------|
| 각 파일에 `logger.debug()` 직접 추가 | 채택 | 가장 단순, 기존 패턴 그대로 |
| 데코레이터 패턴으로 자동 로깅 | 미채택 | 기존 코드가 데코레이터 미사용, 도입 비용 큼 |
| Proxy 기반 자동 로깅 | 미채택 | Chrome 61 호환성 이슈 (CLAUDE.md) — 단, 이 코드는 Node.js용이므로 기술적으로는 가능하나, 코드베이스 복잡도 증가 |
