## 구현계획

### 배경

`client.worker.ts`의 `startWatch` 함수(189-417줄)는 11개 설정 단계를 수행하면서 두 개의 대형 인라인 구조를 포함한다. 모듈 스코프에는 이미 `esbuildResult`, `devServer`, `hmrService` 등 per-session 가변 상태가 선언되어 있다. [근거: 코드 `client.worker.ts:62-66`]

### 목표

- `startWatch`의 설정 흐름(dist 초기화 → public 복사 → polyfills → dev server → HMR → esbuild context → watch → index.html 감시 → 이벤트)을 선형으로 읽을 수 있게 한다 [근거: Rule "추출 함수는 모듈 스코프에 배치"]
- 동작을 변경하지 않는다 [근거: Rule "동작은 추출 전후 동일"]

### 비목표

- `build` 함수 변경 [근거: wbs 경계]
- `stopWatch` 함수의 기존 로직 변경 [근거: wbs 경계]
- 새 테스트 추가 (기존 테스트 없음, 순수 리팩토링)

### 설계

1. **모듈 스코프 변수 추가** (line 62 부근): `lastMetafile`, `isInitialBuild`, `initialBuildResolve`를 기존 모듈 변수(`esbuildResult` 등) 아래에 선언 [근거: D1]

2. **`createSourceFileCachePlugin()` 함수** (모듈 스코프):
   - 반환: `esbuild.Plugin` (`name: "sd-build-start"`)
   - 내부에 `prevMtimes` Map을 클로저로 보유
   - `onStart`: watchFiles + typeScriptFileCache mtime 비교 → `esbuildResult.sourceFileCache.invalidate()` + `buildStart` 이벤트
   - `onEnd`: mtime 기록
   - 모듈 변수 접근: `esbuildResult`, `sender`, `isInitialBuild`

3. **`createDevBuildEndHandler(basePath, actualPort, outdir, entryNames, pkgDir)` 함수** (모듈 스코프):
   - 반환: `(result: esbuild.BuildResult) => Promise<void>`
   - index.html 재생성 + HMR 디스패치 + build 이벤트 + 초기 빌드 resolve + 에러 핸들링
   - 파라미터: `basePath: string`, `actualPort: number`, `outdir: string`, `entryNames: string[]`, `pkgDir: string`
   - 모듈 변수 접근: `lastMetafile`, `hmrService`, `sender`, `isInitialBuild`, `initialBuildResolve`

4. **`stopWatch` 확장**: 기존 정리 로직 뒤에 `lastMetafile = undefined`, `isInitialBuild = true`, `initialBuildResolve = undefined` 추가

5. **`startWatch` 축소**: 인라인 코드를 함수 호출로 대체
   ```typescript
   plugins: [createSourceFileCachePlugin()],
   onEnd: createDevBuildEndHandler(basePath, actualPort, outdir, entryNames, info.pkgDir),
   ```

### 대안 검토

- **상태 객체(DevWatchState) 전달**: 스코프가 명시적이나 기존 모듈 변수 패턴과 불일치. D1에서 기각.
