## 구현계획

### 배경

`createAngularCompilerPlugin().setup()` 내의 `onStart` 콜백이 ~205줄로, 7개 관심사를 인라인으로 포함한다. 상위 3개 큰 관심사를 `setup` 스코프의 이름 있는 함수로 추출하여 탐색 비용을 줄인다.

### 목표

- `onStart` 콜백을 ~70줄의 오케스트레이션 코드로 축소 [근거: Rule "추출 후 외부 동작이 변경되지 않아야 한다"]
- 증분 빌드, 첫 빌드, processWebWorker 각각을 독립 함수로 분리하여 관심사별 탐색 가능 [근거: Rule "추출 함수는 setup 스코프 내에 배치"]

### 비목표

- `onLoad`, `onEnd`, `onDispose` 핸들러 변경 [근거: wbs 경계]
- 파일 상단 유틸리티 함수 변경 [근거: wbs 경계]
- emit/diagnostics/stylesheet 브릿징 추출 — 각각 6~12줄로 추출 효과 미미 [근거: wbs 범위]

### 설계

3개 함수를 `setup` 스코프 내, `onStart` 호출 앞에 정의:

```typescript
// ── 서브함수: 증분 빌드 ──
async function handleIncrementalBuild(
  errors: esbuild.PartialMessage[],
  warnings: esbuild.PartialMessage[],
): Promise<void> { /* 316-383줄 로직 */ }

// ── 서브함수: 첫 빌드 ──
async function handleFirstBuild(): Promise<void> { /* 384-409줄 로직 */ }

// ── 서브함수: WebWorker 프로세서 생성 ──
function createWebWorkerProcessor(
  errors: esbuild.PartialMessage[],
  warnings: esbuild.PartialMessage[],
): (workerFile: string, containingFile: string) => string { /* 412-456줄 로직 → 내부 함수 반환 */ }
```

- `errors`/`warnings`: `onStart` 내 로컬 변수이므로 파라미터로 전달
- 나머지 클로저 변수: `setup` 스코프에서 직접 접근
- `handleIncrementalBuild`는 `angularCompiler.update()` 호출로 `async`

### 대안 검토

| 대안 | 미채택 이유 |
|------|------------|
| 클래스로 추출 | 단일 파일 내 리팩토링에 과도한 구조 변경. 기존 패턴(팩토리 함수 + 클로저)과 불일치 |
| 별도 파일로 추출 | 클로저 상태를 파라미터로 전달해야 하여 시그니처가 비대해짐 |
