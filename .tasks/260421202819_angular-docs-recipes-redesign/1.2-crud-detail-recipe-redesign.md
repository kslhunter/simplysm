## 구현계획

### 배경

현행 `crud-detail.md`는 "page + modal + control 3뷰 동시 지원 + 편집/저장 + 삭제/복구" 풀옵션 기준의 단일 완성 예제(§3, `crud-detail.md:39-462`)를 baseline으로 두고, 나머지 변형(§5 보조 기능 / §6 복합 상세)을 diff 형태로 서술한다. 이 구조는 LLM/개발자가 **단순 조회 상세 폼부터 시작**할 때도 풀옵션 §3에서 "뺄 것"을 추적해야 하는 부담을 강요한다. WBS Feature 1.2는 이를 "최소 뼈대(읽기 전용 상세 폼, page 뷰 전용) → 확장 누적" 구조로 재편하여 시작점을 최소로 낮추고, 필요한 확장만 선택적으로 얹는 조립 흐름을 확립한다. Feature 1.1(`crud-list.md` 재설계)이 완료된 상태이므로 하이브리드 표현 포맷·부록 A/B·MOVE 표식·이관 후보 목록 형식을 그대로 답습한다. [근거: wbs.md:5, wbs.md:126, Impact Mapping D2]

### 대안 검토

- **§3를 3뷰 풀옵션 그대로 두고 "최소 시작점 링크"만 추가** — 거절. WBS 목표는 §3 자체를 최소로 만드는 것. 풀옵션 §3을 두면 LLM이 여전히 풀옵션을 복사 시작점으로 사용. [근거: wbs.md:40]
- **최소 뼈대에 `injectViewTypeSignal`·`@if (viewType() === "page")` 분기 포함 (Feature 1.1과 일관)** — 거절. 사용자 재고 (결정 3): "최소뼈대면 viewType 안쓰는게 맞지 않나". MyInfoPage.ts 같은 page 전용 화면이 viewType 없이 동작. D7로 확정. [근거: 사용자 답변 2026-04-21]
- **최소 뼈대에서 lastModified 블록 제외 (확장 A로 이동)** — 거절. 사용자 재고 (결정 2): "A가 맞는거 같음". 조건부 렌더이므로 도메인에 필드 없어도 자동 숨김. D6으로 확정. [근거: 사용자 답변 2026-04-21]
- **확장 A~F 순수 연쇄 누적 (A→B→C→D→E→F 일방)** — 거절. 사용자 답변 (결정 1): "누적+분기 병행". C/D가 뷰 분기로 병행, E/F가 A에만 의존하는 구조가 실 사용 패턴에 맞음. D8로 확정.
- **확장 섹션을 diff patch 형식(± 기호)으로 표현** — 거절. Feature 1.1과 동일한 이유(주석 번호가 가독성 높음). [근거: Feature 1.1 대안 검토]
- **부록 A에 확장 E·F까지 누적** — 거절. 확장 E(보조 기능)은 도메인별 고유, 확장 F(복합 상세)는 하위 컬렉션 있는 화면에만 적용. 풀스택 합본에 포함하면 LLM이 모든 화면에 이를 복사하여 불필요한 기능 추가. A+B+C+D(3뷰 + 편집 + 삭제)가 "가장 일반적인 상세 폼"으로 적절. [근거: 설계 결정 D8 — 부록 A 기준 명시]
- **테스트 추가** — 거절. 설계 결정 D4로 명시적으로 배제. [근거: 사용자 답변 2026-04-21]
