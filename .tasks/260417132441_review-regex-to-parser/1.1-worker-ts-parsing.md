## 구현계획

### 배경

`findWorkerPatterns()`는 `acorn.parse()`로 JS AST를 생성하는데, acorn은 JavaScript 전용이라 TS 구문(`import type`, 타입 어노테이션 등)을 처리하지 못한다. 파싱 실패 시 `catch { return []; }`로 조용히 빈 배열을 반환하므로, `createWorkerBundlePlugin`의 onLoad 필터(`/\.[cm]?[jt]sx?$/`)로 들어오는 `.ts` 파일의 Worker 패턴이 **조용히 누락**된다 [근거: review.md LOGIC-001, `esbuild-worker-plugin.ts:46-54`].

실증 회귀: `packages/service-server/src/protocol/protocol-wrapper.ts:35-40`의 `import.meta.resolve("../workers/service-protocol.worker")` 호출이 번들 대상에서 누락된다. 동일 파일에 `import type { Bytes } from "@simplysm/core-common"` 등 TS 구문이 존재하기 때문이다 [근거: 사용자 검증].

### 목표

- TS(`.ts`/`.cts`/`.mts`) 파일에서도 Worker/SharedWorker 및 `import.meta.resolve` 패턴이 정확히 탐지·치환된다 [근거: Rule "TS 파일은 JS로 변환한 후 Worker 패턴을 탐지한다"]
- TS 변환 실패(실제 문법 오류)는 조용히 무시되지 않고 esbuild 에러로 보고된다 [근거: D2, Rule "TS 변환 실패는 errors에 보고한다"]
- JS 파일의 기존 동작과 모든 기존 테스트 20개는 그대로 유지된다 [근거: WBS 범위 "기존 테스트 통과 보장"]

### 비목표

- `.tsx`/`.jsx` 파일의 Worker 패턴 탐지 — 처리 경로에 해당 파일이 존재하지 않음 [근거: D1, WBS 제외사항]
- `bundleWorker()`, `processWorkerBundle()`, `findWorkerPatterns()` 내부 AST 순회 로직 변경 [근거: WBS 경계]
- `createWorkerBundlePlugin`의 onLoad 필터 패턴 (`/\.[cm]?[jt]sx?$/`) 변경 — 방어적으로 TSX/JSX도 매치 유지하되, 그 경로에서는 기존 acorn 직접 파싱 동작 (사실상 Worker 매칭 없음) [근거: D1]
- acorn → TypeScript-aware 파서(`acorn-typescript` 등) 교체 [근거: WBS 제외사항]

### 설계

**A. `transformWorkerPatterns()` 내부 TS 변환 분기** (`esbuild-worker-plugin.ts:209`)

```typescript
export function transformWorkerPatterns(
  content: string,
  filePath: string,
  build: esbuild.PluginBuild,
): TransformWorkerResult | undefined {
  // ① 사전 필터 — 원본 content 기준 (D3)
  if (!content.includes("Worker") && !content.includes("import.meta.resolve")) {
    return undefined;
  }

  // ② TS 변환 분기 (D1, D2)
  let effectiveContent = content;
  const errors: esbuild.PartialMessage[] = [];
  const warnings: esbuild.PartialMessage[] = [];

  if (/\.[cm]?ts$/.test(filePath)) {
    try {
      const transformed = build.esbuild.transformSync(content, {
        loader: "ts",
        sourcemap: false,
      });
      effectiveContent = transformed.code;
      warnings.push(...transformed.warnings);
    } catch (e) {
      const failure = e as { errors?: esbuild.PartialMessage[]; warnings?: esbuild.PartialMessage[] };
      return {
        contents: content,
        errors: failure.errors ?? [{ text: `TS transform failed: ${String(e)}`, location: null }],
        warnings: failure.warnings ?? [],
      };
    }
  }

  // ③ AST 기반 패턴 탐지 (변환된 JS로)
  const matches = findWorkerPatterns(effectiveContent);
  if (matches.length === 0) return undefined;

  // ④ 이후 processWorkerBundle + chunks 조립은 effectiveContent 기준으로 수행
  // (기존 content 참조를 effectiveContent로 일괄 치환)
}
```

기존 함수 내부에서 `content`로 참조되는 모든 부분(예: `match.existingOpts = content.slice(...)`, chunks 조립의 `content.slice(cursor, rep.start)`)을 `effectiveContent`로 일괄 치환한다 [근거: Rule "TS 파일은 JS로 변환한 후 Worker 패턴을 탐지한다"].

**B. `createWorkerBundlePlugin` onLoad loader 분기 변경** (`esbuild-worker-plugin.ts:369`)

```typescript
return {
  contents: result.contents,
  loader: /\.[cm]?tsx$/.test(args.path) || args.path.endsWith(".jsx")
    ? ("tsx" as const)   // .tsx/.jsx: 변환 안 함, esbuild가 JSX 처리
    : ("js" as const),   // .ts/.cts/.mts: transformSync로 변환됨, .js/.cjs/.mjs: 원본 JS
  errors: result.errors.length > 0 ? result.errors : undefined,
  warnings: result.warnings.length > 0 ? result.warnings : undefined,
};
```

현재 `/\.[cm]?tsx?$/.test(args.path) ? "ts" : "js"`에서 `.ts` 확장자도 "ts" 로더로 반환하던 것을, TS는 이미 JS로 변환되었으므로 "js"로 반환한다. TSX/JSX는 방어적으로 "tsx" 유지 [근거: D4].

**C. 테스트 보강** (`packages/sd-cli/tests/esbuild/esbuild-worker-plugin.spec.ts`)

- 신규 describe 블록: `describe("transformWorkerPatterns — TypeScript 파일 처리", () => { ... })`

- fixtures는 기존 `worker.js`, `node-worker.js` 재사용 가능 (filePath가 `.ts`여도 Worker 파일 자체는 `.js`이면 됨)
