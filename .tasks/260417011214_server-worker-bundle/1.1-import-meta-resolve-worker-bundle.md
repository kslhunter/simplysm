### 설계 결정

| # | 결정사항 | 선택 | 근거 |
|---|---------|------|------|
| D1 | Node.js Worker 번들 빌드 platform | 메인 빌드의 `build.initialOptions.platform`을 계승 | 서버 빌드(platform: "node")에서 감지된 Worker는 Node.js API를 사용하므로 platform: "node" 필요. 브라우저 Worker 패턴은 항상 `platform: "browser"`로 유지. |
| D2 | 경로 치환 방식 | `import.meta.resolve("path")` → `new URL("worker-HASH.js", import.meta.url).href` | `import.meta.resolve`는 `file://` URL을 반환. `new URL("relative", import.meta.url).href`도 동일하게 `file://` URL을 반환. `core-node/worker.ts:58`에서 `file://` 시작이면 `fileURLToPath`로 변환하므로 호환됨. |
| D3 | 감지 범위 | `import.meta.resolve("상대경로")` 패턴 전체를 감지 (Worker.create에 한정하지 않음) | minification 후 `Worker.create` 함수명이 변경될 수 있음. `import.meta.resolve`가 상대 경로와 함께 사용되면 번들 후 경로가 무효화되므로, Worker 여부와 무관하게 별도 번들 + 경로 치환이 올바른 처리. |

## 구현계획

### 배경

현재 `esbuild-worker-plugin.ts`는 브라우저 Worker 패턴(`new Worker(new URL("path", import.meta.url))`)만 감지한다. 서버 빌드에서 `@simplysm/service-server`의 `Worker.create(import.meta.resolve("../workers/service-protocol.worker"))` 패턴이 번들에 그대로 남지만 Worker 파일이 dist에 출력되지 않아 런타임 실패가 발생한다.

기존 `transformWorkerPatterns` 함수를 확장하여 `import.meta.resolve("상대경로")` 패턴도 감지하고, Worker 파일을 별도 번들로 빌드한 뒤 경로를 치환해야 한다.

### 목표

- `import.meta.resolve("상대경로")` 패턴을 감지하여 Worker 파일을 별도 번들로 빌드 [근거: Rule "import.meta.resolve 패턴 감지"]
- Node.js Worker는 메인 빌드의 platform을 계승하여 빌드 [근거: D1]
- `import.meta.resolve("path")`를 `new URL("worker-HASH.js", import.meta.url).href`로 치환 [근거: D2]
- 기존 브라우저 Worker 패턴 동작에 영향 없음 [근거: Rule "기존 동작 유지"]

### 비목표

- `import.meta.resolve`의 범용 처리 (절대 모듈 경로 등) [근거: wbs 제외사항]
- `@simplysm/core-node` Worker.create 구현 변경 [근거: wbs 제외사항]

### 설계

#### 새 정규식 추가

```typescript
// Node.js import.meta.resolve 패턴: import.meta.resolve("./relative/path")
// 상대 경로(./ 또는 ../)만 감지 — 절대 모듈 경로("some-package")는 무시
const NODE_WORKER_PATTERN =
  /\bimport\.meta\.resolve\s*\(\s*["'](\.\.?\/[^"']+)["']\s*\)/g;
```

캡처 그룹:
- Group 1: 상대 경로 (예: `"../workers/service-protocol.worker"`)

빠른 사전 필터: `content.includes("import.meta.resolve")` 추가 [근거: 기존 `content.includes("Worker")` 패턴과 동일한 최적화]

#### `bundleWebWorker` → `bundleWorker` 리네임 + platform 파라미터

```typescript
function bundleWorker(
  build: esbuild.PluginBuild,
  workerFile: string,
  platform: "browser" | "node" | "neutral",
): esbuild.BuildResult {
  // ...기존 로직 동일, platform 파라미터 사용
  return build.esbuild.buildSync({
    ...build.initialOptions,
    platform,
    // ... 나머지 동일
  });
}
```

[근거: D1 — 브라우저 Worker는 "browser", Node.js Worker는 메인 빌드의 platform 계승]

기존 브라우저 Worker 호출: `bundleWorker(build, fullWorkerPath, "browser")`
Node.js Worker 호출: `bundleWorker(build, fullWorkerPath, build.initialOptions.platform ?? "browser")`

#### `transformWorkerPatterns` 확장

기존 `WORKER_PATTERN` 처리 후, `NODE_WORKER_PATTERN`도 처리:

```typescript
// 사전 필터 확장
const hasBrowserWorker = content.includes("Worker") && WORKER_PATTERN.test(content);
if (hasBrowserWorker) WORKER_PATTERN.lastIndex = 0;

const hasNodeWorker = content.includes("import.meta.resolve") && NODE_WORKER_PATTERN.test(content);
if (hasNodeWorker) NODE_WORKER_PATTERN.lastIndex = 0;

if (!hasBrowserWorker && !hasNodeWorker) return undefined;

let transformed = content;

// 1. 기존 브라우저 Worker 패턴 처리 (동일)
if (hasBrowserWorker) {
  transformed = transformed.replace(WORKER_PATTERN, (match, ...) => {
    // 기존 로직 — bundleWorker(build, fullWorkerPath, "browser") 호출
  });
}

// 2. Node.js import.meta.resolve 패턴 처리
if (hasNodeWorker) {
  transformed = transformed.replace(NODE_WORKER_PATTERN, (match, resolvePath: string) => {
    const fullWorkerPath = path.resolve(containingDir, resolvePath);

    const workerResult = bundleWorker(
      build,
      fullWorkerPath,
      build.initialOptions.platform ?? "browser",
    );

    // 에러/경고/metafile/outputFiles 수집 — 기존과 동일

    // 경로 치환: new URL("worker-HASH.js", import.meta.url).href
    return `new URL("${workerCodePath}", import.meta.url).href`;
  });
}
```

[근거: D2 — `new URL("path", import.meta.url).href`는 `file://` URL 반환, `core-node/worker.ts:58` 호환]

#### 기존 테스트 영향

기존 브라우저 Worker 테스트는 `bundleWebWorker` → `bundleWorker` 리네임만 영향. 내부 함수이므로 외부 API 변경 없음.

### 대안 검토

| 접근 방식 | 장점 | 단점 | 선택하지 않은 이유 |
|-----------|------|------|-------------------|
| import.meta.resolve를 onResolve로 가로채기 | esbuild 파이프라인 활용 | esbuild가 import.meta.resolve를 플러그인 파이프라인으로 보내지 않음 | 기술적 불가 |
| Worker 파일을 esbuild external로 지정 + 별도 복사 | 단순 | 복사만으로는 Worker의 의존성이 해결되지 않음 (번들링 필요) | Worker 파일 내 import가 해석되지 않음 |
| service-server에서 import.meta.resolve 대신 __dirname 사용 | 라이브러리 수정 | ESM에서 __dirname 미지원, banner shim 필요, 라이브러리 API 변경 | wbs 제외사항 위반 |
