# Feature 1.1 dev 모드 서버 시작 순서 보장

## 참조 자료

### 문제 원인

v14 `DevWatchOrchestrator`에서 이벤트 기반 아키텍처로 전환하면서, 초기 빌드 시 서버가 클라이언트보다 먼저 빌드 완료되면 `batchComplete` → `_onDevBatchComplete` → `_restartServers()`가 즉시 트리거된다. 이 시점에 클라이언트 Vite dev server가 아직 시작되지 않아 `_getClientPort()`가 `undefined`를 반환하고, 서버에 클라이언트 proxy가 등록되지 않는다.

### 영향 받는 파일

- `packages/sd-cli/src/orchestrators/DevWatchOrchestrator.ts`

### v12 기존 동작 (정상)

`SdProjectBuildRunner.rebuild()` 내에서 초기/watch 모두 동일한 순차 흐름:
1. 모든 패키지 빌드 완료 (await)
2. 서버 재시작 (await `_restartServerAsync()`)
3. 클라이언트 distPath 수집 → `setPathProxy` 호출 (await)
4. URL 출력 (한 번)

참조: `D:\workspaces-12\simplysm\packages\sd-cli\src\pkg-builders\SdProjectBuildRunner.ts` 라인 151-273

### v14 현재 동작 (비정상)

- `batchComplete` 핸들러가 `initialize()`에서 등록되어 초기 빌드 중에도 동작 (라인 165)
- `_startServerRuntime()`이 fire-and-forget (`runtimeWorker.start().catch()`)
- URL 출력 경로 3곳: `_startDevMode()` 라인 423 직접 호출, `_restartServers()` 라인 467, `serverReady` 이벤트 라인 526

### 설계 결정

| # | 결정사항 | 선택 | 근거 |
|---|---------|------|------|
| D1 | 초기 빌드와 watch의 서버 시작 흐름 분리 여부 | 분리 | 초기 빌드에서는 `_startDevMode()`가 모든 엔진 준비 후 서버 시작, watch에서는 기존 `batchComplete` 이벤트 경로 유지 |
| D2 | URL 출력 경로 통일 | `serverReady` 이벤트 단일 경로 | `_startDevMode()` 직접 호출과 `_restartServers()` 끝의 호출 제거 |
| D3 | `_restartServers()` 끝의 `_schedulePrintServers()` 제거 | 제거 | 서버 ready 전에 호출되어 불필요한 출력 발생. watch 모드에서도 동일 개선 효과 |

## 구현계획

### 배경

`DevWatchOrchestrator._startDevMode()`에서 서버/클라이언트 엔진의 `startWatch()`를 병렬 실행하는데, `batchComplete` 이벤트 핸들러가 `initialize()`에서 이미 등록되어 있어 서버 빌드 완료 즉시 서버 런타임이 시작된다. v12에서는 단일 `rebuild()` 루프 안에서 모든 빌드 완료 → 서버 시작 → proxy → URL 순차 처리를 보장했다.

### 목표

- 초기 빌드 시 모든 엔진 `startWatch()` 완료 후 서버 런타임 시작 (클라이언트 포트 확보 보장)
- URL 출력을 `serverReady` 이벤트 단일 경로로 통일
- watch 모드는 기존 `batchComplete` 이벤트 기반 동작 유지

### 비목표

- `_startServerRuntime()`의 fire-and-forget 구조 변경 (현 구조 유지)
- watch 모드에서의 `_onDevBatchComplete` 로직 변경

### 설계

#### `_startDevMode()` 수정

```
1. 모든 엔진 startWatch() 병렬 실행 → await Promise.allSettled()
2. 독립 클라이언트 resultCollector 등록 (기존 동일)
3. Capacitor 초기화 (기존 동일)
4. printErrors()
5. _restartServers()  ← 새로 추가 (클라이언트 포트 확보 보장)
6. 독립 클라이언트만 존재하고 서버 없으면 _schedulePrintServers()
7. batchComplete 핸들러 등록  ← initialize()에서 이동
```

#### `_restartServers()` 수정

`_schedulePrintServers()` 호출 제거 (라인 467). URL 출력은 `serverReady` → `_schedulePrintServers()` 경로로만.

#### URL 출력 경로 (수정 후)

- 초기 빌드: `_startDevMode()` → `_restartServers()` → `_startServerRuntime()` → `serverReady` → `_schedulePrintServers()`
- watch: `batchComplete` → `_onDevBatchComplete()` → `_restartServers()` → `_startServerRuntime()` → `serverReady` → `_schedulePrintServers()`
- 독립 클라이언트만: `_startDevMode()` → `_schedulePrintServers()` 직접 호출

### 대안 검토

| 접근 방식 | 선택 여부 | 이유 |
|-----------|-----------|------|
| `batchComplete` 핸들러를 `_startDevMode()` 끝으로 이동 | 채택 | 초기 빌드 중 조기 서버 시작 방지, watch에서는 기존 동작 유지 |
| `_initialBuildDone` 플래그 + `_onDevBatchComplete`에서 조건 분기 | 미채택 | 상태 플래그보다 이벤트 등록 시점 제어가 단순 |
| `_restartServers()`에서 클라이언트 포트 polling 대기 | 미채택 | 타임아웃/경합 조건 복잡, 실패 시 여전히 proxy 미등록 |
