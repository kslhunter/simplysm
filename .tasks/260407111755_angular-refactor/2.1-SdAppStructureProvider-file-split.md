## 구현계획

### 배경
`sd-app-structure.provider.ts`(449줄)은 타입 정의(8개), 정적 유틸리티(20개 메서드, 344줄), 추상 프로바이더, 컴포지션 훅이 한 파일에 혼재. Utils 클래스가 파일의 77%를 차지한다. [근거: refactor.md DESIGN-002]

### 목표
- 단일 파일을 3개 관심사별 파일로 분리하여 탐색성 향상 [근거: Rule "public API 동일 유지"]
- 모든 기존 테스트 통과 유지 [근거: Rule "기존 동작 보존"]

### 비목표
- Utils 내부 로직 리팩토링 [근거: wbs 경계 "Utils 내부 로직 리팩토링 없음"]
- 새로운 public export 추가 [근거: wbs 경계 "public API 변경 없음"]

### 설계

**파일 분할 구조:**
```
core/providers/
├── sd-app-structure.types.ts     ← 8개 타입/인터페이스 (~60줄)
├── sd-app-structure.utils.ts     ← SdAppStructureUtils 클래스 (~350줄)
└── sd-app-structure.provider.ts  ← Provider + usePermsSignal (~50줄)
```

**의존 방향:** `types.ts` ← `utils.ts` ← `provider.ts`

**import 갱신 대상:**

| 파일 | 현재 import 심볼 | 변경 후 import 소스 |
|------|-----------------|-------------------|
| `index.ts` | 8개 심볼 from provider | types 5개, utils 1개, provider 2개로 분리 |
| `sd-permission-table.control.ts` | `ISdPermission` (type) | from `sd-app-structure.types` |
| `sd-base-container.control.ts` | `SdAppStructureProvider` | 변경 없음 (provider에 유지) |

### 대안 검토
**re-export 패턴 (기각):** provider.ts에서 types와 utils를 re-export하면 소비처 import 변경이 불필요하지만, barrel export 금지 규칙에 위반되고 파일 분할의 의미가 퇴색된다.
