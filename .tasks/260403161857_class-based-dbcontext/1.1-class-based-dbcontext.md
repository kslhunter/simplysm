# Feature 1.1 class 기반 DbContext

## 참조 자료

### 배경
- GitHub issue #17: `defineDbContext()`에 40+ 테이블 등록 시 TS7056 발생
- 함수형 `defineDbContext`는 모든 테이블 타입을 단일 제네릭 파라미터에 합침
- phantom field(`$inferSelect`)를 conditional type으로 교체 시도했으나, `any` passthrough 불가로 실패 확인
- v12 class 기반에서는 프로퍼티별 타입 분산으로 문제 없었음

### 합의된 API
- `this.queryable(TableBuilder | ViewBuilder)` — queryable factory 반환
- `this.executable(ProcedureBuilder)` — executable factory 반환
- `static migrations: Migration[]` — 마이그레이션 정의
- table/view 구분은 `instanceof TableBuilder` / `instanceof ViewBuilder`로 런타임 판별

### 대상 패키지
- `packages/orm-common` — DbContext 핵심 모듈

### 설계 결정

| # | 결정사항 | 선택 | 근거 |
|---|---------|------|------|
| D1 | TS7056 해결 방식 | class 기반 DbContext | phantom→conditional type 불가 확인, class 프로퍼티별 분산이 유일한 해결책 |
| D2 | table/view 구분 방식 | `instanceof` 런타임 판별 | 별도 `this.table()`/`this.view()` 불필요, `queryable()` 하나로 통합 |
| D3 | migration 정의 위치 | `static migrations` | 스키마 메타데이터로 인스턴스가 아닌 클래스 레벨에 위치 |
| D4 | 기존 API 호환성 | `@deprecated` 유지 | defineDbContext/createDbContext를 제거하면 외부 소비자 프로젝트가 깨짐 |
| D5 | builder 태그 방식 | `Object.defineProperty` non-enumerable | accessor 함수에 builder 참조를 태그하여 lazy meta 스캔 지원 |

## 구현계획

### 배경

현재 orm-common의 DbContext는 2단계 함수형 API(`defineDbContext` → `createDbContext`)로 구성. `defineDbContext`가 모든 테이블 타입을 단일 제네릭 `TTables`에 합치기 때문에 40+ 테이블 시 TS7056 발생. class 기반으로 전환하면 각 테이블이 개별 class property로 독립 직렬화되어 근본 해소.

### 목표

- `DbContext` abstract base class 제공
- `this.queryable()` / `this.executable()` 등록 메서드
- 기존 `createDbContext`와 동일한 연결/트랜잭션/DDL/초기화
- 기존 테스트 전수 통과
- `defineDbContext`/`createDbContext`는 `@deprecated` 유지

### 비목표

- 외부 패키지(orm-node, service-server) 마이그레이션 — 별도 Feature
- phantom field 변경 — 불필요 (class 프로퍼티 분산으로 해결)

### 설계

#### DbContext class 핵심 구조

```typescript
abstract class DbContext implements DbContextBase {
  status: DbContextStatus = "ready";
  _migration = this.queryable(_Migration);

  constructor(executor: DbContextExecutor, opt: { database: string; schema?: string })

  protected queryable<T extends TableBuilder | ViewBuilder>(builder: T):
    () => Queryable<T["$inferSelect"], ...>
  protected executable<T extends ProcedureBuilder>(builder: T):
    () => Executable<T["$params"], T["$returns"]>

  connect / connectWithoutTransaction / transaction
  createTable / dropTable / ... (DDL)
  initialize(options?)

  get meta(): { tables, views, procedures, migrations }  // lazy scan
}
```

#### builder 태그

`queryable()`/`executable()`이 반환하는 factory에 `__sdBuilder`를 `Object.defineProperty`(non-enumerable)로 부착. `meta` getter에서 `Object.entries(this)` 스캔 → `instanceof`로 table/view/procedure 분류.

### 대안 검토

| 접근 방식 | 선택 | 이유 |
|-----------|------|------|
| phantom → conditional type | 미채택 | `any` passthrough 불가 |
| InferDeepRelations 깊이 제한 | 미채택 | 중첩 include 타입 손실 |
| class 기반 DbContext | **채택** | 프로퍼티별 분산, v12 검증 패턴 |
