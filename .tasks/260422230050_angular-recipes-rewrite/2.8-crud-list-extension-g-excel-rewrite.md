### 선행 확장 A 재사용 지점 (확장 G 고유)

- `_upsertItem(db, item, logType)`: 업로드 행별 호출 경로. `logType: "엑셀업로드"`로 감사 로그 구분 [근거: @packages/angular/docs/recipes/crud-list/extension-a-inline-edit.md:335-358]
- `_search(usePagination)`: `false` 전달 시 전체 조회 (페이지네이션 없이). 다운로드 경로에서 재사용 [근거: 동 파일 L307-333]
- `_appSharedData.emitAsync(SHARED_DATA_KEY, ids)`: 업로드 완료 후 공유 데이터 변경 통지 [근거: 확장 A `onSubmit` 동일 패턴, L272]
- `busyCount` / `_sdToast.try` / `_refresh`: 진입점 2.1의 표준 비동기 파이프라인

### 진입점 2.1 + 확장 A 결합 시점 (얹기 위치)

- 확장 A가 도입한 inline 도구 dock (`packages/angular/docs/recipes/crud-list/extension-a-inline-edit.md:160-166`, `@if (canEdit() && viewType() === "page")` 가드 아래 "등록" 버튼 포함 dock) 내부에 "엑셀 업로드 / 엑셀 다운로드" 버튼 2개를 뒤쪽에 추가한다.
- 확장 B가 병용되는 경우 dock 내부 버튼 순서: "등록 → 선택 삭제 → 선택 복구 → 엑셀 업로드 → 엑셀 다운로드".

### 공통 규칙 반영

- `_common-rules.md` "시트 셀 내부 컨트롤에 `[inset]="true" [size]="'sm'"` 명시" — 확장 G는 시트 셀을 수정하지 않으므로 해당 규칙과 무관. 재서술하지 않는다.
- `_common-rules.md` "`mark(sig)`를 '저장 감지'로 사용하지 않는다" — 확장 G는 일괄 저장 경로를 거치지 않고 즉시 upsert → 재조회. diff 개념 없음. 재서술하지 않는다.
- `_common-rules.md` "공유 데이터 사용 화면은 `_refresh()` 선두에서 `wait()` 호출" — 확장 A에서 이미 적용 완료. 확장 G가 재서술하지 않는다.

현행 `packages/angular/docs/recipes/crud-list/extension-g-excel.md`(125줄)는 diff 스타일 템플릿을 **이미 대부분 충족**한다. 부족한 점은 (a) sibling 2.7 확정 템플릿 대비 `**🚫 흔한 실수**` 서브섹션이 부재하고, (b) 일부 포인트가 "다운로드는 `_search(false)`…" 같은 도입부가 2인칭스럽거나 과장 대문자(**반드시**, **필수**) 반복이며, (c) `## Cross-reference` 섹션이 없다는 점이다. 본 Feature는 **소스 시그니처 재검증 + sibling 템플릿 완전 정합 + 🚫 흔한 실수 신설(zod optional 남용)**을 수행한다. 코드 diff 본문(업로드 `_excelWrapper.read → _upsertItem` 루프, 다운로드 `_search(false) → write → toBlob → downloadBlob → close`)은 **보존**한다.

### 필수 필드를 `z.string().optional()`로 선언

\`\`\`typescript
// ❌ 모든 zod 필드에 .optional() 부착 — 빈 셀·누락 행이 그대로 _upsertItem에 전달되어
//    DB NOT NULL 위반 또는 name/phone 공백 row가 upsert된다
new ExcelWrapper(
  z.object({
    id: z.number().optional().describe("ID"),
    name: z.string().optional().describe("이름"),           // 필수 필드인데 optional
    phone: z.string().optional().describe("전화번호"),
    categoryId: z.number().optional().describe("카테고리.ID"),
  }),
);

// ✅ 필수 필드는 .optional() 없이 선언 — 빈 셀 행은 safeParse 단계에서 차단
new ExcelWrapper(
  z.object({
    id: z.number().optional().describe("ID"),
    name: z.string().describe("이름"),                      // 필수
    phone: z.string().optional().describe("전화번호"),
    categoryId: z.number().optional().describe("카테고리.ID"),
  }),
);
\`\`\`

**근거**: `ExcelWrapper.read`는 각 행을 `_schema.safeParse(record)`로 검증하고 실패 시
에러를 던진다(`packages/excel/src/excel-wrapper.ts:77`). zod 스키마가 업로드 유효성의
유일한 방어선이므로, 필수 필드에 `.optional()`을 달면 **검증 자체가 통과**해 잘못된 값이
`_upsertItem`까지 내려간다. `isDeleted` 컬럼이 있는 테이블은
[공통 규칙: 삭제 방식](../_common-rules.md#삭제-방식은-db-스키마에-따라-결정한다)에 따라
`isDeleted: z.boolean()` 필드를 추가한다 (확장 B 병용).

### 대안 검토

- **대안 1: anti-pattern 옵션 A(`_upsertItem` 우회 bulk insert) 또는 B(`getDataTable` 직접 호출) 채택**
  - 기각 사유(사용자 결정 D2): zod 스키마 설계가 업로드 검증의 유일한 방어선이며 원문 주석(required vs optional)에 선례가 있다. 옵션 A는 "재사용 원칙"에 가깝고, 옵션 B는 LLM이 실제로 할 가능성이 낮다 (원문·sibling 코드가 ExcelWrapper 중심).
- **대안 2: "FK id 변환 `toMapValues`" 및 "`busyMessage` 필요 시 추가"를 별도 섹션(`## 선택 기법`)으로 승격**
  - 기각 사유(D4, D5): 본 확장 고유 실전 팁이며 포인트 불릿 단위로 이미 충분한 정보량. 섹션 분해는 반-기법 "섹션 남발".
- **대안 3: `SdFileDialogProvider.showAsync`의 `Array.isArray` 가드 제거** (오버로드 시 항상 단일 File)
  - 기각 사유(D8): 런타임 타입 좁힘은 오버로드 계약에 의존하며, 향후 리팩토링(멀티 선택 기본화 등)에 방어적. 원문 유지.
