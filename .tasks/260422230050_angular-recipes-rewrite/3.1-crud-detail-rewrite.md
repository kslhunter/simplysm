## 구현계획

### 배경

현행 `packages/angular/docs/recipes/crud-detail.md`(466줄)는 구지침 시절 작성되어 T1(Recipe) 템플릿 정합이 미흡하다. 진입점 역할에 비해 §4 분해 테이블(4개)·§11 뷰 타입 분기 설명·부록 B 확장 매트릭스 표(5x10) 등이 과잉이며, 공통 규칙을 본문에 중복 수록한다. Feature 1.1에서 `_common-rules.md`가 T3로 정비된 현시점에는 본 진입점이 (a) When to use / When NOT to use로 recipe 선택, (b) 최소 뼈대 self-contained 코드, (c) 확장 A~F 인덱스 3가지에 집중하는 구조가 적합하다. 소스 API 시그니처(`<sd-form>`, `SdCommandDirective`, `injectViewTypeSignal` 등)는 소스(`packages/angular/src/controls/form/sd-form.ts`, `packages/angular/src/core/commands/sd-command.ts`, `packages/angular/src/core/routing/injectViewTypeSignal.ts:7-40`)에서 재검증을 거쳐야 한다.

### 목표

- T1(Recipe) 템플릿 7개 섹션(제목 요약 / When to use / 전제조건 / 기본 레시피 / 변형 / 🚫 흔한 실수 / 관련 Entry)을 갖춘다 [근거: Rule "T1 템플릿 구조를 따른다"]
- 최소 뼈대는 page 뷰 읽기 전용 상세 폼 단독 구현으로 self-contained하게 복붙 가능하다 [근거: Rule "최소 뼈대는 self-contained 복붙 가능 코드다"]
- 확장 A~F 선택 가이드와 상세 링크를 한 표로 제공한다 [근거: Rule "확장 A~F 인덱스를 제공한다"]

- 466줄 → 대략 230~280줄로 축약 (분해 테이블·뷰 분기·부록 제거분)

# Recipe: CRUD 상세폼 화면 직접 조립

{1~2문장 요약 — 무엇을 만들고, 무엇을 대체하는가}

## When to use / When NOT to use

- ✅ 단일 레코드 CRUD 상세폼을 `<sd-busy-container>` + `<sd-topbar-container>` + `<sd-form>`로 직접 조립해야 할 때
- ✅ page / modal / control 뷰 중 필요한 뷰만 선택적으로 지원해야 할 때
- ❌ CRUD 리스트(시트) 화면 → [`crud-list.md`](./crud-list.md)
- ❌ 페이지/모달 뷰 분기만 필요한 단순 컨테이너 → [`page-modal-container.md`](./page-modal-container.md)
- ❌ 데이터 선택 버튼 → [`data-select-button.md`](./data-select-button.md)

## 전제조건

- Provider: `provideSdAngular({ clientName })` 부트스트랩 완료

## 🚫 흔한 실수 (Anti-patterns)

> 공통 규칙(`mark` 오용, `injectViewTypeSignal()` 호출 위치, `_sdSharedData.wait()` 조건, soft-delete 선택 기준, 시트 셀 `[inset]/[size]`)은 [레시피 공통 규칙](./_common-rules.md)을 참조한다.

### 지원할 뷰를 확인하지 않고 3뷰 분기를 미리 박는다

\`\`\`typescript
// ❌ 실제로는 page 뷰만 쓰는데 modal·control 분기를 선제 조립
// - close output, viewType, modal 하단 dock, <ng-template #modalActionTpl>가 모두 죽은 코드
@Component({ ... })
export class CustomerDetail implements SdModalContentDef<boolean | undefined> {
  close = output<boolean | undefined>();
  viewType = injectViewTypeSignal();
  // ...
  template: `
    @if (viewType() === "page") { <sd-topbar>...</sd-topbar> }
    @if (viewType() === "modal" && canEdit()) { <sd-dock [position]="'bottom'">...</sd-dock> }
    ...
  `
}

// ✅ 기본 레시피 = page 전용. modal이 필요해지는 시점에 확장 C를, control은 확장 D를 얹는다
@Component({ ... })
export class CustomerDetail {
  itemId = input<number>();
  // page 전용 — viewType 분기 없음
}
\`\`\`

**근거**: 필요하지 않은 뷰의 계약·분기·슬롯은 죽은 코드로 남고, `implements SdModalContentDef`·`close.emit` 경로가 실제 호출되지 않아 LLM이 모달 사용처 탐색 시 오판 원인이 된다.

### `effect` 내부 비동기 호출을 `untracked`로 감싸지 않는다

\`\`\`typescript
// ❌ _refresh() 내부 signal 읽기가 effect 의존성으로 등록 → 무한 루프
effect(() => {
  this.itemId();
  void this._refresh(); // this.perms() / this.data() 읽기가 그대로 의존성
});

// ✅ untracked로 감싸 의존성 등록 차단
effect(() => {
  this.itemId(); // 여기서만 의존성 등록
  void untracked(async () => {
    await this._sdToast.try(() => this._refresh());
  });
});
\`\`\`

**근거**: Angular effect는 콜백 실행 중 읽힌 모든 signal을 의존성으로 등록한다. 비동기 작업 내부에서 signal을 읽으면 루프가 발생한다.

### `setupCanDeactivate`를 `computed`·`effect`·메서드에서 호출한다

\`\`\`typescript
// ❌ NG0203 — inject()는 injection context에서만 호출 가능
protected readonly canEdit = computed(() => {
  setupCanDeactivate(() => !this._dirty()); // 런타임 에러
  return true;
});

// ✅ 생성자 또는 필드 이니셜라이저에서만
constructor() {
  setupCanDeactivate(() => !this._dirty());
}
\`\`\`

**근거**: `setupCanDeactivate`는 `inject(Router)` 등을 사용하므로 injection context가 필수다.
