## 구현계획

### 배경

현행 `packages/angular/docs/recipes/crud-detail/extension-a-edit-save.md`(201줄)는 구지침 시절 작성되어 (a) 진입점 `crud-detail.md`의 구버전 §13 anchor(`#규칙-2-…`)를 참조하고, (b) `mark` 저장 감지 오해를 ❌/✅ 블록이 아닌 포인트 산문 문단으로 설명하며, (c) 일부 설명이 진입점·공통 규칙 본문과 중복 가능성이 있다. Feature 1.1 완료본(`_common-rules.md`)과 Feature 3.1 완료본(진입점 T1 재작성)을 기준으로, sibling Feature 3.3(`extension-b-delete-restore.md`)이 이미 확정한 diff 스타일 extension 템플릿을 준수하여 재정렬한다. 기존 diff 코드의 내용(편집/저장 로직, `_dataSnapshot`, `obj.clone` / `obj.equal`, `setupCanDeactivate`, Ctrl+S 경로 통합)은 소스 정합 검증을 거쳐 **보존**하되, 참조 링크·anti-pattern 노출 방식·3인칭 서술만 개정한다.

### 목표

- sibling extension-b와 동일한 diff 스타일 템플릿(브레드크럼 / 제목 / 선행 / 요약 / 도입 요소 / 번호 코드 / 포인트) 갖춤 [근거: Rule "sibling과 동일한 diff 스타일 템플릿"]

> **선행:** 없음 (최소 뼈대 §3에 직접 얹음)

{1~2문장 요약 — 무엇을 도입하고, 어떤 확장과 상호작용하는가}

**이 확장이 도입하는 요소:**

- **imports:** `computed`, `viewChild`, `obj`, `setupCanDeactivate`, `mark`, `SdCommandDirective` outputs `sdSaveCommand` 추가, `tablerDeviceFloppy`
- **DI:** 없음 (최소 뼈대와 동일)
- **파생:** `canEdit = computed(() => perms().includes("edit"))` (뷰 분기 없음 — 편집은 page/modal/control 모든 뷰에서 가능, 뷰별 UI는 확장 C/D)
- **상태:** `_dataSnapshot?: ICustomer` (직전 `_refresh()` 시점의 data 깊은 복제), `isNew = computed(() => data().id == null)` (신규 레코드 여부)
- **권한 키 확장:** `injectPermsSignal` 두 번째 인자 `["use"]` → `["use", "edit"]`
- **hostDirectives·host:** outputs에 `sdSaveCommand` 추가, host에 `(sdSaveCommand)="onSaveButtonClick()"` 추가
- **viewChild:** `formCtrl = viewChild<SdForm>("formCtrl")` (Ctrl+S 경로 공유)
- **메서드:** `onSaveButtonClick`, `onSubmit`, `_checkIgnoreChanges`; `onRefreshButtonClick` 선두에 변경 체크 추가
- **for Template:** `protected readonly mark = mark;` (템플릿 `(valueChange)="mark(data)"`용)
- **생성자:** `setupCanDeactivate(() => this._checkIgnoreChanges())`
- **템플릿:** topbar에 "저장" 버튼 추가(`@if (canEdit())`), `<sd-form>` → `<sd-form #formCtrl (formSubmit)="onSubmit()">`, 필드 `[readonly]="true"` → `[disabled]="!canEdit()"`, 입력 필드에 `(valueChange)="mark(data)"` 추가
- **_refresh 변경:** 말미에 `this._dataSnapshot = data.id == null ? undefined : obj.clone(this.data());` 추가

**포인트:**

- **`obj.equal`은 deep equal**(`packages/core-common/src/utils/obj.ts:172`)이므로 field mutation도 snapshot 대비 저장 판정에는 자동 반영된다. `(valueChange)="mark(data)"`는 OnPush 재렌더링/연계 computed 갱신 용도(별개 목적).
- **snapshot은 반드시 `obj.clone`으로 깊은 복제.** `this._dataSnapshot = this.data()` 얕은 참조 대입은 `data().field = "x"` 같은 mutation을 snapshot까지 오염시켜 비교가 실패한다. `obj.clone`(`packages/core-common/src/utils/obj.ts:19`)을 사용한다.
- **`isNew = computed(() => data().id == null)`은 PK 형태에 주의.** 클라이언트 UUID 선할당·자연키·복합키 등 id가 항상 존재하는 스키마에서는 `isNew`를 별도 `signal<boolean>` + `_refresh()` 내부 세팅으로 바꾸고, snapshot 분기도 `this.isNew() ? undefined : obj.clone(this.data())`로 치환한다.
- **Ctrl+S 경로 통일:** `hostDirectives` → `(sdSaveCommand)="onSaveButtonClick()"` → `formCtrl()?.requestSubmit()` → `<sd-form (formSubmit)="onSubmit()">`. 버튼 클릭과 단축키가 완전히 동일한 경로로 수렴한다.
- **`setupCanDeactivate(() => this._checkIgnoreChanges())`**: 라우트 이탈 시 snapshot 대비 변경이 있으면 `confirm` 호출. modal 뷰([확장 C](./extension-c-modal-view.md))에서는 modal을 항상 이탈 허용으로 조건을 확장한다.
- **조용한 저장(`silent` 파라미터):** 프로그래밍 저장에서 "변경사항이 없습니다." info 토스트를 억제하려면 `onSubmit(silent: boolean)` 시그니처를 도입하여 `if (!silent) this._sdToast.info(...)`로 감싼다.
- **`_checkIgnoreChanges`는 `_dataSnapshot == null`을 true로 취급** — 신규·로드 전은 이탈/새로고침 즉시 허용, snapshot이 있어도 `obj.equal`로 동일하면 허용.

**🚫 흔한 실수**

> 공통 규칙(`mark` 오용 전체, `setupCanDeactivate` 호출 위치, soft-delete 선택 기준 등)은 [레시피 공통 규칙](../_common-rules.md)을 참조한다. 이 섹션은 **편집/저장 확장 고유 실수**만 다룬다.

### `mark(data)`로 저장 여부를 판정한다

\`\`\`typescript
// ❌ mark 호출 여부로 저장 가능 여부를 분기 — 의미 없는 전제
protected async onSubmit(): Promise<void> {
  if (!this._lastMarkCalled) return;   // mark가 호출되지 않았으므로 저장할 게 없다는 잘못된 판정
  // ...
}

// ✅ snapshot과 현재값을 obj.equal로 비교하여 변경 판단
protected async onSubmit(): Promise<void> {
  if (!this.isNew() && this._dataSnapshot != null
      && obj.equal(this.data(), this._dataSnapshot)) {
    this._sdToast.info("변경사항이 없습니다.");
    return;
  }
  // ...
}
\`\`\`

**근거**: `mark(sig)`는 shallow copy로 OnPush 재렌더링·연계 computed 알림을 유발하는 통지 수단이며 "값이 변했는지" 감지와는 무관하다. 값 비교는 `obj.equal` deep equal이 담당한다. → [공통 규칙: `mark(sig)`를 '저장 감지' 수단으로 사용하지 않는다](../_common-rules.md#marksig를-저장-감지-수단으로-사용하지-않는다)
```

### 대안 검토

- **대안 1: T1 진입점 템플릿(When to use / 전제조건 / 변형 / Anti-patterns / 관련 Entry)으로 확장까지 승격**
  - 기각 사유: 이미 재작성된 sibling `extension-b-delete-restore.md:1-101`가 diff 스타일을 선택했다. 같은 폴더 확장끼리 템플릿을 혼용하면 독자(Claude Code)가 "이 파일 형식이 왜 다른가"를 학습해야 하는 추가 인지 부담이 생기고, WBS Feature 2.2~2.8·3.2~3.7 모두 diff 스타일 전제로 정의되어 있음.
- **대안 2: `mark` 안티패턴을 포인트 문단으로만 유지**
  - 기각 사유: WBS Feature 3.2 범위 명세가 "❌/✅" 형식을 명시. 포인트 산문은 ❌/✅ 대비보다 시각적 식별성이 낮고, 공통 규칙에서도 같은 안티패턴을 ❌/✅ 블록으로 서술하므로 형식 일관성이 필요.
- **대안 3: snapshot 얕은 참조 대입 오류도 ❌/✅ 블록으로 승격**
  - 기각 사유: WBS에 명시되지 않았고, `obj.clone` 미사용은 "깊은 복제" 주의 한 줄로 충분히 전달된다. 섹션 남발은 반-기법 "과도한 안티패턴 섹션" 위반.
