## 구현계획

### 배경

현행 `packages/angular/docs/recipes/crud-detail/extension-b-delete-restore.md`(101줄)는 이미 sibling diff 스타일 템플릿을 준수한다. 다만 (a) WBS 3.3에서 명시한 "❌/✅ 물리 삭제 경로 혼용 금지" Anti-patterns 섹션이 현재 포인트 산문 한 줄(L97)로만 언급되어 sibling A(`extension-a-edit-save.md:202-226`)가 확정한 `## 🚫 흔한 실수` 포맷과 불일치하고, (b) 적용 조건 블록쿼트(L9)의 `../_common-rules.md#삭제-방식-soft-delete-vs-물리-삭제` anchor가 공통 규칙 L139 실제 헤더와 달라 1-level deep 링크가 끊어진 상태다. 이번 재작성은 **템플릿 정합 + anchor 복구 + Anti-patterns 1건 승격**에 한정되며, 코드 diff·포인트 본문은 보존한다.

### 목표

> 공통 규칙(삭제 방식 선택 기준, `mark` 오용, `setupCanDeactivate` 호출 위치 등)은 [레시피 공통 규칙](../_common-rules.md)을 참조한다. 이 섹션은 **삭제/복구 확장 고유 실수**만 다룬다.

### 물리 삭제 경로와 soft-delete 토글을 한 화면에 혼용한다

```typescript
// ❌ 같은 화면에서 두 경로를 병행 — 삭제 의미가 불명확해지고,
//    서버 조회 필터(`isDeleted: false`)와 물리 DELETE가 충돌한다
protected async onHardDeleteButtonClick(): Promise<void> {
  if (!confirm("영구 삭제하시겠습니까?")) return;
  await this._appOrm.connectAsync(async (db) => {
    await db.customer.where((it) => [expr.eq(it.id, this.data().id)]).delete();
  });
  // ...
}
private async _toggleDelete(del: boolean): Promise<void> {
  // ... isDeleted: del 업데이트 (soft-delete)
}

// ✅ isDeleted 컬럼 유무로 단일 경로를 선택한다.
//    컬럼이 있으면 `_toggleDelete`(soft-delete)만,
//    컬럼이 없으면 이 확장 자체를 사용하지 않고 물리 삭제 단일 경로로 간다.
private async _toggleDelete(del: boolean): Promise<void> {
  if (this.busyCount() > 0) return;
  if (!this.perms().includes("edit")) return;
  if (del && !confirm("삭제하시겠습니까?")) return;
  // ... await db.customer.where(...).update({ isDeleted: del });
}
```

**근거**: 동일 테이블에 soft-delete와 물리 DELETE 경로가 공존하면 삭제 이력·복구 가능 여부·참조 무결성이 불일치하게 된다. 서버 리스트 조회가 `isDeleted: false` 필터로 삭제 행을 숨기는 전제에서 물리 DELETE가 섞이면, "복구 불가 삭제"와 "복구 가능 삭제"가 같은 화면에서 구분 없이 발동된다. → [공통 규칙: 삭제 방식은 DB 스키마에 따라 결정한다](../_common-rules.md#삭제-방식은-db-스키마에-따라-결정한다)
```

#### 변경 없는 구간

- L1 브레드크럼 / L3 제목 / L5 선행 / L7 요약 / L11-16 도입 요소 / L18-93 코드 6단계 / L95-100 포인트 → **보존**

#### 소스 시그니처 재검증 체크리스트

- `tablerEraser`, `tablerRestore` — `@ng-icons/tabler-icons` export 존재 (진입점 3.1·확장 A에서 `tablerRefresh`, `tablerDeviceFloppy` 경로와 동일)
- `_toggleDelete` 내부 `db.customer.where(...).update({ isDeleted: del })` — 확장 A의 `db.customer.upsertAsync(this.data())`와 동일한 앱별 ORM 전제. 스니펫 형태 유지
- 확장 A 산출물과의 결합 — `busyCount`(L61 확장 A 보존), `perms().includes("edit")`(확장 A L55 추가분), `_refresh()`(확장 A L179 재정의본) 재사용 관계 유지

### 대안 검토

- **대안 1: Anti-patterns 2건(물리 삭제 혼용 + 복구 시 confirm 오용) 승격**
  - 기각 사유: 사용자 결정으로 1건 확정. WBS 3.3 범위에 "복구 confirm" 언급 없고 포인트 L98 1줄 산문으로 충분. 반-기법 "과도한 안티패턴 섹션" 회피.
- **대안 2: 포인트 L97 "isDeleted 컬럼이 없는 테이블은 이 확장 미사용" 문장을 Anti-patterns 섹션으로 통째 이관**
  - 기각 사유: 포인트 L97은 "컬럼 유무 → 경로 선택" **결정 규칙**이고, Anti-patterns는 "두 경로 혼용 코드" **실수 시각화**로 역할이 다르다. 이관 시 포인트가 얇아지고 결정 기준이 묻힌다. 설계 결정 D4로 역할 분리 유지.
- **대안 3: anchor 불일치를 공통 규칙 헤더 변경으로 해결**
  - 기각 사유: Feature 1.1 완료본 수정은 본 Feature 범위 외. 확장 B의 링크 텍스트만 수정하는 편이 영향 범위가 작다.
