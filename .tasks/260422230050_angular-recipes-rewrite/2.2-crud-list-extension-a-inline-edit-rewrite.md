### 진입점 2.1 (최소 뼈대) 기준 일치 대상

확장 A는 진입점 `crud-list.md`의 최소 뼈대 위에 **얹는 diff**로만 기술한다.

- `packages/angular/docs/recipes/crud-list.md:85-301` — 최소 뼈대 컴포넌트.
- `crud-list.md:97-99` — `hostDirectives: [{ directive: SdCommandDirective, outputs: ["sdRefreshCommand"] }]` → 확장 A는 `"sdSaveCommand"` 추가.
- `crud-list.md:100-102` — `host: { "(sdRefreshCommand)": "onRefreshButtonClick()" }` → `(sdSaveCommand)` 바인딩 추가.
- `crud-list.md:192` — `perms = injectPermsSignal(["sales.customer"], ["use"])` → `"edit"` 키 추가.
- `crud-list.md:79-83` — `ICustomer` 인터페이스 확장(편집 필드·신규 행 허용 `id?`·감사·카테고리).
- `crud-list.md:250-254` — `_refresh` 말미에 `_itemsSnapshot = obj.clone(r.items)` 추가.
- `crud-list.md:213-234` — 기존 초기 effect는 유지, 생성자에 `setupCanDeactivate(() => this._checkIgnoreChanges())` 한 줄 추가.
- `crud-list.md:242-247` — `onRefreshButtonClick` 선두에 `if (!this._checkIgnoreChanges()) return;` 추가.

### 공통 규칙 반영

- `_common-rules.md` "시트 셀 내부 컨트롤에 `[inset]="true" [size]="'sm'"` 명시" — 본 확장은 inline 편집 도입으로 `<sd-textfield>`·`<sd-shared-data-select>`를 셀로 교체하므로 해당 규칙이 직접 적용됨. 본문에 재서술하지 않고 1줄 요약 + 공통 규칙 링크.
- `_common-rules.md` "`mark(sig)`를 '저장 감지' 수단으로 사용하지 않는다" — 본 확장에서 `(valueChange)="mark(items)"`를 사용하므로 오해 소지 큼. 포인트에 1줄 요약 + 공통 규칙 링크.
- `_common-rules.md` "삭제 방식 (soft-delete vs 물리 삭제)" — 본 확장은 삭제를 다루지 않음. `oneWayDiffs`가 delete를 감지하지 못한다는 제약만 설명하며 삭제 UX는 확장 B/C 링크로 위임.

### 배경

현행 `packages/angular/docs/recipes/crud-list/extension-a-inline-edit.md`(376줄)는 이미 diff 스타일 템플릿을 쓰고 있으나, (a) "inline 편집 vs 모달 편집(확장 F) 선택 기준"이 요약 문단 1문장에만 묻혀 있어 시각적으로 드러나지 않고, (b) `oneWayDiffs`가 delete를 다루지 않는다는 본 확장 고유 실수가 포인트 산문 문단에 숨어 있으며, (c) `mark`·`setupCanDeactivate`·시트 셀 `[inset]/[size]` 관련 주의사항이 공통 규칙과 중복될 소지가 있다. Feature 2.1 재작성본(진입점 T1)과 공통 규칙 T3, sibling 확장 템플릿(`extension-b-delete-restore.md`)을 기준으로 상단 적용 조건 블록쿼트, 🚫 흔한 실수 서브섹션, 공통 규칙 링크 위임을 정비한다. 코드 diff 본문(편집 도입·Ctrl+S 경로·snapshot·`_upsertItem`·감사 로그)은 소스 정합 재검증 후 **보존**한다.

### `items` 배열에서 기존 row를 물리 제거

\`\`\`typescript
// ❌ 기존 row를 배열에서 제거 — oneWayDiffs는 delete를 반환하지 않으므로
//    저장 시 서버는 이 row가 사라진 사실을 감지하지 못한다.
onDeleteRow(item: ICustomer): void {
  this.items.update((list) => list.filter((it) => it !== item));
}

// ✅ 삭제 의사는 isDeleted 플래그로 표현 → diff의 type: "update"로 전송
onDeleteRow(item: ICustomer): void {
  this.items.update((list) => list.map(
    (it) => it.id === item.id ? { ...it, isDeleted: true } : it,
  ));
}

// ✅ 예외: 신규 행(id == null)은 저장 포기 시 물리 제거해도 된다 — snapshot에 없어 diff 자체 없음
onRemoveNewItemButtonClick(item: ICustomer): void {
  this.items.update((list) => list.filter((it) => it !== item));
}
\`\`\`

**근거**: `oneWayDiffs`의 반환 `type`은 `"create" | "update" | "same"`만 있으며 delete를
다루지 않는다(`packages/core-common/src/extensions/arr-ext.types.ts:206`). soft-delete 경로는
[확장 B: 선택 삭제/복구](./extension-b-selection.md) / [확장 C: inline 삭제/복구](./extension-c-inline-delete.md)
참조. `isDeleted` 컬럼 없는 테이블에서는 [공통 규칙: 삭제 방식](../_common-rules.md#삭제-방식은-db-스키마에-따라-결정한다) 참조.

### 대안 검토

- **대안 1: 전용 `## When to use / When NOT to use` 섹션 도입**
  - 기각 사유: sibling extension(crud-detail 확장 B)이 `> **적용 조건:**` 블록쿼트로 이미 확정. 같은 폴더 확장에서 템플릿을 혼용하면 독자(Claude Code)가 "이 파일은 왜 형식이 다른가"를 학습해야 하는 인지 부담. WBS 2.2의 "선택 기준 명시" 요구는 블록쿼트 1~2줄로도 충분히 충족.
- **대안 2: `mark(items)` 오해 anti-pattern을 ❌/✅ 블록으로 추가(3.2 패턴 재사용)**
  - 기각 사유: 공통 규칙 `_common-rules.md:196-229`에 이미 ❌/✅ 블록으로 상세 기술되어 있음. 본문 재서술은 공통 규칙 위임 원칙 위반. 1줄 요약 + 링크로 위임.
- **대안 3: `items` 물리 제거와 snapshot 얕은 참조 대입 2건을 모두 ❌/✅ 블록으로 승격**
  - 기각 사유: snapshot 얕은 참조 대입은 포인트에서 `obj.clone` 사용 1줄로 충분히 전달 가능. 섹션 남발은 매뉴얼 반-기법. WBS 2.2는 "관련 anti-pattern" 등으로 상한 없음을 시사하나, self-contained 문서의 시각 밀도를 고려해 고유 실수 1건만 승격.
