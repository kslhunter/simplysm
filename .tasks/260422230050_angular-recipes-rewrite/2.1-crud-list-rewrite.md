## 구현계획

### 배경

현행 `packages/angular/docs/recipes/crud-list.md`(519줄)는 T1(Recipe) 템플릿 이전 구조로, 14개 H2 섹션 + 부록 B(확장 매트릭스)로 구성된다. T1 템플릿은 "When to use / 전제조건 / 기본 레시피 / 변형 / Anti-patterns / 관련 Entry" 6-섹션을 요구한다. 본 Feature는 **단일 파일 전면 재작성**이며, 확장 Feature(2.2~2.8)가 본 파일의 "기본 레시피"를 선행으로 참조하므로 최소 뼈대 코드의 안정성이 중요하다.

## 🚫 흔한 실수 (Anti-patterns)

### modal = 선택 모달로 반사적 부착

\`\`\`typescript
// ❌ viewType()==="modal"만 보고 선택 모달 계약을 반사적으로 부착
export class CustomerList implements SdSelectModal<ICustomer> {
  selectMode = input<"single"|"multi">();
  selectedItemKeys = input<any[]>([]);
  close = output<SelectModalOutputResult<ICustomer>>();
  // ... 조회 전용에도 하단 "선택 해제 / 확인" 바, cumulativeSelection 전부 부착
}

// ✅ modal 용도를 먼저 확정한다
//   (a) 선택: 확장 D 스켈레톤부터
//   (b) 조회 전용: 확장 E 스켈레톤부터 (SdSelectModal 계약 부착 안 함)
\`\`\`

**근거**: 조회 전용 modal에 선택 계약을 부착하면 호출되지 않아 죽은 코드가 되고, LLM이 풀 스택 합본을 복사하면서 반사적으로 이식하는 회귀가 잦다. [확장 E](./crud-list/extension-e-readonly-modal.md) 참조.

### 뷰 분기를 완전 분리 블록으로 작성

\`\`\`html
<!-- ❌ page 블록과 modal 블록을 각각 완성 — 필터·시트가 중복 -->
@if (viewType() === "page") {
  <sd-topbar-container> ... <sd-form> ... <sd-sheet /> ... </sd-topbar-container>
}
@if (viewType() === "modal") {
  <sd-topbar-container> ... <sd-form> ... <sd-sheet /> ... </sd-topbar-container>
}

<!-- ✅ 하나의 껍데기 + 차이점만 @if로 얹는다 -->
<sd-topbar-container>
  @if (viewType() === "page") { <sd-topbar> ... </sd-topbar> }
  <sd-dock-container>
    <sd-dock class="p-default"> <sd-form> ... </sd-form> </sd-dock>
    <sd-sheet ...> ... </sd-sheet>
  </sd-dock-container>
</sd-topbar-container>
\`\`\`

**근거**: 필터 1줄 수정에 두 블록을 모두 고치는 상황이 생기면 구조가 잘못된 것이다.

### `orderBy` 람다 + `obj.getChainValue` 회귀

\`\`\`typescript
// ❌ string overload 도입 전 우회 코드 (LLM 훈련 데이터에 잔존)
for (const s of sortingDefs) {
  qr2 = qr2.orderBy(
    (item) => obj.getChainValue(item, s.key, true) as any,
    s.desc ? "DESC" : "ASC",
  );
}

// ✅ string overload 사용 (체인 경로도 string 지원: "user.name")
for (const s of sortingDefs) {
  qr2 = qr2.orderBy(s.key, s.desc ? "DESC" : "ASC");
}
\`\`\`

**근거**: `Queryable.orderBy`는 string overload를 지원한다(`packages/orm-common/src/exec/queryable.ts:420`). 람다 형태는 overload 도입 전 회피책이며 타입 추론·as 캐스팅을 깨뜨린다.

### 테스트용 public API 노출

\`\`\`typescript
// ❌ 테스트에서 private 메서드에 접근하려고 얇은 public wrapper 노출
async submit(diffs: any[]) { await this._submitAsync(diffs); }

// ✅ TestBed fixture에서 click·dispatch 이벤트 경로 또는 host의 sdSaveCommand 트리거
fixture.nativeElement.dispatchEvent(new KeyboardEvent("keydown", { key: "s", ctrlKey: true }));
\`\`\`

**근거**: public wrapper는 캡슐화를 깨고 컴포넌트의 외부 API 인상을 오염시킨다.

#### 예제 코드 주석 가이드

D1 결정에 따라 분해 표 대신 예제 주석으로 의도 정보를 전달한다. 다음 **비자명 의도**에 한해 1줄 주석만 부착한다 (소스를 읽으면 알 수 있는 정보는 주석 달지 않음):

- `filter` 선언부: `// 입력 버퍼. onFilterSubmit 시 lastFilter로 스냅샷`
- `lastFilter` 선언부: `// 조회 트리거 — effect 의존성은 이 signal`
- `busyCount` 선언부: `// 중첩 비동기 작업 카운트 (0 초과 시 busy 표시)`
- `mark(lastFilter)` 호출부: `// 값 변경 없이 참조만 갱신 → effect 재실행`
- `initialized.set(true)`: `// 최초 조회 완료 — @if (initialized()) 가드 해제`
- `_search(usePagination)` 파라미터: `// false는 전체 조회 (엑셀 다운로드 등에서 재사용)`

- **대안 B — 기본 레시피를 여러 `.ts` 파일로 분할 게시**: self-contained 원칙 위배. LLM 1회 로드로 코드 완성 불가
