## 구현계획

### 배경

`capacitor.ts`(618줄)의 `Capacitor` 클래스에 라이프사이클 오케스트레이션, NPM 설정 관리, 설정 파일 생성, URL 조작 등 여러 관심사가 혼재되어 있다. 기존에 `capacitor-android.ts`, `capacitor-build.ts`, `capacitor-icon.ts`는 이미 독립 모듈로 분리되어 있으며, 이들은 `cpx.spawn`을 직접 사용하고 개별 파라미터를 받는 함수 패턴을 따른다. [근거: DESIGN-004, 기존 코드 패턴]

### 목표
- NPM 설정 로직(`_initCap` + `_setupNpmConf` + `_findWorkspaceRoot`, 143줄)을 `capacitor-npm-config.ts`로 분리 [근거: Rule "NPM 설정 로직이 독립 모듈로 분리된다"]
- 설정 파일 생성 로직(`_writeCapConf` + `_updateServerUrl` + `_toPascalCase`, 50줄)을 `capacitor-config-writer.ts`로 분리 [근거: Rule "설정 파일 생성 로직이 독립 모듈로 분리된다"]
- Capacitor 클래스를 오케스트레이션만 담당하는 경량 파사드로 축소 [근거: wbs "Capacitor 클래스는 경량 파사드로 유지"]

### 비목표
- `capacitor-android.ts`, `capacitor-build.ts`, `capacitor-icon.ts` 변경 [근거: wbs 경계]
- 잠금 파일 관리(`_acquireLock`/`_releaseLock`) 분리 [근거: wbs 경계 "잠금 파일 관리 로직은 Capacitor 클래스에 유지"]
- 공개 API(`create`, `initialize`, `run`, `build`) 시그니처 변경 [근거: wbs "기존 기능의 동작 변경 없이"]

### 설계

#### capacitor-npm-config.ts

`_initCap`과 `_setupNpmConf`를 2개의 exported 함수로 추출한다. `_findWorkspaceRoot`는 모듈 내부 함수로 배치한다.

```typescript
// packages/sd-cli/src/capacitor/capacitor-npm-config.ts

/**
 * .capacitor/package.json을 구성하고 의존성 변경 여부를 반환한다.
 */
export async function setupCapNpmConfig(
  capPath: string,
  pkgPath: string,
  config: SdCapacitorConfig,
  npmConfig: NpmConfig,
  platforms: string[],
  exclude: string[],
): Promise<boolean>;

/**
 * Capacitor 프로젝트 NPM 초기화 (pnpm install, cap init, www placeholder).
 * 의존성 변경 시 true를 반환한다.
 */
export async function initCapNpmProject(
  capPath: string,
  pkgPath: string,
  config: SdCapacitorConfig,
  npmConfig: NpmConfig,
  platforms: string[],
  exclude: string[],
): Promise<boolean>;

// 내부 함수
function findWorkspaceRoot(pkgPath: string): string;
```

[근거: D1 — 기존 패턴(개별 파라미터), D2 — cpx.spawn 직접 사용, D3 — findWorkspaceRoot는 npm config에서만 사용]

#### capacitor-config-writer.ts

`_writeCapConf`와 `_updateServerUrl`을 2개의 exported 함수로 추출한다. `_toPascalCase`는 모듈 내부 함수로 배치한다.

```typescript
// packages/sd-cli/src/capacitor/capacitor-config-writer.ts

/**
 * capacitor.config.ts를 생성한다.
 */
export async function writeCapacitorConfig(
  capPath: string,
  config: SdCapacitorConfig,
): Promise<void>;

/**
 * capacitor.config.ts의 server.url을 업데이트한다.
 */
export async function updateServerUrl(
  capPath: string,
  url: string,
): Promise<void>;

// 내부 함수
function toPascalCase(str: string): string;
```

[근거: D4 — toPascalCase는 config writer에서만 사용]

#### Capacitor 클래스 축소

추출 후 Capacitor 클래스에 남는 요소:
- **static**: `create()`, `_validateConfig()`, `_LOCK_FILE_NAME`, `_logger`
- **오케스트레이션**: `initialize()`, `run()`, `build()`
- **인프라**: `_exec()`, `_execCap()`, `_acquireLock()`, `_releaseLock()`, `_validateTools()`, `_addPlatforms()`
- **필드**: `_capPath`, `_platforms`, `_npmConfig`, `_pkgPath`, `_config`, `_exclude`

`initialize()`는 `initCapNpmProject()` → `writeCapacitorConfig()` → `_addPlatforms()` → 기존 모듈 호출로 변경.
`run()`은 `updateServerUrl()` 호출로 변경.

[근거: D5 — _exec/_execCap은 오케스트레이션에서 계속 사용]

### 대안 검토

**A. 모든 로직을 단일 유틸리티 모듈로 추출** — 관심사가 다른 로직을 하나로 묶으면 기존 문제(관심사 혼재)가 반복된다. 기각.

**B. Options 객체 패턴 사용** — `{ capPath, pkgPath, config, ... }` 형태. 기존 모듈(`capacitor-android.ts` 등)이 개별 파라미터를 사용하므로 일관성이 깨진다. 기각.
