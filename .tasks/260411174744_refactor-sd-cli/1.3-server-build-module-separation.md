## 구현계획

### 배경

`server-build.worker.ts`(497줄)에 esbuild context 관리(생성/rebuild/재생성/dispose), FsWatcher 감시 루프(onChange 핸들러 ~75줄), 빌드 오케스트레이션(esbuild + tsc 병렬)이 혼재되어 있다. Feature 1.1에서 초기화 보일러플레이트, Feature 1.2에서 감시 경로 수집이 이미 추출되었으며, 남은 관심사를 분리한다. [근거: DESIGN-001 "4가지 독립 관심사가 단일 워커에 혼재"]

### 목표

- esbuild context 생명주기를 `server-esbuild-context.ts`로 캡슐화 [근거: Rule "esbuild context 생명주기는 server-esbuild-context.ts에서 캡슐화"]
- FsWatcher 감시 루프를 `server-watch-manager.ts`로 분리 [근거: Rule "FsWatcher 감시 루프는 server-watch-manager.ts에서 관리"]
- LOGIC-001 리소스 해제 패턴을 `recreateContext()` 메서드로 캡슐화 [근거: Rule "LOGIC-001 리소스 해제"]
- `server-build.worker.ts`를 Types + build() + rebuildAll() + startWatch(조합) 셸로 축소 [근거: Rule "경량 셸"]

### 비목표

- server-artifacts.ts 추출 — 인라인 코드 ~7줄은 추출 가치 없음 [근거: D1]
- 다른 워커(library-build, ngtsc-build, client) 변경 [근거: WBS 경계]
- esbuild/tsc 설정 변경 [근거: WBS 경계]
- build() 함수의 내부 로직 변경 — esbuild.build() 직접 호출은 watch context와 무관 [근거: WBS 경계]

### 설계

#### `workers/server-esbuild-context.ts` — esbuild context 생명주기 모듈

모듈 스코프 변수 + export 함수 패턴. 워커가 단일 인스턴스이므로 모듈 스코프 상태로 충분하다. [근거: D2]

```typescript
// 모듈 스코프 상태
let esbuildContext: esbuild.BuildContext | undefined;
let lastMetafile: esbuild.Metafile | undefined;

// esbuild watch context 생성
export async function createContext(options: {
  pkgDir: string;
  entryPoints: string[];
  env?: Record<string, string>;
  external: string[];
}): Promise<void>

// esbuild rebuild + metafile 갱신 + outputFiles 디스크 기록
// context 없으면 null 반환
export async function rebuild(): Promise<{
  success: boolean;
  errors?: string[];
  warnings?: string[];
} | null>

// LOGIC-001: old 보관 → undefined 선제 초기화 → 새 생성 → finally에서 old dispose
export async function recreateContext(options: {
  pkgDir: string;
  entryPoints: string[];
  env?: Record<string, string>;
  external: string[];
}): Promise<void>

// context dispose + 상태 초기화
export async function dispose(): Promise<void>

// metafile 접근자 (watch manager의 필터링에 사용)
export function getMetafile(): esbuild.Metafile | undefined

// context 존재 여부
export function hasContext(): boolean
```

의존성: `esbuild`, `esbuild/esbuild-config.ts`의 `createServerEsbuildOptions`, `writeChangedOutputFiles` [근거: 현재 worker의 esbuild 관련 import 이동]

#### `workers/server-watch-manager.ts` — FsWatcher 감시 루프 모듈

server-build 전용 감시 루프. 파일 변경 분류 + metafile 필터링 + context 재생성을 캡슐화한다. [근거: D3]

```typescript
export interface ServerWatchLoopConfig {
  info: ServerWatchInfo;
  cwd: string;
  watchPaths: string[];
  logger: ConsolaInstance;
  initialExternals: string[];
  // 콜백
  onBuildStart: () => void;
  onBuild: (result: ServerCombinedBuildEvent) => void;
  onError: (message: string) => void;
  rebuild: () => Promise<ServerCombinedBuildEvent>;
}

export async function startServerWatchLoop(config: ServerWatchLoopConfig): Promise<FsWatcher>
```

onChange 핸들러 내부 로직 (현재 worker lines 394-472 이동):
1. `hasFileAddOrRemove(changes)` → tsconfig 재파싱, entryPoints 재수집, package.json 변경 시 externals 재수집, `esbuildCtx.recreateContext()` 호출, `config.rebuild()`, `config.onBuild(result)`
2. `!esbuildCtx.hasContext()` 또는 `!esbuildCtx.getMetafile()` → `config.rebuild()`
3. metafile.inputs 기반 필터링 → 관련 파일이면 `config.rebuild()`, 아니면 건너뜀 (pnpm symlink → realpath 대응 포함)

의존성: `server-esbuild-context.ts`, `build-change-filter.ts`, `core-node`의 `FsWatcher`/`pathx`, `utils/tsconfig.ts`, `deps/server-production-files.ts`의 `collectAllExternals`

#### `workers/server-build.worker.ts` — 경량 워커 셸로 축소

축소 후 구조:
- **Types** (ServerBuildInfo, ServerWatchInfo, ServerBuildResult, ServerCombinedBuildEvent, ServerBuildWorkerEvents) — 외부 소비자가 import하므로 유지
- **cleanup()** — `esbuildCtx.dispose()` + publicWatcher/srcWatcher close
- **build()** — 현재와 동일 (esbuild.build 직접 호출, watch context와 무관)
- **rebuildAll()** — esbuild 부분을 `esbuildCtx.rebuild()`로 대체, tsc/lint는 유지
- **startWatch()** — esbuild context 생성 → 초기 빌드 → .config.json 작성 → watchPublicFiles → startServerWatchLoop 호출로 축소
- **stopWatch(), worker 생성** — 현재와 동일

### 대안 검토

| 대안 | 선택하지 않은 이유 |
|------|------------------|
| 클래스 기반 EsbuildContext | 워커가 단일 인스턴스이므로 클래스의 다중 인스턴스 능력이 불필요. 기존 모듈 스코프 패턴과 불일치 |
| 범용 WatchManager | metafile 필터링, context 재생성 등 server-build 고유 로직이 많아 범용화 시 과도한 추상화 |
| onChange 핸들러를 worker에 유지 | DESIGN-001의 핵심 이슈(관심사 혼재)가 해결되지 않음. startWatch가 여전히 ~120줄 |
| rebuildAll을 esbuild context 모듈로 이동 | rebuildAll은 esbuild + tsc + lint를 조합하므로 esbuild 모듈에 넣으면 tsc/lint 의존성이 유입됨 |
