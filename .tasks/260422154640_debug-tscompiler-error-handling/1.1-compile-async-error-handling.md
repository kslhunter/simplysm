## 구현계획

### 배경
`SdTsCompiler.compileAsync()` (`:140-400`)는 5개 단계를 순차 실행한다: analyzeAsync → findAffectedFiles → emit → collectDiagnostics → lintAndGlobalScss. 현재 이들을 하나의 try-catch로 감싸서, 한 곳이 크래시하면 나머지 전부 스킵되고, 원인 파일 정보도 불충분하다.

### 목표
- 단계별 격리로 부분 복구 [근거: Rule "단계별 크래시 시 후속 단계는 계속 진행"]
- 크래시 시 원인 파일 포함된 에러 메시지 [근거: Rule "크래시 에러 메시지에 원인 파일 정보가 포함"]
- 파일 단위 루프 전수 추적 [근거: Rule "파일 단위 루프에서 현재 파일을 추적"]

### 비목표
- TS 컴파일러 버그 자체 수정 [근거: wbs 경계]
- 다른 파일(esbuild 플러그인)의 에러 처리 [근거: wbs 경계]

### 설계

#### 단계별 try-catch 구조

#### `_createCrashDiagnostic` 헬퍼

```typescript
private _createCrashDiagnostic(e: unknown): SerializedDiagnostic {
  const contextLabel = this._formatCrashContext();
  const sdError = e instanceof Error
    ? new SdError(e, `TsCompiler 내부 크래시 @${contextLabel}`)
    : new SdError(`TsCompiler 내부 크래시 @${contextLabel}`, String(e));
  this._logger.debug(sdError.stack ?? sdError.message);
  return {
    category: ts.DiagnosticCategory.Error,
    code: 0,
    messageText: sdError.message,
  };
}
```

#### 단계 간 의존성 처리

| 단계 | 크래시 시 후속 영향 |
|------|---------------------|
| analyzeAsync | `_ngtscProgram` 미설정 → Angular emit/diagnostics에서 `_ngtscProgram` null 체크로 스킵 |
| findAffectedFiles | `affectedFiles=undefined`, `_affectedSourceFiles` 빈 Set → emit/diagnostics는 전체 대상으로 진행 |
| emit | `emitResults=undefined` → diagnostics/lint 영향 없음 |
| collectDiagnostics | diagnostics 빈 배열 → lint 영향 없음 |
| lintAndGlobalScss | `lintResult=undefined` → 다른 결과 영향 없음 |

- **단일 try-catch 유지 + 파일 추적만 추가**: 구현 간단하지만 부분 복구 불가. 한 단계 크래시 시 나머지 정보 전부 유실.
