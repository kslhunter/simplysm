## 구현계획

### 배경

`client.worker.ts`의 `createDevBuildEndHandler`는 esbuild onEnd 콜백을 생성한다. 정상 경로에서는 초기/후속 빌드를 `isInitialBuild` 플래그로 분기하여 초기 빌드는 `initialBuildResolve`로, 후속 빌드는 `sender.send("build")`로 전달한다. 그러나 catch 블록은 이 분기 없이 항상 `sender.send("error")`를 호출하고, 초기 빌드일 때 `initialBuildResolve`도 추가 호출하여 이중 보고가 발생한다. [근거: 리뷰 LOGIC-001]

또한 catch 블록의 `initialBuildResolve`는 `result.warnings`를 포함하지 않아, 정상 경로와 달리 esbuild 경고가 유실된다. [근거: 리뷰 LOGIC-002]

### 목표

- catch 블록의 `sender.send("error")`를 후속 빌드에서만 호출하도록 조건 분기 추가 [근거: Rule "초기 빌드 catch에서는 initialBuildResolve만 사용"]
- catch 블록의 `initialBuildResolve`에 `result.warnings`를 포함 [근거: Rule "catch의 initialBuildResolve에 esbuild warnings를 포함"]

### 비목표

- 정상 경로(try 블록)의 초기/후속 빌드 분기 변경 [근거: wbs 경계 "정상 경로는 변경하지 않음"]
- client-worker.spec.ts에 catch 블록 테스트 추가 [근거: wbs 경계에 테스트 추가 없음, 테스트는 Epic 2에서 다룸]

### 설계

변경 대상: `client.worker.ts:317-324` catch 블록 1곳

현재:
```typescript
} catch (err) {
  const message = errNs.message(err);
  sender.send("error", { message });
  if (isInitialBuild) {
    isInitialBuild = false;
    initialBuildResolve?.({ success: false, errors: [message] });
  }
}
```

변경 후:
```typescript
} catch (err) {
  const message = errNs.message(err);
  if (!isInitialBuild) {
    sender.send("error", { message });
  } else {
    isInitialBuild = false;
    initialBuildResolve?.({
      success: false,
      errors: [message],
      warnings:
        result.warnings.length > 0
          ? result.warnings.map(formatEsbuildMessage)
          : undefined,
    });
  }
}
```

- `if (!isInitialBuild)` 패턴은 정상 경로 line 288과 동일 [근거: D1]
- warnings 변환 패턴은 정상 경로 line 311-314와 동일

### 대안 검토

- **catch에서 항상 두 경로 모두 호출하되 ResultCollector 키 중복을 허용**: Map 덮어쓰기로 동작은 맞지만, 비결정적 최종 상태가 유지보수 위험. 기각.
