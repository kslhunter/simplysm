## 구현계획

### 배경

v14 sd-cli에서 TypeScript 컴파일은 3개 독립 경로로 구현되어 있다:

1. **TSC 경로**: `tsc-build.ts`의 `runTscPackageBuild` 함수 — stateless, 매 호출마다 tsconfig 파싱 + host 생성 + `EmitAndSemanticDiagnosticsBuilderProgram` 생성. `library-build.worker.ts`와 `esbuild-tsc-plugin.ts`에서 호출.
2. **Angular 경로**: `angular-compiler.ts`의 `AngularCompiler` 클래스 — stateful, `NgtscProgram` + `BuilderProgram` + `AngularSourceFileCache` 관리. `angular-build-pipeline.ts`를 거쳐 `ngtsc-build.worker.ts`에서 호출.
3. **esbuild-angular 경로**: `esbuild-angular-compiler-plugin.ts` — 자체 `parseTsconfigFile` + `AngularCompiler` 래핑. `client.worker.ts`에서 esbuild 플러그인으로 사용.

세 경로가 tsconfig 파싱, rootNames 필터링, 프로그램 생성을 각각 독립 구현하여 중복과 불일치 발생. [근거: wbs "rootNames 필터링 누락 같은 버그가 구조적으로 발생"]

### 목표

- 단일 `SdTsCompiler` 클래스로 tsconfig 파싱, rootNames 필터링, compiler host 생성, program 생성 통합 [근거: wbs "통합 SdTsCompiler 클래스"]

```
  → angularCompilerOptions 병합 [Angular 시]
  → tsBuildInfoFile 설정
  → compilerOptionsTransformer [제공 시]
```

- `sourceMap`: Non-Angular이면 `output.js`, Angular이면 `false` [근거: tsc-build.ts:97, ngtsc-build-core.ts:49]

### 대안 검토

**A. 기존 `AngularCompiler` 클래스를 확장하여 Non-Angular 지원 추가**
- 장점: 기존 코드 변경 최소화
- 단점: `AngularCompiler` 이름이 Non-Angular를 포함하여 혼란. 내부 로직이 Angular 전제로 설계됨 (예: `emitAffectedFiles`의 `ignoreForEmit` 분기, `collectDiagnostics`의 Angular 진단 캐시)
- 미선택 사유: 이름과 책임이 불일치. v12의 "하나의 클래스" 설계 방향과도 맞지 않음

**B. `runTscPackageBuild` 함수를 확장하여 Angular 지원 추가**
- 장점: 함수형 접근, 간단한 호출 패턴
- 단점: stateless이므로 Angular의 `AngularSourceFileCache`, `NgtscProgram` 증분 재사용 불가. 매 호출마다 프로그램 재생성으로 성능 저하
- 미선택 사유: Angular 증분 빌드에 필수적인 상태 관리 불가

**C. (선택됨) 새로운 `SdTsCompiler` stateful 클래스**
- 장점: v12 패턴 재사용, Angular/Non-Angular 통합, 증분 빌드 자연스러운 지원, 명확한 책임
- 단점: 신규 코드 작성 필요 (기존 코드 이관)
- 선택 사유: WBS 목표에 가장 부합. v12에서 이미 검증된 패턴
