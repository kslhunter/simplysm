## 구현계획

### 배경

`@simplysm/excel`의 `ExcelCell.setStyle`(`packages/excel/src/excel-cell.ts:236~263`)은 퍼블릭 `ExcelStyleOptions`를 내부 `ExcelStyle`(`packages/excel/src/xml/excel-xml-style.ts:14~21`)로 매핑한다. 현재 매핑(`:258~260`)은 프리셋 `opts.numberFormat`만 `ExcelUtils.convertNumFmtNameToId()`를 통해 `style.numFmtId`로 변환한다.

하위 레이어는 이미 임의의 formatCode를 지원한다:

- `ExcelStyle`에 `numFmtCode?: string` 필드 존재 (`:16`).
- `ExcelXmlStyle.add()`(`:71~106`)와 `addWithClone()`(`:108~185`)에서 `numFmtCode`가 있으면 private `_setNumFmtCode()`(`:284~321`)를 호출해 styles.xml의 `numFmts` 배열에 등록하고 반환된 numFmtId를 cellXf에 반영 + `applyNumberFormat="1"` 설정.
- `_setNumFmtCode()`는 동일 formatCode 중복 등록을 검사(`:286~290`)하고, 사용자 정의 numFmtId를 180부터 증분 할당(`:302~320`).
- 코드 순서상 `numFmtCode`가 뒤에 처리되어 먼저 설정된 `numFmtId`를 덮어쓴다 → **커스텀 우선 우선순위가 하위 레벨에서 이미 구현**.

따라서 이번 Feature의 실질 변경은 **퍼블릭 타입 확장 1건 + 매핑 3줄 수정 + 테스트 6건 + 문서 2개**로 국한된다.

### 목표

- `ExcelStyleOptions.numberFormatCode?: string`로 임의의 Excel formatCode 지정 가능 [근거: Rule "numberFormatCode로 임의의 Excel formatCode를 셀에 적용한다", D1]
- 프리셋+커스텀 동시 지정 시 커스텀 우선 [근거: Rule "동시 지정 시 numberFormatCode가 우선", D2]
- 동일 formatCode는 1회만 등록, 서로 다른 formatCode는 독립 numFmtId [근거: Rule "동일 formatCode는 numFmts에 중복 등록되지 않는다", Rule "서로 다른 formatCode는 독립된 numFmtId로 등록된다"]
- 왕복 변환 후 보존 [근거: Rule "왕복 변환 후 보존"]
- 기존 스타일 속성 보존 [근거: Rule "기존 스타일에 커스텀 formatCode 추가 시 기존 속성이 보존된다"]

### 비목표

- `ExcelCell`에 전용 메서드 추가 [근거: WBS 경계, D5]
- `ExcelNumberFormat` 리터럴 타입 확장 [근거: WBS 경계, D6]
- v12식 체이닝 API 재도입 [근거: WBS 경계]

- `getValue()` 로직 변경 [근거: WBS 경계 — 커스텀 numFmtId는 기존대로 `number` fallback]

### 설계

#### 1) 타입 확장 — `packages/excel/src/types.ts`

`ExcelStyleOptions`에 `numberFormatCode?: string` 필드 추가 [근거: D1]. 기존 `numberFormat` 필드는 그대로 유지 (하위 호환).

```typescript
export interface ExcelStyleOptions {
  /** 배경색 (ARGB 형식, 예: "00FF0000") */
  background?: string;
  /** 테두리 위치 */
  border?: ExcelBorderPosition[];
  /** 가로 정렬 */
  horizontalAlign?: ExcelHorizontalAlign;
  /** 세로 정렬 */
  verticalAlign?: ExcelVerticalAlign;
  /** 숫자 형식 프리셋 */
  numberFormat?: ExcelNumberFormat;
  /**
   * 커스텀 Excel formatCode 문자열 (예: "0.000000", "#,##0.00", "0.00%").
   * `numberFormat`과 동시 지정 시 이 필드가 우선 적용된다.
   */
  numberFormatCode?: string;
}
```

기존 `@example` JSDoc에 `numberFormatCode` 예시 한 줄 추가 (주석만 변경, 동작 영향 없음).

#### 2) 매핑 확장 — `packages/excel/src/excel-cell.ts:258~260`

현재:

```typescript
if (opts.numberFormat != null) {
  style.numFmtId = ExcelUtils.convertNumFmtNameToId(opts.numberFormat).toString();
}
```

변경 [근거: D2, D3]:

```typescript
if (opts.numberFormatCode != null) {
  style.numFmtCode = opts.numberFormatCode;
} else if (opts.numberFormat != null) {
  style.numFmtId = ExcelUtils.convertNumFmtNameToId(opts.numberFormat).toString();
}
```

`else if`로 커스텀이면 프리셋 매핑을 스킵. 내부 `ExcelStyle`에 두 필드가 공존하는 상태를 원천 차단 — 하위 `add/addWithClone`의 동작은 어느 쪽이든 같지만, 디버깅 시 `ExcelStyle` 객체만 보고 의도를 명확히 알 수 있다.

`setStyle`의 JSDoc(`:227~235`)에 `@param opts.numberFormatCode` 한 줄 추가.

#### 3) 테스트 — `packages/excel/tests/excel-cell.spec.ts`

기존 `describe("셀 스타일", ...)` 블록(`:300~`) 말미에 아래 6개 테스트 추가 [근거: sd-testing 규칙 — 실제 인스턴스만 사용, 모킹 없음].

검증은 기존 왕복 테스트(`:352~369`)와 동일한 XML 직접 검증 패턴을 사용한다:

```typescript
const styleData = await (wb as any).zipCache.get("xl/styles.xml");
const xf = styleData.data.styleSheet.cellXfs[0].xf[parseInt(styleId, 10)];
const formatCode = styleData.getNumFmtCode(xf.$.numFmtId);
```

테스트 6건:

| # | 제목 | 검증 내용 | Rule |
|---|---|---|---|
| T1 | `numberFormatCode로 커스텀 숫자 형식 적용` | `"0.000000"` 지정 후 styleId→xf→getNumFmtCode가 `"0.000000"` 반환, `applyNumberFormat === "1"` | Rule 1 |
| T2 | `numberFormat과 numberFormatCode 동시 지정 시 커스텀 우선` | `{ numberFormat: "number", numberFormatCode: "0.000000" }` → formatCode `"0.000000"` | Rule 2 |
| T3 | `동일 formatCode는 numFmts에 중복 등록되지 않음` | 두 셀 같은 `"0.000000"` → 두 xf의 numFmtId 동일, `numFmts[0].numFmt`에서 `"0.000000"` 항목 1개 | Rule 3 |
| T4 | `서로 다른 formatCode는 독립된 numFmtId로 등록` | 세 셀에 `"0.000000"`, `"#,##0.00"`, `"0.00%"` → 서로 다른 numFmtId, 세 항목 모두 등록 | Rule 4 |
| T5 | `왕복 변환 후 커스텀 formatCode 보존` | toBytes → 새 Workbook으로 재로드 → 동일 셀의 styleId로 조회 시 formatCode `"0.000000"` | Rule 5 |
| T6 | `기존 스타일에 커스텀 formatCode 추가 시 기존 속성 보존` | `{ background: "00FF0000" }` 적용 후 `{ numberFormatCode: "0.000000" }` 추가 → 최종 xf에서 fillId의 배경색이 `"00FF0000"`, numFmtId의 formatCode가 `"0.000000"` | Rule 6 |

각 테스트는 기존 테스트의 `ExcelWorkbook` 생성 → `addWorksheet` → `setValue/setStyle` → `getStyleId` → XML 검증 시퀀스를 답습.

### 대안 검토

- **옵션 A: `numberFormat: ExcelNumberFormat | string`으로 union 확장** — 프리셋과 커스텀이 같은 필드에 혼재해 해석 시 예약어 하드코딩 분기가 필요. 타입 안전성 손실. **기각** [근거: AskUserQuestion 결과]
- **옵션 C: `ExcelCell.setNumberFormatCode(code)` 전용 메서드** — v14는 `setStyle({...})` 선언형 일원화 패턴이므로 스타일 설정 경로가 둘로 나뉘는 것을 지양. **기각** [근거: AskUserQuestion 결과]
- **private `_setNumFmtCode`를 public으로 승격** — 추상화 계층 침범. 하위 XML 조작 메서드를 소비자에게 직접 노출하면 향후 리팩토링 자유도 상실. **기각**
- **`setStyle` 매핑에서 `numberFormatCode`가 있어도 `numFmtId`까지 함께 설정** — 하위 `add/addWithClone`의 덮어쓰기 순서 덕에 결과는 동일하나, `ExcelStyle`에 두 필드가 공존하는 상태가 남아 디버깅·리팩토링 시 혼란. 가독성·명시성 위해 `else if` 채택. [근거: D3]
