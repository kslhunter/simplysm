## 구현계획

### 배경

서버 빌드의 esbuild tsc 플러그인(`esbuild-tsc-plugin.ts`)은 현재 `parseTsconfig()` + `runTscPackageBuild()`를 직접 호출한다. Feature 1.1~1.3에서 생성된 `SdTsCompiler`가 동일한 기능을 통합 제공하므로, 플러그인과 워커를 전환한다.

### 목표

- `esbuild-tsc-plugin.ts`가 `SdTsCompiler` 인스턴스를 사용하도록 전환 [근거: WBS "runTscPackageBuild 직접 호출 → SdTsCompiler 인스턴스 사용"]
- `server-build.worker.ts`의 lint 중복 제거 — SdTsCompiler의 lint 통합 활용 [근거: Feature 1.3 "compileAsync 결과에 lint 포함"]
- `server-esbuild-context.ts`의 위임 메서드 호환성 유지 [근거: WBS 경계]

### 비목표

- esbuild 플러그인 구조(onStart/onEnd) 변경 [근거: WBS 경계]
- `server-watch-manager.ts` 로직 변경 [근거: WBS 경계]
- `ServerEsbuildEngine.ts` 인터페이스 변경 [근거: WBS 경계]

### 설계

**esbuild-tsc-plugin.ts 변경:**

- `SdTsCompiler` import, `runTscPackageBuild`/`parseTsconfig` import 제거
- `TscPluginOptions`에 `lint` 필드 추가
- 내부 `SdTsCompiler` 인스턴스를 클로저 변수로 관리 (onStart 시 lazy 생성)
- onStart: `compiler.compileAsync()`를 `Promise.resolve().then()`으로 microtask 스케줄링
- onEnd: `ISdTsCompilerResult`에서 program, affectedFiles, diagnostics, errors, lint 추출
- `resetBuilderProgram()`: `compiler = undefined` (다음 onStart에서 새 인스턴스 생성)
- `TscPluginResult`에 `getLintResult()` getter 추가

**server-esbuild-context.ts 변경:**

- `TscPluginResult.getLintResult` 위임 메서드 `getTscLintResult()` 추가
- 기존 위임 메서드 시그니처 유지

**server-build.worker.ts 변경:**

1. 일회성 빌드 `js=true` 경로:
   - `createTscPlugin`에 `lint` 옵션 전달
   - 별도 `LintWithProgramRunner` 인스턴스 생성 및 실행 코드 제거
   - `tscPlugin.getLintResult()`로 lint 결과 접근

2. 일회성 빌드 `js=false` 경로:
   - `runTscPackageBuild` → `new SdTsCompiler({ output: { js: false, dts }, lint }).compileAsync()`
   - `ISdTsCompilerResult`에서 program, diagnostics, errors, lint 추출

3. watch 모드 `js=true` 경로:
   - `esbuildCtx.createContext()` 시 lint 옵션 전달
   - `rebuildAll()`에서 `esbuildCtx.getTscLintResult()`로 lint 결과 접근
   - 별도 `watchLintRunner` 제거

4. watch 모드 `js=false` 경로:
   - 클로저에 `SdTsCompiler` 인스턴스 보관 (기존 `lastBuilderProgram` 대체)
   - `rebuildAll()`에서 `compiler.compileAsync()` 호출
   - `ISdTsCompilerResult`에서 lint 결과 포함

### 대안 검토

- **SdTsCompiler를 플러그인 외부에서 생성하여 주입**: 유연하지만 생명주기 관리가 복잡해짐. 현재 `createTscPlugin`이 내부에서 관리하는 패턴이 더 단순
- **SdTsCompiler에 reset() 메서드 추가**: 가능하지만 `createContext()`가 새 플러그인을 생성하므로 인스턴스 재생성이 자연스러움
