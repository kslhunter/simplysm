### 설계 결정
| # | 결정사항 | 선택 | 근거 |
|---|---------|------|------|
| D1 | NgtscProgram 노출 방식 | `ISdTsCompilerResult`에 `ngtscProgram?: NgtscProgram` 필드 추가 | HMR은 `compileAsync` 이후에만 사용하므로 result 포함이 자연스러움. staleSourceFiles는 이전 result의 `program`에서 캡처 가능. getter 방식은 불필요한 상태 관리 추가 |
| D2 | SerializedDiagnostic → esbuild PartialMessage 변환 | `result.program`으로 line/column 계산하는 어댑터 함수 생성 | `SerializedDiagnostic.start` (byte offset) + `result.program.getSourceFile(fileName).getLineAndCharacterOfPosition(start)`로 line/column 산출 가능. 기존 타입 변경 불필요 |
| D3 | 클라이언트 SCSS 상태 흐름 | 외부 콜백(plugin-owned maps)을 통한 흐름 유지 | `createClientTransformStylesheet`가 plugin-owned `stylesheetDependencies`/`stylesheetErrors`에 직접 기록. SdTsCompiler 내부 SCSS 상태는 라이브러리용. 클라이언트는 plugin이 직접 관리 |
| D4 | `AngularCompilerPluginOptions` 인터페이스 유지 | 인터페이스 구조 유지, 내부 구현만 SdTsCompiler로 교체 | plugin-specific 옵션(JavaScriptTransformer, loadResultCache, typeScriptFileCache 등)은 SdTsCompiler와 무관. 인터페이스 변경 최소화 |

## 구현계획

### 배경
현재 클라이언트 빌드 경로는 `esbuild-angular-compiler-plugin.ts`에서 `parseTsconfigFile` + `AngularCompiler`를, `vite-angular-plugin.ts`에서 `AngularBuildPipeline`을 각각 사용한다. Feature 1.1~1.3에서 `SdTsCompiler`가 이 로직을 통합했으므로, 호출부를 전환한다.

### 목표
- `esbuild-angular-compiler-plugin.ts` 내부의 `AngularCompiler` 직접 사용을 `SdTsCompiler`로 교체 [근거: Rule "esbuild 플러그인이 SdTsCompiler를 사용하여 첫 빌드를 수행한다"]
- `vite-angular-plugin.ts`의 `AngularBuildPipeline` 사용을 `SdTsCompiler`로 교체 [근거: Rule "vite-angular-plugin이 SdTsCompiler를 사용한다"]
- 중복 `parseTsconfigFile` 제거 [근거: Rule "parseTsconfigFile 중복 제거"]

### 비목표

### 설계

#### ISdTsCompilerResult 확장

`sd-ts-compiler-result.ts`에 `ngtscProgram` 필드 추가:

```typescript
import type { NgtscProgram } from "../angular/angular-build";

export interface ISdTsCompilerResult {
  // ... 기존 필드 ...
  /** NgtscProgram 참조 (Angular only, HMR용). Non-Angular이면 undefined */
  ngtscProgram?: NgtscProgram;
}
```

`SdTsCompiler.compileAsync()`의 return에 `ngtscProgram: this._ngtscProgram` 추가.

#### SerializedDiagnostic → esbuild PartialMessage 변환 함수

`esbuild-angular-compiler-plugin.ts`에 `convertDiagnostic`을 대체하는 함수:

```typescript
function convertSerializedDiagnosticToEsbuild(
  d: SerializedDiagnostic,
  program: ts.Program,
  cwd: string,
): esbuild.PartialMessage {
  let location: esbuild.PartialMessage["location"] = null;
  if (d.file != null && d.start != null) {
    const sf = program.getSourceFile(d.file.fileName);
    if (sf != null) {
      const pos = sf.getLineAndCharacterOfPosition(d.start);
      location = {
        file: path.relative(cwd, d.file.fileName),
        line: pos.line + 1,
        column: pos.character,
      };
    }
  }
  return { text: d.messageText, location };
}
```

#### esbuild 플러그인 전환 (핵심)

`createAngularCompilerPlugin`의 `setup()` 내부:

1. **SdTsCompiler 인스턴스 생성** (클로저에 보관):
   ```typescript
   const sdTsCompiler = new SdTsCompiler({
     pkgDir: path.dirname(pluginOptions.tsconfig),
     cwd,
     output: { js: true, dts: false },
     sourceFileCache: pluginOptions.sourceFileCache,
     transformStylesheet: pluginOptions.transformStylesheet,
     externalStylesheets: pluginOptions.externalStylesheets,
     compilerOptionsTransformer: createCompilerOptionsTransformer(pluginOptions, preserveSymlinks),
   });
   ```

2. **`handleFirstBuild` 교체**: `parseTsconfigFile` + `new AngularCompiler(...)` → `sdTsCompiler.compileAsync(undefined, emitOptions)`
3. **`handleIncrementalBuild` 교체**: `angularCompiler.update(expandedModifiedFiles)` → `sdTsCompiler.compileAsync(expandedModifiedFiles, emitOptions)`
4. **onStart 통합 흐름**:
   - stylesheetErrors 리셋
   - 증분 빌드 시: staleSourceFiles 캡처 (이전 `lastResult.program`에서), referencedFileTracker.update, additionalResults 클리어
   - processWebWorker + workerTransformer 생성
   - `sdTsCompiler.compileAsync(modifiedFiles, { additionalTransformers: { before: [workerTransformer] } })`
   - emitResults → typeScriptFileCache 매핑
   - diagnostics → esbuild errors/warnings 변환 (`convertSerializedDiagnosticToEsbuild` 사용)
   - stylesheetDependencies → referencedFileTracker 브릿징
   - stylesheetErrors → esbuild errors 브릿징
   - HMR: `result.ngtscProgram`으로 `collectHmrCandidates` + `emitHmrUpdateModule`

5. **onLoad 훅 플래그**: `shouldTsIgnoreJs`, `useTypeScriptTranspilation`은 첫 빌드 후 `result.program.getCompilerOptions()`에서 결정

6. **제거 대상**: `parseTsconfigFile` 함수, `angularCompiler` 변수, `handleFirstBuild`/`handleIncrementalBuild` 서브함수 (onStart에 통합)

#### vite-angular-plugin 전환

`AngularBuildPipeline` → `SdTsCompiler` + 로컬 Map:

```typescript
let sdTsCompiler: SdTsCompiler | undefined;
const emittedFilesBySource = new Map<string, string>();

// buildStart:
const result = await sdTsCompiler.compileAsync(
  pendingWatchChanges.size > 0 ? pendingWatchChanges : undefined,
);
for (const r of result.emitResults ?? []) {
  emittedFilesBySource.set(pathx.posix(r.sourceFileName), r.contents);
}
// diagnostics 보고

// transform:
const emitted = emittedFilesBySource.get(normalizedId);
```

### 대안 검토

1. **NgtscProgram getter vs result property**: getter는 old/new program 구분이 모호하고 별도 상태 관리 필요. result property는 각 compileAsync 호출의 결과로 명확히 구분됨. → result property 선택
2. **Raw ts.Diagnostic[] 반환 vs SerializedDiagnostic 변환**: raw 반환은 순환 참조 포함으로 직렬화 불가. `result.program`으로 line/column 계산은 순환 참조 없이 동일 결과 도출. → SerializedDiagnostic + program 변환 선택
3. **SCSS 상태를 SdTsCompiler에 통합 vs plugin 유지**: 클라이언트의 `createClientTransformStylesheet`가 plugin-owned maps에 직접 기록하는 구조. SdTsCompiler 내부 SCSS 상태는 라이브러리용(`createLibraryTransformStylesheet` 자동 생성 시). 양쪽 경로를 통합하려면 callback 인터페이스 변경 필요 → 기존 구조 유지 선택
