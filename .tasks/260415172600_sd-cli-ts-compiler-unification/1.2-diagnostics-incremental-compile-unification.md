## 구현계획

### 배경

Feature 1.1에서 `SdTsCompiler` 클래스가 생성되어 tsconfig 파싱, rootNames 필터링, compiler host 생성, program 생성 (`compileAsync`)이 통합되었다. 현재 `compileAsync`는 `{ program, builderProgram, isForAngular }`만 반환하며, affected files 추적, emit, diagnostics 수집은 아직 분산된 상태이다:

- **Non-Angular**: `tsc-build.ts:153-198`에서 affected files + emit + diagnostics를 `runTscPackageBuild` 함수 내에서 처리
- **Angular**: `angular-compiler.ts:298-563`에서 `_findAffectedFiles`, `emitAffectedFiles`, `collectDiagnostics` 3개 메서드로 분리

Feature 1.2는 이 세 기능을 `SdTsCompiler.compileAsync` 내부로 통합한다.

[근거: WBS "진단이 4곳에 분산되어 일관성 유지가 어려움"]

### 목표

- `compileAsync`가 compile → affected → emit → diagnostics 전체 파이프라인을 실행 [근거: D1 결정]
- affected files 추적 통합 (Non-Angular: `Set<string>`, Angular: 리소스 의존성 포함) [근거: WBS "affected files 추적 통합"]
- 진단 수집 통합 (7종 Non-Angular + Angular template 진단, `isWorkspaceDiagnostic` 필터 + `serializeDiagnostic` 직렬화) [근거: WBS "진단 수집 통합"]
- Angular emit 통합 (`emitAffectedFiles` 패턴, `EmitResult[]` 반환) [근거: WBS "emit 처리 통합"]
- TypeScript 5.9 + NgtscProgram 크래시 방어 패턴 보존 [근거: angular-compiler.ts:308-336, 482-486, 534-541]

### 비목표

- esbuild용 `convertDiagnostic` (ts.Diagnostic → esbuild PartialMessage) 변환 [근거: WBS 경계 "컴파일러 자체에 esbuild 의존성을 넣지 않음"]

공통 후처리:
```typescript
private _finalizeDiagnostics(rawDiagnostics: ts.Diagnostic[]): {
  diagnostics: SerializedDiagnostic[];
  errorCount: number;
  warningCount: number;
  errors?: string[];
} {
  const filtered = rawDiagnostics.filter(d => isWorkspaceDiagnostic(d, this._options.cwd));
  const serialized = filtered.map(serializeDiagnostic);
  const errorCount = filtered.filter(d => d.category === ts.DiagnosticCategory.Error).length;
  const warningCount = filtered.filter(d => d.category === ts.DiagnosticCategory.Warning).length;
  const errors = filtered
    .filter(d => d.category === ts.DiagnosticCategory.Error)
    .map(formatDiagnosticError);
  return { diagnostics: serialized, errorCount, warningCount, errors: errors.length > 0 ? errors : undefined };
}
```

### 대안 검토

**A. affected files/emit/diagnostics를 각각 독립 메서드로 노출**
- 장점: 유연성 극대화, 호출자가 단계별 제어 가능
- 단점: 호출 순서 실수 위험 (emit 전 diagnostics 호출 시 결과 불완전), v12 패턴 불일치
- 미선택 사유: D1 결정에서 단일 메서드 방식 채택

**B. Non-Angular도 EmitResult[]를 반환하는 방식으로 emit 통일**
- 장점: Angular/Non-Angular 간 API 완전 통일
- 단점: Non-Angular은 writeFile 훅으로 이미 디스크에 쓰기를 수행하므로 EmitResult 수집이 불필요한 오버헤드. 호출부(library-build.worker)에서 반환된 EmitResult를 다시 디스크에 쓰는 이중 작업 발생
- 미선택 사유: Non-Angular은 writeFile 훅 경유가 자연스러움 (Feature 1.1에서 이미 설정)

**C. (선택됨) Non-Angular은 내부 emit + undefined, Angular은 EmitResult[] 반환**
- 장점: 각 경로의 기존 패턴을 최대한 보존하면서 단일 메서드로 통합
- 단점: result.emitResults의 존재 여부가 isForAngular에 의존
- 선택 사유: 기존 코드의 동작을 변경 없이 이관 가능, 호출부 변경(Epic 2) 시 자연스러운 전환
