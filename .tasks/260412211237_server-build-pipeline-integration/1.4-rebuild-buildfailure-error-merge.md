## 구현계획

### 배경

현재 `rebuild()` 함수(`server-esbuild-context.ts:72-99`)는 `context.rebuild()`를 직접 await한다. esbuild는 빌드 에러 시 `BuildFailure`를 throw하므로, 에러 병합 코드(`:89-91`)에 도달하지 못하고 tsc 에러가 누락된다. `build()` 함수(`server-build.worker.ts:168-185`)에서는 `.catch()` 패턴으로 이 문제를 방지하고 있다. [근거: 리뷰 LOGIC-001]

### 목표

- `context.rebuild()` throw 시 에러를 catch하여 tsc 에러와 병합 [근거: Rule "context.rebuild() throw 시 에러를 catch"]
- 반환 타입 불변 [근거: WBS 경계]

### 비목표

- `build()` 함수의 `.catch()` 패턴 변경 [근거: WBS 경계]
- 정상 경로 동작 변경 [근거: Rule "정상 경로 불변"]
- `server-watch-manager.ts` 변경 [근거: WBS 경계]

### 설계

**대상 파일:** `packages/sd-cli/src/workers/server-esbuild-context.ts`

**1. import 추가:**

```typescript
import { err as errNs } from "@simplysm/core-common";
```
[근거: `errNs.message(err)` 사용을 위해. `server-build.worker.ts:6` 패턴]

**2. `rebuild()` 변경:**

```typescript
export async function rebuild(): Promise<{
  success: boolean;
  errors?: string[];
  warnings?: string[];
} | null> {
  if (context == null) return null;

  let result: esbuild.BuildResult;
  try {
    result = await context.rebuild();
  } catch (err) {
    // esbuild BuildFailure 또는 기타 에러 처리
    const tscErrors = tscPlugin?.getErrors() ?? [];
    const allErrors = [errNs.message(err), ...tscErrors];
    return {
      success: false,
      errors: allErrors.length > 0 ? allErrors : undefined,
      warnings: undefined,
    };
  }

  // 정상 경로 — 기존 코드 유지
  if (result.metafile != null) {
    lastMetafile = result.metafile;
  }

  if (result.outputFiles) {
    await writeChangedOutputFiles(result.outputFiles);
  }

  const esbuildErrors = result.errors.map((e) => e.text);
  const tscErrors = tscPlugin?.getErrors() ?? [];
  const allErrors = [...esbuildErrors, ...tscErrors];
  const warnings = result.warnings.map((w) => w.text);

  return {
    success: allErrors.length === 0,
    errors: allErrors.length > 0 ? allErrors : undefined,
    warnings: warnings.length > 0 ? warnings : undefined,
  };
}
```
[근거: Rule "throw 시 에러를 catch" + D1 "errNs.message(err) 사용"]

**3. 테스트 추가 (`server-esbuild-context.spec.ts`):**

`rebuild` describe에 reject 시나리오 추가:
- `context.rebuild()` reject + tsc 에러 없음 → esbuild 에러만 반환
- `context.rebuild()` reject + tsc 에러 있음 → 에러 병합
- `context.rebuild()` reject + tsc 플러그인 없음 → esbuild 에러만 반환
- `context.rebuild()` reject 시 이전 metafile 유지

### 대안 검토

1. **BuildFailure.errors 개별 추출**: `(err as any).errors?.map(e => e.text)`. 더 상세한 에러 정보이지만, `as any` 캐스팅 필요 + `build()` 패턴과 비대칭. **선택하지 않음.** [근거: D1]

2. **rebuild() 호출자에서 catch 후 tsc 조회**: `rebuildAll()`에서 `rebuild()` throw를 catch하고 `esbuildCtx.getTscProgram()` 등을 조회. `rebuild()` 내부 수정 불필요이지만, 호출자마다 에러 처리 로직 중복 + `startServerWatchLoop`의 catch도 수정 필요. **선택하지 않음.** [근거: 관심사 분리 — 에러 병합은 rebuild()의 책임]
