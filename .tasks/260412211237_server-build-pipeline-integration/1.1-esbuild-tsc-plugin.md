## 구현계획

### 배경

현재 서버 빌드 파이프라인에서 esbuild(TS→JS transpile + 번들링)와 tsc(타입체크 + DTS emit)가 `server-build.worker.ts`에서 수동으로 병렬 실행된다 (`server-build.worker.ts:146-185`). 클라이언트 빌드는 이미 `createCompilerPlugin`으로 esbuild 플러그인 내에 Angular AOT 컴파일러를 통합하고 있으나 (`esbuild-client-config.ts:99`), 서버는 분리 구조를 유지하고 있다. [근거: WBS 프로젝트 개요]

### 목표

- esbuild 플러그인으로 tsc를 통합하여 단일 `esbuild.build()` / `context.rebuild()` 호출로 타입체크 + DTS emit을 처리 [근거: Rule "createTscPlugin은 esbuild.Plugin과 getter 객체를 반환한다"]
- microtask 스케줄링으로 esbuild Go 네이티브 transpile과 tsc의 실질적 병렬성 유지 [근거: Rule "onStart에서 tsc를 microtask로 스케줄링하고 await하지 않는다"]
- BuilderProgram 캐싱으로 watch 모드 증분 빌드 지원 [근거: Rule "lastBuilderProgram을 캐싱하여 watch 모드 증분 빌드를 지원한다"]

### 비목표

- lint 실행 — 워커에서 ts.Program을 받아 처리 [근거: WBS 경계 "lint 실행 자체는 이 플러그인에서 하지 않음"]
- esbuild 옵션 생성 변경 [근거: WBS 경계 "createServerEsbuildOptions은 변경하지 않음"]
- esbuild TS→JS transpile 변경 [근거: WBS 경계 "플러그인은 타입체크 + DTS만 담당"]
- output.js === false 시 fallback — Feature 1.3에서 처리 [근거: WBS 경계]

### 설계

**새 파일:** `packages/sd-cli/src/esbuild/esbuild-tsc-plugin.ts`

**인터페이스:**

```typescript
import type esbuild from "esbuild";
import type ts from "typescript";
import type { TypecheckEnv } from "../utils/tsconfig";
import type { SerializedDiagnostic } from "../typecheck/typecheck-serialization";

export interface TscPluginOptions {
  pkgDir: string;
  cwd: string;
  output: { dts: boolean };
  env?: TypecheckEnv;
  includeTests?: boolean;
}

export interface TscPluginResult {
  plugin: esbuild.Plugin;
  getProgram(): ts.Program | undefined;
  getAffectedFiles(): ReadonlySet<string> | undefined;
  getDiagnostics(): SerializedDiagnostic[];
  getErrors(): string[] | undefined;
  resetBuilderProgram(): void;
}
```
[근거: WBS "옵션: pkgDir, cwd, output: { dts: boolean }, env?, includeTests?" + 설계 결정 D1]

**핵심 메커니즘:**

1. **onStart**: microtask 내에서 `parseTsconfig(pkgDir)` + `runTscPackageBuild()` 실행. `Promise.resolve().then()` 패턴으로 Promise를 생성하되 await하지 않음 [근거: Rule "onStart에서 tsc를 microtask로 스케줄링" + 설계 결정 D2]
2. **onEnd**: tsc Promise를 await하여 결과를 클로저 변수에 저장. `result.errors`에 push하지 않음 [근거: Rule "result.errors에 push하지 않는다"]
3. **Getter**: 클로저 변수를 직접 참조하여 외부 접근 제공 [근거: Rule "getter는 마지막 빌드 결과를 반환한다"]

**의존 모듈 (import 필요):**

- `runTscPackageBuild`, `TscPackageBuildResult` — `../utils/tsc-build` [근거: 기존 tsc 빌드 함수 재사용]
- `parseTsconfig` — `../utils/tsconfig` [근거: tsconfig 파싱]
- `err as errNs` — `@simplysm/core-common` [근거: 에러 메시지 추출 (`server-build.worker.ts:6` 패턴)]

### 대안 검토

1. **onStart에서 tsc await (12.x 방식)**: onStart에서 tsc를 완료 후 빌드 진행. 12.x에서는 onLoad에서 tsc emit JS를 전달하기 위해 필요했으나, 14.x는 esbuild 자체 transpile을 사용하므로 불필요. 직렬 실행으로 성능 저하. **선택하지 않음.** [근거: WBS "12.x는 onStart에서 await했으나, 이번에는 await하지 않고 microtask로 병렬 실행"]

2. **result.errors에 push**: onEnd에서 `result.errors.push(...tscErrors)`. esbuild가 `BuildFailure`를 throw할 위험. **선택하지 않음.** [근거: WBS "result.errors에 push하면 esbuild.build()가 BuildFailure를 throw할 위험"]

3. **parseTsconfig를 onStart 동기 호출 (microtask 외부)**: onStart에서 `parseTsconfig`를 동기 호출 후 microtask 생성. parseTsconfig 예외 시 tscPromise가 미생성되어 onEnd에서 상태 갱신 불가. **선택하지 않음.** [근거: 설계 결정 D2]
