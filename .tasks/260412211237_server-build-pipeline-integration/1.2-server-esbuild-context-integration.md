## 구현계획

### 배경

현재 `server-esbuild-context.ts`는 esbuild watch context만 관리하며, tsc는 `server-build.worker.ts`에서 별도로 수동 실행된다 (`server-build.worker.ts:243-296`). Feature 1.1에서 구현된 `createTscPlugin()`(`esbuild-tsc-plugin.ts`)을 esbuild context에 통합하면, 단일 `rebuild()` 호출로 esbuild transpile + tsc 타입체크를 함께 트리거할 수 있다. [근거: WBS 프로젝트 개요]

### 목표

- `createContext()`에서 tsc 플러그인을 생성하여 esbuild context에 포함 [근거: Rule "createContext에서 tsc 옵션 제공 시 플러그인 생성"]
- `rebuild()`에서 tsc 에러를 esbuild 에러와 자동 병합 [근거: Rule "rebuild에서 esbuild 에러와 tsc 에러를 병합"]
- `recreateContext()`에서 tsc 증분 상태 리셋 [근거: Rule "recreateContext에서 LOGIC-001 + tsc resetBuilderProgram"]
- 위임 메서드로 tsc 결과 외부 접근 제공 [근거: Rule "위임 메서드가 tsc 플러그인 상태를 외부에 노출"]

### 비목표

- `server-build.worker.ts` 변경 — Feature 1.3 범위 [근거: WBS Feature 1.3]
- `server-watch-manager.ts` 코드 변경 [근거: WBS "실질적 코드 변경 없음. 동작 확인만 수행"]
- `createServerEsbuildOptions()` 변경 [근거: WBS 경계]

### 설계

**대상 파일:** `packages/sd-cli/src/workers/server-esbuild-context.ts`

**1. `EsbuildContextOptions` 확장** [근거: WBS "인터페이스에 tsc 관련 옵션 추가" + 설계 결정 D1]

```typescript
export interface EsbuildContextOptions {
  pkgDir: string;
  entryPoints: string[];
  env?: Record<string, string>;  // esbuild define (기존)
  external: string[];
  tsc?: {                         // tsc 플러그인 옵션 (신규, optional)
    cwd: string;
    output: { dts: boolean };
    env?: TypecheckEnv;
    includeTests?: boolean;
  };
}
```

**2. 모듈 스코프 상태** [근거: WBS "플러그인 인스턴스를 모듈 스코프에 보관"]

```typescript
let tscPlugin: TscPluginResult | undefined;
```

**3. `createContext()` 변경** [근거: WBS "tsc 플러그인을 포함한 esbuild context 생성" + 설계 결정 D2]

- `options.tsc` 존재 → `createTscPlugin({ pkgDir: options.pkgDir, ...options.tsc })` 호출, 모듈 스코프에 저장
- `options.tsc` 부재 → 기존 `tscPlugin` 재사용 (watch 중 `recreateContext` 경유)
- `esbuild.context()` 호출 시 `plugins: tscPlugin != null ? [tscPlugin.plugin] : []`

**4. `rebuild()` 변경** [근거: Rule "rebuild에서 esbuild 에러와 tsc 에러를 병합"]

- `context.rebuild()` 실행 (tsc 플러그인의 onStart/onEnd가 자동 트리거됨)
- `tscPlugin?.getErrors() ?? []`로 tsc 에러 조회
- `[...esbuildErrors, ...tscErrors]` 병합
- `success: allErrors.length === 0`
- metafile 갱신, outputFiles 기록은 기존 동작 유지

**5. `recreateContext()` 변경** [근거: WBS "LOGIC-001 + resetBuilderProgram()" + 설계 결정 D3]

- LOGIC-001 선제 초기화 단계에 `tscPlugin?.resetBuilderProgram()` 추가
- `createContext(options)` 호출 — `options.tsc` 없으면 기존 플러그인 재사용

**6. `dispose()` 변경** [근거: WBS "플러그인 참조 해제"]

- `tscPlugin = undefined` 추가 (context dispose 이전)

**7. 위임 메서드** [근거: WBS "새 메서드 (플러그인 getter 위임)"]

```typescript
getTscProgram(): ts.Program | undefined       → tscPlugin?.getProgram()
getTscAffectedFiles(): ReadonlySet<string> | undefined → tscPlugin?.getAffectedFiles()
getTscDiagnostics(): SerializedDiagnostic[]   → tscPlugin?.getDiagnostics() ?? []
```

**의존 모듈 (import 추가):**

```typescript
import type ts from "typescript";
import { createTscPlugin, type TscPluginResult } from "../esbuild/esbuild-tsc-plugin";
import type { TypecheckEnv } from "../utils/tsconfig";

```

### 대안 검토

1. **tsc 옵션을 flat 필드로 추가 (`tscEnv` 등 이름 변경)**: `env` 충돌을 `tscEnv`로 해결. 단, `cwd`, `includeTests` 등이 tsc 전용임을 구분하기 어려움. optional 필드가 많아져 필수/선택 구분 모호. **선택하지 않음.** [근거: codebase `ServerBuildInfo.pm2`의 nested optional 패턴과 일관성]

2. **`createContext()`에서 항상 새 플러그인 생성**: `recreateContext()`에서도 tsc 옵션 재전달 필요 → `server-watch-manager.ts` 호출부 변경 필요. **선택하지 않음.** [근거: WBS "실질적 코드 변경 없음"]

3. **tsc 플러그인을 별도 함수로 분리 관리**: `createContext`와 별개로 `initTscPlugin()`, `disposeTscPlugin()` 추가. API 표면 증가, 호출 순서 관리 복잡. **선택하지 않음.** [근거: WBS "createContext(): tsc 플러그인을 포함한 esbuild context 생성" — 통합 의도 명확]
