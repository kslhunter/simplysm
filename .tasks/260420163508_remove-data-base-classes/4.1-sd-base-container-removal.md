## 구현계획

### 배경

Feature 4.1은 `SdBaseContainer`가 감추던 "페이지/모달/control 분기 + 타이틀 계산 + 권한 제한 + 초기화 숨김 + busy 오버레이" 조합을 **레시피 형태로 풀어쓰기**하여, LLM 에이전트 세션에서 이 추상화 층을 참조하지 않고도 소비 화면을 조립할 수 있게 한다. 실제 `sd-base-container.ts` 파일 삭제는 `src/data/data-sheet/*`·`src/data/data-detail/*`의 참조가 선행(Feature 1.1/2.1)돼야 하므로, 사용자 결정(D1, 2026-04-20)에 따라 Feature 6.1로 이관된다.

섹션 구성:

1. **Overview** — 이 레시피가 대체하는 구 API(`SdBaseContainer`)와 도입 배경(레시피 기반 조립). 문서 상단에 "Feature 6.1 완료 이후의 `injectViewTypeSignal()` 신 시그니처를 기준으로 작성되었습니다" 주의문 1줄.
2. **언제 사용하는가** — 페이지, 모달, control 뷰를 **같은 컴포넌트**로 재사용하고 싶은 모든 화면. 페이지·모달 중 하나만 쓰는 화면은 분기를 생략해도 됨을 명시.
3. **완성 예제 (Full Component)** — standalone + OnPush + `ViewEncapsulation.None` 기반 단일 컴포넌트 전체 코드. 다음을 모두 포함:
   - `inject` 체인: `SdAppStructureProvider`, `SdActivatedModalProvider` (optional), `SdSystemLogProvider`, `injectCurrentPageCodeSignal`, `injectFullPageCodeSignal`, `injectViewTypeSignal` (인자 없이 호출)
   - signal inputs: `header = input<string>()`, `restricted = input(false, { transform: booleanAttribute })`, `initialized = input<boolean | undefined>(undefined)`, `busy = input(false, { transform: booleanAttribute })`, `busyMessage = input<string>()`, `viewType = input<SdViewType>()` (선택적 오버라이드)
   - computed: `currViewType`, `modalOrPageTitle`
   - 템플릿: `<sd-busy-container>` 최상위 → `@if (initialized() == null || initialized())` → `@if (restricted())` / `@else if (currViewType() === "page")` (`<sd-topbar-container>` + `<sd-topbar>` + `<h4>{{ modalOrPageTitle() }}</h4>` + 페이지 topbar 보조 슬롯 + 본문) / `@else if (currViewType() === "modal")` (flex-column + 본문 + 선택적 bottom 슬롯) / `@else` (raw 본문)
   - 본문은 `<!-- 여기에 화면 본문 -->` 주석으로 표기하여 소비 화면이 채우도록 안내
4. **분해 설명** — 각 블록(`<sd-busy-container>`, `@if (initialized() == null || initialized())`, `@if (restricted())`, `@if page`, `@if modal`, `@else control`, `modalOrPageTitle`)이 담당하는 역할과 근거. 원본 `sd-base-container.ts:41-113` 코드와 1:1 대응.
5. **뷰 타입 결정** — `injectViewTypeSignal()` 동작 설명(모달 provider 존재 → modal, 라우트 컴포넌트 일치 → page, 그 외 → control). `viewType` input 오버라이드는 "필요 시" 한 단락으로만 언급(기본 사용 패턴은 인자 없는 호출).
6. **타이틀 우선순위** — `header() ?? modalComponent().title() ?? getTitleByFullCode(currPageCode() ?? fullPageCode())`. try/catch 래핑 이유(`getTitleByFullCode`가 아이템 미등록 시 throw하므로 빈 문자열 fallback + `writeAsync("warn", ...)`).
7. **주의사항** — (a) 신규 유틸 함수를 추출하지 말 것(추상화 재도입). (b) `injectParent` 사용 금지(Angular internal 트릭, Feature 6.1에서 삭제). (c) `<sd-base-container>`는 Feature 6.1 완료 후 제거되므로 신규 코드에서는 쓰지 말 것.

레시피는 **공개 API로 남는 심볼만** 참조한다: `SdBusyContainer`, `SdTopbarContainer`, `SdTopbar`, `SdViewType`, `injectCurrentPageCodeSignal`, `injectFullPageCodeSignal`, `injectViewTypeSignal`, `SdAppStructureProvider`, `SdActivatedModalProvider`, `SdSystemLogProvider`. [근거: wbs.md:213-216]

### 대안 검토

- **Alt1: 레시피를 `docs/recipes/` 대신 `docs/features.md`에 인라인 추가**
  - 기각 사유: WBS가 `docs/recipes/` 경로 명시 (wbs.md:20). 기존 `features.md`는 개별 Feature의 구현 문서이며, "조립 패턴 스니펫"인 레시피와 목적이 다름. 레시피가 features.md에 섞이면 1.1~3.1의 레시피도 같은 파일을 수정하게 되어 충돌 가능성 증가.

- **Alt2: `useBaseContainer()` 헬퍼 도입으로 signal·computed 묶음 제공**
  - 기각 사유: wbs.md:217 "새로운 유틸 함수는 만들지 않음(추상화 재도입 방지)" / D5 위반. 본 WBS의 Goal(추상화 0)과 정반대.

- **Alt3: 레시피에서 `injectViewTypeSignal`을 쓰지 않고 `ElementRef.tagName` + `reflectComponentType` 직접 비교 예제 제공**
  - 기각 사유: wbs.md:213-214 `injectViewTypeSignal`은 유지 대상 + 6.1에서 신 시그니처로 정비 예정. 재활용이 자연스럽고, 내부 복잡도를 유틸에 위임하는 것이 "추상화 재도입"에 해당하지 않음(기존 공개 API 재사용).

- **Alt4: 파일 삭제·index.ts export 제거까지 4.1에서 처리하기 위해 data-sheet/data-detail 참조를 선제 제거**
  - 기각 사유: Feature 경계 침범(1.1/2.1 범위). 4.1이 1.1/2.1보다 먼저 수행된다는 WBS 의존성 매트릭스(wbs.md:345-347)와 양립하려면 중간 상태에서 참조자만 일시 제거하는 패치가 필요한데, 1.1/2.1에서 어차피 파일 통째 삭제되므로 이중 작업. 사용자 결정(D1, 2026-04-20)으로 이 대안은 최종 기각.

- **Alt5: `base-container.spec.ts`를 레시피 예제 기반 통합 테스트로 대체**
  - 기각 사유: 레시피는 문서이며, 소비 앱이 복사해 쓰는 스니펫이므로 라이브러리 내부 테스트 대상이 아님. 레시피가 참조하는 구성 요소(`SdBusyContainer`, `SdTopbarContainer`, `injectViewTypeSignal` 등)는 이미 각자의 spec을 보유. [근거: D4]
