## 구현계획

### 배경

3개 커맨드 테스트 파일에 sd-testing.md 위반이 존재한다:
- publish.spec.ts: 내부 함수(`runBuild`) 인자 검증 1건
- check.spec.ts: mock 호출 여부/인자 검증 ~18건
- typecheck.spec.ts: mock 호출 횟수/인자 검증 ~25건

관련 순수 함수(`toTypecheckEnvs`, `discoverWorkspacePackages`)는 이미 별도 테스트가 존재하므로, 통합 테스트에서 mock 인자 검증을 제거해도 커버리지 손실이 없다. [근거: typecheck-env.spec.ts, package-utils.spec.ts]

### 목표

- 구현 결합 검증(mock 호출 횟수/인자)을 결과 기반 검증(exitCode, stdout, result 객체)으로 전환 [근거: sd-testing.md "구현 결합 검증 금지"]
- 외부 사이드이펙트 검증(프로세스 실행, 파일 쓰기)은 유지 [근거: sd-testing.md "사이드이펙트를 검증한다"]
- 기존 시나리오 커버리지 유지 [근거: WBS "불필요한 mock 제거 후에도 테스트가 동일 시나리오를 커버하는지 검증"]

### 비목표

- 새로운 테스트 시나리오 추가 (Decision Table에서 누락 발견된 check types 조합 2건은 별도 이슈) [근거: WBS 경계]
- 정당한 mock 제거 (네트워크/파일시스템/외부 프로세스/CompilerHost 등) [근거: sd-testing.md "물리적으로 돌아갈 수 없는 것만 mock"]
- 프로덕션 코드 구조 변경 (함수 추출 등) [근거: 이미 필요한 함수가 추출되어 있음]

### 설계

**publish.spec.ts 변경:**
- `mocks.runBuild.mock.calls[0][0].targets` 인자 검증 → `getExecaCalls("pnpm", "publish")` 결과에서 publish 설정 없는 패키지 미포함 확인으로 전환 [근거: D1]
- 나머지 테스트(getExecaCalls, fsx.write.mock.calls)는 외부 사이드이펙트 검증으로 현행 유지

**check.spec.ts 변경:**
- `expect(mocks.executeTypecheck).toHaveBeenCalled()` → `expect(stdoutOutput).toContain("TYPECHECK")` [근거: D2]
- `expect(mocks.executeTypecheck).not.toHaveBeenCalled()` → `expect(stdoutOutput).not.toContain("TYPECHECK")` [근거: D2]
- `expect(mocks.executeTypecheck).toHaveBeenCalledWith(expect.objectContaining({targets: [...]}))` → 제거. 경로 변환은 discoverWorkspacePackages 단위 테스트에서 커버 [근거: D2]
- `expect(mocks.executeLint).toHaveBeenCalledWith(...)` → `expect(stdoutOutput).toContain("LINT")` + exitCode 검증 [근거: D2]
- `expect(mocks.runLintInWorker).not.toHaveBeenCalled()` → 제거. lint 결과가 engine lint에서 왔는지 worker에서 왔는지는 구현 세부사항 [근거: sd-testing.md]
- `expect(mocks.executeLint).toHaveBeenCalledWith(expect.objectContaining({fix: true}))` → fix 옵션은 파라미터 패스스루이므로 간접 검증(exitCode 변화 없음)으로 대체 [근거: sd-testing.md]
- target resolution 테스트 ~10건: mock 인자 검증 제거, exitCode 성공 확인으로 단순화 [근거: D2]

**typecheck.spec.ts 변경:**
- `expect(mocks.createBuildEngine).toHaveBeenCalledTimes(N)` → `expect(result.success).toBe(true/false)` + `expect(result.errorCount).toBe(N)` [근거: D3]
- `expect(engine.run).toHaveBeenCalledWith({js, dts, env, ...})` → 제거. env 매핑은 toTypecheckEnvs 단위 테스트에서 커버 [근거: D3]
- `expect(engine.stop).toHaveBeenCalled()` → 제거. 리소스 정리는 내부 구현 세부사항 [근거: sd-testing.md]
- `describe("env-based task creation")` 블록 → 삭제. 전체 시나리오가 typecheck-env.spec.ts에서 커버 [근거: D3]
- `expect(mocks.createBuildEngine).toHaveBeenCalledWith(expect.objectContaining({name, config}))` → 제거. result 기반 검증으로 대체 [근거: D3]
- 유지되는 mock: deserializeDiagnostic(테스트 데이터 미직렬화), typescript(CompilerHost 필요), loadSdConfig(파일시스템), createBuildEngine(엔진 생성), typecheckNonPackageFiles(파일시스템/컴파일러)

**유지되는 정당한 mock (전체):**
| mock 대상 | 사유 |
|-----------|------|
| `@simplysm/core-node` (fsx, cpx) | 파일시스템, 프로세스 실행 |
| `@simplysm/storage` | 네트워크 I/O (SFTP/FTP) |
| `ssh2` | 네트워크 I/O |
| `@inquirer/prompts` | 사용자 상호작용 |
| `fs`, `os` | 파일시스템, OS 시스템콜 |
| `loadSdConfig` | sd.config.ts 파일 로드 |
| `runBuild` | 프로덕션 빌드 (파일시스템/프로세스) |
| `createBuildEngine` | 엔진 생성 (Worker Thread) |
| `typecheck-serialization` | 테스트 데이터가 미직렬화 형식 |
| `typescript` | CompilerHost 필요 |
| `discoverWorkspacePackages` | 파일시스템 (pnpm-workspace.yaml) |

### 대안 검토

**방안: check.ts에서 resolveTargetPaths() 함수 추출**
- `targets.map(t => workspacePackages.get(t)!)`를 별도 함수로 추출
- 기각 사유: 3줄 코드라 함수 추출 대비 효용 낮음. `discoverWorkspacePackages` 단위 테스트 + check.spec.ts 결과 검증으로 충분

**방안: mock 엔진을 env에 따라 다른 결과 반환하도록 설정**
- typecheck.spec.ts에서 결과 차별화를 통한 간접 검증
- 기각 사유: mock 복잡도 증가. 단순 result 검증이 더 유지보수 용이
