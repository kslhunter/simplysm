## 구현계획

### 배경

현재 `dev-watch-orchestrator.spec.ts`는 16개의 `vi.mock()`을 사용한다. [근거: 테스트 파일 분석]

코드베이스 탐색 결과:
- `buildPathMapFromConfig` mock은 원본과 **100% 동일**한 코드를 복제 (`packages/sd-cli/src/utils/package-utils.ts:76-84`) [근거: 코드 대조]
- `@simplysm/core-common` err.message mock도 원본과 동일한 로직 복제 (`packages/core-common/src/utils/error.ts`) [근거: 코드 대조]
- `ResultCollector`는 순수 Map 기반 클래스이며, mock이 `new Map() + add/get/toMap` 동일 구조를 재구현 [근거: `packages/sd-cli/src/infra/ResultCollector.ts`]
- `RebuildManager`는 `EventEmitter<{ batchComplete }>` 상속, `consola.withTag()` 로거만 의존. Worker/fs 없음 [근거: `packages/sd-cli/src/utils/rebuild-manager.ts`]
- `filterPackagesByTargets`, `validateTargets`는 순수 함수 (logger.debug 호출만 존재) [근거: `packages/sd-cli/src/utils/package-utils.ts:236-280`]
- `classifyWatchPackages`/`classifyDevPackages`는 pathMap + config → 패키지 분류 순수 함수 (현재도 실제 실행 중) [근거: `packages/sd-cli/src/utils/package-utils.ts:298-395`]
- DevWatchOrchestrator는 `createBuildEngine(pkg, { resultCollector, rebuildManager, ... })`로 인프라 객체를 전달 [근거: `packages/sd-cli/src/orchestrators/DevWatchOrchestrator.ts:169-174`]

  createBuildEngine: vi.fn((pkg: any, options: any) => {
    const engine = {
      run: vi.fn().mockResolvedValue({ success: true, ... }),
      startWatch: vi.fn().mockImplementation(async () => {
        const resolve = options.rebuildManager.registerBuild(
          `${pkg.name}:build`, `${pkg.name} (${pkg.config.target})`,
        );
        options.resultCollector.add({
          name: pkg.name, target: pkg.config.target,
          type: "build", status: "success",
          build: { success: true, errors: [], warnings: [], diagnostics: [] },
        });
        resolve();
      }),
      stop: vi.fn().mockResolvedValue(undefined),
      _pkgName: pkg.name,
    };
    mockBuildEngines.push(engine);
    return engine;
  }),
}));

### 대안 검토

**A안: importOriginal만 추가, assertion 미변경** — vi.mock에 importOriginal 패턴만 추가하고 호출 검증 assertion은 그대로 유지. 변경 최소화되지만 구현 결합 검증이 남아 wbs 목표(리팩토링 내성)를 달성하지 못함. **채택하지 않음.**

**B안 (채택): mock 제거 + assertion 전환** — 순수 모듈 mock 제거, 실제 인프라 사용, 동작 결과 검증. 변경량이 크지만 wbs 목표에 부합.
