## 구현계획

### 배경

서버 빌드는 `server-build.worker.ts`에서 두 가지 경로로 실행된다:
- **프로덕션(one-shot)**: `esbuild.build()` 직접 호출 (`server-build.worker.ts:168`)
- **Watch/dev**: `server-esbuild-context.ts`의 `esbuild.context()` 래퍼 (`server-esbuild-context.ts:65`)

양쪽 모두 plugins 배열을 호출 측에서 구성하며, 현재는 `tscPlugin.plugin`만 포함한다. Feature 1.1에서 생성한 `createWorkerBundlePlugin()`을 이 배열에 추가하면 된다. [근거: wbs 1.3 범위]

### 목표

- 서버 프로덕션 빌드에 Worker 번들링 플러그인 적용 [근거: Rule "프로덕션 빌드에 Worker 플러그인 적용"]
- 서버 watch/dev 빌드에 Worker 번들링 플러그인 적용 [근거: Rule "Watch/dev 빌드에 Worker 플러그인 적용"]
- 기존 빌드 동작(tsc, external 등)에 영향 없음 [근거: Rule "기존 서버 빌드 동작 보존"]

### 비목표

- `createServerEsbuildOptions` 함수 시그니처 변경 [근거: D1 — 기존 패턴 유지]
- 서버의 Node.js `worker_threads` Worker 처리 [근거: wbs "Node.js worker_threads 기반이므로 대상 아님"]

### 설계

#### 프로덕션 빌드 변경 (`server-build.worker.ts`)

현재 (`server-build.worker.ts:168`):
```typescript
jsResult = await esbuild.build({ ...esbuildOptions, plugins: [tscPlugin.plugin] })
```

변경 후:
```typescript
jsResult = await esbuild.build({
  ...esbuildOptions,
  plugins: [createWorkerBundlePlugin(), tscPlugin.plugin],
})
```

[근거: Rule "프로덕션 빌드에 Worker 플러그인 적용"]

#### Watch/dev 빌드 변경 (`server-esbuild-context.ts`)

현재 (`server-esbuild-context.ts:65-70`):
```typescript
context = await esbuild.context({
  ...baseOptions,
  plugins: tscPlugin != null ? [tscPlugin.plugin] : [],
  metafile: true,
  write: false,
});
```

변경 후:
```typescript
const workerPlugin = createWorkerBundlePlugin();
context = await esbuild.context({
  ...baseOptions,
  plugins: tscPlugin != null ? [workerPlugin, tscPlugin.plugin] : [workerPlugin],
  metafile: true,
  write: false,
});
```

[근거: Rule "Watch/dev 빌드에 Worker 플러그인 적용", tsc 옵션 유무 양쪽 모두 처리]

#### 플러그인 순서

Worker 플러그인을 tsc 플러그인보다 앞에 배치. tsc 플러그인은 `onStart`/`onEnd`만 사용하여 순서가 기능에 영향 없지만, Worker 패턴 감지(`onLoad`)가 빌드 파이프라인의 파일 처리 단계이므로 의미적으로 앞에 위치시킨다. [근거: `esbuild-tsc-plugin.ts:46,63` — onStart/onEnd만 사용]

### 대안 검토

| 접근 방식 | 장점 | 단점 | 선택하지 않은 이유 |
|-----------|------|------|-------------------|
| `createServerEsbuildOptions`에 plugins 포함 | 단일 수정 지점 | 호출 측의 `{...options, plugins: [tsc]}` 패턴이 덮어씀 | 기존 spread 패턴과 충돌 — 모든 호출 측을 함께 수정해야 하므로 오히려 변경 범위 증가 |
| 호출 측에서 plugins 추가 (선택) | 기존 패턴 유지, 변경 최소 | 2곳 수정 | 가장 단순하고 안전 |
