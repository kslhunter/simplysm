## 구현계획

### 배경

Feature 2.3에서 NgtscEngine이 BuildEngine 인터페이스를 구현하여 Angular Library AOT 컴파일을 수행한다. `transformResource` 인터페이스가 `AngularLibraryHostExtensions`에 정의되어 있으나, D2 결정에 의해 null을 반환하는 상태이다. v12에서는 `@angular/build` 내부의 `ComponentStylesheetBundler`를 사용했으나, v14에서는 exports 필드 차단으로 접근 불가하다.

### 목표

- sass 패키지를 직접 사용하는 재사용 가능한 SCSS 컴파일 모듈 구현
- `transformResource`에서 인라인/외부 SCSS 컴파일 (NgtscEngine + vitest-plugin)
- 전역 SCSS (`scss/styles.scss`) → `dist/styles.css` 컴파일
- Watch mode에서 SCSS 파일 변경 시 재컴파일

### 비목표

- CSS 후처리 (PostCSS, autoprefixer — Feature 4.1)
- Client 빌드의 스타일 처리 (Feature 3.x — ViteEngine 내장)
- SCSS minification/optimization (프로덕션 최적화는 후속)

#### SCSS 컴파일 모듈 API (`utils/scss-compiler.ts`)

```typescript
import * as sass from "sass";

interface ScssCompileResult {
  css: string;
  /** 컴파일에 참여한 의존 파일 목록 (loadedUrls → 절대 경로) */
  dependencies: string[];
}

/** 인라인 SCSS 문자열을 CSS로 컴파일한다 */
function compileScssString(
  source: string,
  containingFile: string,
  loadPaths: string[],
): ScssCompileResult;

/** 외부 SCSS 파일을 CSS로 컴파일한다 */
function compileScssFile(
  filePath: string,
  loadPaths: string[],
): ScssCompileResult;
```

- `compileScssString`: `sass.compileString(source, { url, loadPaths, silenceDeprecations })` 호출
  - `url`: `new URL(pathToFileURL(containingFile))` — 상대 경로 해석의 기준점
- `compileScssFile`: `sass.compile(filePath, { loadPaths, silenceDeprecations })` 호출
- 두 함수 모두 sass 동기 API 사용 (Worker 스레드에서 실행되므로 블로킹 무방)
- `loadedUrls` → `dependencies`로 변환 (file:// URL → 절대 경로)
- 컴파일 에러 시 sass 예외를 그대로 전파 (호출자가 처리)

#### Import 경로 해석 전략

sass `loadPaths` 옵션으로 처리:

| 경로 유형 | 해석 방법 |
|-----------|-----------|
| 상대 경로 (`../scss/commons/variables`) | sass 기본 동작 — containingFile 기준 상대 해석 |
| 패키지 내 경로 (`commons/variables`) | `loadPaths: [path.join(pkgDir, "scss")]` |
| node_modules 경로 (`@simplysm/angular/scss/...`) | `loadPaths: [path.join(cwd, "node_modules")]` |

sass는 `_` prefix와 `.scss` 확장자를 자동 탐색하므로 (`_variables.scss`), 별도 처리 불필요.

#### transformResource 구현 (`ngtsc-build-core.ts`)

```typescript
// createNgtscProgramWithHost 내부
const scssDependencies = new Map<string, Set<string>>(); // containingFile → Set<dep>

hostExt.transformResource = async (data, context) => {
  if (context.type !== "style") return null;

  const loadPaths = [
    path.join(pkgDir, "scss"),
    path.join(info.cwd, "node_modules"),
  ];

  try {
    if (context.resourceFile != null && context.resourceFile.endsWith(".scss")) {
      const result = compileScssFile(context.resourceFile, loadPaths);
      trackDeps(scssDependencies, context.containingFile, result.dependencies);
      return { content: result.css };
    }

    if (context.resourceFile != null) {
      // .css 등 비-SCSS 파일 → null 반환 (readResource가 처리)
      return null;
    }

    // 인라인 스타일 — SCSS로 시도, 순수 CSS면 그대로 통과
    const result = compileScssString(data, context.containingFile, loadPaths);
    trackDeps(scssDependencies, context.containingFile, result.dependencies);
    return { content: result.css };
  } catch (err) {
    // SCSS 컴파일 에러 → null 반환하되 에러를 수집
    scssErrors.push(formatScssError(err, context.containingFile));
    return { content: "/* SCSS compilation error */" };
  }
};
```

SCSS 컴파일 에러는 빌드 결과의 `dts.errors`에 포함하여 보고한다.

#### 전역 SCSS 컴파일

`runNgtscBuild`와 `runNgtscRebuild`에 emit 단계 이후 전역 SCSS 컴파일 단계를 추가:

1. `path.join(pkgDir, "scss", "styles.scss")` 존재 여부 확인
2. 존재하면 `compileScssFile(stylesPath, loadPaths)` 호출
3. 결과를 `path.join(pkgDir, "dist", "styles.css")`에 기록
4. 컴파일 에러 시 빌드 결과 errors에 추가

#### Watch mode SCSS 지원

`ngtsc-build.worker.ts` 변경:

1. **FsWatcher 패턴 확장**: `*.{ts,tsx}` → `*.{ts,tsx,scss,css}`
2. **SCSS 의존성 추적**: `scssDependencies` Map을 `runNgtscRebuild`에 전달, 컴파일 시 갱신
3. **`getModifiedResourceFiles` 구현**: FsWatcher가 감지한 변경 중 `.scss`/`.css` 파일을 `Set<string>`으로 반환 → Angular incremental compilation이 해당 리소스를 사용하는 컴포넌트를 재분석
4. **전역 SCSS 재컴파일**: `.scss` 파일 변경 시 전역 스타일도 재컴파일

```typescript
// ngtsc-build-core.ts — createNgtscProgramWithHost에 추가
hostExt.getModifiedResourceFiles = () => modifiedResourceFiles;
```

#### packages/angular/package.json 변경

- `"style": "./styles.css"` → `"style": "./dist/styles.css"`
- `"build:styles"` 스크립트 제거 (sd-cli가 빌드 시 처리)

### 대안 검토

| 접근 방식 | 선택 여부 | 이유 |
|-----------|-----------|------|
| sass 패키지 직접 사용 | 채택 | ComponentStylesheetBundler 접근 불가, sass API가 안정적이고 단순 |
| v12 SdStyleBundler 패턴 (ComponentStylesheetBundler 래핑) | 미채택 | `@angular/build` exports 필드가 내부 경로 차단 |
| sass 비동기 API (`compileStringAsync`) | 미채택 | Worker 스레드에서 실행, 동기 API가 단순하고 충분 |
| 별도 SCSS Worker 분리 | 미채택 | NgtscProgram의 `analyzeAsync()`가 `transformResource`를 호출하므로 같은 프로세스에서 실행해야 함 |
| loadPaths 대신 custom importer | 미채택 | loadPaths로 상대/패키지/node_modules 경로 모두 커버 가능, 추가 복잡성 불필요 |
