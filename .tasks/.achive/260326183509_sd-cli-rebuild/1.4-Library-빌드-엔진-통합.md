# Feature 1.4 Library 빌드 엔진 통합

## 참조 자료

- [wbs.md](wbs.md)

### 설계 결정

| # | 결정사항 | 선택 | 근거 |
|---|---------|------|------|
| D1 | Worker 통합 방식 | 1 Worker 통합 (library + dts → 단일 워커) | esbuild(Go 바이너리)는 Node.js 스레드를 블로킹하지 않아 Promise.all로 tsc와 병렬 실행 가능. 패키지당 스레드 2→1 감소, tsconfig 중복 파싱 제거 |
| D2 | Watch mode 파일 감시 | FsWatcher 단일화 + createIncrementalProgram | 1 Worker 통합의 자연스러운 귀결. ts.createWatchProgram 자체 감시 제거, FsWatcher 하나로 esbuild + tsc 동시 트리거. tsBuildInfoFile로 incremental 상태 유지 |
| D3 | EngineResult 구조 | js/dts 분리 유지 | BuildOrchestrator가 js/dts를 구분 출력. Feature 1.3에서 "1.4에서 통합 가능" 언급했으나 현재 소비자가 분리 구조에 의존하므로 유지 |
| D4 | typecheck 명령어의 dts.worker | 유지 | Feature 1.6에서 명령어 재구성 시 처리. 1.4 범위에서 typecheck 명령어 변경 불필요 |
| D5 | library.worker | 삭제 | 합쳐진 워커로 대체. EsbuildEngine만 사용하므로 소비자 영향 없음 |

## 구현계획

### 배경

Feature 1.3에서 EsbuildEngine이 library.worker(esbuild JS) + dts.worker(tsc typecheck/.d.ts)를 2개 Worker 스레드로 래핑하는 추상화가 완성되었다. 현재 패키지당 2개 Worker 스레드가 생성되어 tsconfig를 각각 파싱하고, 파일 감시도 이중화(FsWatcher + ts.createWatchProgram)되어 있다. EsbuildEngine 내부에 `_startLibraryWatch()`/`_startDtsWatch()` 분리 패턴이 남아있다.

### 목표

- library.worker + dts.worker를 하나의 library-build.worker로 합침
- FsWatcher 단일화, tsconfig 파싱 1회로 통합
- EsbuildEngine이 1개 워커만 관리하도록 단순화
- 기존 BuildEngine 인터페이스(external contract) 변경 없음

### 비목표

- Server BuildEngine 적용 (Feature 1.5)
- EngineResult js/dts 통합 (현재 분리 유지, D3)
- dts.worker.startWatch() 제거 (Feature 1.6에서 정리)
- typecheck 명령어 변경 (Feature 1.6)
- Angular/Client 엔진 (Features 2.2, 3.1)

### 설계

#### tsc 빌드 유틸리티 추출 (utils/tsc-build.ts)

dts.worker.build()의 package-mode 로직(~135줄)을 공유 유틸로 추출한다. merged worker와 dts.worker 양쪽에서 사용.

```typescript
interface TscPackageBuildOptions {
  pkgDir: string;
  cwd: string;
  emit: boolean;  // true = .d.ts 생성 + typecheck, false = typecheck only
}

interface TscPackageBuildResult {
  success: boolean;
  errors?: string[];
  diagnostics: SerializedDiagnostic[];
  errorCount: number;
  warningCount: number;
}

function runTscPackageBuild(options: TscPackageBuildOptions): TscPackageBuildResult
```

내부 단계:
1. parseTsconfig(pkgDir)
2. emit 여부에 따라 rootFiles 결정 (emit=true: src만, emit=false: src+tests)
3. CompilerOptions 설정 (noEmit, declaration, outDir 등)
4. IncrementalCompilerHost 생성 + DTS path rewriter 적용 (emit=true 시)
5. createIncrementalProgram → emit → diagnostics 수집/필터링
6. TscPackageBuildResult 반환

dts.worker.build()에서 package-mode 분기(`info.pkgDir != null`)의 로직이 이 함수로 이전된다. non-package mode(`info.pkgDir == null`)는 dts.worker에 유지.

#### 합쳐진 워커 (workers/library-build.worker.ts)

```typescript
// Types
interface LibraryBuildInfo {
  name: string;
  config: SdBuildPackageConfig;
  cwd: string;
  pkgDir: string;
  output: BuildOutput;  // { js: boolean; dts: boolean }
}

interface LibraryBuildResult {
  js: { success: boolean; errors?: string[]; warnings?: string[] };
  dts: { success: boolean; errors?: string[]; diagnostics: SerializedDiagnostic[] };
}

interface CombinedBuildEvent {
  js: { success: boolean; errors?: string[]; warnings?: string[] };
  dts: { success: boolean; errors?: string[] };
}

interface LibraryBuildWorkerEvents {
  buildStart: Record<string, never>;
  build: CombinedBuildEvent;
  error: { message: string };
}
```

**build() 실행 흐름:**
1. parseTsconfig(pkgDir) → entryPoints/rootNames (1회)
2. esbuild.build() 시작 (async → Go 바이너리에서 실행)
3. runTscPackageBuild() 실행 (sync → Node.js, esbuild Go와 병렬)
4. esbuild Promise await → outputFiles 처리
5. LibraryBuildResult 반환 (js/dts 분리)

```
시퀀스:
  esbuild.build() 시작 ─── Go 프로세스 실행 ─── 결과 반환 ──┐
  runTscPackageBuild() ─── tsc 분석/emit ─── 완료 ────────────┤
                                                               ├─ 결합 반환
```

**startWatch() 실행 흐름:**
1. parseTsconfig(pkgDir) → entryPoints/rootNames
2. output.js=true 시: esbuild.context() 생성 (watch-notify plugin 불필요)
3. 초기 빌드: esbuild context.rebuild() + runTscPackageBuild() 병렬
4. 초기 build 이벤트 송신
5. FsWatcher.watch(src/\*\*/\*.{ts,tsx}) 시작
6. onChange({ delay: 300 }):
   - buildStart 이벤트 송신
   - add/unlink 시: re-parseTsconfig, esbuild context 재생성
   - esbuild context.rebuild() + runTscPackageBuild() 병렬
   - build 이벤트 송신 (combined)

**stopWatch():** esbuild context dispose + FsWatcher close

#### EsbuildEngine 변경

2-worker 관리 → 1-worker 관리로 단순화:

```typescript
class EsbuildEngine implements BuildEngine {
  private _worker: WorkerProxy<typeof LibraryBuildWorkerModule> | undefined;

  async run(output: BuildOutput): Promise<EngineResult> {
    this._createWorker();
    const result = await this._worker!.build({
      name, config, cwd, pkgDir, output,
    });
    return { success: result.js.success && result.dts.success, js: ..., dts: ... };
  }

  async startWatch(output: BuildOutput): Promise<void> {
    this._createWorker();
    // 이벤트 핸들러 등록 (buildStart → rebuildManager, build → resultCollector)
    // worker.startWatch() 호출
    // 초기 build 이벤트로 Promise resolve
  }

  async stop(): Promise<void> {
    if (this._isWatchMode) this._worker?.stopWatch();
    this._worker?.terminate();
  }
}
```

제거 대상: `_libraryWorker`, `_dtsWorker`, `_createWorkers()`, `_startLibraryWatch()`, `_startDtsWatch()`

### 대안 검토

| 접근 방식 | 선택 여부 | 이유 |
|-----------|-----------|------|
| tsc 로직을 utils/에 추출하여 공유 | 채택 | dts.worker와 ~135줄 중복 방지. dts.worker는 Feature 1.6까지 유지 |
| tsc 로직 중복 (merged worker 독립 구현) | 미채택 | dts.worker와 동일 로직 중복. 버그 수정 시 2곳 갱신 필요 |
