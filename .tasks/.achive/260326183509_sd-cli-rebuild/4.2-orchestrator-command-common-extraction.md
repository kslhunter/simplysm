# Feature 4.2 Orchestrator 및 명령어 공통 로직 추출

## 참조 자료

- [wbs.md](wbs.md)

### 코드 현황

#### Orchestrator 초기화 중복

BuildOrchestrator.initialize()와 DevWatchOrchestrator.initialize() 모두:
1. sd.config.ts 로드 (`loadSdConfig`)
2. 타겟 검증 (`validateTargets`)
3. 패키지 분류 (target별 분류)
4. 엔진 생성 (`createBuildEngine`)

를 각각 별도 구현. DevWatchOrchestrator는 추가로 discoverWorkspacePackages → mergeTestsPackagesIntoConfig → 인프라(ResultCollector/SignalHandler/RebuildManager) 생성 → 엔진 생성을 수행.

#### 패키지 분류 3벌

- `classifyPackages()` (BuildOrchestrator.ts) — build용: buildPackages/serverPackages/clientPackages
- `_classifyWatchPackages()` (DevWatchOrchestrator.ts) — watch용: libraryPackages + watchHookPackages
- `_classifyDevPackages()` (DevWatchOrchestrator.ts) — dev용: serverPackages + clientPackages + serverClientsMap

공통 부분: 패키지 순회 + target 필터링. 차이점: 출력 구조.

#### typecheck tests/ 별도 경로

`typecheck.ts`에 tests/ 디렉토리 전용 typecheck가 tsc 직접 실행으로 구현(~75줄). DevWatchOrchestrator에서는 이미 `mergeTestsPackagesIntoConfig()`로 tests/ 패키지를 config에 합쳐서 일반 패키지와 동일 경로로 처리.

#### lint 실행 이중화

lint worker 생성 + 실행 + 결과 수집 코드가 두 곳에 존재:
- `BuildOrchestrator.ts` — build 시 lint + build 병렬 실행 (fix: false)
- `check.ts` — check --type lint 시 lint 실행 (fix: options.fix)

Worker 생성 → lint(options) → terminate 패턴이 동일. 차이점은 fix 옵션과 결과 매핑뿐.

### 설계 결정

| # | 결정사항 | 선택 | 근거 |
|---|---------|------|------|
| D1 | 패키지 분류 함수 통합 방식 | 공통 순회 추출 + 3개 함수 유지 | 각 함수의 독립성 유지하면서 순회+필터링 중복만 제거. 모드별 반환 타입이 달라 단일 함수로 통합 시 타입 안전성 저하 우려 |
| D2 | typecheck tests/ 통합 방식 | typecheck 자체 로직에 mergeTestsPackagesIntoConfig로 병합 | 기존 typecheck 구조를 유지하면서 tests/ 전용 코드만 제거. BuildEngine 경로 전환은 범위 과대 |
| D3 | DevWatchOrchestrator의 loadAndValidateConfig 사용 | 사용하지 않음 (loadSdConfig + validateTargets 개별 호출) | config 로드와 검증 사이에 tests/ merge 단계가 필요하여 loadAndValidateConfig의 "로드+검증 원자적 수행" 패턴이 맞지 않음 |

## 구현계획

### 배경

sd-cli v14에는 BuildOrchestrator와 DevWatchOrchestrator 두 Orchestrator가 있으며, 초기화 흐름(config 로드 → 검증 → 분류)이 중복 구현되어 있다. 패키지 분류 로직은 3벌(build/watch/dev), lint 실행은 2곳(BuildOrchestrator/check.ts), typecheck의 tests/ 처리는 별도 tsc 직접 실행으로 구현되어 있다. 모든 변경은 기존 동작을 유지하는 순수 리팩토링이다.

### 목표

- 두 Orchestrator의 초기화 중복을 공유 유틸로 추출
- 3개 분류 함수의 공통 순회 로직을 추출
- typecheck의 tests/ 별도 경로를 제거하고 기존 BuildEngine 경로로 통합
- lint 실행을 공통 유틸로 추출

### 비목표

- BuildEngine 인터페이스 변경
- Orchestrator의 인프라(ResultCollector/SignalHandler/RebuildManager) 구조 변경
- typecheck를 전면적으로 재구성 (tests/ 통합만 수행)

### 설계

#### 공통 순회 유틸 (`package-utils.ts`에 추가)

```typescript
/**
 * 패키지 config를 순회하며 null 필터링 + target 필터링을 수행한다.
 * 3개 분류 함수(classifyPackages, classifyWatchPackages, classifyDevPackages)의
 * 공통 순회 로직을 추출한 유틸이다.
 *
 * @param packages - sd.config.ts의 packages (또는 mergeTestsPackagesIntoConfig 결과)
 * @param targets - 필터링할 패키지명 목록 (빈 배열이면 전체)
 * @returns null이 아닌 패키지 목록 (target 필터 적용)
 */
export function iteratePackages(
  packages: Record<string, SdPackageConfig | undefined>,
  targets: string[],
): Array<{ name: string; config: SdPackageConfig }>;
```

#### 공유 초기화 유틸 (`orchestrator-utils.ts` 신규)

```typescript
/**
 * Orchestrator 공통 초기화: config 로드 + 타겟 검증.
 * BuildOrchestrator.initialize()와 DevWatchOrchestrator.initialize()에서 호출한다.
 */
export async function loadAndValidateConfig(params: {
  cwd: string;
  dev: boolean;
  options: string[];
  targets: string[];
}): Promise<SdConfig>;
```

두 Orchestrator의 initialize()에서 loadSdConfig + validateTargets 호출을 이 함수로 대체. DevWatchOrchestrator의 추가 단계(discover, merge, infra, engine)는 Orchestrator에 유지.

#### typecheck tests/ 통합

typecheck.ts의 executeTypecheck()를 수정:
1. `discoverWorkspacePackages(cwd)` 호출하여 workspace 패키지 탐색
2. `mergeTestsPackagesIntoConfig(sdConfig.packages, workspacePackages)` 호출하여 tests/ 패키지를 config에 병합
3. `pathMap`을 사용하여 패키지 디렉토리 경로 해석 (기존 하드코딩 `packages/{name}` → `pathMap.get(name)`)
4. 기존 BuildEngine 경로(lines 100-114)에서 tests/ 패키지도 자동 처리됨 (target:"node" → TscEngine)
5. `nonPkgTargets` 분기와 직접 tsc 실행 코드(lines 188-262) 삭제
6. `extractTargetPackageNames()`의 타겟 해석도 pathMap 기반으로 변경 (tests/orm → "orm")

#### lint 공통 유틸 (`lint-utils.ts` 신규)

```typescript
/**
 * lint Worker를 생성하고 실행한 뒤 terminate하는 공통 유틸.
 * BuildOrchestrator.start()와 check.ts에서 호출한다.
 */
export async function runLint(options: LintOptions): Promise<LintResult>;
```

### 대안 검토

| 접근 방식 | 선택 여부 | 이유 |
|-----------|-----------|------|
| 패키지 분류를 단일 함수로 통합 | 미채택 | 모드별 반환 타입이 달라 타입 안전성 저하 (D1) |
| typecheck를 전면 BuildEngine 경로로 전환 | 미채택 | 이미 일반 패키지는 BuildEngine 사용 중. tests/ 통합만으로 충분 (D2) |
