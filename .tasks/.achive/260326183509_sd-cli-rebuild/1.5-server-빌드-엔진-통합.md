## 요구명세

## 구현계획

### 배경

Feature 1.3/1.4에서 EsbuildEngine과 library-build.worker가 Library 패키지의 BuildEngine 추상화를 완성했다. Server 패키지는 아직 server.worker를 직접 사용하며, esbuild만 실행하고 typecheck가 없다. BuildOrchestrator와 DevOrchestrator 모두 server.worker를 직접 생성하여 사용한다.

### 목표

- Server 빌드에 typecheck 통합 (esbuild + tsc 병렬 실행)
- ServerEsbuildEngine 구현으로 BuildEngine 인터페이스 적용
- BuildOrchestrator, DevOrchestrator를 ServerEsbuildEngine 사용으로 전환
- 기존 server.worker 완전 제거

### 비목표

- Orchestrator 상위 수준 재구성 — 명령어 재분배, dev/watch 대상 변경 (Feature 1.6)
- typecheck/lint/test 명령어 통합 (Feature 1.6)
- Worker 동시 생성 수 제한 (Feature 1.6)

### 설계

#### server-build.worker.ts

library-build.worker와 동일한 3-function 인터페이스 (build, startWatch, stopWatch). 기존 server.worker의 esbuild 로직을 이식하고 tsc 병렬 실행을 추가한다.

##### 타입

```typescript
// build 모드 입력
interface ServerBuildInfo {
  name: string;
  cwd: string;
  pkgDir: string;
  output: BuildOutput;            // { js, dts } — server는 항상 js=true, dts=false
  env?: Record<string, string>;
  configs?: Record<string, unknown>;
  externals?: string[];
  pm2?: { name?: string; ignoreWatchPaths?: string[] };
  packageManager?: "volta" | "mise";
}

// watch 모드 입력
interface ServerWatchInfo {
  name: string;
  cwd: string;
  pkgDir: string;
  output: BuildOutput;
  env?: Record<string, string>;
  configs?: Record<string, unknown>;
  externals?: string[];
  replaceDeps?: Record<string, string>;
}

// build 결과 (LibraryBuildResult과 동일 구조 + mainJsPath)
interface ServerBuildResult {
  js: { success: boolean; errors?: string[]; warnings?: string[] };
  dts: { success: boolean; errors?: string[]; diagnostics: SerializedDiagnostic[] };
  mainJsPath: string;
}

// watch 이벤트 (CombinedBuildEvent과 동일 구조 + mainJsPath)
interface ServerCombinedBuildEvent {
  js: { success: boolean; errors?: string[]; warnings?: string[] };
  dts: { success: boolean; errors?: string[] };
  mainJsPath: string;
}
```

##### build() 흐름

1. parseTsconfig → getPackageSourceFiles
2. collectAllExternals (optional peer deps + native modules + manual)
3. **esbuild.build (async, Go binary)** ‖ **runTscPackageBuild (sync, incremental)** 병렬
4. generateProductionFiles (run 모드만)
5. copyPublicFiles
6. Combined result 반환

##### startWatch() 흐름

1. collectAllExternals
2. createAndBuildContext (esbuild context + watch-notify plugin)
3. 초기 빌드: esbuild rebuild ‖ tsc parallel
4. watchPublicFiles (public/ + public-dev/)
5. collectDeps → FsWatcher (workspace deps + replaceDeps)
6. onChange: file add/remove → context 재생성 + rebuildAll, file change → metafile 필터 → esbuild rebuild + tsc parallel

server.worker의 기존 로직(collectAllExternals, generateProductionFiles, collectDeps, metafile 필터링)을 그대로 이식. tsc 호출은 library-build.worker의 runTscPackageBuild 패턴을 따른다.

#### ServerEsbuildEngine.ts

EsbuildEngine과 동일한 패턴으로 server-build.worker를 WorkerProxy로 래핑한다.

```typescript
interface ServerEsbuildEngineOptions {
  cwd: string;
  pkg: ServerPackageInfo;
  resultCollector?: ResultCollector;
  rebuildManager?: RebuildManager;
}

class ServerEsbuildEngine implements BuildEngine {
  async run(output: BuildOutput): Promise<EngineResult>     // worker.build() → EngineResult 변환
  async startWatch(output: BuildOutput): Promise<void>      // worker.startWatch() + 이벤트 핸들링
  async stop(): Promise<void>                                // stopWatch() + terminate()
}
```

run()은 ServerBuildResult를 EngineResult로 변환한다 (mainJsPath는 engine 내부에서 사용하지 않음).
startWatch()은 worker "build" 이벤트를 ResultCollector에 보고하고, RebuildManager에 등록한다.

#### engines/types.ts 변경

```typescript
export type ServerPackageInfo = PackageInfo & { config: SdServerPackageConfig };
```

#### engines/index.ts 변경

createBuildEngine factory에 server 분기 추가:
```typescript
export function createBuildEngine(
  pkg: BuildPackageInfo | ServerPackageInfo,
  options: { cwd: string; resultCollector?: ResultCollector; rebuildManager?: RebuildManager },
): BuildEngine {
  if (pkg.config.target === "server") {
    return new ServerEsbuildEngine({ ...options, pkg: pkg as ServerPackageInfo });
  }
  return new EsbuildEngine({ ...options, pkg: pkg as BuildPackageInfo });
}
```

#### BuildOrchestrator 변경

server 빌드 섹션(현재 lines 279-314)을 library 빌드와 동일하게 createBuildEngine → engine.run() 패턴으로 전환. server.worker import 제거. EngineResult.dts.diagnostics를 library와 동일한 파이프라인으로 수집/출력.

classifyPackages()에서 server를 별도 분류하는 로직은 유지하되, server도 createBuildEngine을 사용.

#### DevOrchestrator 변경

server.worker 직접 사용 → ServerEsbuildEngine으로 전환.

- 기존 `_serverBuildWorkers` Map → `_serverEngines` Map<string, BuildEngine>
- ServerEsbuildEngine에 ResultCollector + RebuildManager 주입
- RebuildManager "batchComplete" 핸들러에서 ResultCollector의 server build 결과 확인 → 성공 시 runtime 재시작
- mainJsPath는 `path.join(this._cwd, "packages", name, "dist", "main.js")`로 산출
- startWatch() Promise resolve 시 초기 빌드 결과 확인 → 성공 시 초기 runtime 시작
- server-runtime.worker 관리는 기존 로직 유지 (engine 범위 밖)

### 대안 검토

| 접근 방식 | 선택 여부 | 이유 |
|-----------|-----------|------|
| server.worker에 tsc 직접 추가 | 미채택 | 700줄+ 대형 파일 복잡도 증가, library-build.worker와 구조 불일치 (D1) |
| EsbuildEngine 파라미터화로 server 지원 | 미채택 | library/server 결과 형식 차이로 조건 분기 증가, 관심사 분리 저하 (D2) |
| DevOrchestrator에 onBuild callback 주입 | 미채택 | ResultCollector + RebuildManager 패턴이 WatchOrchestrator와 일관적 (D5) |
