# Feature 1.8 Library tsc emit 통합

## 참조 자료

### 설계 결정

| # | 결정사항 | 선택 | 근거 |
|---|---------|------|------|
| D1 | writeChangedOutputFiles() 처리 | 유지 (삭제하지 않음) | server-build.worker에서 사용하므로 esbuild-config.ts에서 삭제 불가. .js extension regex 로직은 별도 추출하여 tsc writeFile hook에서도 사용 |
| D2 | JS emit 시 sourceMap 설정 | sourceMap: true | 현재 tsc-build.ts는 sourceMap: false (DTS 전용). JS emit 모드에서는 소스맵 필요 |

| D4 | runTscPackageBuild 인터페이스 | emit: boolean → output: BuildOutput | 소비자가 library-build.worker 단 1곳이므로 안전. output 플래그 4가지 조합을 직접 표현 |
| D5 | library-build.worker 파일 처리 | 기존 파일 재작성 (새 파일 생성 X) | git history 보존, import 경로 변경 최소화 |

## 구현계획

### 배경

현재 Library 패키지(node/browser/neutral)의 빌드는 `EsbuildEngine`이 담당하며, `library-build.worker`에서 esbuild(JS emit) + tsc(DTS emit/typecheck)를 병렬로 실행한다. esbuild는 Library에서 단순 파일별 트랜스파일(`bundle: false`)만 수행하고, DTS와 typecheck는 어차피 tsc가 담당한다. WBS 아키텍처 결정에 따라, tsc 단일 프로세스로 JS + DTS를 모두 emit하도록 전환하여 빌드 파이프라인을 단순화한다.

### 목표

- `runTscPackageBuild()`에 JS emit 모드를 추가하여 tsc가 JS + DTS를 동시에 emit
- ESM .js 확장자를 tsc writeFile hook에서 처리하는 유틸리티 추가
- `TscEngine` 클래스를 BuildEngine 인터페이스로 구현
- `library-build.worker`를 tsc 전용으로 재작성
- `createBuildEngine` 팩토리에서 TscEngine 라우팅
- `EsbuildEngine` 및 Library esbuild 전용 코드 제거

### 비목표

- Server 빌드의 esbuild 사용 변경 (ServerEsbuildEngine 유지)
- Angular Library 빌드 변경 (NgtscEngine 유지)
- 빌드 성능 최적화 (tsc는 esbuild보다 느리지만 단순성·정확성 우선)
- `writeChangedOutputFiles()` 제거 (server-build.worker에서 사용)

### 설계

#### runTscPackageBuild() 인터페이스 변경

현재 `emit: boolean` 파라미터를 `output: BuildOutput`으로 변경한다. 소비자는 `library-build.worker` 단 1곳이므로 안전하게 변경 가능하다.

```
output 조합 → compilerOptions 매핑:
┌─────────────────────────┬──────────────────────────────────────────────────┬───────────────────┐
│ output                  │ compilerOptions                                  │ rootFiles          │
├─────────────────────────┼──────────────────────────────────────────────────┼───────────────────┤
│ {js:true, dts:true}     │ noEmit:false, declaration:true, sourceMap:true   │ src 파일만         │
│ {js:true, dts:false}    │ noEmit:false, declaration:false, sourceMap:true  │ src 파일만         │
│ {js:false, dts:true}    │ emitDeclarationOnly:true (현재 동작)              │ src 파일만         │
│ {js:false, dts:false}   │ noEmit:true (현재 동작)                           │ src + test 전체    │
└─────────────────────────┴──────────────────────────────────────────────────┴───────────────────┘
```

tsBuildInfoFile은 emit 여부로 구분: `(js||dts) ? "build.tsbuildinfo" : "typecheck.tsbuildinfo"`

#### writeFile hook 설계

emit 모드에서 host.writeFile에 두 가지 변환을 적용한다:
1. **경로 정규화** — `createOutputPathRewriter(pkgDir)`: path alias로 인한 중첩 경로를 flat 구조로 변환 (기존 유틸리티 재사용)
2. **ESM .js 확장자** — `addJsExtensionToImports(content)`: `.js` 파일의 상대 import에 `.js` 확장자 추가 (신규 유틸리티)

`addJsExtensionToImports()`는 `output-path-rewriter.ts`에 추가한다. `writeChangedOutputFiles()`의 regex와 동일 패턴을 사용하되, 텍스트 단위로 동작하여 tsc writeFile hook에서 직접 사용 가능하다.

#### TscEngine 클래스 구조

`EsbuildEngine`과 동일한 패턴. worker 참조만 `library-build.worker`로 유지하되, worker 내부가 tsc 전용으로 변경됨.

- `constructor(options: TscEngineOptions)` — cwd, pkg, resultCollector, rebuildManager
- `run(output)` — `worker.build()` → EngineResult 매핑 (js/dts 결과는 동일 tsc 결과에서 분리 보고)
- `startWatch(output)` — worker events(buildStart/build/error) 처리, Promise 기반 초기 빌드 대기
- `stop()` — `worker.stopWatch()` + `terminate()`

#### library-build.worker 재작성

esbuild 관련 코드를 전부 제거하고 tsc 단일 빌드로 전환한다:
- `build()`: `runTscPackageBuild({ output })` 단일 호출
- `startWatch()`: FsWatcher 설정 → 변경 시 `runTscPackageBuild()` incremental 재빌드
- `cleanup()`: FsWatcher만 정리 (esbuildContext 불필요)
- watch 모드에서 파일 추가/제거 시 별도 처리 불필요 — tsc가 rootNames 기반으로 자동 발견

결과 타입(`LibraryBuildResult`, `CombinedBuildEvent`)은 그대로 유지하여 Engine과의 호환성을 보존한다. js/dts 결과는 동일 tscResult에서 매핑한다.

### 대안 검토

| 접근 방식 | 선택 여부 | 이유 |
|-----------|-----------|------|
| tsc 단일 프로세스 (JS+DTS+typecheck) | 채택 | WBS 아키텍처 결정. 단순성, 정확성. Library에서 esbuild의 역할이 파일별 트랜스파일뿐이므로 tsc로 대체 가능 |
| esbuild(JS) + tsc(DTS+typecheck) 유지 | 미채택 | 현재 상태. 두 도구 조합으로 인한 복잡성(esbuildContext 관리, 파일 추가/제거 시 context 재생성 등) |
| 별도 tsc-build.worker 파일 생성 | 미채택 | library-build.worker를 재작성하는 것이 git history 보존과 import 경로 변경 최소화에 유리 |
