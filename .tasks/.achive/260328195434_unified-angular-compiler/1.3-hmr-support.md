# Feature 1.3 통합 컴파일러 — HMR 지원 (client only)

## 참조 자료

- [wbs.md](wbs.md)

### 설계 결정

| # | 결정사항 | 선택 | 근거 |
|---|---------|------|------|
| D1 | HMR 활성화 조건 | dev 모드에서만 (`_enableHmr: true`) | wbs.md 완료 후 목표 상태에서 client HMR은 dev 모드만 해당. watch는 client에 적용 안 됨 |
| D2 | templateUpdates 전달 방식 | component-middleware 패턴 (Vite middleware에서 `/@ng/component?c=...` 서빙) | Angular 런타임이 `/@ng/component` prefix를 하드코딩하여 HTTP 요청. 유일한 선택지 |
| D3 | staleSourceFiles 관리 | AotCompilation 내부 자동 관리 (AngularFacade 외부 관리 불필요) | `AotCompilation.initialize()` 내부에서 `#state.typeScriptProgram.getSourceFile()`로 수집 |
| D4 | HMR 불가 시 폴백 | `templateUpdates` undefined → Vite 기본 full module invalidation | Angular 공식 패턴과 동일. `emitHmrUpdateModule()` null 시 templateUpdates 전체 undefined |

### HMR 아키텍처 참조

#### Angular HMR 전체 흐름

```
파일 변경 (dev server)
    ↓
sdAngularPlugin.handleHotUpdate({file})
    ├─ facade.update({file})
    │  └─ AotCompilation.initialize() (내부)
    │     ├─ _enableHmr + modifiedFiles.size ≤ 32 → useHmr 판단
    │     ├─ staleSourceFiles 수집 (수정 전 SourceFile 보존)
    │     ├─ analyzeAsync() → AOT 분석
    │     ├─ collectHmrCandidates() → HMR 후보 Set<ClassDeclaration>
    │     ├─ emitHmrUpdateModule(node) → HMR update 모듈 코드
    │     └─ templateUpdates: Map<updateId, updateText> 반환
    ├─ emitAffectedFiles() → emitted JS 캐시
    ├─ templateUpdates 있으면 → 저장 (middleware에서 서빙용)
    └─ Vite에 affected modules 반환
         ↓
Vite HMR: 클라이언트에 module update 전파
         ↓
Angular 런타임: /@ng/component?c=<componentId>&t=<timestamp> HTTP 요청
         ↓
component-middleware: templateUpdates.get(componentId) → JS 응답
         ↓
Angular 런타임: 컴포넌트 hot-replace (full page reload 없음)
```

#### templateUpdates Map 구조

```
Key: encodeURIComponent(`${canonicalFileName}@${className}`)
  예: src%2Fapp%2Fapp.component.ts%40AppComponent
Value: HMR update 모듈 JS 코드 (emitHmrUpdateModule() 반환값)
```

#### component-middleware 프로토콜

```
URL: /@ng/component?c=<componentId>
Method: GET
Response Content-Type: text/javascript
Response Cache-Control: no-cache
Response Body: templateUpdates.get(encodeURIComponent(componentId)) ?? ''
```

#### SUPPORTED_FIELD_NAMES (HMR 가능 메타데이터)

`template`, `templateUrl`, `styles`, `styleUrl`, `stylesUrl`

#### HMR_MODIFIED_FILE_LIMIT

32 (수정 파일 수 초과 시 전체 rebuild)

## 구현계획

### 배경

현재 `AngularFacade`는 `@angular/build/private`의 `createAngularCompilation()`을 래핑하여 client 빌드를 수행한다. `AotCompilation.initialize()`가 이미 `templateUpdates`를 반환하지만, `AngularFacade`가 이 값을 무시하고 `affectedFiles`와 `referencedFiles`만 추출하고 있다. `sdAngularPlugin`의 `handleHotUpdate`는 파일 변경 시 `facade.update()` → `emitAffectedFiles()` → Vite module invalidation으로 처리하지만, Angular HMR(컴포넌트 단위 hot-replace)은 지원하지 않는다.

Angular의 HMR 메커니즘은 `_enableHmr` 컴파일러 옵션 활성화 → `collectHmrCandidates()` → `emitHmrUpdateModule()` → `templateUpdates` Map 생성 → `/@ng/component?c=<id>` HTTP 엔드포인트로 서빙하는 흐름이다.

### 목표

- `AngularFacade`가 `_enableHmr`를 활성화하고 `templateUpdates`를 전파하도록 수정
- `sdAngularPlugin`에서 `templateUpdates`를 수집하고 component-middleware로 서빙
- dev 모드에서 Angular HMR이 동작하여 컴포넌트 템플릿/스타일 변경 시 full page reload 없이 hot-replace

### 비목표

- Library(angular-compiler.ts) HMR 지원 — library는 dev server 없음
- `emitHmrUpdateModule()`의 내부 로직 변경 — Angular 컴파일러가 제공
- HMR 지원 필드(SUPPORTED_FIELD_NAMES) 확장 — Angular 컴파일러가 결정

### 설계

#### AngularFacadeOptions 확장

```typescript
export interface AngularFacadeOptions {
  // ... 기존 필드
  /** HMR 활성화 (dev 모드에서 사용) */
  enableHmr?: boolean;
}
```

#### AngularInitResult 확장

```typescript
export interface AngularInitResult {
  affectedFiles: ReadonlySet<string>;
  referencedFiles: readonly string[];
  /** HMR template update 모듈 (key: componentId, value: JS 코드) */
  templateUpdates?: ReadonlyMap<string, string>;
}
```

#### AngularFacade.initialize() 변경

`compilerOptionsTransformer`에서 `enableHmr`이면 `_enableHmr: true` 추가:

```typescript
(compilerOptions) => ({
  ...compilerOptions,
  noEmit: false,
  declaration: false,
  _enableHmr: this._options.enableHmr ?? false,
})
```

반환값에 `templateUpdates` 포함:

```typescript
return {
  affectedFiles: ...,
  referencedFiles: ...,
  templateUpdates: result.templateUpdates as ReadonlyMap<string, string> | undefined,
};
```

#### sdAngularPlugin 변경

1. 플러그인 레벨에 `templateUpdates: Map<string, string>` 상태 추가
2. `buildStart()`에서 `enableHmr: options.dev`로 facade 생성, 초기 `templateUpdates` 수집
3. `handleHotUpdate()`에서:
   - `templateUpdates.clear()` (이전 데이터 정리)
   - `facade.update()` 후 `initResult.templateUpdates`를 `templateUpdates`에 복사
   - `templateUpdates`가 있으면(HMR 가능) → Vite에 affected modules만 반환 (Vite의 기본 HMR 메커니즘이 Angular 런타임의 `/@ng/component` 요청을 트리거)
4. `configureServer()`에서 component-middleware 등록:
   - `/@ng/component` prefix 매칭
   - `?c=<componentId>` 쿼리에서 ID 추출
   - `templateUpdates.get(encodeURIComponent(componentId)) ?? ''` 응답
   - `Content-Type: text/javascript`, `Cache-Control: no-cache`

#### component-middleware 구현 위치

`vite-angular-plugin.ts` 내부에 private 함수로 구현 (별도 파일 불필요, 로직 단순):

```typescript
function angularComponentMiddleware(
  templateUpdates: Map<string, string>,
): (req: IncomingMessage, res: ServerResponse, next: () => void) => void {
  return (req, res, next) => {
    // /@ng/component?c=<componentId> 매칭
    // ...
  };
}
```

### 대안 검토

| 접근 방식 | 선택 여부 | 이유 |
|-----------|-----------|------|
| component-middleware (HTTP 엔드포인트) | **채택** | Angular 런타임이 `/@ng/component` URL을 하드코딩. 유일한 호환 방식 |
| Vite virtual module (`\0@ng/component...`) | 미채택 | Angular 런타임이 HTTP URL로 요청하므로 virtual module로는 서빙 불가 |
| templateUpdates를 emit 결과에 인라인 | 미채택 | Angular HMR 프로토콜이 별도 HTTP 요청 기반 |
