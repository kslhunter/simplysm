### HMR 구현 참조 — collectHmrCandidates 알고리즘

AotCompilation 내부의 `collectHmrCandidates(modifiedFiles, { compiler }, staleSourceFiles)` 알고리즘:

```
수정 파일 순회:
  ├─ 템플릿 파일? → compiler.getComponentsWithTemplateFile(file) → 후보 추가
  ├─ 스타일 파일? → compiler.getComponentsWithStyleFile(file) → 후보 추가
  └─ .ts 소스 파일? → analyzeFileUpdates(stale, current, compiler)
     ├─ stale 파일 없음 → 전체 무효화 → full rebuild
     ├─ current 파일 없음 → 전체 무효화 → full rebuild
     └─ AST 비교:
        ├─ statement 수 불일치 → null → full rebuild
        ├─ ClassDeclaration: name/heritage/modifiers 변경 → null
        ├─ @Component 데코레이터 메타데이터:
        │  ├─ 지원 필드만 변경: template, templateUrl, styles, styleUrl, stylesUrl → 후보 추가
        │  └─ 비지원 필드 변경 → null → full rebuild
        └─ 기타 statement: 텍스트 변경 → null → full rebuild
```

All-or-nothing 전략: 하나의 수정 파일이라도 비지원 변경이면 전체 HMR 취소.

### stale source file 수집

AngularCompiler.initialize() 호출 전에 이전 _builderProgram에서 수정 파일의 이전 SourceFile을 보존:
```
for (modifiedFile of sourceFileCache.modifiedFiles) {
  staleSourceFiles.set(modifiedFile, previousBuilderProgram.getSourceFile(modifiedFile))
}
```

### NgCompiler HMR 관련 API

| API | 역할 |
|-----|------|
| `compiler.getComponentsWithTemplateFile(path)` | 템플릿 파일을 사용하는 컴포넌트 Set 반환 |
| `compiler.getComponentsWithStyleFile(path)` | 스타일 파일을 사용하는 컴포넌트 Set 반환 |
| `compiler.emitHmrUpdateModule(classDecl)` | HMR update 모듈 JS 코드 생성 (실패 시 null) |
| `compiler.getCurrentProgram()` | 현재 ts.Program 반환 |

### templateUpdates Map 구조

```
Key: encodeURIComponent(`${canonicalFileName}@${className}`)
Value: emitHmrUpdateModule() 반환 JS 코드
```

### HMR 활성화 조건

```
_enableHmr 옵션 true + modifiedFiles 존재 + modifiedFiles.size ≤ 32
```

### client transformStylesheet 패턴 (sass.compileAsync + postcss)

```typescript
async (data, containingFile, stylesheetFile?) => {
  if (stylesheetFile?.endsWith(".scss")) {
    const result = await sass.compileAsync(stylesheetFile, { loadPaths });
    // 의존성 수집
    let css = result.css;
    if (postCssProcessor) css = (await postCssProcessor.process(css, { from: stylesheetFile })).css;
    return css;
  }
  if (stylesheetFile != null) return null; // .css → readResource가 처리
  // 인라인 SCSS
  const result = await sass.compileStringAsync(data, { url: pathToFileURL(containingFile), loadPaths });
  // 의존성 수집
  let css = result.css;
  if (postCssProcessor) css = (await postCssProcessor.process(css, { from: containingFile })).css;
  return css;
}
```

## 구현계획

### 배경

현재 client Angular 빌드는 `AngularFacade` 클래스가 `@angular/build/private`의 `createAngularCompilation`(AotCompilation), `SourceFileCache`, `ComponentStylesheetBundler`를 래핑한다. `sdAngularPlugin`(Vite 플러그인)이 AngularFacade를 사용하여 빌드, HMR, JS 변환을 수행한다.

Feature 1.1~1.3에서 구현된 통합 `AngularCompiler`는 NgtscProgram + BuilderProgram 기반 incremental 최적화를 제공하며, Feature 2.1에서 library 빌드가 이미 마이그레이션되었다. client 빌드도 AngularCompiler로 전환하여 `@angular/build/private` 의존을 `JavaScriptTransformer` 1개로 최소화한다.

### 목표

- AngularFacade 제거, `sdAngularPlugin`이 AngularCompiler + JavaScriptTransformer를 직접 사용
- AngularCompiler에 HMR 지원 추가 (stale file tracking, collectHmrCandidates, templateUpdates)
- ComponentStylesheetBundler를 sass.compileAsync + postcss로 대체
- `@angular/build/private` import를 JavaScriptTransformer만 남기고 전부 제거

### 비목표

- library 빌드 변경 (Feature 2.1에서 완료)
- lint 통합 (Feature 3.x에서 별도 수행)
- JavaScriptTransformer 대체 (wbs.md 제외 사항)
- client.worker.ts 구조 변경 (Vite config 생성 경로는 현재와 동일)

#### AngularCompiler HMR 확장

`AngularCompilerOptions`에 추가:
```
enableHmr?: boolean
```

`initialize()` 반환 타입 확장:
```
{ affectedFiles, templateUpdates?: Map<string, string> }
```

`initialize()` 내부 흐름 변경:
```
1. (기존) packageJsonCache 관리
2. (기존) compilerOptionsTransformer 적용
3. (신규) enableHmr=true + sourceFileCache.modifiedFiles.size > 0 + size ≤ 32이면:
   - 이전 _builderProgram에서 modifiedFiles의 stale SourceFile 수집
4. (기존) 호스트 생성, NgtscProgram 생성, ensureSourceFileVersions, BuilderProgram 생성
5. (기존) analyzeAsync()
6. (신규) enableHmr=true + staleSourceFiles 존재하면:
   - collectHmrCandidates(sourceFileCache.modifiedFiles, compiler, staleSourceFiles)
   - 각 candidate에 대해 compiler.emitHmrUpdateModule(node)
   - templateUpdates Map 생성
7. (기존) findAffectedFiles
8. (기존) 상태 저장
9. 반환: { affectedFiles, templateUpdates }
```

#### hmr-candidates.ts

AotCompilation의 hmr-candidates.js 알고리즘을 TypeScript로 재구현:

`collectHmrCandidates(modifiedFiles, compiler, staleSourceFiles)`:
- 입력: modifiedFiles(Set<string>), compiler(NgCompiler), staleSourceFiles(Map<string, ts.SourceFile>)
- 출력: Set<ts.ClassDeclaration> | null (null = HMR 불가)
- 알고리즘: Feature 문서의 "HMR 구현 참조" 섹션 참조

`analyzeFileUpdates(staleSource, updatedSource)`:
- 입력: stale/current ts.SourceFile
- 출력: Set<ts.ClassDeclaration> | null
- statement 수 비교 → ClassDeclaration별 name/heritage/modifiers 비교 → @Component 데코레이터 메타데이터 비교 (SUPPORTED_FIELD_NAMES만 허용)

#### scss-compiler.ts 확장

```typescript
export async function compileScssFileAsync(filePath, loadPaths): Promise<ScssCompileResult>
export async function compileScssStringAsync(source, containingFile, loadPaths): Promise<ScssCompileResult>
```

sass.compileAsync/compileStringAsync를 사용하여 이벤트 루프를 블록하지 않음.

#### vite-angular-plugin.ts 마이그레이션

플러그인 레벨 상태:
```
compiler: AngularCompiler | undefined
sourceFileCache: AngularSourceFileCache
jsTransformer: JavaScriptTransformer
emittedFiles: Map<string, string>
templateUpdates: Map<string, string>
hmrLock: Promise<void>
scssDependencies: Map<string, Set<string>>  // SCSS 의존성 추적 (watch 모드)
```

`buildStart()`:
1. AngularSourceFileCache 생성 (또는 재사용)
2. AngularCompiler 생성 (rootNames, compilerOptions, angularCompilerOptions, sourceFileCache, transformStylesheet, compilerOptionsTransformer, externalStylesheets)
3. compilerOptionsTransformer: `(opts) => ({ ...opts, noEmit: false, declaration: false, _enableHmr: options.dev })`
4. initialize() 호출
5. emitAffectedFiles() → emittedFiles 캐시
6. collectDiagnostics() → 진단 보고

`handleHotUpdate()`:
1. hmrLock으로 경쟁 조건 방지 (기존 패턴 유지)
2. templateUpdates.clear()
3. compiler.update(modifiedFiles) → { affectedFiles, templateUpdates }
4. templateUpdates 수집
5. emitAffectedFiles() → emittedFiles 캐시 갱신
6. collectDiagnostics() → 진단 보고
7. affected modules 반환

`transform()`:
1. emittedFiles에서 emit된 JS 조회
2. jsTransformer.transformData()로 JS 변환
3. 변환된 코드 반환

`buildEnd()`:
1. dev 모드가 아니면 jsTransformer.close()
2. emittedFiles.clear()

`configureServer()`:
1. angularComponentMiddleware 등록 (기존 패턴 유지)
2. server close 시 jsTransformer.close()

### 대안 검토

| 접근 방식 | 선택 여부 | 이유 |
|-----------|-----------|------|
| HMR을 AngularCompiler 내부에 구현 | **채택** | stale file 수집이 compilation 상태(_builderProgram)에 밀접. 외부에서 하면 internal state 노출 필요 |
| HMR을 vite-angular-plugin 외부에서 구현 | 미채택 | AngularCompiler의 이전 _builderProgram에 접근 불가 |
| hmr-candidates를 AngularCompiler 클래스 내부에 인라인 | 미채택 | analyzeFileUpdates의 AST 비교가 복잡하여 별도 유틸리티로 분리가 명확 |
| scss-compiler에 async 추가 대신 별도 파일 | 미채택 | 동일 모듈에서 sync/async 제공이 일관적. library는 sync, client는 async 사용 |
