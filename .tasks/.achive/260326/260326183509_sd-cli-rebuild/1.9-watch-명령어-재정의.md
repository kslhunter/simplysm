## 요구명세

```gherkin
Feature: 1.9 watch 명령어 재정의

  Background:
    Given sd.config.ts에 패키지 설정이 정의되어 있다
    And pnpm workspace에 패키지들이 등록되어 있다
    And 루트 tsconfig.json paths로 workspace 패키지들이 src/에 연결되어 있다

  Rule: watch 대상은 Library와 Scripts 패키지만이다

    Scenario: Library 패키지 watch
      Given target이 "node"인 Library 패키지가 있다
      When watch 명령어를 실행한다
      Then 해당 패키지의 빌드 엔진이 watch 모드로 시작된다

    Scenario: Scripts 패키지 watch (watch hook 있음)
      Given target이 "scripts"이고 watch hook이 설정된 패키지가 있다
      When watch 명령어를 실행한다
      Then watch hook이 실행된다
      And 지정된 파일 변경 시 hook이 재실행된다

    Scenario: Scripts 패키지 watch (watch hook 없음)
      Given target이 "scripts"이고 watch hook이 없는 패키지가 있다
      When watch 명령어를 실행한다
      Then 해당 패키지는 watch 대상에서 제외된다

    Scenario: Server 패키지는 watch에서 제외
      Given target이 "server"인 패키지가 있다
      When watch 명령어를 실행한다
      Then 해당 패키지의 빌드 엔진이 시작되지 않는다

  Rule: watch hook은 Library와 Scripts 패키지에서 사용할 수 있다

    Scenario: Library 패키지에 watch hook 설정
      Given target이 "node"이고 watch hook이 설정된 Library 패키지가 있다
      When watch 명령어를 실행한다
      Then 빌드 엔진 watch와 watch hook이 동시에 독립적으로 실행된다

    Scenario: watch hook 미설정 Library 패키지
      Given target이 "browser"이고 watch hook이 없는 Library 패키지가 있다
      When watch 명령어를 실행한다
      Then 빌드 엔진 watch만 실행된다

    Scenario: Server/Client 타입에서 watch hook 옵션 제거
      Given SdServerPackageConfig 타입 정의가 있다
      Then watch 속성이 존재하지 않는다

  Rule: workspace 의존성 패키지의 소스 변경을 감지한다

    Scenario: 의존 패키지의 소스 변경 감지
      Given 패키지 B가 workspace 패키지 A를 의존한다
      And B의 빌드 엔진이 watch 모드로 실행 중이다
      When A의 소스 파일이 변경된다
      Then B가 A의 소스 변경을 감지한다
      And B의 incremental 리빌드가 트리거된다

    Scenario: 연쇄 의존성 리빌드
      Given 패키지 C가 B를 의존하고 B가 A를 의존한다
      And A, B, C 모두 watch 모드로 실행 중이다
      When A의 소스 파일이 변경된다
      Then A, B, C 모두 리빌드가 트리거된다

    Scenario: 비의존 패키지는 리빌드하지 않음
      Given 패키지 D가 A를 의존하지 않는다
      When A의 소스 파일이 변경된다
      Then D는 리빌드되지 않는다

    Scenario: 외부 npm 패키지 변경은 감시하지 않음
      Given 패키지 B가 외부 npm 패키지 lodash를 의존한다
      When lodash의 파일이 변경된다
      Then B의 리빌드가 트리거되지 않는다
```

## 구현계획

### 배경

현재 `DevWatchOrchestrator._classifyWatchPackages()`는 Library, Server, Scripts(watch hook) 세 종류를 분류한다. Library와 Server 모두 `BuildEngine.startWatch()`로 watch 모드를 실행하며, Server는 JS만 emit한다. `library-build.worker`와 `ngtsc-build.worker`는 자기 패키지의 `src/` 만 감시하고, `server-build.worker`는 `collectDeps()`로 workspace 전이 의존성의 `src/`까지 감시한다. watch hook은 `SdScriptsPackageConfig`에만 `watch?: SdWatchHookConfig`로 존재한다.

### 목표

- watch 모드에서 server 패키지를 제외하고 Library + Scripts만 대상으로 한다
- watch hook을 Library 패키지에서도 사용할 수 있게 타입을 확장한다
- library-build.worker와 ngtsc-build.worker에서 workspace 의존 패키지의 src/ 변경을 감지하여 리빌드를 트리거한다

### 비목표

- replaceDeps 패키지의 dist/ 감시를 library 워커에 추가하는 것 (orchestrator 레벨에서 별도 처리됨)
- tsc incremental compilation 도입 (현재 rebuildAll 방식 유지)
- dev 명령어 변경 (server 전용, 기존 그대로)

### 설계

#### 타입 변경 (`sd-config.types.ts`)

`SdBuildPackageConfig`에 `watch?: SdWatchHookConfig` 추가:

```typescript
interface SdBuildPackageConfig {
  target: BuildTarget;
  copySrc?: string[];
  publish?: SdPublishConfig;
  watch?: SdWatchHookConfig;  // 추가
}
```

`SdServerPackageConfig`, `SdClientPackageConfig`에는 추가하지 않는다 (D1).

#### Orchestrator 변경 (`DevWatchOrchestrator.ts`)

`_classifyWatchPackages()`에서:
- server 분기 제거 — `_serverPackages`에 아무것도 추가하지 않음
- Library 패키지 중 `config.watch != null`인 경우 `_watchHookPackages`에도 추가

`_startWatchMode()`에서:
- `_serverEngines` 관련 startWatch 호출 제거
- Library watch hook 실행은 기존 `_watchHookPackages` 루프가 자동 처리

#### Worker 변경 (`library-build.worker.ts`, `ngtsc-build.worker.ts`)

`startWatch()`에서 `collectDeps(info.pkgDir, info.cwd)`를 호출하여 workspace 전이 의존성을 수집하고, 해당 패키지들의 `src/` 디렉토리를 FsWatcher 감시 대상에 추가:

```
기존: [pkgDir/src/**/*.{ts,tsx}]
변경: [pkgDir/src/**/*.{ts,tsx}, ...workspaceDeps.map(d => cwd/packages/d/src/**/*.{ts,tsx})]
```

ngtsc-build.worker는 SCSS/CSS 패턴도 포함:
```
기존: [pkgDir/src/**/*.{ts,tsx,scss,css}, pkgDir/scss/**/*.{scss,css}]
변경: [기존 + ...workspaceDeps.map(d => cwd/packages/d/src/**/*.{ts,tsx,scss,css})]
```

### 대안 검토

| 접근 방식 | 선택 여부 | 이유 |
|-----------|-----------|------|
| 워커 내부에서 collectDeps 호출 | 채택 | server-build.worker와 동일 패턴, 워커가 자체적으로 의존성 관리 |
| orchestrator에서 deps 계산 후 워커에 전달 | 미채택 | BuildInfo 타입 변경 필요, 기존 패턴과 불일치 |
| dist/ 감시로 연쇄 리빌드 | 미채택 | tsconfig paths가 src/를 참조하므로 src/ 감시가 정확 |

### Vertical Slices

#### [x] Slice 1: watch 대상에서 server 제거
- **구현 내용:** `_classifyWatchPackages()`에서 server 분기 제거, `_startWatchMode()`에서 server engine 관련 코드 제거, shutdown에서 server engine 정리 제거
- **Scenarios:**
  - Scenario: Library 패키지 watch
  - Scenario: Server 패키지는 watch에서 제외

- **의존:** Slice 1
- **Scenarios:**

- **의존:** Slice 1
