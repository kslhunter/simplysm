# Feature 1.1 자식 프로세스 인코딩 자동 처리

## 참조 자료

### GitHub Issue
- [#9 core-node에 자식 프로세스 인코딩 자동 처리 유틸리티 추가](https://github.com/anthropics/simplysm/issues/9)

### 환경
- OS: Windows 11 (시스템 로케일: 한국어, CMD 코드 페이지: 949)
- Node.js: v20.20.1
- 패키지: @simplysm/sd-cli@14.0.7, @simplysm/core-node@14.0.7

### 현재 execa 사용 위치 (sd-cli만 해당)
- `packages/sd-cli/src/sd-cli.ts` — Node 프로세스 재실행, CPU affinity (shell)
- `packages/sd-cli/src/electron/electron.ts` — Electron._exec(), electron 프로세스 spawn
- `packages/sd-cli/src/capacitor/capacitor.ts` — Capacitor._exec()
- `packages/sd-cli/src/commands/check.ts` — vitest 실행
- `packages/sd-cli/src/commands/publish.ts` — git/npm/pnpm 호출
- `packages/sd-cli/src/workers/server-build.worker.ts` — execaSync("node", ["-v"])

### 설계 결정

| # | 결정사항 | 선택 | 근거 |
|---|---------|------|------|
| D1 | 유틸리티 내부 구현 | child_process 직접 사용 | core-node 의존성 최소화, sd-cli에서 execa 의존성 제거 가능, 바이너리 출력 제어 용이 |

## 요구명세

```gherkin
Feature: 1.1 자식 프로세스 인코딩 자동 처리

  Background:
    Given @simplysm/core-node에 자식 프로세스 실행 유틸리티가 존재한다
    And 유틸리티는 Node.js child_process 모듈을 내부적으로 사용한다

  Rule: 시스템 인코딩을 자동 감지한다

    Scenario: Windows CP949 시스템에서 인코딩 감지
      Given Windows OS에서 CMD 코드 페이지가 949이다
      When 시스템 인코딩을 감지한다
      Then 인코딩이 "euc-kr"로 식별된다

    Scenario: Linux UTF-8 시스템에서 인코딩 감지
      Given Linux OS에서 LANG 환경변수가 "en_US.UTF-8"이다
      When 시스템 인코딩을 감지한다
      Then 인코딩이 "utf-8"로 식별된다

    Scenario: 인코딩 감지 실패 시 UTF-8 fallback
      Given 시스템 인코딩을 감지할 수 없다
      When 시스템 인코딩을 감지한다
      Then 인코딩이 "utf-8"로 fallback된다

  Rule: stdout/stderr를 시스템 인코딩으로 디코딩한다

    Scenario: CP949 인코딩된 에러 메시지를 정상 디코딩
      Given Windows CP949 시스템에서 자식 프로세스를 실행한다
      When 자식 프로세스가 CP949로 인코딩된 한글 에러 메시지를 출력한다
      Then stdout/stderr가 올바른 한글 문자열로 디코딩된다

    Scenario: UTF-8 시스템에서는 변환 없이 통과
      Given UTF-8 시스템에서 자식 프로세스를 실행한다
      When 자식 프로세스가 UTF-8로 인코딩된 메시지를 출력한다
      Then stdout/stderr가 그대로 문자열로 반환된다

    Scenario: stdio inherit 모드에서는 인코딩 변환 불필요
      Given stdio 옵션이 "inherit"로 설정되어 있다
      When 자식 프로세스를 실행한다
      Then 출력이 부모 프로세스의 터미널로 직접 전달된다
      And 인코딩 변환이 수행되지 않는다

  Rule: 기존 execa 호출 패턴을 모두 대체한다

    Scenario: stdout 캡처 패턴 대체
      Given Electron._exec()에서 execa(cmd, args, {cwd, env})를 사용한다
      When 유틸리티로 교체한다
      Then 동일한 cmd, args, cwd, env 옵션으로 실행된다
      And stdout가 올바른 인코딩으로 디코딩되어 반환된다

    Scenario: reject false 패턴 대체
      Given check.ts에서 execa("pnpm", args, {reject: false})를 사용한다
      When 유틸리티로 교체한다
      Then exitCode, stdout, stderr가 모두 반환된다
      And 프로세스 실패 시 예외가 발생하지 않는다

    Scenario: 동기 실행 패턴 대체
      Given server-build.worker.ts에서 execaSync("node", ["-v"])를 사용한다
      When 동기 유틸리티로 교체한다
      Then stdout가 동기적으로 반환된다

    Scenario: shell 실행 패턴 대체
      Given sd-cli.ts에서 execa({shell: true})`${command}`를 사용한다
      When 유틸리티로 교체한다
      Then shell: true 옵션으로 명령어가 실행된다

    Scenario: stdio inherit 패턴 대체
      Given sd-cli.ts에서 execa("node", args, {stdio: "inherit"})를 사용한다
      When 유틸리티로 교체한다
      Then stdio가 "inherit"로 설정되어 부모 프로세스와 연결된다

    Scenario: 프로세스 kill 패턴 대체
      Given electron.ts에서 subprocess.kill()로 자식 프로세스를 종료한다
      When 유틸리티로 교체한다
      Then 반환된 프로세스 객체의 kill()로 종료할 수 있다

  Rule: sd-cli에서 execa 의존성을 제거한다

    Scenario: execa 의존성 제거
      Given sd-cli의 모든 execa 호출이 유틸리티로 교체되었다
      When sd-cli의 package.json에서 execa를 제거한다
      Then 빌드와 실행이 정상 동작한다
```

## 구현계획

### 배경

core-node는 파일시스템(fsx), 경로(pathx), 파일감시(FsWatcher), 워커(Worker) 유틸리티를 제공하지만 자식 프로세스 실행 유틸리티는 없다. sd-cli에서 execa 라이브러리(^9.6.1)를 6개 파일에서 직접 사용하고 있으며, Windows CMD 코드 페이지(예: 949)에서 자식 프로세스 출력이 UTF-8로 잘못 디코딩되어 한글이 깨지는 문제가 있다.

### 목표

- core-node에 `cpx` 네임스페이스로 자식 프로세스 실행 유틸리티 추가
- 시스템 인코딩 자동 감지 및 stdout/stderr 올바른 디코딩
- sd-cli의 모든 execa 호출을 cpx로 교체, execa 의존성 제거

### 비목표

- 프로세스 풀링, 재시도, 타임아웃 등 고급 기능
- stdin 입력 지원 (현재 사용 패턴 없음)

### 설계

#### 모듈 구조

- `packages/core-node/src/utils/cp.ts` — 구현
- `packages/core-node/src/index.ts` — `export * as cpx from "./utils/cp"` 추가

#### API

```typescript
export function getSystemEncoding(): string;
export function exec(cmd: string, args: string[], options?: ExecOptions): ExecProcess;
export function execSync(cmd: string, args: string[], options?: ExecSyncOptions): ExecResult;

interface ExecOptions {
  cwd?: string;
  env?: Record<string, string>;
  stdio?: "pipe" | "inherit";
  shell?: boolean;
  reject?: boolean; // default: true
}

type ExecSyncOptions = Omit<ExecOptions, "reject">;

interface ExecResult {
  stdout: string;
  stderr: string;
  exitCode: number;
}
```

`ExecProcess` — `PromiseLike<ExecResult>`을 구현하여 `await exec(...)` 가능, `.kill()` 메서드로 프로세스 종료, `.catch()` 메서드로 에러 핸들링 지원.

#### 인코딩 감지

1. Windows: `child_process.execSync("chcp", { shell: true })` → 숫자 추출 → 코드 페이지 매핑
2. Linux/macOS: `process.env.LANG` 또는 `process.env.LC_ALL`에서 인코딩 추출
3. 감지 실패: UTF-8 fallback
4. 결과: 모듈 레벨 변수에 캐싱

#### 코드 페이지 → TextDecoder 인코딩 매핑

| Code Page | 인코딩 |
|-----------|--------|
| 65001 | utf-8 |
| 949 | euc-kr |
| 932 | shift-jis |
| 936 | gbk |
| 950 | big5 |
| 1252 | windows-1252 |

#### stdout/stderr 디코딩

- pipe 모드: spawn에서 raw Uint8Array 수집 → `bytes.concat()` (core-common) → `TextDecoder.decode()`
- inherit 모드: 디코딩 불필요 (터미널이 처리)

### 대안 검토

| 접근 방식 | 선택 여부 | 이유 |
|-----------|-----------|------|
| child_process 직접 사용 | 채택 | 의존성 최소화, 바이너리 출력 제어 용이 |
| execa 래핑 | 미채택 | core-node에 불필요한 의존성 추가 |
| iconv-lite로 디코딩 | 미채택 | TextDecoder가 필요한 인코딩을 모두 지원 |
| 매 실행마다 인코딩 감지 | 미채택 | chcp 실행 오버헤드, 런타임 중 변경 거의 없음 |
