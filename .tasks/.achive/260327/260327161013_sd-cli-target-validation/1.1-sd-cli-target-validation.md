# Feature 1.1 sd-cli target 검증 통일

## 참조 자료

### 현재 동작

- check 명령어만 targets를 경로 기반(`packages/X`)으로 처리하고, 나머지(watch/dev/build/publish)는 패키지명(`X`)으로 처리
- check에서 패키지명 입력 시 정규식 불일치 → 전체 패키지가 실행되는 버그
- 모든 명령어에서 존재하지 않는 target은 silent skip → "No packages to ..." 메시지만 출력

### 관련 파일

- `packages/sd-cli/src/commands/check.ts` — check 명령어 진입점
- `packages/sd-cli/src/commands/typecheck.ts` — `extractTargetPackageNames` (경로 기반 정규식)
- `packages/sd-cli/src/commands/lint.ts` — `filterByTargets` 호출
- `packages/sd-cli/src/utils/package-utils.ts` — `filterPackagesByTargets` (watch/dev/build 공유)
- `packages/sd-cli/src/commands/publish.ts` — 자체 targets 로직
- `packages/sd-cli/src/orchestrators/BuildOrchestrator.ts` — build의 `classifyPackages`
- `packages/sd-cli/src/orchestrators/DevWatchOrchestrator.ts` — watch/dev의 targets 처리
- `packages/sd-cli/src/sd-cli-entry.ts` — CLI positional args 정의 (check 명령어 describe 수정)

### 수정 방향

- A안: check.ts 진입점에서 패키지명 → `packages/{name}` 경로로 정규화 후 하위에 전달
- 공통: 모든 명령어에서 sdConfig.packages에 없는 target → 에러

### 설계 결정

| # | 결정사항 | 선택 | 근거 |
|---|---------|------|------|
| D1 | 여러 targets 중 일부만 유효하지 않을 때 | 전체 에러 | 오타를 즉시 인지, 의도하지 않은 범위 실행 방지 |

## 구현계획

### 배경

sd-cli의 모든 명령어(check/watch/dev/build/publish)는 `[targets..]`로 대상 패키지를 지정할 수 있다. watch/dev/build/publish는 패키지명(`core-node`)으로 `targets.includes(name)` 매칭하지만, check만 경로 기반(`packages/core-node`) 정규식을 사용하여 패키지명 입력 시 전체 실행되는 버그가 있다. 또한 모든 명령어에서 존재하지 않는 target을 silent skip하여 사용자에게 알리지 않는다.

### 목표

- 모든 명령어에서 targets를 패키지명으로 통일
- 존재하지 않는 target 입력 시 에러 발생 (전체 중단)
- 비어있을 때 전체 실행 동작 유지

### 비목표

- tests/ 경로를 targets로 지원하는 것 (통합 테스트는 targets 없이 전체 실행 또는 vitest 직접 사용)
- CLI 인터페이스 변경 (기존 positional args 유지)

### 설계

#### 공통 유틸리티: `validateTargets`

`package-utils.ts`에 추가. targets 배열의 각 항목이 `sdConfig.packages` 키에 존재하는지 검증. 하나라도 없으면 SdError를 throw.

```typescript
function validateTargets(targets: string[], packages: Record<string, unknown>): void {
  if (targets.length === 0) return;
  const packageNames = Object.keys(packages);
  const unknown = targets.filter((t) => !packageNames.includes(t));
  if (unknown.length > 0) {
    throw new SdError(`Unknown target: ${unknown.join(", ")}`);
  }
}
```

#### check 명령어 (A안: check.ts 진입점에서 정규화)

`runCheck`에서:
1. sdConfig를 로드
2. `validateTargets(targets, sdConfig.packages)` 호출
3. targets가 비어있지 않으면 `packages/{name}` 경로로 정규화
4. 정규화된 targets를 typecheck/lint/test에 전달

typecheck.ts의 `extractTargetPackageNames`과 lint.ts의 `filterByTargets`는 경로 기반 입력을 그대로 처리하므로 수정 불필요.

#### watch/dev (DevWatchOrchestrator)

`filterPackagesByTargets` 호출 전에 `validateTargets` 호출. `filterPackagesByTargets` 자체에 검증을 넣지 않고, 호출부에서 검증한다 — filterPackagesByTargets는 scripts 제외 등 자체 필터가 있어서 검증과 혼합하면 책임이 불분명해짐.

#### build (BuildOrchestrator)

`classifyPackages` 호출 전에 `validateTargets` 호출.

#### publish

기존 inline targets 체크 전에 `validateTargets` 호출.

### 대안 검토

| 접근 방식 | 선택 여부 | 이유 |
|-----------|-----------|------|
| check.ts 진입점에서 정규화 (A안) | 채택 | 변경 범위 최소, typecheck/lint 코드 수정 불필요 |
| typecheck/lint 각각에서 패키지명 인식 (B안) | 미채택 | 변경 범위 넓음, 중복 로직 |
| filterPackagesByTargets 내부에 검증 통합 | 미채택 | 필터링과 검증의 책임 혼합, scripts 제외 등과 얽힘 |
