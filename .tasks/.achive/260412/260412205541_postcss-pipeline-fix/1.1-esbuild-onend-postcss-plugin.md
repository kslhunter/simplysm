## 구현계획

### 배경

sd-cli의 client 빌드에서 `@angular/build`의 `createCompilerPlugin`은 `.ts` 파일 내 inline SCSS에 PostCSS를 적용하지만, library에서 빌드된 `.js` 파일의 inline CSS와 side-effect SCSS import(`esbuild-scss-plugin`)에는 PostCSS가 적용되지 않는다. Feature 1.1은 esbuild `onEnd` 훅에서 모든 출력 CSS에 PostCSS를 일괄 적용하는 독립 플러그인 모듈을 생성한다. [근거: wbs 배경 및 기술적 제약]

### 목표

- esbuild 빌드 완료 후 모든 `.css` 출력 파일에 PostCSS 적용 [근거: Rule ".css 출력 파일에 PostCSS 전체 적용"]
- `.js` 출력 파일 내 Angular 컴포넌트의 `styles: [...]` inline CSS에 PostCSS 적용 [근거: Rule "ɵɵdefineComponent 호출 내 styles 배열"]
- acorn AST 파서로 정확한 styles 배열 위치 추출 및 PostCSS 적용 후 재주입 [근거: D1, D2]

### 비목표

- `esbuild-scss-plugin`의 PostCSS 지원 [근거: wbs 경계 "Feature 1.2"]
- `esbuild-client-config`의 설정 변경 [근거: wbs 경계 "Feature 1.2"]
- sourcemap 갱신 [근거: 기존 onEnd 플러그인 `sd-legacy-strip-dynamic-import`도 sourcemap 미갱신, `esbuild-client-config.ts:194-209`]

### 설계

**새 파일**: `packages/sd-cli/src/esbuild/esbuild-postcss-plugin.ts`

**의존성 추가** (sd-cli의 `package.json`):
- `acorn: ^8.x`
- `acorn-walk: ^8.x`
- (postcss는 이미 의존성에 존재: `package.json:41`)

**인터페이스**:
```typescript
// esbuild-scss-plugin.ts의 createScssPlugin() 팩토리 패턴 준수
import type esbuild from "esbuild";
import type postcss from "postcss";

export interface CreatePostcssPluginOptions {
  /** 이미 로딩된 PostCSS 플러그인 인스턴스 배열 */
  plugins: postcss.AcceptedPlugin[];
}

export function createPostcssPlugin(options: CreatePostcssPluginOptions): esbuild.Plugin;
```
[근거: `esbuild-scss-plugin.ts:6-10`의 `CreateScssPluginOptions` + `createScssPlugin()` 패턴. postcss 타입은 `client-transform-stylesheet.ts:4`의 import 패턴]

**onEnd 콜백 흐름**:
1. `options.plugins`가 비어 있으면 즉시 return [근거: Rule "빈 배열 시 처리 생략"]
2. `result.metafile == null`이면 즉시 return [근거: `sd-legacy-strip-dynamic-import`의 `esbuild-client-config.ts:196` 패턴]
3. `postcss(options.plugins)`로 프로세서 생성 [근거: `client-transform-stylesheet.ts:63-65` 패턴]
4. metafile outputs에서 `.css` 파일 목록 추출 → 각 파일에 `processor.process(css, { from: filePath })` 적용 → 덮어쓰기 [근거: Rule ".css 파일 PostCSS 적용"]
5. metafile outputs에서 `.js` 파일 목록 추출 → `code.includes("styles")` 사전 필터링 [근거: Rule "사전 필터링"]
6. `acorn.parse(code, { ecmaVersion: "latest", sourceType: "module" })` [근거: D1]
7. `acorn-walk.ancestor(ast, { Property })` — `Property`의 ancestors에 `CallExpression`(callee가 `*.ɵɵdefineComponent`)이 있고, key가 `"styles"`이며 value가 `ArrayExpression`인 경우 매칭 [근거: D2]
8. 매칭된 배열의 `Literal` 요소(문자열)에 대해 `{ value, start, end }` 수집 [근거: Rule "문자열 리터럴 추출"]
9. 수집된 CSS 문자열에 `processor.process(css, { from: jsFilePath })` 적용 [근거: `client-transform-stylesheet.ts:98` 패턴]
10. 끝→시작 순으로 원본 소스의 해당 위치를 `JSON.stringify(processedCss)`로 교체 → 파일 덮어쓰기 [근거: Rule "offset 역순 교체"]
11. PostCSS 실패 시 `result.errors.push({ text: ... })` [근거: D3]

**AST 탐색 상세**:
```
CallExpression (i0.ɵɵdefineComponent)
  arguments[0]: ObjectExpression
    properties: [
      Property (key: "styles", value: ArrayExpression)
        elements: [Literal (string)]  ← 이것을 추출
    ]
```
- `walk.ancestor`로 `Property` 노드 방문 시, ancestors 배열에서 `CallExpression.callee.property.name === "ɵɵdefineComponent"` 확인
- esbuild 출력은 ESM이며 `ɵ`(U+0275)는 유니코드 문자 그대로 출력됨

**에러 처리**:
- PostCSS 실패 시 파일별로 `result.errors`에 에러 추가, 나머지 파일은 계속 처리 [근거: D3]

### 대안 검토

| 대안 | 기각 이유 |
|------|----------|
| 정규식 기반 styles 추출 | 사용자 지시: "AST를 쓰던지 해야지" (wbs 근거) |
| @babel/parser 사용 | acorn 대비 ~10배 의존성, esbuild 출력 JS에 과도한 기능 (D1) |
| 범용 매칭 (모든 styles 속성) | 오탐 가능성 (D2) |
