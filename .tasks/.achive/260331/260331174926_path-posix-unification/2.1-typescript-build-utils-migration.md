## 참조 자료

### 설계 결정

| # | 결정사항 | 선택 | 근거 |
|---|---------|------|------|
| D1 | 인터페이스 타입(`affectedFiles: ReadonlySet<string>` 등) 변경 여부 | `string` 유지 | `PosixPath`는 `string` 서브타입이므로 호환. 소비자(worker 등)는 별도 Feature에서 마이그레이션 |
| D2 | `adjustMapSources` 내 `path.relative` 결과 POSIX 변환 여부 | 변환 적용 | source map `sources` 배열은 POSIX가 표준. 경로 통일 취지에 부합 |
| D3 | 변경 불필요 파일 | `tsconfig.ts`, `typecheck-serialization.ts`, `typecheck.ts` 제외 | `tsconfig.ts`는 이미 `pathx.isChildPath()` 사용, 나머지는 경로 정규화 없음 |

      When posix() 함수로 대체한다
      Then posix(this._cwd)와 posix(sf.fileName)으로 워크스페이스 범위를 필터링한다

    Scenario: lint-with-program에서 affected 파일 교차 필터링 시 경로를 POSIX로 정규화한다
      Given lint() 메서드에서 f.replace(/\\/g, "/")로 파일 경로를 정규화하여 affectedFiles.has()로 확인하고 있다
      When posix() 함수로 대체한다
      Then affectedFiles.has(posix(f))로 교차 필터링한다

  Rule: pathx.norm() 사용을 posixResolve()로 대체하고 path.sep를 "/"로 변경한다

    Scenario: output-path-rewriter에서 dist 경로를 POSIX로 생성한다

      Then posixResolve(pkgDir, "dist")로 distDir을 생성하고 distPrefix는 distDir + "/"로 구성한다
      And ownNestedPrefix도 posixResolve(distDir, pkgName, "src") + "/"로 구성한다

    Scenario: output-path-rewriter에서 입력 fileName을 POSIX로 정규화한다
      Given 클로저 내부에서 pathx.norm(fileName)으로 정규화하고 있다
      When posix()로 대체한다
      Then posix(fileName)으로 입력을 정규화한다 (이미 절대 경로이므로 resolve 불필요)

    Scenario: output-path-rewriter에서 flat 경로를 POSIX로 재작성한다
      Given nested 구조를 flat 구조로 재작성할 때 path.join(distDir, ...)을 사용하고 있다
      When posixResolve()로 대체한다
      Then posixResolve(distDir, fileName.slice(ownNestedPrefix.length))로 POSIX 경로를 생성한다

      When posix()를 적용한다
      Then source map의 sources 배열에 POSIX 경로가 기록된다

      Given isNonPackageFile에서 path.resolve(fileName)과 path.resolve(packagesDir) + path.sep으로 비교하고 있다
      When posixResolve()와 "/"로 대체한다

## 구현계획

### 배경

sd-cli의 TypeScript 빌드 유틸리티에서 Windows 경로를 POSIX로 정규화할 때, 세 가지 ad-hoc 패턴이 혼재하고 있다:
1. `.replace(/\\/g, "/")` — 6건 (diagnostic-utils 2, tsc-build 1, lint-with-program 3)
2. `pathx.norm()` — 3건 (output-path-rewriter)
3. `path.resolve()` + `path.sep` — 2건 (typecheck-non-package)

Feature 1.1에서 core-node에 `posix()`와 `posixResolve()`가 도입되었으므로, 이 유틸리티들로 통일한다.

### 목표

- 5개 파일의 모든 ad-hoc 경로 정규화를 `posix()` / `posixResolve()`로 대체
- `path.sep` 사용을 `"/"` 리터럴로 대체
- `pathx.norm()` 사용을 `posixResolve()`로 대체

### 비목표

- 인터페이스 타입 변경 (`affectedFiles: ReadonlySet<string>` 등은 `string` 유지 — D1)
- Feature 2.2 대상 파일 (ngtsc-build-core, angular-compiler, vite-angular-plugin)
- Feature 2.3 대상 파일 (esbuild-config, vite-config)
- Feature 3.x 대상 파일 (worker 파일들)

### 설계

각 파일의 변경은 기계적 패턴 치환이다. 새로운 로직이나 API를 도입하지 않는다.

| 파일 | 변경 패턴 | 건수 |
|------|-----------|------|
| `diagnostic-utils.ts` | `.replace(/\\/g, "/")` → `posix()` | 2 |
| `tsc-build.ts` | `.replace(/\\/g, "/")` → `posix()` | 1 |
| `lint-with-program.ts` | `.replace(/\\/g, "/")` → `posix()` | 3 |
| `output-path-rewriter.ts` | `pathx.norm()` → `posixResolve()`/`posix()`, `path.sep` → `"/"`, `path.join` → `posixResolve()` | 6 |
| `typecheck-non-package.ts` | `path.resolve()` → `posixResolve()`, `path.sep` → `"/"` | 3 |

### 대안 검토

| 접근 방식 | 선택 여부 | 이유 |
|-----------|-----------|------|
| 각 파일에 `posix`/`posixResolve`를 직접 import | 채택 | 기존 코드베이스 패턴과 일치. `pathx.posix()` 형태로도 사용 가능하나 직접 import가 더 간결 |
| `pathx.posix()` 네임스페이스 import 유지 | 미채택 | `output-path-rewriter.ts`는 이미 `pathx` import를 사용하므로 해당 파일에서는 유지. 나머지 파일은 새로 import하므로 직접 import이 간결 |
