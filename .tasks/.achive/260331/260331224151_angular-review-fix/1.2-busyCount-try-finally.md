## 구현계획

### 배경

`AbsSdDataDetail`과 `AbsSdDataSheet`의 async 메서드들이 `busyCount.update(v => v + 1)` → `await _sdToast.try(...)` → `busyCount.update(v => v - 1)` 패턴을 사용한다. `_sdToast.try()`는 non-Error 값이 throw되면 재throw하므로(`sd-toast.provider.ts:149-150`), busyCount 감소 코드에 도달하지 못해 영구 busy 상태가 된다.

### 목표

- 모든 busyCount 증감 패턴에 try-finally 적용
- 공통 유틸리티 `withBusy` 추출로 패턴 통일

### 비목표

- `_sdToast.try()`의 에러 처리 로직 변경 (별도 이슈)
- `sd-data-select-button.control.ts` 수정 (busyCount 미사용)

### 설계

#### `withBusy` 유틸리티 함수

```typescript
// packages/angular/src/core/utils/withBusy.ts
import type { WritableSignal } from "@angular/core";

export async function withBusy(
  busyCount: WritableSignal<number>,
  fn: () => Promise<void>,
): Promise<void> {
  busyCount.update((v) => v + 1);
  try {
    await fn();
  } finally {
    busyCount.update((v) => v - 1);
  }
}
```

#### 적용 패턴

**일반 메서드** (doRefresh, doSubmit 등):
```typescript
// Before
this.busyCount.update((v) => v + 1);
await this._sdToast.try(async () => { ... });
this.busyCount.update((v) => v - 1);

// After
await withBusy(this.busyCount, () => this._sdToast.try(async () => { ... }));
```

**constructor effect** (initialized.set 포함):
```typescript
// Before
this.busyCount.update((v) => v + 1);
await this._sdToast.try(async () => { ... });
this.busyCount.update((v) => v - 1);
this.initialized.set(true);

// After
await withBusy(this.busyCount, () => this._sdToast.try(async () => { ... }));
this.initialized.set(true);
```

constructor effect는 `queueMicrotask(async () => { ... })` 내부이므로, `withBusy`가 throw하면 `initialized.set(true)`에 도달하지 못한다. 이는 기존 동작과 동일하다 — `_sdToast.try()`가 재throw하는 케이스에서는 원래도 `initialized.set(true)`에 도달하지 못했다.

### 대안 검토

| 접근 방식 | 선택 여부 | 이유 |
|-----------|-----------|------|
| `withBusy` 유틸리티 추출 | 채택 | 11곳의 중복 패턴을 단일 함수로 통일, try-finally 누락 방지 |
| 각 위치에 inline try-finally 추가 | 미채택 | 동일 패턴 11곳 반복, 향후 추가 시 누락 위험 |
