## 구현계획

### 배경

sd-cli의 Angular 빌드 테스트 11개 파일 중 3개(`ngtsc-build-core.spec.ts`, `scss-compiler.spec.ts`, `ngtsc-scss-config.spec.ts`)가 `packages/angular`을 직접 참조하여 테스트 실행 시 워크스페이스 상태를 변경(dist 삭제). 2개 파일(`angular-build-pipeline.spec.ts`, `.acc.spec.ts`)이 동일 API를 중복 테스트. 1개 파일(`angular-compiler.spec.ts`)이 1515줄로 과대. [근거: wbs 범위 분석]

### 설계

#### 1. basic-lib fixture 생성

위치: `tests/angular/fixtures/packages/basic-lib/` [근거: D1, 기존 basic-app 패턴 참조]

```
basic-lib/
├── src/
│   ├── test-provider.ts      (@Injectable — ɵprov 검증용)
│   ├── test-directive.ts     (@Directive — ɵdir 검증용)
│   └── test-component.ts     (@Component — 기본 AOT 검증)
├── scss/
│   ├── styles.scss           (전역 스타일 entry — compileGlobalScss 검증용)
│   └── commons/
│       └── _variables.scss   (@use 해석 검증용)
├── node_modules/             (gitignored, basic-app과 동일 Angular 패키지 복사)
├── tsconfig.json             (library mode: declaration true, noEmit false)
├── package.json              (sideEffects: ["./dist/**/*.css"])
└── src/scss.d.ts             (declare module "*.scss" {})
```

node_modules는 basic-app과 동일하게 gitignored + 수동 복사 방식. @angular/core, @angular/common, @angular/compiler, @angular/platform-browser 필요. [근거: basic-app fixture의 node_modules 31MB, 실제 Angular 패키지 복사본]

#### 2. ngtsc-build-worker.spec.ts 격리 (핵심)

이 파일은 `tests/workers/`에 위치하지만 describe가 "ngtsc-build-core: NgtscProgram AOT compilation"으로 실제로는 AngularBuildPipeline + ngtsc-build-core를 테스트하는 통합 테스트이다 (대상 불일치). [근거: WBS 코드 확인]

변경 내용: [근거: Rule "외부 패키지 격리"]

```typescript
// Before (ngtsc-build-worker.spec.ts:9-10)
const workspaceRoot = resolve(import.meta.dirname, "../../../..");
const angularPkgDir = resolve(workspaceRoot, "packages/angular");

// After
const FIXTURE_DIR = resolve(import.meta.dirname, "../angular/fixtures/packages/basic-lib");
```

- `buildWithPipeline()` 함수: `angularPkgDir` → `FIXTURE_DIR`, `workspaceRoot` → `FIXTURE_DIR` (cwd도 fixture 내부)
- beforeAll/afterAll dist 삭제: `packages/angular/dist` → `basic-lib/dist` (fixture 내부)
- AOT 검증: `core/providers/sd-theme-provider.js` → `test-provider.js` (ɵprov), `core/directives/sd-events.js` → `test-directive.js` (ɵdir)
- `compileGlobalScss`: `buildScssLoadPaths`의 cwd/pkgDir을 fixture 기반으로 변경

#### 2-1. ngtsc-build-core.spec.ts 경로 참조 수정 (minor)

`buildScssLoadPaths` 테스트에서 packages/angular 경로를 fixture 또는 임의 경로로 변경. 실제 파일시스템 접근 없이 경로 구성만 검증하므로 간단한 수정. [근거: Rule "외부 패키지 격리"]

#### 5. angular-build-pipeline 중복 해소

통합 전략: [근거: Rule "중복 통합"]

**acc.spec.ts에서 유지** (더 포괄적):
- `client mode: initializes, emits compiled JS, tracks SCSS deps, and collects diagnostics`
- `library mode: initializes with sync SCSS and emits files`
- `findAffectedByScss returns owner files for a dependency SCSS`
- `update re-compiles changed files incrementally`
- `getPackageSourceFiles includes fixture files by default`

**spec.ts에서 추가 편입** (acc.spec.ts에 없는 고유 케이스):
- `getTsProgram throws if called before initialize`
- `collectRawDiagnostics returns ts.Diagnostic array filtered by workspace`
- `collectRawDiagnostics throws if called before initialize`
- `writeEmitResults writes emitted files to disk`
- `update throws if called before initialize`

**삭제** (중복):
- spec.ts의 `initialize returns PipelineResult`, `getEmittedFile`, `getDiagnostics`, `findAffectedByScss empty`, `update returns updated diagnostics` — acc.spec.ts가 더 포괄적으로 커버

결과: 통합된 `angular-build-pipeline.spec.ts` (~250줄 예상). acc.spec.ts 삭제.

공통 헬퍼: `parseFixtureConfig()`, `createPipelineOptions()` — spec.ts의 유틸리티를 통합 파일에 유지.

#### 6. angular-compiler.spec.ts 3파일 분할

공유 mock setup 추출: [근거: D3]

`tests/utils/_angular-compiler-test-setup.ts`:
```typescript
// NgtscProgram mock, mock 변수들, createRealTsProgram 헬퍼
export const mockAnalyzeAsync = vi.fn()...;
export const ngtscConstructorSpy = vi.fn();
export function createRealTsProgram(files, extraOptions) {...}
// vi.mock("../../src/utils/angular-build") 선언
```

분할 결과:

| 파일 | 내용 | 예상 줄수 |
|---|---|---|
| `angular-source-file-cache.spec.ts` | AngularSourceFileCache Unit + 통합 (line 105-227) | ~120줄 |
| `angular-compiler.spec.ts` | AngularCompiler Unit + 초기화 + affected + diagnostics (line 233-852) | ~620줄 |
| `angular-compiler-emit.spec.ts` | emitAffectedFiles + update (line 858-1515) | ~650줄 |

각 파일은 `_angular-compiler-test-setup.ts`를 import하여 mock setup을 공유.

**주의**: vitest에서 `vi.mock()`은 각 테스트 파일 내에서 호이스팅되므로, 공유 파일에서 `vi.mock()`을 직접 호출할 수 없음. 대안:
- 각 파일에서 `vi.mock()` 선언을 유지 (mock factory만 공유 헬퍼에서 export)
- `createRealTsProgram`과 mock 변수는 공유 파일에서 export

#### 7. 패턴 통일

이미 격리된 파일들의 패턴 검토: [근거: Rule "일관된 테스트 패턴"]

- describe 구조: `describe("모듈명", () => describe("기능", () => it("시나리오")))` 패턴
- import 스타일: 정적 import + vi.mock 호이스팅 + 동적 import 패턴
- mock 패턴: `vi.mock()` → `await import()` 순서 일관화
- cleanup: `beforeEach(vi.clearAllMocks)` 패턴 통일

### 대안 검토

**공유 node_modules 방식**: basic-app과 basic-lib의 node_modules를 `fixtures/node_modules/`에 통합 → Angular compiler의 모듈 해석이 각 fixture의 tsconfig 기반이므로, 상위 디렉토리의 node_modules를 안정적으로 찾는다는 보장 없음. 기존 패턴(fixture별 node_modules) 유지가 안전. [근거: basic-app의 기존 동작 방식 확인]

**mock 기반 ngtsc-build-core 테스트**: AOT 컴파일을 모킹하여 unit 테스트화 → ngtsc-build-worker.spec.ts가 이미 이 방식. ngtsc-build-core는 파이프라인의 실제 AOT 동작을 검증하는 통합 테스트이므로 실제 컴파일이 필수. [근거: sd-testing.md "모킹 안 하면 테스트가 물리적으로 돌아갈 수 없는가?"]
