# Feature 1.1 typecheck-lint 통합 (ts.Program 공유)

## 참조 자료

### 현재 아키텍처

- typecheck는 모든 명령어에서 항상 실행됨 (`types.ts:61` "typecheck is always included — not optional")
- lint는 check/build에서만 실행, watch/dev에서 미실행
- typecheck와 lint가 별도 ts.Program을 각각 생성 중 (ESLint `parserOptions: { project: true }`)
- 프로젝트 규모: 581파일, 45K줄, 18패키지

### 엔진별 ts.Program 생성

| 엔진 | Program 타입 | 추출 방법 |
|------|-------------|-----------|
| TscEngine (library) | tsc ts.Program | `runTscPackageBuild()` 반환값 |
| NgtscEngine (angular library) | NgtscProgram | `.getTsProgram()` |
| ServerEsbuildEngine (server) | tsc ts.Program | `runTscPackageBuild()` 반환값 |
| ViteEngine (client) | AngularFacade 내부 | `getProgram()` getter 추가 필요 |

### 명령어별 변경 전/후

| 명령어 | 변경 전 | 변경 후 |
|--------|---------|---------|
| check | typecheck \|\| lint \|\| test (병렬) | typecheck → lint (직렬) \|\| test (병렬) |
| build | (emit+typecheck) \|\| lint (병렬) | emit+typecheck → lint (직렬) |
| watch | emit+typecheck (lint 없음) | emit+typecheck → lint (incremental) |
| dev | emit+typecheck (lint 없음) | emit+typecheck → lint (incremental) |

### ESLint API 확인 사항

- `@typescript-eslint/parser`의 `parserOptions.programs` 옵션으로 외부 ts.Program 주입 가능
- `parserOptions.project`를 null로 설정하면 ESLint가 자체 Program 생성하지 않음
- `FlatESLint` 인스턴스는 `lintFiles()`를 여러 번 호출 가능 (rules/config 1회 로드 후 캐시)
- `lintFiles()`에 특정 파일 경로 배열을 전달하여 해당 파일만 lint 가능

## 구현계획

### 배경

현재 sd-cli에서 typecheck와 lint는 별도 Worker thread에서 독립 실행된다. 각각 ts.Program을 따로 생성하여 중복 비용이 발생하며, watch/dev에서는 lint가 없다. ts.Program은 Worker thread 간 공유가 불가하므로(직렬화 불가), lint를 빌드 워커 내부로 통합하여 같은 thread에서 Program을 공유해야 한다.

### 목표

- 빌드 워커 내부에서 typecheck 후 같은 ts.Program으로 lint 실행
- watch/dev에서 incremental lint 지원
- check/build에서 별도 lint 워커 제거, 엔진 내 lint 결과 사용

### 비목표

- ESLint rule 변경이나 추가
- 파일 단위 의존성 추적 기반 최적화 (패키지 전체 re-lint로 충분)
- `pnpm lint` 단독 명령어 변경 (기존 동작 유지)

### 설계

#### lint-with-program 유틸리티

새 유틸리티 `packages/sd-cli/src/utils/lint-with-program.ts`:
- `runLintWithProgram(program: ts.Program, options: { cwd, pkgDir, fix }): Promise<LintResult>`
- `FlatESLint` 인스턴스 생성 시 `overrideConfig.languageOptions.parserOptions = { programs: [program], project: null }`
- `lintFiles()`에 패키지 소스 파일 경로 전달
- watch 모드용: `LintSession` 클래스 — FlatESLint 인스턴스를 유지하고 `lint(program, files)` 반복 호출

#### tsc-build.ts 변경

`TscPackageBuildResult`에 `program: ts.Program` 필드 추가. `runTscPackageBuild()`에서 생성한 incremental program의 `getProgram()`으로 추출.

#### ngtsc-build-core.ts 변경

`runNgtscBuild()`에서 NgtscProgram도 반환 (`runNgtscRebuild()`는 이미 반환 중).

#### AngularFacade 확장

`getProgram(): ts.Program | undefined` getter 추가. `AngularCompilation` 내부의 program에 접근.

#### 워커 이벤트 확장

`CommonBuildWorkerEvents.build`에 lint 결과 추가:
```typescript
build: {
  js: { success: boolean; errors?: string[]; warnings?: string[] };
  dts: { success: boolean; errors?: string[] };
  lint: { success: boolean; errorCount: number; warningCount: number; formattedOutput: string };
};
```

#### 워커별 lint 통합

각 빌드 워커에서 typecheck 완료 후:
1. ts.Program 추출
2. `runLintWithProgram(program, { cwd, pkgDir })` 호출
3. 결과를 `build` 이벤트에 포함

#### check/build/watch/dev 변경

- `check.ts`: 별도 `runLint()` 제거, engine의 lint 결과 수집 (test만 별도 병렬 유지)
- `BuildOrchestrator`: 별도 `lintTask()` 제거, engine의 lint 결과 수집
- `DevWatchOrchestrator`: 이미 engine 이벤트를 수집하므로 lint 결과도 자동 포함
- `BaseEngine.startWatch()`: lint 결과를 ResultCollector에 추가

### 대안 검토

| 접근 방식 | 선택 여부 | 이유 |
|-----------|-----------|------|
| lint를 빌드 워커 안으로 이동 | 채택 | 같은 thread = Program 공유 가능 |
| Program을 직렬화하여 lint 워커로 전송 | 미채택 | ts.Program은 복잡한 그래프, 직렬화 비실용적 |
| SharedArrayBuffer로 Program 공유 | 미채택 | ts.Program은 SAB 호환 구조가 아님 |
| 파일 단위 의존성 추적 re-lint | 미채택 (비목표) | 패키지 전체 re-lint로 현재 규모에서 충분 |
