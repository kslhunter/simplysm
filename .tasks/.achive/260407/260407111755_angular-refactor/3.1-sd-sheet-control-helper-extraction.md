## 구현계획

### 배경

SdSheetControl(773줄)은 이미 4개 helper composable(useSheetCellAgent, useSheetColumnFixing, useSheetDomAccessor, useSheetLayoutEngine)을 분리했으나, 리사이징 상태 관리(~77줄), 표시 아이템 파이프라인(~61줄), 셀 스타일/클래스 계산(~165줄)이 여전히 control에 남아 있다. [근거: refactor.md DESIGN-003]

기존 helper들은 `use*` composable 패턴을 따른다: options 객체로 Signal 의존성을 받고, signal과 method를 포함한 객체를 반환한다. [근거: `useSheetColumnFixing.ts`, `useSheetCellAgent.ts` 코드 확인]

### 목표

- SdSheetControl을 ~460줄 수준으로 축소 [근거: refactor.md DESIGN-003 suggestion]
- 리사이징/파이프라인/스타일링 각각을 독립적인 composable로 분리 [근거: wbs "추출된 composable은 src/ui/data/sheet/ 디렉토리에 배치"]

### 비목표

- SdSheetControl 템플릿 분할(sub-component화) [근거: wbs 경계]
- 기존 4개 helper 변경 [근거: wbs 경계]
- SdSheetControl의 public API(input/output/model) 변경 [근거: wbs 경계]

### 대안 검토

1. **template에서 composable 직접 참조 (`styling.getHeaderCellStyle()` 등)**: 기존 `layout.headerDefTable()` 패턴과 동일하여 가능하나, 기존 property명 재할당이 더 안전하고 변경 범위가 최소화됨. 기각.
2. **Mixin 패턴**: TypeScript mixin은 class 기반이며 signal composable 패턴과 불일치. 코드베이스에 mixin 사용례 없음. 기각.
3. **셀 스타일링에서 getDataCellClass 제외**: "스타일"과 "클래스"를 분리하면 관련 로직이 흩어짐. wbs가 "스타일/클래스 계산"을 하나로 묶고 있음. 기각.
