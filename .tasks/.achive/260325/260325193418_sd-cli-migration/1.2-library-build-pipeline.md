## 요구명세

```gherkin
Feature: 1.2 Library 빌드 파이프라인

  Background:
    Given sd-cli v14 프로젝트에 Library 패키지(target: node|browser|neutral)가 설정되어 있다

  Rule: esbuild로 unbundled JavaScript 변환을 수행한다

    Scenario: node target 패키지 빌드
      Given target이 "node"인 Library 패키지가 있다
      When Library 빌드를 실행한다
      Then 각 src/*.ts 파일이 dist/*.js + dist/*.js.map으로 변환된다
      And esbuild platform은 "node", target은 "node20"이다
      And format은 "esm"이다
      And bundle은 false이다 (파일 단위 변환)

    Scenario: browser target 패키지 빌드
      Given target이 "browser"인 Library 패키지가 있다
      When Library 빌드를 실행한다
      Then 각 src/*.ts 파일이 dist/*.js + dist/*.js.map으로 변환된다
      And esbuild platform은 "browser", target은 "chrome84"이다

    Scenario: neutral target 패키지 빌드
      Given target이 "neutral"인 Library 패키지가 있다
      When Library 빌드를 실행한다
      Then esbuild platform은 "browser", target은 "chrome84"이다

    Scenario: 상대 import 경로에 .js 확장자 자동 추가
      Given src/foo.ts에 `import { bar } from "./bar"` 가 있다
      When Library 빌드를 실행한다
      Then dist/foo.js에서 import 경로가 "./bar.js"로 변환된다

    Scenario: 이미 확장자가 있는 import는 유지
      Given src/foo.ts에 `import data from "./data.json"` 가 있다
      When Library 빌드를 실행한다
      Then dist/foo.js에서 import 경로가 "./data.json" 그대로 유지된다

    Scenario: 변경되지 않은 파일은 디스크 쓰기 스킵
      Given 이전 빌드 결과 dist/foo.js가 존재한다
      And src/foo.ts의 빌드 결과가 이전과 동일하다
      When Library 빌드를 실행한다
      Then dist/foo.js의 타임스탬프가 변경되지 않는다

  Rule: TypeScript 컴파일러로 .d.ts 파일을 생성한다

    Scenario: .d.ts 및 .d.ts.map 생성
      Given src/index.ts가 있다
      When Library 빌드를 실행한다
      Then dist/index.d.ts와 dist/index.d.ts.map이 생성된다

    Scenario: monorepo path alias로 인한 nested 구조를 flat으로 재작성
      Given src/foo.ts가 monorepo 내 다른 패키지를 path alias로 참조한다
      When Library 빌드를 실행한다
      Then .d.ts가 dist/{pkgName}/src/foo.d.ts가 아닌 dist/foo.d.ts로 생성된다
      And 다른 패키지의 .d.ts는 생성되지 않는다
      And .d.ts.map의 sources 경로도 함께 조정된다

    Scenario: node 환경의 컴파일러 옵션
      Given target이 "node"인 패키지가 있다
      When DTS 빌드를 실행한다
      Then TypeScript lib에서 DOM 관련 라이브러리(lib.dom, lib.webworker)가 제외된다
      And types에 "node"가 포함된다

    Scenario: browser 환경의 컴파일러 옵션
      Given target이 "browser" 또는 "neutral"인 패키지가 있다
      When DTS 빌드를 실행한다
      Then types에서 "node"가 제외된다

    Scenario: src/ 파일만 대상으로 .d.ts 생성
      Given src/index.ts와 tests/index.test.ts가 있다
      When DTS 빌드를 실행한다
      Then dist/index.d.ts만 생성된다
      And tests/ 파일의 .d.ts는 생성되지 않는다

    Scenario: tsBuildInfo로 증분 컴파일
      Given 이전 빌드의 .cache/dts.tsbuildinfo가 존재한다
      When Library 빌드를 실행한다
      Then 변경된 파일만 재컴파일된다

    Scenario: 진단은 패키지 src/ 내 파일만 필터링
      Given 다른 패키지에 타입 에러가 있다
      When DTS 빌드를 실행한다
      Then 현재 패키지 src/ 내의 에러만 보고된다

  Rule: copySrc 패턴의 파일을 src/에서 dist/로 복사한다

    Scenario: copySrc 패턴으로 파일 복사
      Given copySrc: ["**/*.css"]이 설정되어 있다
      And src/styles/app.css가 있다
      When Library 빌드를 실행한다
      Then dist/styles/app.css로 복사된다 (상대 경로 보존)

    Scenario: copySrc 미설정 시 복사 스킵
      Given copySrc가 설정되지 않았다
      When Library 빌드를 실행한다
      Then 소스 파일 복사 단계가 실행되지 않는다

  Rule: Watch 모드에서 파일 변경 시 자동 재빌드한다

    Scenario: 파일 내용 변경 시 rebuild
      Given Watch 모드로 Library 빌드가 실행 중이다
      When src/foo.ts의 내용이 변경된다
      Then esbuild context.rebuild()가 수행된다
      And 변경된 파일만 dist/에 갱신된다

    Scenario: 파일 추가 시 entry points 갱신
      Given Watch 모드로 Library 빌드가 실행 중이다
      When src/new-file.ts가 추가된다
      Then entry points가 갱신되어 esbuild context가 재생성된다
      And dist/new-file.js가 생성된다

    Scenario: 파일 삭제 시 entry points 갱신
      Given Watch 모드로 Library 빌드가 실행 중이다
      When src/old-file.ts가 삭제된다
      Then entry points가 갱신되어 esbuild context가 재생성된다

    Scenario: Watch 모드에서 copySrc 파일 변경 추적
      Given copySrc: ["**/*.css"]이 설정되고 Watch 모드가 실행 중이다
      When src/styles/app.css가 변경된다
      Then dist/styles/app.css가 갱신된다

    Scenario: Watch 모드에서 copySrc 파일 삭제 추적
      Given copySrc: ["**/*.css"]이 설정되고 Watch 모드가 실행 중이다
      When src/styles/old.css가 삭제된다
      Then dist/styles/old.css도 삭제된다

    Scenario: Watch 모드에서 DTS 자동 재빌드
      Given Watch 모드로 DTS 빌드가 실행 중이다
      When src/foo.ts의 타입이 변경된다
      Then dist/foo.d.ts와 dist/foo.d.ts.map이 갱신된다

  Rule: SolidJS 플러그인은 지원하지 않는다

    Scenario: esbuild 설정에 SolidJS 플러그인 미포함
      Given Library 패키지가 있다
      When Library 빌드를 실행한다
      Then esbuild 설정에 SolidJS 플러그인이 포함되지 않는다
```

## 구현계획

### 배경

Library 빌드 파이프라인 코드는 v13에서 v14로 복사·적응 과정에서 이미 구현되어 있다. Feature 1.1에서 WorkerManager, ResultCollector, SignalHandler, CLI 프레임워크 등 인프라가 구축되었고, 그 위에 LibraryBuilder, DtsBuilder, library.worker, dts.worker, copy-src 등이 동작 중이다. 단, Library 빌드 관련 단위 테스트가 0개이며, wbs.md 제외 사항인 SolidJS 플러그인 코드가 잔존한다.

### 목표

- SolidJS 플러그인 코드 제거 (esbuild-config.ts)
- Library 빌드 파이프라인 전체 단위 테스트 작성 (요구명세의 모든 Gherkin Scenario 커버)

### 비목표

- Watch 오케스트레이션 — WatchOrchestrator 조율 레이어 (Feature 1.5)
- Server 빌드 파이프라인 (Feature 1.3)
- 코드 검사 파이프라인 — typecheck, lint (Feature 1.4)
- 빌드 오케스트레이션 — BuildOrchestrator (Feature 1.7)
- Server용 esbuild 설정 (`createServerEsbuildOptions`) 테스트 (Feature 1.3)

#### 모킹 전략

기존 테스트(base-builder.spec.ts, worker-events.spec.ts)의 패턴을 따른다:
- `esbuild`: vi.mock으로 `build()`, `context()` 모킹 — OutputFile 배열 반환
- `@simplysm/core-node`: vi.mock으로 `Worker.create()`, `FsWatcher.watch()` 모킹
- `node:fs/promises`: vi.mock으로 `readFile`, `writeFile`, `mkdir`, `cp` 모킹
- `consola`: vi.mock으로 로거 모킹
- TypeScript 컴파일러: vi.mock으로 `createIncrementalProgram`, `createWatchProgram` 모킹
