```gherkin
Feature: 1.3 Server 빌드 파이프라인

  Background:
    Given sd.config.ts에 target: "server"인 패키지가 정의되어 있다
    And 해당 패키지의 TypeScript 소스 코드가 존재한다

  Rule: 서버 코드를 esbuild로 단일 파일 번들링한다

    Scenario: 프로덕션 빌드로 단일 ESM 번들 생성
      Given 서버 패키지의 tsconfig과 소스 파일이 준비되어 있다
      When build()를 실행한다
      Then dist/main.js가 ESM 형식(format:esm)의 단일 번들로 생성된다
      And platform은 node, target은 node20이다
      And 코드가 minify된다

    Scenario: Watch 모드 빌드 시 minify하지 않음
      Given 서버 패키지의 tsconfig과 소스 파일이 준비되어 있다
      When startWatch()를 실행하여 초기 빌드가 완료된다
      Then dist/main.js가 ESM 형식의 단일 번들로 생성된다
      And 코드가 minify되지 않는다

    Scenario: CJS require() 호환을 위한 createRequire shim
      Given 서버 코드에서 CJS 모듈을 사용한다
      When 번들링한다
      Then 출력 파일 상단에 createRequire shim banner가 포함된다
      And ESM 환경에서 require()를 호출할 수 있다

    Scenario: 환경변수 빌드타임 치환
      Given sd.config.ts에 env: { "API_URL": "https://api.example.com" }이 설정되어 있다
      When 번들링한다
      Then 소스의 process.env.API_URL이 "https://api.example.com" 문자열 상수로 치환된다

  Rule: 번들에서 제외할 외부 모듈을 자동/수동으로 결정한다

    Scenario: Native 모듈 자동 외부화
      Given 의존성 트리에 binding.gyp를 포함한 패키지가 있다
      When 외부 모듈을 수집한다
      Then 해당 패키지가 외부 모듈로 분류되어 번들에서 제외된다

    Scenario: 미설치 optional peer dependency 자동 외부화
      Given 의존성의 peerDependenciesMeta에 optional: true인 패키지가 있다
      And 해당 패키지가 resolve되지 않는다
      When 외부 모듈을 수집한다
      Then 해당 패키지가 외부 모듈로 분류된다

    Scenario: sd.config.ts에서 수동 외부화
      Given sd.config.ts에 externals: ["some-pkg"]이 설정되어 있다
      When 외부 모듈을 수집한다
      Then "some-pkg"가 외부 모듈 목록에 포함된다

    Scenario: 외부 모듈을 dist/package.json dependencies에 반영
      Given 외부 모듈로 ["bcrypt", "some-pkg"]가 수집되었다
      When 프로덕션 빌드를 완료한다
      Then dist/package.json의 dependencies에 { "bcrypt": "*", "some-pkg": "*" }가 포함된다

  Rule: 빌드 시 프로덕션 배포 파일을 생성한다

    Scenario: 런타임 설정 파일 생성
      Given sd.config.ts에 configs가 설정되어 있다
      When 빌드한다
      Then dist/.config.json에 해당 설정이 JSON으로 기록된다

    Scenario: dist/package.json 생성
      Given 패키지의 package.json에 name, version, type 필드가 있다
      And 외부 모듈이 수집되었다
      When 빌드한다
      Then dist/package.json에 name, version, type이 복사되고 외부 모듈이 dependencies로 추가된다

    Scenario: Volta 환경의 package.json
      Given sd.config.ts에 packageManager: "volta"가 설정되어 있다
      When 빌드한다
      Then dist/package.json에 volta 필드(node 버전)가 추가된다

    Scenario: Mise 환경의 mise.toml 생성
      Given sd.config.ts에 packageManager: "mise"가 설정되어 있다
      And 프로젝트 루트에 mise.toml이 있다
      When 빌드한다
      Then dist/mise.toml이 생성되고 루트 mise.toml의 Node 버전이 참조된다

    Scenario: Mise 환경에서 루트 mise.toml 미존재 시 기본값
      Given sd.config.ts에 packageManager: "mise"가 설정되어 있다
      And 프로젝트 루트에 mise.toml이 없다
      When 빌드한다
      Then dist/mise.toml의 Node 버전이 "20"으로 설정된다

    Scenario: OpenSSL 설정 파일 생성
      When 빌드한다
      Then dist/openssl.cnf가 생성되고 레거시 OpenSSL provider 활성화 설정이 포함된다

    Scenario: PM2 설정 파일 생성
      Given sd.config.ts에 pm2 설정이 있다
      When 빌드한다
      Then dist/pm2.config.cjs가 생성된다
      And watch, watch_delay(2000ms), ignore_watch 설정이 포함된다
      And 환경변수가 포함된다
      And interpreter가 packageManager에 따라 설정된다

    Scenario: PM2 미설정 시 pm2.config.cjs 미생성
      Given sd.config.ts에 pm2 설정이 없다
      When 빌드한다
      Then dist/pm2.config.cjs가 생성되지 않는다

  Rule: 정적 파일을 dist에 복사한다

    Scenario: 프로덕션 빌드 시 public/ 복사
      Given 서버 패키지에 public/ 디렉토리가 있다
      When build()를 실행한다
      Then public/ 내용이 dist/에 복사된다
      And public-dev/는 복사되지 않는다

    Scenario: Watch 모드 시 public/ + public-dev/ 복사
      Given 서버 패키지에 public/과 public-dev/ 디렉토리가 있다
      When startWatch()를 실행한다
      Then public/과 public-dev/ 내용이 dist/에 복사된다
      And public-dev/ 파일이 public/ 파일보다 우선한다

  Rule: 빌드된 서버를 실행하고 관리한다

    Scenario: 서버 정상 시작
      Given dist/main.js가 server 인스턴스를 export한다
      When server-runtime.worker의 start()를 실행한다
      Then 환경변수를 process.env에 주입한 후 main.js를 dynamic import한다
      And server.listen()으로 서버를 시작한다
      And serverReady 이벤트와 함께 포트 번호를 전달한다

    Scenario: 포트 충돌 시 자동 증가
      Given 원래 포트가 이미 사용 중이다
      When start()를 실행한다
      Then 다음 포트를 순차적으로 시도한다
      And 최대 20개 포트까지 시도한다

    Scenario: 모든 포트 사용 불가 시 에러
      Given 원래 포트부터 20개 포트가 모두 사용 중이다
      When start()를 실행한다
      Then error 이벤트를 발생시킨다

    Scenario: 서버 런타임 에러 전파
      Given 서버가 실행 중이다
      When uncaughtException 또는 unhandledRejection이 발생한다
      Then error 이벤트를 발생시킨다

  Rule: Watch 모드에서 변경 감지 후 리빌드한다

    Scenario: startWatch() 중복 호출 방지
      Given startWatch()가 이미 실행 중이다
      When startWatch()를 다시 호출한다
      Then 중복 실행되지 않는다

    Scenario: metafile.inputs에 포함된 파일 변경 시 리빌드
      Given startWatch()가 실행 중이다
      When metafile.inputs에 포함된 소스 파일이 변경된다
      Then buildStart 이벤트 후 리빌드가 실행된다

    Scenario: metafile.inputs에 없는 파일 변경 시 스킵
      Given startWatch()가 실행 중이다
      When metafile.inputs에 포함되지 않은 파일이 변경된다
      Then 리빌드를 실행하지 않는다

    Scenario: 파일 추가/삭제 시 esbuild context 재생성
      Given startWatch()가 실행 중이다
      When 새 파일이 추가되거나 기존 파일이 삭제된다
      Then esbuild context를 재생성한 후 리빌드를 실행한다

    Scenario: Workspace 의존성 파일 변경 감시
      Given startWatch()가 실행 중이다
      And workspace 의존성 패키지가 있다
      When 의존성 패키지의 소스 파일이 변경된다
      Then 해당 변경이 리빌드 판단에 반영된다

    Scenario: replaceDeps 경로 변경 감시
      Given startWatch()가 실행 중이다
      And replaceDeps가 설정되어 있다
      When replaceDeps 대상 패키지의 dist 파일이 변경된다
      Then 해당 변경이 리빌드 판단에 반영된다

    Scenario: 출력 변경 없는 리빌드 시 파일 미갱신
      Given startWatch()가 실행 중이다
      When 리빌드가 완료되었으나 출력이 이전과 동일하다
      Then 파일을 덮어쓰지 않는다
```

## 구현계획

### 배경

Feature 1.3의 구현 코드는 v13에서 v14로 마이그레이션되어 이미 동작 중이다. 핵심 파일:
- `packages/sd-cli/src/workers/server.worker.ts` (734줄): build() + startWatch()
- `packages/sd-cli/src/workers/server-runtime.worker.ts` (172줄): start() + 포트 할당
- `packages/sd-cli/src/utils/esbuild-config.ts` (330줄): createServerEsbuildOptions, writeChangedOutputFiles
- `packages/sd-cli/src/utils/copy-public.ts`: copyPublicFiles, watchPublicFiles
- `packages/sd-cli/src/utils/package-utils.ts`: collectDeps

기존 19개 테스트 파일이 있으나 server.worker, server-runtime.worker에 대한 테스트가 없고, esbuild-config.spec.ts도 createServerEsbuildOptions를 테스트하지 않는다.

### 목표

- 요구명세의 모든 Scenario에 대한 테스트 커버리지 확보
- 테스트 과정에서 발견된 이슈 수정

### 비목표

- Orchestrator 수준 로직 (Feature 1.5/1.6/1.7 범위)
- 기존 코드의 리팩토링 (동작하는 코드를 건드리지 않음)

### 설계

기존 테스트 패턴을 따른다:
- **Worker 테스트**: `createWorker` 모킹으로 workerFns 캡처 후 직접 호출 (`library-worker.spec.ts` 패턴)
- **모킹 대상**: esbuild, fs/promises, @simplysm/core-node (FsWatcher), net, consola
- **유틸리티 테스트**: 함수 직접 import 후 의존성 모킹 (`esbuild-config.spec.ts` 패턴)

테스트 파일:
| 파일 | 테스트 대상 |
|------|-----------|
| `tests/esbuild-config.spec.ts` (기존 확장) | createServerEsbuildOptions 추가 |
| `tests/server-worker.spec.ts` (신규) | server.worker build() + startWatch() |
| `tests/server-runtime-worker.spec.ts` (신규) | server-runtime.worker start() + 포트 할당 |

### 대안 검토

| 접근 방식 | 선택 | 이유 |
|-----------|------|------|
| 단위 테스트 (모킹) | 채택 | 기존 19개 테스트의 일관된 패턴, 빠른 실행, CI 안정성 |
| E2E 테스트 (실제 esbuild 빌드) | 미채택 | 느리고 환경 의존적, 기존 패턴과 불일치 |
