## 요구명세

```gherkin
Feature: 1.5 Watch 오케스트레이션

  Background:
    Given monorepo에 sd.config.ts가 존재한다
    And watch 명령어가 실행된다

  Rule: Library 패키지에 대해 LibraryBuilder + DtsBuilder를 동시 조율한다

    Scenario: Library 패키지가 있으면 빌더를 생성하고 watch를 시작한다
      Given sd.config.ts에 node 타겟 패키지 "core-common"이 정의되어 있다
      And sd.config.ts에 browser 타겟 패키지 "core-browser"가 정의되어 있다
      When WatchOrchestrator가 초기화된다
      Then "core-common"에 대해 LibraryBuilder와 DtsBuilder가 생성된다
      And "core-browser"에 대해 LibraryBuilder와 DtsBuilder가 생성된다
      And 각 빌더의 watch 모드가 시작된다

    Scenario: Library 패키지가 없고 scripts+watch만 있으면 빌더를 생성하지 않는다
      Given sd.config.ts에 Library 타겟 패키지가 없다
      And scripts 타겟 패키지 "sd-scripts"에 watch 설정이 있다
      When WatchOrchestrator가 초기화된다
      Then LibraryBuilder와 DtsBuilder가 생성되지 않는다
      And watch hook만 시작된다

    Scenario: watch 대상 패키지가 전혀 없으면 조기 종료한다
      Given sd.config.ts에 Library 타겟 패키지가 없다
      And scripts+watch 패키지도 없다
      When WatchOrchestrator가 초기화된다
      Then "No packages to watch" 메시지가 출력된다
      And 프로세스가 종료된다

  Rule: 초기 빌드가 완료될 때까지 대기 후 결과를 출력한다

    Scenario: 모든 패키지의 초기 빌드가 성공한다
      Given 3개 Library 패키지가 watch 모드로 시작된다
      When 각 패키지의 LibraryBuilder와 DtsBuilder 초기 빌드가 모두 완료된다
      Then "Initial build completed" 메시지가 출력된다
      And 빌드 결과가 출력된다

    Scenario: 일부 빌더가 실패해도 나머지를 대기한다
      Given 3개 Library 패키지가 watch 모드로 시작된다
      When 1개 패키지의 DtsBuilder가 타입 에러로 실패한다
      And 나머지 빌더가 정상 완료된다
      Then Promise.allSettled로 모든 빌더 완료를 대기한다
      And 에러를 포함한 전체 결과가 출력된다
      And watch 모드는 계속 유지된다

  Rule: replaceDeps 설정이 있으면 소스 변경을 실시간 감시한다

    Scenario: replaceDeps 설정이 있으면 감시를 시작한다
      Given sd.config.ts에 replaceDeps 설정이 존재한다
      When WatchOrchestrator가 초기화된다
      Then watchReplaceDeps()가 호출되어 소스 디렉토리 감시가 시작된다

    Scenario: 소스 파일이 변경되면 node_modules로 복사한다
      Given replaceDeps 감시가 활성화되어 있다
      When 소스 디렉토리의 파일이 변경된다
      Then 300ms 딜레이 후 변경된 파일이 대상 node_modules로 복사된다

    Scenario: replaceDeps 설정이 없으면 감시하지 않는다
      Given sd.config.ts에 replaceDeps 설정이 없다
      When WatchOrchestrator가 초기화된다
      Then replaceDeps 감시가 시작되지 않는다

  Rule: scripts 패키지의 watch hook을 지원한다

    Scenario: scripts+watch 설정이 있으면 초기 hook을 실행하고 감시를 시작한다
      Given scripts 타겟 패키지 "sd-scripts"에 watch 설정이 있다
      And watch.target이 ["dist/**/*.js"]이다
      And watch.cmd가 "node"이고 watch.args가 ["run-task.js"]이다
      When 초기 빌드가 완료된다
      Then "node run-task.js"가 cwd=패키지 디렉토리에서 실행된다
      And dist/**/*.js에 대한 FsWatcher 감시가 시작된다

    Scenario: 감시 대상 파일이 변경되면 hook을 재실행한다
      Given watch hook 감시가 활성화되어 있다
      When 감시 대상 파일이 변경된다
      Then 300ms 딜레이 후 hook cmd가 재실행된다

    Scenario: hook cmd가 실패해도 프로세스가 계속된다
      Given watch hook이 실행 중이다
      When hook cmd가 exit code 1로 종료된다
      Then warn 로그가 출력된다
      And watch 모드는 계속 유지된다

  Rule: RebuildManager로 재빌드 진행률을 배치 표시한다

    Scenario: 파일 변경 시 재빌드를 배치로 처리한다
      Given 초기 빌드가 완료된 상태다
      When Library 패키지의 소스 파일이 변경된다
      Then 워커에서 buildStart 이벤트가 발생한다
      And RebuildManager에 빌드가 등록된다
      And "Rebuilding... (패키지명)" 메시지가 출력된다
      And 빌드 완료 후 "Rebuild completed (패키지명)" 메시지가 출력된다
      And 에러가 있으면 출력된다

    Scenario: 동시 다발적 변경은 하나의 배치로 묶인다
      Given 초기 빌드가 완료된 상태다
      When 여러 패키지의 소스 파일이 동시에 변경된다
      Then 하나의 배치로 수집되어 "Rebuilding... (pkg1, pkg2)" 형태로 출력된다

    Scenario: 배치 처리 중 새 변경이 발생하면 다음 배치로 누적된다
      Given 재빌드 배치가 진행 중이다
      When 새로운 파일 변경이 발생한다
      Then 현재 배치 완료 후 다음 배치로 처리된다

  Rule: copySrc 설정이 있으면 파일 복사 감시를 시작한다

    Scenario: copySrc 설정이 있으면 감시를 시작한다
      Given Library 패키지에 copySrc 설정이 존재한다
      When WatchOrchestrator가 시작된다
      Then watchCopySrcFiles()가 호출되어 src/→dist/ 복사 감시가 시작된다

    Scenario: copySrc 설정이 없으면 감시하지 않는다
      Given Library 패키지에 copySrc 설정이 없다
      When WatchOrchestrator가 시작된다
      Then copySrc 감시가 시작되지 않는다

  Rule: Graceful shutdown을 지원한다

    Scenario: SIGINT 수신 시 모든 리소스를 정리한다
      Given watch 모드가 실행 중이다
      When SIGINT 신호가 수신된다
      Then "Shutting down..." 메시지가 출력된다
      And LibraryBuilder와 DtsBuilder가 shutdown된다
      And 모든 FsWatcher가 close된다
      And replaceDeps watcher가 dispose된다
      And "Done" 메시지가 출력된다

  Rule: targets 인자로 특정 패키지만 선택할 수 있다

    Scenario: targets 인자가 지정되면 해당 패키지만 watch한다
      Given sd.config.ts에 5개 패키지가 정의되어 있다
      When targets 인자로 ["core-common", "core-browser"]가 지정된다
      Then 2개 패키지만 watch 대상으로 선정된다

    Scenario: targets 인자가 없으면 모든 패키지를 watch한다
      Given sd.config.ts에 5개 패키지가 정의되어 있다
      When targets 인자가 비어있다
      Then 모든 패키지가 watch 대상으로 선정된다
```

## 구현계획

### 배경

WatchOrchestrator는 v13에서 복사된 277줄의 코드로, Library 패키지(node/browser/neutral)의 watch 모드를 조율한다. 의존 모듈(LibraryBuilder, DtsBuilder, RebuildManager, ResultCollector, SignalHandler 등)은 Feature 1.1~1.2에서 v14에 적응되었고, 개별 단위 테스트가 존재한다. 그러나 WatchOrchestrator 자체의 테스트가 없어, 오케스트레이션 로직의 v14 환경 정상 동작을 보장할 수 없다.

기존 테스트 현황:

| 모듈 | 테스트 파일 | 상태 |
|------|-----------|------|
| RebuildManager | `rebuild-manager.spec.ts` | 있음 |
| BaseBuilder | `base-builder.spec.ts` | 있음 |
| SignalHandler | `signal-handler.spec.ts` | 있음 |
| ResultCollector | `result-collector.spec.ts` | 있음 |
| WorkerManager | `worker-manager.spec.ts` | 있음 |
| copy-src | `copy-src.spec.ts` | 있음 |
| replace-deps | `replace-deps.spec.ts` | 있음 |
| output-utils | `output-utils.spec.ts` | 있음 |
| **WatchOrchestrator** | — | **없음** |

### 목표

- WatchOrchestrator의 단위 테스트를 작성하여 오케스트레이션 로직을 검증한다
- 테스트 실행으로 발견된 문제를 수정한다

### 비목표

- 개별 워커 테스트 (이미 존재)
- 인프라 모듈 테스트 (이미 존재)
- WatchOrchestrator 코드 리팩토링
- E2E 테스트 (실제 파일 시스템, 실제 Worker)

### 설계

#### 모킹 전략

WatchOrchestrator는 의존 모듈의 조합자이므로, 의존 모듈을 모킹하고 조합 로직만 테스트한다.

| 모듈 | 모킹 방식 | 이유 |
|------|-----------|------|
| `loadSdConfig` | `vi.mock` → SdConfig 반환 | 실제 sd.config.ts 로드 방지 |
| `filterPackagesByTargets` | `vi.mock` → 필터된 패키지 반환 | 필터링 로직은 별도 테스트 존재 |
| `LibraryBuilder` | `vi.mock` → mock class | 빌더 로직은 별도 테스트 존재 |
| `DtsBuilder` | `vi.mock` → mock class | 동일 |
| `ResultCollector` | `vi.mock` → mock class | 결과 수집은 별도 테스트 존재 |
| `RebuildManager` | `vi.mock` → mock class (on 메서드 포함) | 배치 처리는 별도 테스트 존재 |
| `SignalHandler` | `vi.mock` → mock class | 신호 처리는 별도 테스트 존재 |
| `watchReplaceDeps` | `vi.mock` → mock result (dispose) | replaceDeps 로직은 별도 테스트 존재 |
| `watchCopySrcFiles` | `vi.mock` → mock watcher (close) | copySrc 로직은 별도 테스트 존재 |
| `FsWatcher.watch` | `vi.mock` → mock watcher (onChange, close) | watch hook 파일 감시 |
| `child_process.spawn` | `vi.mock` → mock child (on) | watch hook 명령 실행 |
| `printErrors` | `vi.mock` → `vi.fn()` | 출력 검증 |

#### 테스트 경계

WatchOrchestrator 테스트에서는 **조합 로직**만 검증한다. 의존 모듈의 내부 동작(RebuildManager 배치 처리, replaceDeps 파일 복사 등)은 각 모듈의 기존 테스트에서 이미 검증되므로, WatchOrchestrator에서는 "올바른 인자로 호출되는지"만 확인한다.

| 요구명세 Scenario | 테스트 수준 | 검증 내용 |
|-------------------|-----------|-----------|
| 파일 변경 시 재빌드를 배치로 처리 | WatchOrchestrator: batchComplete → printErrors 호출 | RebuildManager.on("batchComplete") 등록 확인 |
| 동시 다발적 변경 배치 처리 | RebuildManager 테스트에서 이미 검증 | WatchOrchestrator에서는 테스트 불필요 |
| 배치 중 새 변경 다음 배치 누적 | RebuildManager 테스트에서 이미 검증 | WatchOrchestrator에서는 테스트 불필요 |
| 소스 변경 시 node_modules 복사 | replace-deps 테스트에서 이미 검증 | WatchOrchestrator에서는 watchReplaceDeps 호출만 확인 |

### 대안 검토

| 접근 방식 | 선택 여부 | 이유 |
|-----------|-----------|------|
| 의존 모듈 모킹 + 조합 로직 테스트 | 채택 | 빠르고 안정적, 오케스트레이션 로직에 집중 |
| 실제 Worker 사용 통합 테스트 | 미채택 | 느리고 환경 의존적, 개별 워커 테스트 이미 존재 |
| E2E 테스트 (실제 watch 실행) | 미채택 | 실행 시간 길고 CI 불안정, ROI 낮음 |
