# Feature 3.5 서비스 연동 프로바이더

## 참조 자료

- [wbs.md](./wbs.md)

### 설계 결정

| # | 결정사항 | 선택 | 근거 |
|---|---------|------|------|
| D1 | ISharedSignal.$get() 패턴 | 래퍼 객체 반환 (SharedDataHandle) | 타입 안전, monkey-patch 제거, Angular 표준 패턴. `handle.items()` → `T[]`, `handle.get(key)` → `T \| undefined` |
| D2 | Provider cleanup 패턴 | DestroyRef.onDestroy() + fire-and-forget close | effect() cleanup은 sync만 지원, client.close()는 async. 앱 종료 시점이므로 await 불필요 |
| D3 | HMR reload 로직 | 전체 제거 | v14 ServiceClient에 "reload" 이벤트 없음. Angular 21 네이티브 HMR로 대체 (WBS 결정) |
| D4 | SdSharedDataChangeEvent 패턴 | defineEvent()로 전환 | v14 service-common API. SdServiceEventListenerBase 클래스 → 함수형 이벤트 정의 |
| D5 | loadingCount 타입 | signal(0) | SdBusyProvider.globalBusyCount 패턴과 동일. reactive 추적 가능 |

```gherkin
Feature: 3.5 서비스 연동 프로바이더

  Background:
    Given Angular 21 앱이 실행 중이다
    And SdToastProvider와 SdAngularConfigProvider가 제공된다

  Rule: 명명된 키로 서비스 클라이언트를 연결·해제·조회한다

    Scenario: 새 키로 서비스 클라이언트 연결
      Given SdServiceClientFactoryProvider가 주입된다
      When 키 "main"과 기본 옵션으로 connectAsync()를 호출한다
      Then ServiceClient가 생성되어 WebSocket으로 서버에 연결된다
      And 클라이언트가 내부 맵에 키 "main"으로 저장된다

    Scenario: 연결된 클라이언트 조회
      Given 키 "main"으로 연결된 클라이언트가 있다
      When get("main")을 호출한다
      Then 해당 ServiceClient 인스턴스가 반환된다

    Scenario: 클라이언트 연결 해제
      Given 키 "main"으로 연결된 클라이언트가 있다
      When closeAsync("main")을 호출한다
      Then 클라이언트가 close()되고 내부 맵에서 제거된다

    Scenario: 이미 연결된 키로 재연결 시도
      Given 키 "main"으로 연결된 클라이언트가 있다
      When 키 "main"으로 connectAsync()를 다시 호출한다
      Then "이미 연결된 클라이언트" 에러가 발생한다

    Scenario: 연결 끊긴 키로 재연결 시도
      Given 키 "main"으로 연결했으나 연결이 끊긴 클라이언트가 있다
      When 키 "main"으로 connectAsync()를 다시 호출한다
      Then "이미 연결이 끊긴 클라이언트" 에러가 발생한다

    Scenario: 미연결 키로 조회
      When get("unknown")을 호출한다
      Then "연결하지 않은 클라이언트 키" 에러가 발생한다

  Rule: 요청/응답 진행도를 토스트로 표시한다

    Scenario: 요청 전송 진행도 토스트
      Given 키 "main"으로 연결된 클라이언트가 있다
      When 클라이언트에서 request-progress 이벤트가 발생한다
      Then SdToastProvider.info()로 "요청을 전송하는 중입니다." 토스트가 생성된다
      And 진행도 시그널이 (completedSize / totalSize × 100)으로 업데이트된다

    Scenario: 응답 수신 진행도 토스트
      Given 키 "main"으로 연결된 클라이언트가 있다
      When 클라이언트에서 response-progress 이벤트가 발생한다
      Then SdToastProvider.info()로 "응답을 전송받는 중입니다." 토스트가 생성된다
      And 진행도 시그널이 업데이트된다

    Scenario: 전송 완료 시 토스트 정리
      Given 진행도 토스트가 표시 중이다
      When completedSize === totalSize인 이벤트가 발생한다
      Then 해당 uuid의 토스트가 진행도 맵에서 제거된다

  Rule: Provider 소멸 시 모든 연결을 정리한다

    Scenario: 앱 종료 시 연결 정리
      Given 키 "main"과 "sub"로 연결된 클라이언트가 있다
      When 앱이 종료되어 Provider가 소멸된다
      Then 모든 클라이언트에 close()가 호출된다
      And 내부 맵이 비워진다

  Rule: 공유 데이터를 등록하고 핸들로 조회한다

    Scenario: 데이터 등록 후 첫 조회
      Given SdSharedDataProvider 구현체가 주입된다
      And register("users", getter)로 데이터 소스가 등록되었다
      When getHandle("users")을 호출한다
      Then 데이터가 비동기 로드된다
      And 서비스 이벤트 리스너가 등록된다
      And SharedDataHandle이 반환된다 (items: Signal<T[]>, get: (key) => T | undefined)

    Scenario: 이미 로드된 데이터 재조회
      Given "users" 핸들이 이미 생성되었다
      When getHandle("users")을 다시 호출한다
      Then 기존 핸들이 반환된다 (데이터 리로드 없음)

    Scenario: 미등록 이름으로 조회
      When getHandle("unknown")을 호출한다
      Then 에러가 발생한다

    Scenario: 키로 단건 조회
      Given "users" 핸들이 로드되었다
      When handle.get(userId)을 호출한다
      Then 해당 key의 항목이 반환된다 (없으면 undefined)

    Scenario: register 재호출로 getter 변경
      Given "users" 핸들이 이미 생성되었다
      When 새로운 getter로 register("users", newGetter)를 호출한다
      Then 기존 리스너 키가 초기화된다
      And 새 getter로 데이터가 리로드된다

  Rule: 서비스 이벤트로 실시간 동기화한다

    Scenario: 전체 데이터 리로드 이벤트
      Given "users" 핸들이 로드되었다
      When 다른 클라이언트가 emitAsync("users")를 호출한다 (changeKeys 없음)
      Then 이벤트를 수신하여 전체 데이터를 리로드한다
      And handle.items() 시그널이 새 데이터로 교체된다

    Scenario: 부분 업데이트 이벤트
      Given "users" 핸들에 [A, B, C] 데이터가 있다
      When changeKeys [B]로 이벤트가 수신된다
      Then B를 기존 데이터에서 제거하고 새로 로드된 B를 추가한다
      And orderBy 설정에 따라 재정렬한다

    Scenario: 필터 기반 이벤트 전파
      Given 동일 이름 "users"에 서로 다른 filter로 등록된 핸들이 있다
      When emitAsync("users", changeKeys)를 호출한다
      Then 동일 filter를 가진 리스너에만 이벤트가 전파된다

    Scenario: 모든 로딩 완료 대기
      Given 여러 데이터가 비동기 로드 중이다
      When wait()를 호출한다
      Then loadingCount가 0 이하가 될 때까지 대기한다
```

## 구현계획

### 배경

Feature 1.9에서 forward dependency(SdToastProvider, SdBusyProvider 미존재)로 이관된 2개 Provider를 v14 환경에 맞게 마이그레이션한다. v12 원본 코드가 source of truth이며, v14 API(signal, effect, createServiceClient, defineEvent)로 치환한다.

### 목표

- SdServiceClientFactoryProvider: 명명된 키 기반 서비스 클라이언트 관리 + 진행도 토스트
- SdSharedDataProvider: 공유 데이터 실시간 동기화 (abstract class + SharedDataHandle)
- v14 API 완전 치환, HMR reload 로직 제거

### 비목표

- SdPrintProvider (Feature 3.5.1)
- SdSharedDataProvider 구현체 (앱별 구현)
- features/shared-data 컨트롤 (Epic 7)

#### SdServiceClientFactoryProvider API

| 멤버 | 시그니처 | 설명 |
|------|---------|------|
| connectAsync | `(key: string, options?: Partial<ServiceConnectionOptions>) => Promise<void>` | 서비스 클라이언트 생성·연결, 진행도 이벤트 등록 |
| closeAsync | `(key: string) => Promise<void>` | 클라이언트 해제·맵 제거 |
| get | `(key: string) => ServiceClient` | 연결된 클라이언트 반환 |

inject 의존:
- `SdToastProvider` — 진행도 토스트
- `SdAngularConfigProvider` — clientName
- `DestroyRef` — cleanup

v12 대비 변경:
- `new SdServiceClient(name, config)` → `createServiceClient(name, options)`
- `ISdServiceConnectionConfig` → `ServiceConnectionOptions` (host, port, ssl, maxReconnectCount)
- `client.connectAsync()` → `client.connect()`
- `client.closeAsync()` → `client.close()`
- `client.on("reload", ...)` → 제거 (D3)
- `$effect(onCleanup)` → `DestroyRef.onDestroy()` (D2)
- 기본 옵션: `{ host: location.hostname, port: Number(location.port), ssl: location.protocol.startsWith("https") }`

#### SdSharedDataProvider API

| 멤버 | 시그니처 | 설명 |
|------|---------|------|
| loadingCount | `Signal<number>` | 진행 중 로딩 수 (D5) |
| initialize | `abstract () => void` | 앱별 구현 (register 호출) |
| register | `<K>(name: K, getter: ISharedDataInfo<T[K]>) => void` | 데이터 소스 등록 |
| getHandle | `<K>(name: K) => SharedDataHandle<T[K]>` | 핸들 반환 (D1) |
| emitAsync | `<K>(name: K, changeKeys?) => Promise<void>` | 변경 이벤트 발행 |
| wait | `() => Promise<void>` | 로딩 완료 대기 |

#### SharedDataHandle 타입

```typescript
export interface SharedDataHandle<T extends ISharedDataBase<string | number>> {
  items: Signal<T[]>;
  get(key: T["__valueKey"] | undefined): T | undefined;
}
```

내부적으로 `computed(() => items().toMap(i => i.__valueKey))`로 Map을 캐싱하고, `get(key)`는 이 Map에서 조회한다. get()은 computed signal read이므로 reactive context에서 자동 추적된다.

#### SdSharedDataChangeEvent

```typescript
export const SdSharedDataChangeEvent = defineEvent<
  { name: string; filter: unknown },
  (string | number)[] | undefined
>("SdSharedDataChange");
```

v12 `SdServiceEventListenerBase` 클래스 → v14 `defineEvent()` 함수형 정의 (D4).

v12 대비 변경:
- `$signal` → `signal()`, `$computed` → `computed()`
- `client.emitAsync(EventClass, selector, data)` → `client.emitEvent(SdSharedDataChangeEvent, selector, data)`
- `client.addEventListenerAsync(EventClass, info, cb)` → `client.addListener(SdSharedDataChangeEvent, info, cb)`
- `ObjectUtils.equal()` → `obj.equal()`
- `Wait.until()` → `wait.until()`
- `loadingCount++/--` → `loadingCount.update(v => v + 1/- 1)`

### 대안 검토

| 접근 | 선택 | 이유 |
|------|------|------|
| Angular resource() for data loading | 미채택 | 부분 업데이트(changeKeys) 미지원, 이벤트 기반 동기화와 비호환 |
| effect() cleanup for destroy | 미채택 | sync만 지원, client.close()는 async (D2) |
| SharedDataHandle에 WritableSignal 노출 | 미채택 | 외부 직접 수정 방지, 읽기 전용 Signal 노출 |
