## 참조 자료

### 설계 결정

| # | 결정사항 | 선택 | 근거 |
|---|---------|------|------|
| D1 | Lint과 Build 실행 순서 | 병렬 (Clean → Lint+Build 동시) | v13/v14 모두 동일 구현, 빌드 시간 단축이 목적 |

```gherkin
Feature: 1.7 프로덕션 빌드 오케스트레이션

  Background:
    Given monorepo 루트에 sd.config.ts가 존재한다
    And sd.config.ts에 패키지별 target 설정이 정의되어 있다

  Rule: 패키지를 target별로 분류한다

    Scenario: node/browser/neutral target 패키지를 buildPackages로 분류
      Given sd.config.ts에 target이 "node"인 패키지 "core-common"이 있다
      When 패키지를 분류한다
      Then "core-common"은 buildPackages에 포함된다
      And buildPackages는 JS빌드와 DTS생성을 모두 수행한다

    Scenario: server target 패키지를 serverPackages로 분류
      Given sd.config.ts에 target이 "server"인 패키지 "demo-server"가 있다
      When 패키지를 분류한다
      Then "demo-server"는 serverPackages에 포함된다
      And serverPackages는 JS빌드만 수행한다 (DTS 제외)

    Scenario: client target 패키지를 빌드에서 제외
      Given sd.config.ts에 target이 "client"인 패키지 "demo-client"가 있다
      When 패키지를 분류한다
      Then "demo-client"는 buildPackages에도 serverPackages에도 포함되지 않는다

    Scenario: scripts target 패키지를 빌드에서 제외
      Given sd.config.ts에 target이 "scripts"인 패키지 "sd-claude"가 있다
      When 패키지를 분류한다
      Then "sd-claude"는 buildPackages에도 serverPackages에도 포함되지 않는다

    Scenario: targets 인자로 특정 패키지만 필터링
      Given sd.config.ts에 "core-common"과 "core-node" 패키지가 있다
      When targets에 ["core-common"]을 지정하여 패키지를 분류한다
      Then "core-common"만 빌드 대상에 포함된다
      And "core-node"는 제외된다

    Scenario: targets 인자가 빈 배열이면 모든 패키지 포함
      Given sd.config.ts에 여러 패키지가 있다
      When targets에 빈 배열을 지정하여 패키지를 분류한다
      Then client/scripts를 제외한 모든 패키지가 빌드 대상에 포함된다

    Scenario: 빌드 대상 패키지가 없는 경우
      Given sd.config.ts에 client과 scripts target 패키지만 있다
      When 패키지를 분류한다
      Then 빌드 대상이 0개로 판정된다
      And "No packages to build" 메시지를 출력한다

  Rule: 빌드 순서를 보장한다 (Clean → Lint+Build 병렬)

    Scenario: Clean 단계가 Build보다 먼저 완료
      Given 빌드 대상 패키지 "core-common"의 dist 폴더에 이전 빌드 산출물이 있다
      When 프로덕션 빌드를 실행한다
      Then dist 폴더가 먼저 삭제된다
      And 삭제 완료 후 빌드가 시작된다

    Scenario: Lint와 Build가 병렬로 실행
      Given 빌드 대상에 여러 패키지가 있다
      When 프로덕션 빌드를 실행한다
      Then Lint 태스크와 Build 태스크가 동시에 실행된다
      And 모든 태스크가 완료될 때까지 대기한다

  Rule: buildPackage는 JS빌드와 DTS생성을 병렬 실행한다

    Scenario: Library 패키지 빌드 성공
      Given target이 "browser"인 패키지 "core-common"이 빌드 대상이다
      When 해당 패키지를 빌드한다
      Then libraryWorker로 JS빌드와 dtsWorker로 DTS생성이 병렬 실행된다
      And 두 작업 모두 성공하면 빌드 결과에 성공으로 기록된다

    Scenario: Library 패키지의 copySrc 처리
      Given target이 "node"인 패키지에 copySrc 설정이 있다
      When 해당 패키지 빌드가 완료된다
      Then copySrc에 지정된 파일이 dist로 복사된다

    Scenario: copySrc 미설정 시 복사 생략
      Given 패키지에 copySrc 설정이 없다
      When 해당 패키지 빌드가 완료된다
      Then 파일 복사 단계가 수행되지 않는다

  Rule: serverPackage는 JS빌드만 수행한다

    Scenario: Server 패키지 빌드 성공
      Given target이 "server"인 패키지 "demo-server"가 빌드 대상이다
      When 해당 패키지를 빌드한다
      Then serverWorker로 JS빌드만 실행된다
      And DTS 생성은 수행되지 않는다
      And 환경변수(VER, DEV)와 config.env가 병합되어 전달된다

    Scenario: Server 패키지에 pm2 설정이 있는 경우
      Given server 패키지에 pm2 설정이 있다
      When 해당 패키지를 빌드한다
      Then pm2 설정이 serverWorker에 전달된다

  Rule: Worker 스레드 생명주기를 관리한다

    Scenario: 빌드 성공 시 Worker 종료
      Given 패키지 빌드가 성공적으로 완료되었다
      When 빌드 결과가 수집된다
      Then 사용된 Worker가 terminate()로 종료된다

    Scenario: 빌드 실패 시에도 Worker 종료 보장
      Given 패키지 빌드 중 에러가 발생했다
      When 에러가 catch된다
      Then finally 블록에서 Worker가 terminate()로 종료된다

  Rule: 빌드 결과를 수집하고 보고한다

    Scenario: 에러 발생 시 패키지명과 target으로 출력
      Given 패키지 "core-common"의 JS빌드가 실패했다
      When 빌드 결과를 출력한다
      Then "core-common (browser)" 형태로 에러 메시지가 출력된다

    Scenario: 경고가 있는 빌드 결과 출력
      Given 패키지 빌드에 warnings가 포함되어 있다
      When 빌드 결과를 출력한다
      Then 경고 메시지가 패키지명과 함께 출력된다

    Scenario: DTS diagnostics 중복 제거
      Given 여러 패키지의 DTS 빌드에서 동일한 diagnostic이 발생했다
      When 빌드 결과를 출력한다
      Then sortAndDeduplicateDiagnostics로 중복이 제거된다
      And 색상과 컨텍스트가 포함된 형식으로 출력된다

    Scenario: 빌드 실패 시 프로세스 종료 코드 설정
      Given 하나 이상의 빌드 태스크가 실패했다
      When 빌드가 완료된다
      Then process.exitCode가 1로 설정된다

    Scenario: 모든 빌드 성공 시 완료 메시지
      Given 모든 빌드 태스크가 성공했다
      When 빌드가 완료된다
      Then "Build completed" 메시지가 출력된다
      And process.exitCode는 설정되지 않는다

  Rule: 초기화 시 설정을 로드하고 환경을 준비한다

    Scenario: sd.config.ts 로드 성공
      Given 프로젝트 루트에 유효한 sd.config.ts가 있다
      When BuildOrchestrator를 초기화한다
      Then sd.config.ts가 dev=false로 로드된다
      And 패키지 분류가 수행된다

    Scenario: sd.config.ts 로드 실패
      Given sd.config.ts에 문법 에러가 있다
      When BuildOrchestrator를 초기화한다
      Then 에러 메시지가 로깅된다
      And process.exitCode가 1로 설정된다
      And 예외가 throw된다

    Scenario: 버전 정보 준비
      Given 프로젝트 루트에 package.json이 있다
      When BuildOrchestrator를 초기화한다
      Then package.json에서 버전을 읽어 VER 환경변수를 준비한다
      And DEV 환경변수를 "false"로 설정한다

    Scenario: options 인자를 sd.config.ts에 전달
      Given build 명령어에 --opt "production" 인자가 지정되었다
      When BuildOrchestrator를 초기화한다
      Then sd.config.ts 로드 시 options에 ["production"]이 전달된다
```

## 구현계획

### 배경

BuildOrchestrator는 `build` 명령어의 프로덕션 빌드를 조율하는 오케스트레이터로, 이미 390줄로 구현 완료되어 있다. `classifyPackages` 함수의 단위 테스트 6개가 `tests/build-orchestrator.spec.ts`에 존재하지만, `BuildOrchestrator` 클래스(initialize, start, shutdown)에 대한 테스트는 없다.

### 목표

- BuildOrchestrator 클래스의 테스트 커버리지 확보
- initialize(), start() 메서드의 주요 경로 검증
- 기존 classifyPackages 테스트와 일관된 파일 구조 유지

### 비목표

- Worker 내부 빌드 로직 테스트 (library-worker.spec.ts, server-worker.spec.ts에서 커버)
- 실제 파일시스템/프로세스 통합 테스트
- copySrcFiles 내부 로직 테스트 (copy-src.spec.ts에서 커버)

### 설계

#### 테스트 파일 구조

기존 `tests/build-orchestrator.spec.ts`에 classifyPackages 테스트가 있으므로, BuildOrchestrator 클래스 테스트를 `tests/orchestrators/build-orchestrator.spec.ts`에 작성한다 (dev-orchestrator.spec.ts와 같은 위치).

#### 모킹 전략

dev-orchestrator.spec.ts의 패턴을 따른다:
- `consola`: withTag → 로거 메서드 모킹
- `@simplysm/core-node`: Worker.create → 프록시 객체 모킹
- `loadSdConfig`: 설정 반환값 모킹
- `getVersion`: 버전 문자열 모킹
- `fsx.rm`: dist 삭제 모킹
- `copySrcFiles`: 파일 복사 모킹

#### Worker 프록시 모킹

libraryWorker, dtsWorker, serverWorker, lintWorker를 모킹하여:
- `.build()` / `.lint()` 호출 인자 검증
- 반환값(성공/실패) 시뮬레이션
- `.terminate()` 호출 검증

### 대안 검토

| 접근 방식 | 선택 여부 | 이유 |
|-----------|-----------|------|
| 기존 build-orchestrator.spec.ts에 클래스 테스트 추가 | 미채택 | classifyPackages는 순수 함수이나 BuildOrchestrator는 모킹이 필요하여 파일 분리가 적절 |
| orchestrators/ 디렉토리에 별도 파일 | 채택 | dev-orchestrator.spec.ts, watch-orchestrator.spec.ts와 일관된 위치 |
