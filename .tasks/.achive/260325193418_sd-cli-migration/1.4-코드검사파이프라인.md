## 요구명세

```gherkin
Feature: 1.4 코드 검사 파이프라인

  Background:
    Given monorepo 프로젝트의 루트 디렉토리에 있다
    And sd.config.ts에 패키지별 target(node/browser/neutral/scripts)이 설정되어 있다

  Rule: lint 명령어는 ESLint로 코드 스타일을 검사한다

    Scenario: 전체 프로젝트 lint 실행
      Given eslint.config.ts 파일이 존재한다
      When sd-cli lint을 실행한다
      Then 프로젝트의 **/*.{ts,tsx,js,jsx} 파일을 ESLint로 검사한다
      And eslint.config.ts의 globalIgnores 패턴에 해당하는 파일은 제외한다
      And 검사 결과를 stylish 포맷으로 출력한다

    Scenario: targets 지정 lint
      When sd-cli lint packages/core-common을 실행한다
      Then packages/core-common 경로의 파일만 검사한다

    Scenario: lint 자동 수정
      When sd-cli lint --fix를 실행한다
      Then ESLint 자동 수정을 적용한다

    Scenario: lint 규칙별 시간 측정
      When sd-cli lint --timing을 실행한다
      Then TIMING 환경변수를 설정하여 규칙별 실행 시간을 출력한다

    Scenario: lint 캐시 활용
      Given 이전 lint 실행으로 .cache/eslint.cache가 존재한다
      When sd-cli lint을 실행한다
      Then 캐시를 활용하여 변경된 파일만 검사한다

    Scenario: lint 에러 발견
      Given ESLint 규칙 위반이 있는 파일이 존재한다
      When sd-cli lint을 실행한다
      Then 에러 수와 경고 수를 출력한다
      And process.exitCode를 1로 설정한다

  Rule: typecheck 명령어는 패키지별 TypeScript 타입 검사를 병렬 수행한다

    Scenario: node target 패키지 타입체크
      Given 패키지의 target이 "node"이다
      When sd-cli typecheck을 실행한다
      Then 해당 패키지를 node 환경으로 타입체크한다

    Scenario: browser target 패키지 타입체크
      Given 패키지의 target이 "browser"이다
      When sd-cli typecheck을 실행한다
      Then 해당 패키지를 browser 환경으로 타입체크한다

    Scenario: neutral target 패키지 타입체크
      Given 패키지의 target이 "neutral"이다
      When sd-cli typecheck을 실행한다
      Then 해당 패키지를 node 환경과 browser 환경으로 각각 타입체크한다

    Scenario: scripts target 패키지 제외
      Given 패키지의 target이 "scripts"이다
      When sd-cli typecheck을 실행한다
      Then 해당 패키지는 타입체크에서 제외된다

    Scenario: targets 지정 typecheck
      When sd-cli typecheck packages/core-common을 실행한다
      Then packages/core-common 패키지만 타입체크한다

    Scenario: typecheck 옵션 전달
      When sd-cli typecheck --opt key=value를 실행한다
      Then sd.config.ts에 key=value 옵션을 전달한다

    Scenario: typecheck Worker 병렬 처리
      Given 타입체크 대상 패키지가 N개이다
      When sd-cli typecheck을 실행한다
      Then Worker 스레드 풀(최대 CPU 코어의 7/8)로 병렬 실행한다

    Scenario: typecheck 증분 컴파일
      Given 이전 실행으로 .cache/typecheck-{env}.tsbuildinfo가 존재한다
      When sd-cli typecheck을 실행한다
      Then 캐시를 활용하여 변경된 파일만 검사한다

    Scenario: typecheck 에러 발견
      Given Worker에서 타입 에러가 발견된다
      When 타입체크가 완료된다
      Then 진단 정보를 직렬화하여 Main 스레드로 전달한다
      And 역직렬화 후 포매팅하여 출력한다
      And process.exitCode를 1로 설정한다

  Rule: test는 vitest subprocess로 실행한다

    Scenario: test 실행
      When sd-cli check --type test를 실행한다
      Then pnpm vitest --run을 subprocess로 실행한다

    Scenario: test targets 필터
      When sd-cli check --type test packages/core-common을 실행한다
      Then pnpm vitest packages/core-common --run을 실행한다

    Scenario: test는 독립 명령어가 아니다
      When sd-cli test를 실행한다
      Then 명령어가 존재하지 않아 에러가 발생한다

    Scenario: test 실패
      Given vitest 실행 결과에 실패한 테스트가 있다
      When 테스트가 완료된다
      Then stdout에서 실패 수를 파싱하여 보고한다

  Rule: check 명령어는 모든 검사를 병렬 통합 실행한다

    Scenario: 전체 check 실행
      When sd-cli check을 실행한다
      Then typecheck, lint, test를 Promise.allSettled로 동시 실행한다
      And 결과를 TYPECHECK → LINT → TEST → SUMMARY 순서로 출력한다

    Scenario: check 선택적 실행
      When sd-cli check --type lint,test를 실행한다
      Then lint과 test만 실행한다

    Scenario: check 모두 성공
      Given typecheck, lint, test 모두 성공한다
      When sd-cli check이 완료된다
      Then "ALL PASSED"를 출력한다

    Scenario: check 일부 실패
      Given typecheck은 실패하고 lint, test는 성공한다
      When sd-cli check이 완료된다
      Then "1/3 FAILED (typecheck)"를 출력한다
      And process.exitCode를 1로 설정한다

  Rule: 모든 검사 명령어는 공통으로 targets 필터링과 디버그 모드를 지원한다

    Scenario: targets 미지정
      When 검사 명령어를 targets 없이 실행한다
      Then 전체 프로젝트를 대상으로 검사한다

    Scenario: debug 모드
      When 검사 명령어에 --debug를 추가한다
      Then 디버그 로그를 출력한다
```

## 구현계획

### 배경

v14 sd-cli에 lint(`commands/lint.ts`), typecheck(`commands/typecheck.ts`), check(`commands/check.ts`) 명령어가 v13에서 복사되어 이미 동작 중이다. Worker(`workers/lint.worker.ts`, `workers/dts.worker.ts`)와 유틸리티(`utils/typecheck-serialization.ts`)도 구현 완료 상태이다. 기존 22개 테스트 파일 중 이 세 명령어에 대한 테스트는 없다.

### 목표

- CLI 설명과 JSDoc에서 Stylelint 문구 제거 (D1 반영)
- lint/typecheck/check 파이프라인의 핵심 동작을 테스트로 검증

### 비목표

- Stylelint 통합 (D1 결정)
- 기존 검사 로직 변경
- E2E 수준 통합 테스트 (실제 ESLint/TypeScript/vitest 프로세스 실행)

### 설계

#### 코드 수정

| 파일 | 위치 | 변경 내용 |
|------|------|----------|
| `src/sd-cli-entry.ts` | 86행 | `"Run ESLint + Stylelint"` → `"Run ESLint"` |
| `src/commands/lint.ts` | 112행 JSDoc | `"Run ESLint/Stylelint"` → `"Run ESLint"` |

#### 테스트 전략

- 기존 패턴 유지: vitest, `vi.mock` + dynamic import
- 순수 유틸리티 함수: 직접 단위 테스트
- 외부 의존성(ESLint, TypeScript, execa, Worker): `vi.mock`으로 모킹
- CLI 인자 파싱: `createCliParser` export 활용 (sd-cli-entry.spec.ts 패턴)

#### 테스트 파일 구조

| 테스트 파일 | 대상 모듈 | 주요 테스트 항목 |
|------------|----------|----------------|
| `tests/lint.spec.ts` | `commands/lint.ts` | loadIgnorePatterns, executeLint, runLint |
| `tests/typecheck.spec.ts` | `commands/typecheck.ts` | extractPackages, executeTypecheck, runTypecheck |
| `tests/check.spec.ts` | `commands/check.ts` | formatSection, spawnVitest, runCheck |

### 대안 검토

| 접근 방식 | 선택 | 이유 |
|-----------|------|------|
| Mock 기반 단위 테스트 | 채택 | 빠르고 안정적, 기존 프로젝트 테스트 패턴과 일치 |
| 실제 ESLint/TypeScript 실행 E2E 테스트 | 미채택 | 속도 느림, 환경 의존성 높음, 기존 패턴 불일치 |
