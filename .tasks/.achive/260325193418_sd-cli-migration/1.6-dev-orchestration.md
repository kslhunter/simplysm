## 요구명세

```gherkin
Feature: 1.6 Dev 오케스트레이션

  Background:
    Given sd.config.ts가 로드되어 있다
    And dev: true 옵션으로 초기화되었다

  Rule: Server 패키지를 dev 모드로 빌드한다

    Scenario: 여러 Server 패키지를 병렬 빌드
      Given sd.config.ts에 server 타겟 패키지가 2개 정의되어 있다
      When DevOrchestrator가 시작된다
      Then 각 패키지별로 독립적인 Server Build Worker가 생성된다
      And 각 Worker가 watch 모드로 초기 빌드를 시작한다

    Scenario: Server 패키지가 없으면 조기 종료
      Given sd.config.ts에 server 타겟 패키지가 없다
      When DevOrchestrator가 시작된다
      Then 경고 메시지를 출력한다
      And 프로세스가 종료된다

  Rule: 빌드 성공 시 Server Runtime을 시작한다

    Scenario: 초기 빌드 성공 후 Runtime 시작
      Given Server Build Worker가 초기 빌드를 완료했다
      And 빌드가 성공했다
      When build 이벤트가 발생한다
      Then 새 Server Runtime Worker가 생성된다
      And main.js를 import하여 server.listen()을 호출한다
      And 서버 URL을 출력한다

    Scenario: 빌드 실패 시 Runtime 시작하지 않음
      Given Server Build Worker가 빌드를 시도했다
      And 빌드가 실패했다
      When build 이벤트가 발생한다
      Then Server Runtime Worker를 시작하지 않는다
      And 에러 결과를 출력한다

    Scenario: 포트 충돌 시 자동 포트 할당
      Given 서버의 지정 포트가 이미 사용 중이다
      When Runtime Worker가 server.listen()을 시도한다
      Then 자동으로 다음 포트를 시도한다 (최대 20회)
      And 사용 가능한 포트로 서버를 시작한다

  Rule: 소스 변경 시 서버를 자동 재시작한다

    Scenario: 관련 파일 수정 시 rebuild 후 재시작
      Given 서버가 실행 중이다
      When src/ 내 metafile에 포함된 파일이 수정된다
      Then esbuild rebuild가 실행된다
      And 출력이 변경되면 기존 Runtime Worker를 종료한다
      And 새 Runtime Worker로 서버를 재시작한다

    Scenario: 무관한 파일 수정 시 rebuild 스킵
      Given 서버가 실행 중이다
      When src/ 내 metafile에 포함되지 않은 파일이 수정된다
      Then rebuild를 스킵한다

    Scenario: 출력 변경 없으면 재시작 스킵
      Given 서버가 실행 중이다
      When rebuild가 성공했지만 출력 파일에 변경이 없다
      Then 서버를 재시작하지 않는다

    Scenario: 파일 추가/삭제 시 context 재생성
      Given 서버가 실행 중이다
      When src/ 내 파일이 추가되거나 삭제된다
      Then esbuild context를 재생성한다
      And rebuild를 실행한다

    Scenario: workspace 의존 패키지 소스 변경 시 rebuild
      Given 서버가 실행 중이다
      And Server 패키지가 workspace 의존성을 가진다
      When 의존 패키지의 src/ 파일이 수정된다
      Then rebuild가 트리거된다

  Rule: Dev 환경을 구성한다

    Scenario: 환경변수 주입
      Given sd.config.ts에 server 패키지 env 설정이 있다
      When dev 모드로 빌드한다
      Then DEV="true", VER={version}과 패키지별 env가 병합되어 주입된다

    Scenario: public/public-dev 파일 복사 및 감시
      Given Server 패키지에 public/, public-dev/ 폴더가 있다
      When dev 모드로 빌드한다
      Then public/, public-dev/ 파일을 dist/로 복사한다
      And 파일 변경을 감시하여 자동 복사한다

    Scenario: 런타임 설정 파일 생성
      Given sd.config.ts에 server 패키지 configs 설정이 있다
      When dev 모드로 빌드한다
      Then dist/.config.json에 configs 내용을 기록한다

  Rule: 의존성 교체(replaceDeps) 변경을 감시한다

    Scenario: replaceDeps dist 변경 시 rebuild
      Given sd.config.ts에 replaceDeps 설정이 있다
      And 서버가 실행 중이다
      When replaceDeps 패키지의 node_modules/*/dist/*.js가 변경된다
      Then rebuild가 트리거된다

    Scenario: replaceDeps 미설정 시 감시 생략
      Given sd.config.ts에 replaceDeps 설정이 없다
      When DevOrchestrator가 시작된다
      Then replaceDeps 감시를 생략한다

  Rule: Graceful Shutdown을 지원한다

    Scenario: SIGINT로 종료
      Given 서버가 실행 중이다
      When SIGINT 신호를 수신한다
      Then 모든 Build Worker를 종료한다
      And 모든 Runtime Worker를 종료한다
      And 파일 감시자를 정리한다
      And 프로세스가 종료된다

  Rule: 빌드 에러를 복구한다

    Scenario: esbuild rebuild 연속 실패 시 폴백
      Given esbuild context.rebuild()가 3회 연속 실패했다
      When 다음 rebuild가 시도된다
      Then esbuild.build()로 폴백하여 context를 재생성한다

    Scenario: Runtime 예외 발생 시 watcher 유지
      Given 서버가 실행 중이다
      When Runtime Worker에서 uncaughtException이 발생한다
      Then 에러 이벤트를 발생시킨다
      And 파일 감시는 계속 동작한다
```

## 구현계획

### 배경

DevOrchestrator (453줄)는 `sd-cli dev` 명령어의 중앙 조율자로, Feature 1.3의 server.worker와 server-runtime.worker를 조율하여 Server 패키지 개발 모드를 제공한다. 코드는 이미 완전히 동작하며, 이 구현계획은 기존 동작의 테스트 검증을 위한 것이다.

### 목표

- DevOrchestrator의 오케스트레이션 로직을 테스트로 검증
- `tests/orchestrators/dev-orchestrator.spec.ts` 신규 작성

### 비목표

- DevOrchestrator 코드 변경 (기존 동작 공식화)
- Worker 내부 로직 테스트 (server-worker.spec.ts, server-runtime-worker.spec.ts에서 커버)
- Client dev 지원 (Epic 4)

### 설계

#### 테스트 계층 분리

| 계층 | 테스트 파일 | 커버 범위 |
|------|------------|----------|
| Orchestrator | dev-orchestrator.spec.ts (신규) | Worker 생성, 이벤트 응답, Runtime 교체, shutdown |
| Worker | server-worker.spec.ts (기존) | metafile 필터링, context 재생성, public 파일, esbuild 폴백 |
| Runtime | server-runtime-worker.spec.ts (기존) | 포트 할당, server.listen, 예외 처리 |

#### Gherkin Scenario → 테스트 계층 매핑

**DevOrchestrator 계층 (신규 테스트):**
- 여러 Server 패키지를 병렬 빌드
- Server 패키지가 없으면 조기 종료
- 초기 빌드 성공 후 Runtime 시작
- 빌드 실패 시 Runtime 시작하지 않음
- 관련 파일 수정 시 rebuild 후 재시작 (build 이벤트 → Runtime 교체)
- 환경변수 주입 (DEV, VER을 Worker에 전달)
- replaceDeps 미설정 시 감시 생략
- SIGINT로 종료
- Runtime 예외 발생 시 watcher 유지

**Worker 계층 (기존 테스트에서 커버):**
- 포트 충돌 시 자동 포트 할당 → server-runtime-worker.spec.ts
- 무관한 파일 수정 시 rebuild 스킵 → server-worker.spec.ts
- 출력 변경 없으면 재시작 스킵 → server-worker.spec.ts
- 파일 추가/삭제 시 context 재생성 → server-worker.spec.ts
- workspace 의존 패키지 소스 변경 시 rebuild → server-worker.spec.ts
- public/public-dev 파일 복사 및 감시 → server-worker.spec.ts
- 런타임 설정 파일 생성 → server-worker.spec.ts
- replaceDeps dist 변경 시 rebuild → server-worker.spec.ts
- esbuild rebuild 연속 실패 시 폴백 → server-worker.spec.ts

#### 테스트 패턴

watch-orchestrator.spec.ts와 동일한 패턴:
- vi.mock으로 모든 의존성 mock (consola, loadSdConfig, filterPackagesByTargets, watchReplaceDeps, getVersion, WorkerManager, SignalHandler, RebuildManager, printErrors)
- vi.mock 후 `await import()`로 동적 import
- Worker의 `on()` 핸들러를 캡처하여 이벤트 시뮬레이션
- helper 함수로 config 생성 및 기본 mock 설정

### 대안 검토

| 접근 방식 | 선택 여부 | 이유 |
|-----------|-----------|------|
| 단위 테스트 (mock Worker) | 채택 | 빠르고 안정적, 오케스트레이션 로직에 집중 |
| 통합 테스트 (실제 Worker) | 미채택 | Worker 테스트는 Feature 1.3에서 완료, 느리고 불안정 |
| E2E 테스트 (실제 프로젝트) | 미채택 | 환경 의존성 높음, CI 불안정 |
