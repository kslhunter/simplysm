  Background:
    Given sd-cli v14 프로젝트가 설정되어 있다

  # --- Worker 스레드 관리 인프라 ---

  Rule: Worker 스레드를 중앙에서 관리한다 (WorkerManager)

    Scenario: Worker 생성 및 ID 추적
      When WorkerManager.create("core:build", workerPath)를 호출한다
      Then "core:build" ID로 WorkerProxy가 생성된다
      And WorkerManager.size가 1이다
      And WorkerManager.ids에 "core:build"가 포함된다

    Scenario: Worker 조회
      Given "core:build" Worker가 생성되어 있다
      When WorkerManager.get("core:build")를 호출한다
      Then 해당 WorkerProxy를 반환한다

    Scenario: 존재하지 않는 Worker 조회
      When WorkerManager.get("nonexistent")를 호출한다
      Then undefined를 반환한다

    Scenario: 단일 Worker 종료
      Given "core:build" Worker가 생성되어 있다
      When WorkerManager.terminate("core:build")를 호출한다
      Then Worker가 종료된다
      And WorkerManager.size가 0이다

    Scenario: 전체 Worker 일괄 종료
      Given "core:build"와 "core:dts" Worker가 생성되어 있다
      When WorkerManager.terminateAll()을 호출한다
      Then 모든 Worker가 종료된다
      And WorkerManager.size가 0이다

  Rule: Worker 이벤트를 표준화된 패턴으로 처리한다 (worker-events)

    Scenario: build 성공 이벤트 처리
      Given Worker 이벤트 핸들러가 등록되어 있다
      When Worker가 build 이벤트를 { success: true }로 발행한다
      Then ResultCollector에 status: "success"로 저장된다
      And buildResolver가 호출된다

    Scenario: build 에러 이벤트 처리
      Given Worker 이벤트 핸들러가 등록되어 있다
      When Worker가 build 이벤트를 { success: false, errors: ["msg"] }로 발행한다
      Then ResultCollector에 status: "error"와 message가 저장된다

    Scenario: error 이벤트 처리
      Given Worker 이벤트 핸들러가 등록되어 있다
      When Worker가 error 이벤트를 { message: "fatal" }로 발행한다
      Then ResultCollector에 status: "error"와 해당 message가 저장된다

  Rule: 빠른 연속 리빌드를 배치로 묶어 처리한다 (RebuildManager)

    Scenario: 동시 리빌드 배치 처리
      When registerBuild("a", "title")와 registerBuild("b", "title")를 연속 호출한다
      And 두 빌드의 resolver를 모두 호출한다
      Then "batchComplete" 이벤트가 1번 발행된다

    Scenario: 배치 처리 중 새 리빌드 등록
      Given 배치가 진행 중이다
      When 새 registerBuild("c", "title")를 호출한다
      Then 현재 배치 완료 후 새 배치가 자동 실행된다

  Rule: Worker 프로세스 유틸리티를 제공한다 (worker-utils)

    Scenario: SD_DEBUG 환경변수로 디버그 레벨 적용
      Given SD_DEBUG 환경변수가 "true"이다
      When applyDebugLevel()을 호출한다
      Then consola.level이 debug로 설정된다

    Scenario: 클린업 핸들러가 시그널 시 실행된다
      Given registerCleanupHandlers(cleanup, logger)가 호출되었다
      When SIGTERM 시그널이 수신된다
      Then cleanup 함수가 실행된다

    Scenario: once guard가 중복 호출을 차단한다
      Given createOnceGuard("label")로 guard가 생성되었다
      When guard 함수를 두 번 호출한다
      Then 두 번째 호출에서 에러가 발생한다

  # --- 빌드 결과 수집 및 보고 ---

  Rule: 빌드 결과를 중앙에서 집계한다 (ResultCollector)

    Scenario: 빌드 결과 추가 및 조회
      When ResultCollector.add({ name: "core", target: "node", type: "build", status: "success" })를 호출한다
      Then ResultCollector.get("core:build")로 해당 결과를 조회할 수 있다

    Scenario: 동일 키 결과 갱신
      Given "core:build" 결과가 status: "building"으로 등록되어 있다
      When status: "success"로 다시 add한다
      Then "core:build" 결과의 status가 "success"로 갱신된다

    Scenario: 전체 결과 맵 조회
      Given 여러 빌드 결과가 등록되어 있다
      When ResultCollector.toMap()을 호출한다
      Then 모든 결과가 포함된 Map을 반환한다

  Rule: 빌드 결과를 포맷팅하여 보고한다 (output-utils)

    Scenario: 에러와 경고 메시지 포맷팅
      When formatBuildMessages(errors, warnings)를 호출한다
      Then 색상이 적용된 포맷팅 결과를 반환한다

    Scenario: 서버 URL과 포트 출력
      Given 서버 결과에 port: 3000이 포함되어 있다
      When printServers(results)를 호출한다
      Then 서버 URL이 포트와 함께 출력된다

  Rule: 빌드 환경 정보를 제공한다 (build-env)

    Scenario: cwd의 package.json 버전 반환
      Given cwd에 version: "14.0.0"인 package.json이 있다
      When getVersion(cwd)를 호출한다
      Then "14.0.0"을 반환한다

    Scenario: version 필드 없는 package.json
      Given cwd에 version 필드 없는 package.json이 있다
      When getVersion(cwd)를 호출한다
      Then "0.0.0"을 반환한다

  # --- 프로세스 시그널 처리 ---

  Rule: SIGINT/SIGTERM에 graceful shutdown한다 (SignalHandler)

    Scenario: 프로그래밍 방식 종료 요청
      Given SignalHandler가 생성되어 있다
      When requestTermination()을 호출한다
      Then waitForTermination() Promise가 해소된다
      And isTerminated()가 true를 반환한다

    Scenario: 종료 전 상태 확인
      Given SignalHandler가 생성되어 있다
      Then isTerminated()가 false를 반환한다

    Scenario: 시그널 핸들러가 중복 실행되지 않는다
      Given SignalHandler가 생성되어 있다
      When requestTermination()을 두 번 호출한다
      Then waitForTermination() Promise는 한 번만 해소된다

  # --- CLI 진입점 및 명령어 등록 ---

  Rule: CLI 진입점이 dev/production 모드를 구분하여 실행한다 (sd-cli)

    Scenario: .ts 파일 실행 시 직접 import
      Given sd-cli.ts가 .ts 확장자로 실행된다
      When CLI가 시작된다
      Then CPU 친화도를 적용한다
      And sd-cli-entry를 직접 import하여 실행한다

    Scenario: .js 파일 실행 시 2단계 실행
      Given sd-cli.js가 .js 확장자로 실행된다
      When CLI가 시작된다
      Then Phase 1에서 replaceDeps를 설정한다
      And Phase 2에서 새 Node 프로세스를 --max-old-space-size=8192로 spawn한다

    Scenario: CPU 친화도 설정
      Given CPU가 8코어이다
      When CPU 친화도를 적용한다
      Then ceil(8/4)=2개 코어를 제외하고 나머지 코어를 사용한다

  Rule: 명령어를 yargs로 등록한다 (sd-cli-entry)

    Scenario: 8개 명령어가 등록된다
      When CLI 파서가 초기화된다
      Then lint, typecheck, check, watch, dev, build, publish, replace-deps 명령어가 등록된다

    Scenario: --debug 전역 옵션
      When --debug 플래그로 명령어를 실행한다
      Then SD_DEBUG 환경변수가 "true"로 설정된다
      And consola.level이 debug로 설정된다

    Scenario: --help 통합 도움말
      When 명령어 없이 --help를 실행한다
      Then 모든 명령어의 도움말이 통합 표시된다

    Scenario: -o 옵션 전달
      When -o key=value 옵션으로 명령어를 실행한다
      Then options 배열이 sd.config.ts 함수에 전달된다

  # --- 설정 파일 로딩 및 검증 ---

  Rule: sd.config.ts를 동적 로딩하고 검증한다 (sd-config)

    Scenario: 정상 설정 파일 로딩

      When loadSdConfig({ cwd, dev: true, options: [] })를 호출한다

    Scenario: 설정 파일이 존재하지 않는다
      Given sd.config.ts가 존재하지 않는다
      When loadSdConfig를 호출한다
      Then 에러가 발생한다

    Scenario: default export가 함수가 아니다
      Given sd.config.ts의 default export가 객체이다
      When loadSdConfig를 호출한다
      Then 에러가 발생한다

    Scenario: packages 속성이 없다
      Given sd.config.ts 함수가 packages 없는 객체를 반환한다
      When loadSdConfig를 호출한다
      Then 에러가 발생한다

    Scenario: dev와 options 파라미터 전달
      Given sd.config.ts가 params를 사용하는 함수를 export한다
      When loadSdConfig({ cwd, dev: true, options: ["key=val"] })를 호출한다
      Then 설정 함수에 { cwd, dev: true, options: ["key=val"] }이 전달된다

  # --- 빌더 기본 생명주기 ---

  Rule: 빌더 기본 생명주기를 관리한다 (BaseBuilder)

    Scenario: 초기화 시 Worker 생성과 이벤트 핸들러 등록
      When Builder.initialize()를 호출한다
      Then createWorkers()가 실행된다
      And registerEventHandlers()가 실행된다
      And 각 패키지별 initialBuildPromise가 생성된다

    Scenario: build 모드 실행
      Given Builder가 초기화되어 있다
      When Builder.build()를 호출한다
      Then 각 패키지의 buildPackage()가 병렬 실행된다
      And 모든 initialBuildPromise가 해소될 때까지 대기한다

    Scenario: watch 모드 실행
      Given Builder가 초기화되어 있다
      When Builder.startWatch()를 호출한다
      Then 각 패키지의 startWatchPackage()가 실행된다
      And 모든 initialBuildPromise가 해소될 때까지 대기한다

    Scenario: shutdown 시 Worker 정리
      Given Builder가 초기화되어 있다
      When Builder.shutdown()을 호출한다
      Then WorkerManager.terminateAll()이 호출된다

  # --- 로컬 패키지 심링크 ---

  Rule: 로컬 패키지를 심링크로 교체한다 (replace-deps)

    Scenario: replaceDeps 설정으로 심링크 생성
      Given sd.config.ts에 replaceDeps: { "pkg-a": "/path/to/pkg-a" } 설정이 있다
      When setupReplaceDeps를 실행한다

    Scenario: 소스 패키지 변경 시 심링크 갱신
      Given replaceDeps 감시가 활성화되어 있다
      When 소스 패키지의 dist 파일이 변경된다
      Then 심링크 대상이 갱신된다

## 구현계획

### 배경

Feature 1.1의 인프라 모듈 11개가 이미 v14에 구현·동작 중이나 단위 테스트가 전무하다. 기존 테스트는 3개 파일(27 cases)이며, 인프라 모듈은 하나도 포함되지 않는다. Vitest v4.1.1(node 환경)에서 describe/it/expect/vi 패턴이 확립되어 있다.

### 목표

- 핵심 인프라 모듈 11개에 대한 단위 테스트를 작성하여 동작을 검증한다
- 대상: WorkerManager, ResultCollector, SignalHandler, worker-events, RebuildManager, worker-utils, BaseBuilder, sd-config, build-env, output-utils, replace-deps

### 비목표

- CLI 진입점(sd-cli.ts)의 프로세스 spawn/CPU 친화도 통합 테스트 — 프로세스 수준 동작은 단위 테스트로 검증 불가
- sd-cli-entry.ts 명령어 핸들러 테스트 — 기존 2개 테스트로 등록 확인 충분, 핸들러 구현은 각 Feature에서
- 구체 빌더(LibraryBuilder, DtsBuilder) 테스트 — Feature 1.2에서
- Worker 구현(library.worker, server.worker 등) 테스트 — 각 Feature에서

### 대안 검토

| 접근 방식 | 선택 여부 | 이유 |
|-----------|-----------|------|
| 모듈별 개별 spec 파일 | 채택 | 기존 패턴 준수, 독립적 실행 가능 |
| 단일 통합 spec 파일 | 미채택 | 파일이 너무 커짐, 격리 어려움 |
| Worker.create를 vi.mock으로 mock | 채택 | 실제 Worker 스레드 불필요, 단위 테스트에 적합 |
| 실제 Worker 스레드 사용 | 미채택 | 테스트 속도 저하, 비결정적 |
