## 구현계획

### 배경
`AngularCompiler` 클래스(623 LOC)가 순수 AOT 컴파일과 HMR 후보 수집을 모두 담당한다. 그러나 HMR 코드는 프로덕션에서 사용되지 않는 dead code이다. 클라이언트 dev 모드의 HMR은 `@angular/build/private`의 `createCompilerPlugin`이 자체 처리한다. [근거: DESIGN-004, 코드 분석]

### 목표
- `AngularCompiler`에서 HMR 관련 코드 제거하여 순수 AOT 컴파일만 담당하도록 함 [근거: Rule "AngularCompiler는 HMR 관련 코드를 포함하지 않아야 함"]
- 미사용 파일(`hmr-candidates.ts`) 및 관련 테스트 제거 [근거: Rule "미사용 파일은 제거되어야 함"]

### 비목표
- `AngularSourceFileCache` 클래스 수정 — `modifiedFiles`는 Angular resource dependency tracking(`getModifiedResourceFiles` 훅, line 231)에서도 사용하므로 유지 [근거: wbs 경계 "AngularSourceFileCache는 AOT 컴파일의 핵심 부분"]
- `hmr-service.ts`, `hmr-client-script.ts`, `esbuild-client-config.ts` 수정 — client.worker.ts 경로의 HMR 인프라이며 AngularCompiler와 무관 [근거: wbs 경계 "sdAngularPlugin의 외부 인터페이스는 변경하지 않음"]
- `client.worker.ts` 수정 — `createCompilerPlugin` 경로를 사용하므로 변경 불필요

### 대안 검토

**HMR 래퍼 클래스 분리 (선택하지 않음):**
WBS 원문은 "HMR 래퍼 또는 sdAngularPlugin 내부로 이동"을 제안했으나, HMR 코드가 프로덕션에서 미사용(dead code)임이 확인되어 사용처 없는 코드를 분리·유지하는 것은 불필요한 복잡도를 추가한다. [근거: D1]
