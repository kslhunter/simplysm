## 구현계획

### 배경

`BuildOrchestrator`의 `_addBuildPackageTasks`(L261-300), `_addServerPackageTasks`(L306-343), `_addClientPackageTasks`(L350-434) 3개 메서드가 거의 동일한 빌드 실행 패턴을 반복한다. 차이점은 `BuildOutput` 인자, env 병합 여부, 엔진 옵션(outDir/base), 후처리(copySrc/네이티브 빌드)뿐이다.

### 목표
- ~100 LOC의 중복 코드를 단일 private 메서드로 통합 [근거: DESIGN-003]
- 유형별 차이점(output, env, 후처리)은 호출측에서 명시적으로 전달 [근거: wbs 범위]

### 비목표
- BuildOrchestrator의 외부 인터페이스 변경 [근거: wbs 경계]
- 네이티브 빌드 로직의 구조 변경 [근거: wbs 경계]

### 설계

**`_runEngineTask` private 메서드 추가:**

```typescript
private async _runEngineTask(params: {
  name: string;
  target: string;
  config: SdBuildPackageConfig | SdServerPackageConfig | SdClientPackageConfig;
  output: BuildOutput;
  engineOptions?: { outDir?: string; base?: string };
  fileCache: Map<string, string>;
}): Promise<BuildStepResult>
```

내부 흐름:
1. `pkgDir` 계산: `pathx.posixResolve(this._cwd, "packages", params.name)`
2. `createBuildEngine({ name, dir: pkgDir, config }, { cwd: this._cwd, ...engineOptions })` 호출
3. `try/finally`에서 `engine.run(output)` 실행
4. `engineResult.build.diagnostics.map(d => deserializeDiagnostic(d, fileCache))` 역직렬화
5. `BuildStepResult` 생성 및 반환
6. `finally`에서 `engine.stop()` 호출

**각 메서드 리팩토링:**
- `_addBuildPackageTasks`: `_runEngineTask` 호출 (dts: true) + copySrc 후처리
- `_addServerPackageTasks`: `_runEngineTask` 호출 (env 병합, dts: false)
- `_addClientPackageTasks`: `_runEngineTask` 호출 (env 병합, outDir/base, dts: false) + 네이티브 빌드 후처리

### 대안 검토

| 대안 | 장점 | 단점 | 판정 |
|------|------|------|------|
| 3개 메서드를 하나로 통합 (switch문) | 코드 최소화 | 후처리 로직이 뒤섞여 가독성 저하, 단일 책임 위반 | 기각 |
| 클래스 외부 유틸 함수로 추출 | 재사용 가능 | 현재 내부에서만 사용, 인스턴스 상태 접근 필요 | 기각 |
| **private 메서드로 추출** | 인스턴스 상태 접근 자연스러움, 3개 메서드 구조 유지 | - | **채택** |
