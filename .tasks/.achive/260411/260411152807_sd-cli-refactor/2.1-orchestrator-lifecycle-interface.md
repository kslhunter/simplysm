## 구현계획

### 배경

sd-cli의 4개 Orchestrator(Build, Watch, Dev, Typecheck)는 동일한 `initialize() → start() → shutdown()` 생명주기를 따르지만, 이를 강제하는 인터페이스가 없다. 또한 TypecheckOrchestrator는 `loadSdConfig()`를 직접 호출하여 config 로드 경로가 분산되어 있다. [근거: DESIGN-001, ARCH-001]

기존 코드의 관련 구조:
- `engines/types.ts`에 `BuildEngine` 인터페이스가 정의되어 있음 — 동일 패턴으로 `orchestrators/types.ts`에 Orchestrator 인터페이스를 정의
- `BuildOrchestrator`는 이미 `loadAndValidateConfig()`를 사용 — TypecheckOrchestrator만 변경 필요
- `check.ts`에서 targets 검증이 완료된 후 TypecheckOrchestrator를 호출 — TypecheckOrchestrator 내부에서 중복 검증 불필요

### 목표

- `OrchestratorLifecycle<TStartResult>` 인터페이스를 정의하여 모든 Orchestrator가 동일한 생명주기 계약을 따르도록 한다 [근거: DESIGN-001]
- TypecheckOrchestrator의 config 로드를 `loadAndValidateConfig()`로 통일한다 [근거: ARCH-001 부분 해결]

### 비목표

- BaseOrchestrator의 config 로드 방식 변경 (`loadSdConfig()` 직접 호출 유지) [근거: WBS 제외사항 "ARCH-001 완전 통합은 현재 범위 초과"]
- Orchestrator 상속 구조 변경 (Build/Typecheck를 BaseOrchestrator 상속으로 전환하지 않음) [근거: WBS 경계]
- `awaitTermination()`을 인터페이스에 포함하지 않음 [근거: 일회성 Orchestrator에 불필요]

### 설계

**1. 인터페이스 정의** — `src/orchestrators/types.ts` 신규 생성 [근거: engines/types.ts 패턴]

```typescript
export interface OrchestratorLifecycle<TStartResult = void> {
  initialize(): Promise<void>;
  start(): Promise<TStartResult>;
  shutdown(): Promise<void>;
}
```

**2. 인터페이스 적용** [근거: Rule "모든 Orchestrator가 인터페이스를 구현"]

| 클래스 | 변경 | TStartResult |
|--------|------|-------------|
| BaseOrchestrator | `implements` 미적용 (D3: `initialize(params)` 시그니처 비호환) | — |
| WatchOrchestrator | `implements OrchestratorLifecycle` 추가 | `void` (default) |
| DevOrchestrator | `implements OrchestratorLifecycle` 추가 | `void` (default) |
| BuildOrchestrator | `implements OrchestratorLifecycle<boolean>` 추가 | `boolean` |
| TypecheckOrchestrator | `implements OrchestratorLifecycle<TypecheckResult>` 추가 | `TypecheckResult` |

**3. TypecheckOrchestrator config 로드 변경** [근거: ARCH-001 부분 해결]

변경 전 (`TypecheckOrchestrator.ts:108`):
```typescript
const sdConfig = await loadSdConfig({ cwd: this._cwd, dev: false, opt: this._options.options });
```

변경 후:
```typescript
const sdConfig = await loadAndValidateConfig({
  cwd: this._cwd, dev: false, options: this._options.options, targets: [],
});
```

- `targets: []` — check.ts에서 이미 검증 완료 [근거: D2]
- 이후 흐름 (discoverWorkspacePackages, mergeTestsPackagesIntoConfig, extractTargetPackageNames)은 변경 없음

**4. 테스트 변경** — `tests/orchestrators/typecheck-orchestrator.spec.ts`

변경 전:
```typescript
vi.mock("../../src/utils/sd-config", () => ({
  loadSdConfig: mocks.loadSdConfig,
}));
```

변경 후:
```typescript
vi.mock("../../src/utils/orchestrator-utils", () => ({
  loadAndValidateConfig: mocks.loadAndValidateConfig,
}));
```

- mock 함수명 변경: `loadSdConfig` → `loadAndValidateConfig`
- mock 반환값은 동일 (SdConfig 객체)
- `loadAndValidateConfig`는 내부에서 `loadSdConfig` + `validateTargets`를 호출하는 래퍼이므로, mock 반환 구조가 동일

### 대안 검토

**대안 A: BaseOrchestrator에도 loadAndValidateConfig 적용**
BaseOrchestrator도 loadSdConfig() + validateTargets()를 별도 호출하므로 loadAndValidateConfig()로 통일할 수 있다. 그러나 WBS 제외사항에서 "ARCH-001 완전 통합은 현재 범위 초과"로 명시되어 있고, BaseOrchestrator 변경 시 Watch/Dev 테스트까지 영향받으므로 현재 범위에서 제외했다.

**대안 B: 인터페이스를 BaseOrchestrator.ts에 인라인 정의**
별도 파일 없이 BaseOrchestrator.ts에 인터페이스를 정의할 수 있다. 그러나 BuildOrchestrator와 TypecheckOrchestrator가 BaseOrchestrator를 import하지 않는 독립 클래스이므로, 인터페이스만을 위한 import가 순환 의존을 유발할 가능성이 있다. engines/types.ts 패턴처럼 별도 파일이 적절하다.
