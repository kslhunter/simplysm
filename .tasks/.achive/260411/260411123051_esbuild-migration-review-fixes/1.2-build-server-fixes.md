## 구현계획

### 배경

esbuild 기반 클라이언트 빌드 시스템은 `EsbuildClientEngine` → `client.worker.ts` → `esbuild-client-config.ts` 구조로 동작한다. Worker Thread가 esbuild context를 관리하며, dev 모드에서는 HTTP 서버와 HMR 서비스도 함께 운영한다.

현재 코드에 리뷰에서 발견된 4건의 이슈(DESIGN-001, DESIGN-002, LOGIC-002, DESIGN-004)가 있으며, 이를 수정하여 빌드 안정성과 개발 편의성을 개선한다.

### 목표

- onEnd 콜백이 esbuild watch 주기와 동기화되어 동시 쓰기/순서 역전 방지 [근거: Rule "onEnd 콜백은 esbuild watch 주기와 동기화되어야 한다"]
- dev 서버 응답에 캐시 방지 헤더를 추가하여 stale 파일 서빙 방지 [근거: Rule "dev 서버 정적 파일 응답에는 캐시 방지 헤더가 필요하다"]
- 빌드 실패 시 상세 에러 정보를 전파하여 디버깅 편의성 확보 [근거: Rule "프로덕션 빌드 실패 시 esbuild의 상세 에러 정보를 전파한다"]
- Worker에서 sd.config.ts 이중 로딩을 제거하여 불필요한 jiti 로드 제거 [근거: Rule "Worker는 메인 프로세스에서 이미 로드한 설정을 재로드하지 않는다"]

### 비목표

- HMR 관련 수정 (Feature 1.1 범위) [근거: wbs 경계 "HMR 관련 수정은 Feature 1.1에서 처리"]
- dev 서버의 동기 파일 I/O → 비동기 전환 [근거: wbs 제외 사항 "단일 사용자 대상, 현재 성능 충분"]

### 대안 검토

**DESIGN-001 대안: onEnd 내부에서 Promise.resolve() 래핑**
esbuild 플러그인의 onEnd가 항상 Promise를 반환하도록 `Promise.resolve(options.onEnd!(result))`로 래핑하는 방법. 불필요한 Promise 래핑이 추가되므로, 타입을 `void | Promise<void>`로 변경하고 반환값을 그대로 전달하는 것이 더 명확하다.

**DESIGN-004 대안: info.name으로 pkgName 대체**
`info.name`(sd.config.ts 키)이 scope-stripped pkgName과 동일하므로 package.json 읽기도 제거 가능. 그러나 두 값의 동일성이 보장되는 계약이 명시적이지 않고, readFileSync 비용은 무시 가능하므로 package.json 읽기를 유지한다.
