## 구현계획

### 배경
`dev-http-server.ts`의 HTTP 핸들러가 `existsSync`/`statSync`/`readFileSync`를 사용하여 이벤트 루프를 블로킹하고 TOCTOU race condition이 존재한다.

### 목표
- 동기 파일 I/O를 비동기로 전환 [근거: 이벤트 루프 블로킹 제거]
- TOCTOU 제거: `stat` 시도 → ENOENT catch 패턴 [근거: existsSync/readFileSync 간 race condition]
- 스트리밍 응답: `createReadStream` + `pipeline` [근거: D1]
- I/O 에러 핸들링: 500 응답 [근거: 프로세스 크래시 방지]

### 비목표
- 인터페이스 변경 [근거: wbs 경계]
- HTTP/2, gzip, ETag [근거: wbs 제외 사항]

### 설계

1. **HTTP 핸들러 async 분리** [근거: http.createServer 콜백에서 async 분리]
   - `http.createServer` 콜백에서 `onRequest` 훅 처리 후, async `serveStatic()` 호출
   - `void serveStatic(req, res)` 패턴 (fire-and-forget, 에러는 내부 catch)

2. **`serveFile` 헬퍼** [근거: D2, 정적 파일과 SPA fallback에서 동일 로직]
   ```
   serveFile(filePath, res): Promise<boolean>
     stat(filePath) → 디렉토리면 false
     writeHead(200, Content-Type, Cache-Control)
     pipeline(createReadStream, res)
     return true
     catch: headersSent면 res.end() + true, 아니면 false
   ```

3. **serveStatic 흐름** [근거: TOCTOU 제거]
   ```
   serveStatic(req, res):
     basePath 확인 → 404
     serveFile(filePath) → true면 return
     serveFile(indexPath) → true면 return (SPA fallback)
     404
   ```

4. **에러 분류** [근거: ENOENT vs 기타 에러 구분]
   - ENOENT: SPA fallback으로 진행 (serveFile이 false 반환)
   - 기타 에러 (EACCES 등): 500 응답

### 대안 검토
- `fs.promises.readFile` (비동기 버퍼링): 더 단순하지만 스트리밍 이점 없음. D1에 의해 createReadStream 선택
