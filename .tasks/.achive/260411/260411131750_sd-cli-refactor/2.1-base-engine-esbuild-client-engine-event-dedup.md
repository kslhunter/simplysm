## 구현계획

### 배경

`BaseEngine.startWatch()`(130~210행)과 `EsbuildClientEngine.startWatch()`(91~162행)에서 buildStart/build/error 이벤트 처리 패턴이 ~25줄 중복된다. 이 중복으로 한쪽만 수정하면 다른 쪽에 반영되지 않는 유지보수 위험이 있다.

두 엔진의 이벤트 데이터 형태가 다르다:
- `CommonBuildWorkerEvents["build"]`: `{ build: { success, errors?, warnings? }, lint? }` (중첩)
- `ClientWorkerEvents["build"]`: `{ success, errors?, warnings? }` (평탄)

### 목표

- buildStart/build/error 이벤트의 공통 처리 로직을 `setupWatchEvents()` 헬퍼로 추출한다 [근거: Rule "헬퍼가 buildStart/build/error 공통 로직을 캡슐화"]
- 이벤트 데이터 정규화를 `normalizeBuild` 콜백으로 처리한다 [근거: D1 "헬퍼가 worker.on() 직접 호출 + normalizeBuild 콜백"]
- 초기 빌드 완료 감지를 `waitForInitialBuild()`로 제공한다 [근거: Rule "초기 빌드 완료 감지를 헬퍼가 제공"]

### 비목표

- BaseEngine의 템플릿 메서드 패턴 변경 [근거: wbs 경계]
- EsbuildClientEngine을 BaseEngine 상속으로 전환 [근거: wbs 경계]
- lint 결과 보고를 헬퍼에 포함 (BaseEngine 내부에서 별도 처리 유지)

#### BaseEngine.startWatch() 변경

```typescript
// Before: 80줄의 이벤트 처리 코드
// After: setupWatchEvents() 호출 + lint/warnings 별도 처리

async startWatch(output: BuildOutput): Promise<void> {
  this._isWatchMode = true;
  this._createWorker();

  const { waitForInitialBuild } = setupWatchEvents(this._worker!, {
    name: this._pkg.name,
    target: this._getTarget(),
    resultCollector: this._resultCollector,
    rebuildManager: this._rebuildManager,
    normalizeBuild: (data) => (data as CommonBuildWorkerEvents["build"]).build,
  });

  // lint 결과 + 경고 로깅 (BaseEngine 전용)
  this._worker!.on("build", (data) => {
    const event = data;
    if (event.build.warnings?.length) {
      logger.warn(`${this._pkg.name}: ${event.build.warnings.join(", ")}`);
    }
    if (event.lint != null) {
      const lintResult: BuildResult = { /* ... */ };
      this._resultCollector?.add(lintResult);
    }
  });

  this._callStartWatch(output).catch(() => { /* isInitialBuild는 헬퍼가 관리 */ });
  await waitForInitialBuild();
}
```

#### EsbuildClientEngine.startWatch() 변경

```typescript
// Before: 70줄의 이벤트 처리 코드
// After: setupWatchEvents() 호출 + serverReady 별도 처리

async startWatch(_output: BuildOutput): Promise<void> {
  this._isWatchMode = true;
  this._createWorker();

  // serverReady (EsbuildClientEngine 전용)
  this._worker!.on("serverReady", (data) => {
    this.port = (data as { port: number }).port;
  });

  setupWatchEvents(this._worker!, {
    name: this._pkg.name,
    target: "client",
    resultCollector: this._resultCollector,
    rebuildManager: this._rebuildManager,
    normalizeBuild: (data) => data as NormalizedBuildInfo,
  });
  // waitForInitialBuild 미사용 — worker.startWatch() await 유지

  const port = typeof this._pkg.config.server === "number"
    ? this._pkg.config.server : undefined;
  await this._worker!.startWatch({ ... });
}
```

### 대안 검토

**호출측이 핸들러 메서드 호출 (선택하지 않음)**: 타입 안전성이 높지만 호출측 코드량이 증가하여 중복 제거 효과가 감소. 각 엔진에 ~6줄의 이벤트 구독 보일러플레이트가 남음.

**EsbuildClientEngine을 BaseEngine 상속으로 전환 (wbs 경계에 의해 제외)**: 가장 강한 중복 제거이나 serverReady/port 관리 등 생명주기 차이가 상속 복잡도를 증가시킴.
