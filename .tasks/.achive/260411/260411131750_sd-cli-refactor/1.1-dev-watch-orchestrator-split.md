## 구현계획

### 배경

`DevWatchOrchestrator`(595줄)는 `mode` 필드로 watch/dev를 분기하는 단일 클래스이다. watch 전용 필드 7개(`_libraryEngines`, `_libraryPackages`, `_watchHookPackages`, `_copySrcWatchers`, `_distDeleteWatchers`, `_watchHookWatchers`, `_watchHookChildren`)와 dev 전용 필드 7개(`_serverEngines`, `_clientEngines`, `_serverPackages`, `_clientPackages`, `_serverClientsMap`, `_baseEnv`, `_serverRuntimeWorkers` + 타이머 2개)가 혼재한다. [근거: refactor.md DESIGN-001]

기존 커맨드(`commands/watch.ts`, `commands/dev.ts`)는 동일한 `DevWatchOrchestrator`에 `mode`를 주입하여 사용한다. [근거: 소스코드 직접 확인]

### 목표

- watch/dev 모드를 각각 독립 클래스로 분리하여 변경 파급 범위를 해당 모드 내로 제한 [근거: Rule "WatchOrchestrator는 watch 전용", "DevOrchestrator는 dev 전용"]
- 서버 런타임 관리를 별도 클래스로 추출하여 단일 책임 원칙 적용 [근거: Rule "ServerRuntimeManager는 서버 런타임 워커의 생명주기만 관리"]
- 공통 초기화를 BaseOrchestrator로 중복 제거 [근거: D1]

### 비목표

- Orchestrator start() 내부 분해 [근거: wbs 경계 "Feature 1.2에서 다룸"]
- 엔진 계층 변경 [근거: wbs 경계 "엔진 계층의 변경은 이 Feature에서 다루지 않음"]
- BuildOrchestrator의 BaseOrchestrator 상속 [근거: BuildOrchestrator는 SignalHandler/ResultCollector/RebuildManager를 사용하지 않아 공통 초기화 구조가 다름]

#### BaseOrchestrator (추상 기반 클래스)

```typescript
// src/orchestrators/BaseOrchestrator.ts

export interface BaseOrchestratorOptions {
  targets: string[];
  options: string[];
}

export abstract class BaseOrchestrator {
  protected readonly _cwd: string;
  protected readonly _logger: ConsolaInstance;

  // 인프라
  protected _resultCollector!: ResultCollector;
  protected _signalHandler!: SignalHandler;
  protected _rebuildManager!: RebuildManager;

  // 공통 상태
  protected _pathMap = new Map<string, string>();
  protected _replaceDeps?: Record<string, string>;
  protected _replaceDepWatcher?: WatchReplaceDepResult;
  protected _hasPackages = false;

  constructor(logTag: string) {
    this._cwd = process.cwd();
    this._logger = consola.withTag(logTag);
  }

  async initialize(params: {
    targets: string[];
    options: string[];
    dev: boolean;
  }): Promise<void> {
    // 1. sd.config.ts 로드
    const sdConfig = await loadSdConfig({ cwd: this._cwd, dev: params.dev, opt: params.options });
    // 2. pathMap 구축
    this._pathMap = buildPathMapFromConfig(sdConfig.packages);
    // 3. 대상 유효성 검사
    validateTargets(params.targets, sdConfig.packages);
    // 4. replaceDeps 저장 + watch 시작
    this._replaceDeps = sdConfig.replaceDeps;
    if (sdConfig.replaceDeps != null) {
      this._replaceDepWatcher = await watchReplaceDeps(this._cwd, sdConfig.replaceDeps);
    }
    // 5. 서브클래스 초기화 (패키지 분류, 엔진 생성 등)
    await this._initializeMode(sdConfig, params.targets, params.options);
    // 6. 패키지 유무 확인 후 인프라 초기화
    if (!this._hasPackages) return;
    this._signalHandler = new SignalHandler();
    this._resultCollector = new ResultCollector();
    this._rebuildManager = new RebuildManager(this._logger);
  }

  abstract start(): Promise<void>;

  async awaitTermination(): Promise<void> {
    if (!this._hasPackages) return;
    await this._signalHandler.waitForTermination();
  }

  async shutdown(): Promise<void> {
    this._replaceDepWatcher?.dispose();
    this._replaceDepWatcher = undefined;
    if (!this._hasPackages) return;
    process.stdout.write("⏳ 종료 중...\n");
    await this._shutdownMode();
    process.stdout.write("✔ 종료 완료\n");
  }

  protected abstract _initializeMode(
    config: SdConfig,
    targets: string[],
    options: string[],
  ): Promise<void>;
  protected abstract _shutdownMode(): Promise<void>;
}
```

**설계 포인트:**
- `_hasPackages` 플래그 설정은 `_initializeMode()` 내에서 서브클래스가 담당한다. 패키지 분류 후 총 패키지 수를 계산하여 설정. [근거: watch/dev가 다른 기준으로 패키지를 분류하므로]
- 인프라 객체(SignalHandler, ResultCollector, RebuildManager) 생성은 `_initializeMode()` 이후에 수행한다. `_hasPackages`가 false이면 생성을 건너뛴다. [근거: 현재 코드의 동작 유지 — `DevWatchOrchestrator.ts:153-158`]
- `_initializeMode()`에서 인프라가 필요한 경우(예: batchComplete 핸들러 등록, 엔진 생성), 인프라 생성 순서를 조정해야 할 수 있다. 해결: `_hasPackages` 설정만 `_initializeMode()`에서 하고, 인프라 생성과 엔진 생성을 `initialize()`에서 순차 처리. 또는 `_initializeMode()`를 두 단계로 분리: `_classifyPackages()`(분류만) + `_createEngines()`(엔진 생성). → **실제 구현 시 현재 코드의 실행 순서를 정확히 유지하는 방향으로 결정.**
