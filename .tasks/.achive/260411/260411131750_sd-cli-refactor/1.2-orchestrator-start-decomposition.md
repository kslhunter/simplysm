## 구현계획

### 배경

Feature 1.1에서 DevWatchOrchestrator가 WatchOrchestrator와 DevOrchestrator로 분리되었다. 이제 `BuildOrchestrator.start()` (244줄)과 `TypecheckOrchestrator.start()` (170줄)이 여러 단계의 로직을 한 메서드에 포함하고 있어, 특정 단계만 수정할 때 전체 메서드를 이해해야 하는 문제가 있다.

### 목표
- `BuildOrchestrator.start()`를 단계별 private 메서드로 분해하여 각 단계를 독립적으로 파악 가능하게 한다 [근거: Rule "BuildOrchestrator.start() 단계별 분해"]
- `TypecheckOrchestrator.start()`를 단계별 private 메서드로 분해하여 각 단계를 독립적으로 파악 가능하게 한다 [근거: Rule "TypecheckOrchestrator.start() 단계별 분해"]

### 비목표
- WatchOrchestrator/DevOrchestrator 변경 [근거: wbs 경계 + D1]
- 클래스 분리 [근거: wbs 경계 "BuildOrchestrator/TypecheckOrchestrator의 클래스 분리는 하지 않음"]
- 새 테스트 추가 [근거: wbs "기존 테스트 유지, 메서드 분해는 내부 변경이므로 public API 불변"]

### 설계

#### BuildOrchestrator.start() 분해

현재 `start()` (244줄)의 내부 구조:
- Phase 1: dist 클린 (lines 217-219, ~3줄)
- Phase 2: 빌드 태스크 생성 — buildPackages/serverPackages/clientPackages 각각에 대해 (lines 222-376, ~155줄)
- Phase 3: 태스크 실행 + rejected 핸들링 (lines 378-394, ~17줄)
- Phase 4: 결과 출력 (lines 396-436, ~40줄)

분해 후:

```typescript
async start(): Promise<boolean> {
  if (this._allPackageNames.length === 0) return false;

  await this._cleanDist();
  const { results, hasUntrackedError } = await this._buildAllPackages();
  return this._printBuildResults(results, hasUntrackedError);
}

// Phase 1: dist 폴더 정리
private async _cleanDist(): Promise<void>

// Phase 2+3: 빌드 태스크 생성 + 실행
// - 내부에서 패키지 유형별 헬퍼 호출
// - 동시성 제어 실행 (runWithConcurrency)
// - rejected 태스크 핸들링
private async _buildAllPackages(): Promise<{
  results: BuildStepResult[];
  hasUntrackedError: boolean;
}>

// 패키지 유형별 태스크 생성 헬퍼
private _addBuildPackageTasks(
  tasks: Array<() => Promise<void>>,
  results: BuildStepResult[],
  fileCache: Map<string, string>,
): void

private _addServerPackageTasks(
  tasks: Array<() => Promise<void>>,
  results: BuildStepResult[],
  fileCache: Map<string, string>,
): void

private _addClientPackageTasks(
  tasks: Array<() => Promise<void>>,
  results: BuildStepResult[],
  fileCache: Map<string, string>,
): void

// Phase 4: 결과 출력
private _printBuildResults(
  results: BuildStepResult[],
  hasUntrackedError: boolean,
): boolean
```

태스크 생성과 실행을 `_buildAllPackages()`로 묶는 이유: 태스크 closure가 `results` 배열과 `fileCache`를 캡처하므로, 이들의 생명주기를 하나의 메서드에서 관리하는 것이 자연스럽다.

#### TypecheckOrchestrator.start() 분해

현재 `start()` (170줄)의 내부 구조:
- Early return: 대상 없음 (lines 168-178, ~10줄)
- Phase 1: 패키지 타입체크 실행 (lines 180-275, ~95줄)
- Phase 2: 비패키지 타입체크 (lines 278-287, ~10줄)
- Phase 3: 결과 집계 + 포맷 (lines 289-331, ~42줄)

분해 후:

```typescript
async start(): Promise<TypecheckResult> {
  const phaseLabel = this._options.lint === true ? "타입체크/린트" : "타입체크";

  if (this._typecheckTasks.length === 0 && !this._includeNonPackage) {
    // early return (10줄, 인라인 유지)
  }

  const fileCache = new Map<string, string>();
  const packageResults = await this._executePackageTypechecks(fileCache);
  const nonPkgResults = this._executeNonPackageTypecheck(fileCache);
  return this._aggregateTypecheckResults(packageResults, nonPkgResults, phaseLabel);
}

// Phase 1: 패키지 타입체크 실행
private async _executePackageTypechecks(fileCache: Map<string, string>): Promise<{
  allDiagnostics: ts.Diagnostic[];
  totalErrorCount: number;
  totalWarningCount: number;
  lintErrorCount: number;
  lintWarningCount: number;
  lintSuccess: boolean;
  lintOutputs: string[];
}>

// Phase 2: 비패키지 타입체크
private _executeNonPackageTypecheck(fileCache: Map<string, string>): {
  diagnostics: ts.Diagnostic[];
  errorCount: number;
  warningCount: number;
}

// Phase 3: 결과 집계 및 포맷
private _aggregateTypecheckResults(
  packageResults: { allDiagnostics, totalErrorCount, totalWarningCount, lintErrorCount, lintWarningCount, lintSuccess, lintOutputs },
  nonPkgResults: { diagnostics, errorCount, warningCount },
  phaseLabel: string,
): TypecheckResult
```

### 대안 검토

**대안: 태스크 생성과 실행을 완전히 분리** (`_createBuildTasks()` + `_executeBuildTasks(tasks)`)
- 태스크 closure가 `results` 배열과 `fileCache`를 캡처하므로, 분리하면 이들을 인자로 전달하거나 필드로 승격해야 함
- 관련 없는 상태(fileCache 등)가 인스턴스에 남아 혼동 유발
- 선택하지 않은 이유: 생성과 실행의 결합도가 높아 분리의 실익보다 복잡성 증가가 큼
