# sd-prompt: Eval-Driven Prompt Development

프롬프트 파일이란 룰(.codex/rules/\*.md), 시스템 프롬프트, 커스텀 지시 등 모든 .md 프롬프트를 포함한다.

## 작업 추적

Step 1~5는 장기 프로세스이다. 스킬 시작 시점에 `update_plan`으로 각 Step을 등록한다. Step 진입 시 `in_progress`, 완료 시 `completed`로 갱신한다. 개선 루프(Step 4)·Regression Guard(Step 5)로 이전 Step에 재진입할 때도 해당 Step을 다시 `in_progress`로 되돌려 상태를 반영한다.

## 작업 범위

작업 전에 사용자 요청이 요구하는 Step 범위를 확정한다. 명시되지 않은 후속 Step을 추측으로 실행하지 않는다.

- "Eval 파일만 작성", "Eval 작성만", "실행하지 마"가 있으면 Step 1~2만 수행하고 기대 Eval 파일을 생성한다. Step 4 Eval 실행과 Step 5 리팩터링은 수행하지 않으며, 최종 응답에 실행하지 않았다고 보고한다.
- "Eval 실행", "Eval 수행", "스킬 테스트"가 있으면 Step 4까지 수행한다. Eval 파일이 없거나 오래된 경우 Step 1~2를 먼저 수행해 갱신한다.
- "개선", "수정", "프롬프트 개선"이 있으면 Step 1~4를 수행한다. 단, 사용자 요청이 "제안만", "분석만", "파일 수정하지 마"를 포함하면 파일을 수정하지 않고 필요한 결정사항과 수정안을 보고한다.
- "리팩터링", "refactor", "refact"가 있으면 Step 5까지 수행한다. Step 5는 전체 Eval PASS 이후에만 진입한다.

## 산출물 파일 구조

```
대상 파일 옆에 {확장자를 제거한 대상파일명}.eval.md 로 생성한다.

예시:
  .codex/rules/{name}.md             → .codex/rules/{name}.eval.md
  .codex/skills/{name}/SKILL.md      → .codex/skills/{name}/SKILL.eval.md
  {경로}/{name}.md                    → {경로}/{name}.eval.md
```

Eval 파일 작성 요청을 처리할 때는 작업 전에 대상 프롬프트 경로에서 기대 Eval 경로를 먼저 계산한다.
완료 전 기대 Eval 경로의 파일이 실제로 존재하는지 확인하고, 최종 응답에는 실제 생성한 Eval 파일 경로를 포함한다.
기대 Eval 경로와 실제 생성 경로가 다르면 완료하지 말고 기대 Eval 경로로 파일을 이동하거나 다시 작성한다.

## Step 1: 의도 정의 (Intent)

프롬프트 작성·개선 전에 다음 항목을 명확화 대상으로 정한다:

- **유형**: 스킬(특정 명령으로 트리거) vs 룰(항상/조건부 적용) vs 일반 프롬프트
- **트리거 조건**: 어떤 발화/상황에서 발동하는가 (스킬인 경우)
- **입력**: 무엇을 받는가
- **출력**: 무엇을 내놓는가

위 항목을 `$sd-inner-clarify` 스킬에 전달하여 명확화한다.
명확성 분류, 근거 탐색, 재분류, 사용자 질문 여부는 `$sd-inner-clarify`의 기준을 따른다.

## Step 2: Eval 시나리오 정의

### Eval 유형

| Eval 유형         | 설명                                                    | 판정 방식                 |
| ----------------- | ------------------------------------------------------- | ------------------------- |
| **행동 Eval**     | 특정 입력·환경에서 대상 프롬프트가 지켜야 하는 행동 계약 | Rubric 기반 LLM 판단      |
| **안티패턴 Eval** | 대상 프롬프트가 만들면 안 되는 실패 모드                 | 행동/결과 확인 + LLM 판단 |

### 체크리스트 작성 원칙

Judge의 정확도는 Eval이 대상 프롬프트의 실제 성공 조건을 얼마나 잘 모델링하는지에 달려있다. 다음 원칙을 따른다:

- **CRITICAL**: 체크리스트의 모든 항목은 사용자 요청, 사용자 답변, 대상 프롬프트, 적용 규칙·참조 문서에서 도출되어야 한다.
- 체크리스트는 파일·문자열 존재 여부보다 먼저 대상 프롬프트의 행동 계약을 평가한다.
- 객관적 기준과 Rubric을 함께 작성한다.
- 하나의 항목은 하나만 평가한다.
- Judge가 관찰 가능 소스에서 PASS/FAIL을 판정할 수 있는 내용만 작성한다.
- **조건부 행동을 체크리스트에 넣지 않는다** — 입력·상태에 따라 발생할 수도, 안 할 수도 있는 행동은 체크 항목으로 부적합하다. 해당 입력에서 **반드시 발생하는 행동**만 넣는다.
- 파일 존재, 섹션 존재, 특정 문자열 포함/미포함은 보조 assertion으로만 사용한다. 이것만으로 행동 Eval을 구성하지 않는다.
- `run-output.jsonl`을 체크리스트의 평가 대상명으로 직접 쓰지 않는다. `run-output.jsonl`은 Judge가 행동을 판정하기 위해 참고하는 실행 로그일 뿐이다.

#### Judge 관찰 가능 소스

Judge는 아래 **두 가지만** 볼 수 있다. 체크리스트의 모든 항목은 이 소스에서 PASS/FAIL을 판정할 수 있어야 하지만, 항목 문구는 사용자 관점의 행동·결과를 기준으로 작성한다.

| 소스               | 설명                                               | 판정 가능 예시                                          |
| ------------------ | -------------------------------------------------- | ------------------------------------------------------- |
| **workspace 파일** | 스킬 실행 후 workspace에 생성·수정된 파일          | 파일 존재 여부, 파일 내 특정 문자열·구조·섹션 포함 여부 |
| **실행 로그**      | `run-output.jsonl`에 기록된 `codex exec --json` 이벤트와 `run-error.log` | 사용자에게 제시한 질문·선택지·보고·최종 응답의 행동 흐름, 실행 오류 |

**Judge가 볼 수 없는 것:** 도구 호출 여부/순서, 내부 추론, 파일을 "읽었는지" 여부. 이런 것은 체크 항목으로 넣지 않는다.
**Judge가 봐야 하는 것:** 입력 대비 결과의 의미적 정확성, 금지된 행동의 부재, 필요한 질문/중단/수정/생성의 수행 여부, 산출물의 업무 규칙 준수 여부.

#### 자가검증

각 체크 항목을 작성한 후 아래 질문을 모두 통과해야 한다.

- 이 항목은 대상 프롬프트의 성공 행동이나 실패 모드를 평가하는가?
- Judge가 workspace 파일 또는 실행 로그를 근거로 PASS/FAIL을 판정할 수 있는가?
- 파일명, 섹션명, 문자열 검색 같은 표면 검사가 아니라 의미적 행동 계약을 평가하는가?
- 단순 표면 검사가 필요한 경우, 행동 계약을 보조하는 assertion으로만 쓰였는가?

"아니오"가 하나라도 있으면 재작성하거나 삭제한다.

### Eval 파일 형식

#### 입력 작성 원칙

- **스킬:** 반드시(MUST) 실제 호출 방식인 `$skill-name` 형식을 입력으로 사용한다. 예: `$sd-prompt .codex/skills/foo/SKILL.md`
- **프롬프트:** 프롬프트가 적용되어야 하는 상황의 자연어 발화를 입력으로 사용한다.

```markdown
# Eval: {skill-or-prompt-name}

## 행동 Eval

### 시나리오 1: {이름}

- 입력: "$sd-prompt .codex/skills/foo/SKILL.md 개선" (스킬)
- 성공 행동:
  - [ ] {대상 프롬프트가 이 입력에서 반드시 수행해야 하는 의미적 행동 1}
  - [ ] {대상 프롬프트가 이 입력에서 반드시 수행해야 하는 의미적 행동 2}
- 보조 assertion:
  - [ ] {성공 행동을 뒷받침하는 파일/구조/문자열 검증 1}
- Judge rubric:
  - PASS: {성공으로 볼 구체 조건}
  - FAIL: {실패로 볼 구체 조건}

### 시나리오 2: {이름}

- 입력: "{자연어 발화}" (프롬프트)
- 성공 행동:
  - [ ] {대상 프롬프트가 이 입력에서 반드시 수행해야 하는 의미적 행동 1}
  - [ ] {대상 프롬프트가 이 입력에서 반드시 수행해야 하는 의미적 행동 2}
- 보조 assertion:
  - [ ] {성공 행동을 뒷받침하는 파일/구조/문자열 검증 1}
- Judge rubric:
  - PASS: {성공으로 볼 구체 조건}
  - FAIL: {실패로 볼 구체 조건}

## 안티패턴 Eval

모든 시나리오에 공통으로 적용되는 금지 기준만 작성한다.
특정 시나리오에서만 금지되는 행동은 해당 시나리오의 체크리스트에 작성한다.

- [ ] {공통으로 하면 안 되는 실패 행동 1}
- [ ] {공통으로 하면 안 되는 실패 행동 2}
```

## Step 3: 프롬프트 작성·개선

### 스킬인 경우: SKILL.md 구조

`.codex/skills/sd-prompt/references/skill-guide.md`를 읽고 구조 가이드에 따라 작성한다.
기존 스킬을 개선하는 경우, 기존 프론트매터·트리거 표현·참조 파일 경로는 변경 필요성이 명확할 때만 수정한다.

### 프롬프트인 경우: .md 구조

일반 `.md` 프롬프트는 신규 작성 시 프론트매터를 추가하지 않는다.
기존 파일에 프론트매터가 있으면 의미를 확인한 뒤 유지하거나, 불필요한 경우 사용자 승인 후 제거한다.
본문 구조는 대상 프롬프트의 용도에 맞추되, 트리거 조건·입력·출력·금지/대안·검증 기준이 필요한 경우 명시 섹션으로 분리한다.

### 스킬 작성 규칙

스킬을 작성하거나 개선할 때는 간결성보다 정확성을 최우선 가치로 둔다.
부정확한 결과를 낼 가능성이 있다면, 과하더라도 질문, 근거 확인, 검증, 중단을 선택하도록 스킬을 작성한다.

### 품질 원칙

- **금지에는 대안을 함께 제시한다** — "`Buffer` 사용 금지"만으로는 불충분. "`Buffer` 금지 — `Uint8Array`를 사용한다"로 작성한다
- **강한 규칙에 키워드를 구분한다** — `반드시(MUST)`, `절대(NEVER)`, `항상(ALWAYS)`, `CRITICAL`, `IMPORTANT`. IMPORTANT/CRITICAL은 진짜 중요한 규칙에만 사용한다.
- **모호한 표현을 제거한다** — "적절하게", "필요시", "경우에 따라" 등은 LLM이 추측하게 만든다. 구체적인 조건과 행동으로 바꾸거나 사용자에게 직접 질문하고 응답을 기다린다.
- **정확성을 유지한 범위에서 간결하게 유지한다** — 핵심 규칙과 전체 Step 흐름은 SKILL.md에 남긴다. 상세 절차·템플릿·긴 예시는 명시적 참조 경로를 두고 "Progressive Disclosure" 원칙에 따라 분리한다.

## Step 4: Eval 실행 & 판정

### 실행 절차

`.codex/skills/sd-prompt/references/eval-runner.md`를 읽고 절차에 따라 Eval을 실행한다.

### 개선 루프

FAIL이 1개라도 있으면 다음 단계로 진행할 수 없다. 이유를 불문하고 수정 없이 다음 단계로 넘어가는 것은 금지한다.
Judge 보고서의 개선 제안에 대해:

1. `.codex/rules/sd-options.md` 형식으로 사용자에게 질문한다.
   - FAIL 판정이유, 해당 부분의 실제 출력, 제안별 영향 범위를 포함한다.
2. 승인된 제안에 따라 작성 원칙에 맞추어 수정한다.
3. 수정 범위에 따라 재실행한다.
   - 프롬프트 파일이 수정된 경우: 새 workspace를 생성하고 시나리오 실행부터 Judge 판정까지 다시 수행한다.
   - Eval 파일만 수정된 경우: 기존 시나리오 workspace와 `run-output.jsonl`, `run-error.log`, `run-exit-code.txt`를 유지하고, 수정된 Eval 파일 기준으로 Judge 판정만 다시 수행한다.

## Step 5: 프롬프트 리팩터링 (Refactor)

전체 Eval PASS 후, 개선 루프에서 누적된 패치를 정리하여 정돈된 프롬프트를 만든다.

### Prompt Smell 탐지

각 Smell은 아래 **탐지 규칙**에 해당할 때만 리포트한다. **예외 조건**에 해당하면 Smell로 치지 않는다. 리포트 시 **원문 라인 인용**(`파일경로:라인`)을 반드시 포함한다 — 근거를 댈 수 없으면 리포트 금지.

#### 중복 지시
- 탐지: 동일 지시(동사+목적어 수준)가 2곳 이상에 등장
- 예외: 양쪽 모두 `CRITICAL`/`MUST`/`절대`/`반드시` 등 강조 키워드가 붙어 있고, 서로 다른 Step·섹션 경계에서 **의도적 강조**로 읽히는 경우
- 연산: 통합

#### 잔재 지시
- 탐지: 현재 흐름에서 더 이상 참조·호출되지 않는 지시
- 예외: 후속 Step이나 다른 참조 문서에서 전제로 인용되는 지시
- 연산: 삭제

#### 장황한 표현
- 탐지: 의미 단위가 중복 수식·군더더기로 채워진 문장 (예: "처음부터 끝까지 빠짐없이 전부 다")
- 예외: 법·규칙 문언처럼 정확한 범위·경계를 명시해야 하는 지시
- 연산: 의미 유지하며 압축

#### 용어 불일치
- 탐지: 같은 개념이 2개 이상의 단어로 지칭됨
- 예외: 최초 정의에서 동의어를 명시 병기한 뒤 일관 사용하는 경우
- 연산: 통일 (주 용어 선정 후 전면 치환)

#### 상충 지시
- 탐지: 두 지시가 동일 조건에서 서로 다른 행동을 요구
- 예외: 상위·하위 관계나 우선순위가 명시되어 충돌이 해소된 경우
- 연산: 우선순위 결정 후 통합 또는 삭제

#### 구조 산만
- 탐지: 동일 주제의 지시가 3곳 이상에 흩어져 있음
- 예외: 각 Step·섹션에서 **국소적으로만** 필요한 지시여서 공통 추출이 오히려 독립성을 해치는 경우
- 연산: 재배치 (공통 섹션으로 추출하거나 한 Step 안으로 모음)

발견된 Prompt Smell은 Smell 유형, 원문 라인, 탐지 근거, 제안 연산, 영향 범위를 포함하여 `.codex/rules/sd-options.md` 형식으로 사용자에게 선택지를 제시한다.
사용자가 승인한 항목만 수정하고, 수정 완료 후 남은 Prompt Smell 검토를 계속한다.
Smell 여부나 수정 방법 자체가 불명확하면 `$sd-inner-clarify` 스킬을 호출하여 명확화한다.

### Regression Guard

리팩터링 후 수정 범위에 따라 Eval을 재실행한다.
FAIL 시 Step 4의 **개선 루프**로 돌아가 수정하고, Eval 전체가 PASS될 때까지 반복한다.
