# plan 단계

대상 spec.md 및 관련 자료를 읽고 → 현황 매핑 + 변경 계획 (R별 변경 위치/방식/테스트 + R 간 작업 순서).

## 산출물

```
.specs/{yyMMddHHmmss}/REQ-XXX-slug/
  spec.md         ← 입력 (이미 존재)
  plan.md         ← 본 단계 산출물
```

## 워크플로

1. 입력: 대상 REQ ID

2. 통독: 대상 spec.md / overview.md / raw input(있으면) / 관련 타 spec.md·plan.md / 매핑된 demo.md / 기존 코드베이스
   - DEMO 매핑 판단: overview.md `## DEMO 매핑` 줄에서 대상 REQ ID 포함 여부. 섹션·매핑 없으면 demo 없음.
   - 매핑된 demo.md/scaffold는 UI 정본 (plan UI R 설계의 wireframe·이벤트 흐름 중복 X).

3. 초안 plan.md 작성 (템플릿: [references/plan-md-template.md](references/plan-md-template.md))
   - **R별 현황 매핑** (4단계: 구현/부분/미구현/차이있음)
   - **R별 설계** (R 성격별 조건부 — "R 성격별 설계 정보" 참조)
   - **R별 변경 위치** (파일 경로 + 함수/컴포넌트 이름. 라인 번호 X)
   - **R별 변경 방식** (자연어. 복잡한 로직만 의사코드)
   - **R별 테스트** (TDD/사후/생략 + 케이스)
   - **작업 순서** (R 간 의존성, 권장 순서, 병렬 가능 여부)
   - **통합/E2E 테스트** (R 간 흐름)
   - **결과** 메타 (`proceed` | `skip-to-verify`)
   - 결정 근거 없으면 Q. 모든 결정은 근거 출처 명시.

4. Q 다이얼로그 (한 번에 하나씩) → 사용자 답변 → 즉시 plan.md 갱신
   - **spec 모순 발견 시**: Q로 알림 → 사용자 답변 받아 spec.md 수정 + spec.md 메타 `이력` 기록 → 변경된 R 부분만 재계획. plan 단계 종료 X.

5. Q 0개 도달 시 종료 절차:
   ```
   loop:
       plan.md 전체 재검토 (R별 현황/변경 위치/방식 정합성 / 누락 결정거리 / 작업 순서 / 테스트 모드 / 모호 표현 / 미해결 의존)
       if 신규 Q 등록됨:
           "Q 다이얼로그" 재진입 → Q 0 도달
           continue
       break

   loop:
       역방향 문서 검토 (overview, spec, demo)
       if 신규 모순/수정 등록됨:
           "Q 다이얼로그" 재진입 → Q 0 도달
           continue
       break

   산출물 소비자 친화적 보고
   상태 ← planned
   ```
   - 보고: 산출물 소비자 어휘 자연어. REQ 차원 변경 요약(R별 위치·방식 핵심) + 작업 순서 + 결과. 파일·함수명 외 기술 용어 최소화. 별도 승인 게이트 X.

## 현황 분류 (4단계)

| 분류 | 의미 |
|---|---|
| **구현** | spec R 의도가 코드에 이미 반영됨 |
| **부분** | R 일부만 구현됨 (예: UI는 있으나 로직 없음) |
| **미구현** | 관련 코드 없음 |
| **차이있음** | 구현되어 있으나 R 의도와 불일치 |

## 변경 계획 입도

- **변경 위치**: 파일 경로 + 함수/컴포넌트 이름 (라인 번호 X — 코드 변경에 취약)
- **변경 방식**: 자연어. 복잡한 로직(상태 머신, 알고리즘)만 의사코드. 완전한 코드 스니펫 X (implement 단계 의미 무력화)

## R 성격별 설계 정보

"변경 위치/방식"만으로 그림이 안 그려지는 R은 **설계** 서브섹션 추가. 단순 변경(색상/문구/상수)은 생략.

| R 성격 | 설계 내용 |
|---|---|
| **UI** | wireframe(텍스트 ASCII — 좌우분할/탭/select 등 화면 구조) + 이벤트 흐름(클릭→모달→저장 시퀀스) + 상태 변화 |
| **API** | 엔드포인트(메서드+경로) / 요청·응답 스키마 / 에러 케이스 / 인증·권한 |
| **데이터 모델** | 스키마 변경(테이블/컬럼/제약) / 마이그레이션 / 기존 데이터 처리 |
| **외부 연동** | 호출 시퀀스 / 실패·재시도·타임아웃 / 멱등성 |
| **단순 변경** | (생략) |

UI R wireframe 작성 규칙:
- 텍스트 ASCII 박스 (코드블록)
- 영역 배치 / 요소 라벨 / 페이지 이동 / 모달·드롭다운 상태 (색·폰트·픽셀·아이콘 제외)
- REQ 묶음 화면 통합 UX 단위 (좌우분할 vs 상단 select 등)
- 결정 단위(레이아웃 → 영역 배치 → 요소 흐름)로 분해해 한 번에 하나씩 Q → 답변 받아 누적

**매핑된 demo.md가 있는 UI R**: scaffold가 정본. plan은 "demo.md 참조"만 적고 wireframe·이벤트 흐름 생략. 추가 결정만 기록.

## 테스트 모드 선택

**우선순위: TDD > 사후 > 생략**. 가능한 가장 높은 모드 선택.

| 모드 | 적용 조건 | R 성격 예 |
|---|---|---|
| **TDD** | 입력 → 출력을 코드로 단언 가능 | 비즈니스 로직, 알고리즘, 데이터 변환, mock 가능한 외부 연동 |
| **사후** | 동작 후 상태/응답을 코드로 단언 가능 | UI 동작, 실제 외부 API, DB 변경 결과 |
| **생략** | 위 둘 다 불가 / 검증 비용 대비 가치 낮음 | 일회성 스크립트, 단순 마이그레이션 |

판단 모호 → Q ("TDD로 끌어올릴 여지" 먼저 검토).

## 결과

| 결과 | 의미 | 다음 동작 |
|---|---|---|
| `proceed` | 변경할 R 있음 | implement 진행 |
| `skip-to-verify` | 모든 R 이미 구현됨 | verify 직행 |

(`back-to-spec` 분기는 없음. spec 모순은 plan 안에서 처리 후 계속.)

## 핵심 원칙

- self-contained 블록 (R 블록 안에 현황/변경/테스트 인라인)
- raw input 불변
- ID 불변
- 자동 판단 금지: 결정 근거 없으면 Q 등록 (현황/모드 판단 포함). 모든 결정은 plan.md에 근거 출처 명시.
- 한 번에 하나씩 Q

## 안티패턴

- ❌ 라인 번호로 변경 위치 표기
- ❌ 변경 방식에 완전한 코드 스니펫
- ❌ 결정 근거 없는 추정을 Q 없이 단정
- ❌ R 단위 정보를 별도 섹션으로 분리 (self-contained 블록 깨짐)
- ❌ 작업 순서를 R 안에 적기 (R 간 관계는 별도 섹션)
- ❌ 마지막 Q 답변 직후 plan.md 전체 재검토 없이 planned 전환
- ❌ 역방향 검토 없이 planned 전환
- ❌ 단순 변경 R(색상/문구/상수)에 설계 서브섹션 추가
- ❌ demo.md가 있는 UI R인데 plan에 wireframe/이벤트 흐름 중복 작성
- ❌ demo.md 없는 UI R인데 wireframe(텍스트 ASCII) 누락
- ❌ wireframe·이벤트 흐름을 통째 작성 후 한꺼번에 컨펌 (결정 단위로 분해해 하나씩 Q)
- ❌ UI/API/데이터 모델/외부 연동 R인데 설계 서브섹션 누락
