# sd-category: WBS 호출 단위 분해

대규모 요구사항을 큰 카테고리로 1차 분해해 sd-wbs 호출 단위를 정한다.

`plan : task = wbs : 카테고리`. wbs가 plan 하나를 task로 분해하듯, 본 스킬은 wbs 하나를 부르기 좋은 카테고리로 분해한다.
산출물 `category-map.md`는 사용자가 sd-wbs 호출 단위를 정할 때 참고하는 자료다. sd-wbs가 자동으로 받아오지 않는다.

## 카테고리의 정의

카테고리는 사용자 활동(business capability)을 묶은 큰 관리 단위다. 액터(이해관계자·내부 사용자)가 일상 업무에서 수행하는 동작이 응집된 단위로 가른다.

**입도 기준:** 카테고리는 wbs 호출 단위가 되는 큰 묶음이다. `~~ 관리`·`~~ 영역` 같은 명사형 묶음으로 가른다. `가입`·`대출`·`반납` 같은 단일 액션은 카테고리가 아니라 wbs 내부 Activity·Task다.

다음은 카테고리 분해 축이 아니다.

- 시스템·기술 산출물 (테이블·모델·뷰·프로시저·미러링 모델 수)
- 외부 시스템 통합·동기화 자체 (ERP·PG·메시징·SaaS 어댑터 등)
- 인프라성 cross-cutting (파일 서버, 자동 업데이트, 인증 인프라, 로그 송출 등)
- 데이터 흐름·통합 워크플로
- 코드 응집·패키지 구조

외부 시스템·인프라는 카테고리가 사용하는 메커니즘이지 카테고리 자체가 아니다. 사용 카테고리에 흡수하거나 0단계 부트스트랩(워크스페이스 인프라)에 통합한다.

## 분해 원칙

다음 분할은 절대 하지 않는다.

| 분할 방식 | 왜 안 되는가 | 대신 |
|---|---|---|
| 다단 분해 (3단 이상) | sd-wbs의 Activity·Task 영역까지 침범한다 | 카테고리 자체를 둘로 나눈다 |
| 유스케이스·단일 액션별 (`가입`·`대출`·`반납`·`등록`) | 한 관리 영역을 행위로 쪼갠 거다. wbs 내부 Activity·Task 단위 | `~~ 관리`로 합친다 |
| 레이어 (Backend/Frontend/DB/관리자/사용자) | 솔루션 공간을 가르는 거지 문제 공간이 아니다 | 사용자 동작 단위로 본다 |
| 액터별 (관리자/직원/고객) | 같은 영역을 권한으로 쪼개면 응집이 깨진다 | 카테고리 안에서 액터를 표기한다 |
| CRUD별 (Customer Create/Read/Update) | 한 영역을 동작으로 쪼갠 거다 | 한 카테고리로 합친다 |
| 잡탕 (`기타`/`공통`/`Utility`/`Common`) | 분해가 끝나지 않았다는 신호다 | 해체해서 어울리는 카테고리에 흡수, 또는 인프라로 분리 |

사용자가 위 분할을 직접 요청하더라도 그대로 따르지 않는다. wbs 호출 단위 관점으로 다시 해석해 사용자 활동의 큰 묶음으로 가른다.

## ID 형식

- 카테고리: `1`, `2`, `3` ... (식별 목적의 단순 일련번호. 순서적 의미 없음)
- 카테고리는 평탄 구조로 나열한다. 다단 ID(`1.1`, `1.1.1` 등)는 사용하지 않는다.
  - 사유: 의존이 카테고리를 가로지르므로 다단 카테고리 그룹이 호출 묶음 역할을 못 한다. 호출 묶음은 의존 단계(Step 5-3)가 담당한다.

## sd-wbs 본체는 건드리지 않는다

`category-map.md`는 사용자 참고용이다.
sd-wbs의 입력 시그니처를 바꾸지 않고, sd-category가 sd-wbs를 자동으로 부르지도 않는다.
사용자가 `category-map.md`를 보고 *"1단계 카테고리들로 wbs 만들어줘"* 또는 *"1번 카테고리만 wbs 만들어줘"* 같이 직접 부른다.

## Step 1: 자료 완독과 카테고리 1차 식별

요구사항 자료를 끝까지 읽고 카테고리 후보를 거칠게 잡는다. 정련은 Step 2~3에서 한다.

모든 항목은 `sd-clarify` 지침에 따라 명확화한다.

### 입력 형태별 처리

- 문서 파일(docx, xlsx, pdf 등)이 들어오면 `/sd-doc-extract`로 내용을 뽑아 분석한다.
- 기존 `category-map.md` 경로가 들어오고 수정 요청이면 그 문서를 읽어서 갱신한다.
- 마이그레이션처럼 기존 시스템이 요구사항 출처일 때는 그 코드베이스를 보고 카테고리를 파악한다.

### 기존 category-map.md 수정 시 보존 규칙

- 기존 카테고리 번호, 사용자 메모는 임의로 초기화·삭제하지 않는다.
- 번호를 바꿔야 한다면 옛 번호 → 새 번호 매핑과 변경 사유를 문서에 적는다.

### 원본 완독

- 첨부 파일, 메시지 본문, 메일 thread, 회의록 같은 원본은 끝까지 읽는다. 키워드 검색만으로 끝내지 않는다.
- 자료별 분량(페이지·라인·통수)을 보고에 적어 부분 독해를 드러낸다.
- 자료를 다 읽기 전에는 다음 단계로 넘어가지 않는다.

### 1차 식별 방법

- 사용자 활동을 묶었을 때 자연스럽게 응집되는 `~~ 관리` 단위
- 조직도/부서가 자료에 드러나면 그 매핑
- EventStorming pivotal events가 있다면 그 묶음

### 카테고리 후보 작성 규칙

각 후보에 다음을 같이 적는다.

- 임시 이름 (`~~ 관리`·`~~ 영역` 형식 권장)
- 1줄 설명 (이 카테고리가 무엇을 다루는가)
- 핵심 액터 (이해관계자·내부 사용자)
- 인용 근거 (요구사항 출처, 사용자 답변 등)

### 활동 단위 게이트

모든 후보에 다음 질문을 적용한다. 한 건이라도 시스템·통합·인프라 단위로 잡혀 있으면 후보에서 빼고 흡수처를 정한다.

> 이 후보가 사라지면 액터의 어떤 활동(사용자 동작)이 못 일어나는가?

- 답이 "기술 데이터 흐름이 끊어진다" / "외부 시스템 연동이 끊어진다" / "인프라 동작이 끊어진다" → 카테고리 아님. 사용 카테고리에 흡수하거나 0단계 부트스트랩에 통합. Step 2 진입 금지.
- 답이 "액터가 활동 X를 못 한다" → 카테고리. Step 2 진행.

## Step 2: 의존성 매트릭스

카테고리 사이의 의존을 정리한다. Step 5-3 호출 순서 안내의 직접 입력이다.

모든 항목은 `sd-clarify` 지침에 따라 명확화한다.

### 의존성 판단 기준

A의 산출물·결정·이벤트가 B에 영향을 줄 수 있으면 의존으로 등록한다.
"코드끼리 import 안 한다"가 곧 "의존이 없다"는 아니다.
의존이 없다는 근거를 댈 수 없으면 의존이 있다고 본다.

### 매트릭스 형식

```
| 카테고리 | 의존 대상 | 의존 사유 |
|---|---|---|
| 1 | 없음 | (Bootstrap) |
| 2 | 1 | 1의 회원 식별자를 쓴다 |
| 3 | 1 | 1의 도서 식별자를 쓴다 |
```

### 의존성 검증

1. 의존이 `없음`인 카테고리가 적어도 하나 있어야 한다 (1단계 시작점).
2. A→B→A 같은 순환이 없어야 한다.
3. 산출물·이벤트·결정의 영향 관계가 표에 빠짐없이 들어가 있는지 확인한다.

## Step 3: 자가검증

1차로 뽑은 결과를 메인 세션이 다음 항목으로 점검한다. 한 건이라도 걸리면 `sd-clarify`로 명확화한 뒤 Step 1~2로 돌아간다.

1. **MECE 점검** — 두 카테고리의 핵심 활동이 같거나 강하게 겹치지 않는지. 겹치면 owner를 정하거나 한쪽으로 합친다.
2. **입도 검증** — 카테고리가 `~~ 관리`·`~~ 영역` 단위로 묶여 있는지. `가입`·`대출`·`반납` 같은 단일 액션이 카테고리로 올라와 있으면 같은 관리 영역끼리 합친다.
3. **레이어/액터/CRUD 분할 검출** — 카테고리 이름·설명·분해 기준에 `Backend`/`Frontend`/`Admin`/`User`/`Create`/`Read` 등이 분류 기준으로 들어가면 위반. 사용자 동작의 큰 묶음 단위로 다시 가른다.
4. **활동 단위 검증** — 모든 카테고리가 액터 동작 단위인가? 시스템·기술 산출물·외부 통합·인프라 cross-cutting 단위로 빠진 후보가 있는가? 있으면 활동 단위 게이트로 돌아가 흡수처를 정한다.
5. **미확정 표현 제거** — 본문에 추측·잠정 표현(`아마도`/`추정`/`보임`/`예상`) 또는 미루기 표현(`추후 결정`/`협의 필요`/`별도 확정`/`미확정`/`보류`) 잔존 검출. 발견 시 `sd-clarify`로 명확화 후 본문에서 제거.

## Step 4: 격리 검증

알아서 생략하지 않는다. 자체 요약 텍스트로 대체하지 않는다. 반드시 Agent tool을 호출한다.

문서를 다 만든 뒤, 작성자 편향을 걷어내고 빠진 정보를 잡기 위해 메인 세션과 분리된 subagent로 격리 검증을 돌린다.

### 검증 호출

subagent (effort: `low`)에 다음을 넘긴다:

- **category-map.md 절대 경로** — 검증 대상
- **원본 자료 절대 경로 목록** — 첨부 파일(docx/xlsx/pdf 등). `/sd-doc-extract`로 뽑아 둔 파일이 있다면 같이 넘긴다.
- **사용자가 처음에 보낸 요청 메시지 본문** — 프롬프트에 인라인으로 박는다.

subagent에는 한 가지 제약을 건다: "보고만 한다. category-map.md는 수정하지 않는다."

### subagent 프롬프트에 들어갈 검증 가이드

#### 검증 항목

1. **양방향 커버리지 (정량 매핑 표)** — 원본에서 뽑은 비즈니스 활동·도메인 어휘·이해관계자가 카테고리에 매핑되어 있는지.
   - 뽑을 항목: 비즈니스 활동 / 도메인 어휘 / 이해관계자(액터)
   - 누락: 원본에는 있는데 매핑이 안 된 항목
   - 근거 없는 추가: category-map에는 있는데 원본·근거에서 추적이 안 되는 항목
2. **잡탕 카테고리 검출** — `기타`/`공통`/`Utility`/`Common`/`Misc` 같은 catch-all 이름은 해체 권고.

#### 완독 의무

원본 자료(첨부 파일·인라인 요청 메시지)는 끝까지 읽는다. 키워드 검색만으로 끝내지 않는다.

#### 출력 포맷

- **요약** — 원본 항목 수 / 매핑·누락·근거 없는 추가·잡탕 (각 정수)
- **정량 매핑 표** — 컬럼: `원본 표현` / `출처(자료명·위치)` / `category-map 반영 위치` / `category-map 표현` (반영 위치가 비면 누락이다)
- **항목별 목록** — 각 검증 항목의 발견 건. 출처·권장 반영 위치·권장 처리 방향을 적는다.
  - 누락: "카테고리 X에 추가"
  - 근거 없는 추가: "근거 보강" / "삭제"
  - 잡탕 카테고리: "해체해 어울리는 카테고리에 흡수" / "인프라로 분리"

### 메인이 결과를 처리하는 방식

1. 결과 항목은 모두 `sd-clarify` 지침에 따라 명확화한다.
2. 카테고리 구조 자체를 다시 짜야 하면 Step 1~2 해당 단계로 돌아간다.

각 sd-wbs 호출은 새 세션에서 진행되니, category-map.md에 빠진 정보가 있어서는 안 된다.

## Step 5: category-map.md 작성과 수행 순서 안내

### 5-1. 산출 경로

- 입력이 이미 `.tasks/` 안의 문서라면 같은 폴더에 둔다 (예: `.tasks/260411_some-project/category-map.md`).
- 그 외에는 `.tasks/{timestamp}_{topic}/category-map.md`.
  - `{timestamp}`: `date +%y%m%d%H%M%S` 결과
  - `{topic}`: 영어 kebab-case (예: `library-system`)

### 5-2. 문서 템플릿

```markdown
# Category Map: {프로젝트 한 줄 요약}

## 카테고리 분해

### 1. {카테고리 이름}

- **1줄 설명:** [무엇을 다루는가]
- **핵심 액터:** [이해관계자·내부 사용자]
- **포함 활동:** [이 카테고리에 들어갈 wbs Activity 후보 3~7개]
- **인접 카테고리:** 2, 3
- **인용 근거:** [요구사항 출처, 사용자 답변 등]

### 2. {카테고리 이름}

- **1줄 설명:** ...
- **핵심 액터:** ...
- **포함 활동:** ...
- **인접 카테고리:** 1
- **인용 근거:** ...

## 의존성 매트릭스

| 카테고리 | 의존 대상 | 의존 사유 |
|---|---|---|
| 1 | 없음 | (Bootstrap) |
| 2 | 1 | 1의 회원 식별자를 쓴다 |
| 3 | 1 | 1의 도서 식별자를 쓴다 |

## 수행 순서 안내

[Step 5-3 — 호출 단위 판단 기준 + 의존성 기반 단계별 묶음]
```

### 5-3. 수행 순서 안내

문서 작성과 격리 검증이 끝나면 사용자에게 sd-wbs 호출 가이드를 보여 준다.

- 호출 단위 판단 기준을 한 줄로 적는다.
  - 의존 단계 통째로: 단계 내 카테고리가 2~3개로 적고 응집도가 높을 때
  - 카테고리 하나씩: 단계 내 카테고리가 4개 이상이거나, 카테고리마다 따로 wbs가 필요할 때
- 의존성 매트릭스를 바탕으로 단계별 묶음을 적는다.
  - 의존이 `없음`인 카테고리 (Bootstrap)을 1단계로
  - 그 앞 단계에만 의존하는 카테고리를 다음 단계로

#### 안내 형식

```
1단계 (병렬 가능)
  - 1 인증 관리
  - 2 도서 재고 관리

2단계 (1단계 완료 후)
  - 3 도서 대출 관리 (← 1, 2)
```

호출 명령은 사용자가 자기 말로 `category-map.md`를 가리키며 sd-wbs를 직접 부른다.
