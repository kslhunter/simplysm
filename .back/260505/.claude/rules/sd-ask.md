# sd-ask: 사용자 질문/선택지 제시 형식

사용자에게 질문하거나 선택지를 제시할 때 본 지침을 적용한다.

## 필수 의무

- 다음 사유로 질문을 생략하지 않는다: "이 정도 질문은 과하다", "단순 확인이니 생략".
- 단일 경로만 합리적으로 보일 때도, "수행 안 함"을 포함한 선택지 구조로 제시한다.

## 질문 운영

- 질문 대기열 우선: 사용자 답변이 필요한 항목이 있으면 질문 대기열에 등록한다.
- 한 번에 하나씩: 각 질문마다 사용자 답변을 받은 뒤 다음 질문을 제시한다.
- 결정 대상 분리: 한 질문은 하나의 결정 대상만 다룬다. 조합·번들 옵션(예: "A+B+C 모두 수정" vs "A만" vs "B만")으로 묶어 제시 금지.
- 답변 누적: 앞선 질문의 답변은 저장된 결정으로 취급한다.
- 실행 시작 조건: 질문 대기열이 비고 모든 필수 질문의 답변을 받은 뒤에만 수정·실행·검증 등 후속 프로세스를 시작한다.
- 누락 답변 처리: 사용자가 현재 질문에 답하지 않으면 같은 질문을 다시 묻는다.
  - 누락 항목을 임의 추천안으로 처리하지 않는다.
- 추가 질문 처리: 답변 수집 중 또는 작업 중 새로 물어봐야 할 항목이 발견되면 후속 프로세스를 시작하지 않고 질문 대기열에 추가한다.
- 질문 정렬: 의존성 → 정보이득 → 발견 출처 순.
  - 의존성 우선: 상위 결정이 하위에 영향을 미치면 상위 먼저.
  - 정보이득 내림차순: 동일 의존성 내에서 상→중→하.
    - 상: 라우터·스키마·아키텍처 등 광범위 영향
    - 중: 모듈/컴포넌트 내 영향
    - 하: 단일 위치 영향
  - 발견 출처 묶음: 동일 정보이득 내에서 Step/Feature 번호·대상 식별자 단위로 묶음. 한 묶음 소진 후 다음 묶음. 진행 중 묶음에서 발견된 새 질문은 해당 묶음 끝에 추가.

## 응답 수령

- `AskUserQuestion` 등 도구를 호출하지 않는다 — 선택지 제시 형식이 곧 질문이며, 사용자 응답은 자유 텍스트로 받는다.
- 사용자 응답 형태:
  - 라벨 prefix만 (예: `B`) — 직전 선택지 제시 형식의 해당 옵션을 선택한 것으로 처리한다.
  - 라벨 + 보충 (예: `B로 가되 X도 추가`) — 옵션 선택 + 사용자 추가 의견을 모두 반영한다.
  - 자유 텍스트 (예: "둘 다 검토해줘", "다른 방식이 떠올랐는데 ...") — 라벨에 매칭되지 않으면 사용자 의도대로 처리한다.
- 답변 미수령 처리: 사용자가 다른 주제로 응답하면 결정 미수령으로 간주하고 같은 형식을 재제시한다 (질문 운영의 누락 답변 처리 룰 적용).

## 선택지 제시 형식

각 질문은 다음 5개 블록을 순서대로 출력한다.

1. 결정 대상 헤더 (`### {대상명}`)
2. 컨텍스트 (헤더 없는 산문)
3. 선택지 (헤더 없는 불릿 리스트 + 영향 범위 인용블록)
4. 평가표 (헤더 없는 표 + 추천 인용블록)
5. 예시 (헤더 없는 본문, 조건 충족 시에만 출력)

결정 대상 헤더 외 나머지 4개 블록은 마크다운 헤더(`####` 등)를 사용하지 않는다. 산문·불릿·표·인용블록의 시각적 차이만으로 블록을 구분한다.

선택지 제시 형식 출력 끝에만 가로선을 둔다 (블록 사이에는 가로선 없음).

블록마다 자기 완결: 사용자가 위쪽으로 스크롤하지 않고도 해당 블록 내용만으로 판단 가능해야 한다.
발견사항 N건의 통합 분석을 위쪽에 길게 몰아 쓰지 않는다 (필요 시 1~3줄 개괄만 허용).

사용자 시점 자기완결: 선택지 제시 형식 전체 텍스트는 사용자가 이미 본 정보만으로 의미가 통해야 한다.
- 허용 출처: 누적 맥락(사용자 발언·기존 tool 결과·세션 산출물), 인용된 코드·문서, 일반 도메인 어휘.
- 금지: Claude 사고과정에서만 도출된 중간 개념·용어·전제·약어를 그대로 노출하는 것.
- 사고과정 산물을 꼭 써야 하면 그 개념을 만드는 과정 자체를 2번 컨텍스트에 풀어 설명한다. 풀이 불가능하면 그 개념 자체를 별도 결정 대상으로 끌어올린다.

### 1. 결정 대상 헤더

- 다건: `### [{번호}/{전체}] {대상 식별자/경로:라인}`
- 단건: `### {대상 식별자/경로:라인}`

"결정 대상:" 같은 prefix는 붙이지 않는다. 대상명 자체로 곧바로 헤더를 시작한다.

### 2. 컨텍스트

결정 대상 헤더 직후에 1~3문장 산문으로 작성한다. 무엇이 발견됐고 왜 결정이 필요한지를 한 흐름으로 풀어 쓴다.

- 코드/문서 인용은 결정 판단에 본문이 꼭 필요할 때만 첨부한다. 좌표(파일경로:라인)만으로 충분하면 좌표만 적는다.
- 인용 형식 (필요 시):
  - 파일경로: 프로젝트/워크스페이스 루트 기준 상대 경로 (예: `docs/회의/2026-03-17_매출관리.txt`, `packages/order-app/src/pages/OrderPage.tsx`).
  - 위치 좌표: 파일 형식별 식별자 (`:라인` / `Slide N` / `Sheet 시트명!Cell` / `p.N`).
  - 금지: 파일 식별 불가 좌표 단독 인용 (`Slide 13`, `body.txt:266`, `회의대본_5 L1349` 등). 동일 형식 파일이 여러 개 존재할 때 사용자가 자리를 못 찾는다.
- (sd-clarify Step 2를 거친 경우) 분류 결과는 산문 끝에 한 줄로 덧붙인다 (예: `분류: ASSUMED 유지 — UX 정책 결정 필요`).

다음 형태로 대체 금지: "핵심 질문: ..." 한 줄 요약, "{대상} 처리" 축약, 위쪽 통합 분석 참조("발견 1 처리" 등).
4단 분리(현재 상태/발견 요지/결정 사안/분류) 헤더로 쪼개지 않는다 — 한 흐름의 산문에 통합한다.

어휘:

- 결정의 영향이 닿는 사용자 관점에서 작성한다.
  - UI·동작·정책·문구가 변하는 결정 (사용자 = 최종고객): 화면명·UI 요소·사용자 동작·결과로 풀어 쓴다. 시스템 내부 용어(코드 식별자·내부 변수명·파일 경로) 본문 노출 금지 (좌표 인용은 허용).
  - 코드 구조·아키텍처·패키지 분리 등 사용자 = 개발자인 결정: 코드 식별자 그대로 사용 가능.
- 식별자만 나열하여 컨텍스트를 채우지 않는다 (사용자 유형 무관). 식별자·좌표는 인용으로만 등장하고, 문제·결정 사유는 풀어 쓴 산문으로 전달한다.
- 1회독 점검: 사용자가 위로 스크롤·검색하지 않고 한 번 읽어 무슨 결정인지 이해되는가. 안 되면 산문을 풀어 다시 쓴다.

### 3. 선택지

각 선택지를 다음 관점으로 제시한다.

- 변경 후 모습: 결정 성격에 맞는 가장 직관적인 양식을 자유 선택 (코드 변경이 본질일 때만 ```diff` 블록, 그 외에는 한 줄 설명·불릿·구조도·표 1행 등).
- 영향 범위: 파급되는 파일·모듈·API (구현·작업 비용도 여기 서술). 선택지 불릿 직후 인용블록 한 줄로 분리 (`> 영향 범위: A는 ..., B는 ..., C는 ...`).

원칙:

- 사용자가 원문을 찾지 않아도 이 출력만으로 판단 가능해야 한다.
- 옵션마다 헤더(`##### A. ...`) + 코드블록 + 설명 문단 3단 구조를 의무로 두지 않는다. 짧은 결정은 옵션 1줄(`- A. 라벨: 한 줄 설명.`)로 충분.

### 4. 평가표

평가축 3개 이상 선정 후 단일 매트릭스 표 1개 + 추천 한 줄 인용블록만 출력한다 (그 외 부연 문단 추가 금지).

- 평가축은 결정 결과의 사용자 가치만 측정 (구현·작업 비용은 3번 선택지의 영향 범위에 서술).
- 모든 평가축은 "높을수록 좋음" 방향으로 통일.
- 행 = 선택지(평균 내림차순), 열 = 평가축 + 평균.
- 축별 점수를 반드시 노출한 뒤 평균을 10점 만점으로 병기 (최종 점수만 표기 금지).
- 표 직후 인용블록으로 추천을 한 줄 명시: `> 추천: {선택지} — {사유 한 줄}`.

점수 산정 (Claude 내부 절차 — 사용자 출력에 별도 헤더로 노출 금지):

- 원안·변형안 동일 기준 평가: 사용자 원안에 가산점·하한 없음. 변형안과 같은 평가축으로 점수 매김.
- 추상가치 깎기 금지: `일관성`·`직관성`·`보존`·`확장성` 같은 추상명사 단독으로 점수 깎지 않는다.
  - 깎으려면 구체 시나리오 1개 이상 인용 (원안·변형안 모두 적용).
- 변형안 도입 책임: 원안 외 변형안을 추가할 때 "원안의 어떤 결함을 어떤 메커니즘으로 해결하는가"가 그 변형안의 선택지 한 줄 설명·평가표 점수에서 자연스럽게 드러나야 한다.

예시:

| 선택지 | 일관성 | 직관성 | 워크플로 보존 | 평균 |
|---|---|---|---|---|
| A. xxx | 10 | 10 | 7 | `9.0` |
| B. yyy | 6 | 7 | 9 | `7.3` |
| C. 수행 안 함 | 2 | 10 | 5 | `5.7` |

> 추천: A — 워크플로 보존이 1단계 낮지만 일관성·직관성이 모두 최상

### 5. 예시

다음 조건 중 하나에 해당할 때만 평가표 직후 출력한다.

- 옵션 라벨만으로 결과 차이를 추정하기 어려운 경우
- 추상 정책·UX 변경 등 구체 입력값으로 환원해야 이해 가능한 경우

양식은 자유. 다음 원칙만 지킨다.

- 구체 입력값/상황으로 환원해 결과를 보여줄 것
- 추상 옵션 라벨을 그대로 반복하지 말 것
- 결정의 성격(코드 비교·수치 대비·정책 풀이 등)에 맞는 가장 직관적인 형식을 선택할 것

양식 예시:

- 코드 비교: 변경 전후 `diff` 블록 1쌍
- 수치 비교: 입력값별 결과를 짧은 불릿 1~2줄로 정리
- 정책 풀이: 옵션 라벨 없이 시나리오 결과만 풀어쓴 1~2문단
- 옵션 나열: 옵션 라벨 + 결과 불릿 (적용 예시 참조)

금지:

- 표 사용: 평가표(4번)와 형식 중복.
- 시간 순서 시나리오 흐름: "X 입력 → 모달 → 닫기 → 재입력" 같은 흐름이 아니라 결과 자체를 정리.
- 3번 선택지의 옵션과 단순 중복: 라벨·설명만 반복하지 말고 그것이 보여주지 못하는 구체 결과값으로 환원.

어휘:

- 2번 컨텍스트의 어휘 룰을 동일하게 적용한다.

## 적용 예시

가상의 결정 1건을 선택지 제시 형식으로 풀어쓴 예시. 위에서부터 1. 결정 대상 헤더 → 2. 컨텍스트 → 3. 선택지 → 4. 평가표 순으로 대응한다 (5번 예시는 본 사례에서 생략).
