# sd-plan

개발 착수 전, 사용자 발언·제공 자료·현재 코드베이스·공식 문서를 근거로 브레인스토밍과 조사를 수행하고, 실행 가능한 개발계획서 `plan.md` 를 작성한다.

**핵심 목적**: 구현자가 추측하지 않고 개발을 시작할 수 있도록 범위·비범위·결정·리스크·작업 순서·검증 기준을 한 파일에 고정한다. 계획 작성 후 자동 구현으로 넘어가지 않고 정지한다.

## 입출력

- **Input**: 사용자 요청, 대화 중 확정된 내용, 사용자가 제공한 자료, 현재 코드베이스, 공식 문서·표준.
- **Output**: `.docs/{yyMMddHHmmss}_{제목}/plan.md` 1개.
- **폴더**:
  - `{yyMMddHHmmss}`: 계획 작성 시점의 현재 로컬 시각.
  - `{제목}`: 사용자와 합의한 작업 제목. 한국어·영문·숫자·공백·`_`·`-` 허용. 파일시스템 금지 문자(`\\ / : * ? " < > |`)는 제거하거나 의미가 보존되는 문자로 치환.
  - 제목이 불명확하면 작성 전 사용자에게 묻는다.
  - 같은 경로가 이미 있으면 덮어쓰지 말고 사용자에게 새 제목 또는 재진입 여부를 묻는다.

## 본질

- **독립 계획서**: 특정 선행 문서 형식에 의존하지 않는다. 입력 자료가 있으면 근거로 활용하되, 별도 문서 체계의 하위 산출물로 취급하지 않는다.
- **자동 구현 금지**: `plan.md` 작성·검증·보고 후 정지한다. 사용자가 별도 구현 지시를 하기 전까지 코드 수정·빌드·테스트 실행으로 넘어가지 않는다.
- **근거 없는 결정 금지**: `결정 근거`가 부족하면 `[OPEN]` 으로 남기거나 사용자에게 묻는다.
- **브레인스토밍은 결정이 아니다**: 발산 단계에서는 선택지와 근거를 모을 뿐이며, 수렴 단계에서 근거 있는 항목만 채택한다.
- **기법 최소 적용**: 아래 기법 라우터에서 필요한 것만 사용한다. 모든 기법·모든 섹션을 억지로 채우지 않는다.
- **범위 방어**: 포함 범위뿐 아니라 비범위를 반드시 적는다. "나중에 필요할 수 있음" 은 계획에 넣지 않는다.
- **작업 단위**: 내부 구현 조각이 아니라 검증 가능한 산출물 단위로 나눈다.
- **불확실성 표면화**: `[OPEN]` 은 숨기지 않는다. Blocking `[OPEN]` 이 있으면 상태를 `Blocked` 로 둔다.

## 워크플로

### 0단계: 접수·경로 확정

1. 작업 대상과 목적을 한 문장으로 확정한다.
2. 제목을 확정하고 산출 경로 `.docs/{yyMMddHHmmss}_{제목}/plan.md` 를 계산한다.
3. 계획 작성에 필요한 입력 자료 목록을 만든다.
4. 다음이 불명확하면 시작 전 사용자에게 묻는다.
   - 무엇에 대한 계획인지
   - 제목을 무엇으로 할지
   - 사용자가 명시한 필수 자료가 어디 있는지

### 1단계: 자료 수집

- 제공 자료와 관련 파일을 직접 읽는다.
- 코드베이스 조사는 현재 워킹트리 기준으로 수행한다.
- `.back/` 및 `.gitignore` 등재 경로는 사용자 명시 없이는 읽지 않는다.
- 의존성 조사는 `node_modules` 가 아니라 lock 파일과 package manifest 를 우선한다.
- 외부 라이브러리·표준 동작이 계획에 영향을 주면 공식 문서 또는 표준을 확인한다.

### 2단계: 발산 조사

범위가 작으면 메인 에이전트가 직접 수행한다. 범위가 넓거나 관점이 독립적이면 병렬 독립 서브에이전트로 조사한다.

권장 조사 관점:

| 관점      | 조사 내용                                           |
| --------- | --------------------------------------------------- |
| 요구·자료 | 사용자 요청, 제공 자료, 빠진 정보, 모호한 표현      |
| 코드 패턴 | 유사 구현, 파일 구조, 테스트 방식, 네이밍·계층 패턴 |
| 외부 근거 | 공식 문서, 표준, API 제약                           |
| 리스크    | 데이터 변경, 호환성, 배포, 롤백, 검증 난점          |

서브에이전트 제약:

- 보고 전용. 파일 수정 금지.
- 최종 결정 금지.
- 근거 없는 추정은 `[OPEN]` 또는 `확인 불가` 로 보고.
- 조사 결과에는 근거 위치를 포함.

### 3단계: 기법 라우터

작업 성격에 맞는 기법만 선택한다.

| 상황                            | 사용할 기법                      | plan.md 에 남길 산출                                                         |
| ------------------------------- | -------------------------------- | ---------------------------------------------------------------------------- |
| 문제·해결 방향이 모호함         | Double Diamond / Design Thinking | 문제 프레이밍, 탐색한 대안, 선택·기각 이유                                   |
| 목표와 구현 항목의 연결이 약함  | Impact Mapping                   | 목표, actor, 기대 변화, deliverable, 핵심 가정                               |
| 고객 outcome·기회 근거가 충분함 | Opportunity Solution Tree        | outcome, opportunity, solution 후보, 검증할 가정                             |
| UI·사용자 흐름 중심             | User Story Mapping               | 사용자 단계, 핵심 흐름, release slice, 누락 흐름                             |
| 복잡한 업무·도메인 흐름         | Event Storming 초안              | 이벤트, 명령, 정책, 예외, hotspot. 이해관계자 검증 전에는 확정으로 쓰지 않음 |
| 시스템 경계·외부 연동 중심      | C4 / Context Mapping             | actor, system/container/component, 인터페이스, 책임 경계                     |
| 중요한 기술·정책 결정           | ADR/RFC 후보                     | 맥락, 선택지, 결정, 결과, 재검토 조건                                        |
| 버그·실패 해결 계획             | RCA                              | 최소 2개 원인 가설, 근거, 채택·기각, 해결 방향                               |
| 우선순위·범위 조정              | MoSCoW 기본, RICE/WSJF 조건부    | Must/Should/Could/Won't, 점수 근거, 순서 근거                                |
| 불확실성·실패 가능성 큼         | Assumption Mapping / Pre-mortem  | 핵심 가정, 실패 시나리오, 예방책, 조기 경고 신호                             |

주의:

- RICE/WSJF 는 수치 근거가 있을 때만 사용한다. 점수를 추정으로 채우지 않는다.
- Opportunity Solution Tree 는 고객·outcome 근거가 충분할 때만 사용한다.
- Event Storming 은 단독 확정 모델이 아니라 계획용 초안으로만 둔다.

### 4단계: 수렴·결정

1. 조사 결과의 중복을 제거하고 의미상 같은 선택지를 병합한다.
2. 선택지는 다음 우선순위로 평가한다.
   - 사용자 요구와 충돌하지 않는가
   - 현재 코드베이스의 일관된 패턴과 맞는가
   - 공식 문서·표준과 맞는가
   - 가장 단순한가
   - 나중을 위한 추상화가 아닌가
3. 근거 있는 선택만 `Accepted` 로 둔다.
4. 근거 부족 선택지는 `Proposed` 또는 `[OPEN]` 으로 둔다.
5. 사용자 가치, 공개 계약, UX, 범위, 데이터 손실, 비용·일정에 영향을 주는 결정이 근거만으로 확정되지 않으면 사용자에게 묻거나 Blocking `[OPEN]` 으로 둔다.

### 5단계: plan.md 작성

아래 "plan.md 형식" 으로 작성한다.

작성 규칙:

- 비자명 항목에는 `(근거: ...)` 를 붙인다.
- 모르면 `[OPEN]` 으로 쓴다.
- 해당 없음은 빈칸이 아니라 `[N/A]` 와 이유를 적는다.
- 동일 정보의 원천은 하나만 둔다. 중복 섹션에는 요약·참조만 둔다.
- `TASK` 는 검증 가능한 산출물 단위로 작성한다.
- `변경 금지` 대상을 명시해 범위 이탈을 막는다.

### 6단계: 독립 검증

작성한 plan 을 독립 서브에이전트로 검증한다. 대상이 아주 작으면 메인 직접 검증도 가능하지만, 중요한 계획이면 독립 검증을 기본으로 한다.

검증 축:

| 검증          | 목적                                               |
| ------------- | -------------------------------------------------- |
| 자료 커버리지 | 입력 자료의 중요한 요구·제약이 plan 에 반영됐는지  |
| 근거 검증     | 비자명 결정의 근거가 실제 존재하는지               |
| 과계획 검증   | 요청·근거에 없는 기능·옵션·추상화가 들어갔는지     |
| 실행 가능성   | 작업 순서, 의존관계, 검증 명령, 롤백이 모순 없는지 |
| 참조 무결성   | REQ/DEC/TASK/AC/TEST/GATE 참조가 끊기지 않았는지   |

검증 결과 처리:

- 근거 위조·부족 → 근거 제거 후 `[OPEN]` 또는 해당 항목 삭제.
- 누락 발견 → plan 보강.
- 과계획 발견 → 삭제. 후속 후보로 남길 근거가 없으면 남기지 않는다.
- 실행 불가 발견 → 작업 순서·게이트 수정 또는 Blocking `[OPEN]`.
- 서브에이전트 실패 시 부분 결과로 완료 보고하지 않고, 실패를 보완한 뒤 재검증한다.

### 7단계: 검토 패키지 보고 후 정지

보고 항목:

- 생성한 plan 경로.
- 핵심 목표·범위 한 줄 요약.
- 상태: `Ready` / `Blocked`.
- Blocking `[OPEN]` 목록.
- 주요 결정과 리스크.
- 검증 결과 요약.
- 미반영 자료가 있으면 그 사유.
- 다음 단계 제안.

보고 후 정지한다.
