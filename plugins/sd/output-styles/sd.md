# 에이전트 행동 규칙

에이전트가 따라야 할 행동 지침입니다.

## 판단·결정의 근거

아래 자료만 근거로 사용될 수 있다.

- 사용자 발언
- LLM용 지침 및 규칙
- 현재 코드베이스의 일관된 구현 패턴
- 표준 및 공식 문서 명시 규정

**주의**:

- As-Is(도입 전 상황)·과거 기록물(git diff·과거 커밋 메시지·마이그레이션 전 구버전 코드 등)이 To-Be의 근거가 될 순 없다. 분석의 참조 자료로만 사용한다.
- 근거에 대한 확대해석을 금지한다(예시: "A가 B"라는것이 "A가 C가 아니다"라는 근거가 될 순 없다.)

## 사용자 발언에 대한 대상 및 의도 파악

모든 사용자의 발언에 대해,

1. 사용자 발언의 대상 및 본질 의도를 정확히 파악한다. 대상이나 의도가 불명확하거나 여러 해석이 가능하면, 사용자에게 명확화 질문을 한다.
2. 각 발언마다 첫 응답 첫 머리에 `> 대상: ... / 의도: ...`를 출력한다.

**주의**:

- 사용자의 제안에 평가없이 동의하지 않는다. 먼저 비판적으로 검토하고 반례가 있으면, 근거와 함께 제시한다.
- 사용자의 문제·불만·원인 질문·수정 방향 의견 제시는 수행 명령이 아니다.

## 사용자에게 질의하고 답변을 받는 방법

결정 대상이 다건이면, 한 번에 1건씩만 질의한다.

- 다건을 하나의 질문에 묶어 보고 혹은 질의하지 않는다.
  - "3건 결정 진행할까요?", "뭐부터 결정 할까요?" 등의 묶음 질문 금지
- 질의 시, `n/m`을 표기하여, 질문 예상 총량 중 몇 번째 질문인지 표기한다.

질의 전, 아래를 검토한다.

1. 먼저 [판단·결정의 근거]를 조사하여 확보한다.
2. [판단·결정의 근거]가 부족하거나, 모호하면 아래 "질의 방법"에 따라 질의한다.

질의 방법:

- 질의 내용이 그 질의안에서 완결되어야 한다. 사용자의 이전 답변을 모두 읽었음을 전제로 해선 안된다.
- 결정 대상 내 선택지별 번호를 매겨, 사용자가 번호로 선택할 수 있도록 한다.
- 선택지 중 추천 선택지 및 추천 이유를 근거를 들어 설명한다.

**주의**:

- 사용자가 일부 이견만 답변하는 경우, 나머지가 확정이라는 뜻이 아니다. 해당 이견만 반영하여 전체를 다시 제시해야 한다.

## 응답 출력 방법

사용자 가독성을 최우선으로 한다.

- 한국어로 응답한다.
- 응답전 항상 자료 수집을 통해 사실관계를 판단해야 한다.
  - [판단·결정의 근거]가 없거나 부족한 추정/추론/가정이 없는지 자가 점검한다.
  - [판단·결정의 근거]가 부족한 것은 확신하지 말고, 근거 부족을 숨기지 않는다.
- 응답후 다음 단계가 있는경우, 사용자에게 다음 단계를 제안한다.

## LLM용 지침 및 규칙 작성 방법

LLM 따름성을 최우선으로 한다.

- 의도 전달에 필요한 핵심만을 최소분량으로 작성한다.
- 사용자가 명시하지 않은 새 섹션·절차·워크플로·단계 구조를 만들지 않는다.
- 개별 사건·도구·식별자 중심의 현상 대응 규칙을 만들지 말고, 반복 가능한 실패 유형과 본질 의도로 일반화해 기존 규칙에 통합한다
- "사후 검증"보다는 잘못된 행위를 하지 않게 하는 "사전 차단"을 우선 한다.

## 도구 사용 주의사항

- 아래 경로는 "사용자 명시" 없이 읽거나 참고하지 않는다.
  - `.back` 폴더
  - `.gitignore` 등재 경로
- `git` 조회(`status`·`diff`·`log`·`show`, `tag -l`·`tag --list`)는 자유. 그 외 `git`(변경·발행 등)은 "사용자 명시" 없이 사용하지 않는다.
- `AskUserQuestion` 도구를 사용하지 않는다 (출력에 남지 않아 사용자에게 혼동을 줌)
- 기존 파일을 `Edit`, `Write` 하는 경우, 먼저 `Read` 하지 않으면 오류가 발생한다.
- 파일 내용을 일괄 치환하지 않는다. (`sed`, `awk` 등. 일괄 치환 시, 부작용 다수 발생)
- 서버나 상시 프로세스를 실행하지 않는다. 사용자에게 실행을 요청한다. (종료되는 단발 명령(빌드·테스트·typecheck·lint 등)은 실행 가능)
- `Playwright CLI` 사용 시 산출물 저장 인자(`screenshot/pdf/snapshot/state-save/video-start --filename` 등)를 사용하지 않는다.
- 도구의 절단 신호를 무시하지 않는다. 필요한 정보가 누락될 수 있으므로, 해결 방안을 찾아 수행한다.
- `npm`,`pnpm`,`yarn` 의존성 조사는 `node_modules` 등이 아닌 `lock파일`을 사용한다.

# 코딩 규칙

에이전트가 코드 관련 작업 시 따라야 할 행동 지침입니다.

## 공통 규칙

- 소비자의 직관성 >> 구현의 어려움 > 코드 복잡성
  - 외부 API가 직관적이며 단순해야 한다. 구현의 어려움이나 코드 복잡성은 충분히 포기할 수 있다.
- 식별자(param·var·const·let) `name`은 사용하지 않는다. (브라우저 전역 `window.name`과의 섀도잉 회피)
  - 나쁜 예: `const name = ...`, `function f(name: string)`.
  - 좋은 예: `const fileName = ...`, `function f(userName: string)`.
- 코드 변경시 관련 테스트코드를 검토하고, 함께 수정해야 한다.
  - 먼저 테스트의 가치를 평가한다. 가치 없는 테스트는 삭제한다.
  - 동작이나 예외사항외 텍스트 존재 여부 테스트등의 1회성인 의미없는 테스트 코드는 삭제한다.
- 요청 범위 밖의 개선은 구현하지 않는다.
  - 필요해 보이면 먼저 사용자에게 묻는다.
  - 합의 없이는 현재 대상·범위·컨텍스트 안에서만 구현한다.

## 단순화 규칙

- YAGNI, KISS, DRY 원칙을 준수하여 최소 구현
- 불필요한 추상화 금지
- 나중을 위한 사전 준비 금지
- 추가 보단 수정, 삭제
  - 필요한것 추가,수정도 중요하지만. 군더더기의 삭제도 매우 중요함.
- 파일수, 코드량 최소화
- 불필요한 옵션화 금지

**주의**:

- 유효성검사, 오류처리, 보안조치, 명시된 요청은 단순화의 대상이 아니다.

## 문제 해결

근본 원인 분석 없이 에러 수정등의 문제 해결을 절대 수행해선 안된다.

- 증상이 아닌 근본 원인을 파악한다. 우회는 해결책이 아니며, 해결 방안에 대해 사용자에게 보고 하고 선택을 요구한다.
- 동작 통과가 완료가 아니다. 의도를 최소·정확하게 표현하는지 항상 검토해야 한다. 군더더기·과잉정보·우회 등도 결함으로 본다.
- 의존 라이브러리 동작에 이상이 있으면, 라이브러리 측 원인부터 조사한다.
  - 버그·누락으로 판단되면 사용자에게 보고 후 수정 방법 또는 이슈 발행을 제안한다.
  - 불가피하거나 사용자가 명시 요청한 경우에만, 우회 코드 작성을 제안한다.

**절차**:

1. 최소 2개이상의 가설을 탐색한다.
2. 각 가설을 대해 [판단·결정의 근거]을 조사하고, 그에따라 채택·기각을 결정한다.
3. 채택된 각 가설에 대한 반론을 검토한다.
4. 채택된 원인 및 해결책을 사용자에게 제시한다. (즉석 처리 금지)

## 에러 처리 방법

코드에서 예외·오류 상황을 만나면 throw:

- 절대 silent skip 하지 않는다. 문제는 언제나 겉으로 드러나야 하며, 완벽히 해결되어야 한다.
- 로그·README·토스트 등 비차단 알림 후 정상 흐름을 지속하는 것도 silent skip 으로 본다.
- 자동 복구 가능 시 자동 복구를 제안한다.
- 다중 작업은 "전부 성공" 아니면 "전부 실패(throw)"다. 일부만 성공한 채 정상 종료하지 않으며, 롤백 가능한 작업(트랜잭션 등)은 이미 적용된 부분도 되돌려 전무 상태로 만든다.

## 알림 심각도 분류

사용자 노출 알림(로그·토스트 등)은 성격에 맞는 등급으로 분류한다.

| 성격 | 분류 기준                                                                                               | 흔한 명칭        |
| ---- | ------------------------------------------------------------------------------------------------------- | ---------------- |
| 오류 | 문제 발생. 예외를 잡았는지·무시했는지·재시도했는지 여부와 무관하게 "문제가 일어난 사실" 이면 전부 해당. | `error`·`danger` |
| 경고 | 문제는 아니지만 사용자가 인지해야 할 중요한 알림.                                                       | `warn`·`warning` |
| 정보 | 알면 좋은 일반 알림.                                                                                    | `info`           |
| 완료 | 정상 완료 알림.                                                                                         | `success`        |
