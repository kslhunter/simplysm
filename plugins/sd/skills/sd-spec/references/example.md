## 1. 개요

### 1.1 핵심 목적

여러 소스(기본 파일, 환경별 파일, 환경변수)의 설정을 정해진 우선순위로 병합해 단일 설정 객체로 제공합니다.

### 1.2 주요 목표

- 앱 부팅 시 1회 호출로 검증된 설정 객체를 수령합니다.
- 미설정 키(undefined)를 임의 기본값으로 덮지 않고 그대로 전달합니다.

### 1.3 소비자/이해관계자

- 이 라이브러리를 import 하는 앱(서버, CLI) 개발자입니다.

### 1.4 환경/플랫폼

- Node.js 20+, TypeScript 입니다. 파일시스템에 의존하므로 브라우저는 미지원입니다.

## 2. 사용 시나리오

### 2.1 부팅 시 설정 로드

관련 섹션: [단위.loadConfig], [단위.defineSchema], [타입.ConfigSchema]

흐름:

1. 앱이 스키마를 `defineSchema` 로 선언합니다.
2. 부팅 진입점에서 `loadConfig(schema, options)` 를 1회 호출합니다.
3. 병합, 검증된 설정 객체를 수령합니다. 검증 실패 시 `ConfigError` 를 throw 해 부팅을 중단합니다.

```ts
const schema = defineSchema({
  port: "number",
  dbUrl: "string",
  debug: "boolean?",
});
const config = loadConfig(schema, { env: "production" });
```

## 3. 기타 요구사항

### 3.1 undefined 보존

- 관련 섹션: [단위.loadConfig], [단위.우선순위 병합 규칙], [타입.ConfigSchema]
- 요구 의도: 미설정 선택 키는 `undefined` 로 전달합니다. `""`, `0`, `false` 로 치환하지 마세요. 소비자가 "미설정"과 "설정된 falsy 값"을 구분할 수 있어야 합니다.

### 3.2 동기 로드

- 관련 섹션: [단위.loadConfig]
- 요구 의도: 부팅 경로에서 쓰이므로 동기 API 입니다. 비동기 소스는 범위 외입니다. (근거: 부팅 단순화 — 소비자 요청)

#### 4.1 loadConfig (kind: api)

관련 섹션: [기타 요구.undefined 보존], [기타 요구.동기 로드], [단위.defineSchema], [단위.ConfigError], [단위.우선순위 병합 규칙], [타입.ConfigSchema], [타입.LoadOptions], [외부 의존.파일시스템]

- 목적: 스키마 + 옵션을 받아 병합, 검증된 설정 객체를 동기로 반환합니다.
- 인터페이스, 계약: `loadConfig(schema, options?)` 입니다.
  - `schema` 는 [단위.defineSchema] 가 반환한 [타입.ConfigSchema] 핸들이고, `options` 는 [타입.LoadOptions] 입니다.
  - 반환은 그 스키마에서 추론된 설정 객체이며, 선택 키는 `T | undefined` 입니다.
  - 검증 실패 시 [단위.ConfigError] 를 throw 합니다.
- 동작, 내용: [단위.우선순위 병합 규칙] 순서로 소스를 병합하고 스키마 타입을 검증합니다. 미설정 선택 키는 `undefined` 로 유지합니다([기타 요구.undefined 보존]).
- 경계, 예외:
  - 필수 키가 없으면 [단위.ConfigError] 를 throw 합니다 (어느 키인지 메시지에 포함합니다).
  - 타입 불일치(예: `port` 가 비숫자)면 [단위.ConfigError] 입니다.
  - 설정 파일이 없으면 그 소스만 건너뛰고(에러가 아닙니다) 다른 소스로 진행합니다.
  - 파일 읽기 권한 오류면 throw 합니다 ([외부 의존.파일시스템] 예외 처리).
- 완료 기준: 위 각 경계 케이스(필수 키 부재, 타입 불일치, 파일 부재, 권한 오류)와 정상 병합이 단위 테스트로 검증됩니다. 미설정 선택 키가 `undefined` 로 보존됨을 단언합니다.

#### 4.2 defineSchema (kind: api)

관련 섹션: [단위.loadConfig], [단위.ConfigError], [타입.ConfigSchema]

- 목적: 설정 스키마를 선언하고 추론 가능한 타입 핸들을 반환합니다.
- 인터페이스, 계약: `defineSchema(shape)` 이며, `shape` 는 [타입.ConfigSchema] 의 `shape` 필드 형식입니다. 반환은 그 shape 를 담은 [타입.ConfigSchema] 핸들입니다.
- 동작, 내용: shape 를 내부 검증기로 변환합니다. 알 수 없는 타입 토큰은 선언 시점에 throw 합니다. → [단위.ConfigError] 를 사용합니다.
- 경계, 예외: 빈 shape 는 허용합니다(빈 설정). 미지원 타입 토큰은 [단위.ConfigError] 입니다.
- 완료 기준: 지원 토큰, 선택 접미, 미지원 토큰 거부가 테스트로 검증됩니다.

#### 4.3 ConfigError (kind: api)

관련 섹션: [단위.loadConfig], [단위.defineSchema]

- 목적: 설정 로드, 검증 실패를 나타내는 공개 에러 타입입니다.
- 인터페이스, 계약: `class ConfigError extends Error` 입니다. `key?: string`(문제 키), `reason: "missing" | "type" | "io"` 를 가집니다.
- 동작, 내용: throw 시 위 필드를 채웁니다. 메시지는 사람이 읽을 수 있는 한 줄입니다.
- 경계, 예외: 해당 없음입니다. 단순 값 객체입니다.
- 완료 기준: 각 reason 별로 적절히 throw 됨이 [단위.loadConfig] 테스트에서 함께 검증됩니다.

#### 4.4 우선순위 병합 규칙 (kind: infra)

관련 섹션: [기타 요구.undefined 보존], [단위.loadConfig], [타입.LoadOptions], [공통 정의.병합 우선순위]

- 목적: 여러 소스의 병합 우선순위를 한 곳에 고정합니다.
- 인터페이스, 계약: 외부 노출이 없습니다. [단위.loadConfig] 내부 규칙이며 적용 범위는 모든 로드입니다.
- 동작, 내용: [공통 정의.병합 우선순위] 를 모든 로드에 적용합니다. 파일 매핑은 환경별 파일이 `config.<env>.json`, 기본 파일이 `config.json` 입니다. 상위 소스의 키가 하위를 덮습니다.
- 경계, 예외:
  - 같은 키가 여러 소스에 있으면 [공통 정의.병합 우선순위] 로 상위만 채택합니다.
  - 어느 소스에도 없으면 undefined 입니다([기타 요구.undefined 보존]).
  - [타입.LoadOptions] 의 `env` 가 undefined 이고 `process.env.NODE_ENV` 도 없으면 환경별 파일 소스 자체를 생략하고 나머지 소스로 병합합니다.
- 완료 기준: 우선순위 덮어쓰기, undefined 전파, 환경 미해석 시 환경별 파일 소스 생략이 테스트로 검증됩니다.

## 5. 공통 정의

### 5.1 용어 사전

- **설정 소스**: 설정 키-값을 제공하는 출처입니다 — 기본 파일, 환경별 파일, 환경변수.
- **병합 우선순위**: 같은 키가 여러 소스에 있을 때의 채택 순서입니다. 환경변수 > 환경별 파일 > 기본 파일.

### 5.2 환경변수 키 규약

- 환경변수는 `APP_` 접두 + 대문자 스네이크입니다 (예: `APP_DB_URL`). 스키마 키 `dbUrl` 이 `APP_DB_URL` 에 매핑됩니다. [OPEN] 중첩 키 매핑 규칙 — 단일 레벨만 확인됐고 중첩 객체 매핑은 미확인입니다.

## 6. 핵심 타입, 자료구조

### 6.1 ConfigSchema

필드:

| 필드  | 타입                        | 필수 | 비고                                             |
| ----- | --------------------------- | ---- | ------------------------------------------------ |
| shape | `Record<string, TypeToken>` | 필수 | 키별 타입 토큰 (`TypeToken` 값 범위는 아래 제약) |

제약:

- `TypeToken` 은 `"number" | "string" | "boolean"` 입니다. `?` 접미는 선택 키입니다.
- shape 키는 유일합니다.
- 선택 키(`?`)는 추론 타입에서 `T | undefined` 입니다.

### 6.2 LoadOptions

필드:

| 필드 | 타입     | 필수 | 비고                                                |
| ---- | -------- | ---- | --------------------------------------------------- |
| env  | `string` | 선택 | 환경 이름. 미지정 시 `process.env.NODE_ENV` 로 해석 |
| dir  | `string` | 선택 | 설정 파일 디렉터리. 미지정 시 cwd                   |

## 7. 외부 의존, 인터페이스

### 7.1 파일시스템

관련 섹션: [단위.loadConfig]

- 대상: 로컬 파일시스템입니다 (Node `fs`).
- 방향, 성격: 읽기(동기)입니다.
- 경유: `config.json`, `config.<env>.json` 경로입니다.
- 예외 처리:
  - 파일이 없으면 해당 소스를 생략합니다(에러가 아닙니다).
  - 권한, IO 오류면 `ConfigError(reason: "io")` 를 throw 해 부팅을 중단합니다.

## 8. 결정 맥락

### 비동기 설정 소스 — 안 함

- 현재 결정: 동기 API 만 제공합니다. 비동기 소스(원격 설정 서버 등)는 미지원입니다.
- 근거: [기타 요구.동기 로드] (부팅 단순화 — 소비자 요청).
- 검토 경계: 로컬 파일, 환경변수만 검토했습니다. 원격, 네트워크 소스는 논의하지 않았습니다. 후속 LLM 이 "비동기가 낫지 않나"를 재론하기 전에, 아무도 검토하지 않은 영역임을 인지하세요.

### [제외] 설정 핫 리로드

- 후속 처리: 별도 spec 입니다.
- 근거: 현재 범위가 아닙니다.
- 자료 위치: 기획 메모 (가상).

### 화면 예시 (kind: screen) — 상태 있는 대화형, 사람 대상

> 타입렌즈 적용 시 성격이 "사람 대상 + 상태 있음"이라 아래 차원이 강하게 걸립니다. api 예시엔 없던 차원들입니다.
>
> - 품질 축의 상호작용(피드백, 오류 예방, 오류 복구, 일관성).
> - 경계(잘못된 입력 보정)와 실패:타이밍/순서.

#### 4.x 탭 대시보드 화면 (kind: screen)

관련 섹션: [단위.집계 조회 API], [타입.대시보드 필터]

- 목적: 여러 지표를 탭으로 나눠 한 화면에서 조회합니다. 탭 전환으로 지표군을 바꿉니다.
- 인터페이스, 계약: 진입 라우트는 `/dashboard` 입니다. 입력은 URL 쿼리(선택 탭, 기간 필터), 출력은 선택 탭의 지표 패널이며, 소비자는 로그인 사용자(사람)입니다.
- 동작, 내용: 탭 선택 시 그 지표를 [단위.집계 조회 API] 로 조회해 패널을 렌더합니다. 기간 필터 변경 시 현재 탭만 재조회합니다. 탭, 필터 상태는 URL 에 반영해 새로고침, 공유 시 복원합니다.
- 경계, 예외:
  - 로딩 중에는 이전 데이터를 유지하고 로딩을 표시합니다 (빈 화면 깜빡임을 금지합니다).
  - 빈 결과는 "데이터 없음"으로 오류와 구분해 표시합니다.
  - 조회 실패 시 그 패널에 오류와 재시도 행동을 제시합니다. 다른 탭은 영향이 없습니다.
  - 잘못된 URL 쿼리(없는 탭, 기간 역전)는 기본 탭, 기간으로 보정하고 사용자에게 알립니다.
  - 느린 응답 중 탭을 재전환하면 이전 요청을 취소하거나 최신 선택만 반영합니다 (순서 역전으로 옛 데이터가 덮어쓰는 것을 방지합니다).
- 완료 기준: 탭 전환, 필터 변경, 로딩, 빈 결과, 조회 실패, URL 복원, 빠른 연속 전환이 시연/테스트로 확인됩니다.

### 배치, 파이프라인 예시 (kind: job) — 자립 실행, 재실행 가능

> 타입렌즈 적용 시 성격이 "예약 실행 + 재실행 가능 + 대량 처리"라, 계약:불변식(멱등), 품질:신뢰, 성능(수용량), 실패:부분, 타이밍이 강하게 걸립니다. 화면 예시와도 또 다른 축입니다.

#### 4.y 야간 지표 집계 배치 (kind: job)

관련 섹션: [외부 의존.원장 DB], [단위.집계 조회 API]

- 목적: 매일 새벽 전일 원장을 집계해 지표 스냅샷 테이블에 적재합니다. 조회 화면은 이 스냅샷을 읽습니다.
- 인터페이스, 계약: 트리거는 스케줄러(매일 02:00)입니다. 입력은 대상 일자(기본 전일), 출력은 그 일자의 스냅샷 행이며, 소비자는 스케줄러와 운영자(기계 + 사람)입니다.
- 동작, 내용: 대상 일자 원장을 읽어 지표별로 합산한 뒤 스냅샷을 upsert 합니다 (이미 있으면 덮어씁니다).
- 경계, 예외:
  - 재실행이 안전해야 합니다(멱등). 같은 일자를 두 번 돌려도 결과가 동일하며 중복 적재하지 않습니다.
  - 부분 실패로 일부 지표만 적재된 채 끝내지 않습니다. 전건 성공이 아니면 그 일자를 롤백합니다.
  - 원장이 메모리 한계를 넘으면 분할 처리합니다(대량 수용).
  - 02:00 에 못 돌면(지연) 밀린 일자도 함께 처리하거나 경보합니다.
  - 원장 DB 접속 실패 시 스냅샷을 손대지 않고 실패로 종료하며 경보합니다 (부분 상태로 남기지 않습니다).
- 완료 기준: 정상 집계, 재실행 멱등, 부분 실패 롤백, 대량 분할, 지연 보정, DB 실패 처리가 테스트로 검증됩니다.

### 워크플로 단계 예시 (kind: workflow-step) — 비코드 산출물, 내용 완전성 완료기준

> 위 단위들(본편 §4.1-4.4 와 부록 화면, 배치)은 모두 코드 산출물이라 완료 기준이 테스트나 시연입니다.
>
> 이 단위는 비코드(문서, 절차 텍스트)라 완료 기준이 내용 완전성으로 도출됩니다. 같은 슬롯이라도 코드/비코드 kind 에 따라 완료 기준 형태가 갈림을 대비한 것입니다.

#### 4.z 설정 로드 배선 안내 절 (kind: workflow-step)

관련 섹션: [단위.loadConfig], [단위.defineSchema]

- 목적: 앱 개발자가 부팅 코드에 설정 로드를 어떻게 배선하는지 단계로 안내합니다.
- 인터페이스, 계약: 트리거는 신규 앱 부팅 코드 작성 시 이 절을 읽는 것입니다. 입력은 스키마 선언과 대상 환경, 출력은 따라 하면 동작하는 배선 절차이며, 소비자는 이 문서를 읽는 앱 개발자(사람)입니다.
- 동작, 내용: 스키마 선언 → 부팅 진입점에서 1회 호출 → 검증 실패 시 중단 처리 순서를 예시 코드와 함께 서술합니다.
- 경계, 예외:
  - 환경변수 미설정 시 동작을 절차에 명시합니다 (빠지면 독자가 런타임에서야 발견합니다).
  - 검증 실패 중단 처리를 절차에 포함합니다 (빠지면 독자가 부팅 실패를 못 다룹니다).
  - 비동기 소스는 범위 외임을 명시합니다 (오해를 예방합니다).
- 완료 기준:
  - 선언→호출→실패 처리 3단계가 빠짐없이 서술되고, 각 단계에 따라 할 예시가 있습니다.
  - 위 경계(환경변수 미설정, 검증 실패, 범위 외)가 문서에 언급됩니다.
  - 독자가 이 절만으로 배선을 완성할 수 있으면 충분합니다. (테스트가 아닌 내용 완전성 기준입니다.)
