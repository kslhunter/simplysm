# config-loader 개발 분석서 (예시)

> sd-spec §별 본문의 형식 모범. 실제 산출물은 spec bundle 로, 여기의 각 § 는 하위 page 로 분리된다(§1·§8·§9 는 루트 `spec.md`, §2~§7 은 각 page) — 이 파일은 그 page 본문의 형식 모범으로만 참조한다.
> 가상의 작은 라이브러리 — 환경별 설정을 파일 + 환경변수에서 병합해 로드. kind=api·infra 중심. 다른 kind(doc-section·workflow-step)도 같은 슬롯 세트를 따름.

## 1. 개요

### 1.1 핵심 목적

여러 소스(기본 파일·환경별 파일·환경변수)의 설정을 정해진 우선순위로 병합해 단일 설정 객체로 제공.

### 1.2 주요 목표

- 앱 부팅 시 1회 호출로 검증된 설정 객체 수령.
- 결측(미설정 키)을 임의 기본값으로 덮지 않고 그대로 전달.

### 1.3 소비자/이해관계자

- 이 라이브러리를 import 하는 앱(서버·CLI) 개발자.

### 1.4 환경/플랫폼

- Node.js 20+ · TypeScript. 브라우저 미지원(파일시스템 의존).

## 2. 사용 시나리오

### 2.1 부팅 시 설정 로드

관련 섹션: [단위.loadConfig], [단위.defineSchema], [타입.ConfigSchema]

흐름:

1. 앱이 스키마를 `defineSchema` 로 선언.
2. 부팅 진입점에서 `loadConfig(schema, options)` 1회 호출.
3. 병합·검증된 설정 객체 수령. 검증 실패 시 `ConfigError` throw 로 부팅 중단.

```ts
const schema = defineSchema({ port: "number", dbUrl: "string", debug: "boolean?" });
const config = loadConfig(schema, { env: "production" });
```

## 3. 기타 요구사항

### 3.1 결측 보존

- 요구 의도: 미설정 선택 키는 `undefined` 로 전달 — `""`·`0`·`false` 로 치환 금지. 소비자가 "미설정"과 "설정된 falsy 값"을 구분 가능해야 함.
- 관련 섹션: [단위.loadConfig], [타입.ConfigSchema]

### 3.2 동기 로드

- 요구 의도: 부팅 경로에서 쓰이므로 동기 API. 비동기 소스는 범위 외. (근거: 부팅 단순화 — 소비자 요청)

#### 4.1 loadConfig (kind: api)

관련 섹션: [단위.defineSchema], [단위.ConfigError], [단위.우선순위 병합 규칙], [외부 의존.파일시스템]

- 목적: 스키마 + 옵션을 받아 병합·검증된 설정 객체를 동기로 반환.
- 인터페이스·계약: `loadConfig(schema: Schema, options?: [타입.LoadOptions]): InferredConfig`. 반환은 스키마에서 추론된 타입 — 선택 키는 `T | undefined`. 검증 실패 시 [단위.ConfigError] throw.
- 동작·내용: [단위.우선순위 병합 규칙] 순서로 소스를 병합 → 스키마 타입 검증 → 결측 선택 키는 `undefined` 유지(§3.1).
- 경계·예외:
  - 필수 키 결측 → `ConfigError` throw (어느 키인지 메시지 포함).
  - 타입 불일치(예: `port` 가 비숫자) → `ConfigError`.
  - 설정 파일 부재 → 그 소스만 건너뜀(에러 아님), 다른 소스로 진행.
  - 파일 읽기 권한 오류 → throw([외부 의존.파일시스템] 예외 처리).
- 완료 기준: 위 각 경계 케이스(필수 결측·타입 불일치·파일 부재·권한 오류)와 정상 병합이 단위 테스트로 검증됨. 결측 선택 키가 `undefined` 로 보존됨을 단언.

#### 4.2 defineSchema (kind: api)

- 목적: 설정 스키마를 선언하고 추론 가능한 타입 핸들을 반환.
- 인터페이스·계약: `defineSchema(shape: [타입.SchemaShape]): Schema`. `"number"`·`"string"`·`"boolean"` 및 `?` 접미(선택) 지원.
- 동작·내용: shape 를 내부 검증기로 변환. 알 수 없는 타입 토큰은 선언 시점 throw.
- 경계·예외: 빈 shape → 허용(빈 설정). 미지원 타입 토큰 → `ConfigError`.
- 완료 기준: 지원 토큰·선택 접미·미지원 토큰 거부가 테스트로 검증됨.

#### 4.3 ConfigError (kind: api)

- 목적: 설정 로드·검증 실패를 나타내는 공개 에러 타입.
- 인터페이스·계약: `class ConfigError extends Error`. `key?: string`(문제 키), `reason: "missing" | "type" | "io"`.
- 동작·내용: throw 시 위 필드 채움. 메시지는 사람이 읽을 수 있는 한 줄.
- 경계·예외: 해당 없음 — 단순 값 객체.
- 완료 기준: 각 reason 별로 적절히 throw 됨이 [단위.loadConfig] 테스트에서 함께 검증됨.

#### 4.4 우선순위 병합 규칙 (kind: infra)

관련 섹션: [단위.loadConfig], [공통 정의.병합 우선순위]

- 목적: 여러 소스의 병합 우선순위를 한 곳에 고정.
- 인터페이스·계약: 외부 노출 없음 — [단위.loadConfig] 내부 규칙. 적용 범위 = 모든 로드.
- 동작·내용: 우선순위(높음→낮음): 환경변수 > 환경별 파일(`config.<env>.json`) > 기본 파일(`config.json`). 상위 소스의 키가 하위를 덮음. (근거: [공통 정의.병합 우선순위])
- 경계·예외: 같은 키가 여러 소스에 있으면 상위만 채택. 어느 소스에도 없으면 결측(§3.1).
- 완료 기준: 우선순위 덮어쓰기·결측 전파가 테스트로 검증됨.

## 5. 공통 정의

### 5.1 용어 사전

- **설정 소스**: 설정 키-값을 제공하는 출처 — 기본 파일·환경별 파일·환경변수.
- **병합 우선순위**: 같은 키가 여러 소스에 있을 때 채택 순서. 환경변수 > 환경별 파일 > 기본 파일.

### 5.2 환경변수 키 규약

- 환경변수는 `APP_` 접두 + 대문자 스네이크(예: `APP_DB_URL`). 스키마 키 `dbUrl` ↔ `APP_DB_URL` 매핑. [OPEN] 중첩 키 매핑 규칙 — 단일 레벨만 확인됨, 중첩 객체 매핑 미확인.

## 6. 핵심 타입·자료구조

### 6.1 [타입.ConfigSchema]

설계 자연 도출 — [단위.loadConfig]·[단위.defineSchema] 가 참조.

필드:

| 필드  | 타입                        | 필수 | 비고                                                                     |
| ----- | --------------------------- | ---- | ------------------------------------------------------------------------ |
| shape | `Record<string, TypeToken>` | 필수 | 키별 타입 토큰. `TypeToken` = `"number"｜"string"｜"boolean"`(+`?` 선택) |

제약: shape 키는 유일. 선택 키(`?`)는 추론 타입에서 `T｜undefined`.

### 6.2 [타입.LoadOptions]

필드:

| 필드 | 타입     | 필수 | 비고                                                                             |
| ---- | -------- | ---- | -------------------------------------------------------------------------------- |
| env  | `string` | 선택 | 환경 이름. 미지정 시 `process.env.NODE_ENV`, 그것도 없으면 환경별 파일 소스 생략 |
| dir  | `string` | 선택 | 설정 파일 디렉터리. 미지정 시 cwd                                                |

## 7. 외부 의존·인터페이스

### 7.1 [외부 의존.파일시스템]

설계 자연 도출 — [단위.loadConfig] 가 설정 파일을 동기 읽기.

관련 섹션: [단위.loadConfig]

- 대상: 로컬 파일시스템 (Node `fs`).
- 방향·성격: 읽기 (동기).
- 경유: `config.json` · `config.<env>.json` 경로.
- 예외 처리:
  - 파일 부재 → 해당 소스 생략(에러 아님).
  - 권한·IO 오류 → `ConfigError(reason: "io")` throw, 부팅 중단.

## 8. 결정 맥락

### 비동기 설정 소스 — 안 함

- 현재 결정: 동기 API 만. 비동기 소스(원격 설정 서버 등) 미지원.
- 근거: §3.2 동기 로드 요구 (부팅 단순화 — 소비자 요청).
- 검토 경계: 로컬 파일·환경변수만 검토. 원격·네트워크 소스는 논의 안 함 — 후속 LLM 이 "비동기가 낫지 않나" 재론하기 전에, 아무도 검토 안 한 영역임을 인지할 것.

- 후속 처리: 별도 spec.
- 근거: 현재 범위 아님.
- 자료 위치: 기획 메모 (가상).
