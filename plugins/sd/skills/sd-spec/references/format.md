# sd-spec §별 작성법 (§1~§7)

초안·init 배치와 부분 수정이 따르는 §별 작성법. 요건(§1·§2·§3)·공통(§5)·설계(§4·§6·§7) 작성법을 한 파일로 통합.

- **공유 형식**(섹션 구조·신뢰도 표기·본문 내 참조·산출 단위 슬롯·진행 방법)·**골격**·**§8** 은 `SKILL.md` 참조.
- **설계 입력**: 확정된 §1~3 + §5 를 입력으로 §4 를 도출하고, §4 가 참조한 타입·외부 의존에서 §6·§7 을 파생.
- §5 공통 정의는 요건·설계 양쪽에서 도출·편집되는 공통(공통 자연 도출). §6 핵심 타입·§7 외부 의존은 설계 산물(§4 파생).

## §1 개요

**작성 단위**: §1.1·§1.2·§1.3·§1.4.

**모범**: example.md §1.

### §1.1 핵심 목적

- 한 줄 동사형의 큰 단위로 작성 — 이 산출물이 무엇을 해결하는가.
- §2.x 의 시나리오 항목 나열 금지 (그 표현은 §1.2 의 역할).

### §1.2 주요 목표

- 단위: 소비자가 이 산출물로 달성하려는 목표 1건 (단위 단위가 아님).
- 표현: 한 줄. 소비자 관점 어휘 사용.
- §2 사용 시나리오 헤더와 1:1 매핑되는 것이 일반적.

### §1.3 소비자/이해관계자

- 이 산출물을 쓰는·읽는 주체를 역할로 일반화 (예: "라이브러리를 import 하는 앱 개발자", "이 매뉴얼을 읽는 신규 작업자", "이 skill 을 호출하는 에이전트").

### §1.4 환경/플랫폼

- 산출물이 동작·소비되는 환경 — 런타임·언어·플랫폼·버전 제약. 명시한 범위에 맞게 설계하며 그 외 환경 동작은 책임 범위 외.

## §2 사용 시나리오

소비자가 산출물을 쓰는 흐름. 산출물 종류에 따라 무게가 다름 — 라이브러리·CLI 는 호출 흐름이 핵심, 문서는 독자 동선이 얇을 수 있음(얇으면 짧게, 억지로 부풀리지 않음).

**작성 단위**: §2.x 1개당 위→아래:
1. 흐름 (소비자 관점 단계, 또는 대표 호출 예시).
2. 관련 섹션 한 줄.

**모범**: example.md §2.

### 분할 단위 = 소비자 목표 1건

- §2.x 1건 = 소비자가 한 번에 달성하는 목표 흐름 (진입~완료). §1.2 주요 목표와 1:1 대응이 일반적.
- 내부 단계 전환(여러 단위 호출·여러 절 참조)은 분리 사유 아님 — 한 흐름 안에 단계로 표현.

### 본문 구조

- **흐름**: 소비자 관점 단계를 한 줄씩, 또는 대표 호출/사용 예시(코드 펜스·명령·동선). 단위 내부 구현 디테일은 적지 않음 — 단위·타입은 이름으로만 참조.
- **관련 섹션**: "본문 내 참조" 절 룰 따름.

### 안티패턴

- ❌ 내부 함수 호출 순서·파일 구조를 시나리오로 적기 (그건 §4 단위·구현 소관).
- ❌ 코드 As-Is 구조 기준으로 시나리오를 쪼개기.

## §3 기타 요구사항

**작성 단위**: §3.x 1개당. 짧으면 한 단위로, 길면 "요구 의도" + "관련 섹션" 분리.

**모범**: example.md §3.

### 분할 단위 = 단일 비기능·제약 요구

- 산출물 전반에 걸리는 비기능 요구·제약 — 성능·호환성·에러 정책·보안·접근성·버전 정책 등.
- 산출물 전반 공통 룰(예: "모든 공개 API 는 결측을 null 로 보존")도 §3 에 포함 — 그 설계는 §4 단위·§5 공통 정의에서 풀이.

### 본문 구조

- 요구 의도 (한 줄 또는 한 문단).
- 관련 섹션 한 줄.
- 구현 디테일은 §4 본문에 작성.

## §4 산출 단위

본 스킬의 핵심. 산출물의 단위를 단일 슬롯 세트로 기술 — **부품 집합형**은 반복 부품(공개 API 심볼·문서 절·워크플로 단계·공통 기반 등), **자립 실행형**은 실행 슬라이스(분해 축은 아래 "설계 분할 절차").

**작성 단위**: §4.x 1개당 "산출 단위 슬롯"(SKILL.md) 순서로 위→아래. 신규·정정·골격 신설 동일.

**모범**: example.md §4 (kind 별 1건 이상).

### 설계 분할 절차

설계 단계에서 §4 단위를 §1~3·§5 에서 도출:

0. **분해 축 판정**: §1 핵심 목적·§1.4 환경으로 산출물 형태를 판정.
   - **부품 집합형** — 소비자가 개별 부품을 독립적으로 씀(라이브러리 심볼·CLI 명령·문서 절·LLM Skill 단계·프레임워크 위 화면). 조립은 소비자·프레임워크 몫. → **1a 구조 단위**.
   - **자립 실행형** — 산출물 자체가 하나의 실행물(앱·서비스·데몬 — 부품을 스스로 조립해야 실행됨). 소비자는 실행 결과를 씀. → **1b 실행 슬라이스**.

1a. **구조 단위 도출** (부품 집합형): §2 사용 시나리오가 닿는 표면 + §3 요구 → 그 표면을 이루는 단위(공개 API·문서 절·워크플로 단계·공통 기반)로 분해. 자료에서 식별된 단위만, 없는 단위 발명 금지.

1b. **실행 슬라이스 도출** (자립 실행형): §2 관통 흐름을 세로로 슬라이스.
    - **실행되는 최소 골격**(부팅~최소 end-to-end 한 흐름)을 첫 단위로, 그 위에 **기능 증분**을 얹음 — **각 단위 완료 시 산출물이 새 능력을 갖춘 채 여전히 실행**되어야 함(walking-skeleton).
    - 순수 뷰·계산·저장 등 **재사용 부품**은 구조 단위(1a)로 두고, 슬라이스가 그 부품에 상태·데이터를 주입해 조립(하이브리드). 부품은 빌드 하위(먼저), 슬라이스는 상위(뒤).
    - 분해 근거 = §2 관통 흐름. 없는 슬라이스 발명 금지.

2. **kind 판정**: 각 단위의 성격으로 `kind` 태그 부여(api/doc-section/workflow-step/infra/generic/…). 애매하면 generic.
3. **런타임 타입렌즈 적용**: 각 단위마다 *그 성격에 맞는 품질·예외 차원을 스스로 열거*해 "경계·예외" 슬롯을 채움. (종류별 체크리스트를 본 문서가 제공하지 않음 — 단위마다 도출.)
4. **§6·§7 파생 (점진 누적)**: 단위가 참조하는 `[타입.X]`·`[외부 의존.X]` 를 그 자리에서 §6·§7 에 즉시 추가·갱신. 끝나고 모으는 집계 단계 없음 — 누적이 곧 §6·§7 작성.

도출 근거가 없는 항목은 `[OPEN]`.

### 안티패턴 (분해)

- ❌ **자립 실행형인데 부품만 나열** — 조립·부팅·배선이 §4 에 안 나오거나 맨 끝 한 단위로 몰림(leaf-first: 부품을 다 만들어도 실행물이 마지막에서야 나옴). → 실행 슬라이스(1b), 골격 먼저.
- ❌ **부품 집합형인데 억지로 실행 슬라이스** — 라이브러리 심볼·문서 절을 "골격→증분"으로 쪼갬. → 구조 단위(1a).

### 단위 목록 표 (§4 첫머리)

3컬럼: `§ | 이름 | kind` + (선택) 한 줄 요약. 단위가 추가·제거되면 표도 갱신. 배열 — 부품 집합형은 같은 kind·도메인끼리 인접, **자립 실행형은 빌드 순서(재사용 부품 먼저 → 골격 → 증분)**.

### 단위 정의 (§4.x 표준 구조)

헤더에 kind 표기 유지: `#### N.N 단위명 (kind: api)`.

슬롯 작성 (SKILL.md "산출 단위 슬롯"):

- **목적**: 무엇을·왜 (한두 줄).
- **인터페이스·계약**: 소비 측이 닿는 표면 + 약속. 성격에 맞게 — api=시그니처·인자·반환·타입(`[타입.X]` 참조), doc-section=다룰 내용 개요·대상 독자, workflow-step=트리거·입력·출력·산출, infra=적용 범위·구성 시점. 구현 코드가 아니라 *계약*을 기술(추상 레벨 고정).
- **동작·내용**: 내부 규칙·로직·서술. 분기·계산식·경계 조건을 그대로 풀어씀(단순화 차단).
- **경계·예외**: 타입렌즈로 도출한 차원(api=결측·동시성·에러 계약·경계값, doc-section=오해 소지·선행지식 누락, workflow-step=실패·재시도·부분성공 등)을 누락 없이.
- **완료 기준**: 코드 kind = 검증 가능한 기준(이 단위가 맞다고 어떻게 아는가 — sd-impl TDD 입력). 비코드 kind = 내용 완전성 기준(이 절/단계가 충분하다고 보는 기준).
- 슬롯이 그 단위에 해당 없으면 비우지 말고 *왜 해당 없음인지* 한 줄(누락과 구분).

### 모달·교차 참조

- 한 단위가 다른 단위를 호출·재사용하면 새 단위를 만들지 말고 `[단위.X]` 로 참조. 호출 측 "동작·내용"에 "→ [단위.X] 사용" 명시.
- 양측(호출·피호출) 모두에 관련 섹션 자동 누적.

## §5 공통 정의

작성 중 자연스럽게 도출됨. 새 어휘·규격을 발견하면 추가.

**모범**: example.md §5.

- **§5.1 용어 사전**: 도메인·산출물 어휘·약어·의미 정의.
- **§5.2~ 기타 공통 규격**: 산출물 전반 규격(버전 규칙·네이밍 규약·공통 포맷 등).
- 특정 단위 본문에서만 쓰이는 규칙(그 단위 한정 변환·해석)은 §5 에 두지 않음 → 사용처 본문에 둠.

### 외부 자료 명세 (해당 시)

산출물이 소비하는 외부 정의 자료(외부 규격·표준 포맷·고정 스키마)는 자료별 표로 명세. 모든 필드를 1행 1정의(자료 자체의 객관 명세). 셀은 근거 있을 때만 — 추정 금지, 근거 없으면 `[OPEN]`. "원본 참조"로 본문 정의 대체 금지.

## §6 핵심 타입·자료구조

**분류**: 설계 자연 도출 — §4 단위가 참조한 타입·자료구조에서 파생. **§4 어디서도 참조 안 되는 타입은 만들지 않음**(§4 종속).

**모범**: example.md §6.

- 섹션 구조: `필드/멤버:` 표 + `제약:` 불릿.
- 필드 표 컬럼: `필드 | 타입 | 필수 | 비고`.
  - 비고에는 **그 필드가 무엇인지**(형식·값 범위·의미·제약·예시)만. 용도·매핑은 §4 단위 본문에서.
  - **결측 보존**: 값 없음이 가능한 필드는 nullable 로 명시 — 기본값 치환으로 결측을 숨기지 않음.
- 제약: 불변식·관계·유일성 등.

## §7 외부 의존·인터페이스

**분류**: 설계 자연 도출 — §4 단위가 호출·의존하는 외부(외부 시스템·플랫폼 API·외부 패키지·파일시스템·네트워크)에서 파생. **§4 이 참조 안 하는 외부 의존은 만들지 않음**(§4 종속).

**모범**: example.md §7.

### 정의

- 포함: 상대 시스템 고유 인터페이스, 외부 패키지·플랫폼 API 의존, 파일시스템·네트워크 등 외부 부수효과 경계.
- 디테일 범위: 도메인 약속·계약 레벨까지만. 구체 endpoint·메서드 시그니처·SDK 호출 디테일은 구현 단계.

### 본문 구조

- **기본 정보** (라벨 bullet): `대상: <외부 시스템/패키지/리소스>` · `방향·성격: <호출/수신/읽기/쓰기 등>` · `경유: <방식>`.
- **자료 매핑** (해당 시): 외부 필드 ↔ 본 산출물 출처 표.
- **예외 처리**: 실패 케이스별 위험·대처·재시도 한계.
- **관련 섹션**: "본문 내 참조" 절 룰 따름.
