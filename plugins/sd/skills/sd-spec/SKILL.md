# sd-spec

임의의 개발 산출물(라이브러리, CLI, 앱, 화면, 문서, LLM Skill 등 SI/업무시스템 외 전부)의 요구를 분석해 spec bundle 을 산출합니다. 목적은 정확한 spec 이며, 환각과 누락을 차단합니다.

본문 형식은 [references/example.md](references/example.md) 가 유일한 모범이고, 슬롯 정의와 판단 규칙은 이 문서입니다.

- 작성 전에 대상 § 의 예시를 열어 직접 대조하세요. 이 파일은 예시로 알 수 없는 것만 규정합니다.
- example.md 는 단일 파일 표현이라 각 § 가 bundle 에서는 page 로 분리됩니다. `#### N.N` 헤더를 그대로 복사하지 말고 `# [카테고리.이름] …` 로 변환하세요.

SI 와의 경계: 업무 프로세스, 화면, 도메인 모델 중심의 SI/업무시스템은 sd-spec-si 소관입니다. 입력이 명백히 SI 면 그쪽으로 안내하세요.

## 산출물

위치는 `.specs/{title}/spec.md` 와 그 하위 page 입니다. `{title}` 은 사용자와 합의한 산출물명입니다.

```text
.specs/{title}/
  spec.md                  루트 — §1 개요, 인덱스, §8 결정 맥락, §9 작업 메모만. 본문 복제 금지
  requirements/scenarios/  requirements/others/
  design/units/
  common/definitions.md
  types/  interfaces/
```

| §   | 섹션                  | 본문 위치                       | 루트 인덱스 컬럼                              |
| --- | --------------------- | ------------------------------- | --------------------------------------------- |
| §1  | 개요                  | 루트 (목적, 목표, 소비자, 환경) | (인덱스 없음)                                 |
| §2  | 사용 시나리오         | `requirements/scenarios/*.md`   | `ref \| 제목 \| 파일 \| 요약`                 |
| §3  | 기타 요구사항         | `requirements/others/*.md`      | `ref \| 제목 \| 파일 \| 요약`                 |
| §4  | 산출 단위 (핵심)      | `design/units/*.md`             | `ref \| 이름 \| kind \| 파일 \| 요약 \| 구현` |
| §5  | 공통 정의             | `common/definitions.md`         | 링크 1줄 (단일 컨테이너 page)                 |
| §6  | 핵심 타입, 자료구조   | `types/*.md`                    | `ref \| 타입 \| 파일 \| 요약`                 |
| §7  | 외부 의존, 인터페이스 | `interfaces/*.md`               | `ref \| 대상 \| 방향, 성격 \| 파일 \| 요약`   |
| §8  | 결정 맥락             | 루트                            | (메타)                                        |
| §9  | 작업 메모             | 루트                            | (메타)                                        |

- page 참조는 § 번호가 아니라 `[카테고리.이름]` 만 쓰세요. § 번호는 분석 중 자주 바뀝니다.
  - 예: `[단위.토큰 파서]`, `[타입.설정 객체]`, `[외부 의존.파일시스템]`, `[시나리오.첫 실행 설정]`, `[기타 요구.undefined 보존]`, `[공통 정의.버전 규칙]`.
- §2, §3, §4, §7 본문은 sub-section 제목 직후 첫 줄에 `관련 섹션: [카테고리.이름], …` 을 두세요 (다른 슬롯을 쓰다 자동 누적됩니다. 없으면 줄 자체를 생략합니다).
- 신뢰도 표기 — 자료에서 해석, 도출한 비자명 항목에만 줄끝 `(근거: 출처)` 를 답니다.
  - 근거 없으면 `[OPEN]` 입니다.
  - `[구현]` 은 루트 §4 인덱스 `구현` 컬럼에만 쓰고 page 헤더에는 쓰지 마세요.
- 같은 분류에 동일 제목 파일이 있으면 새로 만들지 말고 기존 page 재진입으로 보세요.

## 산출 단위 (§4)

본 스킬의 핵심입니다. 산출물 종류와 무관하게 단일 슬롯 세트로 기술하고, 차이는 `kind` 태그와 런타임 타입렌즈로 흡수합니다.

```
# [단위.단위명] 단위명 (kind: <성격 한 단어>)
관련 섹션: …
- 목적:                 무엇을, 왜 (한두 줄)
- 인터페이스, 계약:      소비 측이 닿는 표면 + 약속. 구현이 아니라 계약을 기술할 것
- 동작, 내용:            내부 규칙, 로직. 분기, 계산식, 경계를 그대로 풀어쓸 것
- 경계, 예외:            아래 런타임 타입렌즈로 도출한 차원
- 완료 기준:            코드 kind = 검증 가능한 기준(sd-impl TDD 입력) / 비코드 kind = 내용 완전성 기준
```

- 슬롯이 해당 없으면 비우지 말고 왜 해당 없음인지 한 줄 적으세요 (누락과 구분).
- `kind` 는 서술 태그입니다. 애매하면 `generic` 입니다.
  - `api`, `cli`, `doc-section`, `workflow-step`, `screen`, `job`, `infra`, `generic` 등 무엇이든 쓰고, 새 성격이면 자유롭게 적으세요.
- 코드 kind 와 비코드 kind 는 산출물이 실행 코드인지 텍스트(문서, 프롬프트)인지로 갈립니다. 완료 기준 형태와 `[구현]` 판정이 이 구분을 따릅니다.

## 런타임 타입렌즈 (성격 기반 차원 도출)

"경계, 예외" 슬롯을 저장된 체크리스트가 아니라 그 단위의 성격에서 도출한 차원으로 채우세요.

- 종류별 체크리스트를 본 문서에 두지 않는 것이 핵심입니다.
- 화면, CLI, 파이프라인, 문서 무엇이 와도 그 자리서 도출합니다.

1. 성격 서술 먼저 (예시 보기 전) — 이 단위의 유형, 소비자, 입력, 출력, 상태, 부작용, 실패 지점을 한 줄로 서술하세요. 차원을 example 이나 다른 단위에서 베끼지 마세요 (앵커링 차단).
2. 네 축으로 차원 생성 — 축만 고정이고, 구체 차원은 성격에서 도출해야 합니다:
   - 품질 (무엇을 볼까) — ISO/IEC 25010 9특성(기능적합, 성능효율, 호환, 상호작용, 신뢰, 보안, 유지보수, 유연, 안전) 중 실제로 걸리는 것만 봅니다.
     순수 계산 함수는 기능적합, 신뢰 위주이고, 사람 대상 화면은 상호작용, 안전이 더해집니다.
   - 실패 (어떻게 깨질까) — 각 입력, 출력, 부작용에 가이드워드를 곱해 이탈을 열거하세요.
     가이드워드: 없음, 과다, 과소, 부분, 부가(의도 외 부작용), 역전, 치환(엉뚱한 대상/형식), 간헐, 타이밍/순서(조기, 지연, 순서역전).
   - 계약 — 전제(호출자가 지킬 것), 후행(단위가 보장할 것), 불변식(항상 성립)입니다. 각 위반이 예외 차원입니다.
   - 경계 — 동작이 갈리는 입력, 상태 축을 유효/무효로 분할하세요. 순서 관계가 있으면 경계값(min, min±1, max, max±1), 그리고 0/1/N, 빈값, null, 시간 처음/끝을 봅니다.
3. 성격 근거 + 반앵커링 — 각 차원에 "이 단위 성격상 왜 필요한가"를 한 줄 적으세요. 익숙한 종류(특히 `api`) 관성에서 나온 무관 차원은 제거하고, 이 단위 고유 차원은 추가합니다.
4. 차원별 국소 점검 — 각 차원을 spec 에 대고 위치, 결함을 지목하세요.
   - "전반적 개선"이나 근거 없는 "맞나?" 식 재검토를 하지 마세요.
   - 반드시 차원(외부 기준)에 걸어 점검해야 합니다.

위 축, 특성 목록은 차원을 빠짐없이 도출하기 위한 발상 격자이지 채워야 할 슬롯이 아닙니다. 해당 없는 축은 건너뛰세요.

도출한 차원이 요청, 자료에 없는 새 요구를 만들면 spec 에 쓰지 말고 `논의`하세요. 타입렌즈는 이미 있는 요구의 경계를 드러내는 도구이지 요구를 늘리는 도구가 아닙니다.

## 절차

1. 준비 — 산출물명을 합의하세요.
   - `.specs/{title}/` 이 이미 있으면 재진입인지 확인합니다.
   - 골격(루트 + `common/definitions.md`)을 생성하고, 자료는 직접 읽으세요.
2. 요건 (§1-3 + §5) — §1 개요는 루트에, §2 사용 시나리오, §3 기타 요구는 page 로 작성하고 인덱스를 갱신하세요.
   - 어휘, 공통 규격은 `common/definitions.md` 에 누적합니다.
   - §4, §6, §7 은 아직 만들지 마세요.
3. 설계 (§4 + §6, §7 파생) — §1-3, §5 를 입력으로 §4 단위를 하나씩 순차로 작성하고 루트 인덱스를 즉시 갱신하세요.
   - 각 단위마다 런타임 타입렌즈를 적용합니다.
   - 그 단위가 참조하는 `[타입.X]`, `[외부 의존.X]` 를 그 자리에서 §6, §7 에 추가, 갱신해야 합니다. 끝에 몰아서 모으는 단계는 없습니다.
4. 검증 — 독립 서브에이전트(`subagent_type: sd:sd-verify`)로 검증해야 합니다.
   - 검증 축은 근거 좌표 실재 대조와 원자료↔spec 누락 역대조입니다.
   - 위조로 보고된 근거는 `(근거: …)` 를 떼고 `[OPEN]` 으로 강등하세요 (원 좌표는 `(원 좌표: …)` 로 병기 보존).
5. 보고 후 정지 — 요약 + `[OPEN]` 목록(파급 큰 것 먼저) + 검증 결과 + 미반영 자료를 채팅으로 제시하고 멈추세요.
   - 후속 수정으로 자동 진입하지 마세요.

### 자료가 기존 산출물일 때 (`/sd-spec init [범위]`)

절차는 동일하고 자료만 기존 산출물(코드, 문서, 기존 skill)입니다.
범위가 안 오면 사용자와 합의하고, 조사는 워킹트리 파일 직접 읽기, 검색으로만 하세요.
추가로:

- 산출물이 결정 근거입니다. export 표면, 라우트, 화면 트리, CLI 명령, 문서 목차, skill 흐름에서 시나리오와 단위를 역추론하되, 산출물에 없는 동작을 쓰지 마세요.
  - 역추론 항목은 비자명 취급이라 `(근거: <파일 경로[:라인]>)` 를 부착합니다.
  - 추론 한계(의도, 왜)는 `[OPEN]` 입니다.
- 산출물의 단위 전수 목록과 §4 목록을 역대조해 단위 자체가 빠진 누락을 찾으세요. 누락이면 설계로 회귀해 추가하고 재대조합니다.
- 단위마다 산출물과 대조해 차이가 0건이면 루트 §4 인덱스에 `[구현]` 을 표기하세요 (기존 산출물은 동작하는 것으로 간주하므로 테스트, 시연이 불필요합니다).
  - 대조는 독립 서브에이전트로 단위별 병렬 실행하세요.
  - "확인 불가" 항목이나 `[OPEN]` 이 남은 단위는 마킹을 보류하세요.
- 차이는 전부 spec 수정으로 해소합니다.
  - 산출물 위반이면 문서를 산출물에 맞추세요.
  - spec 내부 모순이면 산출물 기준으로 정정하세요.
  - spec 미정의 + 산출물 존재면 산출물 동작을 추가하세요.

### 재진입, 부분 수정

기존 bundle 에 대한 모든 지시는 규모와 무관하게 이 경로입니다.

- 루트 인덱스에서 대상 page 를 찾아 읽고, 그 본문이 `[카테고리.이름]` 으로 가리키는 page 를 재귀적으로 읽어야 합니다. 루트 §8, §9 도 읽으세요.
- 구조 변경 시 `[카테고리.이름]` 참조를 전수 검색해 끊기는 참조를 함께 갱신해야 합니다.
  - 단위 삭제, 분할로 그 단위만 참조하던 §6, §7 항목이 고아가 되면 함께 제거하세요 (다른 단위도 참조하면 유지합니다).

## 작성 원칙

- 대화로 확정하며 씁니다. 사용자만 답할 수 있는 지점에서 멈춰 합의하고, 합의분을 그 자리서 반영한 뒤 다음으로 넘어가세요.
  - 구현 수준(파일 배치, 내부 자료구조, 사용할 라이브러리 API, 네이밍)은 sd-impl 소관이라 묻지 마세요.
  - `init` 경로만 예외입니다. 실행 중 묻지 말고 `[OPEN]` 으로 남겨 사후 정정하세요. 단 제목, 폴더 판단은 그 자리서 확인해야 합니다.
- 모르면 `[OPEN]` 입니다.
  - 질문에 딸려온 답변을 능동 결정으로 확정하지 마세요.
  - `[OPEN]` 은 사용자가 답을 유보한 것과 `init` 경로에만 남습니다.
  - `[OPEN]` 이 하나라도 남으면 미완성이므로 검토 패키지에서 전수 보고해야 합니다.
- 추상 레벨을 고정하세요. spec 은 _무엇을, 왜_(요구, 계약) 수준에 머뭅니다.
  - _어떻게_(구현 코드, 내부 자료구조 선택)로 조기에 점프하지 마세요.
  - 단 산출 단위의 인터페이스, 계약 자체는 요구 수준이므로 정확히 기술해야 합니다.
- 단순화를 차단해야 합니다. 계약, 분기, 경계를 그대로 풀어쓰세요.
  - 방어 처리(NULL 강제, 0 클램프, 분기 생략)로 임의 변형하지 마세요.
  - 정확한 풀이 부담이 크면 단순화안을 `[OPEN]` 으로 표기하거나 검토 패키지에서 보고하세요.
- 단일 출처를 지켜야 합니다. canonical(§6 타입, §7 외부 의존, §5 공통 정의)의 정의 내용을 §4 단위 본문에 복제하지 마세요.
  - 이름 참조만 쓰고 단위 본문엔 용도, 매핑, 적용만 둡니다.
  - canonical 을 고칠 때는 그것을 참조하는 단위를 역방향 전수 검색해 인라인 복제가 남았는지 훑고, 복제분은 canonical 로 통합한 뒤 이름 참조로 대체하세요.
- 파생은 종속물입니다. §4 어디서도 참조되지 않는 §6 타입, §7 외부 의존은 만들지 마세요.
- 내용물은 직접 도출해야 합니다. 다른 page 나 example 에서 가져올 것은 형식뿐입니다.

## 판단 규칙

- §4 분해 축 — 먼저 산출물 형태를 판정하세요.
  - 부품 집합형이면 §2 가 닿는 표면을 이루는 구조 단위로 분해하고, 같은 kind, 도메인끼리 인접 배치합니다.
    - 부품 집합형: 소비자가 개별 부품을 독립적으로 씀 — 라이브러리 심볼, CLI 명령, 문서 절, skill 단계, 프레임워크 위 화면. 조립은 소비자 몫.
  - 자립 실행형 (산출물 자체가 하나의 실행물 — 앱, 서비스, 데몬)이면 §2 관통 흐름을 세로로 실행 슬라이스 하세요.
    - 실행되는 최소 골격(부팅→최소 end-to-end)을 첫 단위로 하고 그 위에 기능 증분을 얹어, 각 단위 완료 시 산출물이 새 능력을 갖춘 채 여전히 실행되게 해야 합니다(walking-skeleton).
    - 순수 뷰, 계산, 저장 등 재사용 부품은 구조 단위로 두고 슬라이스가 조립하게 하세요. 배열은 빌드 순서(부품 → 골격 → 증분)를 따릅니다.
  - 자료에서 식별된 단위만 쓰세요. 없는 단위를 발명하지 마세요.
  - 안티패턴은 둘입니다.
    - 자립 실행형인데 부품만 나열해 조립, 부팅이 맨 끝 한 단위로 몰리는 것(leaf-first).
    - 부품 집합형인데 라이브러리 심볼, 문서 절을 억지로 "골격→증분"으로 쪼개는 것.
- 실행 경계 — 한 단위는 **따로 실행, 배포되는 자리**를 가로지르지 않습니다. 서버 프로세스, 브라우저 번들, 단말, CLI 프로세스가 각각 다른 자리입니다.
  - 판정: 완료 기준을 한 자리에서 전부 검증할 수 있는가. 두 자리가 필요하면 두 단위입니다.
  - 이름이 같은 개념이어도 자리가 다르면 별개 단위입니다.
  - 예외: 반대편이 응답을 받아 쓰기만 하고 자기 동작(주기, 수명, 상태 관리)이 없으면 한 단위입니다. 계약을 정의하는 쪽이 본체입니다.
  - 본문에 "A용과 B용으로 나뉩니다" 를 쓰게 됐다면 이미 두 단위입니다. 그 문장을 분할 신호로 읽으세요.
- §2 분할 — §2.x 1건은 소비자가 한 번에 달성하는 목표 흐름(진입→완료)입니다.
  - §1.2 주요 목표와 1:1 이 일반적입니다.
  - 내부 단계 전환(여러 단위 호출)은 분리 사유가 아니라 한 흐름 안의 단계입니다.
  - 내부 함수 호출 순서나 파일 구조를 시나리오로 적지 마세요.
- §3 vs §5 — 산출물 전반에 걸리는 비기능, 제약 요구는 §3, 그 규격, 어휘 정의는 §5 입니다.
  - 특정 단위에서만 쓰이는 규칙은 §5 가 아니라 사용처 본문에 두세요.
- 의존 방향 — 단위 간 참조는 비순환이며 한 방향입니다.
  - 기반(먼저 빌드 — 재사용 부품, 골격)이 상위(나중 빌드 — 증분)를 참조하면 역전입니다.
  - 상위를 통째로 참조하지 말고 공통 부분을 별도 기반 단위로 추출해 양쪽이 참조하게 하세요.
  - 한 단위가 다른 단위를 쓰면 새 단위를 만들지 말고 `[단위.X]` 로 참조하고, 호출 측 "동작, 내용"에 `→ [단위.X] 사용` 을 명시하세요.
- `[구현]` 제거 — §4 단위나 그 의존(관련 섹션의 참조, 본문의 `[타입.X]`, `[공통 정의.X]`)을 고쳤을 때 판정합니다.
  - 구현(코드 kind 는 코드, 비코드 kind 는 산출물 텍스트)을 새로 만들거나 고쳐야 하면 제거하고, 문구, 참조 정리면 유지하세요.
  - 부착은 sd-impl, init 소관입니다.
