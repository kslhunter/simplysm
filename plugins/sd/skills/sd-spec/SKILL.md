# sd-spec

임의의 개발 산출물(라이브러리·API·문서·LLM Skill·기타) 요구를 분석해 spec.md 1개로 산출. 최우선 목적 = 정확한 spec (환각 차단·누락 차단). 연산 단위로 채워나감 — 호출 1회 = 연산 1개, spec.md 라는 영속 산출물에 대한 연산의 모음.

**SI 와의 경계**: SI/업무시스템(업무 프로세스·화면·도메인 모델 중심)은 sd-spec-si 소관. 본 스킬은 그 외 개발 산출물 — 산출물의 **산출 단위**(공개 API 심볼·문서 절·워크플로 단계 등)가 분석 중심. 입력이 명백히 SI 업무시스템이면 sd-spec-si 로 안내.

## 입출력

- **Input**: 산출물 요구를 알 수 있는 자료(기획 메모·이슈·레퍼런스·구두 설명 등 비정형 포함) + 사용자와의 대화 + (재진입 시) 기존 spec.md. init 배치는 자료 = 기존 산출물(코드·문서·기존 skill).
- **Output**: spec.md 1개. 코드 산출 단위의 후속 구현 계약은 sd-impl, 문서·skill 등 비코드 산출 단위는 작성 단계의 입력.
- **폴더**: `.specs/{yyMMddHHmmss}_{slug}/`.
  - `yyMMddHHmmss`: 현재 시각을 이 형식으로 생성 (예: `260513204500` = 2026-05-13 20:45:00; PowerShell `Get-Date -Format "yyMMddHHmmss"`, bash `date +%y%m%d%H%M%S` 등).
  - `slug`: 짧은 한·두 단어. 허용 문자는 한글·영문·`_`·`-`·공백 (그 외 문자는 금지).

## 산출 단위와 kind

본 스킬의 핵심 = **산출 단위**(§4). 산출물 종류 무관하게 **단일 슬롯 세트**로 기술하고, 각 단위는 성격을 나타내는 `kind` 태그를 가짐.

**kind 는 서술 태그** — 스킬에 종류별 지침을 저장하지 않음. 흔한 값: `api`(함수·클래스·컴포넌트·디렉티브·CLI 명령·공개 타입)·`doc-section`(문서 장/절)·`workflow-step`(절차·LLM Skill 단계)·`infra`(공통·기반·부트스트랩)·`generic`(그 외). 새 성격이면 자유롭게 적음.

**런타임 타입렌즈** — 종류별 완전성은 메타지시로 처리: 각 단위 작성·검증 시 *그 단위의 성격을 추론 → 그 성격에 맞는 품질·예외 차원을 스스로 열거 → 각 차원을 점검*. (예: `api`면 nullable·동시성·에러 계약, `doc-section`이면 대상 독자·선행지식, `workflow-step`이면 트리거·실패 처리 등을 *그 자리에서 도출해* 점검.) 종류별 체크리스트를 본 문서에 박지 않음.

## 연산

sd-spec 은 3종의 연산으로 동작. 사용자 지시를 받으면 아래 디스패치로 분기. 작성은 배치로 한 번에 하고, 사용자가 사후 검토(검토 패키지)로 정정.

### 디스패치

| 지시 유형 | 연산 | 처리 경로 |
| --------- | ---- | --------- |
| "분석해줘"·"요구사항 분석"·"초안 작성"·"spec 작성" 류 (신규 spec.md 작성) | 초안 배치 | 메인 에이전트가 직접 순차 수행 (아래 "초안 배치") |
| arg `init` (`/sd-spec init [범위]`) — 기존 산출물(코드·문서·skill)을 근거로 신규 spec.md 역작성 | init 배치 | 메인 에이전트가 직접 순차 수행 (아래 "init 배치") |
| 그 외 모든 지시 ("X를 Y로"·"A를 B와 합쳐"·"이 섹션 이상해"·"설계만 다시"·재진입 정정) | 부분 수정 | SKILL.md 인라인 처리 (아래 "부분 수정") |

- 초안 배치·init 배치는 메인 에이전트가 자율 진행. 실행 중 사용자에게 묻지 않음 (모르면 `[OPEN]`) — 즉시 확인이 필요한 모호점도 배치 중에는 `[OPEN]` + 검토 패키지 보고로 대체 (부분 수정 등 대화형 연산에서는 즉시 확인).
- 초안 배치·init 배치는 **신규 spec.md 작성 전용**. 기존 spec.md 가 있는 재진입(부분 재작업·정정·"설계만 다시")은 모두 부분 수정 경로.
- arg `init` 없이 "기존 코드/문서 기반 spec 작성"·"현황 spec 화" 류 발화만 온 경우: init 배치 의도로 추정하되 **진입 전 사용자 확인 필수** — 확인 없이 init 배치 진입 금지.

### 초안 배치 (메인 직접 순차 수행)

신규 spec.md 작성 지시. 메인 에이전트가 spec.md 를 **한 줄기로 순차 빌드**함 (앞 단위가 만든 §5·§6·§7 을 뒤 단위가 재사용·확장). 작성은 전부 메인 직접, **검증만 독립 서브에이전트**.

**준비**:

- 폴더·경로: "입출력" 의 폴더 규칙으로 신규 `.specs/{yyMMddHHmmss}_{slug}/spec.md` 경로를 만들고, "spec.md 골격" 으로 골격(§1~§8 빈 헤더)을 작성.
- 산출물명: 사용자와 합의한 이름(제목 `{name}`). 날짜: 현재 날짜를 `yyyy-MM-dd` 로 (§8 로그 타임스탬프용). 자료는 직접 읽음.

**단계 (직렬 — 각 단계는 그 시점에 확정된 것만 다룸)**:

1. **요건 (§1~3 + §5)**: `references/format.md` 의 요건·공통 작성법을 읽음. 자료를 직접 읽어 §1 개요·§2 사용 시나리오·§3 기타 요구를 작성. 작성 중 나오는 어휘·공통 규격은 §5 에 누적. **§4·§6·§7 은 빈 헤더로 두고 손대지 않음** (설계 단계 이전). 비자명 항목엔 근거, 모르면 `[OPEN]`.

2. **설계 (§4 산출 단위 순차 빌드 + §6·§7·§5 점진 누적)**: `references/format.md` 의 설계 작성법을 읽음. §1~3·§5 를 입력으로 §4 산출 단위를 **하나씩 순차로** 작성. 각 단위는 단일 슬롯 세트(아래 "산출 단위 슬롯") + `kind` 태그로 기술하고, **런타임 타입렌즈**로 그 성격의 품질·예외 차원을 도출해 채움. 단위가 참조하는 §6 핵심 타입·§7 외부 의존을 **그 자리에서 즉시 추가·갱신**, 새 용어는 §5 에 누적. §4 첫머리 단위 목록 표도 단위가 늘 때마다 갱신. 별도 "집계" 단계 없음 — 누적이 곧 §6·§7 작성.

3. **검증 (독립 서브에이전트, 규모 비례)**: 작성 완료 spec 을, 작성한 메인이 아닌 **독립 서브에이전트로 검증**(자기검증 편향 차단). 검증 항목 — ① 근거 좌표 1:1 실재 대조(원자료 재독), ② 원자료↔spec 전수 누락 역대조 + 자료 커버리지, ③ 요구 커버리지(요건 → §4 역대조), ④ dangling 참조 검색. 규모에 비례해 병렬로 펼치되, 대상이 아주 작으면 메인 직접도 허용. 근거 위조로 판정된 항목은 `(근거: …)` 를 떼고 `[OPEN]` 으로 강등(원 좌표는 메모로 보존).

4. **검토 패키지 + 정지**: "연산 사이 검토" 의 검토 패키지를 제시하고 정지.

### init 배치 (산출물-first 역작성)

기존 산출물(코드·문서·기존 skill)을 자료로 삼아 신규 spec.md 를 역작성하고, §4 각 단위를 산출물과 대조 검증 후 `[구현]` 마킹. 산출물이 결정 근거 — 대조 차이는 전부 spec 수정으로 해소.

**범위**: `init` 뒤에 범위(패키지·경로·파일)가 오면 그 범위로 한정, 없으면 사용자와 범위 합의. 조사는 워킹트리 파일을 직접 읽기·검색으로만 수행.

**준비**: 초안 배치 준비와 동일. 자료 = 분석 범위의 기존 산출물.

**단계 (직렬)**:

1. **요건 (§1~3 + §5)**: 초안 배치 1단계와 동일하되 자료 = 기존 산출물. export 표면·문서 목차·skill 흐름에서 사용 시나리오를 역추론해 작성. 역추론 항목은 비자명 취급 — `(근거: <파일 경로[:라인]>)` 부착, 추론 한계(의도·왜)는 `[OPEN]`.

2. **설계 (§4 + §6·§7·§5)**: 초안 배치 2단계와 동일하되, 단위·슬롯·동작을 산출물에서 직접 도출. 산출물에 없는 동작 작성 금지. 각 단위의 `kind` 는 산출물 성격에서 판정.

3. **전수 커버리지 역대조 (독립 서브에이전트)**: 산출물의 단위 전수 목록(공개 export·문서 절·skill 단계 등) ↔ §4 단위 목록을 역대조 — spec 에 단위 자체가 없는 누락 발견. 누락 발견 시 2단계로 회귀해 단위 추가 후 재대조.

4. **단위 검토 + `[구현]` 마킹**: §4 단위마다 검토 서브에이전트 1개를 병렬 실행. 서브에이전트는 **보고 전용** — spec.md 를 수정하지 않음. prompt 는 아래 "단위 검토 서브에이전트 prompt".
   - 보고 처리 (메인이 일괄 편집 — 차이는 전부 spec 수정으로 해소):
     - (a) 산출물 위반 → spec 작성 오류. 문서를 산출물에 맞게 수정.
     - (b) spec 내부 모순 → 산출물 기준으로 정정.
     - (c) spec 미정의 + 산출물 채움 → 산출물 동작을 spec 에 추가.
   - 수정한 단위만 재대조 서브에이전트 재실행. **차이 0건 단위의 헤더에 `[구현]` 부착** (기존 산출물은 동작하는 것으로 간주 — 테스트·시연 불요). 산출물로 확인 불가한 `[OPEN]` 항목이 남은 단위는 마킹 보류.

5. **검증 (독립 서브에이전트)**: ① 근거 좌표(파일 경로·라인) 실재 대조, ② dangling 참조 검색. (누락 역대조는 3단계가 수행, 요구 커버리지는 §1~3 자체가 §4 역추론이므로 생략.)

6. **검토 패키지 + 정지**: "연산 사이 검토" 동일.

#### 단위 검토 서브에이전트 prompt

아래를 그대로 복사 후 `<…>` 만 채움:

````
sd-spec init 배치의 spec ↔ 산출물 단위 대조를 수행해줘.

**대상**:
- spec.md 경로: <절대경로>
- 단위 식별자: <§4.x>
- 산출물 분석 범위: <경로 목록 또는 "전체">

**작업**:

1. spec.md 의 §<단위> 본문 + 그 본문이 참조하는 §5/§6/§7 항목을 읽기.
2. 분석 범위에서 해당 단위에 대응하는 산출물(코드·문서 절·skill 단계 등)을 직접 검색해 찾아 모두 읽기.
3. spec ↔ 산출물을 항목(슬롯·동작·분기·계약) 단위로 1:1 대조.
4. 차이 발견 시 아래 3분류로 보고:

   - (a) **산출물 위반**: spec 에 적혔는데 산출물에 없거나 다름.
   - (b) **spec 내부 모순**: §A 정의 vs §B 정의 충돌. (양쪽 인용 명시)
   - (c) **spec 미정의 + 산출물 존재**: 산출물 동작인데 spec 본문에 정의·분기·경계 케이스 명시 없음.

5. 보고 형식 (각 차이 1건마다):

   ### 차이 N: <쉬운 어휘로 표현된 한줄 요약>
   - 분류: (a) / (b) / (c)
   - spec 위치: §X.x line Y
   - spec 인용: "..."
   - 산출물 위치: <file:line>
   - 산출물 동작: <쉬운 어휘로>

6. 산출물로 존재·동작을 확인할 수 없는 spec 항목은 "확인 불가" 로 별도 목록 보고.
7. 차이 0건 + 확인 불가 0건이면 `차이 없음, 검증 통과` 1줄만 응답.

**제약**:

- 파일 수정 금지 — 보고 전용.
- 보고 본문에 내부 식별자(변수명·함수명·타입 키워드 등) 노출 금지. 기능·동작 어휘로 풀어 쓸 것. 단 공개 계약(공개 함수명·CLI 옵션명 등)은 그대로 인용 가능.
````

### 부분 수정 (인라인)

초안 배치·init 배치(신규 spec.md 작성) 외의 모든 지시는 SKILL.md 가 메인 에이전트로 직접 처리. 재진입(기존 spec.md 에 대한 추가 작업 — "설계만 다시"·재설계 포함)도 이 경로.

**입력 spec.md 읽기 범위**: 부분 수정 착수 전 ① 수정 대상 § 본문 → ② 그 본문이 이름 기반 참조(`[단위.X]`·`[타입.X]`·`[공통 정의.X]` 등)로 가리키는 § 를 재귀적으로(참조의 참조까지) → ③ §8 본문 외 확정 사항 전체 를 읽음. 다른 세션이 누적한 결정·제약은 전역이면 §8·단위 한정이면 그 단위의 진행방법 NOTE 나 인라인 `[OPEN]` 에 모이도록 형식이 규정함. 부분 검색·부분 읽기로 대상 § 만 보고 §8·참조 § 를 빠뜨리지 않음.

- **정밀 지시** ("§4.2 의 X 슬롯을 Y로", "이 항목 `[OPEN]` 으로") → 바로 편집. 무관 섹션은 건드리지 않음 (일괄 치환 금지 — 편집 대상을 유일하게 좁혀서 수정).
- **모호 지적** ("이 섹션 이상해", "여기 흐름이 안 맞아") → 무엇이 문제인지 진단을 먼저 제시 → 사용자 합의 → 편집. 추측으로 바로 고치지 않음.
- **구조 변경** (병합·분할·추가) → 이름 기반 참조 cascade:
  - `[단위.X]`·`[타입.X]` 등 이름 기반 참조를 검색으로 전수 추적해, 병합·분할·삭제로 끊기는 참조를 함께 갱신.
  - § 번호는 자주 바뀌므로 이름으로 추적. 변경 후 dangling 참조가 남지 않게 확인.
- **구현 마커 제거** (§4 자신 또는 그 의존 § 를 수정한 경우) → 아래 "§4 `[구현]` 마커 제거" 절을 따름.
- 작성 형식·신뢰도 표기는 아래 "작성 원칙" 과 **대상 섹션의 작성법**(`references/format.md`)을 따름.

### §4 `[구현]` 마커 제거

§4 단위 본문이나 그 본문이 의존하는 § 를 수정했을 때, 그 §4 헤더의 `[구현]` 마커를 제거할지 판정. sd-spec 부분 수정·sd-impl spec 수정 양쪽이 따르는 단일 출처(sd-impl 은 지금 재구현 중인 본 단위는 제외).

**의존 식별** — §4 단위 본문에 다음이 나타나면 그 §의 의존 대상:

- `관련 섹션:` 줄의 `[단위.X]`·`[외부 의존.X]` 등.
- 본문 어디든 등장하는 `[타입.X…]`·`[공통 정의.X]`.

**판정·보고** — 그 수정 때문에 §4 의 구현(코드kind=코드, 비코드kind=산출물 텍스트)을 새로 만들거나 고쳐야 하면 제거, 구현 변경 없이 spec 과 맞는 문서상 변경(문구·참조 정리 등)이면 유지. 기능 추가도 제거 — 직접·의존 수정 구분이 아니라 구현 변경 필요 여부로만 판정. 에이전트가 영향 §4 마다 판정해 결과만 보고하고, 불분명한 항목만 번호·한 줄 이유로 합의.

### 연산 사이 검토

각 연산(배치·부분 수정) 완료 후 동일하게:

1. spec.md 갱신 (작성/편집 완료).
2. **검토 패키지** 를 채팅으로 제시:
   - 이번에 쓴 섹션의 한 줄 요약.
   - `[OPEN]` 목록 (이번 연산이 남긴 미확정 항목).
   - 검증 결과 요약 (배치 연산은 검증 서브에이전트가 반환한 근거 위조·누락·dangling 참조 보고).
   - 자료 커버리지 보고 (쓴 자료 중 spec 에 미반영된 부분).
   - **검증 서브에이전트 실패 시** (배치): 하나라도 실패하면 부분 결과로 검토 패키지를 만들지 말고 실패 사실을 `[error]` 로 알린 뒤 해당 검증만 재실행해 보완. 전건 정상 반환이어야 검증 완료로 간주.
3. **정지**. 초안 배치가 끝나도 후속 수정으로 자동 진입 금지. 다음 연산은 사용자가 호출.

## 작성 원칙

배치·부분 수정 모두에 적용되는 spec 정확성 원칙 (상위 행동 규칙·sd-design-rules 와 중복 금지, sd-spec 고유분만).

- **비자명 항목 inline 근거** — 자료에서 해석·도출한 비자명 항목에는 근거를 부착(아래 "신뢰도 표기"). 사용자가 직접 말한 자명한 항목엔 붙이지 않음.
- **모르면 `[OPEN]`** — 근거가 없으면 임의로 채우지 말고 `[OPEN]` 으로 표기 (판정 기준은 "신뢰도 표기" 절). `[OPEN]` 이 하나라도 남으면 미완성 — 검토 패키지에서 전수 보고.
- **추상 레벨 고정** — spec 은 *무엇을·왜*(요구·계약) 수준에 머묾. *어떻게*(구현 코드·내부 자료구조 선택 등)로 조기 점프 금지 — 구현 결정은 sd-impl·작성 단계 소관. (단 산출 단위의 인터페이스·계약 자체는 요구 수준이므로 정확히 기술.)
- **단순화 차단** — spec 의 계약·분기·경계를 그대로 풀어쓰기. 방어 처리(NULL 강제·0 클램프·가드·분기 생략)로 임의 변형 금지(상위 "인터페이스 설계 시"·"결측 보존"의 spec 적용). 정확 풀이 부담이 크면 단순화안을 `[OPEN]` 표기하거나 검토 패키지에서 보고.
- **모호 표면화** — 한 단위가 여러 해석을 허용하면 그대로 두지 말고 모호 지점을 `[OPEN]` 으로 드러내거나 더 정밀한 표현으로 좁힘.
- **형식 준수** — 각 § 작성법 규약 + `references/example.md` 모범 §를 형식 모범으로 직접 대조 (모범을 읽지 않고 텍스트 규칙만으로 작성 금지). 다른 §·example 에서는 **형식만** 가져오고 **내용물**(슬롯·항목·계약·동작)은 본 §의 자료·발언에서 직접 도출.

검증 단계(독립 서브에이전트)는 위 원칙의 준수를 독립 컨텍스트에서 사후 검증함. 사람 사후 검토(검토 패키지)가 최종 안전망.

## spec.md 형식

### 섹션 구조

| §   | 섹션 | 분류 |
| --- | ---- | ---- |
| §1 | 개요 | 요건 (목적·목표·소비자·환경) |
| §2 | 사용 시나리오 | 요건 (소비자가 산출물을 쓰는 흐름) |
| §3 | 기타 요구사항 | 요건 (비기능·제약) |
| §4 | 산출 단위 | 설계 (kind 태그 단위 — 핵심) |
| §5 | 공통 정의 | 공통 자연 도출 (요건·설계 양쪽에서 도출·편집) |
| §6 | 핵심 타입·자료구조 | 설계 자연 도출 (§4 에서 파생) |
| §7 | 외부 의존·인터페이스 | 설계 자연 도출 (§4 에서 파생) |
| §8 | 본문 외 확정 사항 | 메타 (결정이 발생할 때마다 누적) |

- **§6·§7 불변식**: §4 에 없는 단위의 타입·외부 의존은 존재할 수 없음 — 설계 산물로서 §4 의 종속.

### 산출 단위 슬롯 (§4)

각 산출 단위는 **단일 슬롯 세트**로 기술. 종류 무관 동일 슬롯, 차이는 `kind` 태그 + 런타임 타입렌즈로 흡수.

```
#### [단위 이름]  (kind: <api|doc-section|workflow-step|infra|generic|…>)
- 목적: 무엇을·왜
- 인터페이스·계약: 소비 측이 닿는 표면 + 약속 (api=시그니처·타입, doc-section=다룰 내용·대상, workflow-step=트리거·입출력 등 — 성격에 맞게)
- 동작·내용: 내부 규칙·로직·서술
- 경계·예외: 런타임 타입렌즈로 그 성격에 맞는 차원을 열거해 채움
- 완료 기준: 코드kind=테스트 가능 기준 / 비코드kind=내용 완전성 기준
```

- 슬롯이 그 단위에 자연스럽지 않으면 비우지 말고 *왜 해당 없음인지* 한 줄 적음 (누락과 구분).
- §4 첫머리에 단위 목록 표(이름·kind·한 줄 요약)를 두고 단위가 늘 때마다 갱신.

### 신뢰도 표기

| 표기 | 의미 |
| ---- | ---- |
| (무표기) | 직접·자명, 또는 미검토 초안. 기본 상태. |
| 줄끝 `(근거: 출처)` | 자료에서 해석·도출한 **비자명** 항목의 근거 (예: `(근거: 이슈#12)`). 사용자가 직접 말한 자명 항목엔 안 붙임. 위치 = 표는 비고 칸, 산문은 줄 끝. |
| `[OPEN]` | 근거 없음. 필요 시 추측·필요자료 메모 동반. |
| `[구현]` | §4 단위 구현 완료 표시. 부착은 sd-impl·sd-spec init 배치 소관 (init 배치는 산출물 대조 차이 0건 시 부착). §4 또는 그 의존 § 수정 시 제거는 sd-spec·sd-impl 양쪽 수행 (위 "§4 `[구현]` 마커 제거" 절). |

- `[OPEN]` 판정: 근거 부족(상위 행동 규칙 "결정 근거" 적용). 추정 / 답변 범위 흡수 = 근거 없음 → `[OPEN]`.
- 확정 여부는 사용자가 직접 관리 — 헤더에 상태 마커를 붙이지 않음.
- 예외: §8 로그 항목은 순서 보존용 날짜를 유지(`- YYYY-MM-DD: ...`). 신뢰도 마커가 아니라 로그 타임스탬프.

### 본문 내 참조 (이름 기반)

다른 섹션을 참조할 때 § 번호 대신 `[카테고리.이름]` 형식 사용. § 번호는 분석 중 자주 바뀌므로 이름 기반이 더 안정적.

예: `[단위.토큰 파서]`·`[타입.설정 객체]`·`[외부 의존.파일시스템]`·`[공통 정의.버전 규칙]`.

**관련 섹션 한 줄**: §2·§4·§7 본문에 `관련 섹션: [카테고리.이름], ...` 형식의 한 줄로 참조·의존 섹션을 콤마로 나열. 별도 작성 단위가 아님 — 다른 sub-section 작성 시 곁가지로 자동 누적.

### 진행 방법 누적

작업 중 사용자와 진행 방식을 합의하면 즉시 누적. 적용 범위에 따라 2 경로:

- **spec 전체 적용** → §8 의 진행 방법 항목으로 누적 (`- YYYY-MM-DD: ...` bullet).
- **분석 단위 한정** → 해당 단위 도입부에 `> **NOTE** (진행 방법): <한 줄>` blockquote + 다단. 단위에 `[OPEN]` 이 남아 있으면 본 NOTE 가 재진입 시 진행 룰 회복의 출처. 단위 확정 후 유지·제거 자유.

## §별 작성법

각 § 의 작성법(분할 절차·본문 구조·sub-section·모범)은 `references/format.md` 에 있음. 작성·부분 수정 시 읽기:

- 공유 형식(위 "spec.md 형식" 절)·골격·§8 은 본 SKILL.md 에 유지.
- **부분 수정** 시: `references/format.md` 의 편집 대상 섹션 작성법을 읽은 뒤 편집.
- **초안 배치·init 배치** 는 메인이 요건 단계·설계 단계에서 `references/format.md` 를 읽음.

## §8 본문 외 확정 사항

§1~§7 의 어느 곳에도 자연스럽게 들어가지 않는 결정·메모를 누적. §1~§7 의 적절한 자리에 넣을 수 있는 결정은 §8 에 두지 않음 (누락 도피처가 아님).

### 형식

- **헤더 1줄** (필수): `- YYYY-MM-DD: <결정 한 줄>`. 분석 제외 시: `- YYYY-MM-DD [제외]: <결정 한 줄>`.
  - 날짜는 항목 작성 시점의 현재 날짜 `yyyy-MM-dd` (배치는 준비 단계 생성값 재사용). 순서 보존용 로그 타임스탬프.
- **자식 bullet**: 형식 자유. **결정 근거 1개 이상 필수**. 분석 제외 시 추가 필수: `후속 처리`·`자료 위치`.

### 포괄 결정 종류

매번 분류하지 않음 — 자연 흐름대로 누적. 분석 제외 신호가 있을 때만 `[제외]` 마커 부착.

- **진행 방법**: spec 전체 작업에 대한 사용자 합의 진행 방식. (분석 단위 한정은 "진행 방법 누적" 절.)
- **미래 결정**: 해당 단계 도달 전에 미리 내린 결정 — sd-spec 자신의 후속 참조용.
- **구현 영역 결정**: spec 본문에 들어가지 않는 구현 측 결정 (예: 라이브러리 선택) — sd-impl·작성 단계의 후속 참조용.
- **부정 결정**: "X 안 함" 부정 명시 — 반복 질문 방지용.
- **분석 제외**: 본 spec 에서 다루지 않는 항목 — 다른 spec·sd-dev·운영 잔손 등 외부 후속 처리 대상.

## spec.md 골격 (초안·init 배치)

`{name}` 은 사용자와 합의한 산출물명.

```markdown
# {name} 개발 분석서

## 1. 개요

### 1.1 핵심 목적

### 1.2 주요 목표

### 1.3 소비자/이해관계자

### 1.4 환경/플랫폼

## 2. 사용 시나리오

## 3. 기타 요구사항

## 4. 산출 단위

## 5. 공통 정의

## 6. 핵심 타입·자료구조

## 7. 외부 의존·인터페이스

## 8. 본문 외 확정 사항
```

초안 배치 작성 범위:
- 요건 단계: §1 개요·§2.x/§3.x 헤더·본문·§5 공통 정의 작성. 미확정은 인라인 `[OPEN]`. §4·§6·§7 은 헤더만.
- 설계 단계: §4 산출 단위 본문 작성 → 그 §4 가 참조한 타입·외부 의존을 모아 §6·§7 파생 작성.
- §8 에는 자료에서 도출된 제외 결정(`[제외]` 마커) 반영.
