# sd-estimate

근거 있는 산정으로 뻥튀기, 낙관 편향, 임의값을 차단합니다. 고객이 "뻥튀기"라고 의심할 여지를 남기지 않습니다.

## 입출력

- Input (자유) — 산정 대상 범위를 알 수 있는 자료라면 무엇이든 됩니다. spec(spec.md/spec-si.md), 회의록, 메일, 기능/화면 목록, PPT, 구두 설명 등 정형/비정형 무관합니다.
  - 입력에서 "산정 대상 작업 목록"을 도출하는 것이 1단계입니다.
- Output — 두 가지입니다.
  - 고객용 견적서 (HTML + 전달용 PDF) — 작업별 공수, 금액 위주이며, 내부 산정 용어는 노출하지 않습니다.
  - 내부 산정 내역서 (작업 분해 + 3점 추정 표) — 근거 보관용이며 고객에게 동봉하지 않습니다.
- 사용자 입력 우선 — 사내 표준 공수, 단가, 실적이 제공되면 그것이 최우선 근거입니다.

## 핵심 원칙 (편향 차단 — 위반 시 산정 무효)

1. 분해를 강제합니다.
   - 큰 덩어리("화면 하나에 N일") 추정을 하지 말고 잘게 쪼갠 뒤 합산하세요(bottom-up).
   - 덩어리가 클수록 낙관, 패딩이 드러나지 않습니다.
2. 3점 추정을 씁니다.
   - 단일값을 쓰지 마세요.
   - 모든 작업을 낙관(O)/최빈(M)/비관(P) 3점으로 잡고 PERT `(O+4M+P)/6` 을 쓰세요.
3. 유추가 우선입니다. 사내 유사 프로젝트 실적이 있으면 그것이 모든 추정의 1차 기준점입니다.
4. 근거, 가정을 명시합니다. 모르는 값은 임의로 채우지 말고 `[가정: …]` 또는 `[OPEN]` 으로 두세요.
5. 생산성 보정은 근거 있을 때만 합니다.
   - 사내 실적으로 입증되지 않은 생산성 배수를 단정하지 마세요.
   - "프레임워크 쓰니 1/3" 같은 정량 배수는 근거가 약합니다.
6. 고객 산출물과 내부 산정을 분리합니다.
   - 고객 견적서는 작업별 공수, 금액 + 합계 + 전제(일반어)만 담습니다.
   - 고객 견적서에 노출하지 말아야 할 것:
     - 내부 도구명(`sd-*`)
     - 산정 과정 용어: PERT, O/M/P, 낙관/비관, 델파이, reference class, tier
     - 자신 없어 보이는 표현("가정 기반, 실적 미대조")
     - 단가 방법론명

## 절차

각 단계 산출물은 사용자가 검토, 정정합니다.

### 1. 작업 분해 (WBS)

입력이 무엇이든 동일하게 "할 일 목록"으로 환원하세요.

- 입도는 1작업이 대략 0.5-3 M/D 입니다. 그보다 크면 더 쪼개세요.
- 빠지기 쉬운 작업도 식별해야 합니다: 설계, 연동 시험, 데이터 마이그레이션, 배포 셋업, 안정화.
- 입력에 없어 추정 불가한 범위는 `[OPEN]` 으로 두고 견적 범위 외로 하되, 전제 조건에 일반어로 명시하세요.

### 2. 유형 분류 + 유형별 M/D 기준 확인

작업을 유형으로 묶어 산정 단위를 잡으세요.

- 유형 목록은 고정이 아니라 견적 대상에서 도출해야 합니다.
  - 유형 예: 마스터 CRUD, 단순 조회, 복합 화면, 트랜잭션, 외부 연동, 배치/자동, 로직/계산, 비화면 작업.
- 유형별 M/D 기준은 사용자에게 물어 확정해야 합니다. 임의값, 기본값을 쓰지 마세요.
  - 단가를 확정받듯 "이런 유형은 대략 몇 M/D"라는 생산성 기준도 사용자 확정 사항입니다.
  - 사내 표준 공수, 실적이 제공되면 그것이 최우선 근거입니다.
- 마이그레이션과 신규를 구분해 물어야 합니다.
  - 검증된 레거시, 명세가 있어 로직, 화면, 산식이 확정된 이식, 통합과, 요건, 설계, UX 미확정 신규 개발은 같은 유형이라도 M/D 가 다릅니다(신규가 더 큼).
- 화면 1개는 vertical slice(모델+서버+화면+테스트)입니다. 동형(파생) 화면은 한 단계 낮은 유형으로 두세요.
- 횡단 인프라(인증, 이력, 재고/변동 엔진 등)는 화면과 별도 항목으로 분리해 이중 계상을 방지하세요.

### 3. 3점 추정 → PERT

각 작업에 O/M/P(M/D)를 매기고 `PERT = (O+4M+P)/6` 을 계산해 표로 작성하세요.

| 작업 | 유형 | O   | M   | P   | PERT |
| ---- | ---- | --- | --- | --- | ---- |

- O/M/P 는 §2 에서 확정한 유형별 기준으로 매기세요. 비관(P)에 통합, 디버깅, 요건 변경 리스크를 반영해야 합니다.
- 합계 PERT 가 기본 공수입니다. 합계 O-P 는 변동 범위이며 내부용이라 고객 견적서에 노출하지 마세요.

### 4. 유추 보정

사내 유사 프로젝트 실적과 대조해 합계를 보정하세요. 실적이 없으면 그 사실을 명시하고 비관(P)에 가중해야 합니다.

### 5. 합계 + 리스크 내재

- 기본 공수는 ΣPERT 입니다.
- 리스크 예비비, 사업관리, 기술문서를 별도 라인으로 두지 말고 각 작업 단가에 내재시키세요.
  - 단가를 보수적으로 책정해 포함시킵니다.
  - 고객 견적서에 "예비비", "PM/문서" 라인을 두지 마세요.
- 단 내부 산정 내역서에는 내재 사실과 정도(기초 공수 vs 최종 M/D)를 반드시 명시해야 합니다.
  - 근거 없는 패딩과 구분하는 투명성 장치입니다.
- 끝자리는 tfoot `절삭` 행으로 맞추세요.

### 6. 금액 산정

`금액 = 공수(M/D) × 단가` 입니다.

- 사용자 지정 단가가 1순위이며, 지정이 없으면 §7-1 에 따라 물어서 확정하세요. 임의값을 쓰지 마세요.
- 필요 시 직접경비, 기술료/이윤, VAT 는 별도 행으로 둡니다.

- 공표 노임단가를 청구 단가로 그대로 쓰지 마세요. 등급 평균이고 직접인건비만이라(제경비, 기술료 미포함) 원가 이하입니다.

### 7. 견적서 생성

(7-1) 필수 정보 확인 — 아래는 견적서에 그대로 인쇄되므로, 자료에 없으면 임의로 채우거나 `[OPEN]` 으로 두지 말고 물어서 확정해야 합니다 (확정 전 산출 보류):

- 수신처(고객사)명.
- 제안사(발신) 주소, 담당자명, 연락처 — 발행처, 문의처. 사내 표준값이 있으면 그대로 씁니다. (상호, 워드마크는 템플릿 고정)
- 유형별 M/D 기준 (§2) — 작업당 M/D.
- M/D 단가 — M/D당 금액.
- 결제조건(착수/중도/잔금 비율), 납기, VAT 별도/포함 여부.
- 그 외 자료에서 확정되지 않는 헤더, 조건 값.

(7-2) 생성 — [references/estimate-template.html](references/estimate-template.html) 을 복제해 채우세요:
공급/수신 정보, 발행일, 유효기간, 항목별 표(작업, 공수, 단가, 금액), 소계, VAT, 합계, 결제조건, 납기, 전제(일반어로만).

- 항목이 수십-백 단위면 「[부록] 과업 세부 내역 — 항목별 산출물」이 필수입니다.
  - 견적서 끝(전제 다음, 서명 앞)에 두고, 견적 내역 각 항목에 포함된 산출물(화면, 기능)을 전수 나열해 "이 항목에 뭐가 들어가나"를 보이게 하세요.
  - 내부 용어(tier, 복잡도, 내재, 기초 build)를 쓰지 마세요. 산출물 명칭만 씁니다.
  - 공수, 금액은 「견적 내역」을 따르고 부록엔 중복 표기하지 마세요.
  - 항목이 적으면 섹션을 삭제하세요.

(7-3) PDF 출력 + 텅 빔 점검 — `sd-html-to-pdf` 스킬로 PDF 를 만든 뒤, `python "${CLAUDE_SKILL_DIR}/scripts/check-page-fill.py" <견적서.pdf>` 로 페이지별 하단 빈 공간을 실측하세요.

- 항목이 많으면 `page-break-inside:avoid` 블록(거래조건, 전제, 부록)이 통째로 다음 페이지로 밀려 앞 페이지가 크게 빌 수 있습니다.
- 경고가 나오면 표 셀 padding, 폰트를 줄이거나 밀린 섹션을 조정한 뒤, PDF 를 다시 만들어 재점검하세요.

## 출력 형식 (템플릿)

[references/estimate-template.html](references/estimate-template.html) 은 디자인 토큰(`:root`) + A4 인쇄 CSS + 섹션 컴포넌트 + `「…」` 플레이스홀더입니다.

- 디자인 토큰, 컴포넌트 클래스는 그대로 재사용해야 합니다. 새 컴포넌트나 임의 인라인 스타일을 만들지 마세요.
- 인쇄 CSS, 표 래퍼 구조는 건드리지 마세요. `@page{margin:0}`(브라우저 머리글, 바닥글 차단)은 불변입니다.
  - 상하 여백은 `@page` 가 아니라 전체 콘텐츠를 감싼 `table.psheet` 의 thead/tfoot spacer(`.run-top`/`.run-bot`)가 담당해 매 페이지 반복됩니다.
  - 이 래퍼, spacer 높이, `.sheet` 좌우 패딩, `print-color-adjust:exact`, `page-break` 제어를 바꾸면 PDF 품질이 깨집니다.
- 자기완결 1파일이어야 합니다. 외부 폰트, CDN, 스크립트를 추가하지 마세요. 폰트는 템플릿의 시스템 스택 그대로 씁니다.
- 액센트 1색(`--accent`)만 조정할 수 있습니다. navy 베이스 팔레트는 고정입니다.
- 공급자 고정값(상호, 워드마크, 직인 블록)은 유지하고, 주소, 담당자, 연락처와 수신처, 건명, 금액, 조건은 7-1 확인값으로 채우세요.
- 섹션 주석 `[공통, 필수]`/`[선택]` 을 따르세요. 해당 내용이 없으면 `[선택]` 섹션은 통째로 삭제합니다. tfoot `절삭` 행도 끝자리를 맞출 때만 남기세요.
- 플레이스홀더 `「…」` 는 전부 실제 값으로 채워야 합니다. 빈 채로 산출하지 마세요.
- 금액 표기는 천단위 콤마, 우정렬, 공수는 PERT 반올림값 중앙정렬입니다. 공급가액=Σ금액, VAT, 소계, 합계가 산술적으로 맞는지 산출 전 검산하세요.

## 내부 산정 내역서

1-5단계 산출물(작업 분해 + 3점 추정 표 + 합계)을 보관하세요. 고객 견적서와 분리하며 기본적으로 동봉하지 않습니다.

- 항목이 수십-백 단위면 세부 부록을 별도로 두세요 (예: `estimate-internal-appendix.md`).
  - 각 항목을 복잡도, M/D 로 전수 나열해 모듈 합계를 역추적 가능하게 합니다.
  - 부록 끝에 `세부 항목 → 고객 라인 매핑 → 예비, 문서 내재 → 최종` 까지 닫아 검산 일치를 확인하세요.
