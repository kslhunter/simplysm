# sd-debug

메인 루프가 직접 오케스트레이션합니다. 의심 관점을 도출해 가설을 발굴하고, 가설별 검증, 해결책 도출, 적대검증을 거쳐 검증된 해결책을 제안합니다.

## 디버깅 원칙 (전 단계 공통 — 서브에이전트에도 주입하세요)

- 모든 판정은 실제 코드, 설정을 직접 읽어 확인해야 합니다. 추측은 '가설'로만 등록하고 사실로 단정하지 마세요.
- 결측(null/undefined)은 결측대로 다루세요. 빈 값을 추측으로 채우지 마세요.
- 입력이 부족하면 코드베이스를 직접 검색, 조사해 보강하세요.

## 절차

### 1. 문제 확정

증상, 기대동작, 관찰결과를 확정하세요.

- 대화 중 오류를 논의하다 진입했으면 그때까지의 맥락(증상, 에러, 스택, 시도, 관찰)을 요약해 문제 설명으로 합성하세요.
- 문제 설명조차 불명확하면 사용자에게 물어야 합니다.

### 2. 의심 관점 도출 (메인 직접)

원인을 찾을 때 서로 겹치지 않는 의심 관점(범주)을 증상에 맞게 도출하고, 각 관점이 의심하는 구체 지점을 부여하세요.

- 보통 3-6개입니다. 증상이 좁게 가리키면 적게, 막연하면 넓게 잡으세요.
- 예시 범주는 동시성, 타이밍, 데이터, 결측, 타입, 계약, 로직, 경계조건, 외부의존, 환경, 설정, 상태, 생명주기입니다. 예시일 뿐이니 증상에 맞게 가감하세요.

### 3. 가설 발굴

관점마다 원인 가설을 발굴하고, 어떤 관점에도 매이지 않는 자유탐색 가설도 1건 추가하세요 (사각지대 안전망).

- 관점이 여러 개이고 조사 범위가 넓으면 관점마다 서브에이전트를 펼치세요. 각자 자기 관점만 보므로 사각지대가 줄어 놓치는 원인이 적어집니다.
- 관점이 적고 범위가 좁으면 메인이 직접 발굴하세요.
- 각 가설에 원인, 맞다면 보일 근거, 틀렸다면 보일 반증 신호를 채우세요.
- 그 관점에서 원인이 안 보이면 비우세요. 억지로 생성하지 마세요.

### 4. 중복 제거 (메인 직접)

'같은 근본 원인'을 가리키는 가설끼리만 합치세요.

- 근본 원인이 다르면 절대 합치지 마세요.
  - 서로 다른 원인을 뭉개면 검증에서 통째로 탈락합니다.
- 개수를 인위적으로 줄이지 마세요.
  - 놓치지 않는 것이 우선입니다.

### 5. 검증 + 해결책 도출

가설을 발굴자와 무관하게 코드로 재확인하는 독립성이 핵심입니다.

- 가설이 1건이라도 독립 서브에이전트(`subagent_type: sd:sd-verify`)로 수행하는 것이 기본입니다.
- 다수면 가설마다 병렬로 펼치세요.

판정은 관대 기준으로 해야 합니다. 일부라도 뒷받침되면 통과시키고, 근거 전무만 기각하세요.

- `confirmed` — 코드에서 근거를 확인했습니다.
- `uncertain` — 근거가 부분적, 애매하지만 코드에서 일부라도 뒷받침됩니다.
  - 통과시킨 뒤 적대검증이 거릅니다.
- `rejected` — 명백히 틀렸거나, 근거가 전혀 확인되지 않고 반증 신호가 우세합니다.

통과 가설은 확인한 코드 근거 위에서 해결책을 최대 2개, 서로 접근이 다르게 도출하세요.

- 근본 원인을 직접 제거하는 정도가 높은 순으로 둡니다.
- 과도한 설계나 증상만 가리는 임시방편은 배제하세요.

### 6. 적대검증

통과 가설의 각 해결책을 독립 서브에이전트로 공격하세요 (해결책마다 1개). 기본 입장은 "이 해결책은 결함이 있다"로 두고, 아래 4관점을 서로 끌려가지 않게 독립 판정해야 합니다:

- 인과 — 이 가설의 원인을 실제로 제거하는지, 원인-증상 인과가 성립하는지.
- 회귀, 부작용 — 새 버그, 룰 위반, 엣지케이스(결측, 동시성/트랜잭션, soft delete 동명 레코드, 권한 분기, 타입/스키마 제약)를 유발하는지.
- 증거 정합 — 가설의 근거가 실제 코드, 스택과 일치하는지, 오인, 과장은 없는지.
- 대안 원인 — 이 가설 말고 다른 원인이 진짜일 가능성은 없는지.

관점마다 통과 여부와 코드 근거, 치명적이면 치명 표시, 교정안을 받으세요.

전건 정상이어야 완료입니다. 하나라도 실패하면 부분 결과로 진행하지 말고, 실패를 알린 뒤 그것만 재실행하세요.

### 7. 판정, 우선순위 (메인 집계)

- 기각 — 어느 한 관점이라도 치명적 결함이면 탈락합니다 (치명 1표면 탈락).
- 통과 — 기각이 없고 통과 관점이 과반입니다.
- 통과 해결책에 교정안을 반영하고, 통과하지 못한 관점의 지적은 잔존 리스크로 보존하세요.
- 우선순위는 검증 확신도(confirmed > uncertain) + 적대검증 통과 강도 + 원인-증상 직접성으로 정합니다.

### 8. 결과 렌더 후 결정

- 원인 가설 — 통과 가설 (+ 기각된 가설과 사유).
- 검증 — 각 항목의 판정, 근거 (uncertain 은 "근거 약함"으로 표시).
- 해결책 — 채택분(교정 반영) + 잔존 리스크.

채택 후보가 1건 이상이면 스스로 우선순위를 정해 가장 우선한 1건만 제안하세요.

- 전체를 나열하지 마세요.
- 사용자가 고른 해결책만 실제 수정에 착수해야 합니다.

검증된 해결책이 0건이면 통과 가설, 탈락 사유, 기각 목록을 제시해 다음 수동 디버깅의 출발점으로 삼게 하세요.
