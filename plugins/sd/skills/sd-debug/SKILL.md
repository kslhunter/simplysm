# sd-debug

디버깅 요청 시 메인 루프가 직접 오케스트레이션함. 관점을 직접 도출한 뒤, 문제 규모에 따라 관점별 가설 발굴과 가설별 검증·해결책·적대검증을 독립 서브에이전트로 펼치거나 직접 수행하고, 검증된 해결책을 병합·우선순위화·결정 처리함.

## 디버깅 원칙 (전 단계 공통)

발굴·검증·적대검증 서브에이전트에 항상 주입하고, 메인 루프가 직접 수행할 때도 동일하게 적용할 것:

- 모든 판정은 실제 코드/설정을 직접 읽어 확인할 것. 근거 없는 추측·일반론 금지(추측은 '가설'로만 등록할 것, 사실로 단정 금지).
- 현재 워킹트리만 기준으로 할 것. git log/diff/show/blame 등 과거 조회 금지. `.back/` 및 `.gitignore` 등재 경로(node_modules·dist·.tmp 등) 읽지 말 것.
- 결측(null/undefined)은 결측대로 다룰 것. 빈 값을 추측으로 채우지 말 것.
- 입력 정보가 부족하면 코드베이스를 직접 검색·조사해 보강할 것.

## 절차

### 1. 문제 확정

증상·기대동작·관찰결과를 확정할 것.

- 대화 중 오류를 논의하다 진입했으면, 그때까지의 맥락(증상·에러·스택·시도·관찰)을 요약해 문제 설명으로 합성할 것.
- 에러 메시지·스택·재현조건·관련 코드 경로·환경은 있으면 함께 모을 것(선택).
- 문제 설명조차 불명확하면 사용자에게 물을 것.

### 2. 의심 관점 도출 (메인 루프 직접)

증상을 보고, 원인을 찾을 때 서로 겹치지 않는 '의심 관점(범주)'을 도출할 것:

- 증상 성격에 맞춰 동적으로 고를 것. 예시 범주: 동시성·타이밍, 데이터·결측, 타입·계약, 로직·경계조건, 외부의존·환경·설정, 상태·생명주기. (예시일 뿐 — 증상에 맞게 가감할 것)
- 각 관점에 key·title·focus(이 관점이 의심하는 구체 지점) 부여할 것.
- 보통 3-6개로 할 것. 증상을 좁게 가리키면 적게, 막연하면 넓게 잡을 것.

### 3. 규모 판단 → 펼침 여부 결정

- **가설 발굴**: 관점이 여러 개이고 코드베이스 조사 범위가 넓으면 → 관점마다 서브에이전트를 펼칠 것(각 서브에이전트는 자기 관점만 보므로 사각지대가 줄고 재현율이 오름). 관점이 적고 조사 범위가 좁으면 메인 루프가 직접 발굴할 것.
- **검증·적대검증**: 검증자가 가설을 발굴자와 무관하게 코드로 재확인하는 독립성이 핵심임. **가설이 1건이라도 검증·적대검증은 독립 서브에이전트로 수행함이 기본임**. 가설이 다수면 가설마다 서브에이전트를 병렬로 펼칠 것.
- 서브에이전트 다수를 펼칠 때는 **한 응답에 dispatch 를 여러 개** 두면 병렬 실행됨(응답당 하나면 순차 실행됨).

### 4. 가설 발굴

(서브에이전트 펼침 또는 직접) 관점별로 원인 가설을 발굴하고, 어떤 관점에도 매이지 않는 자유탐색 가설도 1벌 추가할 것(사각지대 안전망).

관점별 서브에이전트 프롬프트:

```
문제: <문제 설명>
[디버깅 원칙 주입]

너의 일: 오직 '<title>' 관점에서만 원인 가설을 발굴할 것. 이 관점의 의심 지점: <focus>
- 코드베이스를 직접 검색·조사해 이 관점에 해당하는 원인 후보를 빠짐없이 뽑을 것(재현율 우선).
- 다른 관점의 원인은 무시할 것(중복은 이후 정리함).
- 각 가설에 title·cause·perspective('<title>')·evidenceExpected(맞다면 보일 근거)·refuteSignal(틀렸다면 보일 반증) 채울 것.
- 이 관점에서 원인이 안 보이면 비울 것(억지 생성 금지).
```

자유탐색 서브에이전트는 위에서 `perspective='free'`, 정해진 관점 목록에 잘 안 들어가는 원인일수록 가치가 크다는 지시로 1벌 펼칠 것.

### 5. 가설 중복제거 (메인 루프 직접)

발굴된 가설을 의미 기준으로 병합할 것:

- '같은 근본 원인'을 가리키는 가설끼리만 하나로 합칠 것(표현만 다른 중복 제거). 근본 원인이 다르면 절대 합치지 말 것 — 서로 다른 원인을 뭉개면 검증에서 통째 탈락함.
- 병합 시 evidenceExpected·refuteSignal 은 합쳐 보존, perspective 는 합쳐진 관점들 표기할 것.
- 개수를 인위적으로 줄이지 말 것(재현율 우선). 진짜 중복만 제거할 것.

### 6. 검증 + 해결책 도출

각 가설을 (독립 서브에이전트가 기본 — `subagent_type: sd:sd-verify`, 검증 전용) 코드를 직접 읽어 검증하고, 통과 시 같은 근거 위에서 해결책까지 도출할 것. 서브에이전트 프롬프트:

```
문제: <문제 설명>
[디버깅 원칙 주입]

너의 일: 아래 원인 가설을 실제 코드를 직접 읽어 검증하고(관대 기준), 통과하면 같은 코드 근거 위에서 해결책까지 도출할 것.

1) 검증(verdict):
- confirmed: 코드에서 근거를 확인함.
- uncertain: 근거가 부분적·애매하지만 코드에서 일부라도 뒷받침됨 — 통과시킴(이후 적대검증이 거름).
- rejected: 코드로 보아 '명백히 틀린' 경우, 또는 코드에서 근거가 전혀 확인되지 않고 반증신호가 우세한 경우. 단 일부라도 뒷받침되면 기각하지 말고 uncertain 으로 둘 것('근거 전무'만 기각해 누락 방지).
- reason 에 확인한 코드 위치·내용을 인용할 것. 통과면 refinedCause 에 구체화된 원인을 기술할 것.

2) 해결책(rejected 가 아닐 때만):
- 확인한 코드 근거 위에서, 근본 원인을 가장 직접적으로 제거하는 정도가 높은 순으로 최대 2개, 서로 접근이 다르게 도출할 것.
- 각 후보에 approach·mechanism(원인을 어떻게 제거하나)·changeScope(수정 범위) 채울 것.
- 과도한 설계(over-engineering)·증상만 가리는 임시방편은 피할 것.
- rejected 면 solutions 를 비울 것.

가설:
- 제목: <title>
- 원인: <cause>
- 관점: <perspective>
- 예상 근거: <evidenceExpected>
- 반증 신호: <refuteSignal>
```

`rejected` 가설은 dropped 로 분리할 것(보고용). `confirmed`/`uncertain` 은 통과로 다음 단계로 넘길 것.

### 7. 적대검증

통과 가설의 각 해결책을 (독립 서브에이전트가 기본 — `subagent_type: sd:sd-verify`, 검증 전용) 4관점에서 적대적으로 공격할 것. 해결책마다 서브에이전트 1개를 펼칠 것. 프롬프트:

```
문제: <문제 설명>
[디버깅 원칙 주입]

너의 일: 아래 (원인 가설 + 해결책) 쌍을 다음 4개 관점 각각에서 적대적으로 공격할 것. 기본 입장은 '이 해결책은 결함이 있다'로 두고 약점을 찾을 것. 각 관점을 서로 끌려가지 말고 독립 판정해 관점마다 1개 항목으로 반환할 것.

관점:
- 인과: 해결책이 이 가설의 원인을 실제로 제거하는가. 원인-증상 인과가 성립하는가.
- 회귀·부작용: 해결책이 새 버그·룰 위반·엣지케이스(결측 null/undefined·동시성/트랜잭션·soft delete 동명 레코드·권한 분기·타입/스키마 제약)를 유발하는가.
- 증거 정합: 가설의 근거가 실제 코드/스택과 일치하는가. 오인·과장은 없는가.
- 대안 원인: 이 가설 말고 다른 원인이 진짜일 가능성은 없는가.

각 관점 판정:
- pass=false 로 둘 결함을 찾으면 reason 에 코드 근거와 함께 적고, 치명적(회귀 유발·인과 불성립 등)이면 critical=true 로 둘 것. 교정안 있으면 revisedNote 에 적을 것.
- 그 관점에서 결함이 없으면 pass=true, critical=false, revisedNote="".

원인 가설: <title> — <refinedCause 또는 cause>
해결책: <approach> / <mechanism> (수정 범위: <changeScope>)
```

**fail-fast**: 펼친 서브에이전트 중 하나라도 실패(에러)하면 부분 결과로 진행 금지. 실패 사실을 알린 뒤 해당 서브에이전트만 재실행해 보완할 것. 전건 정상이어야 전 가설·전 해결책 검증 완료로 간주할 것.

### 8. 해결책 판정 (메인 루프 집계)

각 해결책의 4관점 결과를 다음 규칙으로 판정할 것:

- **veto**: 어느 한 관점이라도 `critical=true && pass=false` 면 기각(치명결함 1표면 탈락).
- **passed**: veto 가 없고, `pass=true` 가 과반(passVotes > total/2)이면 통과(채택 후보).
- **risks**: `pass=false` 인 관점의 reason 모음(잔존 리스크).
- **revisions**: 비어있지 않은 revisedNote 모음(교정안).
- `votes` = `passVotes/total` 로 통과 강도를 표기할 것.

### 9. 병합·우선순위화 (메인 루프)

- 같은 근본 원인의 가설이 중복되면 병합할 것.
- 각 가설의 해결책 중 `passed=true` 인 것을 채택하되 revisions(교정)를 반영하고 risks 는 잔존 리스크로 보존할 것.
- (검증 confidence: confirmed>uncertain) + (적대검증 통과 강도 votes) + (원인-증상 직접성)으로 우선순위 정렬할 것.

### 10. 결과 렌더

아래 3블록으로 제시할 것:

- **원인 가설**: 통과 가설의 hypothesis·cause (+ dropped 로 기각된 가설과 사유).
- **검증**: 각 항목의 verdict·verifyReason (uncertain 은 "근거 약함" 으로 표시).
- **해결책**: 채택한 해결책(교정 반영) + 잔존 리스크.

### 11. 결정 진행

채택 해결책 후보가 1건 이상이면 행동 규칙 "제안 규칙" 대로 스스로 우선순위를 정해 가장 우선한 1건만 `제안`할 것(전체 나열 금지). 사용자가 고른 해결책만 실제 수정에 착수할 것.

### 12. 미해결 보고

검증된 해결책이 0건이면 통과 가설의 가설·탈락 사유와 dropped 를 제시해 다음 수동 디버깅의 출발점으로 삼게 할 것.
