# sd-impl

spec 의 구현 § 1개를 현재 코드베이스 상태와 비교해 빠지거나 어긋난 부분만큼 풀 구현함.

## spec 포맷

포맷 2종 — 루트 인덱스가 `spec-si.md` 면 SI, `spec.md` 면 범용. 본문 표기는 포맷에 따라 아래로 읽음:

| 표기               | SI                 | 범용       |
| ------------------ | ------------------ | ---------- |
| **구현 §**         | §4.x / §5.x / §6.x | §4.x       |
| **참조 §**         | §5/§6/§7/§8/§9     | §5/§6/§7   |
| **결정 맥락 §**    | 루트 §10·§11       | 루트 §8·§9 |
| **spec 작성 스킬** | sd-spec-si         | sd-spec    |

## 본질 (횡단 룰 — 전 단계 적용)

- **임의 채움 금지**: 분기·정의·값·계산식·경계를 만나면 `결정 근거` 유무로 판정함.
  - 있으면 그에 따라 채우고, 없거나 모호하면 즉시 멈춰 사용자에게 `제안`함.
  - 추정·단발 사례·"추론 가능"을 근거로 대체 금지. spec·사용자 발언이 유일한 근거임 — 코드 추론으로 채우기 금지.
- **결정 즉시 반영**: 구현 중 spec 반영이 필요한 결정(아래 3경로)이 서면 다음 항목·단계로 넘어가기 전에 그 자리에서 spec 에 반영함.
  - 결정을 기억만 한 채 구현으로 진행 금지. 여러 건이 몰려도 건별로 각각 반영함.
  - 반영 대상 3경로:
    1. `[OPEN]`·모순·미정의를 물어 받은 답(마커 해소).
    2. 기존 확정을 사용자가 번복(확정 문구를 새 결정으로 치환).
    3. 자체 결정한 신규 사항 — `결정 근거`가 확실해 스스로 채웠으나 spec 본문에 아직 명문화되지 않은 결정.
- **YAGNI**: spec 에 없는 구현 추가 금지. 필수사항으로 판명되면 사용자에게 `제안`함.
- **구현 § 완결성**: `[구현]` 은 구현 § 전체 완결에만 부착함 — 되는 부분만 구현한 채 미완으로 남기지 않음.
  - 통째 완성 불가 시 "spec 수정 절차"(구조 변경)로 § 경계를 독립 완성 가능한 크기로 분할하거나 적절한 섹션에 흡수함.

## 워크플로

### 1단계: 입력 확보

- 대상 spec 경로(bundle 루트 또는 루트 인덱스)와 구현 § 식별자를 확보함. 없으면 물음.
- 식별자 매칭이 안 되면 구현 § 목록에서 후보 제시 후 확정함.

**입력 spec 읽기 범위** — 아래 순서로 읽음 (부분 검색·부분 읽기로 결정 맥락·참조 본문을 빠뜨리지 않음):

1. 구현 § 본문.
2. 그 본문이 이름 기반 참조(`[화면.X]`·`[단위.X]`·`[모델.X]`·`[타입.X]`·`[공통 정의.X]` 등)로 가리키는 §/page 를 재귀적으로(참조의 참조까지) 읽음.
3. 결정 맥락 § 전체 — 다른 세션이 남긴 결정·기각 대안·검토 경계를 담으므로, 기각된 안을 재론하거나 미검토 영역을 검토된 양 다루지 않도록 반드시 감안함. 구현 § 한정 맥락은 그 § 의 NOTE·인라인 `[OPEN]` 에 있음.

### 2단계: 외부 입력 점검

구현 § 와 참조 § 항목을 점검함:

- **섹션 `[OPEN]` (초안 부재)**: 본문이 재분석 포인터일 뿐 초안이 없음 → "spec 수정 절차" 적용함.
- **본문 인라인 `[OPEN]`**: `결정 근거` 있으면 결정, 없으면 1건씩 질문함. 답을 받는 즉시 "spec 수정 절차" 로 그 `[OPEN]` 을 확정 내용으로 치환함.
- **사용자 제공 예정 자료**: spec 에 사용자 회신 대기로 적힌 자료 — 회신 후 진행함.
- **묵시적 모호**: 마커는 없지만 spec 이 분기·정의·계산식·경계 케이스를 다루지 않는 부분. 이후 단계에서 발견 시 본 단계로 회귀함.

#### spec 수정 절차

spec 본문 수정이 필요한 모든 경우(인라인·섹션 `[OPEN]` 해소, 구조 변경, 6단계 (b)(c) 처리 등)는 메인 LLM 이 직접 처리함:

1. **spec 작성 스킬 SKILL.md 읽기** — "부분 수정 (인라인)" 경로·신뢰도 표기·형식(§ 작성법)·이름 기반 참조 cascade·단일 출처 불변식(SSOT — canonical 1곳 수정, 복제 잔재는 통합 후 이름 참조로 대체)을 인지함. 단 도메인 답이 확정된 인라인 `[OPEN]` 을 그 자리 문구로 치환하는 경량 반영은 스킬 재독 없이 바로 편집함 — 재독은 초안 작성·구조 변경·모순 정정 등 판단 필요 시에만 수행함.
2. **그 스킬의 "부분 수정 (인라인)" 경로로 편집** — 확정분은 바로 편집, 초안·판단 필요분(섹션 `[OPEN]` 초안·구조 변경·모순 정정)은 진단·초안 제시 → 합의 후 편집함. 수정분은 사후 보고함.
3. **의존 추적** — 그 스킬의 `[구현]` 마커 제거 절의 의존 식별 규칙으로 수정된 § 를 의존으로 가진 구현 § 를 전수 추적함(본 작업 구현 § 자신은 제외).
4. **마커 판정·제거** — 추적된 구현 § 마다 같은 절의 제거/유지 판정(구현 변경 필요 여부)을 적용해, 제거 대상만 루트 인덱스 표의 해당 § 행 `구현` 컬럼에서 제거함. 판정 보고·합의 절차도 같은 절을 따름.

### 3단계: 보조 자료 수집 (있다면 활용)

부재로 워크플로를 멈추지 않음 — 발견되면 따르고, 부재 시 framework 자체 표준(Angular CLI 기본 구조·esbuild 기본 옵션 등)으로 채움.

#### A. 라이브러리·개발 매뉴얼

- `@simplysm/*` — SessionStart 가 주입한 활성 references 경로의 `README.md` 참조 후 "개발 매뉴얼" 로 진입함.
- 그 외 framework — 코드베이스 안의 동등 위치 문서를 참조함.

#### B. 기준 단위 + 계층별 보강

풀 구현은 다층 흐름이 한 줄로 가야 일관성이 유지됨 — 기존 구현물 중 기준 단위 1개를 잡고 비어있거나 부적합한 계층만 다른 단위에서 보강함.

**4계층**:

| 계층        | §4.x (화면)   | §5.x (자동 처리)        | §6.x (공통·기반 기능)                   |
| ----------- | ------------- | ----------------------- | --------------------------------------- |
| 도메인 모델 | 엔티티·필드   | 동일                    | 동일                                    |
| 데이터 접근 | 쿼리·서비스   | 동일                    | 동일                                    |
| 본체        | 화면 컴포넌트 | 자동 처리 로직 + 트리거 | 부수효과 후크 또는 설정·부트스트랩 구성 |
| 테스트      | 단위 테스트   | 동일                    | 동일                                    |

- 범용 포맷은 `kind` 로 본체 계층을 읽음 — api=공개 모듈·함수·타입 / workflow-step=처리 로직 + 트리거 / infra=부트스트랩·설정 구성 / 화면 §=화면 컴포넌트. 도메인 모델·데이터 접근 계층은 구현 § 가 실제 참조할 때만(없으면 "비어있음" 처리).

**기준 단위 선정** (같은 종류끼리 — SI=같은 §군, 범용=같은 `kind`):

1. 도메인이 인접한 풀 구현 단위 후보를 탐색함 (인접 도메인 정의는 spec 의 구현 § 목록 분류·코드베이스 구조 등에서 자유 도출).
2. 후보 1개 → 자동 채택함. 2개 이상 → 목록 제시 후 사용자에게 1회 질문함. 0개 → 같은 종류 전 범위로 확장 후 동일 규칙 적용함.
3. 전 범위에도 0개 → 기준 단위 없이 매뉴얼(A) + framework 자체 표준으로 진행함.

**계층별 보강** — 기준 단위의 4계층 각각을 평가함:

| 평가     | 의미                              | 처리                                      |
| -------- | --------------------------------- | ----------------------------------------- |
| 비어있음 | 해당 계층 파일이 기준 단위에 없음 | 같은 종류 다른 단위에서 그 계층 패턴 차용 |
| 부적합   | 있지만 spec 요구와 어긋남         | 같은 종류 다른 단위에서 그 계층 패턴 차용 |
| 적합     | 그대로 따름                       | 변경 없이 사용                            |

- 차용 패턴은 같은 종류 서로 다른 단위 2개 이상에서 동일하게 나타난 것만 자동 채택함. 단위 1개에서만 쓰인 변종은 배제하고, 여러 패턴이 갈리면 사용자에게 1회 질문함.
- **읽기**: 기준 단위의 적합 계층 파일 + 보강 출처 파일을 모두 읽음 — 5단계 작성 기준이자 7단계 drift 점검 입력임.

#### C. 테스트 환경

단위 테스트 프로젝트 구분·실행 명령·mocking 패턴·dev 서버 실행 명령을 파악함. 부재 시 framework 자체 표준으로 조합함.

### 4단계: spec 분해 표

구현 § 와 참조 § 본문을 항목 단위까지 분해하여 표를 작성함. 표는 assistant 응답으로 출력함(5·6단계의 입력).

**예시** (재고관리 도메인, 박스 입고 화면 §4.1 일부):

| 항목 ID | spec 인용                                  | 현재 코드 상태   | 판정   | 매핑 파일                                          | 의존 |
| ------- | ------------------------------------------ | ---------------- | ------ | -------------------------------------------------- | ---- |
| 1       | §4.1 항목 "박스 바코드" (필수·문자열·24자) | 없음             | 없음   | packages/app/src/screens/incoming/box-form.view.ts | -    |
| 2       | §4.1 동작 "스캔: 바코드 검증·박스 등록"    | 있음 (검증 누락) | 불일치 | (동일)                                             | 1    |

**항목 분해 단위**:

- 도메인 모델: 필드 1개당 1줄 (타입·제약·기본값).
- 계산식: 정의식 1개당 1줄 (좌변·우변·참조).
- 상태값·분기: 케이스 1개당 1줄 (조건·결과).
- UI 항목: 컬럼·필드·버튼 1개당 1줄.
- 동작·자동 처리: 트리거·결과 단위 1줄.

**컬럼**:

- **항목 ID**: 이후 의존 컬럼 참조용 (형식 자유).
- **spec 인용**: spec 위치(page 경로 + ref/절 위치) + 본문 문구.
- **현재 코드 상태**: 코드베이스 조사 결과 사실 — 신규="없음", 갱신="있음(어떻게)". 조사는 워킹트리 파일 직접 읽기·검색으로만 수행함.
- **판정**: 없음 / 불일치 / 일치.
- **매핑 파일**: 이 항목이 작성·갱신될 파일 경로.
- **의존**: 다른 항목 ID.

### 5단계: 작업 사이클

표의 없음·불일치 판정 항목만 의존 순서로 진행함 — 일치 항목은 손대지 않음.

- **데모 골격 보존**: 매핑 파일이 데모 골격(sd-demo 산출물)이면 골격 구조를 유지하며 차이만 보강함.

각 항목 시작 시 **테스트 작성 가능 여부**를 판정함 (3-C 이용):

| 분류               | 적용 대상                                     | 사이클                 |
| ------------------ | --------------------------------------------- | ---------------------- |
| 테스트 가능        | 도메인 로직·계산·변환·서버 함수·데이터 접근   | RED → GREEN → REFACTOR |
| 테스트 불가·비효율 | UI 시각·인터랙션·외부 서비스 실호출·환경 의존 | 구현 → REFACTOR        |

**테스트 단위 = spec 이 독립 산출물로 요구한 단위. 내부 구현을 쪼개지 않음**:

- "테스트 가능" 분류는 그 처리가 spec 이 독립 산출물로 요구한 단위(공개 함수·API·계약)일 때 적용 — 그 단위를 그대로 테스트함.
- 요구가 "동작"(화면·자동 처리·공통·기반·초기화 등)이고 변환·매핑·계산이 그 내부 구현 조각이면 동작 전체를 테스트 단위로 봄 — 동작이 통째로 테스트 가능하면 그 단위로, 아니면(외부 I/O·환경 의존) "테스트 불가·비효율" 로 분류함.
- 내부 구현 조각을 테스트하려고 별도 함수·파일·인터페이스로 분리·추상화 금지.

**무엇을 단언하는가 — 불변식·제약만, 우연한 스냅샷 금지**:

- 깨지면 진짜 결함을 가리키는 불변식·제약만 단언함 (필수값 비어있지 않음·유일성·1:1 관계·멤버십·빈 배열 금지·경계값 등).
- 임의 스냅샷 카운트·분포 총합 단언 금지 — 항목 수·집계 분포(`목록 N건`·`배지 164개`)는 데이터가 정상 변경되면 깨지는데 어떤 제약도 검증하지 못함. 다른 소스 길이로 맞추는 것(`toHaveLength(OTHER.length)`)도 자기참조라 무의미함.
- REFACTOR·정리 중 이런 브리틀 테스트 발견 시 갱신하지 말고 제거함. 카운트가 가리키던 의도가 실제 제약이면 그 제약을 단언하는 테스트로 교체함 (예: 빈 배열이 문제면 전 항목 `length > 0` 단언).

**사이클 단계 정의**:

- **RED**: 테스트만 작성 → 실행 → 실패를 확인함. 구현 파일은 손대지 않음.
- **GREEN**: 테스트를 통과하는 최소 구현 → 통과를 확인함.
- **REFACTOR**: 중복·가독성·3-B 채택 패턴·3-A 매뉴얼 정합 정리(임의 변형 금지) → 테스트 통과 유지함. 검토는 항상 수행하며, 정리 대상이 없으면 코드 변경이 없을 뿐 단계를 건너뛰지 않음.

### 6단계: spec 대조 (서브에이전트 위탁)

5단계 완료 후 서브에이전트에 위탁해 spec ↔ 현재 코드 전체를 독립 대조함 — 같은 LLM 자체 검증의 확인 편향 제거 목적임. 대조 범위는 아래 프롬프트의 3항(단위 전체, 스코프 제한 없음)을 따름.

#### 서브에이전트 호출

- 독립 서브에이전트 1개를 사용함 — `subagent_type`: `sd:sd-verify`.
- `prompt`: 아래 입력 패키지 (그대로 복사 후 `<…>` 부분만 채움).

```
sd-impl 의 spec ↔ 코드 독립 대조를 수행해줘.

**대상**:
- spec 경로: <bundle 루트 절대경로 또는 루트 인덱스(spec-si.md/spec.md) 절대경로>
- 단위 식별자: <SI=§4.x/§5.x/§6.x · 범용=§4.x>

**참조 자료**:

(1) 4단계 spec 분해 표 (인라인):

| 항목 ID | spec 인용 | 현재 코드 상태 | 판정 | 매핑 파일 | 의존 |
| ------- | --------- | -------------- | ---- | --------- | ---- |
| ...     | ...       | ...            | ...  | ...       | ...  |

(2) 현재 구현 파일 목록 (절대경로):
- <file1>
- <file2>
- ...

**작업**:

1. spec 의 §<단위> 본문 + 참조 §/page (SI=§5/§6/§7/§8/§9, 범용=§5/§6/§7) 항목을 다시 읽기. 루트 인덱스(`spec-si.md`/`spec.md`)에서 대상 page 를 찾고 참조 page 까지 읽기.
2. 현재 구현 파일을 모두 읽기.
3. spec ↔ 코드를 항목 단위로 1:1 대조 (단위 전체 대상. "이번 변경분만" 식 스코프 제한 없음).
4. 차이 발견 시 아래 3분류로 보고:

   - (a) **코드 위반**: spec 명확한데 코드가 빠뜨림·다름.
   - (b) **spec 내부 모순**: §A 정의 vs §B 정의 충돌. (양쪽 인용 명시)
   - (c) **spec 미정의 + 코드 임의 채움**: spec 본문에 정의·분기·경계 케이스 명시 없는데 코드가 채움.

5. 보고 형식 (각 차이 1건마다):

   ### 차이 N: <도메인 어휘로 표현된 한줄 요약>
   - 분류: (a) / (b) / (c)
   - spec 위치: §X.x line Y
   - spec 인용: "..."
   - 코드 위치: <file:line>
   - 코드 동작: <도메인 어휘로>
   - 비고: (b) 면 모순 상대 인용 함께

6. 차이 0건이면 `차이 없음, 검증 통과` 1줄만 응답.

**제약**:

- 보고 본문에 코드 식별자(변수명·SQL 함수명·타입 키워드 등) 노출 금지. 도메인 어휘로 풀어 쓸 것. 단 공개 계약(공개 함수명·CLI 옵션명 등)은 그대로 인용 가능.
- "코드가 spec 위반" 으로 단정 금지. 3분류 중 어디에 해당하는지 명시.
- spec 본문에 인용할 수 있는 문구가 없으면 (b)(c) 후보로 처리.

**산출**: 위 3분류 보고 목록 또는 `차이 없음, 검증 통과`.
```

#### 결과 처리

- **(a) 코드 위반**: 5단계 사이클로 재진입하여 코드를 수정함.
- **(b) spec 내부 모순**: 사용자에게 1건씩 보고 (모순 양쪽 인용 + 어느 쪽이 합리적인지 의견) → 처리 방향 묻기 (spec 수정 / 코드 정정) → spec 수정 시 "spec 수정 절차" 적용함.
- **(c) spec 미정의 + 코드 임의 채움**: 사용자에게 1건씩 질문 → 결정 수령 → "spec 수정 절차" 로 반영 → 5단계 재진입함.
- (b)(c) 묶음 보고 금지 — 1건씩 합의함.
- 처리 완료 후 6단계를 재실행함(재대조). 차이 0건 확인 후 7단계 진입함.

### 7단계: 코드 정리

- **횡단 중복**: 작업 사이클 사이에 흩어진 동일 로직을 합침.
- **계층별 drift 점검**: 다항목 누적으로 3-B 채택 패턴에서 이탈한 계층이 있는지 4계층 전체를 횡단 점검하고 이탈분만 수정함 (개별 항목 정합은 5단계에서 선반영).
  - 도메인 모델: 필드·타입·제약·네이밍 패턴 일치.
  - 데이터 접근: 함수 시그니처·쿼리 패턴·에러 처리 일치.
  - 본체: 컴포넌트·트리거·처리 단계·핸들러·의존성 패턴 일치.
  - 테스트: 러너·assertion·mock 패턴 일치.
- **불필요한 코드**: 미사용 import·변수·주석, 요구 없는 옵션·추상화, 어디서도 참조되지 않는 파일을 제거함 (검사 범위는 전체 워크스페이스).
  - 파일 단위 삭제는 후보 목록을 사용자에게 보고 → 확정분만 삭제함 (dynamic import·마이그레이션·문서 자산 등 정적 참조로 탐지 안 되는 보존 대상은 사용자가 제외 지시함).
- **테스트 가치 스윕**: 이번 작업으로 생성·수정한 테스트를 전수 훑어 동작·계약·불변식·예외를 단언하지 않는 임시 테스트를 제거함.
  - 대상 예: 구현 세부·중간 형태 단언, 존재/텍스트 유무만 확인, 상위 동작 테스트에 흡수된 디딤돌 테스트, 5단계에서 놓친 스냅샷 브리틀 테스트.
  - 판정: 깨졌을 때 진짜 결함을 가리키는가 — 아니오면 삭제함.
- **매뉴얼 규약 정합 (횡단)**: 3-A 매뉴얼 규약 중 여러 항목·계층에 걸쳐 작성 후에만 드러나는 위반만 점검·수정함.

정리 후 단위 테스트를 재실행하여 회귀 없음을 확인함.

### 8단계: 시연 검증

- **시연 스킵 조건**: 구현 § 에 세션 시작 시점부터 `[구현]` 마커가 있었고(이전 시연 완료) + 이번 세션 코드 파일 생성·수정 0건(5단계 편집 0건 + 6단계 (a) 0건 + 7단계 정리 편집 0건) → 본 단계 통째로 스킵함 (UI·비-UI 무관, 아래 실행 확인도 생략). 마커가 없던 구현 §(첫 검증)는 코드 변경이 없어도 시연을 수행함.
- **방식 분기**: 화면 §(인터페이스가 화면 컴포넌트[렌더 산출물]인 구현 § — SI=§4.x, 범용=`kind` 로 판정)는 아래 브라우저 시연을 수행함. 비-화면 §(api·cli·infra 등)는 단위 테스트 통과 + 실행 가능 산출물이면 실제 실행 확인(api=대표 호출 예시 실행, cli=명령 실행, infra=부팅 후 구성 반영 확인, SI §5.x=트리거 발생 → 결과 확인, SI §6.x=부수효과는 트리거 발동 → 결과·기록 확인·상시 구성은 앱 부팅 후 구성 반영 확인)으로 갈음함.
- **LLM 관찰 불가 GUI 산출물** (데스크톱 앱 창·네이티브 GUI 등 브라우저 자동화로 못 보는 산출물): 시연 주체는 사용자임 — LLM 은 자신을 시연 주체로 두지 않음("내가 시연했다" 보고 금지). 시연할 항목·입력·기대결과를 구체적으로 안내하고 사용자 회신으로 검증함.

화면 § 브라우저 시연:

1. 사용자에게 요청: "**dev 서버**를 실행하고 접속 주소를 알려달라." — 회신까지 대기함. 사용자가 스킵을 지시하거나 사용자·spec 이 시연 불가 환경(예: 대상 실행 인프라 부재)을 명시하면 본 단계 스킵함.
2. 주소 회신 후 브라우저 자동화 도구로 구현 § 동작 시나리오를 직접 시연함:
   - 기능 개요·동작의 사용자 흐름을 1회씩 수행함.
   - 화면 항목·와이어프레임 위치와 실제 렌더 결과를 비교함.
3. 회귀 발견 시 5단계로 재진입 → 수정 → 재시연함.

### 9단계: 완료 보고

- **결정 반영 최종 게이트** (마커 부착 전 — 대화 맥락을 아는 메인 LLM 직접. 맥락을 모르는 서브에이전트 위탁·6단계 코드 ↔ spec 대조로 대체 불가): 이번 세션의 결정 3경로(질문 답변·기존 확정 번복·자체 결정 신규 사항)를 전수 훑어 spec 반영 여부를 대조함. 미반영분은 마커 부착 전에 "spec 수정 절차" 로 반영함.
- 구현 § 에 `[구현]` 마커를 부착함 — 루트 인덱스 표의 해당 § 행 `구현` 컬럼에 표기함. 이미 있으면 그대로 둠 (날짜·`[확정]` 부착하지 않음).
- **plan.md(개발계획서) 경유 호출이면** 그 plan.md 의 해당 TASK 상태를 `Done (yyyy-MM-dd)` 로 갱신함 — 마커 부착과 같은 시점에 수행함. 다음 작업 안내는 plan 의 TASK 번호순(§8 실행 순서와 일치)을 따름.
- 만들거나 갱신한 파일 목록을 보고함 (마커를 부착한 spec 파일/page 포함).
- 본 세션 "spec 수정 절차" 로 의존 구현 § 마커가 제거된 항목이 있으면 영향 § 목록을 보고함 (재구현 필요 알림). 없으면 생략함.
