# sd-impl

spec(단일 spec.md 또는 spec bundle — SI 루트 spec-si.md / 범용 루트 spec.md) 단위(§4.x 화면 / §5.x 자동 처리 / §6.x 공통·기반 기능) 1개를 현재 코드베이스 상태와 비교해 빠지거나 어긋난 부분만큼 풀 구현. 데모 골격이 있으면 보존. 끝에 사용자 시연으로 회귀 점검.

호출 시나리오 2종 — 동일 워크플로:

- **신규**: spec 단위가 코드베이스에 아직 없음 — 처음 구현.
- **갱신**: spec 단위가 이미 구현되어 있고 spec 변경분에 맞춰 수정.

## 본질 (횡단 룰)

워크플로 전 단계 적용:

- **임의 채움 금지 (`결정 근거` 없으면 질문)**: 분기·정의·값·계산식·경계를 만나면 `결정 근거`(sd.md — 사용자 발언·코드베이스의 **일관된** 구현 패턴·공식문서 명시) 유무로 판정. 있으면 그에 따라 채우고, 없거나 불명확하면(spec 명시 없음·모호 포함) 즉시 멈춰 1건씩 질문. 추정·단발 사례·"추론 가능"을 근거로 대체 금지. 도메인 값·분기·계산식은 spec·사용자 발언이 유일 근거 — 코드 추론으로 채우기 금지. 분석·분해·구현 어느 단계에서 발견하든 동일 적용.
- **결정 즉시 반영 (원자 행동)**: 구현 중 spec 본문과 어긋나는 결정이 서면 **다음 항목·단계로 넘어가기 전에** 그 자리에서 spec 파일을 편집해 반영한다. 반영 대상 결정은 아래 3경로 모두 — 어느 경로든 동일하게 즉시 반영한다.
  1. `[OPEN]`·모순·미정의를 사용자에게 물어 받은 답 (해당 마커 해소).
  2. **기존 확정 번복**: spec 에 이미 확정으로 적힌 값·분기·정의·경계를 사용자가 뒤집음 → 확정 문구를 새 결정으로 치환.
  3. **자체 결정한 신규 사항**: 질문 없이 `결정 근거`(코드베이스의 일관된 패턴·공식문서 명시 등)로 채웠는데 그 내용이 spec 본문에 없던 것 → spec 에 신규 명시. (근거 있어 안 물어봤어도 spec 미기재면 반영 대상.)
  - spec 반영은 구현을 막지 않아(non-blocking) 누락되기 쉬움 — 결정을 기억만 한 채 구현으로 진행 금지. 결정 확정과 spec 편집은 한 호흡으로 붙이며, 여러 건이 몰려도 건별로 각각 반영한다. 편집은 2단계 "spec 수정 절차" 를 따른다.
- **YAGNI**: spec 에 없는 기능·옵션·추상화·방어코드 추가 금지. 필요해질 때까지 만들지 않음 (작성 시점부터 적용).
- **사용자 보고 어휘**: 사용자에게 보고하는 본문에 코드 식별자(변수명·SQL 함수명·타입 키워드 등) 노출 금지. 도메인 어휘로 풀어 보고. 단 공개 계약(공개 함수명·CLI 옵션명 등)은 그대로 노출.
- **단위 완결성 — 부분 구현 금지**: 대상 단위를 이번 세션에 통째로 완성할 수 없으면(일부가 미구축 인프라·미완 선행에 막힘) 되는 부분만 구현한 채 단위를 미완으로 남기지 않음. `[구현]` 은 단위 **전체 완결**에만 부착 — "부분 구현이라 마커 보류"는 안티패턴.
  - 해소: 2단계 "spec 수정 절차"(구조 변경)로 단위 경계를 실제 독립 완성 가능한 단위에 맞춤.
    - 완성 가능분은 완결 단위로 남겨 `[구현]` 부착.
    - 막힌 분은 별도 단위로 **빌드 순서에 맞는 위치에 분리 삽입**(맨 끝 추가 금지)하거나 적절 섹션에 흡수.
    - 경계 분할은 구조 변경이므로 진단·초안 제시 후 사용자 합의.

## 워크플로

### 1단계: 입력 확보

- 대상 spec 경로: 단일 `spec.md`, spec bundle 루트(`.specs/{title}/`), 또는 bundle 루트의 `spec-si.md`(SI)/`spec.md`(범용).
- **spec 포맷 판정** — 루트 파일명과 하위 파일 구조로 포맷을 구분 (이후 모든 단계가 이 판정을 따름): 루트 `spec-si.md` = SI wiki bundle, 루트 `spec.md` + bundle 폴더 = 범용 bundle, 단일 `spec.md` 파일 = SI 단일 파일 legacy.
  - **SI wiki bundle 포맷** (sd-spec-si 산출 — 루트 `spec-si.md` + `requirements/`·`design/`·`common/`·`data/`): 단위 식별자 = `§4.x`(화면)/`§5.x`(자동 처리)/`§6.x`(공통·기반). 루트 인덱스로 대상 page 를 찾아 본문을 읽고, `[구현]` 마커는 루트 `spec-si.md` 인덱스 표(§4/§5/§6)의 해당 단위 행 `구현` 컬럼에 표기한다 (page 헤더 아님).
  - **SI 단일 파일 포맷(legacy)** (과거 sd-spec-si 산출 — §1-11, §4 화면·§5 자동 처리·§6 공통·기반): 단위 식별자 = `§4.x`/`§5.x`/`§6.x`.
  - **범용 bundle 포맷** (sd-spec 산출 — 루트 `spec.md` + `requirements/`·`design/units/`·`common/`·`types/`·`interfaces/`, §1-9): 단위 식별자 = `§4.x`(산출 단위, `kind` 태그). 루트 인덱스로 대상 page(`design/units/*.md`)를 찾아 본문을 읽고, `[구현]` 마커는 루트 `spec.md` §4 인덱스 표의 해당 단위 행 `구현` 컬럼에 표기한다 (page 헤더 아님). 이후 "화면" 전제 지침은 단위 `kind` 로 읽음 — 화면 컴포넌트·브라우저 시연은 인터페이스가 화면 컴포넌트(렌더 산출물)인 단위에만, 그 외(순수 코드 api·cli 등)는 모듈·단위 테스트·실행 확인으로 대체.
- 구현할 단위 식별자.

없으면 묻기. 식별자 매칭이 안 되면 포맷별 후보를 제시 후 확정한다: SI wiki bundle 은 루트 인덱스 표(§4-§6), SI 단일 파일 legacy 는 §4 화면 목록 + §5·§6 헤더, 범용 포맷은 §4 산출 단위 목록.

**입력 spec 읽기 범위**: 경로·식별자 확보 후 아래 ①②③ 순서로 읽음.

- ① 구현 대상 단위(SI=§4.x/§5.x/§6.x, 범용=§4.x) 본문을 읽음. bundle(SI wiki bundle·범용 bundle)은 루트 인덱스로 대상 page 를 찾고 그 page 를 읽음.
- ② 그 본문이 이름 기반 참조(`[화면.X]`·`[단위.X]`·`[모델.X]`·`[타입.X]`·`[공통 정의.X]` 등)로 가리키는 §/page 를 재귀적으로(참조의 참조까지) 읽음.
- ③ 결정 맥락·작업 메모 전체(SI=루트 `spec-si.md` §10·§11, 범용=루트 `spec.md` §8·§9) 를 읽음.

근거: spec 은 다른 세션이 남긴 결정의 영속 산출물이라 안 읽은 영역의 결정·제약을 추측으로 덮어쓰면 안 되며, 그 결정 맥락(근거·기각 대안·검토 경계 등)은 전역이면 §10/§8·단위 한정이면 그 단위의 NOTE 나 인라인 `[OPEN]` 에 모이도록 spec 작성 스킬(SI=sd-spec-si / 범용=sd-spec) 형식이 규정함. 특히 결정 맥락의 "기각 대안·검토 경계" 는 이미 기각된 안을 재론하거나 미검토 영역을 검토된 양 다루지 않도록 하는 근거이므로 반드시 반영.

부분 검색·부분 읽기로 대상 본문만 보고 결정 맥락·참조 본문을 빠뜨리지 않음.

### 2단계: 외부 입력 점검

작업 대상 단위(SI=§4.x/§5.x/§6.x, 범용=§4.x)와 그 단위가 참조하는 §/page (SI=§5/§6/§7/§8/§9, 범용=§5/§6/§7) 항목을 점검:

- **섹션 `[OPEN]` (초안 부재)**: 섹션 본문이 재분석 포인터일 뿐 초안이 없음 → "spec 수정 절차" 적용.
- **본문 인라인 `[OPEN]`**: 결정 근거가 있으면 결정. 없으면 1건씩 질문. **답을 받는 즉시** (다음 OPEN·단계로 넘어가기 전에) "spec 수정 절차" 로 그 `[OPEN]` 문구를 확정 내용으로 치환·해소. 몰아 답변받아도 건별 반영 — 답만 안 채로 4·5단계로 진행 금지.
- **사용자 제공 예정 자료**: spec 본문에 사용자 회신 대기로 적힌 자료. 사용자 회신 후 진행.
- **묵시적 모호**: 명시 마커는 없지만 spec 본문이 분기·정의·정의식·경계 케이스를 다루지 않는 부분. 4단계 분해 중 발견 가능성 높음. 발견 시 본 단계로 회귀.

#### spec 수정 절차

spec 본문 수정이 필요한 경우(인라인 `[OPEN]` 해소·섹션 `[OPEN]` 해소·구조 변경·6단계 (b)(c) 분류 처리 등) 메인 LLM 이 직접 처리:

1. **spec 작성 스킬 SKILL.md 읽기** (SI=sd-spec-si / 범용=sd-spec) — 룰 인지: 부분 수정 인라인 경로·신뢰도 표기·형식 준수(§ 작성법 읽기)·이름 기반 참조 cascade. **단 도메인 답이 확정된 인라인 `[OPEN]` 을 그 자리 문구로 치환하는 경량 반영은 스킬 재독 없이 바로 편집** — 스킬 재독은 초안 작성·섹션 `[OPEN]` 해소·구조 변경·모순 정정 등 판단이 필요한 경우에만.
2. **그 스킬의 "부분 수정 (인라인)" 경로로 편집** — 정밀 반영(도메인 답이 이미 확정된 인라인 `[OPEN]`·6단계 결정 반영)은 바로 편집, 초안·판단 필요분(섹션 `[OPEN]` 초안·구조 변경·모순 정정)은 진단·초안 제시 → 합의 후 편집. 수정분은 사후 보고.
3. **의존 추적** — 그 스킬의 `[구현]` 마커 제거 절(SI=§4-6 / 범용=§4)의 의존 식별 규칙으로 수정된 § 를 의존으로 가진 구현 단위를 전수 추적. 본 작업 단위 자신은 제외 (작업 중).
4. **마커 제거** — 추적된 §4.x/§5.x/§6.x 의 `[구현]` 마커 제거 (bundle 은 루트 인덱스 파일(`spec-si.md`/`spec.md`) 표 `구현` 컬럼, 단일 파일 legacy 는 해당 섹션 헤더). 합의 절차도 같은 절 따름.

본 작업 단위(§4.x/§5.x/§6.x 자신)에는 9단계에서 `[구현]` 마커를 부착.

### 3단계: 보조 자료 수집 (있다면 활용)

부재로 워크플로를 멈추지 않음. framework 별 세부 지침은 본 SKILL.md 본문에 명시하지 않음 — 코드베이스 매뉴얼·기준 단위·테스트 환경이 발견되면 따르고, 부재 시 framework 자체 표준(Angular CLI 기본 구조·esbuild 기본 옵션 등)으로 채워도 됨. 도메인 결정·분기·계산식 등 spec 결정 사항은 본질 "임의 채움 금지" 적용.

#### A. 라이브러리·개발 매뉴얼

- `@simplysm/*` — SessionStart 가 주입한 활성 references 경로의 `README.md` 참조 후 "개발 매뉴얼" 진입.
- 그 외 framework — 코드베이스 안의 동등 위치 문서 참조.

#### B. 기준 단위 + 계층별 보강

풀 구현은 다층 흐름이 한 줄로 가야 일관성이 유지됨. 기존 단위 1개를 통째로 따라가는 방식이 아니라, 기준 단위 1개를 잡고 비어있거나 부적합한 계층만 다른 단위에서 보강.

**4계층**:

| 계층        | §4.x (화면)   | §5.x (자동 처리)        | §6.x (공통·기반 기능)                   |
| ----------- | ------------- | ----------------------- | --------------------------------------- |
| 도메인 모델 | 엔티티·필드   | 동일                    | 동일                                    |
| 데이터 접근 | 쿼리·서비스   | 동일                    | 동일                                    |
| 본체        | 화면 컴포넌트 | 자동 처리 로직 + 트리거 | 부수효과 후크 또는 설정·부트스트랩 구성 |
| 테스트      | 단위 테스트   | 동일                    | 동일                                    |

**범용 포맷**: 위 표는 SI 기준. 범용 spec 단위는 `kind` 로 본체 계층을 읽음 — api=공개 모듈·함수·타입 / workflow-step=처리 로직 + 트리거 / infra=부트스트랩·설정 구성 / 인터페이스가 화면 컴포넌트(렌더 산출물)인 단위=화면 컴포넌트. 도메인 모델·데이터 접근 계층은 단위가 실제 참조할 때만(없으면 "비어있음" 처리).

**기준 단위 선정** (같은 종류끼리 — SI=§4.x↔§4.x·§5.x↔§5.x·§6.x↔§6.x, 범용=같은 `kind` 끼리):

1. 도메인이 인접한 풀구현 단위 후보 탐색 (인접 도메인 정의는 spec 의 §4 단위 목록[SI=화면 목록 / 범용=산출 단위 목록] 분류·코드베이스 구조 등에서 자유 도출).
2. 후보가 1개 → 자동 채택. 2개 이상 → 후보 목록 제시 후 사용자에게 1회 질문. 0개 → 같은 종류 전 범위로 확장 후 동일 규칙 적용.
3. 전 범위에도 0개 → 기준 단위 없이 매뉴얼(A) + framework 자체 표준.

**계층별 보강**: 기준 단위의 4계층 각각을 다음과 같이 평가:

| 평가     | 의미                              | 처리                                      |
| -------- | --------------------------------- | ----------------------------------------- |
| 비어있음 | 해당 계층 파일이 기준 단위에 없음 | 같은 종류 다른 단위에서 그 계층 패턴 차용 |
| 부적합   | 있지만 spec 요구와 어긋남         | 같은 종류 다른 단위에서 그 계층 패턴 차용 |
| 적합     | 그대로 따름                       | 변경 없이 사용                            |

비어있음·부적합 계층은 같은 종류의 서로 다른 단위 2개 이상에서 동일하게 나타난 패턴을 자동 채택. 단위 1개에서만 쓰인 변종은 배제. 여러 패턴이 갈리면 사용자에게 1회 질문.

**읽기**: 기준 단위의 적합 계층 파일 + 보강 출처 파일을 모두 읽기. 5단계 작성 시 채택 패턴 기준이자 7단계 drift 점검의 입력.

#### C. 테스트 환경

단위 테스트 프로젝트 구분·실행 명령·mocking 패턴·dev 서버 실행 명령을 파악. 부재 시 framework 자체 표준으로 조합.

### 4단계: spec 분해 표

대상 단위(SI=§4.x/§5.x/§6.x, 범용=§4.x)와 참조 §/page (SI=§5/§6/§7/§8/§9, 범용=§5/§6/§7) 본문을 **항목 단위까지 분해**하여 표 작성. 표는 assistant 응답으로 출력 (이후 5·6단계의 입력). 일치 항목은 손대지 않음(차이만 작업).

**예시** (재고관리 도메인, 박스 입고 화면 §4.1 일부):

| 항목 ID | spec 인용                                  | 현재 코드 상태   | 판정   | 매핑 파일                                          | 의존 |
| ------- | ------------------------------------------ | ---------------- | ------ | -------------------------------------------------- | ---- |
| 1       | §4.1 항목 "박스 바코드" (필수·문자열·24자) | 없음             | 없음   | packages/app/src/screens/incoming/box-form.view.ts | -    |
| 2       | §4.1 동작 "스캔: 바코드 검증·박스 등록"    | 있음 (검증 누락) | 불일치 | (동일)                                             | 1    |

**항목 분해 단위**:

- 도메인 모델: 필드 1개당 1줄 (타입·제약·기본값).
- 계산식: 정의식 1개당 1줄 (좌변·우변·참조).
- 상태값·분기: 케이스 1개당 1줄 (조건·결과).
- UI 항목: 컬럼·필드·버튼 1개당 1줄.
- 동작·자동 처리: 트리거·결과 단위 1줄.

**컬럼**:

- **항목 ID**: 1, 2 ... (이후 의존 컬럼 참조용. 형식 자유).
- **spec 인용**: spec 위치(단일 파일은 § 위치, bundle 은 page 경로 + ref/절 위치) + 본문 문구.
- **현재 코드 상태**: 코드베이스 조사 결과 사실. 신규 호출 = "없음", 갱신 호출 = "있음(어떻게)". 조사는 워킹트리 파일을 직접 읽기·검색으로만 수행. 갱신 호출도 동일.
- **판정**: 없음 / 불일치 / 일치.
- **매핑 파일**: 이 항목이 작성·갱신될 파일 경로.
- **의존**: 다른 항목 ID.

분해 중 spec 본문이 정의·정의식·분기·경계 케이스를 다루지 않거나 모순되는 부분을 발견 → 2단계로 회귀("spec 수정 절차" 적용).

표 작성 완료 후 5단계 진입.

### 5단계: 작업 사이클

표의 (없음·불일치) 판정 항목만 의존 순서로 진행 (차이만 작업). 일치 항목은 손대지 않음.

**데모 골격 보존**: 작업 대상 매핑 파일이 데모 골격(sd-demo 산출물)이면 골격 구조를 유지하며 차이만 보강.

각 항목 시작 시 **테스트 작성 가능 여부**를 판정 (3-C 의 테스트 환경 이용):

| 분류               | 적용 대상                                     | 사이클                 |
| ------------------ | --------------------------------------------- | ---------------------- |
| 테스트 가능        | 도메인 로직·계산·변환·서버 함수·데이터 접근   | RED → GREEN → REFACTOR |
| 테스트 불가·비효율 | UI 시각·인터랙션·외부 서비스 실호출·환경 의존 | 구현 → REFACTOR        |

**테스트 단위 = spec 이 요구한 산출 단위. 내부 구현을 쪼개지 말 것**:

- 위 "테스트 가능" 분류는 그 처리가 **spec 이 독립 산출물로 요구한 단위**(공개 함수·API·계약)일 때 적용 — 그 경우 그 단위를 그대로 테스트.
- 요구사항이 "동작"(화면·자동 처리·공통·기반 기능·초기화 등)이고 변환·매핑·계산이 그 동작의 **내부 구현 조각**일 뿐이면, 동작 전체를 테스트 단위로 봄. 동작이 통째로 테스트 가능하면 그 단위로, 아니면(외부 I/O·환경 의존) "테스트 불가·비효율" 로 분류.
- **내부 구현 조각을 테스트하려고 별도 함수·파일·인터페이스로 분리·추상화하지 말 것.** spec 이 그 조각을 산출물로 요구하지 않았다면, 테스트는 그 조각을 떼낼 이유가 되지 못함.

**무엇을 단언하는가 — 불변식·제약만, 우연한 스냅샷 금지**:

- 깨지면 진짜 결함을 가리키는 불변식·제약만 단언 (필수값 비어있지 않음·유일성·1:1 관계·멤버십·빈 배열 금지·경계값 등).
- 임의 스냅샷 카운트·분포 총합 단언 금지 — 항목 수·집계 분포(`목록 N건`·`배지 164개`·`desktop 23개`)는 데이터·콘텐츠가 정상 변경되면 깨지는데 어떤 제약도 검증하지 못함. 다른 소스 길이로 맞추는 것(`toHaveLength(OTHER.length)`)도 자기참조라 무의미.
- REFACTOR·정리 단계에서 이런 브리틀 테스트를 발견하면 갱신하지 말고 제거. 카운트가 가리키던 의도가 실제 제약이면 그 제약을 단언하는 테스트로 교체 (예: 빈 배열이 문제면 전 항목 `length > 0` 단언).

**사이클 단계 정의**:

- **RED**: 테스트만 작성 → 단위 테스트 실행 → 실패 확인. **구현 파일은 손대지 않음.**
- **GREEN**: 테스트를 통과하는 **최소** 구현 → 단위 테스트 통과 확인.
- **REFACTOR**: 중복·가독성·3-B 채택 패턴·3-A 매뉴얼 정합 정리(채택 패턴·매뉴얼에서 벗어나는 임의 변형 금지) → 단위 테스트 통과 유지. 검토는 항상 수행하며, 정리 대상이 없으면 코드 변경이 없을 뿐 단계를 건너뛰지 않음.

작업 사이클 중 spec 미정의·모호 분기를 만나면 2단계로 회귀.

### 6단계: spec 대조 (서브에이전트 위탁)

5단계의 모든 항목 완료 후, 별도 서브에이전트에 위탁해 spec ↔ 현재 코드 전체를 독립 대조. 같은 LLM 의 자체 검증에서 발생하는 표면적 확인 편향을 제거하는 목적.

**대조는 작업 단위 전체를 대상으로 함.** 신규·갱신 호출 무관, "이번 변경분만" 식 스코프 제한 없음.

#### 서브에이전트 호출

- 독립 서브에이전트 1개로 펼침.
- `subagent_type`: `sd:sd-verify` (검증 전용).
- 추론·도메인 어휘를 풀어 보고해야 하므로 충분한 능력의 서브에이전트를 씀(검색 전용 에이전트 회피).
- `description`: `sd-impl spec 대조`.
- `prompt`: 아래 입력 패키지 (그대로 복사 후 `<…>` 부분만 채움).

```
sd-impl 의 spec ↔ 코드 독립 대조를 수행해줘.

**대상**:
- spec 경로: <단일 spec.md 절대경로 또는 bundle(SI wiki bundle·범용 bundle) 루트 절대경로 또는 해당 bundle 의 루트 인덱스(spec-si.md/spec.md) 절대경로>
- 단위 식별자: <§4.x / §5.x / §6.x>

**참조 자료**:

(1) 4단계 spec 분해 표 (인라인):

| 항목 ID | spec 인용 | 현재 코드 상태 | 판정 | 매핑 파일 | 의존 |
| ------- | --------- | -------------- | ---- | --------- | ---- |
| ...     | ...       | ...            | ...  | ...       | ...  |

(2) 현재 구현 파일 목록 (절대경로):
- <file1>
- <file2>
- ...

**작업**:

1. spec 의 §<단위> 본문 + 참조 §/page (SI=§5/§6/§7/§8/§9, 범용=§5/§6/§7) 항목을 다시 읽기. bundle(SI wiki bundle·범용 bundle)이면 루트 인덱스(`spec-si.md`/`spec.md`)에서 대상 page 를 찾고 참조 page 까지 읽기.
2. 현재 구현 파일을 모두 읽기.
3. spec ↔ 코드를 항목 단위로 1:1 대조 (단위 전체 대상. "이번 변경분만" 식 스코프 제한 없음).
4. 차이 발견 시 아래 3분류로 보고:

   - (a) **코드 위반**: spec 명확한데 코드가 빠뜨림·다름.
   - (b) **spec 내부 모순**: §A 정의 vs §B 정의 충돌. (양쪽 인용 명시)
   - (c) **spec 미정의 + 코드 임의 채움**: spec 본문에 정의·분기·경계 케이스 명시 없는데 코드가 채움.

5. 보고 형식 (각 차이 1건마다):

   ### 차이 N: <도메인 어휘로 표현된 한줄 요약>
   - 분류: (a) / (b) / (c)
   - spec 위치: §X.x line Y
   - spec 인용: "..."
   - 코드 위치: <file:line>
   - 코드 동작: <도메인 어휘로>
   - 비고: (b) 면 모순 상대 인용 함께

6. 차이 0건이면 `차이 없음, 검증 통과` 1줄만 응답.

**제약**:

- 보고 본문에 코드 식별자(변수명·SQL 함수명·타입 키워드 등) 노출 금지. 도메인 어휘로 풀어 쓸 것. 단 공개 계약(공개 함수명·CLI 옵션명 등)은 그대로 인용 가능.
- "코드가 spec 위반" 으로 단정 금지. 3분류 중 어디에 해당하는지 명시.
- spec 본문에 인용할 수 있는 문구가 없으면 (b)(c) 후보로 처리.

**산출**: 위 3분류 보고 목록 또는 `차이 없음, 검증 통과`.
```

#### 결과 처리

서브에이전트 출력을 받은 후 분류별로 처리:

- **(a) 코드 위반**: 5단계 사이클로 재진입하여 코드 수정.
- **(b) spec 내부 모순**: 사용자에게 1건씩 보고 (모순 양쪽 인용 + 어느 쪽이 합리적인지 의견) → 처리 방향 묻기 (spec 수정 / 코드 정정) → spec 수정 시 2단계 "spec 수정 절차" 적용.
- **(c) spec 미정의 + 코드 임의 채움**: 사용자에게 1건씩 질문 → 결정 수령 → 2단계 "spec 수정 절차" 로 인라인 결정 반영 → 5단계 사이클 재진입.

(b)(c) 모두 한꺼번에 묶음 보고 금지. 1건씩 합의.

처리 완료 후 6단계 재실행 (재대조). 차이 0건 확인 후 7단계 진입.

### 7단계: 코드 정리

- **횡단 중복**: 작업 사이클 사이에 흩어진 동일 로직 합치기.
- **계층별 drift 점검**: 다항목 작업 누적으로 5단계의 3-B 채택 패턴에서 이탈한 계층이 있는지 4계층 전체를 횡단 점검. 이탈분만 채택 패턴으로 수정 (개별 항목 정합은 5단계에서 선반영).
  - 도메인 모델: 필드·타입·제약·네이밍 패턴 일치.
  - 데이터 접근: 함수 시그니처·쿼리 패턴·에러 처리 일치.
  - 본체: 컴포넌트·트리거·처리 단계·핸들러·의존성 패턴 일치.
  - 테스트: 러너·assertion·mock 패턴 일치.
- **불필요한 코드**: 미사용 import·변수·주석, 요구가 없는 옵션·추상화 제거. 작업 결과로 어디서도 참조되지 않는 파일도 포함 (검사 범위는 전체 워크스페이스). **단 파일 단위 삭제는 후보 목록을 사용자에게 보고 → 확정분만 삭제** (dynamic import·마이그레이션·문서 자산 등 정적 참조로 탐지 안 되는 보존 대상은 사용자가 제외 지시).
- **테스트 가치 스윕**: 이번 작업으로 생성·수정한 테스트를 전수 훑어, 동작·계약·불변식·예외를 단언하지 않는 개발용 임시 테스트는 제거. 대상 예: 구현 세부·중간 형태 단언, 존재/텍스트 유무만 확인, 상위 동작 테스트에 이미 흡수된 디딤돌 테스트. 판정: 깨졌을 때 진짜 결함을 가리키는가 — 아니오면 삭제 (5단계 사이클 중 놓친 스냅샷 브리틀 테스트도 여기서 최종 수거).
- **매뉴얼 규약 정합 (횡단)**: 3-A 매뉴얼 규약 중 여러 항목·계층에 걸쳐 작성 후에만 드러나는 위반만 점검·수정 (개별 항목 준수는 5단계에서 선반영).

정리 후 단위 테스트 재실행하여 회귀 없음을 확인.

### 8단계: 시연 검증

**시연 스킵 조건**: 대상 단위에 세션 시작 시점부터 이미 `[구현]` 마커가 있었고(이전 시연 완료) + 이번 세션이 코드 파일을 하나도 생성·수정하지 않음(5단계 편집 0건 + 6단계 (a) 코드 위반 0건 + 7단계 정리 편집 0건) → 본 단계 스킵 후 9단계 진입. 마커가 없던 단위(첫 검증)는 코드 변경이 없어도 시연 수행.

**범용 포맷 / 비-UI 단위**: 브라우저 시연 대신 — 단위 테스트 통과 + 실행 가능 산출물이면 실제 실행 확인(api=대표 호출 예시 실행, cli=명령 실행, infra=부팅 후 구성 반영 확인). dev 서버·브라우저 불요. 아래 브라우저 시연은 인터페이스가 화면 컴포넌트(렌더 산출물)인 단위에만 적용 — 그 외(순수 코드 api·cli·infra 등)는 이 확인으로 갈음 후 9단계 진입.

사용자에게 요청: "**dev 서버**를 실행하고 접속 주소를 알려달라."

사용자가 띄워 주소를 회신할 때까지 대기. 사용자가 본 단계의 스킵을 지시하거나 시연 불가 환경이 명시되면 본 단계 스킵 후 9단계 진입.

주소 회신 후 브라우저 자동화 도구로 §4.x/§5.x/§6.x 동작 시나리오를 직접 시연:

- 기능 개요·동작의 사용자 흐름을 1회씩 수행.
- 화면 항목·와이어프레임 위치와 실제 렌더 결과를 비교.
- §5.x (자동 처리) 는 트리거 발생 → 결과 확인.
- §6.x (공통·기반 기능): 부수효과 동작은 트리거 발동 → 결과·기록 확인, 상시 구성은 앱 부팅 후 구성 반영 확인.

회귀 발견 시 5단계로 회귀 → 수정 → 재시연.

### 9단계: 완료 보고

**결정 반영 최종 게이트** (마커 부착 전, 메인 LLM 직접 — 대화 맥락을 아는 주체만 가능하므로 서브에이전트 위탁 불가): 이번 세션에 내린·번복한 결정(질문 답변·기존 확정 번복·자체 결정 신규 사항)을 전수 훑어, 각각이 spec 본문에 반영됐는지 대조한다. 미반영분 발견 시 마커 부착 전에 2단계 "spec 수정 절차" 로 반영한 뒤 진행한다. 본질 룰 "결정 즉시 반영" 을 놓친 건을 완료 직전에 수거하는 사후 차단 — 6단계 코드↔spec 대조는 대화 맥락을 모르므로 이 공백을 못 메운다.

- 대상 spec 의 해당 구현 단위(SI=§4.x/§5.x/§6.x, 범용=§4.x)에 `[구현]` 마커를 부착. **bundle**(SI wiki bundle·범용 bundle)은 루트 인덱스(`spec-si.md`/`spec.md`) 표(SI=§4/§5/§6, 범용=§4)의 해당 단위 행 `구현` 컬럼에 표기하고, **단일 파일 legacy** 는 해당 섹션 헤더에 붙인다. 이미 `[구현]` 이 있으면 그대로 둠 (날짜·`[확정]` 부착 안 함).
- **plan.md(개발계획서) 경유 호출이면** 그 plan.md 의 해당 TASK 상태를 `Done (yyyy-MM-dd)` 로 갱신 — 마커 부착과 같은 시점에 수행하고 누락하지 않음. 다음 작업 안내는 plan 의 TASK 번호순(§8 실행 순서와 일치)을 따름.
- 만들거나 갱신한 파일 목록 보고 (마커를 부착한 spec 파일/page 포함).
- 본 세션에서 2단계·6단계 "spec 수정 절차" 로 의존 구현 단위(SI=§4.x/§5.x/§6.x, 범용=§4.x) 마커가 제거된 항목이 있으면 영향 단위 목록 보고 (재구현 필요 알림). 없으면 생략.
- 시연에서 사용자 확인이 끝나면 종료.
