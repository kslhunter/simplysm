# sd-impl

## spec 포맷

루트 인덱스가 `spec-si.md` 면 SI, `spec.md` 면 범용입니다.

| 표기           | SI                                 | 범용       |
| -------------- | ---------------------------------- | ---------- |
| 구현 단위      | 화면 / 자동 처리 / 기반            | §4.x       |
| 참조 대상      | 공통 정의 / 모델 / 외부 인터페이스 | §5/§6/§7   |
| 결정 맥락      | 루트 결정 맥락, 작업 메모           | 루트 §8, §9 |
| spec 작성 스킬 | sd-spec-si                         | sd-spec    |

## 본질 (횡단 룰 — 전 단계 적용)

- 임의 채움 금지 — 분기, 정의, 값, 계산식, 경계를 만나면 `결정 근거` 유무로 판정하세요.
  - 있으면 그에 따라 채우고, 없거나 모호하면 즉시 멈춰 제안해야 합니다.
  - 추정, 단발 사례, "추론 가능"을 근거로 대체하지 마세요.
  - spec 과 사용자 발언이 유일한 근거입니다. 코드 추론으로 채우지 마세요.
- 결정 즉시 반영 — 구현 중 spec 반영이 필요한 결정이 서면 다음 항목, 단계로 넘어가기 전에 그 자리에서 spec 에 반영해야 합니다.
  - 기억만 한 채 진행하지 마세요. 여러 건이 몰려도 건별로 반영하세요.
  - 반영 대상은 3경로입니다.
    - `[OPEN]`, 모순, 미정의를 물어 받은 답 (마커 해소).
    - 기존 확정을 사용자가 번복 (확정 문구 치환).
    - `결정 근거`가 확실해 스스로 채웠으나 spec 에 아직 명문화되지 않은 신규 결정.
- YAGNI — spec 에 없는 구현을 추가하지 마세요. 필수로 판명되면 제안하세요.
- 문서 비참조 — spec, plan 은 언제든 삭제, 전면 재작성될 수 있습니다. 코드 어디에도(주석, 테스트 이름, 문자열, 식별자) spec 문구, 항목 ID, § 위치 등 문서로의 연결점을 남기지 마세요.
  - 방향은 문서→코드 단방향입니다. 코드→문서 역참조는 문서 갱신 시 낡은 사본이 되어 어긋납니다.
  - 주석, 테스트 이름은 코드 자체의 동작만 서술하세요.
- 완결성 — `[구현]` 은 구현 단위 전체 완결에만 부착해야 합니다.
  - 통째로 완성이 불가하면 "spec 수정 절차"로 단위 경계를 독립 완성 가능한 크기로 분할하거나 적절한 곳에 흡수하세요.

## spec 수정 절차

전 단계에서 spec 본문 수정이 필요한 모든 경우를 메인이 직접 처리합니다:

1. spec 작성 스킬 SKILL.md 읽기 — 재진입, 부분 수정 경로, 신뢰도 표기, 이름 참조 cascade, 단일 출처(canonical 1곳 수정 + 복제 잔재 통합), `[구현]` 제거 판정을 인지하세요.
   - 단 도메인 답이 확정된 인라인 `[OPEN]` 의 문구 치환 같은 경량 반영은 재독 없이 바로 편집합니다.
2. 그 경로로 편집 — 확정분은 바로 편집하고, 초안, 구조 변경, 모순 정정은 진단, 초안 제시 후 합의를 거쳐 편집하세요. 수정분은 사후 보고합니다.
3. 의존 추적 — 수정한 page 를 의존으로 가진 구현 단위를 전수 추적하세요 (본 작업 단위 자신은 제외).
4. 마커 판정 — 추적된 단위마다 구현 변경 필요 여부로 판정해, 제거 대상만 루트 인덱스 `구현` 컬럼에서 제거하세요.

## 워크플로

### 1단계: 입력 확보

대상 spec 경로와 구현 단위 식별자를 확보하세요. 없으면 묻고, 매칭이 안 되면 후보를 제시해 확정합니다.

읽기 범위는 아래 순서입니다. 부분 검색으로 결정 맥락, 참조 본문을 빠뜨리지 마세요.

1. 구현 단위 본문.
2. 그 본문이 이름 참조(`[화면.X]`, `[모델.X]`, `[공통 정의.X]` 등)로 가리키는 page 를 재귀적으로(참조의 참조까지).
3. 루트 결정 맥락 전체 — 기각된 안을 재론하거나 미검토 영역을 검토된 양 다루지 않도록 반드시 감안해야 합니다. 단위 한정 맥락은 그 page 의 NOTE, 인라인 `[OPEN]` 에 있습니다.

### 2단계: 외부 입력 점검

구현 단위와 참조 항목을 점검하세요:

- page 전체가 `[OPEN]` (본문이 재분석 포인터일 뿐 초안 없음) — "spec 수정 절차"로 갑니다.
- 인라인 `[OPEN]` — `결정 근거` 있으면 결정하고, 없으면 1건씩 질문하세요. 답을 받는 즉시 "spec 수정 절차"로 확정 내용으로 치환해야 합니다.
- 사용자 제공 예정 자료 — 회신 후 진행하세요.
- 묵시적 모호 (마커는 없으나 분기, 정의, 계산식, 경계를 다루지 않음) — 이후 단계에서 발견하면 본 단계로 회귀하세요.

### 3단계: 보조 자료 수집

부재로 멈추지 마세요. 없으면 framework 자체 표준(Angular CLI 기본 구조, esbuild 기본 옵션 등)으로 채웁니다.

- A. 라이브러리, 개발 매뉴얼 — `@simplysm/*` 이면 SessionStart 가 주입한 활성 references 경로의 `README.md` 를 읽고 "개발 매뉴얼"로 진입하세요.
  - 그 외 framework 는 코드베이스 안 동등 위치 문서를 봅니다.
- B. 기준 단위 + 계층별 보강 — 아래에 설명합니다.
- C. 테스트 환경 — 단위 테스트 프로젝트 구분, 실행 명령, mocking 패턴, dev 서버 실행 명령.

기준 단위 + 계층별 보강: 풀 구현은 다층 흐름이 일관되게 이어져야 합니다.
기존 구현물 중 기준 단위 1개를 잡고, 비어있거나 부적합한 계층만 다른 단위에서 보강하세요.

- 4계층은 도메인 모델(엔티티, 필드), 데이터 접근(쿼리, 서비스), 본체, 테스트입니다.
  - 본체는 단위 종류에 따라 달라집니다.
    - 화면 컴포넌트 / 자동 처리 로직+트리거 / 부수효과 후크, 부트스트랩 구성.
    - 범용 포맷은 `kind` 로 읽습니다 (api=공개 모듈, 함수, 타입 / workflow-step / infra).
  - 도메인 모델, 데이터 접근은 구현 단위가 실제 참조할 때만 해당합니다.
- 기준 단위 선정은 같은 종류끼리 합니다. 도메인이 인접한 풀 구현 단위 후보를 탐색해 1개면 자동 채택, 2개 이상이면 목록 제시 후 1회 질문, 0개면 같은 종류 전 범위로 확장하세요.
  - 전 범위에도 0개면 기준 단위 없이 A + framework 표준으로 진행합니다.
- 보강은 기준 단위의 각 계층을 평가해 비어있음, 부적합이면 같은 종류 다른 단위에서 그 계층 패턴을 차용하고, 적합이면 그대로 따릅니다.
  - 차용 패턴은 서로 다른 단위 2개 이상에서 동일하게 나타난 것만 자동 채택하세요.
  - 1개에서만 쓰인 변종은 배제하고, 갈리면 1회 질문합니다.
- 읽기는 기준 단위의 적합 계층 파일과 보강 출처 파일을 모두 대상으로 합니다. 5단계 작성 기준이자 7단계 drift 점검 입력입니다.

### 4단계: spec 분해 표

구현 단위와 참조 본문을 항목 단위까지 분해해 표로 출력하세요 (5, 6단계 입력).

| 항목 ID | spec 인용 | 현재 코드 상태 | 판정 | 매핑 파일 | 의존 |
| ------- | --------- | -------------- | ---- | --------- | ---- |

- 분해 단위는 아래 각 1개당 1줄입니다.
  - 도메인 모델 필드.
  - 계산식.
  - 상태값, 분기 케이스.
  - UI 컬럼, 필드, 버튼.
  - 동작, 자동 처리의 트리거, 결과.
- spec 인용은 page 경로 + 위치 + 본문 문구입니다.
- 현재 코드 상태는 워킹트리 파일 직접 읽기, 검색으로만 조사해야 합니다. 신규는 "없음", 갱신은 "있음(어떻게)"입니다.
- 판정은 없음 / 불일치 / 일치입니다.

### 5단계: 작업 사이클

- 없음, 불일치 항목만 의존 순서로 진행하세요.
- 일치 항목은 손대지 마세요.
- 매핑 파일이 데모 골격(sd-demo 산출물)이면 골격 구조를 유지하며 차이만 보강합니다.

각 항목 시작 시 테스트 작성 가능 여부를 판정해야 합니다 (3-C 이용):

| 분류               | 적용 대상                                     | 사이클                 |
| ------------------ | --------------------------------------------- | ---------------------- |
| 테스트 가능        | 도메인 로직, 계산, 변환, 서버 함수, 데이터 접근   | RED → GREEN → REFACTOR |
| 테스트 불가, 비효율 | UI 시각, 인터랙션, 외부 서비스 실호출, 환경 의존 | 구현 → REFACTOR        |

테스트 단위는 spec 이 독립 산출물로 요구한 단위입니다. 내부 구현을 쪼개지 마세요:

- "테스트 가능" 분류는 그 처리가 spec 이 독립 산출물로 요구한 단위(공개 함수, API, 계약)일 때 적용합니다. 그 단위를 그대로 테스트하세요.
- 요구가 "동작"(화면, 자동 처리, 기반, 초기화 등)이고 변환, 매핑, 계산이 그 내부 구현 조각이면 동작 전체를 테스트 단위로 보세요.
  - 통째로 테스트 가능하면 그 단위로 하고, 아니면 "테스트 불가, 비효율"로 분류합니다.
- 내부 조각을 테스트하려고 별도 함수, 파일, 인터페이스로 분리, 추상화하지 마세요.

무엇을 단언하는지는 불변식, 제약만으로 정합니다:

- 깨지면 진짜 결함을 가리키는 불변식, 제약만 단언하세요 (필수값 비어있지 않음, 유일성, 1:1 관계, 멤버십, 빈 배열 금지, 경계값 등).
- 임의 스냅샷 카운트, 분포 총합을 단언하지 마세요. 데이터가 정상 변경되면 깨지는데 어떤 제약도 검증하지 못합니다. 다른 소스 길이로 맞추는 것도 자기참조라 무의미합니다.
- 발견하면 갱신하지 말고 제거하세요. 카운트가 가리키던 의도가 실제 제약이면 그 제약을 단언하는 테스트로 교체합니다.

사이클:

- RED — 테스트만 작성하고 실행해 실패를 확인하세요. 구현 파일은 손대지 마세요.
- GREEN — 통과하는 최소 구현을 하고 통과를 확인하세요.
- REFACTOR — 중복, 가독성, 3-B 채택 패턴, 3-A 매뉴얼 정합을 정리하고 통과를 유지하세요.
  - 임의로 변형하지 마세요.
  - 정리 대상이 없으면 코드 변경이 없을 뿐이니 단계를 건너뛰지 마세요.

### 6단계: spec 대조 (독립 서브에이전트)

자체 검증의 확인 편향을 제거하기 위해 독립 서브에이전트(`subagent_type: sd:sd-verify`) 1개로 spec 과 현재 코드를 대조하세요.

- 4단계 분해 표와 현재 구현 파일 목록을 프롬프트에 넣고, 서브에이전트가 spec 본문과 그 참조 page 를 다시 읽어 대조하게 하세요.
- 대조 범위는 구현 단위 전체입니다. "이번 변경분만" 식 제한을 두지 마세요.

차이는 아래 3분류로 받으세요:

- (a) 코드 위반 — spec 이 명확한데 코드가 빠뜨리거나 다릅니다. 5단계로 재진입해 코드를 수정하세요.
- (b) spec 내부 모순 — 두 곳의 정의가 충돌합니다(양쪽 인용). 1건씩 보고하고(어느 쪽이 합리적인지 의견 포함) 방향을 결정한 뒤, spec 수정 시 "spec 수정 절차"를 따르세요.
- (c) spec 미정의 + 코드 임의 채움 — spec 에 없는 정의, 분기, 경계를 코드가 채웠습니다. 1건씩 질문해 "spec 수정 절차"로 반영한 뒤 5단계로 재진입하세요.

- 보고에 코드 식별자를 노출하지 말고 도메인 어휘로 받으세요.
- (b)(c)를 묶어 보고하지 말고 1건씩 합의해야 합니다.
- 처리 후 6단계를 재실행해 차이 0건을 확인하고 7단계로 가세요.

### 7단계: 코드 정리

- 횡단 중복 — 사이클 사이에 흩어진 동일 로직을 합치세요.
- 계층별 drift — 다항목 누적으로 3-B 채택 패턴에서 이탈한 계층이 있는지 4계층 전체를 횡단 점검하고 이탈분만 수정하세요.
  - 점검 축은 계층별로 아래와 같습니다.
    - 도메인 모델: 필드, 타입, 제약, 네이밍.
    - 데이터 접근: 시그니처, 쿼리, 에러 처리.
    - 본체: 컴포넌트, 트리거, 핸들러, 의존성.
    - 테스트: 러너, assertion, mock.
- 불필요한 코드 — 미사용 import, 변수, 주석, 요구 없는 옵션, 추상화, 어디서도 참조되지 않는 파일을 제거하세요 (검사 범위는 전체 워크스페이스).
  - 파일 단위 삭제는 후보를 보고한 뒤 확정분만 삭제해야 합니다.
- 테스트 가치 스윕 — 이번 작업으로 생성, 수정한 테스트를 전수 훑어, 동작, 계약, 불변식, 예외를 단언하지 않는 임시 테스트를 제거하세요.
  - 대상 예: 구현 세부, 중간 형태 단언, 존재/텍스트 유무만 확인, 상위 테스트에 흡수된 디딤돌, 5단계에서 놓친 브리틀 테스트.
  - 판정 기준은 깨졌을 때 진짜 결함을 가리키는가입니다.
- 매뉴얼 규약 정합 — 여러 항목, 계층에 걸쳐 작성 후에만 드러나는 위반만 점검하세요.

정리 후 단위 테스트를 재실행해 회귀 없음을 확인해야 합니다.

### 8단계: 시연 검증

- 스킵 조건 — 구현 단위에 세션 시작 시점부터 `[구현]` 마커가 있었고(이전 시연 완료) 이번 세션 코드 파일 생성, 수정이 0건이면 본 단계를 통째로 스킵하세요.
  - 마커가 없던 단위(첫 검증)는 코드 변경이 없어도 시연해야 합니다.
- 방식 — 화면 단위는 아래 브라우저 시연을 따릅니다.
  - 비-화면 단위는 단위 테스트 통과 + 실제 실행 확인으로 갈음하세요.
    - api: 대표 호출 실행.
    - cli: 명령 실행.
    - infra: 부팅 후 구성 반영 확인.
    - 자동 처리: 트리거 발생 후 결과 확인.
    - 기반: 부수효과는 트리거 발동 후 기록 확인, 상시 구성은 부팅 후 반영 확인.
- LLM 관찰 불가 GUI (데스크톱 앱 창, 네이티브 GUI) — 시연 주체는 사용자입니다. "내가 시연했다"고 보고하지 마세요.
  - 시연할 항목, 입력, 기대결과를 구체적으로 안내하고 사용자 회신으로 검증하세요.

브라우저 시연:

- 사용자에게 dev 서버 실행과 접속 주소를 요청해 회신까지 대기하세요 (사용자가 스킵을 지시하거나 시연 불가 환경이면 스킵합니다).
- 주소를 받으면 기능 개요, 동작의 사용자 흐름을 1회씩 수행하고, 화면 항목, 와이어프레임 위치와 실제 렌더 결과를 비교하세요.
- 회귀 발견 시 5단계로 재진입해 수정하고 재시연합니다.
