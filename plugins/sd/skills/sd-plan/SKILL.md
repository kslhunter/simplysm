# sd-plan

개발 착수 전, 사용자 발언·제공 자료·현재 코드베이스·공식 문서를 근거로 브레인스토밍과 조사를 수행하고, 실행 가능한 개발계획서 `plan.md` 를 작성함.

**핵심 목적**: 구현자가 추측하지 않고 개발을 시작할 수 있도록 범위·비범위·결정·리스크·작업 순서·검증 기준을 한 파일에 고정함.

## 입출력

- **Input**: 사용자 요청, 대화 중 확정된 내용, 사용자가 제공한 자료, 현재 코드베이스, 공식 문서·표준.
- **Output**: `.plans/{yyMMddHHmmss}_{제목}/plan.md` 1개. (입력에 spec bundle 이 있으면 "입력 spec 역반영" 절에 따라 그 spec page 도 함께 편집될 수 있음 — 산출 자체는 plan.md.)
- **폴더**:
  - `{yyMMddHHmmss}`: 0단계에서 경로를 계산하는 시점의 현재 로컬 시각. 시·분·초를 임의로 지어내지 않고 명령으로 실제 시각을 조회해 사용함(0단계 참조).
  - `{제목}`: 사용자와 합의한 작업 제목. 한국어·영문·숫자·공백·`_`·`-` 허용함. 파일시스템 금지 문자(`\ / : * ? " < > |`)는 제거하거나 의미가 보존되는 문자로 치환함.
  - 제목이 불명확하면 작성 전 사용자에게 물음.
  - 같은 제목의 기존 plan 폴더(`.plans/*_{제목}`)가 있으면 사용자에게 알리고 진행 여부를 확인함.

## 본질

- **독립 계획서**: 특정 선행 문서 형식에 의존하지 않음. 입력 자료가 있으면 근거로 활용하되, 별도 문서 체계의 하위 산출물로 취급하지 않음.
- **명세 문서 입력 시 목표 고정**: 입력 자료가 구현 상태 마커([구현]/미구현)를 가진 명세 문서(spec bundle 등)이면, 계획의 목표는 대상 미구현 단위를 하나씩 구현 완료하고 해당 섹션에 마커를 찍어 미구현을 0 으로 만드는 것으로 잡음. 미구현 단위 ↔ TASK 를 1:1 기본으로 대응시킴.
- **자동 구현 금지**: `plan.md` 작성·검증·보고 후 정지함. 사용자가 별도 구현 지시를 하기 전까지 코드 수정·빌드·테스트 실행으로 넘어가지 않음.
- **근거 없는 결정 금지**: `결정 근거`가 부족하면 `[OPEN]` 으로 남기거나 사용자에게 물음.
- **브레인스토밍은 결정이 아님**: 발산 단계에서는 선택지와 근거를 모을 뿐이며, 수렴 단계에서 근거 있는 항목만 채택함.
- **기법 최소 적용**: 아래 기법 라우터에서 필요한 것만 사용함. 모든 기법·모든 섹션을 억지로 채우지 않음.
- **범위 방어**: 포함 범위뿐 아니라 비범위를 반드시 적음. "나중에 필요할 수 있음" 은 계획에 넣지 않음.
- **작업 단위**: 내부 구현 조각이 아니라 검증 가능한 산출물 단위로 나눔.
- **TASK 완결성**: 각 TASK 는 그 단위의 구현 + 테스트·검증(화면이면 시연 포함) + 그 단위로 완결된 부분의 원천 자료 상태 반영(마커·문서 갱신 등)을 모두 포함해 TASK 안에서 완결함.
  - 검증·시연·문서 갱신만 모아 놓은 후처리 전용 TASK 를 만들지 않음.
  - 선행 **의존** TASK 가 완결(Done)되기 전에는 그에 의존하는 후속 TASK 에 착수하지 않는 것을 전제로 순서를 짬. 상호 의존이 없는 TASK 는 병렬 착수 가능함.
- **불확실성 표면화**: `[OPEN]` 은 숨기지 않음. Blocking `[OPEN]` 또는 Blocking 가정(ASM)이 있으면 상태를 `Blocked` 로 둠.

## 입력 spec 역반영

**입력 자료에 spec bundle(SI 루트 `spec-si.md` / 범용 루트 `spec.md`)이 포함된 경우에만 발동함. spec 없이 시작한 plan 에는 본 절 전체가 해당 없음.**

plan 도중 확정·변경한 요구 수준 결정(spec 의 _무엇·왜_ — 값·분기·정의·`[OPEN]` 해소·기존 확정 번복·신규 요구)은 그 자리서 입력 spec 에 편집 반영함. spec 편집은 코드 구현이 아니라 spec 정합 유지이므로 "자동 구현 금지"의 예외임. 순수 구현방법 결정(라이브러리 선택 등 추상레벨 밖)은 반영 대상 아님 — plan.md DEC·spec 결정 맥락에만 둠.

### spec 역반영 절차 (sd-impl "spec 수정 절차"와 동형)

1. **spec 작성 스킬 SKILL.md 읽기** (입력 루트 `spec-si.md`=sd-spec-si / `spec.md`=sd-spec) — 부분 수정 인라인 경로·신뢰도 표기·형식 준수·이름 기반 cascade·`[구현]` 마커 제거·단일 출처 불변식(SSOT — canonical 1곳 수정, 복제 잔재는 통합 후 이름 참조로 대체) 룰 인지. 단 확정된 인라인 `[OPEN]` 의 문구 치환 같은 경량 반영은 재독 없이 바로 편집함.
2. **그 스킬 "부분 수정 (인라인)" 경로로 편집** — 정밀 반영은 바로, 초안·구조 변경·모순 정정은 진단·초안 제시 후 편집함.
3. **이름 기반 참조 cascade + 마커 제거** — 그 스킬 마커 제거 절 의존 식별 규칙으로, 수정한 §를 의존으로 가진 구현 단위의 `[구현]` 마커를 전수 제거함.

## 워크플로

### 0단계: 접수·경로 확정

1. 작업 대상과 목적을 한 문장으로 확정함.
2. 제목을 확정하고, 현재 로컬 시각을 명령(`Get-Date`·`date` 등)으로 조회해 산출 경로 `.plans/{yyMMddHHmmss}_{제목}/plan.md` 를 계산함. 시·분·초를 임의로 지어내지 않음. 조회한 이 시각을 폴더 타임스탬프·Plan ID·메타데이터 생성 시각에 동일하게 사용함.
3. 계획 작성에 필요한 입력 자료 목록을 만듦.
4. 다음이 불명확하면 시작 전 사용자에게 물음.
   - 무엇에 대한 계획인지
   - 사용자가 명시한 필수 자료가 어디 있는지

### 1단계: 자료 수집

- 제공 자료와 관련 파일을 직접 읽음.
- 코드베이스 조사는 현재 워킹 트리 기준으로 수행함.
- `.back/` 및 `.gitignore` 등재 경로는 사용자 명시 없이는 읽지 않음.
- 의존성 조사는 `node_modules` 가 아니라 lock 파일과 package manifest 를 우선함.
- 외부 라이브러리·표준 동작이 계획에 영향을 주면 공식 문서 또는 표준을 확인함.

### 2단계: 발산 조사

범위가 작으면 메인 에이전트가 직접 수행함. 범위가 넓거나 관점이 독립적이면 병렬 독립 서브에이전트로 조사함.

권장 조사 관점:

| 관점      | 조사 내용                                           |
| --------- | --------------------------------------------------- |
| 요구·자료 | 사용자 요청, 제공 자료, 빠진 정보, 모호한 표현      |
| 코드 패턴 | 유사 구현, 파일 구조, 테스트 방식, 네이밍·계층 패턴 |
| 외부 근거 | 공식 문서, 표준, API 제약                           |
| 리스크    | 데이터 변경, 호환성, 배포, 롤백, 검증 난점          |

서브에이전트 제약:

- 보고 전용임. 파일 수정 금지.
- 최종 결정 금지.
- 근거 없는 추정은 `[OPEN]` 또는 `확인 불가` 로 보고함.
- 조사 결과에는 근거 위치를 포함함.

### 3단계: 기법 라우터

작업 성격에 맞는 기법만 선택함.

| 상황                           | 사용할 기법                      | plan.md 에 남길 산출                                                         |
| ------------------------------ | -------------------------------- | ---------------------------------------------------------------------------- |
| 문제·해결 방향이 모호함        | Double Diamond / Design Thinking | 문제 프레이밍, 탐색한 대안, 선택·기각 이유                                   |
| 목표와 구현 항목의 연결이 약함 | Impact Mapping                   | 목표, actor, 기대 변화, deliverable, 핵심 가정                               |
| UI·사용자 흐름 중심            | User Story Mapping               | 사용자 단계, 핵심 흐름, release slice, 누락 흐름                             |
| 복잡한 업무·도메인 흐름        | Event Storming 초안              | 이벤트, 명령, 정책, 예외, hotspot. 이해관계자 검증 전에는 확정으로 쓰지 않음 |
| 시스템 경계·외부 연동 중심     | C4 / Context Mapping             | actor, system/container/component, 인터페이스, 책임 경계                     |
| 중요한 기술·정책 결정          | ADR/RFC 후보                     | 맥락, 선택지, 결정, 결과, 재검토 조건                                        |
| 버그·실패 해결 계획            | RCA                              | 최소 2개 원인 가설, 근거, 채택·기각, 해결 방향                               |
| 우선순위·범위 조정             | MoSCoW                           | Must/Should/Could/Won't, 순서 근거                                           |
| 불확실성·실패 가능성 큼        | Assumption Mapping / Pre-mortem  | 핵심 가정, 실패 시나리오, 예방책, 조기 경고 신호                             |

### 4단계: 수렴·결정

1. 조사 결과의 중복을 제거하고 의미상 같은 선택지를 병합함.
2. 선택지는 다음 우선순위로 평가함.
   - 사용자 요구와 충돌하지 않는가
   - 현재 코드베이스의 일관된 패턴과 맞는가
   - 공식 문서·표준과 맞는가
   - 가장 단순한가
   - 나중을 위한 추상화가 아닌가
3. 근거 있는 선택만 `Accepted` 로 둠.
4. 근거 부족 선택지는 `Proposed` 또는 `[OPEN]` 으로 둠.
5. 명시적으로 기각한 선택지는 근거와 함께 `Rejected` 로 남김.
6. 사용자 가치, 공개 계약, UX, 범위, 데이터 손실, 비용·일정에 영향을 주는 결정이 근거만으로 확정되지 않으면 사용자에게 묻거나 Blocking `[OPEN]` 으로 둠.
7. 입력에 spec bundle 이 있으면, Accepted 로 확정된 요구 수준 결정을 **다음 결정으로 넘어가기 전에** "입력 spec 역반영" 절 절차로 입력 spec 에 반영함. 결정을 기억만 한 채 진행 금지. (spec 없는 plan 은 해당 없음.)

### 5단계: plan.md 작성

아래 "plan.md 형식" 으로 작성함.

작성 규칙:

- 비자명 항목에는 `(근거: ...)` 를 붙임.
- 모르면 `[OPEN]` 으로 씀.
- 해당 없음은 빈칸이 아니라 `[N/A]` 와 이유를 적음.
- 동일 정보의 원천은 하나만 둠. 중복 섹션에는 요약·참조만 둠.
- `AC`/`TEST`/`GATE` 의 정의(조건·통과 기준 등)는 §9 표를 정본으로 두고, TASK 블록에는 해당 ID 만 나열함(참조).
- `IMPACT`(§5)는 변경 대상 코드·데이터·설정 단위로 작성하고 관련 `TASK` 와 연결함. `CONSTRAINT`(§2.3)는 1단계 조사에서 확인된 외부·기술 제약을 근거와 함께 기재함.
- `TASK` 는 본질의 "작업 단위"·"TASK 완결성" 규칙대로 작성함.
- **TASK 번호 = 실행 순서**: §8 실행 순서를 먼저 확정한 뒤, 그 순서대로 TASK 번호를 부여함. 번호순과 실행순이 어긋난 plan 을 내지 않음. §8 에는 각 TASK 의 순서·병렬 가능 여부·순서 근거·피해야 할 순서를 남기고, TASK 상세는 중복 기술하지 않음.
- `변경 금지` 대상을 명시해 범위 이탈을 막음.

### 6단계: 독립 검증

작성한 plan 을 독립 서브에이전트(`subagent_type: sd:sd-verify` — 검증 전용)로 검증함. 대상이 아주 작으면 메인 직접 검증도 가능함.

검증 축·발견 형식은 아래 "독립 검증 서브에이전트 prompt" 를 따름(메인 직접 검증 시에도 동일 축 적용).

검증 결과 처리:

- 근거 위조·부족 → 근거 제거 후 `[OPEN]` 또는 해당 항목 삭제함.
- 누락 발견 → plan 보강함.
- 과계획 발견 → 삭제함. 근거 있는 후속 후보는 §2.2 비범위의 `후속 처리` 에 기록함. 사용자 요구 여부가 불확실하면 `[OPEN]`/`제안`으로 처리함.
- 실행 불가 발견 → 작업 순서·게이트 수정하거나 Blocking `[OPEN]` 으로 둠.
- 서브에이전트 실패 시 부분 결과로 완료 보고하지 않고, 실패를 보완한 뒤 재검증함.
- 검증결과 처리를 완료하면 재검증 없이 7단계로 진행함. (반복 아님)

### 7단계: 검토 패키지 보고 후 정지

**요구 반영 최종 게이트** (입력에 spec bundle 있을 때만): 이번 plan 의 요구 수준 결정(Accepted)이 입력 spec 에 다 반영됐는지 전수 대조함. 미반영분은 "입력 spec 역반영" 절 절차로 반영 후 진행함.

보고 항목:

- 생성한 plan 경로.
- 핵심 목표·범위 한 줄 요약.
- 상태: `Ready` / `Blocked`.
- Blocking `[OPEN]`·Blocking 가정(ASM) 목록.
- 주요 결정과 리스크.
- 검증 결과 요약.
- 미반영 자료가 있으면 그 사유.
- 입력 spec 역반영 내역 (spec 입력 시): 수정 page·해소한 `[OPEN]`·제거한 `[구현]` 마커. 없으면 생략.
- 다음 단계 제안.

보고 후 정지함.

## plan.md 형식


## 독립 검증 서브에이전트 prompt

아래를 그대로 복사 후 `<...>` 만 채움.

```
sd-plan 의 plan.md 독립 검증을 수행해줘.

**대상**:
- plan.md 경로: <절대경로>
- 입력 자료 목록: <사용자 발언 요약, 파일 경로, URL, 코드 범위>

**작업**:

1. plan.md 를 끝까지 읽기.
2. 입력 자료와 관련 코드·문서를 직접 읽기.
3. 아래 축으로 검증:
   - 자료 커버리지: 중요한 요구·제약·조건이 plan 에 누락됐는가.
   - 근거 검증: 비자명 결정·작업·리스크의 근거가 실제 존재하는가.
   - 과계획 검증: 요청·근거에 없는 기능·옵션·추상화가 들어갔는가.
   - 실행 가능성: 작업 순서·의존·검증 방법·롤백이 모순 없이 실행 가능한가. TASK 번호순과 §8 실행 순서가 일치하는가.
   - 참조 무결성: SCOPE/FIND/DEC/TASK/AC/TEST/GATE/ASM/OPEN/RISK/BLOCK 참조가 끊기지 않았는가.
   - TASK 완결성: 각 TASK 가 자체 테스트·검증(화면이면 시연)·원천 자료 상태 반영을 포함하는가. 검증·시연·문서 갱신만 모은 후처리 전용 TASK 가 있는가.
4. 문제 발견 시 항목별로 보고:

### 발견 N: <한 줄 요약>
- 분류: 커버리지 / 근거 / 과계획 / 실행가능성 / 참조무결성 / TASK완결성
- plan 위치: <섹션 또는 줄>
- plan 인용: "..."
- 근거 위치: <파일/자료 위치 또는 확인 불가>
- 문제 설명:
- 권장 처리: 삭제 / 수정 / `[OPEN]` / 차단 조건 추가

5. 문제가 없으면 `검증 통과` 1줄만 응답.

**제약**:

- 파일 수정 금지. 보고 전용.
- 근거 없는 추정 금지.
- 구현하지 말 것.
```
