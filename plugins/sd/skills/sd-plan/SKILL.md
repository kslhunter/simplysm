# sd-plan

개발 착수 전, 사용자 발언, 제공 자료, 현재 코드베이스, 공식 문서를 근거로 조사를 수행하고 실행 가능한 개발계획서 `plan.md` 를 작성합니다.

핵심 목적은 구현자가 추측하지 않고 시작할 수 있도록 범위, 비범위, 결정, 리스크, 작업 순서, 검증 기준을 한 파일에 고정하는 것입니다.

## 입출력

- Input — 사용자 요청, 대화 중 확정된 내용, 제공 자료, 현재 코드베이스, 공식 문서, 표준.
- Output — `.plans/{yyMMddHHmmss}_{제목}/plan.md` 1개입니다. 형식은 [references/plan-template.md](references/plan-template.md) 를 따릅니다.
- 폴더 — `{yyMMddHHmmss}` 는 0단계에서 명령으로 조회한 실제 로컬 시각입니다. 임의로 생성하지 마세요.
  - `{제목}` 은 사용자와 합의한 작업 제목이며 파일시스템 금지 문자(`\ / : * ? " < > |`)만 제거, 치환하세요.
  - 같은 제목의 기존 폴더가 있으면 알리고 진행 여부를 확인해야 합니다.

## 본질

- 독립 계획서 — 특정 선행 문서 형식에 의존하지 않습니다. 입력 자료는 근거로 활용하되 다른 문서 체계의 하위 산출물로 취급하지 마세요.
- 명세 문서 입력 시 목표 고정 — 입력이 구현 상태 마커(`[구현]`/미구현)를 가진 명세 문서면, 계획의 목표는 대상 미구현 단위를 하나씩 완료하고 마커를 찍어 미구현을 0 으로 만드는 것입니다.
  - 미구현 단위와 TASK 를 1:1 기본으로 대응시키세요.
- 자동 구현 금지 — `plan.md` 작성, 검증, 보고 후 정지해야 합니다. 별도 구현 지시 전까지 코드 수정, 빌드, 테스트로 넘어가지 마세요.
- 근거 없는 결정 금지 — `결정 근거`가 부족하면 `[OPEN]` 으로 남기거나 물으세요.
- 범위 방어 — 포함 범위뿐 아니라 비범위를 반드시 적어야 합니다. "나중에 필요할 수 있음"은 계획에 넣지 마세요.
- 작업 분할 — TASK 는 vertical slice 입니다. 소비자 관찰 가능한 기능 1개가 데이터-로직-화면을 관통해 그 TASK 안에서 완성됩니다.
  - 판정: "이 TASK 만 Done 이어도 소비자가 쓸 수 있는 동작이 하나 생기는가". 아니면 분할이 틀린 것입니다.
  - layer 단위 TASK(스키마 전체, 서비스 전체, 화면 전체)를 만들지 마세요.
  - 예외: 여러 slice 가 공유하는 기반(공통 스키마, 공통 유틸)만 선행 TASK 로 허용합니다.
- TASK 완결성 — 각 TASK 는 구현 + 테스트, 검증(화면이면 시연) + 그 단위로 완결된 부분의 원천 자료 반영(마커, 문서 갱신)을 TASK 안에서 완결해야 합니다.
  - 검증, 시연, 문서 갱신만 모은 후처리 전용 TASK 를 만들지 마세요.
- 불확실성 표면화 — `[OPEN]` 을 숨기지 마세요. Blocking `[OPEN]` 이나 Blocking 가정(ASM)이 있으면 상태를 `Blocked` 로 두세요.

## 입력 spec 역반영

입력 자료에 spec bundle(루트 `spec-si.md`/`spec.md`)이 있을 때만 발동합니다.

- plan 도중 확정, 변경한 요구 수준 결정(spec 의 _무엇, 왜_ — 값, 분기, 정의, `[OPEN]` 해소, 기존 확정 번복, 신규 요구)은 그 자리서 입력 spec 에 반영하세요.
  - spec 편집은 코드 구현이 아니라 정합 유지이므로 "자동 구현 금지"의 예외입니다.
- 순수 구현방법 결정(라이브러리 선택 등)은 반영 대상이 아니며, plan.md DEC 와 spec 결정 맥락에만 둡니다.

절차 (sd-impl "spec 수정 절차"와 동형):

1. spec 작성 스킬 SKILL.md 읽기 (`spec-si.md`=sd-spec-si / `spec.md`=sd-spec).
   - 인지 항목: 재진입, 부분 수정 경로, 신뢰도 표기, 이름 참조 cascade, 단일 출처(canonical 1곳 수정 + 복제 잔재 통합), `[구현]` 제거 판정.
   - 확정된 인라인 `[OPEN]` 의 문구 치환 같은 경량 반영은 재독 없이 바로 편집합니다.
2. 그 경로로 편집 — 정밀 반영은 바로 하고, 초안, 구조 변경, 모순 정정은 진단, 초안 제시 후 편집하세요.
3. 이름 참조 cascade + 마커 제거 — 수정한 page 를 의존으로 가진 구현 단위의 `[구현]` 마커를 전수 판정, 제거하세요.

## 워크플로

### 0단계: 접수, 경로 확정

작업 대상과 목적을 한 문장으로 확정하고, 제목 확정 후 현재 로컬 시각을 명령(`Get-Date`, `date`)으로 조회해 산출 경로를 계산하세요.

- 조회한 시각을 폴더 타임스탬프, Plan ID, 생성 시각에 동일하게 씁니다.
- 무엇에 대한 계획인지 또는 필수 자료 위치가 불명확하면 시작 전에 물어야 합니다.

### 1단계: 자료 수집

제공 자료와 관련 파일을 직접 읽으세요. 외부 라이브러리, 표준 동작이 계획에 영향을 주면 공식 문서, 표준을 확인해야 합니다.

### 2단계: 발산 조사

범위가 좁으면 메인이 직접 조사하고, 넓거나 관점이 독립적이면 병렬 독립 서브에이전트로 조사하세요.

조사 관점은 넷입니다.

- 요구, 자료 — 요청, 제공 자료, 빠진 정보, 모호한 표현
- 코드 패턴 — 유사 구현, 구조, 테스트, 네이밍
- 외부 근거 — 공식 문서, 표준, API 제약
- 리스크 — 데이터 변경, 호환성, 배포, 롤백, 검증 난점

- 서브에이전트는 보고 전용입니다.
  - 파일 수정이나 최종 결정을 시키지 마세요.
  - 근거 없는 추정은 `[OPEN]`, `확인 불가` 로 보고하고, 결과에 근거 위치를 포함하게 하세요.

### 3단계: 기법 라우터

작업 성격에 맞는 기법만 선택하세요. 모든 기법, 모든 섹션을 억지로 채우지 마세요.

| 상황                                     | 기법                                    | plan.md 에 남길 산출                                                                                       |
| ---------------------------------------- | --------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| 문제, 해결 방향이 모호함                 | Double Diamond / Design Thinking        | 문제 프레이밍, 탐색한 대안, 선택, 기각 이유                                                                |
| 목표와 구현 항목의 연결이 약함           | Impact Mapping                          | 목표, actor, 기대 변화, deliverable, 핵심 가정                                                             |
| UI, 사용자 흐름 중심                     | User Story Mapping                      | 사용자 단계, 핵심 흐름, release slice, 누락 흐름                                                           |
| 복잡한 업무, 도메인 흐름                 | Event Storming 초안                     | 이벤트, 명령, 정책, 예외, hotspot. 이해관계자 검증 전에는 확정으로 쓰지 않음                               |
| 시스템 경계, 외부 연동 중심              | C4 / Context Mapping                    | actor, system/container/component, 인터페이스, 책임 경계                                                   |
| 기존 인터페이스, 데이터 모델을 깨는 변경 | Parallel Change / Branch by Abstraction | expand(신구 병존), migrate(소비자 전수 이전), contract(구 제거)를 각각 TASK 로 분해. 각 단계의 소비자 목록 |
| 중요한 기술, 정책 결정                   | ADR/RFC 후보                            | 맥락, 선택지, 결정, 결과, 재검토 조건                                                                      |
| 버그, 실패 해결 계획                     | RCA                                     | 최소 2개 원인 가설, 근거, 채택, 기각, 해결 방향                                                            |
| 우선순위, 범위 조정                      | MoSCoW                                  | Must/Should/Could/Won't, 순서 근거                                                                         |
| 불확실성, 실패 가능성 큼                 | Assumption Mapping / Pre-mortem         | 핵심 가정, 실패 시나리오, 예방책, 조기 경고 신호                                                           |

### 4단계: 수렴, 결정

발산은 결정이 아닙니다. 선택지와 근거를 모을 뿐이고, 여기서 근거 있는 것만 채택합니다.

1. 중복을 제거하고 의미상 같은 선택지를 병합하세요.
2. 평가 우선순위는 사용자 요구와 충돌하지 않는가 → 코드베이스의 일관된 패턴과 맞는가 → 공식 문서, 표준과 맞는가 → 가장 단순한가 → 나중을 위한 추상화가 아닌가 순입니다.
3. 근거 있는 선택만 `Accepted`, 근거 부족은 `Proposed`, `[OPEN]`, 기각은 근거와 함께 `Rejected` 로 남기세요.
4. 사용자 가치, 공개 계약, UX, 범위, 데이터 손실, 비용/일정에 영향을 주는 결정이 근거만으로 확정되지 않으면 묻거나 Blocking `[OPEN]` 으로 두어야 합니다.
5. spec 입력이 있으면 Accepted 로 확정된 요구 수준 결정을 다음 결정으로 넘어가기 전에 "입력 spec 역반영"으로 반영하세요. 기억만 한 채 진행하지 마세요.

### 5단계: plan.md 작성

[references/plan-template.md](references/plan-template.md) 의 형식으로 작성하세요.

- 비자명 항목에는 `(근거: …)` 를 달고, 모르면 `[OPEN]`, 해당 없음은 빈칸이 아니라 `[N/A]` + 이유로 씁니다.
- 동일 정보의 원천은 하나만 두세요. 중복 위치에는 요약, 참조만 둡니다.
- `AC`/`TEST`/`GATE` 의 정의는 §9 표를 정본으로 두고 TASK 블록에는 ID 만 나열하세요.
- TASK 번호는 실행 순서입니다. §8 실행 순서를 먼저 확정한 뒤 그 순서대로 번호를 부여해야 합니다.
  - 번호순과 실행순이 어긋난 plan 을 내지 마세요.
  - §8 에는 순서, 병렬 가능 여부, 순서 근거, 피해야 할 순서를 남기고 TASK 상세는 중복 기술하지 마세요.
- `변경 금지` 대상을 명시해 범위 이탈을 막으세요.

### 6단계: 독립 검증

작성한 plan 을 독립 서브에이전트(`subagent_type: sd:sd-verify`)로 검증하세요 (아주 작으면 메인이 직접 해도 됩니다). 검증 축:

- 자료 커버리지 — 중요한 요구, 제약, 조건이 누락됐는가.
- 근거 검증 — 비자명 결정, 작업, 리스크의 근거가 실제 존재하는가.
- 과계획 — 요청, 근거에 없는 기능, 옵션, 추상화가 들어갔는가.
- 실행 가능성 — 순서, 의존, 검증 방법, 롤백이 모순 없이 실행 가능한가. TASK 번호순과 §8 이 일치하는가.
- 참조 무결성 — SCOPE/FIND/DEC/IMPACT/TASK/AC/TEST/GATE/ASM/OPEN/RISK/BLOCK 참조가 끊기지 않았는가. 처리 TASK 가 비어 있는 IMPACT 가 있는가.
- TASK 완결성
  - 각 TASK 가 vertical slice 인가(홀로 Done 이어도 소비자가 쓸 동작이 남는가).
  - layer 단위 TASK 는 없는가.
  - 자체 테스트, 검증, 원천 자료 반영을 포함하는가.
  - 후처리 전용 TASK 가 있는가.

결과 처리:

- 근거 위조, 부족 — 근거를 제거하고 `[OPEN]` 으로 두거나 삭제하세요.
- 누락 — 보강하세요.
- 과계획 — 삭제하고 근거 있는 후속 후보만 §2.2 비범위의 `후속 처리` 에 기록하세요.
- 실행 불가 — 순서, 게이트를 수정하거나 Blocking `[OPEN]` 으로 두세요.

서브에이전트 실패 시 부분 결과로 완료 보고하지 말고 보완 후 재검증해야 합니다. 처리를 마치면 재검증 없이 7단계로 가세요 (반복하지 않습니다).

### 7단계: 검토 패키지 보고 후 정지

요구 반영 최종 게이트 (spec 입력 시) — 이번 plan 의 Accepted 결정이 입력 spec 에 다 반영됐는지 전수 대조하고, 미반영분은 반영 후 진행하세요.

보고 내용은 아래 항목입니다.

- plan 경로
- 핵심 목표, 범위 한 줄
- 상태(`Ready`, `Blocked`)
- Blocking `[OPEN]`, ASM 목록
- 주요 결정과 리스크
- 검증 결과 요약
- 미반영 자료와 사유
- spec 역반영 내역(수정 page, 해소한 `[OPEN]`, 제거한 마커)
- 다음 단계 제안

보고 후 정지하세요.
