# sd-demo

화면 명세 1개를 클라이언트 패키지의 화면 컴포넌트 자리에 데모로 생성함. 명세는 SI spec bundle(루트 `spec-si.md`)의 화면 항목 또는 대화로 받은 화면 요구 어느 쪽이든 가능함. 와이어프레임의 배치·라벨·동작 흐름과 일치하는 클릭 가능 UI 산출함. 후속 단계에서 같은 자리에 실제 로직을 채워 진화시킴.

## 본질: UI 가 1순위

대상은 시연을 받는 사용자임. 사용자는 화면만 봄. 코드는 후속 단계에서 다시 작성됨.

- **본 작업의 주력은 template(HTML) 복원** — 와이어프레임을 시각적으로 정확·정돈되게 재현함.
- 코드 골격(시그널·effect·DI·핸들러)은 **코드베이스에서 분석해 따름** — 본 스킬에 라이브러리 규약을 박아두지 않음.
- 데이터 변경 시뮬레이션 금지. 저장·삭제 핸들러는 마커만 작성함. 클릭은 받되 결과 반영 금지.
- 모달 띄우기는 실제로 작동시켜 시연 가치 확보함.

## 워크플로

### 1단계: 입력 확보

호출에 다음 입력이 필요함:

- 화면 명세의 출처 — 다음 중 하나:
  - spec 경로 (있을 때) — sd-spec-si(SI) spec bundle 루트(`.specs/{title}/`) 또는 그 루트 `spec-si.md`. 루트 `spec-si.md` §4 인덱스 표에서 대상 화면 행을 찾아 그 `파일` 컬럼의 page(`design/screens/*.md`) 본문을 명세로 사용함. (범용 sd-spec 의 spec(루트 `spec.md`)은 SI식 화면 명세 형식(§4 화면 인덱스·와이어프레임·항목표)이 없어 본 스킬 대상 아님. 과거 단일 파일 spec.md 는 §4 섹션 본문을 그대로 사용함.)
  - 대화로 받은 화면 요구 (spec 없을 때) — 호출자 발화·후속 대화에서 명세를 확보함. 부족분은 2단계에서 질문함.
- 만들 화면의 식별자 — `[화면.X]` 형태, spec "화면"(§4) 섹션의 화면 항목, 또는 대화에서 지칭한 화면 이름.
- 산출 위치 초안 — 클라이언트 패키지 + 화면 폴더. client 타겟이 1개면 자동 선택, 여러 개면 후보 제시 후 사용자 확정함. (3단계-C 끝에서 도메인이 인접한 결과로 갱신함)

누락된 입력이 있으면 사용자에게 물음. spec 사용 시 식별자 매칭이 안 되면 "화면"(§4) 섹션의 화면 목록 표에서 후보 제시 후 확정함.

**입력 spec 읽기 범위** (spec 사용 시): 대상 화면 항목만 추출하기 전 아래를 순서대로 읽음.

1. 루트 `spec-si.md` §4 인덱스로 대상 화면(§4.x) page 를 찾아 본문을 읽음.
2. 그 본문이 이름 기반 참조(`[화면.X]`·`[모델.X]`·`[공통 정의.X]` 등)로 가리키는 §/page 를 재귀적으로(참조의 참조까지) 읽음.
3. 루트 `spec-si.md` 의 §10 결정 맥락·§11 작업 메모 전체를 읽음.

- 그 화면 관련 결정·제약을 다른 세션이 §10(전역) 또는 해당 단위 page 의 NOTE·인라인 `[OPEN]`(단위 한정)에 남겼을 수 있고, 형식이 그렇게 모이도록 규정함.
- 부분 검색·부분 읽기로 대상 화면 page 만 보고 §10·§11·참조 page 를 빠뜨리지 않음.

**충돌 확인**: 대상 화면(또는 동반 모달 화면) 의 파일이 이미 존재하면 물음 — ① 덮어쓰기 / ② 명세 변경분만 보강 / ③ 취소. 호출자 발화에 명시된 분기가 있으면 묻지 않고 그 분기로 진행함.

### 2단계: 대상 화면 명세 확보

화면 명세에서 다음을 확보함. spec 이 있으면 대상 화면 항목에서 추출하고, 없으면 대화에서 확보하되 부족한 항목은 사용자에게 질문함:

- 헤더 인덱스(Actor · 관련 섹션) + 장치(화면 page 헤더의 `(PC)`/`(PDA)` 표기).
- 기능 개요 · 와이어프레임 · 항목표 · 동작 · 시각 규칙(해당 시) · 도메인 규칙·로직(해당 시).
- 동작 항목에 등장하는 모달 호출 3형(`→ <모달명> 을 모달로 띄움` [부모 종속 sub-section] / `→ [화면.X] 을 모달로 띄움` [화면 전체] / `→ [화면.X] 의 <영역> 을 모달로 띄움` [영역 재활용]) 모두 수집함.

와이어프레임은 데모 재현의 핵심 입력임. spec 없이 진행할 때 와이어프레임이 확보되지 않으면 사용자에게 받아 진행함(텍스트 배치 설명·ASCII 스케치 등). 확보 안 된 채 임의 작화 금지.

### 3단계: 분석 자료 확보

- **[gate] 3단계 진입 시 A(라이브러리 문서) 부터 읽음 — B·C 는 그 뒤. A 미진입 시 3단계 이후 출력 보류함.**
- 안티패턴 — "참고 코드 부재" 신호(빈 패키지·참고할 화면 없음·client 타겟 비어있음 등) 를 이유로 A 를 건너뛰고 B(본체 소스 검색)·C(부위별 수집) 로 바로 진입함.

산출물을 만들기 전, 다음을 분석해 라이브러리 규약을 파악함.

**A. 라이브러리 문서**

코드베이스에 권위 있는 규약·매뉴얼 문서가 있으면 1순위로 따름.

- `@simplysm/*` 사용 시 — SessionStart 가 주입한 활성 references 경로의 `README.md` 읽은 후 "개발 매뉴얼" 표에서 현재 작업 트리거에 해당하는 항목 진입함.
- 그 외 framework 사용 시 코드베이스 안의 동등 위치 문서를 찾아 읽음.

**B. 라이브러리 컴포넌트 소스**

사용 예정 컴포넌트(예: `sd-form`, `sd-crud-list`)가 있으면 **본체 소스를 직접 읽어** input/output·동작을 정확히 파악함. 사용처 검색만으로는 누락된 prop 을 놓침.

**C. 부위별 패턴 레퍼런스 수집**

코드베이스의 클라이언트 화면 전반에서 **부위(부분)별로 공통 패턴**을 수집함. "구성이 똑같은 화면 1개를 골라 통째로 따라하기" 방식은 금지. 일치하는 화면이 있어도, 부위별 종합 결과 위에 추가로 얹음.

**수집 대상 부위** (대상 화면이 사용하는 것만 골라 수집):

| 부위        | 수집 내용                                                      |
| ----------- | -------------------------------------------------------------- |
| 화면 골격   | 컴포넌트 selector·파일 위치·라우팅/메뉴 등록 위치              |
| 헤더/타이틀 | 페이지 타이틀·도구 버튼 배치                                   |
| 툴바        | 검색·필터·추가/삭제 버튼·페이지네이션 위치·정렬 인터랙션       |
| 영역 분할   | 좌우/상하 split·탭·sheet·dock 사용                             |
| 리스트      | 테이블·카드 그리드·트리 마크업·헤더 셀·행 셀·선택/정렬·빈 상태 |
| 폼          | 필드 그리드·라벨/입력 배치·필수 표시·버튼 푸터                 |
| 모달        | 헤더·본문·푸터·확인/취소 버튼·크기                             |
| 빈 상태     | 아이콘·여백·문구                                               |

**절차**:

1. 클라이언트 패키지의 화면 폴더 전반을 훑어 화면 목록을 확보함.
2. 위 부위별로 **각 부위마다 화면 2-4개**를 골라 template 부분을 발췌해 읽음. 도메인 영역(같은 sub-app)이 가까운 화면 우선함. 부위마다 다른 화면을 골라도 됨 (예: 헤더는 화면 X·Y, 리스트는 화면 Z·W).
3. 부위별 공통 패턴(자주 쓰는 슬롯·클래스·요소 구조)을 메모함. 1회만 쓰인 변종은 채택 후보에서 배제하고, 다수에서 반복되는 것을 채택함.
4. 부위별 패턴이 화면마다 갈라지면(예: 리스트가 테이블·카드 두 갈래) 대상 화면의 와이어프레임이 어느 쪽에 해당하는지에 따라 선택함.

**도메인 인접 후보 → 산출 위치 확정**: 같은 sub-app·같은 도메인 폴더에 기존 화면이 1개 이상 있으면 그 폴더로 1단계 산출 위치 초안을 갱신함(자동 채택). 0개면 라우팅·메뉴 등록 위치를 사용자에게 한 번 질문함.

LLM 단독 판단의 한계: 동일 구성 화면이 한 곳도 없다는 이유로 라이브러리 규약만으로 그리는 것 금지. **반드시 부위별로 수집한 패턴을 근거로** 작성함. 부위별 후보가 0개인 부위가 있으면 그 부위만 사용자에게 한 번 질문함(그 화면의 그 부위를 어떻게 처리할지).

### 4단계: 생성

3단계 분석 자료(A/B/C)를 1순위 근거로, **template(HTML) 부터** 채움.

- 파일명·selector·시그널·DI(Dependency Injection) 명명 등은 라이브러리 문서(A) 가 정한 형식 그대로 적용함.
- 슬롯·영역 분할·클래스 패턴은 3단계-C 의 부위별 패턴 채택분을 그대로 적용함. 부위별로 다른 화면을 참조했더라도 각 부위의 채택분을 그대로 옮김.
- 부위별 채택분의 출처(레퍼런스 화면 파일 경로)를 메모해 5단계 점검의 입력으로 활용함.
- 모달 호출이 포함된 화면이면 유형별로 생성함: 부모 종속 모달(같은 page 내 sub-section)은 대상 화면 컴포넌트에 딸린 모달로, 화면 전체형(`→ [화면.X]`)은 동반 모달 화면 항목으로 같은 단계로 생성함. 영역 재활용형(`→ [화면.X] 의 <영역>`)은 그 화면이 미생성 상태면 처리 방식(동반 생성 여부)을 사용자에게 확인함.
- 저장·삭제 등 데이터 변경 핸들러 본문에는 마커(`// sd-demo: 미구현 — 동작 자리`)만 작성함.

**표식 마커 (고정)**

| 위치                     | 마커                                                    |
| ------------------------ | ------------------------------------------------------- |
| 더미 데이터 선언 위      | `// sd-demo: 더미 — 구현 단계에서 교체`                 |
| 미구현 핸들러 본문       | `// sd-demo: 미구현 — 동작 자리`                        |
| 더미 타입 인라인 선언 위 | `// sd-demo: 더미 타입 — 구현 단계에서 @모델/X 로 교체` |
| 임의 추정값 선언/사용 위 | `// sd-demo: 임의 추정값 — 확인 필요`                   |

다른 변형 사용 금지 — 후속 단계에서 검색으로 추적함.

### 5단계: 자체 점검

**패스 1: 부위별 패턴 일치** — 3단계-C 에서 부위마다 채택한 레퍼런스 화면을 다시 읽어 부위별로 비교함:

- 헤더/툴바: 도구 버튼 배치·라벨 형식·간격·클래스가 동일한지.
- 영역 분할: split/탭/sheet/dock 사용이 동일한지.
- 리스트: 헤더 셀·행 셀 마크업·정렬/선택 슬롯이 동일한지.
- 폼: 필드 그리드·라벨/입력 배치·푸터 버튼이 동일한지.
- 모달: 헤더·본문·푸터 구조가 동일한지.
- 빈 상태: 아이콘·여백·문구가 동일한지.

부위 중 한 곳이라도 채택 패턴과 어긋나면(임의 변형·새 클래스 발명·새 슬롯 사용 등) 수정함. "비슷한 화면이 없어서 알아서 그렸다" 식 자기 합리화 금지 — 그 부위의 채택분이 비어 있다는 뜻이므로 3단계-C 로 돌아가 수집·재선택함.

**패스 2: 라이브러리 문서 위배 점검** — 3단계-A 의 매뉴얼 문서 항목별로 일치 여부 확인함. 위배 항목이 있으면 수정 후 재점검함.

### 6단계: 완료 보고

생성한 파일 목록을 보고 후 종료함.
