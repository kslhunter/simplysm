# sd-dev

spec(spec.md, spec-si.md) 없이 사용자와의 대화 합의를 권위 출처로 진행하는 증분 코드 작업입니다.

- 품질 동급 — 산출물 품질, 엄밀성은 spec 파이프라인(sd-impl)과 동급입니다. 차이는 작업 규모뿐이며 품질 수준이 아닙니다.
- 권위 출처 — 1단계에서 합의한 의도가 이후 전 단계의 권위 출처입니다. 합의 결과는 별도 산출물로 저장하지 말고 대화 메모리에만 유지하세요.
- 자동 진행 — 의도 합의 후 워크플로는 자동 진행합니다.
  - 단 파일 삭제, 시연 등 사용자 확인 지점과 `결정 근거` 없는 분기, 정의, 값을 발견한 지점에서는 자동 진행을 중단하고 물어야 합니다.
- 대상 무제한 — spec 단위 풀 구현을 거칠 규모가 아닌 증분이면 산출물 종류로 한정하지 않습니다. 화면 일부 변경(버튼 추가, 버그 수정 등)도 대상입니다.

## 본질 (횡단 룰 — 전 단계 적용)

- 임의 채움 금지 — 분기, 정의, 값, 계산식, 경계를 만나면 `결정 근거`(사용자 발언, 코드베이스의 일관된 구현 패턴, 공식문서 명시, 권장, 도구 실행으로 직접 확인한 결과) 유무로 판정하세요.
  - 있으면 그에 따라 채우고, 없거나 불명확하면 즉시 멈춰 1건씩 물어야 합니다.
  - 사용자가 새 방식을 지시, 합의한 작업에서는 기존 패턴이 근거가 못 됩니다. 기존 코드가 다수라도 지시된 방식을 따르고, 신구 절충 형태를 만들지 마세요.
  - 추정, 단발 사례, "추론 가능"을 근거로 대체하지 마세요.
  - 도메인 값, 분기, 계산식은 사용자 발언이 유일 근거입니다. 코드 추론으로 채우지 마세요.
  - spec 같은 영속 권위 자료가 없어 적용 빈도가 더 높습니다.
- 문서 비참조 — plan, 대화 합의는 언제든 폐기, 전면 재작성될 수 있습니다. 코드 어디에도(주석, 테스트 이름, 문자열, 식별자) plan 항목, 합의 문구로의 연결점, 인용을 남기지 마세요.
  - 방향은 합의→코드 단방향입니다. 주석, 테스트 이름은 코드 자체의 동작만 서술하세요.
- 테스트 목적 내부 분해 금지 — 합의에 없는 추상화, 방어코드나, 테스트를 위한 내부 구현 분리를 하지 마세요 (4단계 테스트 단위 룰).
- 사용자 보고 어휘 — 보고 본문에 내부 구현 식별자(내부 변수명, SQL 함수명, 타입 키워드 등)를 노출하지 마세요.
  - 사용자가 이해하는 기능, 동작 어휘로 풀어 쓰세요.
  - 단 합의한 공개 계약(공개 함수명, CLI 옵션명 등)은 그대로 노출합니다.

## 워크플로

### 1단계: 의도파악

무엇을 만들거나 바꿀지 합의하세요. 진행 전 아래를 확정해야 합니다:

- 작업 종류 (신규 / 수정 / 버그 수정), 대상 파일, 모듈, 패키지.
- 변경의 입출력, 동작 — 이름, 시그니처, 예외 동작.
- 독립 산출물로 합의되는 단위 — 추가, 변경하기로 한 공개 함수, API, CLI 옵션, 모듈 export 계약 (4단계 테스트 단위의 기준).

`결정 근거`가 충분하면 묻지 않고 진행하고, 없거나 불명확한 항목은 안을 만들어 1건씩 제안하세요. 외부 자료(디자인 시안, 샘플 데이터, 접근 자격증명)가 필요하면 이 단계에서 요청해야 합니다.

### 2단계: 분석

자료가 없어도 멈추지 마세요. 발견된 만큼 활용합니다.

- A. 라이브러리, 개발 매뉴얼 — `@simplysm/*` 이면 SessionStart 가 주입한 활성 references 경로의 `README.md` 입니다.
  - 그 외 framework 는 코드베이스 안 동등 위치 문서를 보고, 없으면 표준 패턴을 따르세요.
- B. 기존 패턴 — 작업 영역 인접 코드의 파일 위치, 네이밍, 구조, 계층 분리를 파악하세요.
  - 변경 영역의 다수 사례에서 동일하게 나타난 패턴만 채택 근거입니다.
  - 동일 의도 기존 사용처 1-2개를 읽으세요.
- C. 테스트 환경 — 단위 테스트 프로젝트 구분, 실행 명령, mocking 패턴.

### 3단계: 작업 분해 표

응답 본문에 표로 출력하세요 (4단계 입력). 차이 기준선은 1단계 합의 범위와 현재 코드입니다.

| 항목 | 합의 인용 | 현재 코드 상태 | 판정 | 매핑 파일 | 의존 |
| ---- | --------- | -------------- | ---- | --------- | ---- |

- 분해 단위는 함수, 메서드 1개 / 상태값, 분기 케이스 1개 / 입출력 시그니처 1개 / 버그 1건당 1줄입니다.
- 현재 코드 상태는 신규면 "없음", 기존 수정이면 "있음(현재 동작 요약)"입니다.
- 판정은 없음 / 불일치 / 일치입니다.

### 4단계: TDD 사이클

판정이 "없음", "불일치"인 항목만 의존 순서대로 진행하세요. "일치"는 손대지 마세요.

각 항목 시작 시 테스트 작성 가능 여부를 판정해야 합니다 (2-C 이용):

| 분류                | 적용 대상                                        | 사이클                 |
| ------------------- | ------------------------------------------------ | ---------------------- |
| 테스트 가능         | 도메인 로직, 계산, 변환, 서버 함수, 데이터 접근  | RED → GREEN → REFACTOR |
| 테스트 불가, 비효율 | UI 시각, 인터랙션, 외부 서비스 실호출, 환경 의존 | 구현 → REFACTOR        |

테스트 단위는 합의한 산출 단위입니다. 내부 구현을 쪼개지 마세요:

- "테스트 가능" 분류는 그 처리가 대화에서 독립 산출물로 합의한 단위(공개 함수, API, CLI 옵션, export 계약)일 때 적용합니다. 그 단위를 그대로 테스트하세요.
- 합의가 "동작, 기능"(화면, 자동 처리, 초기화 등)이고 변환, 매핑, 계산이 그 내부 구현 조각일 뿐이면, 동작 전체를 테스트 단위로 보세요.
  - 통째로 테스트 가능하면 그 단위로 하고, 아니면(외부 I/O, 환경 의존) "테스트 불가, 비효율"로 분류합니다.
- 내부 조각을 테스트하려고 별도 함수, 파일, 인터페이스로 분리, 추상화하지 마세요. "이 헬퍼를 공개 API 로 한다"는 합의가 없으면 테스트는 그 조각을 떼낼 이유가 못 됩니다.

무엇을 단언하는지는 불변식, 제약만으로 정합니다:

- 깨지면 진짜 결함을 가리키는 불변식, 제약만 단언하세요 (필수값 비어있지 않음, 유일성, 1:1 관계, 멤버십, 빈 배열 금지, 경계값 등).
- 임의 스냅샷 카운트, 분포 총합을 단언하지 마세요. 항목 수, 집계 분포는 데이터가 정상 변경되면 깨지는데 어떤 제약도 검증하지 못합니다.
  - 다른 소스 길이로 맞추는 것(`toHaveLength(OTHER.length)`)도 자기참조라 무의미합니다.
- 이런 브리틀 테스트를 발견하면 갱신하지 말고 제거하세요. 카운트가 가리키던 의도가 실제 제약이면 그 제약을 단언하는 테스트로 교체합니다.

사이클:

- RED — 테스트만 작성하고 실행해 실패를 확인하세요. 구현 파일에 손대지 마세요.
- GREEN — 통과하는 최소 구현을 하고 재실행해 통과를 확인하세요.
- REFACTOR — 중복, 가독성, 2-B 채택 패턴, 2-A 매뉴얼 정합을 검토해 정리한 뒤 통과 유지를 확인하세요.
  - 임의로 변형하지 마세요.
  - 정리 대상이 없으면 코드 변경이 없을 뿐이니 단계를 건너뛰지 마세요.

사이클 중 합의되지 않은 분기, 모호점을 발견하면 즉시 멈추고 재합의해야 합니다.

### 5단계: 코드 정리

전체 변경분을 한 번 훑어 4단계가 잡지 못한 횡단 이슈와 잔재를 정리하세요.

- 횡단 중복 — 사이클 사이에 흩어진 동일 로직을 합치세요.
- 기존 패턴 정합(drift) — 다항목 누적으로 기존 패턴(파일 위치, 네이밍, 구조, 시그니처, 에러 처리, 테스트 패턴)에서 이탈한 부분만 2-B 채택 패턴으로 수정하세요.
- 불필요한 코드 — 미사용 import, 변수, 주석, 합의 없는 옵션, 추상화, 어디서도 참조되지 않는 파일을 제거하세요 (검사 범위는 전체 워크스페이스).
  - 단 파일 단위 삭제는 후보를 보고한 뒤 확정분만 삭제해야 합니다. dynamic import, 문서 자산 등 정적 참조로 안 잡히는 보존 대상이 있습니다.
- 테스트 가치 스윕 — 이번 작업으로 생성, 수정한 테스트를 전수 훑어, 동작, 계약, 불변식, 예외를 단언하지 않는 임시 테스트는 제거하세요.
  - 대상 예: 구현 세부, 중간 형태 단언, 존재/텍스트 유무만 확인, 상위 테스트에 흡수된 디딤돌.
  - 판정 기준은 깨졌을 때 진짜 결함을 가리키는가입니다.
- 매뉴얼 규약 정합 — 여러 항목, 파일에 걸쳐 작성 후에만 드러나는 위반만 점검하세요.

정리 후 단위 테스트를 재실행해 회귀 없음을 확인해야 합니다.

### 6단계: 합의 대조 (독립 서브에이전트)

자체 검증의 확인 편향을 제거하기 위해 독립 서브에이전트(`subagent_type: sd:sd-verify`) 1개로 합의 범위와 현재 코드를 대조하세요.

sd-impl 은 외부 영속 산출물(spec)을 기준으로 삼지만 sd-dev 의 기준은 대화 합의뿐이고, 서브에이전트는 대화 히스토리를 볼 수 없습니다.

- 3단계 표 + 합의된 입출력, 동작, 예외 동작 요약 + 현재 구현 파일 목록을 누락, 왜곡 없이 프롬프트에 옮겨야 합니다.
  - 여기서 빠뜨린 합의는 검증에서도 걸러지지 못합니다.
- 대조 범위는 합의된 변경 범위 전체입니다. "이번 사이클 변경분만" 식 제한을 두지 마세요.

차이는 아래 3분류로 받으세요:

- (a) 코드 위반 — 합의가 명확한데 코드가 빠뜨리거나 다릅니다. 4단계로 재진입해 코드를 수정하세요.
- (b) 합의 내부 모순 — 합의 항목끼리 충돌합니다(양쪽 인용). 1건씩 보고하고 방향을 결정해 합의를 갱신한 뒤 4단계로 재진입하세요.
- (c) 합의 미정의 + 코드 임의 채움 — 합의에 없는 정의, 분기, 경계를 코드가 채웠습니다. 1건씩 질문해 합의를 갱신한 뒤 4단계로 재진입하세요.

- (b)(c)를 묶어 보고하지 말고 1건씩 합의해야 합니다.
- 처리 후 6단계를 재실행해 차이 0건을 확인하고 7단계로 가세요.

### 7단계: 검증

- 브라우저 시연이 필요한 화면, UI 면 사용자에게 dev 서버 실행을 요청해 주소를 받은 뒤 브라우저 자동화로 합의된 동작 시나리오를 시연하세요.
  - 회귀 발견 시 4단계로 돌아가 수정하고 재시연합니다.
- 그 외(라이브러리, CLI, 내부 모듈, 서버 함수)는 단위 테스트 통과로 회귀를 점검하고, CLI 면 실제 명령 실행 결과 확인을 더하세요.
- plan.md 경유 호출이면 해당 TASK 상태를 `Done (yyyy-MM-dd)` 로 갱신해야 합니다. 누락하지 마세요.
  - 다음 작업 안내는 plan 의 TASK 번호순을 따릅니다.
