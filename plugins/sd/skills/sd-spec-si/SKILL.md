# sd-spec-si

목적은 정확한 spec 이며, 환각과 누락을 차단합니다.

형식은 [references/example.md](references/example.md) 가 유일한 모범입니다.

- 작성 전에 example.md 의 대상 카테고리 `<!-- 경로 -->` 구간을 찾아 직접 대조하세요.
- 이 파일은 예시로 알 수 없는 것만 규정합니다.

## 산출물

위치는 `.specs/{title}/spec-si.md` 와 그 하위 page 입니다. `{title}` 은 사용자와 합의한 시스템명입니다.

```text
.specs/{title}/
  spec-si.md               루트 — 개요, 인덱스, 결정 맥락, 작업 메모만. 본문 복제 금지
  requirements/processes/  requirements/others/
  design/screens/  design/jobs/  design/foundations/
  common/
  data/models/  data/interfaces/
```

- page 참조는 본문 어디서나 `[카테고리.이름]` 만 쓰세요 (`[화면.재고 확인]`, `[모델.박스.수량]`). 파일 경로나 번호를 쓰지 마세요.
- 화면 인덱스의 열거값은 둘입니다.
  - `유형`: 마스터, 트랜잭션, 조회, 기타(레이아웃 셸, 개발 도구 등 비업무).
  - `장치`: PC, PDA, 기타.
- `[구현]` 은 루트 인덱스 `구현` 컬럼에만 쓰세요. page 헤더에 붙이지 마세요.
- 같은 분류에 동일 제목 파일이 있으면 새로 만들지 말고 기존 page 재진입으로 보세요.

## 절차

1. 준비 — 시스템명을 합의하세요.
   - `.specs/{title}/` 이 이미 있으면 재진입인지 사용자에게 확인하세요.
   - 골격(루트 + `common/용어 사전.md`)을 생성하세요.
2. 요건 — 개요는 루트에, 프로세스, 기타 요구는 page 로 씁니다.
   - 도메인 어휘는 용어 사전에 누적하세요.
   - 설계, 파생 정의는 아직 만들지 마세요.
3. 설계 — 화면 → 자동 처리 → 기반 순으로 한 단위씩 진행하세요.
   - 그 단위가 참조하는 모델, 외부 인터페이스, 공통 정의를 그 자리에서 추가, 갱신해야 합니다.
   - 루트 인덱스도 즉시 갱신해야 합니다. 끝에 몰아서 모으는 단계는 없습니다.
4. 검증 — 독립 서브에이전트(`subagent_type: sd:sd-verify`)로 검증해야 합니다.
   - 검증 축은 근거 좌표 실재 대조와 원자료↔spec 누락 역대조입니다.
   - 위조로 보고된 근거는 `(근거: …)` 를 떼고 `[OPEN]` 으로 강등해야 합니다.
5. 보고 후 정지합니다.
   - 요약과 `[OPEN]` 목록(파급 큰 것 먼저), 검증 결과, 미반영 자료를 채팅으로 제시하고 멈추세요.
   - 후속 수정으로 자동 진입하지 마세요.

### 자료가 코드베이스일 때 (`/sd-spec-si init [범위]`)

절차는 동일하고 자료만 코드입니다. 추가로:

- 코드가 결정 근거입니다.
  - 코드에 없는 동작을 쓰지 마세요.
  - 코드로 알 수 없는 업무 의도는 `[OPEN]` 입니다.
- 설계 단위마다 코드와 대조해 차이가 0건이면 루트 인덱스에 `[구현]` 을 표기하세요.
  - 대조는 독립 서브에이전트로 단위별 병렬 실행하세요.
- 코드 동작이 명백한 버그로 보이면 정당한 요구인 양 기록하지 마세요.
  - 그 단위는 마킹을 보류하고 코드 결함 후보로 보고해야 합니다.

### 재진입, 부분 수정

기존 bundle 에 대한 모든 지시는 규모와 무관하게 이 경로입니다.

- 루트 인덱스에서 대상 page 를 찾아 읽고, 그 본문이 `[카테고리.이름]` 으로 가리키는 page 를 재귀적으로 읽어야 합니다. 루트 결정 맥락, 작업 메모도 읽으세요.
- 구조 변경 시 `[카테고리.이름]` 참조를 전수 검색해 끊기는 참조를 함께 갱신해야 합니다.

## 작성 원칙

- 대화로 확정하며 씁니다. 사용자만 답할 수 있는 지점에서 멈춰 합의하고, 합의분을 그 자리서 반영한 뒤 다음으로 넘어가세요.
  - 구현 수준(파일 배치, 내부 자료구조, 사용할 라이브러리 API, 네이밍)은 sd-impl 소관이라 묻지 마세요.
  - `init` 경로만 예외입니다. 실행 중 묻지 말고 `[OPEN]` 으로 남겨 사후 정정하세요. 단 제목, 폴더 판단은 그 자리서 확인해야 합니다.
- 모르면 `[OPEN]` 입니다.
  - 질문에 딸려온 답변을 능동 결정으로 확정하지 마세요.
  - `[OPEN]` 은 사용자가 답을 유보한 것과 `init` 경로에만 남습니다.
- 비자명 항목에 `(근거: 출처)` 를 다세요.
  - 자료에서 해석, 도출한 것만 해당합니다.
  - 사용자가 직접 말한 것엔 붙이지 마세요.
- 추상 레벨을 고정하세요. spec 은 _무엇을, 왜_(업무 요구, 규칙) 수준에 머뭅니다.
  - _어떻게_(구현 코드, 화면 구현 방식, 내부 자료구조 선택)로 조기에 점프하지 마세요.
  - 단 화면 항목, 자동 처리의 트리거, 결과처럼 사용자, 상대 시스템이 닿는 표면은 요구 수준이므로 정확히 기술해야 합니다.
- 단순화를 차단해야 합니다. 식, 분기, 경계를 그대로 풀어쓰세요.
  - 방어 처리(NULL 강제, 0 클램프, 분기 생략)로 임의 변형하지 마세요.
- 단일 출처를 지켜야 합니다. 공통 정의, 모델, 외부 인터페이스의 정의 내용을 설계 단위 본문에 복제하지 마세요.
  - 이름 참조만 쓰고 단위 본문엔 용도, 매핑만 두세요.
  - canonical 을 고칠 때는 참조 단위 본문에 인라인 복제가 남았는지 역방향으로 훑어야 합니다.
- 파생은 종속물입니다. 설계 단위가 참조하지 않는 모델, 외부 인터페이스는 만들지 마세요.
- 내용물은 직접 도출해야 합니다. 다른 page 나 example 에서 가져올 것은 형식뿐입니다.

## 판단 규칙

- 프로세스 page 분할 — 1 page 는 start event(외부 메시지 도착, 시각 도래)부터 end event(외부 가치 전달)까지 한 사이클입니다.
  - 사이클 내부의 담당자 전환, 시간 지연은 분리 사유가 아닙니다. swim lane 으로 표현하세요.
  - 사이클이 아닌 단일 user goal 은 기타 요구사항 page 입니다.
- 요건 항목의 설계 배분 — 사용자 눈에 보이면 화면입니다(레이아웃 셸, 전역 네비게이션 포함).
  - 스케줄, 이벤트 트리거면 자동 처리입니다.
  - 여러 곳이 공유하는 규칙, 규격이면 공통 정의입니다. 가드, 권한, 감사 로그 등 크로스컷은 자동 발동이어도 여기입니다.
  - 앱 부팅 초기화처럼 화면, 자동 처리 어디에도 수반되지 않는 독립 기반만 기반입니다. 비어도 정상입니다.
- 실행 경계 — 한 설계 단위는 따로 실행, 배포되는 자리(서버, PC 브라우저, 단말, 배치 프로세스)를 가로지르지 않습니다.
  - 화면은 `장치` 가 다르면 별개 page 입니다. 같은 업무라도 PC 와 단말은 나눕니다.
  - 기반이 서버와 단말 양쪽을 담으면 쪼개세요. 완료 기준을 한 자리에서 검증할 수 없으면 두 단위입니다.
- 모달 — 부모 한 곳에서만 쓰는 폼은 부모 page 안 sub-section 입니다.
  - 기존 화면을 통째로 띄우면 새 page 없이 `→ [화면.X] 을 모달로 띄움` 으로 씁니다.
  - 어디에도 안 매인 자립 화면만 별도 page 입니다.
- 외부 인터페이스 vs 자동 처리 — 상대 시스템 고유의 협상된 약속(ERP API, 거래처 EDI)만 외부 인터페이스입니다.
  - 표준 프로토콜(메일, FTP, OAuth)은 협상이 없으므로 자동 처리에서 다루세요.
- 의존 방향 — 기반, 재사용 로직이 상위 화면, 처리를 참조하면 역전입니다.
  - 공통 부분을 기반, 공통 정의로 추출해 양쪽이 참조하게 하세요.
  - 단 상위를 구성 대상으로 열거하는 것(메뉴 배열, 권한 매핑)은 역전이 아닙니다.
- `[구현]` 제거 — 설계 단위나 그 의존을 고쳤을 때, 구현을 새로 만들거나 고쳐야 하면 제거하고 문구, 참조 정리면 유지하세요.

## 루트 메타

결정 맥락 — 본문은 결과만 담으므로, 결과만 보면 후속 LLM 이 오판할 지점을 남겨야 합니다.

- 왜 이걸로 골랐는지, 무엇을 기각했는지, 어디까지만 검토했는지, 무엇이 전제인지를 씁니다.
- 결정 대상별로 묶고 뒤집히면 그 묶음을 갱신하세요. 시간순 로그가 아닙니다.
- 분석 제외 항목은 `[제외]` 와 후속 처리, 자료 위치를 함께 씁니다.

작업 메모 — 다음 세션에 이어가려는 WIP 입니다.

- 소진되면 반드시 제거해야 합니다. 최종 spec 엔 비어 있어야 정상입니다.
- 특정 page 에 매인 진행 방법, 결정 맥락은 루트가 아니라 그 page 도입부 NOTE blockquote 로 두세요.
