# sd-wiki-lint

- 메인 루프가 직접 오케스트레이션하세요.
- 위키 구조, CLI, 4관문, 트리 모양 기준은 세션 시작에 주입된 위키 규칙이 권위입니다.
- 핵심은 역할 분담입니다.
  - `lint` CLI — 기계로 가능한 위상 점검만 합니다 (끊긴 상위, cross-link, 고아, 트리 통계).
  - 이 스킬 — 모순, 노후, 누락 개념, 데이터 공백 같은 의미 점검을 본문을 읽어 판정합니다.
  - 둘을 합쳐야 전체 점검입니다.

## 1. 기계 진단

`lint` 를 실행하세요. 결과 해석:

- `orphans`, `brokenLinks` — 끊긴 참조, 고아입니다. 즉시 수정하세요.
  - 단 `target` 이 `...` 처럼 영문자 없이 점, 기호로만 된 건 본문 코드 스팬을 topic 으로 오인한 lint 오탐입니다. 페이지에 고칠 게 없으니 파고들지 말고 넘기세요.
- `treeStats`(`rootCount`, `hubChildCounts`) — 트리 모양 판단 입력입니다.
- `unlinkedTopics` — 독립 지식이 많은 위키에선 정상입니다. 과잉 cross-link 를 강요하지 마세요.
- `lowViewPages` — 전부 `0` 이면 추적 미성숙이라 노이즈이니 무시하세요. 편차가 있을 때만 정리 후보 신호입니다.
- `knowledgeGaps` — 지식 공백 후보입니다.

## 2. 전수 본문 수집

`toc` 로 전체 topic 을 확보한 뒤 모든 페이지를 `read` 하세요. 의미 점검엔 본문이 필수입니다.

- 대량이면 셸 반복으로 묶어 읽고, 출력이 크면 파일로 받으세요.
- 표본이나 요약만 보고 판단하지 마세요.

## 3. 의미 점검 (전수)

각 페이지를 아래 렌즈로 빠짐없이 판정하세요. 근거는 본문과 그 페이지가 명시한 버전, 도구 전제이며, 추정으로 단정하지 마세요.

- 모순 — 같은 주제를 상반되게 서술합니다.
  - 한쪽이 틀렸으면 덮어쓰세요.
  - 버전, 조건이 달라 둘 다 맞으면 적용 조건을 명시해 공존시키세요.
- 노후 — 그 페이지가 명시한 전제 안에서조차 틀린 주장입니다. 공식문서, 재현으로 대조하세요.
  - 내 작업 버전과 다를 뿐이면 노후가 아닙니다. 전제가 본문에 없으면 노후 판정 전에 어느 버전에서 참인지 먼저 확인하세요.
- 검증, 출처(관문3) — 재방문 가능한 출처 없이 단정한 주장입니다.
  - 출처가 확인되면 단정을 유지하고 출처를 보강하세요.
  - 검증 불가, 추정, 전언, 자기 repo 코드 출처는 제거하세요. 없는 게 낫습니다.
- 4관문 위반 — repo 국한(라이브러리 _만드는_ 지식, 고객 1곳 정책 포함), 버전 미안전(구버전서 틀림, 시점 의존), 시한부(X→Y 마이그레이션), 일기(작업 경위, 사례 수치)입니다.
- 누락 개념 — 본문이 반복 언급하나 별도 페이지가 없는 중요 개념입니다 (페이지화 후보).
- 데이터 공백 — `knowledgeGaps` 나 검색 0건 영역입니다 (보강, 조사 후보).
- 품질 — 요약이 라우팅 전용인지(본문 사실 복제 금지), 본문에 특정 건의 수치, 서사, 경위가 섞였는지 봅니다.

## 4. 트리 모양 점검

- 루트 과다 — 관련 묶음을 sub-hub 로 접으세요.
- 과대 hub — 중간 sub-hub 로 분할하세요.
- 잉여 hub — navigation hop 만 늘리면 `delete` 하세요. 자식은 상위로 reparent 됩니다.

## 5. 정리 적용

근거가 한 선택만 가리키면 묻지 말고 즉시 실행하세요. 애매한 것은 전수 점검을 마친 뒤 한 건씩 순차로 `논의`하세요.

- 즉시 실행 — 끊긴 참조 수정, 4관문 위반 삭제, 명백히 틀린 서술, 근거표기 정정, 루트 과다 sub-hub 묶기, 요약, 품질 정정, 잉여 hub 머지입니다.
  - 틀린 페이지(검증불가, 추상화불가, 사실과 어긋남)는 정정보다 삭제를 우선하세요. 오래됐다는 것만으로는 삭제 사유가 아닙니다.
- `논의` 대상 — 둘 다 유효할 수 있는 모순, 코드만으로 노후 확정이 안 되는 항목, 새 페이지화, 공백 보강 제안입니다.
  - 점검 도중 발견해도 그 자리서 묻지 말고 목록에 쌓으세요. 뒤 페이지와의 모순을 모른 채 결정하지 않기 위함입니다.
  - 제시는 반드시 1건씩입니다. 답을 받아 반영한 뒤 다음 건으로 넘어가세요.
- `delete` 전 `read` 로 본문을 읽어 살릴 내용을 확인하고, 읽은 `version` 을 `--base-version` 으로 전달하세요. 부모, 자식을 함께 지울 땐 자식부터 지우세요.
- 다중 작업은 전부성공 아니면 전부실패입니다. 일부라도 실패하면 부분 적용 사실을 보고하세요 (silent skip 금지).

## 6. 재검증, 보고

`논의`를 모두 끝낸 뒤 `lint` 재실행으로 무결성, 트리 통계 개선을 확인하고, before/after(페이지 수, `rootCount`, 무결성) + 자동 처리 내역 + `논의` 결정 반영 내역을 제시하세요.
