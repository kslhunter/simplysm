# 원격 공용 위키

누적 지식 위키의 구조:

- 위치: 로컬 파일이 아닌 팀 공용 원격 서버.
- 페이지 구성: `topic`(유니크 키) + 제목·요약·본문(마크다운)·버전 + **상위 페이지**. 페이지가 상위-자식 관계로 **재귀 트리(forest)** 를 이룸 — 자식 있는 노드는 hub, 자식 없는 노드는 leaf(별도 종류 구분 없이 파생).
- 자동 주입: SessionStart 훅이 세션 시작 시 **ROOT MAP**(상위 없는 최상위 노드의 라우팅 목록)만 주입 — 전체 목차 아님. 그 아래 지식은 트리를 따라 온디맨드로 펼침.

읽기·기록·검색·탐색은 위키 CLI 로 함 — 실행 형식 `bun "${CLAUDE_PLUGIN_ROOT}/scripts/wiki.ts" <명령>`. 사용 가능한 명령:

| 명령               | 동작                                                                                          |
| ------------------ | --------------------------------------------------------------------------------------------- |
| `rootmap`          | 최상위 노드의 라우팅 목록(topic·제목·요약·자식 유무). ROOT MAP — 세션에 자동 주입되므로 보통 갱신 후 새로 볼 때만 호출 |
| `children <topic>` | 그 노드의 직속 자식 라우팅 목록(자식 유무 포함). 없는 topic 이면 에러, 자식 없는 leaf 면 빈 목록 |
| `read <topic>`     | 페이지 1건 조회 — 제목·요약·본문·버전. 없으면 빈 결과                                          |
| `write <topic>`    | 페이지 생성·갱신 — 제목·요약·본문, `--parent <topic>` 로 상위 지정, 갱신 시 기준 버전(낙관락)  |
| `search <키워드>`  | 제목·요약·본문 키워드 검색 — 라우팅 항목 반환                                                  |
| `toc`              | 전체 페이지 평면 목록. 온디맨드 fallback(자동 주입 아님) — 트리 탐색으로 진입점을 못 찾을 때만 |
| `delete <topic>`   | 페이지 삭제 — 자식이 있으면 상위로 재배치(reparent) 후 노드만 삭제(서브트리 보존). `--base-version` 으로 낙관락 |
| `move <topic>`     | 내용 변경 없이 상위만 이동 — `--parent <topic>` 또는 `--root`(최상위로). 순수 위치 변경(`write` 와 달리 본문 재전송 불필요) |
| `lint`             | 위키 점검 — 끊긴 상위·cross-link·고아·트리 통계 진단. 정리 판단은 결과를 받아 직접 |

인증·토큰 갱신은 CLI 가 자동 처리(만료 시 브라우저 로그인). 결과는 JSON.

## 페이지 탐색

세션엔 ROOT MAP 만 주입됨(전체 목차 아님) — 필요한 지식은 트리를 따라 펼쳐 찾음.

- 경로: 주입된 ROOT MAP 에서 관련 최상위 노드 식별 → `children <topic>` 로 자식 펼침 → 더 깊으면 자식의 `children` 반복 → 목표 leaf 의 `read <topic>` 로 본문 활용.
- 자식 유무(`hasChildren`)로 펼칠지 결정 — hub(자식 있음)면 `children` 으로 더 펼치고, leaf(자식 없음)면 바로 `read`(leaf 에 불필요한 `children` 호출 안 함).
- ROOT MAP 에 관련 진입점이 안 보이면 `search` 로 키워드 검색해 진입점 찾기.
- 본문이 다른 `topic` 을 가리키면(cross-link) 그 topic 도 `read` 로 확인.
- 페이지가 노후했고 현재 작업과 맞지 않으면, 사용자 요청을 기다리지 말고 그 자리에서 재검증·갱신.

## 무엇을 담는가 (대상)

작업 중 알게 된 **오래 재사용될 지식** — 빌드·실행 명령, 디버깅 원인·해결, 라이브러리·API 동작, 설계 결정, 반복 패턴 등. 팀이 공유하므로 작성자 한 사람뿐 아니라 다른 작업자도 다시 펼칠 일반 지식만 담음.

- **판정 질문**: "다음에 비슷한 상황을 만났을 때 이 페이지를 열어 시간을 아낄, 비자명하고 반복되는 내용인가?" 아니오거나 애매하면 넣지 않음.

## 무엇을 담지 않는가 (비대상)

위키는 재사용 지식만 담음 — "방금 한 작업" 을 기록하는 곳이 아님. 아래는 새 페이지로 만들지도, 기존 페이지에 덧붙이지도 않음.

- **일회성 작업 기록·의사결정**: 이번 한 건의 작업 절차·변경 내역·영향 요약(작업 서사·완료 보고·리네임/마이그레이션 기록 등), 그리고 도구·방안의 도입·채택 여부를 1회 검토한 평가의 결론. 다시 펼칠 일이 없음.
- **단순 문서 요약**: 공식 문서·`claude-code-guide` 등으로 그 자리에서 쉽게 재확인되는 일반 사실. 단, 문서로는 찾기 어려운 함정·우리 환경 특이 동작·반복 적용 패턴은 예외로 대상.
- **개인·로컬 특이 정보**: 특정 머신·개인 경로·임시 환경에서만 통하는 내용. 공용이라 팀 누구에게나 통하는 지식만 담음.
- **과거 기록물**: commit·PR·이슈·로그·CHANGELOG 성 내용.
- **단일 프로젝트 국한 지식**: 특정 한 프로젝트(고객 SI·단일 앱 등)에만 해당하는 내용. 위키는 회사 전체 재사용 범용 지식 + `@simplysm/*` 공유 라이브러리(모노레포) 수준 지식만 담음 — 단일 프로젝트 지식은 여러 프로젝트·세션이 공유하는 ROOT MAP 을 오염시킴. 그 지식을 어디 두는지는 위키가 관여 안 함.

본문 작성·분량 원칙:

- 작업 과정의 단발 정보는 그 작업 산출물(코드 주석·PR 설명·spec)에 남기고 위키엔 올리지 않음.
- **재사용 지식 페이지라도 특정 건의 사례 수치·진행 경위·사고 서사는 본문에 섞지 않음** — 일반화된 패턴·기준·원인·해결만 남기고 그 건의 결과·경위는 뺌.
- 위키는 얇게 유지하는 편이 검색·주입 비용 면에서 이득.

## 정확성 — 틀린 지식은 없느니만 못하다

사실로 단정된 틀린 정보가 가장 해롭다 — 다른 작업자가 그대로 믿고 따라 시간을 잃음. 그래서 담기 전 검증 수준으로 갈라 다룸:

- **검증됨**(실행·코드·공식문서로 직접 확인): 사실로 단정해 기록.
- **불확실**(외부출처 미검증·추정·전언): 버리지 말되 사실 단정 금지 — 검증 방식(실행확인·코드확인·외부출처(미검증)·추정)·불확실 항목·시간민감 지식의 갱신 날짜를 본문에 명시.
- **신빙성 미달**(표기로도 못 살릴 만큼): 담지 않음. 애매하면 빼는 쪽.

근거·출처도 본문에 남겨 다음 사람이 재검증할 수 있게 함.

## 작성 방법

- **자동 기록(확인 불필요)**: 위키 기록(`write`)은 외부 발행 사전 확인 대상이 아님 — 사용자에게 묻지 않고 자동 수행하는 것이 이 위키의 설계. 대상 여부는 위 "무엇을 담는가/담지 않는가" 기준으로만 판단해, 맞으면 묻지 말고 그대로 기록.
- **중복 확인 선행**: 기록 전 `search`(+ 관련 hub 의 `children`)로 겹치는 기존 페이지를 확인. **있으면** `read` 로 받아 갱신·통합(중복 페이지 생성 금지), **없으면** 새 `topic` 으로 `write`.
- **상위 지정**: 새 페이지는 `--parent <상위topic>` 로 주제에 맞는 hub 아래에 편입. 진짜 새 최상위 도메인일 때만 `--parent` 생략(루트). 없는 상위 topic 을 주면 서버가 거부(throw).
- **재분류·이동**: 분류만 바꾸려면 `move <topic> --parent <상위>`(내용 불변·순수 이동) 또는 `--root`(최상위로). 본문 기록과 함께면 `write --parent`(갱신 시 `--parent` 생략하면 기존 상위 유지). `topic`(정체성)은 불변 — 키 rename 없음.
- **교차 주제**: 여러 hub 에 걸치는 내용은 상위를 여럿 두지 않고 본문의 cross-link(다른 `topic` 언급)로 연결.
- **갱신 충돌 방지(낙관락)**: 공용이라 다른 작업자·세션이 동시에 쓸 수 있음. 갱신은 `read` 로 받은 `version` 을 `--base-version` 으로 넘겨 씀. 읽은 뒤 누가 먼저 바꿨으면 CLI 가 자동 덮어쓰지 않고 충돌을 알림(종료코드 3 · stdout 에 `conflict:true` + 최신 본문 `latest`). 그 `latest` 에 이번 변경을 재통합한 뒤 `--base-version <latest.version>` 으로 다시 write — 남의 수정을 덮어쓰지 않도록 자동 재시도하지 않음.
- **요약 = 라우팅 전용**: *그 페이지를 언제 여는지*(어떤 상황·문제에서 펼치는지)만 적음. **본문 사실의 복제 금지** — 수치·코드·구체 패턴·근거·날짜·세부 결론은 요약에 넣지 않고 본문에만 둠(목차만 읽고 내용을 다 알게 만들면 안 됨). 한 요약은 한 줄, 대략 100자 이내.
- **본문에만 둘 것 (요약 금지)**: 핵심 주장의 근거·출처, 검증 방식·불확실 항목, 시간 민감 지식의 갱신 날짜 — 요약 아닌 본문에 둠(검증 수준별 처리는 "정확성").
- **모순 처리**: 새 지식이 기존과 모순되면 무판단 덧붙이기 금지 — 어느 쪽이 노후인지 판단해 덮어쓰거나, 둘 다 맥락상 유효하면 적용 조건을 명시해 공존.

## 트리 모양 유지

분류·기록 시 트리가 라우터로 기능하도록 모양을 관리 — 고정 숫자 기준 없이 "한눈에 라우팅되는가" 로 판단.

- **루트 수를 작게**: ROOT MAP 은 매 세션 자동 주입되므로 최상위 노드 수가 곧 주입량. 새 주제는 맞는 기존 루트 hub 아래로 넣고, 진짜 새 최상위 도메인일 때만 루트 신설.
- **분할**: hub 의 자식 목록이 한눈에 라우팅되지 않을 만큼 커지고 자연스러운 하위 묶음이 보이면, 중간 sub-hub 를 만들어 관련 자식을 그 아래로 재분류.
- **이동·재분류**: `move <topic> --parent <상위>`(내용 불변) 로 노드를 옮김.
- **머지**: navigation hop 만 늘리는 hub 는 `delete` — `delete` 가 자식을 상위로 자동 재배치(reparent)하므로, hub 를 지우면 자식이 상위로 접혀 올라감(자식 수동 이동 불필요).

## 유지·점검

- **전체 점검·정리는 `sd-wiki-lint` 스킬**: lint(기계 진단)→의미 점검(모순·노후·비대상·누락 개념·데이터 공백)→정리→재검증을 한 흐름으로 완수. "위키 점검·정리·정돈" 요청은 이 스킬로 — 아래는 그 구성 원리.
- **기계 진단은 `lint`**: 끊긴 상위·cross-link 참조, 고아, 트리 통계(루트 과다·과대 hub)를 `lint` 로 한 번에 진단. 검색 결과 0건(지식 공백)·저조회 페이지(정리 후보) 신호도 함께. lint 는 위상 점검만 — 모순·노후 등 의미 점검은 본문을 읽어 직접.
- **판단·정리는 직접**: `lint` 결과를 받아 모순·노후·비대상(작업 기록성·단일 프로젝트 국한) 페이지를 판단해 `write`(정정·통합)·`move`(재분류)·`delete`(제거·머지)로 정리. 데이터 보존 — 삭제는 자식을 상위로 보존(reparent).
- ROOT MAP 이 자동 주입되므로 루트 노드 요약을 짧게, 루트 수를 작게 유지 — 비대해지면 주입이 잘림.
