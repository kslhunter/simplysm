# 원격 공용 위키

누적 지식 위키의 구조:

- 위치: 로컬 파일이 아닌 팀 공용 원격 서버.
- 페이지 구성: `topic`(유니크 키) + 제목·요약·본문(마크다운)·버전 + **상위 페이지**. 페이지가 상위-자식 관계로 **재귀 트리(forest)** 를 이룸 — 자식 있는 노드는 hub, 자식 없는 노드는 leaf(별도 종류 구분 없이 파생).
- 자동 주입: SessionStart 훅이 세션 시작 시 **ROOT MAP**(상위 없는 최상위 노드의 라우팅 목록)만 주입 — 전체 목차 아님. 그 아래 지식은 트리를 따라 온디맨드로 펼침.

읽기·기록·검색·탐색은 위키 CLI 로 함 — 실행 형식 `bun "${CLAUDE_PLUGIN_ROOT}/cli/wiki.ts" <명령>`. 사용 가능한 명령:

| 명령               | 동작                                                                                          |
| ------------------ | --------------------------------------------------------------------------------------------- |
| `rootmap`          | 최상위 노드의 라우팅 목록(topic·제목·요약·자식 유무). ROOT MAP — 세션에 자동 주입되므로 보통 갱신 후 새로 볼 때만 호출 |
| `children <topic>` | 그 노드의 직속 자식 라우팅 목록(자식 유무 포함). 없는 topic 이면 에러, 자식 없는 leaf 면 빈 목록 |
| `read <topic>`     | 페이지 1건 조회 — 제목·요약·본문·버전. 없으면 빈 결과                                          |
| `write <topic>`    | 페이지 생성·갱신 — 제목·요약·본문, `--parent <topic>` 로 상위 지정, 갱신 시 기준 버전(낙관락)  |
| `search <keyword>` | 제목·요약·본문 키워드 검색 — 라우팅 항목 반환                                                  |
| `toc`              | 전체 페이지 평면 목록. 온디맨드 fallback(자동 주입 아님) — 트리 탐색으로 진입점을 못 찾을 때만 |
| `delete <topic>`   | 페이지 삭제 — 자식이 있으면 상위로 재배치(reparent) 후 노드만 삭제(서브트리 보존). `--base-version` 으로 낙관락 |
| `move <topic>`     | 내용 변경 없이 상위만 이동 — `--parent <topic>` 또는 `--root`(최상위로). 순수 위치 변경(`write` 와 달리 본문 재전송 불필요) |
| `lint`             | 위키 점검 — 끊긴 상위·cross-link·고아·트리 통계 진단. 정리 판단은 결과를 받아 직접 |

각 명령의 인자·옵션(`[]` 선택 · `|` 택일 · 모든 명령 앞에 `[--no-browser]` 가능):

```
rootmap
toc
lint
read <topic>
children <topic>
search <keyword>
write <topic> --title <제목> --summary <요약> (--body <본문> | --body-file <경로> | stdin 파이프) [--parent <topic>] [--base-version <기준버전>]
delete <topic> [--base-version <기준버전>]
move <topic> (--parent <topic> | --root)
```

`write` 본문은 `--body`·`--body-file`·stdin 중 하나로만 입력(`--body` 와 `--body-file` 동시 금지). 인증·토큰 갱신은 CLI 가 자동 처리(만료 시 브라우저 로그인). 결과는 JSON.

## 페이지 탐색

세션엔 ROOT MAP 만 주입됨(전체 목차 아님) — 필요한 지식은 트리를 따라 펼쳐 찾음.

- 경로: 주입된 ROOT MAP 에서 관련 최상위 노드 식별 → `children <topic>` 로 자식 펼침 → 더 깊으면 자식의 `children` 반복 → 목표 leaf 의 `read <topic>` 로 본문 활용.
- 자식 유무(`hasChildren`)로 펼칠지 결정 — hub(자식 있음)면 `children` 으로 더 펼치고, leaf(자식 없음)면 바로 `read`(leaf 에 불필요한 `children` 호출 안 함).
- ROOT MAP 에 관련 진입점이 안 보이면 `search` 로 키워드 검색해 진입점 찾기.
- 본문이 다른 `topic` 을 가리키면(cross-link) 그 topic 도 `read` 로 확인.
- 페이지가 노후했고 현재 작업과 맞지 않으면, 사용자 요청을 기다리지 말고 그 자리에서 재검증·갱신.

## 무엇을 담는가 — 판정 질문 + 4관문

**위키의 헌법: 틀린·노후·국한 정보는 없느니만 못하다.** 다른 작업자가 그대로 믿고 따라 시간을 잃기 때문. 그래서 기본값은 **"안 담음"** 이다.

**판정 질문**(담을 가치): "다음에 비슷한 상황에서 이 페이지를 열어 시간을 아낄, 비자명하고 반복되는 내용인가?" 공식 문서로 그 자리서 쉽게 재확인되는 일반 사실은 비자명성 미달이라 안 담음(문서로 찾기 어려운 함정·반복 패턴만 예외). 아니오·애매면 안 담음.

가치가 있어도 아래 **4관문을 모두 통과**할 때만 담는다. 하나라도 못 넘으면 재현 가능한 일반 원리로 추상화하고, 그래도 안 되면 버린다.

### 관문 1 — repo 독립
한 repo·프로젝트에서만 유효한 정보 금지. 특정 repo 의 파일 경로·내부 구조·"우리가 이렇게 만들었다", 특정 고객·프로젝트 1곳의 정책·합의, 개인·로컬 경로는 그 repo 의 로컬 프로젝트 위키(`.wiki/` — 아래 "로컬 프로젝트 위키" 참조)로 보내고 원격 위키엔 안 담음.

- **라이브러리를 *쓰는* 지식은 허용**(특정 repo 아님 — 그 라이브러리 쓰는 모든 곳에 재사용): "simplysm@N·Angular@N 에서 A 대신 B" 등. 단 아래 **라이브러리 4조건**을 함께 충족.
- **라이브러리를 *만드는* 지식은 금지**(그 모노레포 1곳 내부): 빌드 파이프라인·내부 파일 패치·major 업그레이드 수정 위치 등 → 그 repo 문서로.

### 관문 2 — 버전 안전
구버전 라이브러리를 쓰는 repo 에서도 틀리지 않아야. 1순위는 버전 독립 원리로 기술. 불가피한 버전 의존이면 의존 도구·버전 범위를 본문 머리에 명시 + "그 밖 미보장" 경계(버전 없이 단정 금지). "현재 최신은 X" 같은 시점 의존 서술 금지(시간 지나면 거짓).

### 관문 3 — 검증됨 + 출처 추적
실행·코드·공식문서로 직접 확인한 것만 사실로 담음. 추정·전언·미검증은 담지 않음. **모든 핵심 주장에 재방문 가능한 출처를 본문에 남긴다 — 출처 없으면 검증 안 된 것으로 보고 안 담음.**

- 출처 유형: ①사용자 발언·경험("사용자 전언" 표시) ②외부 공식문서·표준(URL·문서명·식별자 — LLM 이 열어 부가정보를 읽을 수 있는 형태) ③재현(실행 명령·결과; 외부 라이브러리는 버전+경로/심볼).
- 위키엔 요지만, 깊은 내용은 출처로 위임(얇게 유지 + 출처로 깊이 연결).
- "합의했다"는 결정이지 사실 검증이 아니다. **자기 repo 코드를 출처로 단 지식은 관문1 위반**(외부 라이브러리는 버전 명시로 출처 가능). 검증 방법·시점·출처는 본문 머리/근거에 남겨 재검증·노후 판단을 돕는다.

### 관문 4 — 영속 (시한부·일기 아님)
- X→Y 버전 전환 절차(마이그레이션)·"방금 한 작업"·완료 보고·1회성 검토 결론·commit/PR/log 성 기록 금지. (라이브러리의 *현 버전 상태 규칙*은 OK, *전환 절차*는 금지.)
- 특정 건의 사례 수치·진행 경위·"~했더니 됐다" 서사 금지 — 일반화된 원리·기준·원인·해결만.
- 다음 분기에도, 몇 년 뒤에도 유효한 원리만.

### 라이브러리 의존 규칙 4조건 (관문1에서 허용한 "쓰는 지식"을 담을 때 전부 충족)
1. 의존 라이브러리+버전 범위 명시(`simplysm@14.x`·`Angular@17`) + "그 밖 미보장" — 관문2.
2. '그 버전 상태의 규칙'만, 'X→Y 전환 절차'는 금지 — 관문4.
3. '왜 그런지' 근거 검증(라이브러리 코드·문서·재현). "고객 합의"는 근거 아님 — 관문3.
4. 그 라이브러리 쓰는 일반에 유효한 원리만, repo·고객 1곳 정책 금지 — 관문1.

## 운영
- **부패 시 삭제 우선**: 노후·검증불가·추상화불가면 고치려 매달리지 말고 삭제. 살리려다 틀린 채 남기느니 없앤다.
- **전제 자가표기**: 버전·OS·도구 의존이 남으면 그 전제를 본문 머리에 명시해 독자가 자기 환경과 즉시 대조하게.
- **얇게 유지**: 검색·주입 비용. 작업 과정 단발 정보는 그 작업 산출물(코드 주석·PR·spec)에 남기고 위키엔 안 올림.

## 작성 방법

- **자동 기록(확인 불필요)**: 위키 기록(`write`)은 외부 발행 사전 확인 대상이 아님 — 사용자에게 묻지 않고 자동 수행하는 것이 이 위키의 설계. 대상 여부는 위 "무엇을 담는가/담지 않는가" 기준으로만 판단해, 맞으면 묻지 말고 그대로 기록.
- **중복 확인 선행**: 기록 전 `search`(+ 관련 hub 의 `children`)로 겹치는 기존 페이지를 확인. **있으면** `read` 로 받아 갱신·통합(중복 페이지 생성 금지), **없으면** 새 `topic` 으로 `write`.
- **상위 지정**: 새 페이지는 `--parent <상위topic>` 로 주제에 맞는 hub 아래에 편입. 진짜 새 최상위 도메인일 때만 `--parent` 생략(루트). 없는 상위 topic 을 주면 서버가 거부(throw).
- **재분류·이동**: 분류만 바꾸려면 `move <topic> --parent <상위>`(내용 불변·순수 이동) 또는 `--root`(최상위로). 본문 기록과 함께면 `write --parent`(갱신 시 `--parent` 생략하면 기존 상위 유지). `topic`(정체성)은 불변 — 키 rename 없음.
- **교차 주제**: 여러 hub 에 걸치는 내용은 상위를 여럿 두지 않고 본문의 cross-link(다른 `topic` 언급)로 연결.
- **갱신 충돌 방지(낙관락)**: 공용이라 다른 작업자·세션이 동시에 쓸 수 있음. 갱신은 `read` 로 받은 `version` 을 `--base-version` 으로 넘겨 씀. 읽은 뒤 누가 먼저 바꿨으면 CLI 가 자동 덮어쓰지 않고 충돌을 알림(종료코드 3 · stdout 에 `conflict:true` + 최신 본문 `latest`). 그 `latest` 에 이번 변경을 재통합한 뒤 `--base-version <latest.version>` 으로 다시 write — 남의 수정을 덮어쓰지 않도록 자동 재시도하지 않음.
- **요약 = 라우팅 전용**: *그 페이지를 언제 여는지*(어떤 상황·문제에서 펼치는지)만 적음. **본문 사실의 복제 금지** — 수치·코드·구체 패턴·근거·날짜·세부 결론은 요약에 넣지 않고 본문에만 둠(목차만 읽고 내용을 다 알게 만들면 안 됨). 한 요약은 한 줄, 대략 100자 이내.
- **본문에만 둘 것 (요약 금지)**: 핵심 주장의 근거·출처, 검증 방식, 의존 도구·버전 전제, 시간 민감 지식의 갱신 날짜 — 요약 아닌 본문에 둠(관문3·운영의 자가표기).
- **모순 처리**: 새 지식이 기존과 모순되면 무판단 덧붙이기 금지 — 어느 쪽이 노후인지 판단해 덮어쓰거나, 둘 다 맥락상 유효하면 적용 조건을 명시해 공존.

## 트리 모양 유지

분류·기록 시 트리가 라우터로 기능하도록 모양을 관리 — 고정 숫자 기준 없이 "한눈에 라우팅되는가" 로 판단.

- **루트 수를 작게**: ROOT MAP 은 매 세션 자동 주입되므로 최상위 노드 수가 곧 주입량. 새 주제는 맞는 기존 루트 hub 아래로 넣고, 진짜 새 최상위 도메인일 때만 루트 신설.
- **분할**: hub 의 자식 목록이 한눈에 라우팅되지 않을 만큼 커지고 자연스러운 하위 묶음이 보이면, 중간 sub-hub 를 만들어 관련 자식을 그 아래로 재분류.
- **이동·재분류**: `move <topic> --parent <상위>`(내용 불변) 로 노드를 옮김.
- **머지**: navigation hop 만 늘리는 hub 는 `delete` — `delete` 가 자식을 상위로 자동 재배치(reparent)하므로, hub 를 지우면 자식이 상위로 접혀 올라감(자식 수동 이동 불필요).

## 로컬 프로젝트 위키 (`.wiki/`)

repo 국한 + 온디맨드 지식의 전담 저장소 — 원격 위키 관문 1 에서 탈락한 지식의 공식 수신처.

**경계 (어디에 쓰는가)**:

- 원격 공용 위키: repo 독립·영속 지식 (위 4관문).
- 로컬 `.wiki/`: 그 repo 에서만 유효한 지식 — 내부 구조·경로·정책·합의·함정. 온디맨드로 열어 볼 지식.
- CLAUDE.md: 매 세션 상시 필요한 최소 지침만. 온디맨드로 충분한 repo 지식은 CLAUDE.md 를 불리지 말고 `.wiki/` 로.
- 관문 1 외 나머지 기준(판정 질문·검증됨·영속·얇게 유지)은 로컬 위키에도 동일 적용 — 틀린·노후 정보는 로컬에서도 없느니만 못하다.

**구조 (평문 md 폴더 트리)**:

- 위치: 프로젝트 루트 `.wiki/**/*.md`. CLI 없음 — Read·Write·Glob·git 으로 직접 다룸.
- 페이지 = md 파일. frontmatter 에 `summary:`(필수 — 라우팅 요약)·`title:`(선택 — 없으면 파일명이 제목). 파일명은 짧은 슬러그, 긴 표시 제목은 `title:` 로.
- 폴더 = hub. 폴더 요약은 폴더 안 `README.md` 의 frontmatter. `.wiki/` 직속 `README.md` 는 트리 자체의 hub 페이지(루트맵 항목 아님).

**탐색**:

- 세션 시작 시 훅이 `.wiki/` 최상위 라우팅 목록(로컬 ROOT MAP)만 주입 — 전체 목차 아님. `.wiki/` 가 없거나 비어 있으면 무주입.
- 주입 목록에서 관련 항목 식별 → 폴더면 열어(Glob + frontmatter) 더 펼치고, 파일이면 Read 로 본문 활용. 원격과 동일한 온디맨드 원리.
- 루트맵 항목에 `(요약 없음)` 이 보이면 그 페이지를 열어 본 김에 frontmatter `summary:` 를 보충.

**작성**:

- 원격과 동일하게 자동 기록 — 대상 판정(repo 국한 + 판정 질문 통과)에 맞으면 묻지 않고 기록. `.wiki/` 가 없으면 만들어 기록.
- 기록 전 기존 페이지 확인(Glob·Grep) — 겹치면 갱신·통합, 없으면 새 파일.
- 요약 = 라우팅 전용(그 페이지를 언제 여는지 한 줄) — 본문 사실 복제 금지. 원격의 요약 규칙과 동일.
- 트리 모양: 최상위 항목 수가 곧 세션 주입량 — 최상위를 작게, 커지면 폴더(hub)로 묶음.

## 유지·점검

- **전체 점검·정리는 `sd-wiki-lint` 스킬**: lint(기계 진단)→의미 점검(모순·노후·비대상·누락 개념·데이터 공백)→정리→재검증을 한 흐름으로 완수. "위키 점검·정리·정돈" 요청은 이 스킬로 — 아래는 그 구성 원리.
- **기계 진단은 `lint`**: 끊긴 상위·cross-link 참조, 고아, 트리 통계(루트 과다·과대 hub)를 `lint` 로 한 번에 진단. 검색 결과 0건(지식 공백)·저조회 페이지(정리 후보) 신호도 함께. lint 는 위상 점검만 — 모순·노후 등 의미 점검은 본문을 읽어 직접.
- **판단·정리는 직접**: `lint` 결과를 받아 모순·노후·4관문 위반(repo 국한·버전 미안전·미검증·시한부/일기) 페이지를 판단해 `write`(정정·통합)·`move`(재분류)·`delete`(제거·머지)로 정리. 부패(노후·검증불가·추상화불가) 시 정정보다 삭제 우선. 삭제는 자식을 상위로 보존(reparent).
- ROOT MAP 이 자동 주입되므로 루트 노드 요약을 짧게, 루트 수를 작게 유지 — 비대해지면 주입이 잘림.
