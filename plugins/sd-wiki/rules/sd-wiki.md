# 원격 공용 위키

팀 공용 원격 서버의 누적 지식 위키입니다.
페이지는 `topic`(유니크 키) + 제목, 요약, 본문(마크다운), 버전 + 상위 페이지이며, 상위-자식 관계로 재귀 트리를 이룹니다 (자식 있으면 hub, 없으면 leaf — 별도 종류 구분 없이 파생).

세션 시작 시 훅이 ROOT MAP(최상위 노드의 라우팅 목록)만 주입합니다. 전체 목차가 아니며, 그 아래 지식은 트리를 따라 온디맨드로 펼칩니다.

## CLI

실행 형식은 `python "${CLAUDE_PLUGIN_ROOT}/cli/wiki.py" <명령>` 입니다.

- 이 경로는 플러그인 설치 위치로 CLI 실행 전용입니다.
- 현재 작업 프로젝트가 아니므로 이 경로 기준으로 파일을 읽거나 쓰지 마세요.

명령:

- `rootmap` — 최상위 라우팅 목록. 자동 주입되므로 보통 갱신 후 새로 볼 때만
- `children <topic>` — 직속 자식 라우팅 목록. 없는 topic 은 에러, leaf 는 빈 목록
- `read <topic>` — 페이지 1건 (제목, 요약, 본문, 버전). 없으면 빈 결과
- `write <topic>` — 생성, 갱신
  - 필수: `--title <제목> --summary <요약>` + 본문 1개 (`--body <본문>` / `--body-file <경로>` / stdin)
  - 선택: `--parent <topic>`, `--base-version <버전>`
- `search <keyword>` — 제목, 요약, 본문 키워드 검색. 라우팅 항목 반환
- `toc` — 전체 페이지 평면 목록. 트리 탐색으로 진입점을 못 찾을 때만 쓰는 fallback
- `delete <topic> [--base-version <버전>]` — 노드만 삭제. 자식은 상위로 재배치(reparent)되어 서브트리 보존
- `move <topic> (--parent <topic> | --root)` — 내용 불변, 상위만 이동 (`write` 와 달리 본문 재전송 불필요)
- `lint` — 끊긴 상위, cross-link, 고아, 트리 통계 진단. 정리 판단은 결과를 받아 직접

- 모든 명령 앞에 `--no-browser` 를 붙일 수 있습니다.
- 인증, 토큰 갱신은 CLI 가 자동 처리합니다 (만료 시 브라우저 로그인).
- 결과는 JSON 입니다.

## 탐색

주입된 ROOT MAP 에서 관련 최상위 노드를 식별하고 → `children` 으로 펼치고 → 더 깊으면 반복하고 → 목표 leaf 를 `read` 하세요.

- `hasChildren` 로 펼칠지 결정하세요. leaf 에 불필요한 `children` 을 호출하지 마세요.
- ROOT MAP 에 진입점이 안 보이면 `search` 로 찾으세요.
- 본문이 다른 `topic` 을 가리키면(cross-link) 그 topic 도 `read` 로 확인하세요.
- 페이지 내용이 현재 작업과 어긋나면, 요청을 기다리지 말고 그 자리에서 재검증, 갱신하세요.
  - 서술 자체가 틀렸으면 고치세요.
  - 그 페이지가 다른 버전을 전제하고 내 버전에서만 동작이 갈리면, 기존 서술을 지우지 말고 버전 조건을 붙여 병기하세요.

## 무엇을 담는가 — 판정 질문 + 4관문

기본값은 "안 담음"입니다.

- 틀린, 노후, 국한 정보는 없느니만 못합니다.
- 다른 작업자가 그대로 믿고 따라 시간을 잃기 때문입니다.

판정 질문은 "다음에 비슷한 상황에서 이 페이지를 열어 시간을 아낄, 비자명하고 반복되는 내용인가?" 입니다.

- 공식 문서로 그 자리서 쉽게 재확인되는 일반 사실은 비자명성 미달이니 담지 마세요 (문서로 찾기 어려운 함정, 반복 패턴만 예외입니다).
- 아니오이거나 애매하면 담지 마세요.

가치가 있어도 아래 4관문을 모두 통과할 때만 담습니다. 하나라도 못 넘으면 재현 가능한 일반 원리로 추상화하고, 그래도 안 되면 버리세요.

관문 1 — repo 독립. 한 repo, 프로젝트에서만 유효한 정보는 금지입니다.

- 특정 repo 의 파일 경로, 내부 구조, "우리가 이렇게 만들었다", 특정 고객, 프로젝트 1곳의 정책, 합의, 개인, 로컬 경로를 담지 마세요.
- 라이브러리를 _쓰는_ 지식은 허용됩니다 (그 라이브러리 쓰는 모든 곳에 재사용되므로). "simplysm@N, Angular@N 에서 A 대신 B" 등입니다.
- 라이브러리를 _만드는_ 지식은 금지입니다 (그 모노레포 1곳 내부입니다). 빌드 파이프라인, 내부 파일 패치, major 업그레이드 수정 위치 등입니다.

관문 2 — 버전 안전. 구버전 라이브러리를 쓰는 repo 에서도 틀리지 않아야 합니다.

- 1순위는 버전 독립 원리로 기술하는 것입니다.
- 불가피한 버전 의존이면 의존 도구, 버전 범위를 본문 머리에 명시하고 "그 밖 미보장" 경계를 함께 적으세요. 버전 없이 단정하지 마세요.
- "현재 최신은 X" 같은 시점 의존 서술은 시간이 지나면 거짓이 되니 쓰지 마세요.

관문 3 — 검증됨 + 출처 추적. 실행, 코드, 공식문서로 직접 확인한 것만 사실로 담습니다.

- 추정, 전언, 미검증은 담지 마세요.
- 모든 핵심 주장에 재방문 가능한 출처를 본문에 남기세요. 출처가 없으면 검증 안 된 것으로 봅니다.
- 출처 유형은 셋입니다.
  - 사용자 발언, 경험("사용자 전언" 표시)
  - 외부 공식문서, 표준(URL, 문서명, 식별자 — LLM 이 열어 읽을 수 있는 형태)
  - 재현(실행 명령, 결과. 외부 라이브러리는 버전+경로/심볼)
- 위키엔 요지만 담고 깊은 내용은 출처로 위임하세요 (얇게 유지하면서 출처로 깊이를 연결합니다).
- "합의했다"는 결정이지 사실 검증이 아닙니다. 자기 repo 코드를 출처로 단 지식은 관문1 위반입니다 (외부 라이브러리는 버전 명시로 출처가 가능합니다).

관문 4 — 영속 (시한부, 일기 아님). 몇 년 뒤에도 유효한 것만 남깁니다.

- X→Y 전환 절차(마이그레이션), "방금 한 작업", 완료 보고, 1회성 검토 결론, commit/PR/log 성 기록을 담지 마세요. 라이브러리의 _버전을 명시한 상태 규칙_ 은 되지만 _전환 절차_ 는 안 됩니다.
- 특정 건의 사례 수치, 진행 경위, "~했더니 됐다" 서사 대신 일반화된 원리, 기준, 원인, 해결만 담으세요.

## 운영

- 틀린 페이지는 삭제를 우선하세요.
  - 검증불가, 추상화불가이거나 서술이 사실과 어긋나면 고치려 매달리지 말고 삭제하세요.
  - 살리려다 틀린 채 남기느니 없애는 게 낫습니다.
  - 오래됐다는 것만으로는 삭제 사유가 아닙니다. 구버전에서 여전히 맞는 서술은 적용 버전을 조건으로 붙여 남기세요.
- 전제를 자가표기하세요. 버전, OS, 도구 의존이 남으면 그 전제를 본문 머리에 명시해 독자가 자기 환경과 즉시 대조하게 하세요.
- 얇게 유지하세요. 검색, 주입 비용 때문입니다.
  - 작업 과정 단발 정보는 그 작업 산출물(코드 주석, PR, spec)에 남기고 위키엔 올리지 마세요.

## 작성 방법

- 자동 기록 — 위키 `write` 는 외부 발행 사전 확인 대상이 아닙니다. 위 4관문 기준에 맞으면 사용자에게 묻지 말고 그대로 기록하세요.
- 중복 확인 선행 — 기록 전 `search`(+ 관련 hub 의 `children`)로 겹치는 페이지를 확인하세요.
  - 있으면 `read` 로 받아 갱신, 통합하세요. 중복을 생성하지 마세요.
  - 없으면 새 `topic` 으로 `write` 하세요.
- 상위 지정 — 새 페이지는 `--parent <상위topic>` 로 주제에 맞는 hub 아래 편입하세요.
  - 진짜 새 최상위 도메인일 때만 생략합니다(루트).
  - 없는 상위를 주면 서버가 거부합니다.
- 재분류 — 분류만 바꾸려면 `move`(내용 불변), 본문 기록과 함께면 `write --parent` 를 쓰세요. 갱신 시 생략하면 기존 상위가 유지됩니다.
  - `topic` 은 불변이며 rename 이 없습니다.
- 교차 주제 — 여러 hub 에 걸치면 상위를 여럿 두지 말고 본문 cross-link 로 연결하세요.
- 낙관락 — 공용이라 동시 수정이 발생합니다.
  - 갱신은 `read` 로 받은 `version` 을 `--base-version` 으로 넘기세요.
  - 충돌 시 CLI 가 덮어쓰지 않고 알립니다 (종료코드 3, `conflict:true` + 최신 본문 `latest`).
  - 그 `latest` 에 이번 변경을 재통합해 다시 write 하세요. 자동 재시도로 남의 수정을 덮어쓰지 마세요.
- 요약은 라우팅 전용입니다. _그 페이지를 언제 여는지_(어떤 상황, 문제에서 펼치는지)만 한 줄 100자 이내로 쓰세요.
  - 수치, 코드, 구체 패턴, 근거, 날짜, 세부 결론은 요약에 넣지 말고 본문에만 두세요. 목차만 읽고 내용을 다 알게 만들면 안 됩니다.
  - 핵심 주장의 근거, 출처, 검증 방식, 버전 전제, 갱신 날짜도 본문 몫입니다.
- 모순 처리 — 새 지식이 기존과 모순되면 무판단으로 덧붙이지 마세요.
  - 어느 쪽이 노후인지 판단해 덮어쓰거나, 둘 다 유효하면 적용 조건을 명시해 공존시키세요.

## 트리 모양 유지

트리가 라우터로 기능하도록 관리하세요. 고정 숫자 기준 없이 "한눈에 라우팅되는가"로 판단합니다.

- 루트 수를 작게 유지하세요. ROOT MAP 은 매 세션 주입되므로 최상위 노드 수가 곧 주입량이고, 비대해지면 잘립니다.
  - 새 주제는 맞는 기존 루트 hub 아래로 넣고 진짜 새 최상위 도메인일 때만 루트를 신설하세요.
  - 루트 노드 요약도 짧게 유지하세요.
- 분할 — hub 의 자식 목록이 한눈에 라우팅되지 않을 만큼 커지고 자연스러운 하위 묶음이 보이면, 중간 sub-hub 를 만들어 재분류하세요.
- 머지 — navigation hop 만 늘리는 hub 는 `delete` 하세요. 자식이 상위로 자동 reparent 되므로 수동 이동이 필요 없습니다.

전체 점검, 정리("위키 점검, 정리, 정돈" 요청)는 `sd-wiki-lint` 스킬로 처리하세요.
