# sd-tdd: TDD 개발

Task 문서(구현계획)를 기반으로, Slice를 등장 순서대로 직렬 구현하는 Double Loop TDD 스킬.

개발 프로세스: WBS 문서 작성 → Task 문서 작성 → TDD 개발

## 기본 원칙

- 메인 직렬 수행: Slice 구현은 메인이 직접 수행한다. `Agent` tool 위임 금지.
- 설계 결정 구속력: 사용자가 확정한 plan 결정을 그대로 따른다.
- 시도 불가·범위 밖 사안: 작업 메모에 누적하여 Step 3-4에서 일괄 전달한다.
- 진짜 실패(테스트 통과 불가·빌드 에러 등): 즉시 사용자에게 보고하고 토론하여 해결한다. 토론 결과 plan에 영향이 있으면 즉시 plan을 갱신한 뒤 다음 Slice를 진행한다.

## 흐름 개요

```
sd-tdd (메인 세션)
├─ Step 1: Task 문서 읽기 + 코드베이스 탐색 + 패턴 메모
├─ Step 2: TaskCreate로 Slice 목록 등록 → 등장 순서대로 직접 구현
│         Slice 단위 구현 가이드: references/slice-tdd-guide.md
└─ Step 3: Task 완료 처리 (정리 → 마킹 → wbs 반영 → 통보)
```

## Step 1: Task 문서 읽기 + 코드베이스 탐색

### 1-1. Task 문서 읽기

Task 문서 경로가 필수이다. 입력되지 않았거나 대화로 유추할 수 없다면 `/sd-plan`을 안내하고 종료한다.

Task 문서 및 WBS 문서의 `## 참조 자료` 섹션 및 그 하위 섹션을 함께 읽고, 참조 자료의 구체적 정보(업무 규칙·데이터 형식·기술 제약 등)를 구현에 반영한다.

### 1-2. 기준 코드 탐색·확인

**CRITICAL: 코드가 source of truth이다.** 문서가 아닌 실제 코드를 기준으로 파악하며, 탐색 없이 다음 단계로 넘어가지 않는다.

#### (a) Task 문서의 `## 코드베이스 분석` 섹션 활용

- `## 코드베이스 분석` 섹션이 있으면, 인용된 **모든 파일을 Read 도구로 직접 읽는다**. 요약만 보고 넘어가지 않는다.
- 인용 라인 주변 컨텍스트(±20줄 권장)를 함께 읽어 패턴의 전체 형태를 파악한다.

#### (b) 섹션이 없거나 부실할 때 — 직접 탐색

- 코드베이스에서 이 Task와 가장 유사한 기존 기능을 찾는다.
- 탐색 대상: 관련 엔티티/모델, 기존 API 엔드포인트 및 패턴, 사용 중인 프레임워크·아키텍처, 기존 시스템 연동 방식, 성능/보안 제약, 관련 테스트 구조, 관련 의존성과 설정.
- 발견한 항목을 `파일경로:라인번호` 인용과 함께 작업 메모로 정리한다. 인용 없는 항목은 신뢰하지 않는다.

#### (c) 패턴 메모 정리

다음 관점에서 이번 Task 구현 시 따를 패턴을 작업 메모(메인 세션 내 텍스트)로 정리한다. Task 문서·별도 파일에 기록하지 않는다.

- 네이밍 규칙 (파일·클래스·함수·변수)
- 디렉토리 구조 / 파일 배치
- 에러 처리·검증 방식
- 의존성 주입·import 패턴
- 테스트 구조·헬퍼 사용 패턴
- **UI 구조·레이아웃 / 컴포넌트 구성·생김새** (HTML 골격, CSS 클래스 네이밍, 컨트롤 배치, 반응형/스타일 토큰 사용 패턴 등)

이 메모는 Step 2 Slice 구현 시 패턴 기준으로 참조한다.

여러 방식이 혼재되어 있거나 유사 패턴이 존재하지 않아 결정할 수 없다면 `sd-clarify` 지침에 따라 패턴을 명확화한다.

### 1-3. 테스트 환경 확인

테스트 환경(vitest 설정·테스트 디렉토리·devDependencies)이 부재하면 첫 Slice 진입 전 `references/test-setup.md`에 따라 환경을 세팅한다. 환경 부재나 plan의 테스트 회피 결정을 이유로 TDD를 건너뛰지 않는다 (plan은 테스트를 결정하지 않는 영역).

## Step 2: Slice 단위 직렬 구현 (메인)

Step 2~3 진행 중 발견한 다음 항목은 **작업 메모(메인 세션 내 텍스트)** 로 누적하여 Step 3-4에서 일괄 전달한다.

- 변경 파일 목록 (신규/수정 경로)
- 시도 불가·범위 밖 사안
- plan/wbs 영향 변경 사항

### 2-1. Slice 목록 등록

기존 `TaskCreate` 목록이 있으면 모두 정리한 뒤, `## 구현 단위 (Story → Slice)`의 Slice를 등장 순서대로 등록한다. 한 Slice = 하나의 task. 첫 Slice를 `in_progress`로 표시한다.

### 2-2. Slice 구현

각 Slice마다 `references/slice-tdd-guide.md`에 따라 메인이 직접 구현한다. Slice 종료 시:

- 해당 task를 `completed`로 마킹
- 변경 파일 경로를 작업 메모에 누적
- 시도 불가·범위 밖 사안을 작업 메모에 누적
- 다음 Slice를 `in_progress`로 마킹하고 진행

### 2-3. 실패·이슈 처리

Slice 구현 중 진짜 실패(테스트 통과 불가·빌드 에러 등)가 발생하면 `sd-debug`를 호출하여 원인 분석과 처리 방향을 받는다.

sd-debug 결과로 다음 중 하나로 처리된다:

- plan 수정 후 재시도: Story 명세·설계 결정 변경
- 다른 접근으로 재시도: plan 변경 없이 다른 구현 방식 적용
- 해당 Slice 또는 후속 Slice 스킵

#### plan 즉시 반영

plan에 영향을 주는 결정이 나오면 다음 Slice 진행 전 Task 문서를 즉시 갱신한다.

- Story 명세 변경: 해당 Scenario·Rule 갱신, `[근거: 사용자 답변 (Step 2-3)]` 태그 추가
- 설계 결정 변경: `### 설계 결정` 표에 새 행 추가 또는 기존 행 갱신, 변경 사유 명시
- Slice 스킵: 해당 Slice 헤더에 스킵 사유 메모 (체크박스는 Step 3-2에서 일괄 처리). 후속 Slice 스킵 시 Step 3-4 누적 보고에 사유와 함께 기록.

wbs 영향이 있는 What 변경(Story 근거 보강·Task 경계 조정·의존성 변경)은 별도 누적했다가 Step 3-3에서 일괄 반영한다.

## Step 3: Task 완료 처리 (메인)

### 3-1. 최종 테스트 정리

Task 전체 테스트를 회귀 테스트 가치 관점에서 직접 정리한다. 다음 항목 적용:

- 중복 Unit Test 삭제 (`test`/`it` 단위 판단. Acceptance Test와 검증 대상·입력값이 동일한 개별 케이스만 삭제. 파일 단위 삭제 금지. Slice 간 중복 포함)
- 구현 결합 테스트 전환/삭제 (내부 상태 값·메서드 호출 횟수 등 구현 세부사항 검증 테스트)
- 공통 setup 추출 (중복 arrange 코드를 헬퍼/beforeEach로)
- 테스트 네이밍 개선 (검증 동작을 문장처럼 읽히게)

정리 후 전체 테스트를 실행하여 회귀가 없는지 확인한다. 회귀가 발생하면 `sd-debug`를 호출하여 원인 분석과 처리 방향을 받는다.

### 3-2. Slice 체크박스 갱신

Task 문서 `## 구현 단위 (Story → Slice)`에서 완료된 Slice의 체크박스를 `[x]`로 갱신한다. 모든 Slice가 `[x]`이면 WBS 파일(`wbs.md`)에서 해당 Task의 `[ ]`를 `[x]`로 갱신한다.

스킵된 Slice는 `[ ]` 상태를 유지하고 Task 문서에 스킵 사유 메모를 남긴다.

### 3-3. wbs 역방향 피드백

Step 2-3에서 누적된 What 변경(Story 근거 보강·Task 경계 조정·의존성 변경 등)을 `sd-clarify` 지침에 따라 명확화한 뒤 wbs.md에 일괄 반영한다.

- Story 근거 보강: 해당 Story의 `(근거: ...)` 줄에 추가 사유 병기
- Task 경계 조정: 해당 Task의 `**경계:**` 항목에 새 줄 추가
- 의존성 변경: 해당 Task의 `**의존성:**` 줄과 `## 의존성 매트릭스` 표 동시 갱신

반영 시 기존 체크박스 상태·번호·사용자 메모는 보존한다.

구조 변경(Task 분할·이관·신규 Task)은 wbs에 직접 반영하지 않고 Step 3-4 누적 보고에 포함하여 사용자가 `/sd-wbs` 또는 `/sd-plan`으로 후속 처리하도록 한다.

How 결정(코드 패턴·테스트 구조 등)은 wbs에 기록하지 않고 plan의 `## 구현 설계`와 `### 설계 결정`에만 유지한다.

누적된 What 변경이 없으면 본 단계는 생략한다.

### 3-4. Task 완료 보고

다음 양식으로 사용자에게 일괄 전달한다.

**변경 사항 요약** (항상 출력 — 후속 sd-check/sd-review 인계용)

- 변경 파일 목록 (작업 메모 누적분)
- 변경 패키지 (변경 파일 경로에서 추출 — 예: `core-common`, `angular`)

**누적 보고** (해당 항목이 있을 때만)

- plan에 즉시 반영된 변경 사항 요약 (Step 2-3 적용분)
- wbs에 반영된 What 변경 요약 (Step 3-3 적용분)
- 의도적으로 스킵된 Slice 목록 + 사유
- 범위 밖 발견 사항 (기존 코드 결함·관련 모듈 이슈 등 사용자 후속 처리 필요)
- wbs 구조 변경이 필요한 신호 (Task 분할·이관·신규 Task 도출 등)
- 그 외 사용자 결정이 필요할 수 있는 사안
