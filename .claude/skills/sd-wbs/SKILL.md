# sd-wbs: 프로젝트 분해 (USM)

WBS는 고객 중심으로 **무엇을 만들어야 하는지(What)** 를 확정하는 산출물이다.
앞으로 해석이 갈리지 않을 고객 동작과 업무 규칙만 남긴다.

이 스킬은 User Story Mapping(USM, Jeff Patton) 기법을 따른다.
사용자 활동(Activity) → 작업(Task) → 사용자 시나리오(Story)의 3계층 구조로 분해한다.

## What/How 경계

이 스킬은 비즈니스 요구사항(What)만 분석한다.

**What — 이 스킬에서 반드시 확정 (위임 금지):**

- 고객/사용자 동작, 업무 규칙, 정책, 예외 흐름
- 수치(최대/최소/기본값/허용 범위), 기간, 시간대, 경계값
- 권한, 역할, 상태, 상태 전이, 열거값(enum 후보)
- 화면/플로우의 분기 조건과 결과
- 기능 포함 여부 자체

**How — 이 단계의 범위가 아님:**

- 인증 방식, 통신 프로토콜, 프레임워크, 아키텍처 패턴
- DB 종류, API 형태, 컴포넌트 구조, 테스트 분해
- 라이브러리 선택, 의존성 주입, import 패턴

분류가 모호하면 What으로 본다.

## Step 1: 요구사항 수집

요구사항과 **프로젝트 개요**(배경, 환경, 전제조건, 기술적 제약)를 함께 파악한다.

**입력 형태별 처리:**

- 문서 파일(docx, xlsx, pdf 등)이 제공된 경우, `/sd-doc-extract`로 내용을 추출하여 분석한다.
- 기존 wbs.md 경로를 제공하고 수정하기를 원하는 경우, 해당 문서를 읽고 업데이트한다.
- 마이그레이션 등 기존 시스템이 요구사항 원천인 경우, 기존 코드베이스를 참조하여 기능을 파악한다.

**기존 wbs.md 수정 시 보존 규칙:**

- 기존 체크박스 상태(`[ ]`/`[x]`), Activity·Task·Story 번호, 사용자 메모, 이미 확정된 제외 사항을 임의 초기화·삭제하지 않는다.
- 번호 변경이 필요한 경우 기존 번호 → 새 번호 매핑과 변경 사유를 문서에 남긴다.

### 원본 완독

- 모든 원본(첨부 파일, 메시지 본문, 메일 thread, 회의 대본)을 끝까지 읽는다. 키워드 검색만 종결 금지.
- 자료별 분량(페이지/라인/통수)을 보고에 명시하여 부분 독해를 표면화한다.
- 모든 자료가 완독되기 전 다음 단계로 진행 금지.

## Step 2: Impact Mapping

Impact Mapping 트리(Goal → Actor → Impact → Deliverable)를 도출한다.

### Impact Mapping 도출 질문

모든 사항은 `sd-clarify` 지침에 따라 명확화 한다.

| 질문                                  | 도출 요소            |
| ------------------------------------- | -------------------- |
| Q1. "왜 만드나?" 반복                 | Goal (측정 가능하게) |
| Q2. "누가 쓰나? 누가 영향받나?"       | Actor                |
| Q3. "그 사람 행동이 어떻게 바뀌어야?" | Impact (행동 변화)   |
| Q4. "가장 단순하게 뭘 만들면?"        | Deliverable          |
| Q5. "뭘 빼나?"                        | 제외 사항            |

**나쁜 예:**

- `인증 방식을 SSO로 할지 자체 인증으로 할지?` → 질문 불필요. 분해 범위에는 "사용자 인증"만 기술
- `어떤 DB를 사용할지?` → 질문 불필요. 분석 단계의 범위가 아님

### Impact Mapping 규칙

- 모든 Activity·Task·Story가 Goal까지 역추적 가능해야 한다 — Goal에 연결되지 않는 기능은 제외 사항으로 보낸다
- Goal은 구체적 목적을 명확히 기술한다. "효율화한다"(X) → "대출·반납 기록을 시스템으로 관리하여 분실을 방지한다"(O). 수치 기반이 가능하면 좋지만 필수 아님.
- Impact는 기능이 아닌 **행동 변화**를 기술한다. "대시보드를 본다"(X) → "업무 상태를 빠르게 파악한다"(O)

### Impact Mapping 결과 보고

명확화 완료 후, 도출된 Impact Mapping 트리를 사용자에게 보고한다. 보고 후 사용자 응답을 기다리지 않고 Step 3으로 진행한다.

출력 형식:

```
## Impact Mapping 결과

- **Goal:** {목표}
  - **Actor:** {이해관계자}
    - **Impact:** {행동 변화}
      - **Deliverable:** {산출물}

- **제외 사항:** {사용자가 제외를 확정한 항목 — 없으면 생략}
```

## Step 3: USM Breakdown

Deliverable을 Activity → Task → Story로 구조화한다.

모든 사항은 `sd-clarify` 지침에 따라 명확화 한다.

### 분해 원칙

USM의 모든 단위는 **사용자 동작 단위**이다. 다음 분할은 절대 금지.

| 금지 분할                                                                  | 사유                                             | 대신                         |
| -------------------------------------------------------------------------- | ------------------------------------------------ | ---------------------------- |
| 아키텍처 레이어 (DB/서비스/UI, 서버/클라이언트, 패키지, 백엔드/프론트엔드) | end-to-end 수직 슬라이스 위배                    | 각 Task가 모든 레이어를 포함 |
| Actor(관리자/직원/고객) 별 동일 도메인 분할                                | 동일 활동을 권한으로 쪼개면 사용자 여정이 분절됨 | Story 안에 Actor·권한 표기   |
| 테스트 단위 분리                                                           | 검증은 구현과 동시 작성                          | 후속 `/sd-tdd`에서 함께 처리 |

**좋은 예:**

- Activity "도서 관리" → Task "도서 등록", "도서 검색", "도서 대출/반납"
- Task "도서 검색" → Story "회원이 도서명으로 검색한다", "회원이 저자명으로 검색한다"

**나쁜 예:**

- Activity "백엔드" / "프론트엔드" — 레이어 분할
- Task "도서 등록 API" / "도서 등록 UI" — 레이어 분할
- Task "도서 등록(관리자)" / "도서 조회(직원)" — Actor 분할

사용자 입력이 위 금지 분할(레이어/Actor)을 명시 요청하더라도 그대로 따르지 않는다. USM 패러다임으로 재해석하여 사용자 동작 단위로 분해하고, 재해석 사항을 재해석 목록에 등록한다.

### 3-1. Activity Backbone 도출

Activity는 사용자가 시스템과 함께 달성하는 큰 활동(=업무 영역)이다. 사용자 여정의 시간 흐름 또는 업무 묶음을 따라 Backbone을 구성한다.

- Activity는 사용자 관점의 기능 영역(비즈니스 기능)으로 도출
- Activity 간 순서는 사용자 여정의 시간 흐름 또는 업무 의존성을 반영

**좋은 예:**

- "회원 가입/인증" → "도서 검색" → "대출/반납" → "도서 관리"

### 3-2. Task 분해

Task는 Activity 안의 사용자 작업이다. 후속 스킬(`/sd-plan`, `/sd-tdd`)의 1 작업 단위이다.

- 각 Task는 end-to-end 수직 슬라이스 (DB → 서비스 → UI 모두 포함)
- Task 단위로 독립 설계·개발·검증 가능

각 Task에는 다음을 반드시 포함한다.

- **경계**: 이 Task가 하지 않는 것 중 다른 Task에서 다루거나 다룰 수 있는 것 (인접 Task와의 경계가 모호하면 특히 중요)
- **근거**: Impact Mapping Deliverable 인용 + 요구사항 출처 + 참조 자료 경로(있으면 확인 목적과 함께)
- **의존성**: 다른 Task와의 의존 관계. 형식: Task 번호만 쉼표로 나열 (예: `1.1, 2.3`) 또는 `없음`

#### Task 최소 단위 작성

처음 만들 때 정의(end-to-end 수직 슬라이스, 1 사용자 작업 단위)를 지키면서 최소 단위로 만든다.

- 기본 동작과 확장 동작의 구분이 가능하면 별도 Task로 분리한다
- 네이밍: `{기능명} — {범위 설명}` (예: "도서 관리 — 기본 CRUD", "도서 관리 — 추천/통계")
- 확장 Task는 기본 Task에 대한 의존성을 명시한다
- 기본 Task만으로 해당 기능의 핵심 동작이 완성되어야 한다
- 분리하기 위해 정의를 깨지 않는다 (트리거 1번에 동시 출력되는 산출물은 한 Task)

#### 의존성 판단 절차

다른 Task의 산출물(API, 컴포넌트, 데이터 구조 등) 또는 결정(명명 규칙, 공통 패턴, 분기 구조 등)이 이 Task에 영향을 줄 가능성이 있으면 의존성에 포함한다. "코드 간 import 없음"은 의존성 없음을 의미하지 않는다.

의존성이 없다는 근거를 명시할 수 없으면 의존성이 있는 것으로 간주한다. 과소 설정(블로킹·재작업)이 과대 설정(약간의 직렬화)보다 비용이 크다.

### 3-3. Story 작성

Story는 Task 안의 한 사용자 시나리오이다. 한 줄 사용자 동작 형식으로 작성한다.

- 형식: `대상/사용자 + 동작 + 조건/결과 + 항목별 근거`
- 항목별 근거는 `(근거: ...)` 형식으로 반드시 기재 (출처: Impact Mapping Deliverable, 요구사항, 사용자 답변, 첨부문서 등)
- 권한·역할 분기는 Story 안의 Actor 표기로 처리 (Task 분할 X)

**좋은 예:**

- "회원이 도서명 또는 저자명으로 도서 목록을 검색한다. (근거: 요구사항 2.1)"
- "검색 결과가 없으면 회원이 빈 결과 상태를 확인한다. (근거: 사용자 답변)"
- "관리자가 도서 정보를 수정한다. 일반 회원에게는 수정 버튼이 보이지 않는다. (근거: 요구사항 3.2)"

**나쁜 예:**

- "검색 기능" — 동작 명시 부족
- "도서 목록 개선" — 완료 판정 불가
- "회원이 검색한다" — 대상·결과 누락

항목별 근거가 없는 Story는 Task에 포함하지 않는다. 근거가 없는 항목은 `sd-clarify` 지침에 따라 포함 여부를 명확화한다.

- 추정 진행, "추후 결정" fallback, 자체 추가 금지.
- wbs.md 본문에 "후속 확정/보류/추후 결정/협의 필요" 같은 미확정 표현 사용 금지.

## Step 4: 자가검증 (Self-Refine)

1차 산출된 분해 결과를 아래 검증 관점 4가지로 **MUST** 순회 점검하여 발견 항목 목록을 확정한다.

모든 발견 항목은 `sd-clarify` 지침에 따라 명확화 한다.

### 검증 관점

Backbone 흐름·Story 단위 적정성·양방향 커버리지는 Step 6 격리 검증에서 다룬다. 이 단계에서는 다음 항목만 점검한다.

1. **의존성 순서** — 의존 대상이 뒤 번호에 있거나 같은 단계 내에 있으면 번호/순서 재정렬.
2. **분해 원칙 준수** — Step 3 분해 원칙(레이어 분할 금지, Actor 분할 금지, 테스트 단위 분리 금지) 위반이 없는지 확인.
3. **미루기 표현 제거** — "후속 확정/보류/추후 결정/협의 필요/plan에서 결정/구현 시 결정/별도 확정" 등 본문 미루기 표현 점검. 발견 시 What이면 `sd-clarify` 지침에 따라 명확화, How이면 본문에서 제거.
4. **항목별 근거 확인** — 모든 Story 끝에 `(근거: ...)`가 있는지 확인. 근거가 없으면 `sd-clarify` 지침에 따라 명확화.

### 의존성 매트릭스

의존성 매트릭스를 생성하여 다음을 확인하고, **반드시 wbs.md 본문 `## 의존성 매트릭스` 섹션에 포함한다**:

1. **누락 확인**: 각 Task의 Story가 다른 Task의 산출물을 참조하거나 결정에 의해 내용이 바뀔 수 있는데 의존성에 빠져 있지 않은지 크로스체크
2. **순환 확인**: A→B→A 같은 순환 의존성이 없는지 확인 (발견 시 Task 분할로 해소)
3. **1단계 존재 확인**: 의존성이 없는 Task가 최소 1개 이상 존재하는지 확인

매트릭스 형식:

```
| Task | 의존 대상 |
|------|----------|
| 1.1  | 없음      |
| 1.2  | 1.1      |
| 2.1  | 1.1      |
| 2.2  | 1.1, 2.1 |
```

## Step 5: WBS 문서 생성

산출물 경로:

- **입력이 `.tasks/` 내 기존 문서인 경우:** 해당 문서와 같은 폴더에 `wbs.md` 생성 (예: `.tasks/260411_some-project/requirements.md` → `.tasks/260411_some-project/wbs.md`)
- **그 외:** `.tasks/{timestamp}_{topic}/wbs.md`
  - `{timestamp}`: `date +%y%m%d%H%M%S` 실행 결과
  - `{topic}`: 영어 kebab-case (예: `task-management`)

### 문서 템플릿

```markdown
# WBS: {주제 한 줄 설명}

## 프로젝트 개요

- **배경:** [왜 이 프로젝트가 필요한지]
- **환경:** [기존 시스템, 운영 환경, 사용자 규모 등]
- **전제조건:** [프로젝트 시작 전 충족되어야 할 조건]
- **기술적 제약:** [사용자가 언급한 기술 스택, 환경 제약 등]
- **참조 자료:** [프로젝트 전역 참조 파일/문서 경로 — 각 항목에 확인 목적을 명시]

## Impact Mapping

- **Goal:** [측정 가능한 목표]
  - **Actor:** [이해관계자]
    - **Impact:** [행동 변화]
      - **Deliverable:** [산출물]

## USM Backbone

### Activity 1. [Activity 이름]

#### [ ] Task 1.1 [Task 이름]

**의존성:** 없음

**경계:**

- 애니메이션 효과는 이 Task에서 다루지 않음

**근거:**

- Impact Mapping Deliverable: "상세 정보 팝업"
- 요구사항: "팝업 형태로 상세 정보 표시"

**Stories:**

##### Story 1.1.1 상세 정보 팝업 열기

- 회원이 목록 항목을 클릭하면 상세 정보가 팝업으로 열린다. (근거: 요구사항 "팝업 형태로 상세 정보 표시")

##### Story 1.1.2 배경 클릭 닫기

- 회원이 팝업 외부 영역을 클릭하면 팝업이 닫힌다. (근거: 사용자 답변 "배경 클릭으로 닫기 필요")

## 제외 사항

- 애니메이션 효과 — 사유: 사용자 명시적 제외 / 출처: 사용자 답변 / 재검토 조건: 별도 UX 개선 Story 요청 시

## 의존성 매트릭스

| Task | 의존 대상 |
| ---- | --------- |
| 1.1  | 없음      |
```

**진행 상황:** Task별 `[ ]` 체크박스로 진행을 추적한다.

**제외 사항:**

- 사용자가 명시적으로 "포함 안 함"으로 결정한 항목과 Impact Mapping에서 Goal에 연결되지 않는 기능을 나열한다.
- 각 항목은 `제외 항목 — 사유: ... / 출처: ... / 재검토 조건: ...` 형식으로 작성한다.
- 사유에는 Goal 미연결, 사용자 명시적 제외, 범위 초과 중 하나를 사용한다. "미확정"은 사유로 사용하지 않는다.

## Step 6: 격리 검증 (정보 유실·누락 점검)

자체 판단으로 생략 금지. 자체 요약 텍스트로 대체 금지. 반드시 Agent tool 호출로 수행한다.

문서 작성 후, 작성자 편향 제거와 정보 유실 차단을 위해 메인 세션과 분리된 subagent로 격리 검증을 수행한다.

### 6-1. 검증 호출

subagent(effort: `low`)를 다음 입력으로 호출한다:

- **wbs.md 절대 경로** — 검증 대상
- **원본 자료 절대 경로 목록** — 첨부 파일(docx/xlsx/pdf 등). `/sd-doc-extract`로 추출된 파일이 있으면 함께 전달.
- **사용자 초기 요청 메시지 본문** — 프롬프트에 인라인 삽입

사용자 명확화 답변·결정사항은 wbs.md의 `근거:` 필드와 "제외 사항"에 반영되어 있으므로 별도 전달하지 않는다.

subagent에 부여할 제약: "보고만 수행. wbs.md를 수정하지 말 것."

### subagent 프롬프트에 포함할 검증 가이드

#### 검증 항목

1. **정량 매핑 표 (양방향 커버리지)** — 원본에서 카테고리별 사실 항목을 추출하여 wbs.md 위치(Story 번호/프로젝트 개요)에 1:1 매핑.

- 추출 카테고리: 수치(최대/최소/기본값/허용 범위, 기간, 시간대, 경계값) / 열거값(상태, 권한, 역할, 옵션 후보) / 업무 규칙·정책 / 제약 조건 / 권한·역할(Actor) / 상태 전이 / 예외 흐름·분기 조건 / 참조 자료 경로 + 확인 목적
- 누락: 원본에 있는데 매핑되지 않은 항목
- 근거 없는 추가: wbs.md에 있는데 원본/근거에서 추적 불가한 항목

2. **의역 변형 검출** — 원문이 구체적인데 wbs.md가 추상화된 사례 (예: 원문 "최대 100건" → wbs "다수 항목")

3. **Backbone 흐름 적정성** — Activity 순서가 사용자 여정의 시간 흐름·업무 의존성과 일치하는지 점검

#### 완독 의무

원본 자료(첨부 파일·인라인 요청 메시지)는 끝까지 읽는다. 키워드 검색만으로 종결하지 않는다.

#### 출력 포맷

- **요약** — 원본 항목 수 / 매핑·누락·근거 없는 추가·의역 변형·Backbone 부적정 (각 정수)
- **정량 매핑 표** — 컬럼: `원본 표현` / `출처(자료명·위치)` / `wbs.md 반영 위치` / `wbs 표현` (반영 위치 빈칸 = 누락)
- **누락 / 근거 없는 추가 / 의역 변형 / Backbone 부적정 목록** — 각 항목 출처, 권장 반영 위치, 권장 처리 방향 포함
  - 누락: "Story X.Y에 추가" / "제외 사항 등록"
  - 근거 없는 추가: "근거 보강" / "삭제"
  - 의역 변형: "원문 표현으로 복원"
  - Backbone 부적정: "Activity 순서 X→Y로 변경"

### 6-2. 메인의 결과 처리

1. 모든 결과 항목은 `sd-clarify` 지침에 따라 명확화 한다.
2. Activity/Task/Story 구조 재작성이 필요하면 Step 3 해당 하위 단계로 되돌아간다.

각 Task는 새 세션에서 진행되므로 wbs.md에 누락이 있어서는 안 된다.

## Step 7: 수행 순서·다음 단계 안내

문서 작성이 완료되면, 의존성을 기반으로 Task를 단계별로 그룹화하여 수행 순서를 안내한다.

- 의존성이 없는 Task들을 1단계로 묶는다
- 이전 단계의 Task에만 의존하는 Task들을 다음 단계로 묶는다
- 같은 단계 내 Task는 병렬 수행 가능함을 표시한다
- 각 Task의 선행 의존성을 `(← ...)` 형태로 명시한다

예시:

```
1단계 (병렬 수행 가능)
  - Task 1.1: 공통 프로바이더 & 플러그인

2단계 (병렬 수행 가능)
  - Task 1.2: 홈 레이아웃 & 사이드바 메뉴 (← 1.1)
  - Task 2.1: 입고 처리 (← 1.1)
  - Task 2.2: 출고 처리 (← 1.1)
```

수행 순서 안내 후, 개발 진입 명령을 안내한다 (예: `/sd-dev {wbs.md_파일경로} 1.1`).
