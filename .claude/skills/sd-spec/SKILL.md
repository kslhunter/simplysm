# sd-spec

요구사항을 분석하여 spec.md 1개로 산출. 최우선 목적 = 정확한 spec (환각 차단·누락 차단). 연산 단위로 채워나감 — 호출 1회 = 연산 1개, spec.md 라는 영속 산출물에 대한 연산의 모음.

## 입출력

- **Input**: Requirement Source (회의록·메일·문서·PDF·발화 등 비정형 자료) + 사용자와의 대화 + (재진입 시) 기존 spec.md.
- **Output**: spec.md 1개 (후속 도구 sd-impl·sd-demo 의 입력 계약).
- **폴더**: `.specs/{yyMMddHHmmss}_{slug}/`.
  - `yyMMddHHmmss`: PowerShell `Get-Date -Format "yyMMddHHmmss"` 명령으로 생성 (예: `260513204500` = 2026-05-13 20:45:00).
  - `slug`: 짧은 한·두 단어. 허용 문자는 한글·영문·`_`·`-`·공백 (그 외 문자는 금지).

## 연산

sd-spec 은 2종의 연산으로 동작. 사용자 지시를 받으면 아래 디스패치로 분기. 작성은 배치로 한 번에 하고, 사용자가 사후 검토(검토 패키지)로 정정.

### 디스패치

| 지시 유형                                              | 연산        | 처리 경로                                     |
| ----------------------------------------------------- | ----------- | --------------------------------------------- |
| "분석해줘"·"요구사항 분석"·"초안 작성"·"spec 작성" 류 (신규 spec.md 작성) | 초안 배치   | 메인 에이전트가 직접 순차 수행 (아래 "초안 배치")    |
| 그 외 모든 지시 ("X를 Y로"·"A를 B와 합쳐"·"이 섹션 이상해"·"설계만 다시"·재진입 정정) | 부분 수정   | SKILL.md 인라인 처리 (아래 "부분 수정")        |

- 초안 배치는 메인 에이전트가 자율 진행. 실행 중 사용자에게 묻지 않음 (모르는 건 [OPEN]).
- 초안 배치는 **신규 spec.md 작성 전용** (요건→설계를 한 흐름으로 통합). 기존 spec.md 가 있는 재진입(부분 재작업·정정·"설계만 다시")은 모두 부분 수정 경로.

### 초안 배치 (메인 직접 순차 수행)

신규 spec.md 작성 지시("분석해줘"·"초안 작성"·"spec 작성" 류). 메인 에이전트가 spec.md 를 **한 줄기로 순차 빌드**함 (코딩하듯 — 앞 단위가 만든 §7·§8·§9 를 뒤 단위가 재사용·확장). 작성은 전부 메인 직접, **검증만 독립 Agent**.

**준비**:

- 폴더·경로: "입출력" 의 폴더 규칙으로 신규 `.specs/{yyMMddHHmmss}_{slug}/spec.md` 경로를 만들고, "spec.md 골격" 으로 골격(§1~§10 빈 헤더)을 Write.
- 시스템명: 사용자와 합의한 시스템명(제목 `{name}`). 날짜: PowerShell `Get-Date -Format "yyyy-MM-dd"` (§10 로그 타임스탬프용). 자료(Requirement Source)는 직접 Read.

**단계 (직렬 — 각 단계는 그 시점에 확정된 것만 다룸)**:

1. **요건 (§1~3 + §7)**: `references/format.md` 의 요건·공통 작성법(§1·§2·§3·§7) + 공유 형식("spec.md 형식" 절)을 Read. 자료를 직접 Read 해 §1 개요·§2 업무 프로세스(pivotal event 로 §2/§3 분할)·§3 기타 요구를 작성. 작성 중 나오는 도메인 어휘·공통 규격은 §7 에 누적. **§4~9 는 빈 헤더로 두고 손대지 않음** (설계가 아직임). 비자명 항목엔 근거, 모르면 [OPEN].

2. **설계 (§4~6 순차 빌드 + §8·§9·§7 점진 누적)**: `references/format.md` 의 설계 작성법(§4~9)을 Read. §1~3·§7 을 입력으로 §4 화면 → §5 자동 처리 → §6 공통·기반 의 단위를 **하나씩 순차로** 작성. 각 단위(§4.x 등)를 작성하면서 그 단위가 참조하는 §8 도메인 모델·§9 외부 인터페이스를 **그 자리에서 즉시 spec 에 추가·갱신** (없으면 신설, 있으면 재사용·필드 확장)하고, 새 용어는 §7 에 누적. §4 첫머리 화면 목록 표도 단위가 늘 때마다 갱신. 별도 "집계" 단계는 없음 — 누적이 곧 §8·§9 작성임 (§8·§9 불변식은 "섹션 구조" 절 참조).

3. **검증 (독립 Agent, 규모 비례)**: 작성 완료 spec 을, 작성한 메인이 아닌 **독립 서브에이전트(Agent 도구)로 검증**함 (자기검증 편향 차단). 검증 항목 — ① 근거 좌표 1:1 실재 대조(원자료 재독), ② 원자료↔spec 전수 누락 역대조 + 자료 커버리지, ③ 요구 커버리지(요건 → §4~6 역대조), ④ dangling 참조 grep. 규모(자료 수·근거 수)에 비례해 항목별/자료별로 Agent 를 병렬로 펼치되, 대상이 아주 작으면 메인 직접도 허용. 근거 위조로 판정된 항목은 `(근거: …)` 를 떼고 [OPEN] 으로 강등(원 좌표는 메모로 보존).

4. **검토 패키지 + 정지**: "연산 사이 검토" 의 검토 패키지를 제시하고 정지.

### 부분 수정 (인라인)

초안 배치(신규 spec.md 작성) 외의 모든 지시는 SKILL.md 가 메인 에이전트로 직접 처리. 재진입(기존 spec.md 에 대한 추가 작업 — "설계만 다시"·재설계 포함)도 이 경로.

- **정밀 지시** ("§4.2 의 X 컬럼을 Y로", "이 항목 [OPEN] 으로") → 바로 Edit. 무관 섹션은 건드리지 않음 (일괄 치환 금지 — Edit 의 `old_string` 을 유일 매칭되게 좁혀서 수정).
- **모호 지적** ("이 섹션 이상해", "여기 흐름이 안 맞아") → 무엇이 문제인지 진단을 먼저 제시 → 사용자 합의 → Edit. 추측으로 바로 고치지 않음.
- **구조 변경** (병합·분할·추가: "A 화면과 B 화면을 합쳐", "이 프로세스를 둘로 나눠") → 이름 기반 참조 cascade:
  - `[화면.X]`·`[모델.X]`·`[프로세스.X]` 등 이름 기반 참조("본문 내 참조" 절)를 grep 으로 전수 추적해, 병합·분할·삭제로 끊기는 참조를 함께 갱신.
  - § 번호는 자주 바뀌므로 이름으로 추적. 변경 후 dangling 참조가 남지 않게 확인.
- **구현 마커 제거** (§4~6 자신 또는 그 의존 § 를 수정한 경우) → 아래 "§4~6 `[구현]` 마커 제거" 절을 따라 영향 §4~6 의 `[구현]` 마커를 제거.
- 작성 형식·신뢰도 표기는 아래 "작성 원칙" 과 **대상 섹션의 작성법** (아래 "§별 작성법" 절 표에서 해당 ref 를 Read) 을 따름.

### §4~6 `[구현]` 마커 제거

§4.x/§5.x/§6.x 본문, 또는 그 본문이 의존하는 § 본문을 수정하면 그 §4~6 의 이전 구현은 무효가 됨 → 해당 §4.x/§5.x/§6.x 헤더의 `[구현]` 마커 제거 (sd-impl 재실행 대기 상태로). sd-spec 부분 수정·sd-impl spec 수정 양쪽이 이 절을 따름 (의존 식별·합의의 단일 출처).

**의존 식별** — §4.x/§5.x/§6.x 본문에 다음 중 하나라도 나타나는 §x.x 는 그 §4~6 의 의존 대상:

- `관련 섹션:` 줄의 `[프로세스.X]`·`[기타.X]`·`[화면.X]`·`[자동 처리.X]`·`[기반.X]`·`[외부 인터페이스.X]`.
- 본문 어느 위치든 등장하는 `[모델.X…]`·`[공통 정의.X]`.
- §7 외부 자료 명세를 컬럼명 일치로 끌어다 쓴 양식 매핑 표 (해당 §7.x).
- 모달 호출 `→ [화면.X]` 의 그 §4.x.

수정 대상이 §4~6 자신이면 그 자신의 `[구현]` 도 제거 대상 (sd-spec). 단 sd-impl 은 본 작업 단위(재구현 중)는 제외.

**합의** — 영향 §4.x/§5.x/§6.x 를 번호 매겨 각각 한 줄 이유와 묶어 "맞나요?" 합의 → 전체 동의 일괄 제거 / 일부 유지 지목 시 지목 항목만 마커 유지.

### 연산 사이 검토

각 연산(배치·부분 수정) 완료 후 동일하게:

1. spec.md 갱신 (write/Edit 완료).
2. **검토 패키지** 를 채팅으로 제시:
   - 이번에 쓴 섹션의 한 줄 요약.
   - `[OPEN]` 목록 (이번 연산이 남긴 미확정 항목).
   - 검증 결과 요약 (배치 연산의 경우 검증 Agent 가 반환한 근거 위조·누락·dangling 참조 보고).
   - 자료 커버리지 보고 (쓴 자료 중 spec 에 미반영된 부분).
   - **검증 Agent 실패 시** (배치): 검증 서브에이전트가 하나라도 실패하면 부분 결과로 검토 패키지를 만들지 말고 실패 사실을 [error] 로 알린 뒤 해당 검증만 재실행해 보완. 전건 정상 반환이어야 검증 완료로 간주.
3. **정지**. 초안 배치가 끝나도 후속 수정으로 자동 진입 금지. 다음 연산은 사용자가 호출.

## 작성 원칙

배치·부분 수정 모두에 적용되는 spec 정확성 원칙 (상위 행동 규칙·sd-design-rules 와 중복 금지, sd-spec 고유분만).

- **비자명 항목 inline 근거** — 자료에서 해석·도출한 비자명 항목에는 근거를 부착(아래 "신뢰도 표기"). 사용자가 직접 말한 자명한 항목엔 붙이지 않음.
- **모르면 [OPEN]** — 근거가 없으면 임의로 채우지 말고 [OPEN] 으로 표기 (판정 기준은 "신뢰도 표기" 절).
- **단순화 차단** — spec 의 식·분기·경계를 그대로 풀어쓰기. 방어 처리(NULL 강제·0 클램프·가드·분기 생략)로 임의 변형 금지(상위 "인터페이스 설계 시"·"결측 보존"의 spec 적용). 정확 풀이 부담이 크면 단순화안을 [OPEN] 표기하거나 검토 패키지에서 보고.
- **형식 준수** — 각 § 작성법 규약 + 그 § 첫머리 "모범" 의 example-spec.md 모범 §를 형식 모범으로 직접 대조 (모범 Read 없이 텍스트 규칙만으로 작성 금지). 다른 §·example 에서는 **형식만** 가져오고 **내용물**(항목·컬럼·필드·액션·동작) 은 본 §의 자료·발언에서 직접 도출.

검증 단계(독립 Agent)는 위 원칙의 준수를 독립 컨텍스트에서 사후 검증함 (검증 항목은 "초안 배치" 3단계 참조). 사람 사후 검토(검토 패키지)가 최종 안전망.

## spec.md 형식

### 섹션 구조

spec.md 의 § 별 섹션 이름과 분류:

**분류 기준**:

- **요건**: 고객 입장 As-Is/To-Be — 무엇을·왜.
- **설계**: 그걸 어떻게 만드나 — 구현 + 구현에 필요한 정보(UI·데이터구조·외부API).
- **공통**: 요건·설계 양쪽에서 도출·편집되는 어휘·규격.
- **자연 도출**: 직접 작성하는 단위가 아니라 다른 섹션을 쓰다 파생되는 섹션. 출처가 공통(§7 — 양쪽)인지 설계(§8·§9 — §4~6 파생)인지로 구분.
- **§8·§9 불변식**: §4~6 에 없는 기능의 도메인 모델·외부 인터페이스는 존재할 수 없음 — 설계 산물로서 §4~6 의 종속.

| §   | 섹션             | 분류                         |
| --- | ---------------- | ---------------------------- |
| §1  | 개요             | 요건 명세                    |
| §2  | 업무 프로세스    | 요건                         |
| §3  | 기타 요구사항    | 요건                         |
| §4  | 화면             | 설계                         |
| §5  | 자동 처리        | 설계                         |
| §6  | 공통·기반 기능   | 설계                         |
| §7  | 공통 정의        | 공통 자연 도출 (요건·설계 양쪽에서 도출·편집) |
| §8  | 도메인 모델      | 설계 자연 도출 (§4~6 에서 파생)              |
| §9  | 외부 인터페이스  | 설계 자연 도출 (§4~6 에서 파생)              |
| §10 | 본문 외 확정 사항 | 메타 (결정이 발생할 때마다 누적)     |

### 신뢰도 표기

spec.md 본문에서 항목의 신뢰도를 나타내는 표기. 전부 날짜 없음 (§10 로그 타임스탬프 제외).

| 표기                | 의미                                                                                                       |
| ------------------- | ---------------------------------------------------------------------------------------------------------- |
| (무표기)            | 직접·자명, 또는 미검토 초안. 기본 상태.                                                                    |
| 줄끝 `(근거: 출처)` | 자료에서 해석·도출한 **비자명** 항목의 근거 (예: `(근거: 회의록 L12)`). 사용자가 직접 말한 자명 항목엔 안 붙임. 위치 = 표는 비고 칸, 산문은 줄 끝. |
| `[OPEN]`            | 근거 없음. 필요 시 추측·필요자료 메모 동반 (예: `[OPEN] 박스당 수량 — As-Is상 24 추정, 미확인`).            |
| `[구현]`            | §4~6 구현 완료 표시. 부착은 sd-impl 소관. §4~6 또는 그 의존 § 수정 시 제거는 sd-spec·sd-impl 양쪽 수행 (아래 "§4~6 `[구현]` 마커 제거" 절).                                                  |

- `[OPEN]` 판정: 근거 부족(상위 행동 규칙 "결정 근거" 적용). As-Is 만 근거 / 추정 / 답변 범위 흡수 = 근거 없음 → `[OPEN]`.
- 확정 여부는 사용자가 직접 관리 — 헤더에 상태 마커(`[확정: 날짜]`·`[OPEN: 날짜]` 등)를 붙이지 않음.
- 예외: §10 "본문 외 확정 사항" 의 로그 항목은 순서 보존용 날짜를 유지(`- YYYY-MM-DD: ...`). 이건 신뢰도 마커가 아니라 로그 타임스탬프.

### 본문 내 참조 (이름 기반)

본문 내에서 다른 섹션을 참조할 때 § 번호 대신 `[카테고리.이름]` 형식 사용. 다단 표기 가능. § 번호는 분석 중 자주 바뀌므로 이름 기반 표기가 더 안정적.

예:
- `[모델.재고]`·`[모델.박스.수량]`·`[모델.박스.품목.코드]`.
- `[화면.재고 확인]`·`[프로세스.입고]`·`[기타.과거 재고 조회]`.
- `[자동 처리.재고 스냅샷]`·`[기반.DataLog 기록]`·`[외부 인터페이스.ERP 입고 통보]`·`[공통 정의.Location 라벨]`.

**관련 섹션 한 줄**: §2~§9 본문에 `관련 섹션: [카테고리.이름], ...` 형식의 한 줄로 참조·의존 섹션을 콤마로 나열 (카테고리 제한 없음). 별도 작성 단위가 아님 — 다른 sub-section 작성 시 곁가지로 자동 누적.

### sub-section 헤더 레벨

§별 sub-section 의 spec.md 본문 표기 룰 통합 — 평문 (헤더 없이 라벨·한 줄·bullet 직접) / h4 마크다운 헤더 (`####`).

| §  | 평문 sub-section (형식)                                       | h4 sub-section                                                       |
| -- | ------------------------------------------------------------- | -------------------------------------------------------------------- |
| §2 | BPMN (mermaid fence) · 흐름 설명 bullet · 관련 섹션 (한 줄)   | (없음)                                                               |
| §4 | 헤더 인덱스 (한 줄씩) · 기능 개요 (라벨 + bullet)             | 와이어프레임 · 항목 · 동작 · 시각 규칙 · 도메인 규칙·로직 · 자유 추가 |
| §5 | 목적 (라벨 + 한 줄) · 트리거 (라벨 + 본문) · 관련 섹션 (한 줄) | 처리 · 예외 처리 · 자유 추가                                         |
| §6 | 목적 · 트리거·적용 범위 (해당) · 관련 섹션 · 참조 매뉴얼 (기본 기능) | (없음 — bespoke 만 본문 자유 서술, 필요 시 h4 자유 추가) |
| §9 | 기본 정보 (라벨 bullet 3) · 관련 섹션 (한 줄)                 | 자료 매핑 · 예외 처리                                                |

본 SKILL.md 내의 `#### BPMN`·`#### 목적` 등의 표기는 작성법 설명용 sub-section 분류 표기. 실제 spec.md 본문에서의 표기는 위 표의 룰 따름.

### 진행 방법 누적

작업 중 사용자와 진행 방식을 합의하면 (예: "시트별로 분석") 즉시 누적. 적용 범위에 따라 2 경로:

**spec 전체에 적용되는 경우** → §10 의 진행 방법 항목으로 누적 (`- YYYY-MM-DD: ...` bullet 형식).

**분석 단위 한정** (§X.Y 또는 그 내부의 sub-section/sub-단위) → 해당 단위 도입부에 NOTE blockquote 작성:
- 형식: `> **NOTE** (진행 방법): <한 줄 요약>` blockquote + 다단 (`> 1. ...`·`> 2. ...` 형식).
- 분석 단위에 `[OPEN]` 항목이 남아 있으면 본 NOTE 가 다른 대화 재진입 시 진행 룰 회복의 출처가 됨.
- 본 단위가 모두 확정되면, NOTE 는 유지 (진행 이력 기록 보존) 하거나 제거 (분석 단위에만 적용되었던 룰이므로) 가능.

## §별 작성법

각 § 의 작성법(분할 절차·본문 구조·sub-section·모범)은 `references/format.md` 에 있음 — 요건·공통(§1·§2·§3·§7)과 설계(§4·§5·§6·§8·§9)를 한 파일로 통합. 작성·부분 수정 시 Read:

- 공유 형식(위 "spec.md 형식" 절: 섹션 구조·신뢰도 표기·본문 내 참조·sub-section 헤더 레벨·진행 방법)·골격·§10 은 본 SKILL.md 에 유지.
- **부분 수정** 시: `references/format.md` 의 편집 대상 섹션 작성법을 Read 한 뒤 편집.
- **초안 배치** 는 메인이 요건 단계·설계 단계에서 `references/format.md` 를 Read.

## §10 본문 외 확정 사항

§1~§9 의 어느 곳에도 자연스럽게 들어가지 않는 결정·메모를 누적. §1~§9 의 적절한 자리에 넣을 수 있는 결정은 §10 에 두지 않음 (누락 도피처가 아님).

**모범**: example-spec.md §10.

### 형식

각 항목의 구조:

- **헤더 1줄** (필수): `- YYYY-MM-DD: <결정 한 줄>`.
  - 분석 제외 시: `- YYYY-MM-DD [제외]: <결정 한 줄>`.
  - 날짜는 "초안 배치" 준비 단계에서 PowerShell `Get-Date` 로 생성한 값. 순서 보존용 로그 타임스탬프이며 신뢰도 마커가 아님.
- **자식 bullet**: 형식 자유 (개수·내용 모두 자유).
  - **결정 근거 1개 이상 필수**.
  - 자유 항목 예시: 자료 위치·영향 범위·대화 발췌·메모·관련 § 등.
  - 분석 제외 시 추가 필수 항목: `후속 처리`·`자료 위치`.

### 포괄 결정 종류

매번 분류하지 않음 — 자연 흐름대로 누적. 분석 제외 신호가 있을 때만 `[제외]` 마커 부착.

- **진행 방법**: **spec 전체** 작업에 대한 사용자 합의 진행 방식 (예: 작성 순서·범위 한정·전체 적용 규칙 등). 분석 단위에 한정된 진행 방법은 `## spec.md 형식` 의 "진행 방법 누적" 절 참조 — sd-spec 자신의 후속 참조용.
- **미래 결정**: 해당 단계에 도달하기 전에 미리 내린 결정 (예: "추후 §4.5 작성 시 X 항목 포함") — sd-spec 자신의 후속 참조용.
- **구현 영역 결정**: spec 본문에 들어가지 않는 구현 측 결정 (예: 라이브러리 선택) — sd-impl 의 후속 참조용.
- **부정 결정**: "X 안 함" 부정 명시 — 반복 질문 방지용.
- **분석 제외**: 본 spec 에서 다루지 않는 항목 — 다른 spec·sd-dev·운영 잔손 등 외부 후속 처리 대상.

### 예시

```
- 2026-05-22: 월간 마감 자동화 — 안 함
  - 근거: 회계팀 수동 처리 선호
  - 자료 위치: 회의록_3.md L120-135
  - 영향: §5 자동 처리 후보에서 제외

- 2026-05-22: 구현 시 결제 라이브러리 X 사용
  - 근거: 사용자 명시 (PG사 계약 호환)

- 2026-05-22 [제외]: 다국어 지원
  - 근거: 현재 단계 아님
  - 후속 처리: 다른 spec 신규
  - 자료 위치: 회의록_3.md L80-95

- 2026-05-22: §4 와이어프레임은 영역 추상화만, 시각 디테일은 항목 표/동작 절로 분리
  - 근거: 사용자 합의 — 와이어 분량 관리
```

## spec.md 골격 (초안 배치)

초안 배치에서 spec.md 를 신규 생성할 때 사용하는 골격. `{name}` 은 사용자와 합의한 시스템명.

```markdown
# {name} 요구 분석서

## 1. 개요

### 1.1 핵심 목적

### 1.2 주요 목표

### 1.3 최종 사용자/이해관계자

### 1.4 환경/장치

## 2. 업무 프로세스

## 3. 기타 요구사항

## 4. 화면

## 5. 자동 처리

## 6. 공통·기반 기능

## 7. 공통 정의

## 8. 도메인 모델

## 9. 외부 인터페이스

## 10. 본문 외 확정 사항
```

초안 배치 작성 범위 (골격은 요건 단계에서 생성, 본문은 두 단계로 채워짐):
- 요건 단계: 골격(§1~§10 헤더) 생성 + §1 개요·§2.x/§3.x 헤더·본문 (BPMN·흐름 설명 등)·§7 공통 정의(공통 자연 도출) 작성. 미확정 항목은 인라인 `[OPEN]`. §4~6·§8·§9 는 헤더만 두고 본문은 비움.
- 설계 단계: §4 화면·§5 자동 처리·§6 공통·기반 기능 본문 작성 → 그 §4~6 이 참조한 모델·외부호출을 모아 §8 도메인 모델·§9 외부 인터페이스를 파생 작성.
- §10 에는 자료에서 도출된 제외 결정 (`[제외]` 마커) 을 반영.
