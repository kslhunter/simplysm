# 모드별 표준 흐름 + 막힘 처리

## 모드별 표준 흐름


### TDD (비즈니스 로직, 알고리즘)
```
1. 실패하는 테스트 작성 (RED)
2. 테스트 실행 → 실패 확인
3. 통과하는 최소 코드 (GREEN)
4. 테스트 실행 → 통과 확인
5. 정리 (REFACTOR)
6. 테스트 재실행 → 통과 유지
```

### 사후 테스트 (UI, 외부 API)
```
1. 코드 작성
2. 동작 확인
3. 테스트 작성
4. 테스트 실행 → 통과 확인
```

### 생략 (마이그레이션, 일회성 스크립트)
```
1. 코드 작성
2. 타입체크/린트 통과 확인
```

### 모드 변경 정책

implement 도중 "이 R은 plan과 다른 모드 적합" 판단되면:
- **자동 변경 금지**. 사용자에게 Q → 승인 받으면 변경 + impl.md `이슈/결정` 기록.

## 막힘 처리

### 자동 시도
단순 에러(타입/린트/단순 테스트 실패)는 **자동 N=2회 시도**:
- 성공 → 다음 단계, impl.md `이슈/결정`에 "N회 시도 후 해결" 기록
- 실패 → 종류별 분기 (아래)

### 막힘 종류 (4가지)

| 종류 | 예시 | 처리 |
|---|---|---|
| 단순 에러 | 타입/린트/단순 테스트 실패 | 자동 N=2회 |
| 코드 문제 | 회귀 검증 실패, 비단순 테스트 실패 | impl.md `상태: 막힘` + Q (해결 방안) |
| 계획 문제 | plan.md ↔ 실제 코드 모순 | impl.md `상태: 보류` + plan 재진입 알림 |
| 정보 부족 | 패턴 모름, 옵션 선택 필요 | impl.md `상태: 막힘` + Q (정보 요청) |

### 사용자 답변 후

- 해결 방안 적용 → 다음 시도
- 우회 → 적용 + impl.md `결정` 기록
- 중단 → implement 단계 중단, plan 재진입

### 계획 재진입 절차

```
1. impl.md `상태: 보류` + 사유 기록
2. plan.md 메타 `상태: re-planning`
3. 사용자 알림 ("implement 중 X 발견. plan 재토론 필요")
4. plan 재진입 → 변경된 부분만 재계획 → 새 체크포인트
5. implement 재개 (보류된 R만 재구현)
```
