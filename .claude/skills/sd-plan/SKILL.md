# plan 단계

spec.md + 기존 코드베이스 → 현황 매핑 + 변경 계획 (R별 변경 위치/방식/테스트 + R 간 작업 순서).

## 산출물

```
.specs/{yyMMddHHmmss}/REQ-XXX-슬러그/
  spec.md         ← 입력 (이미 존재)
  plan.md         ← 본 단계 산출물
```

## 워크플로

1. 입력: 대상 REQ ID

2. 읽기: spec.md + 코드베이스 + raw input(있으면)

3. 초안 plan.md 작성 (템플릿: [references/plan-md-template.md](references/plan-md-template.md))
   - **R별 현황 매핑** (4단계: 구현/부분/미구현/차이있음)
   - **R별 변경 위치** (파일 경로 + 함수/컴포넌트 이름. 라인 번호 X)
   - **R별 변경 방식** (자연어. 복잡한 로직만 의사코드)
   - **R별 테스트** (방식: TDD/사후/생략 + 케이스)
   - **작업 순서** (R 간 의존성, 권장 순서, 병렬 가능 여부)
   - **통합/E2E 테스트** (R 간 흐름)
   - **결과** 메타 필드 (`proceed` | `skip-to-verify`)
   - 100% 확신 못 하는 부분 → Q

4. Q 다이얼로그 (한 번에 하나씩) → 사용자 답변 → 즉시 plan.md 갱신

5. spec 모순 발견 시 (plan 안에서 처리)
   - Q로 알림 → 사용자 답변 받아 spec.md 수정 + spec.md 메타 `이력` 기록
   - 변경된 R 부분만 재계획. plan 단계 종료 X.

6. Q 0개 → **산출물 소비자 친화적 보고** + 사용자 승인 → 체크포인트
   - 보고는 산출물 소비자가 그대로 읽어도 의도가 전달되는 수준 자연어
   - REQ 차원 "어디를 어떻게 바꿀지" 요약 (R별 변경 위치/방식 핵심)
   - 작업 순서 / 결과 명시
   - 기술 용어 최소화 (단, 파일·함수명 같은 위치 식별자는 필요)
   - 사용자 OK → 메타 `상태: planned`, `최근 체크포인트` 기록

## 현황 분류 (4단계)

| 분류 | 의미 |
|---|---|
| **구현** | spec R 의도가 코드에 이미 반영됨 |
| **부분** | R 일부만 구현됨 (예: UI는 있으나 로직 없음) |
| **미구현** | 관련 코드 없음 |
| **차이있음** | 구현되어 있으나 R 의도와 불일치 |

## 변경 계획 입도

- **변경 위치**: 파일 경로 + 함수/컴포넌트 이름 (라인 번호 X — 코드 변경에 취약)
- **변경 방식**: 자연어. 복잡한 로직(상태 머신, 알고리즘)만 의사코드. 완전한 코드 스니펫 X (implement 단계 의미 무력화)

## 테스트 모드 선택

**우선순위: TDD > 사후 테스트 > 생략**. 위에서부터 적용 가능 여부를 따져 가능한 **가장 높은** 모드를 고른다. 낮은 모드로 내려갈수록 테스트가 실제로 작성되지 않을 위험이 커지므로, 안일하게 떨어뜨리지 않는다.

| 모드 | 적용 조건 | 일반적인 R 성격 |
|---|---|---|
| **TDD** | 입력 → 출력을 코드로 단언 가능 | 비즈니스 로직, 알고리즘, 데이터 변환, 순수 함수, mock 가능한 외부 연동 |
| **사후 테스트** | TDD 불가하지만 동작 후 상태/응답을 코드로 단언 가능 | UI 동작, 실제 외부 API 응답, DB 변경 결과 |
| **생략** | 위 둘 다 불가하거나 검증 비용 대비 가치 낮음 | 일회성 스크립트, 단순 마이그레이션 |

판단 모호 → Q. 특히 "TDD로 끌어올릴 여지가 있나?"를 먼저 검토.

## 결과

| 결과 | 의미 | 다음 동작 |
|---|---|---|
| `proceed` | 변경할 R 있음 | implement 진행 |
| `skip-to-verify` | 모든 R 이미 구현됨 | verify 직행 |

(`back-to-spec` 분기는 없음. spec 모순은 plan 안에서 처리 후 계속.)

## 핵심 원칙

- self-contained 블록 (R 블록 안에 현황/변경/테스트 인라인)
- raw input 불변
- ID 불변
- 자동 판단 금지 (현황/모드 판단 모호 시 Q)
- 한 번에 하나씩 Q

## 안티패턴

- ❌ 라인 번호로 변경 위치 표기
- ❌ 변경 방식에 완전한 코드 스니펫
- ❌ 100% 확신 못 하는 추정을 Q 없이 단정
- ❌ R 단위 정보를 별도 섹션으로 분리 (self-contained 블록 깨짐)
- ❌ 작업 순서를 R 안에 적기 (R 간 관계는 별도 섹션)
- ❌ spec.md 자동 수정 (사용자 검토 필수)
- ❌ 체크포인트 없이 종료
