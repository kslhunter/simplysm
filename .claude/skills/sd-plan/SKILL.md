# plan 단계

대상 spec.md 및 관련 자료를 읽고 → 현황 매핑 + 변경 계획 (R별 변경 위치/방식/테스트 + R 간 작업 순서).

## 산출물

```
.specs/{yyMMddHHmmss}/REQ-XXX-슬러그/
  spec.md         ← 입력 (이미 존재)
  plan.md         ← 본 단계 산출물
```

## 워크플로

1. 입력: 대상 REQ ID

2. 읽기: 대상 spec.md + overview.md + raw input(있으면) + 관련 타 spec.md 및 plan.md + 기존 코드베이스
   - 특히 "spec.md, overview.md, raw input(있으면), 관련 타 spec.md 및 plan.md"는 반드시 통독할것

3. 초안 plan.md 작성 (템플릿: [references/plan-md-template.md](references/plan-md-template.md))
   - **R별 현황 매핑** (4단계: 구현/부분/미구현/차이있음)
   - **R별 설계** (R 성격별 조건부 — 아래 "R 성격별 설계 정보" 참조)
   - **R별 변경 위치** (파일 경로 + 함수/컴포넌트 이름. 라인 번호 X)
   - **R별 변경 방식** (자연어. 복잡한 로직만 의사코드)
   - **R별 테스트** (방식: TDD/사후/생략 + 케이스)
   - **작업 순서** (R 간 의존성, 권장 순서, 병렬 가능 여부)
   - **통합/E2E 테스트** (R 간 흐름)
   - **결과** 메타 필드 (`proceed` | `skip-to-verify`)
   - 100% 확신 못 하는 부분 → Q

4. Q 다이얼로그 (한 번에 하나씩) → 사용자 답변 → 즉시 plan.md 갱신
   - **spec 모순 발견 시**: Q로 알림 → 사용자 답변 받아 spec.md 수정 + spec.md 메타 `이력` 기록 → 변경된 R 부분만 재계획. plan 단계 종료 X.

5. Q 0개 도달 → **plan.md 전체 재검토** (R별 현황/변경 위치/변경 방식 정합성 / 누락된 결정거리 / 작업 순서 / 테스트 모드 / 모호 표현 / 미해결 의존) → 신규 Q 발견 시 Q 다이얼로그 재진입 → 재검토 후에도 Q 0개 → **역방향 문서(overview, spec, demo) 검토** → 신규 모순/수정 발견 시 Q 다이얼로그 재진입 → 정합성 OK → **산출물 소비자 친화적 보고** → 메타 `상태: planned` 전환
   - 보고: 산출물 소비자가 그대로 읽어도 의도가 전달되는 수준 자연어. REQ 차원 "어디를 어떻게 바꿀지" 요약 (R별 변경 위치/방식 핵심) + 작업 순서 + 결과. 기술 용어 최소화 (단, 파일·함수명 같은 위치 식별자는 필요). 안내 텍스트라 별도 사용자 승인 게이트 X.

## 현황 분류 (4단계)

| 분류 | 의미 |
|---|---|
| **구현** | spec R 의도가 코드에 이미 반영됨 |
| **부분** | R 일부만 구현됨 (예: UI는 있으나 로직 없음) |
| **미구현** | 관련 코드 없음 |
| **차이있음** | 구현되어 있으나 R 의도와 불일치 |

## 변경 계획 입도

- **변경 위치**: 파일 경로 + 함수/컴포넌트 이름 (라인 번호 X — 코드 변경에 취약)
- **변경 방식**: 자연어. 복잡한 로직(상태 머신, 알고리즘)만 의사코드. 완전한 코드 스니펫 X (implement 단계 의미 무력화)

## R 성격별 설계 정보

R의 성격에 따라 "변경 위치/방식"만으로는 산출물 소비자가 그림을 그릴 수 없는 경우가 있다. 아래 표에 해당하는 R은 **설계** 서브섹션을 추가한다. 단순 변경(예: 색상/문구/상수 값)은 생략한다.

| R 성격 | 설계 서브섹션 내용 |
|---|---|
| **UI** | 레이아웃(좌우 분할/배치/주요 영역), 사용자 이벤트 흐름(클릭→모달→저장 같은 시퀀스), 상태 변화 |
| **API** | 엔드포인트(메서드+경로), 요청/응답 스키마, 에러 케이스, 인증/권한 |
| **데이터 모델** | 스키마 변경(테이블/컬럼/제약), 마이그레이션 전략, 기존 데이터 처리 |
| **외부 연동** | 호출 시퀀스, 실패/재시도/타임아웃 정책, 멱등성 |
| **단순 변경** | (생략) |

표현은 **자연어 우선**. 그림이 꼭 필요하면 짧은 ASCII 박스 허용하되 강제는 아님. 예: "좌측 목록 / 우측 상세 폼, 우상단 + 버튼 → 신규 등록 모달".

**demo 산출물이 있는 UI R**: 레이아웃/이벤트 흐름은 demo.md를 정본으로 삼고, plan에서는 "demo.md 참조" + plan에서 추가로 결정해야 할 부분만 짧게 적는다 (중복 작성 X).

## 테스트 모드 선택

**우선순위: TDD > 사후 테스트 > 생략**. 위에서부터 적용 가능 여부를 따져 가능한 **가장 높은** 모드를 고른다. 낮은 모드로 내려갈수록 테스트가 실제로 작성되지 않을 위험이 커지므로, 안일하게 떨어뜨리지 않는다.

| 모드 | 적용 조건 | 일반적인 R 성격 |
|---|---|---|
| **TDD** | 입력 → 출력을 코드로 단언 가능 | 비즈니스 로직, 알고리즘, 데이터 변환, 순수 함수, mock 가능한 외부 연동 |
| **사후 테스트** | TDD 불가하지만 동작 후 상태/응답을 코드로 단언 가능 | UI 동작, 실제 외부 API 응답, DB 변경 결과 |
| **생략** | 위 둘 다 불가하거나 검증 비용 대비 가치 낮음 | 일회성 스크립트, 단순 마이그레이션 |

판단 모호 → Q. 특히 "TDD로 끌어올릴 여지가 있나?"를 먼저 검토.

## 결과

| 결과 | 의미 | 다음 동작 |
|---|---|---|
| `proceed` | 변경할 R 있음 | implement 진행 |
| `skip-to-verify` | 모든 R 이미 구현됨 | verify 직행 |

(`back-to-spec` 분기는 없음. spec 모순은 plan 안에서 처리 후 계속.)

## 핵심 원칙

- self-contained 블록 (R 블록 안에 현황/변경/테스트 인라인)
- raw input 불변
- ID 불변
- 자동 판단 금지 (현황/모드 판단 모호 시 Q)
- 한 번에 하나씩 Q

## 안티패턴

- ❌ 라인 번호로 변경 위치 표기
- ❌ 변경 방식에 완전한 코드 스니펫
- ❌ 100% 확신 못 하는 추정을 Q 없이 단정
- ❌ R 단위 정보를 별도 섹션으로 분리 (self-contained 블록 깨짐)
- ❌ 작업 순서를 R 안에 적기 (R 간 관계는 별도 섹션)
- ❌ 마지막 Q 답변 직후 plan.md 전체 재검토 없이 planned 전환
- ❌ 역방향 검토 없이 planned 전환
- ❌ 단순 변경 R(색상/문구/상수)에 설계 서브섹션 추가
- ❌ demo.md가 있는 UI R인데 plan에 레이아웃/이벤트 흐름 중복 작성
- ❌ UI/API/데이터 모델/외부 연동 R인데 설계 서브섹션 누락
