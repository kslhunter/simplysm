# sd-plan: Task 구현계획

WBS Task 한 개를 대상으로, Story별 비즈니스 규칙과 코드베이스 기반 구현 설계를 확정한다.

개발 프로세스: WBS 문서 작성 → **Task 문서 작성** → TDD 개발

| 스킬    | 책임                      |
| ------- | ------------------------- |
| sd-wbs  | 사용자 동작 단위 분해     |
| sd-plan | 비즈니스 규칙 + 구현 설계 |
| sd-tdd  | 구현                      |

## Step 1: 입력 확인 및 Task 인벤토리

`wbs 문서 경로 + Task 번호`가 입력되지 않으면 `/sd-wbs`를 안내하고 종료한다.

## Step 2: Story 명세 (Gherkin)

각 Story마다 Gherkin Feature 블록으로 Rule과 Scenario를 작성하고, 미확정 사항은 Question 블록으로 분류한다.

### Rule/Scenario 도출

- **Rule**: WBS Story 근거를 출발점으로 도출한 세부 비즈니스 규칙·정책·검증 조건
- **Scenario**: Rule 내 입력 → 결과 (긍정/부정/경계)

모든 항목은 `sd-clarify` 지침에 따라 명확화한다.

| 기법                          | 적용 시점           | 방법                                              |
| ----------------------------- | ------------------- | ------------------------------------------------- |
| **Decision Table**            | 조건 조합이 있을 때 | 조건 조합 나열 → 빈 칸을 명확화                   |
| **Boundary Value Analysis**   | 숫자/범위가 있을 때 | 경계값 강제 → 미정의 경계를 명확화                |
| **Equivalence Partitioning**  | 입력 분류가 있을 때 | 입력 분류 나열 → 미정의 분류를 명확화             |
| **State Transition**          | 상태가 있는 Story   | 상태 x 이벤트 나열 → 미정의 전이를 명확화         |
| **Perspective-Based Reading** | 최종 검토 시        | 테스터/개발자/사용자 관점 검토 → 빠진 것을 명확화 |

Rule과 Scenario는 반드시 확정 근거를 가져야 한다. 근거가 없으면 반드시 `sd-clarify` 지침에 따라 명확화 해야한다.

### 결과 형식

Story별 Gherkin Feature 블록, `# 근거: ...` 주석. 키워드는 영문, 본문은 사용자 언어:

````markdown
### Story {번호} {이름}

```gherkin
Feature: Story {번호} {이름}
  Background:
    Given {Story 공통 전제}

  Rule: {규칙 제목}
    # 근거: WBS Story 근거 / 답변 #Q?
    Scenario: {긍정 케이스}
      Given ...
      When ...
      Then ...
    Scenario: {경계 케이스}
      ...
```
````

**나쁜 예:** "예약 기능 포함이 결정됨 → 예약 세부규칙(대기열 정책, 미대출 시 자동취소 기간)도 확정" — 기능 포함 여부와 세부 수치/규칙은 별개다. 세부사항은 별도로 분류·질문한다.

## Step 3: 코드베이스 탐색

**CRITICAL: 구현 패턴은 코드가 source of truth이다.** 이 단계 완료 전 Step 4로 진행하지 않는다.

여러 방식이 혼재되어 있거나 유사 패턴이 존재하지 않아 결정할 수 없다면 `sd-clarify` 지침에 따라 패턴을 명확화 한다.

### 3-1. 유사 기능 탐색

코드베이스에서 이 Task와 가장 유사한 기존 기능(동일 도메인·CRUD 패턴·UI 흐름 공유)을 찾는다.

탐색 대상:

- 관련 엔티티/모델 구조
- 기존 API 엔드포인트 및 패턴
- UI 컴포넌트 구조, **레이아웃·생김새**(HTML 골격, CSS 클래스 네이밍, 컨트롤 배치, 스타일 토큰), 라우팅
- 기존 시스템 연동 방식
- 관련 테스트 구조
- 관련 의존성과 설정

### 3-2. 패턴 문서화

탐색 결과를 **코드베이스 분석** 섹션으로 정리한다.

```markdown
## 코드베이스 분석

### 유사 기능: {기능명}

- 엔티티: `path:line` — {구조 요약}
- API: `path:line` — {패턴 요약}
- UI: `path:line` — {구조 요약}
- 테스트: `path:line` — {패턴 요약}

### 프로젝트 컨벤션

- 네이밍 (파일·클래스·함수·변수): {관찰된 패턴} [근거: `path:line`]
- 디렉토리 구조 / 파일 배치: {관찰된 패턴} [근거: `path:line`]
- 에러 처리: {관찰된 패턴} [근거: `path:line`]
- 검증: {관찰된 패턴} [근거: `path:line`]
- 의존성 주입·import 패턴: {관찰된 패턴} [근거: `path:line`]
- 테스트 구조·헬퍼 사용: {관찰된 패턴} [근거: `path:line`]
- UI 구조·레이아웃·컴포넌트 생김새: {관찰된 패턴} [근거: `path:line`]
```

## Step 4: 구현 설계

코드베이스 분석(Step 3)의 패턴을 따른다.

모든 항목은 `sd-clarify` 지침에 따라 명확화한다.

각 항목에 `[근거: ...]` 태그로 출처를 명시한다. 코드 인용 시 `파일경로:라인번호`를 포함한다. 근거없이 설계항목 작성 금지.

- 근거 유형이 추론이나 추측일 수는 없다.

모든 사용자 결정사항은 `### 설계 결정` 표에 기록한다 (D1, D2, ... 순번 부여).

```markdown
## 구현 설계

### 영향 범위

- 신규: {파일 목록}
- 수정: {파일 목록}

### 엔티티 [근거: ...]

{시그니처 또는 코드}

### 서비스 / API [근거: ...]

{시그니처}

### UI [근거: ...]

{구조}

### 검증·에러·의존성·테스트 전략

### 대안 검토

(고려했으나 선택하지 않은 접근 방식과 그 이유. 기존 패턴과 다른 방식을 제안할 경우 필수)

### 설계 결정

| #   | 결정사항 | 선택 | 근거 유형 | 근거 |
| --- | -------- | ---- | --------- | ---- |
| D1  | ...      | ...  | ...       | ...  |
```

## Step 5: 구현 단위 분할 (Story → Slice)

각 Story를 1개 이상 **Slice**로 분할한다.

### Slice 정의

- **Slice**: 구현 규모 단위. Story 안에서 Scenarios의 묶음
- **번호 체계**: `{Story번호}.{문자}` (예: `1.1.1.A`, `1.1.1.B`)
- **체크박스 단위**: Slice (가장 세부 진행 단위)

### Slice마다 기록

- **영향 파일**: 신규/수정 대상 파일 경로 목록 (Slice 단위)
- **구현 범위**: 메서드·컴포넌트 등 작업 대상
- **Scenarios**: 매핑된 Gherkin Scenario 이름

Slice 등장 순서가 곧 수행 순서이다. 영향 파일이 겹치는 Slice는 인접 배치하여 직렬 진행한다.

### 분할 도구 우선순위

1. **USM의 자연스러운 단위** (정상 흐름 / 검증·에러 흐름 / 확장) — 우선
2. **SPIDR** (Spike, Path, Interface, Data, Rule) — 1번이 부족할 때

### 형식

```markdown
## 구현 단위 (Story → Slice)

### Story {번호} {이름}

#### [ ] Slice {Story번호}.A: {제목}

- **영향 파일:**
  - {신규/수정 파일 경로 목록}
- **구현 범위:**
  - {메서드/컴포넌트 단위 명시}
- **Scenarios:** {Scenario 이름 목록}

#### [ ] Slice {Story번호}.B: {제목}

- **영향 파일:** ...
- **구현 범위:** ...
- **Scenarios:** ...
```

## Step 6: Task 문서 생성

- **위치:** wbs 문서가 있는 디렉토리
- **파일명:** `{Task번호}-{Task이름 영문번역}.md` (kebab-case, 특수문자 제거)

```markdown
# Task {번호} {이름}

## 참조 자료

- WBS: @{wbs 상대경로}

## 코드베이스 분석

{Step 3 산출물}

## 구현 설계

{Step 4 산출물}

## 구현 단위 (Story → Slice)

{Step 5 산출물}
```

## Step 7: 격리 검증 (정보 유실·누락 점검)

**CRITICAL: 자체 판단으로 생략 금지(NEVER). 자체 요약 텍스트로 대체 금지(NEVER). 반드시 Agent tool 호출로 수행한다.**

문서 작성 후, 작성자 편향 제거와 정보 유실 차단을 위해 메인 세션과 분리된 Agent tool로 격리 검증을 수행한다.

### 검증 호출

Agent tool(effort: `low`)을 다음 입력으로 호출한다:

- **Task 문서 절대 경로** — Step 6에서 작성한 검증 대상
- **WBS 문서 절대 경로** — Step 1에서 받은 WBS
- **사용자 초기 요청 메시지 본문** — 프롬프트에 인라인 삽입

사용자 명확화 답변·결정사항은 Task 문서의 `### 설계 결정` 표와 `[근거: ...]` 태그에 반영되어 있으므로 별도 전달하지 않는다.

Agent tool에 부여할 제약: "보고만 수행. Task 문서를 수정하지 말 것."

### Agent tool 프롬프트에 포함할 검증 가이드

#### 검증 항목 (8가지 모두 수행)

1. **대화 정보 ↔ 문서 매핑** (정량 매핑 표 + 의역 변형 검출)
   - 사용자 초기 요청에 포함된 구체적 정보(수치·열거값·업무 규칙·제약·정책·예외·상태 전이·권한·기간·시간대·경계값·오류 동작·참조 경로)가 Task 문서의 `참조 자료`·`### 설계 결정`·`Rule`·`Scenario`·`구현 설계`·`구현 단위` 중 한 곳 이상에 반영되었는가?
   - **정량 매핑 표**: `원본 표현` / `출처(메시지 위치)` / `Task 문서 반영 위치` / `Task 문서 표현`. 반영 위치가 비어 있으면 누락 항목.
   - **의역 변형 검출**: 원문이 구체적인데 Task 문서가 추상화된 사례.

2. **WBS Task ↔ Task 문서 역추적성**
   WBS Task의 Stories·경계 항목 각각이 Task 문서의 `Story 명세`·`구현 단위`에 매핑되어 있는가?

3. **Story ↔ Scenario 매핑**
   모든 Story가 Gherkin `Scenario:` 1개 이상에 매핑되는가? 누락된 Story가 있으면 보고한다.

4. **Story ↔ Slice 매핑**
   모든 Story가 `구현 단위` 섹션에서 Slice 1개 이상에 속해 있는가? 누락된 Story가 있으면 보고한다.

5. **결정 유보 표현 검출**
   Task 문서 본문에 결정을 다음 단계로 미루는 의미의 표현이 잔존하는가? (예: "추후 결정", "TBD", "적절히 결정", "별도 확정", "구현 시 결정", "기본값으로 처리"). 시간 부사 "추후 X 발생", 측정값 "기본값 100" 같은 정상 사용은 제외. (예시·인용 본문 제외)

6. **근거 태그 누락**
   `Rule:`, `Scenario:`, `### 설계 결정` 행, `### 구현 설계` 항목 각각에 `[근거: ...]` 또는 등가 태그가 있는가? (Slice는 `Scenarios:` 줄의 Story Scenario 매핑이 근거를 대체한다.)

7. **참조 경로 실재 검증**
   문서에 인용된 `파일경로:라인번호`, `@path` 형태의 경로가 실제 파일 시스템에 존재하는가? (Read/Glob 도구로 확인하며, 라인번호는 파일 라인 수 이내인지만 확인한다.)

8. **Slice 체크박스 형식 검증**
   `구현 단위` 섹션의 모든 Slice 헤더가 `#### [ ] Slice {Story번호}.{문자}: {제목}` 형식으로 시작하는가? 체크박스(`[ ]`)가 누락된 Slice가 있으면 보고한다.

#### 완독 의무

사용자 초기 요청 메시지·WBS 문서·Task 문서는 끝까지 읽는다. 키워드 검색만으로 종결하지 않는다.

#### 출력 포맷

Agent tool은 다음 구조의 보고서를 작성한다.

- **요약 표** — 8개 항목 각각 PASS/FAIL
- **정량 매핑 표** (항목 1)
- **항목별 FAIL 상세**
  - 항목 1: 누락 / 의역 변형 의심 — `[출처] 원문: "..." → 권장 반영 위치: 섹션·라인`
  - 항목 2: WBS 미매핑 — `[WBS 위치] 항목: "..." → Task 문서 미반영`
  - 항목 3: Story 미매핑 — `Story X.Y.Z → Scenario 없음`
  - 항목 4: Story-Slice 미매핑 — `Story X.Y.Z → 어느 Slice에도 미포함`
  - 항목 5: 결정 유보 표현 잔존 — `Task 문서 라인 N: "..."`
  - 항목 6: 근거 태그 누락 — `Task 문서 라인 N: "..."`
  - 항목 7: 참조 경로 무효 — `Task 문서 라인 N: "경로:라인" → 실재 안 함`
  - 항목 8: Slice 체크박스 누락 — `Task 문서 라인 N: "..." → 체크박스 형식 위반`

### 메인의 결과 처리

1. 발견 항목은 `sd-clarify` 지침에 따라 명확화 한다.
2. Story 명세 재작성이 필요하면 Step 2, 구현 설계 재작성이 필요하면 Step 4, Slice 분할 재작성이 필요하면 Step 5로 되돌아간다.

**CRITICAL: 각 Slice는 새 세션에서 구현될 수 있으므로, 절대(NEVER) Task 문서에 누락이 있어서는 안된다.**

## Step 8: 역방향 피드백

plan 진행 중 새로 발견된 What 결정사항이 있으면 wbs.md에 보강한다. 반영 시 기존 체크박스 상태·번호·결정사항은 보존한다.

How 결정(API·DB·UI·테스트 분해 등)은 wbs에 기록하지 않고 plan의 `### 설계 결정`과 `## 구현 설계`에만 유지한다. 변경 사유를 명확히 작성하여 새 세션에서 결정사항을 잇도록 한다.

## Step 9: 다음 단계 안내

Task 설계 완료 후 개발을 위한 다음 단계를 안내한다.

예: `/sd-tdd {Task 문서 경로}`
