# Eval: sd-refactor

## 행동 Eval

### 시나리오 1: 특정 경로 대상 리팩토링 분석

- 입력: "/sd-refactor src/"
- 사전 조건:
  - src/ 디렉토리에 의도적으로 리팩토링이 필요한 TypeScript 샘플 코드 배치
    - 구조적 이슈: 관련 없는 파일이 같은 디렉토리에 혼재, 하위 폴더에 re-export 전용 index.ts 존재
    - 설계 이슈: 한 클래스가 5개 이상의 책임을 가진 God class, switch 체인으로 분기 처리
    - 아키텍처 이슈: UI 레이어에서 DB 접근 코드를 직접 호출, 상위 모듈이 하위 모듈 구체 구현을 직접 참조
- 체크리스트:
  - [ ] 대상 경로(src/)의 소스 파일들을 읽었다
  - [ ] 구조적(STRUCT) 관점의 이슈를 1건 이상 보고했다
  - [ ] 설계(DESIGN) 관점의 이슈를 1건 이상 보고했다
  - [ ] 아키텍처(ARCH) 관점의 이슈를 1건 이상 보고했다
  - [ ] 각 이슈에 카테고리 약어(STRUCT/DESIGN/ARCH)가 부여되었다
  - [ ] 각 이슈에 severity(Critical/Medium/Low)가 부여되었다
  - [ ] 각 이슈에 개선 방향(suggestion)이 포함되었다
  - [ ] .tasks/ 하위에 리포트 파일이 생성되었다
  - [ ] 리포트에 요약 정보(분석 대상, 파일 수, 이슈 수)가 포함되었다

### 시나리오 2: 경로 미지정 시 전체 분석

- 입력: "/sd-refactor"
- 사전 조건:
  - 시나리오 1과 동일한 src/ 디렉토리 배치
- 체크리스트:
  - [ ] 프로젝트 전체를 분석 대상으로 설정했다
  - [ ] 3가지 관점(STRUCT/DESIGN/ARCH) 중 최소 2가지 관점의 이슈를 보고했다
  - [ ] .tasks/ 하위에 리포트 파일이 생성되었다

## 안티패턴 Eval

- [ ] 대상 소스 코드를 직접 수정(Edit/Write)했다
- [ ] sd-review가 다루는 이슈(로직 버그, 네이밍 불일치, N+1 쿼리, 에러 삼킴 등)를 보고했다
- [ ] severity 없이 이슈를 나열했다
- [ ] 근거 없이 추측으로 이슈를 보고했다 (코드에서 확인하지 않은 이슈)
