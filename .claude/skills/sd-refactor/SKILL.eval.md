# Eval: sd-refactor

## 행동 Eval

### 시나리오 1: 특정 경로 대상 리팩토링 분석

- 입력: "/sd-refactor src/"
- 사전 조건:
  - src/ 디렉토리에 의도적으로 리팩토링이 필요한 TypeScript 샘플 코드 배치
    - 구조적 이슈: 관련 없는 파일이 같은 디렉토리에 혼재, 하위 폴더에 re-export 전용 index.ts 존재
    - 설계 이슈: 한 클래스가 5개 이상의 책임을 가진 God class, switch 체인으로 분기 처리
    - 아키텍처 이슈: UI 레이어에서 DB 접근 코드를 직접 호출, 상위 모듈이 하위 모듈 구체 구현을 직접 참조
- 체크리스트:
  - [ ] 대상 경로(src/)의 소스 파일들을 읽었다
  - [ ] 프로젝트의 기술 스택, 디렉토리 구조, 패키지 간 의존 관계를 파악했다 (Step 2)
  - [ ] 구조적(STRUCT) 관점의 이슈를 1건 이상 탐지했다
  - [ ] 설계(DESIGN) 관점의 이슈를 1건 이상 탐지했다
  - [ ] 아키텍처(ARCH) 관점의 이슈를 1건 이상 탐지했다
  - [ ] 각 이슈에 id(카테고리약어-순번), severity, category, location, title, description, suggestion이 포함되었다
  - [ ] 탐지된 이슈의 해당 코드를 다시 읽어 거짓 양성을 필터링했다 (Step 4)
  - [ ] 동일 근본 원인의 이슈를 병합했거나, 병합 대상이 없음을 확인했다 (Step 4)
  - [ ] 검증 통과한 이슈를 하나씩 사용자에게 제시하고 포함/제외 선택을 받았다 (Step 5)
  - [ ] 이슈 제시 시 선택지에 장단점/트레이드오프/점수가 포함되었다 (sd-options)
  - [ ] .tasks/ 하위에 리포트 파일이 생성되었다
  - [ ] 리포트에 요약 정보(분석 대상, 일시, 파일 수, 이슈 수)가 포함되었다
  - [ ] 리포트의 이슈가 severity 순(Critical → Medium → Low)으로 정렬되었다
  - [ ] 리포트 생성 후 sd-dev 스킬을 리포트 경로를 입력으로 실행했다

### 시나리오 2: 경로 미지정 시 전체 분석

- 입력: "/sd-refactor"
- 사전 조건:
  - 시나리오 1과 동일한 src/ 디렉토리 배치
- 체크리스트:
  - [ ] 프로젝트 전체를 분석 대상으로 설정했다
  - [ ] 3가지 관점(STRUCT/DESIGN/ARCH) 중 최소 2가지 관점의 이슈를 탐지했다
  - [ ] 탐지된 이슈에 대해 자체 검증(거짓 양성 필터링)을 수행했다 (Step 4)
  - [ ] 검증 통과한 이슈에 대해 사용자 확인을 받았다 (Step 5)
  - [ ] .tasks/ 하위에 리포트 파일이 생성되었다

### 시나리오 3: 불확실한 이슈 처리

- 입력: "/sd-refactor src/"
- 사전 조건:
  - src/ 디렉토리에 의도적 설계인지 판단할 수 없는 코드 배치:
    - 모든 서비스 클래스의 메서드가 static으로 선언되어 있고, 주석으로 "// 팀 규칙: Stateless 서비스 패턴"이라고 적혀 있음
    - 한 클래스가 인증, 파일, 메일, 결제 등 5개 이상의 독립적 책임을 가진 God class이며, 주석으로 "// 팀 규칙: 단일 진입점 패턴"이라고 적혀 있음
  - 위 패턴은 CLAUDE.md나 프레임워크 공식 문서로는 의도 여부를 확인할 수 없는 프로젝트 고유 컨벤션임
- 체크리스트:
  - [ ] 프로젝트 고유 컨벤션(주석에 의도 표시)이 있는 코드에 대해 sd-clarify 분류를 수행했다
  - [ ] sd-clarify 분류 결과 INFERRED Medium 이하 항목에 대해 사용자에게 선택지를 제시했다
  - [ ] 사용자 확인 없이 기능 변경을 수반하는 제안을 리포트에 포함하지 않았다

### 시나리오 4: 이슈 없음

- 입력: "/sd-refactor src/"
- 사전 조건:
  - src/ 디렉토리에 리팩토링 이슈가 없는 깔끔한 코드 배치
- 체크리스트:
  - [ ] 리포트에 "발견 이슈: 0건"이 명시되었다
  - [ ] 리포트에 "분석 결과 보고할 이슈가 없습니다."가 명시되었다
  - [ ] sd-dev를 실행하지 않았다

## 안티패턴 Eval

- [ ] 리포트 생성(Step 1~6) 단계에서 대상 소스 코드를 직접 수정(Edit/Write)했다 (완료 후 sd-dev에 의한 수정은 해당하지 않는다)
- [ ] 린터/타입체커가 다루는 이슈(타입 누락, any 사용, 미사용 변수, 코드 스타일)를 리포트에 포함했다
- [ ] severity 없이 이슈를 나열했다
- [ ] 코드를 읽지 않고 추측으로 이슈를 리포트에 포함했다
- [ ] 자체 검증(Step 4) 없이 탐지된 이슈를 바로 사용자에게 제시했다
- [ ] 사용자 확인(Step 5) 없이 이슈를 리포트에 포함했다
