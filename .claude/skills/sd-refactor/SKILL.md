# sd-refactor: 리팩토링 분석

sd-review가 "결함 탐지"(함수/모듈 수준)에 집중한다면, sd-refactor는 "구조 개선 방향 제안"(패키지/아키텍처 수준)에 집중한다. 코드를 직접 수정하지 않고 리포트만 생성한다.

## 공통 규칙

### sd-review와의 경계

다음은 sd-review 영역이므로 보고하지 않는다:

- 로직 버그, 비즈니스 로직 오류
- 네이밍 불일치, 파라미터 순서 불일치
- N+1 쿼리, 불필요한 직렬 await
- 에러 삼킴, 리소스 미해제
- 함수명과 동작의 괴리

### 보고 제외 규칙

- **린터/타입체커 영역**: 타입 누락, `any` 사용, 미사용 변수, 코드 스타일
- **거짓 양성**: 프레임워크가 요구하는 패턴, 프로젝트 컨벤션에 의한 의도적 구조
- **불확실한 영역**: 확신할 수 없는 이슈는 확정적으로 단정하지 않는다

이슈가 의도된 설계인지 불확실하면 `.claude/references/sd-clarify.md`를 읽고 명확화한다.

## Step 1: 대상 결정

인자로 경로가 지정되면 해당 경로, 미지정이면 프로젝트 전체를 분석한다.

- `/sd-refactor packages/angular` → `packages/angular` 하위만
- `/sd-refactor` → 프로젝트 루트 전체

## Step 2: 컨텍스트 수집

프로젝트의 기술 스택, 디렉토리 구조, 패키지 간 의존 관계를 파악한다.

## Step 3: 분석

대상 파일을 읽고, 3가지 관점으로 리팩토링 개선점을 탐지한다.

### 분석 절차

1. **전체 구조 파악** — 디렉토리 트리, 파일 배치, 모듈 경계를 조사
2. **의존성 추적** — import/export 관계, 패키지 간 의존 방향을 추적
3. **패턴 식별** — 반복되는 설계 패턴과 안티패턴을 식별
4. **개선 방향 도출** — 각 이슈에 대해 구체적인 개선 방향을 제시

### 체크리스트

#### 구조적 리팩토링 (STRUCT)

파일/모듈/디렉토리의 물리적 배치 개선:

- **기능 기반 재구조화**: 기술 계층(layer) 기준 배치가 기능(feature) 기준 배치보다 불리한 경우
- **Co-location 위반**: 밀접한 파일(컴포넌트, 테스트, 스타일)이 먼 디렉토리에 분산되어 있는 경우
- **모듈 경계 불명확**: public API가 정의되지 않아 내부 구현이 외부에 노출되는 경우
- **순환 의존성**: A→B→A 형태의 순환 참조가 존재하는 경우
- **불필요한 re-export**: 하위 폴더의 barrel index.ts가 순환 의존성 또는 불필요한 결합을 유발하는 경우
- **파일 비대화**: 단일 파일이 과도하게 많은 export를 포함하여 분할이 필요한 경우

#### 설계 리팩토링 (DESIGN)

클래스/인터페이스의 논리적 설계 개선:

- **God Class/Module**: 한 클래스/모듈이 5개 이상의 독립적 책임을 가진 경우
- **상속 남용**: 코드 재사용만을 위한 상속 — 구성(Composition)으로 전환 가능한 경우
- **조건 분기 과다**: switch/if-else 체인이 3개 이상의 타입을 분기 — 다형성 또는 Strategy 패턴으로 전환 가능한 경우
- **인터페이스 비대화**: 하나의 인터페이스가 소비자마다 다른 부분만 사용 — Interface Segregation이 필요한 경우
- **관용적 전환**: 언어/프레임워크의 구 패턴을 최신 관용구로 전환 가능한 경우 (예: callback→async/await, ngOnChanges→input signals)
- **중복 추상화**: 동일 개념에 대해 여러 추상화가 존재하여 통합이 필요한 경우

#### 아키텍처 리팩토링 (ARCH)

레이어/의존성의 거시적 구조 개선:

- **레이어 혼재**: UI 컴포넌트에 비즈니스 로직/데이터 접근 코드가 직접 포함된 경우
- **의존성 역전 위반**: 상위 모듈이 하위 모듈의 구체 구현을 직접 참조하는 경우 (추상에 의존해야 함)
- **경계 타입 부재**: 레이어 간 데이터 전달에 내부 구현 타입을 그대로 사용하여 결합도가 높은 경우
- **모듈 간 과결합**: 모듈 A의 변경이 무관한 모듈 B까지 파급되는 경우
- **공유 코드 산재**: 여러 모듈이 동일 로직을 각자 구현 — 공통 모듈 추출이 필요한 경우
- **단방향 의존성 위반**: 아키텍처에서 정의한 의존 방향을 거슬러 참조하는 경우

### Severity 기준

| Severity     | 기준                                             | 예시                                   |
| ------------ | ------------------------------------------------ | -------------------------------------- |
| **Critical** | 확장/변경 시 광범위한 파급, 아키텍처 의도 훼손   | 순환 의존성, 레이어 혼재, God Class    |
| **Medium**   | 유지보수 비용 증가, 특정 영역에서 불편함 유발     | 상속 남용, Co-location 위반, 과결합    |
| **Low**      | 개선하면 좋지만 당장 문제를 일으키지는 않음       | 관용적 전환, 불필요한 re-export        |

### 이슈 형식

```
id: {카테고리약어}-{순번} (예: STRUCT-001, DESIGN-002, ARCH-001)
severity: Critical | Medium | Low
category: 구조 | 설계 | 아키텍처
location: {파일경로}:{라인번호} 또는 {디렉토리경로}
title: {한 줄 요약}
description: {현재 구조의 문제점 — 왜 개선이 필요한지}
suggestion: {구체적 개선 방향}
```

## Step 4: 리포트 생성

분석 결과를 리포트 파일에 작성한다.

- **중복 제거**: 같은 위치의 같은 이슈를 합친다
- **severity 순 정렬**: Critical → Medium → Low
- **리포트 작성**: 요약 테이블(분석 대상, 일시, 파일 수, 이슈 수) + severity별 이슈 목록

### 산출물 경로

`.tasks/{timestamp}_refactor-{topic}/refactor.md`

- `{timestamp}`: `date +%y%m%d%H%M%S` 실행 결과
- `{topic}`: 영어 kebab-case

이슈가 없으면 "발견 이슈: 0건"과 "분석 결과 보고할 이슈가 없습니다."를 명시한다.

### 완료 후 출력

대화에 다음을 표시한다:

- `refactor.md` 파일 경로
- 수정이 필요하면 `/sd-dev`로 개발을 진행할 수 있다는 안내
