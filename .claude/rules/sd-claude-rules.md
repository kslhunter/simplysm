# 금지 명령어

- `git stash`, `git checkout`, `git restore`, `git reset`, `git clean` 사용 금지.
- `cd` 명령을 통한 타 폴더로의 이동 금지.
- `npx tsc` 사용 금지. 반드시 `pnpm typecheck [targets..]`등의 스크립트 사용
- `npx eslint` 사용 금지. 반드시 `pnpm lint [targets..]`등의 스크립트 사용
- `sed` 사용 금지. 너무 위험함.

# 대화 규칙

- 모든 요청에 대해 항상 깊이 생각 할 것.
- 사용자 발언은 의도의 단서이지 결과물 템플릿이 아니다. 문구를 그대로 옮겨 적지 말고, 무엇을 원하는지 파악한 뒤 작성 위치의 어조·맥락에 맞게 표현을 정돈하여 반영한다.
  - 예: `"~~를 하지말라는 내용을 써줘"` → `"~~를 하지말라"`를 그대로 박는 것이 아니라, 해당 문서/섹션의 기존 표현 방식에 맞춰 한 줄 룰로 다듬어 작성한다.
  - 사용자 발언을 그대로 받아쓰는 것은 의도 파악 실패로 간주한다.
- 내장 도구 적극 활용 (Read/Grep/Glob/Bash/WebFetch/WebSearch/Skill/TaskCreate 등)
- 사용자 요청의 의도가 불명확할 때는 `/sd-clarify` 스킬을 호출하여 명확화.
- 맥락에 맞는 용어 사용
  - 업무 기능·요구사항 논의 → 업무 용어 (사용자가 화면에서 뭘 하는지)
  - DB 스키마 설계 → 테이블·컬럼명
  - 코드 구현 → 함수·클래스명
- 한국 개발 현장 통용 용어 사용
- **CRITICAL**: 사용자가 명시하지 않은 사항 추측으로 행동 금지. 추측한것이 맞는지 `AskUserQuestion` tool로 물어볼 것.
  - 명시적 요청없이 다음 단계를 추측하여 바로 작업 하지 말것
  - 명시적 요청없이 코드/문서등을 바로 수정하지 말것
- 사용자가 직접 확인해야할 사항이 있으면, 계속 진행하지 말고 멈추고 사용자에게 직접 확인 결과를 요청할 것.

# 질문 vs 수정 분리

- 질문형 요청("이게 왜 이래?", "어떻게 동작해?", "맞아?")은 분석·설명으로 처리한다. 사용자가 명시적으로 "수정해줘", "고쳐줘", "바꿔줘"라고 요청하지 않으면 코드/문서 수정으로 전환하지 않는다.
- "A를 B로 바꿔" 같은 명시적 변경 지시가 있을 때만 즉시 수정한다.
- 해결 방식이 열린 요청(예: "이거 어떻게 해결하지?", "리팩토링 방안 좀")은 수정 대상·방향·검증 계획을 먼저 설명하고 사용자 승인을 받은 뒤 수정한다.

# 사용자 질문 시점

**CRITICAL: `/sd-clarify` 호출이나 `sd-options` 적용이 정의된 스킬에서는 정의된 경로로만 사용자에게 질문한다.**

- 정의된 경로 1: 스킬에 명시된 시점(예: "Step N 종료 시점에 `/sd-clarify`")에 `/sd-clarify` 호출
- 정의된 경로 2: `sd-options.md` 형식으로 결정 묶음 제시 후 `AskUserQuestion` 호출
- 그 외 시점·경로의 `AskUserQuestion` 직접 호출 금지. 의문은 명확화 시점까지 누적하여 정의된 경로로 일괄 처리.

# 사용자 편의성 우선

**CRITICAL: 구현 복잡도·코드 양·리팩토링 부담보다 사용자 편의성을 우선한다.**

- 구현 복잡도와 사용자 편의성이 충돌하면 편의성을 택한다.
- 복잡도가 크게 증가해도 편의성 이득이 분명하면 채택한다.
- '구현이 어렵다'는 이유로 편의성 다운그레이드 금지.
- 선택지 평가 시 '사용자 편의성' 축을 반드시 포함하고 가중치를 둔다.

# 사용성 보존

**CRITICAL: 버그 수정·규칙 준수·타입/lint 오류 해결 작업은 사용성 변경 요청이 아니다.**

- 사용자 흐름, 화면 동작, 문구, 기본값, 옵션 의미, 공개 API 동작은 보존한다.
- 작업 중 사용성 문제를 발견해도 같이 고치지 말고, 별도 이슈로 보고만 한다.
- 사용성 변경이 불가피하면 변경되는 사용성, 대안, 영향을 사전 설명하고 사용자 응답을 대기한다.

# 구현 방식 결정 분리

- 사용자가 목표·방향·통합 여부를 확정해도 구현 방식은 별도 결정사항이다.
- 구현 방식 후보가 2개 이상이거나 새 개념(내부 모드/플래그/래퍼/호환 계층/파일 삭제·이동/호출 흐름 변경) 도입이 필요하면 `.claude/rules/sd-options.md`의 형식으로 선택지를 제시하고 응답을 대기한다.
- 회피용 우회 구조(재귀, 순환 의존, 호환성 문제 등)가 발견되면 먼저 사용자에게 보고하고, 그 다음 sd-options 형식으로 질문한다.

# Git

- 사용자가 git 사용을 명시하지 않으면 git repository가 아닌 프로젝트처럼 취급한다.
- 명시적 요청 없이 git 명령(`status`/`log`/`diff`/`commit`/`push`/`branch` 등) 실행 금지.
- 커밋·PR·브랜치 작업은 명시적 요청이 있을 때만 수행한다.

# Playwright

- 사용자가 접속주소를 알려주지 않았다면, 반드시 사용자에게 접속주소를 요청할것. (서버 강제 실행 금지)
- /playwright-cli 스킬을 사용할 것

# 코딩 룰

- 프론트엔드: `.claude/references/sd-frontend-design.md`
- barrel export 금지: `src/` 루트의 `index.ts`외, 하위 폴더 re-export `index.ts` 금지
- 다른 패키지에 대한 re-export 금지
- 정적 import가 불가능한 경우를 제외하고 `import()` 사용 금지
- 구조화된 문법 처리 시 파서 사용 필수. 정규식·문자열 치환으로 우회 금지
- null/undefined 비교 규칙: 일반 값 비교는 `===`/`!==`, null/undefined 검사는 `== null`/`!= null`을 사용.
- 내부 모듈 import 시 `.js` 확장자를 붙이지 않는다. (번들러가 확장자 해석)
- 타입 추론을 해제하는 방식의 수정 금지
- 불필요한 `as` 캐스팅 금지
- 과도한 추상화 금지: 추상화는 실제 중복 3회 이상일 때만 도입. "미래 대비"·"확장성"·"유연성" 사유 금지.
  - 단일 호출처 헬퍼/wrapper 금지 (인라인)
  - 단순 위임만 하는 메서드·함수·클래스 금지
  - 1회용 generic·옵션·extension point 금지

# 룰·스킬·프롬프트 .md 파일 작성

- 작성 위치(파일·섹션)의 용도가 추가/수정 내용과 맞는지 먼저 확인한다. 어긋나면 위치를 바꾼다.
- 작성 위치의 표현 방식을 기존 항목에서 먼저 파악한 뒤 같은 방식으로 작성한다.
  파악할 항목: 어조(명령형/서술형/조건형), 문장 길이, 관점(2인칭/3인칭/주어 생략), 용어 체계, 들여쓰기·불릿 패턴.
- 다른 파일·다른 섹션의 표현 방식을 그대로 옮겨오지 않는다.
- 최대한 간결하게 작성한다. 한 룰은 한 줄. 부연은 하위 불릿으로 분리.

# 응답 전 자기검토

**CRITICAL: 응답 송출 직전 다음 항목을 점검한다. 하나라도 실패하면 재작성 후 송출한다.**

- 사용자가 무엇을 결정·답변·실행해야 하는지 응답 첫 단락에 한 줄로 명시되어 있는가?
- 등장하는 용어·약어·개념이 이 프로젝트(simplysm) 또는 일반 한국 개발 현장에서 통용되는가? 비통용 용어는 첫 등장 시 한 줄 정의 또는 코드/파일 인용으로 대체.
- "이것·저것·그·해당" 지시어가 가리키는 대상이 같은 응답 내에 명시되어 있는가?
- 사용자가 응답만 보고 추가 검색·파일 열람 없이 답변·행동할 수 있는가?
- 추상명사·형용사("적절한·효율적인·합리적인·유연한")로만 구성된 문장이 있는가? 있으면 구체 코드·파일경로·명령으로 교체.
- 선택지를 제시하는 응답이 `sd-options.md` 형식을 따르는가?

## 주의사항

- 세션내 작업 수행중 사용자가 특정 부분 코드를 수정했을 수 있음. 임의로 롤백하지 말것
  - 알고있던 정보와 상이한 코드 정보가 있다면, 사용자에게 보고후 확인을 받을 것.
