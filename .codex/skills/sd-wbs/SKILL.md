# sd-wbs: 프로젝트 분해 (WBS)

WBS는 고객 중심으로 **무엇을 만들어야 하는지(What)** 를 확정하는 산출물이다.
Feature 범위에는 이후 `$sd-dev`가 바로 시작되어도 해석이 갈리지 않는 고객 동작과 업무 규칙만 남긴다.

## Step 1: 요구사항 수집

사용자가 제공한 요구사항에 대한 분석을 시작한다.
문서 파일(docx, xlsx, pdf 등)이 제공된 경우, `$sd-doc-extract`로 내용을 추출하여 분석한다.
기존 wbs 경로를 제공하고 수정하기를 원하는 경우, 해당 문서를 읽고 업데이트한다.
마이그레이션 등 기존 시스템이 요구사항 원천인 경우, 기존 코드베이스를 참조하여 기능을 파악한다.
요구사항과 함께 **프로젝트 개요**(배경, 환경, 전제조건, 기술적 제약)를 파악한다.
`$sd-inner-clarify` 스킬을 호출하여 명확화한다.

## Step 2: Impact Mapping

Impact Mapping 트리(Goal → Actor → Impact → Deliverable)를 구축한다.

### What/How 경계

비즈니스 요구사항(What)에 대한 분석만 한다.

- 기술적 구현 방법(How) — 인증 방식, 통신 프로토콜, 프레임워크, 아키텍처 패턴 등 — 에 대한 결정은 분석 단계에서 하지 않는다.
- `$sd-inner-clarify` 스킬을 호출하여 명확화한다.

### 명확화 항목

| 질문                       | 도출 요소          |
|--------------------------|----------------|
| Q1. "왜 만드나?" 반복          | Goal (측정 가능하게) |
| Q2. "누가 쓰나? 누가 영향받나?"    | Actor          |
| Q3. "그 사람 행동이 어떻게 바뀌어야?" | Impact (행동 변화) |
| Q4. "가장 단순하게 뭘 만들면?"     | Deliverable    |
| Q5. "뭘 빼나?"              | 제외 사항          |

**나쁜예:**

- `인증 방식을 SSO로 할지 자체 인증으로 할지?` → 질문 불필요. Feature 범위에는 "사용자 인증"만 기술
- `어떤 DB를 사용할지?` → 질문 불필요. 분석 단계의 범위가 아님

### Impact Mapping 규칙

- 모든 Feature가 Goal까지 역추적 가능해야 한다 — Goal에 연결되지 않는 기능은 제외 사항으로 보낸다
- Goal은 구체적 목적을 명확히 기술한다. "효율화한다"(X) → "대출·반납 기록을 시스템으로 관리하여 분실을 방지한다"(O). 수치 기반이 가능하면 좋지만 필수 아님.
- Impact는 기능이 아닌 **행동 변화**를 기술한다. "대시보드를 본다"(X) → "업무 상태를 빠르게 파악한다"(O)

## Step 3: Feature Breakdown

Deliverable을 Epic → Feature로 구조화한다.

### Epic 분류 기준

Epic은 **사용자 관점의 기능 영역**(비즈니스 기능) 단위로 그룹화한다.
기술 계층(서버/클라이언트), 패키지, 아키텍처 레이어별로 분류하지 않는다(NEVER).

**좋은 예:**

- "인증" Epic → Feature 1: 사용자 로그인, Feature 2: 비밀번호 재설정
- "알림" Epic → Feature 1: 토스트 알림, Feature 2: 이메일 알림

**나쁜 예:**

- "서버" Epic → 로깅 서비스, 인증 서비스, ... / "클라이언트" Epic → 로깅 호출, 로그인 화면, ...
- "core-node 패키지" Epic → ... / "angular 패키지" Epic → ...

### Feature 분해 원칙

Feature는 독립적으로 설계·개발·검증할 수 있는 최소 **기능** 단위이다.

**CRITICAL: Feature를 아키텍처 레이어(DB/서비스/UI, 서버/클라이언트, 프론트엔드/백엔드, 패키지 등)로 분할하는 것은 절대 금지(NEVER).**
하나의 Feature는 해당 기능을 완성하기 위한 모든 레이어(DB 스키마, API, UI 화면 등)의 산출물을 end-to-end로 포함한다.

- **좋은 예:** "사용자 로그인" Feature → DB users 테이블 + 토큰 발급 API + 로그인 화면을 모두 한 Feature에 포함
- **나쁜 예:** Feature 1 "users 테이블 스키마" / Feature 2 "로그인 API" / Feature 3 "로그인 화면" — 레이어 분할 금지
- **나쁜 예:** Feature 1 "인증 토큰 발급(서버)" / Feature 2 "로그인 화면(클라이언트)" — 서버/클라이언트 분할 금지
- **나쁜 예:** Feature 1 "도서 관리(관리자)" / Feature 2 "도서 조회(직원)" — 동일 도메인("도서")을 Actor(역할)로 분할 금지. "도서 관리" 단일 Feature에 관리자 화면 + 직원 화면을 함께 포함

### Feature 분리 규칙

하나의 Feature가 과도하게 클 때, **기능 범위 기반으로** 분리한다. 분리된 각 Feature는 여전히 end-to-end 수직 슬라이스(DB→서비스→UI)를 유지해야 한다.

**분리 판단 기준** — 아래 중 하나라도 해당하면 분리를 검토한다:

- 범위 항목이 대략 7개를 초과하는 경우
- 기본 동작과 확장 동작이 자연스럽게 구분되는 경우 (예: CRUD vs 통계/추천/일괄처리)
- 독립적으로 구현·검증 가능한 하위 단위로 나뉘는 경우

**분리 방법 — 기본→확장 패턴:**

하나의 기능을 **기본 기능**(핵심 동작)과 **확장 기능**(부가 동작)으로 나눈다.

- 네이밍: `{기능명} — {범위 설명}` (예: "도서 관리 — 기본 CRUD", "도서 관리 — 추천/통계")
- 확장 Feature는 기본 Feature에 대한 의존성을 명시한다
- 기본 Feature만으로 해당 기능의 핵심 동작이 완성되어야 한다

**좋은 예:**

- Feature 1.1: 사용자 관리 — 기본 CRUD (등록, 수정, 삭제, 목록/검색)
- Feature 1.2: 사용자 관리 — 권한/역할 관리 (← 1.1에 의존)

**나쁜 예 (레이어 분리 — 금지):**

- Feature 1.1: 사용자 관리 — DB 스키마
- Feature 1.2: 사용자 관리 — API
- Feature 1.3: 사용자 관리 — UI

### Feature 병합 규칙

**CRITICAL: 기계적 판정 규칙 (예외 없음, 재량 금지)**

아래 중 **하나라도** 해당하면 무조건(MUST) 해당 Feature들을 단일 Feature로 병합한다.

1. **Feature 이름에 Actor(역할)가 괄호/접미사로 포함된 경우** (예: "(관리자)", "(직원)", "(고객)", "관리자용", "직원용")
2. **동일 도메인 엔터티에 대해 아키텍처 레이어별로 Feature를 분할한 경우** (예: "도서 DB 스키마", "도서 API", "도서 UI")
3. **두 Feature의 범위에 동일하거나 유사한 기능명이 각각 등장하는 경우** (예: "도서 목록 조회", "주문 목록 조회") — 뷰/필터/권한 차이는 병합 사유를 면제하지 않는다

그 외 규칙:

- 같은 세부기능을 공유한다는 이유로 독립 모듈을 하나의 Feature로 묶지 않는다. (예: event-bus Feature + 모달 Feature + 토스트 Feature — 묶지 않음)
- 범주는 Epic, 개별 기능이 Feature (예: "알림" Epic → 토스트 알림, 모달 알림, 이메일 알림 각각이 Feature)
- 가능한한 의존성 순서로 정렬
- **테스트 작성을 별도 Feature로 분리하지 않는다(NEVER).** 각 Feature는 `sd-tdd`로 구현될 때 테스트와 프로덕션 코드를 함께 작성한다.

### Feature 작성 규칙

각 Feature에는 다음 4가지를 반드시 포함한다.

- **범위**: 해당 Feature의 세부 기능을 사용자 기능(user-facing function) 수준으로 **MUST 빠짐없이** 나열한다. (절대 누락되어선 안된다. 누락된것은 다음단계에서 제외사항으로 판단될 수 있다.)
- **경계**: 이 Feature가 **하지 않는 것** 중 다른 Feature에서 다루거나 다룰 수 있는 것을 명시한다. 인접 Feature와의 경계가 모호한 경우 특히 중요하다. (프로젝트 전체에서 제외되는 항목은 문서 하단의 "제외 사항"에 기재한다.)
- **근거**: 범위가 도출된 근거 혹은 출처를 명시한다. (요구사항, 사용자 답변, 첨부문서 등) 개발에 필요한 참조 파일/자료 경로가 있으면 확인 목적과 함께 기록한다.
- **의존성**: 다른 Feature와의 의존 관계를 기록한다. 형식: Feature 번호만 쉼표로 나열 (예: `1.1, 2.3`) 또는 `없음`. 의존성에 따라 병렬 진행할 수 있으므로 정확한 판단이 **CRITICAL**.

### 미확정 요구 처리 규칙

**CRITICAL: Feature 범위에는 구현자가 바로 `$sd-dev`로 들어가도 해석이 갈리지 않는 확정된 고객 동작과 업무 규칙만 남긴다.**

- WBS Feature 안에는 "후속 확정", "보류", "추후 결정", "협의 필요" 같은 미확정 usecase를 넣지 않는다.
- 원문에 미확정이라고 적힌 고객 요구, 업무 규칙, 정책, 예외 흐름은 WBS 작성 시점에 `$sd-inner-clarify`로 질문하여 확정한다.
- 확정하지 못한 요구는 Feature로 만들지 않고, 문서 하단 "제외 사항"에 `이번 WBS 범위 제외: 미확정` 사유로 기록한다.
- Feature의 범위 항목은 완료 판정 가능한 사용자 동작으로만 작성한다.
- 기술 구현 방식(API 형태, DB 구조, 프레임워크, 테스트 분해 등)은 WBS에서 결정하지 않는다. 해당 결정은 `$sd-plan`에서 다룬다.

#### 의존성 판단 절차

의존성은 아래 두 종류를 모두 판단한다:

- **(1) 산출물 참조 관계**: 이 Feature의 세부 기능이 다른 Feature가 만든 산출물(API, 컴포넌트, 데이터 구조, 서비스, 모듈 등)을 직접 사용하는 경우.
- **(2) 결정 파급 관계**: 다른 Feature에서 내려지는 결정(명명 규칙, 공통 패턴, 분기 구조, 공유 용어 등)이 확정되지 않으면 이 Feature의 내용이 변할 수 있는 경우.
  - "코드 간 import 없음"이 의존성 없음을 의미하지 **않는다**. 결정 파급은 문서·규칙·명명 수준에서 더 흔히 발생한다.

**판단 절차 (후보 풀 → 제거 방식):**

1. **후보 풀 전수 나열**: 다른 모든 Feature 번호를 후보로 나열한다.
2. **제거 판단**: 각 후보에 대해 "이 Feature와 완전히 무관함을 증명할 수 있는가?" 산출물·결정·도메인 엔터티 중 하나라도 겹칠 가능성이 있으면 제거하지 않는다.
3. **잔류 = 의존성**: 제거되지 않은 번호를 의존성에 기록한다.

**CRITICAL: 기본값은 "의존 있음". 판단이 머뭇거려지면 잔류시킨다.** 과소 설정(병렬 수행 시 블로킹·재작업)이 과대 설정(약간의 직렬화)보다 비용이 크다.

---

각 Feature의 세부 사항을 분류하고 `$sd-inner-clarify` 스킬을 호출하여 불명확한 부분을 명확화한다.
- **나쁜 예:** "예약 기능 포함이 결정됨 → 예약 세부규칙(대기열 정책, 미대출 시 자동취소 기간)도 확정" — 기능 포함 여부와 세부 수치/규칙은 별개다. 세부사항은 별도로 분류·질문한다.

### Feature-Deliverable 역추적 강제 규칙

**CRITICAL: 모든 Feature는 Impact Mapping의 특정 Deliverable에서 유래해야 한다. 근거란에 유래 Deliverable을 명시(인용)하지 못하는 Feature는 추가 금지(NEVER).**

Feature를 작성하다가 "이건 시스템 동작상 당연히 필요하다"는 판단이 드는데 Impact Mapping Deliverable로 역추적 불가한 경우(예: 사용자 계정 관리, 권한 설정, 로그, 알림 설정 등 Impact Mapping에는 없지만 실행에 필요해 보이는 기능):

1. **절대 혼자 추가하지 않는다(NEVER).** "당연히 필요하다"는 추측으로 Feature를 임의 추가하거나 제외 사항에 자체 결정을 기재하는 것은 금지.
2. **반드시 `$sd-inner-clarify`를 호출**하여 해당 기능을 포함할지 질문한다. 질문 형식:
   - 결정 대상: "{기능명}"을 시스템에 포함할지
   - 선택지: 포함 / 미포함 / 수행 안 함
3. **포함으로 결정되면** Step 2로 돌아가 Impact Mapping에 해당 Deliverable을 먼저 추가한 뒤, Feature를 작성한다.
4. **미포함으로 결정되면** "제외 사항"에 기재하고 Feature는 만들지 않는다.

**판단 체크:** Step 3을 마치기 전, 모든 Feature의 근거란을 훑어 **"Impact Mapping Deliverable: ..."** 인용이 **반드시** 1건 이상 존재하는지 확인한다. 없는 Feature가 있으면 위 1~4 절차로 처리한다.

## Step 4: 자가검증 (Self-Refine)

1차 산출된 WBS를 아래 관점으로 **MUST** 재검토하고, 필요 시 **분할·병합·순서조정·보완**을 수행하여 최종 WBS를 확정한다.

### 검증 관점

1. **Feature 크기** — Step 3 "Feature 분리 규칙"의 판단 기준에 따라, 과도하게 큰 Feature는 기본→확장 패턴으로 분할한다.
2. **의존성 순서** — 의존 대상이 뒤 번호에 있거나 같은 단계 내에 있으면 번호/순서를 재정렬한다.
3. **중복/누락/역추적** — 요구사항(Impact Mapping의 Deliverable) 대비 양방향 커버리지를 점검한다.
   - 여러 Feature가 같은 세부 기능을 중복으로 갖고 있으면 하나로 통합하거나 경계를 명확화.
   - **정방향 (Deliverable → Feature):** 요구사항에 있는데 어떤 Feature에도 없는 항목은 추가하거나 "제외 사항"으로 사유와 함께 이동.
   - **역방향 (Feature → Deliverable):** 역추적 불가한 Feature는 Step 3 "Feature-Deliverable 역추적 강제 규칙"에 따라 처리한다.
4. **Feature 독립성 (단일 책임)** — 한 Feature의 이름과 실제 범위가 일치하는지 확인한다. 이름에 드러나지 않는 일을 몰래 수행하면 분리한다.
5. **병합 규칙 준수** — Step 3 "Feature 병합 규칙"의 기계적 판정 규칙을 위반하는 Feature가 없는지 확인한다.
6. **범위 항목의 검증 가능성** — 각 세부 기능이 완료 판정 가능한 구체적 표현인지 확인한다. "개선한다", "최적화한다" 같은 모호한 표현은 구체 동작으로 재작성한다.
7. **미확정 요구 제거** — "후속 확정", "보류", "추후 결정", "협의 필요" 같은 표현이 Feature 범위/경계/근거에 남아 있으면 확정 질문을 수행하거나 "제외 사항"으로 이동한다.

### 의존성 매트릭스

의존성 매트릭스를 생성하고 다음을 확인한다:

1. **누락 확인**: 각 Feature의 세부 기능이 다른 Feature의 산출물을 참조하거나 결정에 의해 내용이 바뀔 수 있는데 의존성에 빠져 있지 않은지 크로스체크
2. **순환 확인**: A→B→A 같은 순환 의존성이 없는지 확인 (발견 시 Feature 분할로 해소)
3. **1단계 존재 확인**: 의존성이 없는 Feature가 최소 1개 이상 존재하는지 확인

매트릭스 형식:

```
| Feature | 의존 대상 |
|---------|----------|
| 1.1     | 없음      |
| 1.2     | 1.1      |
| 2.1     | 1.1      |
| 2.2     | 1.1, 2.1 |
```

## Step 5: WBS 문서 생성

산출물 경로:

- **입력이 `.tasks/` 내 기존 문서인 경우:** 해당 문서와 같은 폴더에 `wbs.md` 생성 (예: `.tasks/260411_some-project/requirements.md` → `.tasks/260411_some-project/wbs.md`)
- **그 외:** `.tasks/{timestamp}_{topic}/wbs.md`
  - `{timestamp}`: 실제 현재 시각을 `yyMMddHHmmss` 형식으로 기재
  - `{topic}`: 영어 kebab-case (예: `task-management`)

### 문서 템플릿

```markdown
# WBS: {주제 한 줄 설명}

## 프로젝트 개요

- **배경:** [왜 이 프로젝트가 필요한지]
- **환경:** [기존 시스템, 운영 환경, 사용자 규모 등]
- **전제조건:** [프로젝트 시작 전 충족되어야 할 조건]
- **기술적 제약:** [사용자가 언급한 기술 스택, 환경 제약 등]
- **참조 자료:** [프로젝트 전역 참조 파일/문서 경로 — 각 항목에 확인 목적을 명시]

## Impact Mapping

- **Goal:** [측정 가능한 목표]
  - **Actor:** [이해관계자]
    - **Impact:** [행동 변화]
      - **Deliverable:** [산출물]

## Feature Breakdown

### Epic 1. [Epic 이름]

#### [ ] Feature 1.1 [Feature 이름]

**의존성:** 없음

**범위:**

- 열기/닫기
- 배경 클릭으로 닫기

**경계:**

- 애니메이션 효과는 이 Feature에서 다루지 않음

**근거:**

- 요구사항: "팝업 형태로 상세 정보 표시"
- 사용자 답변: "배경 클릭으로 닫기 필요"

## 제외 사항

- [제외 항목]
```

**진행 상황:** Feature별 `[ ]` 체크박스로 진행을 추적한다.

**제외 사항:**

- 현재 범위에서 명시적으로 제외하는 항목과, Impact Mapping에서 Goal에 연결되지 않는 기능을 나열한다.
- 각 항목에 **사유**(Goal 미연결, 사용자 명시적 제외, 범위 초과, 이번 WBS 범위 제외: 미확정 등)를 반드시 기재한다.

## Step 6: 정보 유실 방지 검증

문서 작성 후, 대화에서 수집한 모든 구체적 정보가 문서에 기록되었는지 검증한다.

- 사용자의 답변에 포함된 구체적 수치, 열거 항목, 업무 규칙, 제약 조건이 누락 없이 Feature 근거 또는 프로젝트 개요에 기록되었는가?
- 언급된 참조 파일/문서 경로가 확인 목적과 함께 기록되었는가?
- 누락 발견 시 문서에 반영한 뒤 저장한다.

**CRITIAL: 각 Feature는 새 세션에서 진행되므로, 절대(NEVER) wbs문서에 누락이 있어서는 안됨**

## Step 7: 수행 순서 안내

문서 작성이 완료되면, 의존성을 기반으로 Feature를 단계별로 그룹화하여 수행 순서를 안내한다.

- 의존성이 없는 Feature들을 1단계로 묶는다
- 이전 단계의 Feature에만 의존하는 Feature들을 다음 단계로 묶는다
- 같은 단계 내 Feature는 병렬 수행 가능함을 표시한다
- 각 Feature의 선행 의존성을 `(← ...)` 형태로 명시한다

예시:

```
1단계 (병렬 수행 가능)
  - Feature 1.1: 공통 프로바이더 & 플러그인

2단계 (병렬 수행 가능)
  - Feature 1.2: 홈 레이아웃 & 사이드바 메뉴 (← 1.1)
  - Feature 2.1: 입고 처리 (← 1.1)
  - Feature 2.2: 출고 처리 (← 1.1)
```

## Step 8: 다음 단계 안내

WBS 완료 후, 개발을 위한 다음 단계를 안내한다.

예: `$sd-dev {wbs.md_파일경로} 1.1`
